## 0. 한 줄 요약

**외부 통합은 1개만 하는 게 낫고, 그 1개로는 S3 를 추천한다.** OAuth2 는 서류 키워드로는 최상이지만 이 프로젝트의 서사에 아무것도 보태지 않아서, **"계정 충돌을 어떻게 처리했는가"를 산출물로 잡을 때만** 값이 있다. 푸시·결제·검색은 제외 추천.

## 1. 먼저 — 계획 문서의 단언을 철회한다

[`28-remaining-work-plan.md`](../tasks/28-remaining-work-plan.md) §2-5 원문:

> 구현 %에는 기여가 0이지만 **서류 통과율에는 가장 크게 기여한다.**

**측정한 적도, 출처도 없다.** 채용공고를 세어본 적이 없고 서류 결과 데이터도 없다. 이 문서가 그 자리를 대체한다. 아래 (다) 축의 순위도 여전히 인상 기반이며, 그 사실을 §6 에 남긴다.

## 2. 평가 프레임 — Redis 때 쓴 프레임을 그대로 쓰면 안 된다

[`redis-introduction.md`](./redis-introduction.md) 는 **(A) 정확성 / (B) 성능 / (C) 확장성** 셋 중 하나를 충족해야 도입을 정당화하는 엄격한 프레임을 세웠다. 그 프레임은 *"MySQL 로 안 되는가"* 를 묻는다.

**외부 통합에는 그대로 못 쓴다.** 후보 대부분은 기술적으로 "필요"하지 않고, 필요하게 만들려면 **기능을 먼저 만들어야** 한다. 그래서 축을 바꾼다.

| 축 | 묻는 것 |
|---|---|
| **(가) 기능 필요성** | 이미 있는 기능이 이걸 요구하는가, 아니면 통합을 위해 기능부터 새로 만들어야 하는가 |
| **(나) 서사 적합성** | DB 포폴 축(쓰기·읽기)과 이어지는가 ([`db-portfolio-roadmap.md`](./db-portfolio-roadmap.md)) |
| **(다) 서류 키워드** | JD 등장 빈도 — ⚠️ 미측정 |
| **(라) 면접 깊이** | "왜 이렇게 했나요"에 답할 거리가 있는가 |
| **(마) 비용** | 시간 + 외부 콘솔(압축 안 됨) + 금전 |

**원칙**: (가)가 0 인 항목은 문서에 *"키워드용"* 이라고 적고 간다. 면접에서 "왜 넣었냐"에 "키워드 때문"이라고는 답할 수 없으므로, **(가)가 0 이면 (라)가 있어야만 산다.**

## 3. 후보별 분석

### 3-1. S3 🟢

**현 상태 — 하려던 흔적이 코드에 두 군데 남아 있다.**

| 사실 | 근거 |
|---|---|
| `S3_UPLOAD_ERROR(500, "W004", "파일 저장소(S3) 연결에 실패했습니다.")` — **에러코드만 있고 구현이 없다** | `ErrorCode.java:33`, 사용처 grep **0건** |
| `members.profile_image_url VARCHAR(500)` — **컬럼·엔티티 필드가 있는데 읽지도 쓰지도 않는다** | `mysql/schema.sql:16`, `Member.java:34` (필드 선언 외 사용처 0건) |
| 바이너리를 다루는 경로가 **지금 하나도 없다** | 영상은 전부 URL 문자열 (`preferred_url`, `exercise_sessions.reference_source` — 둘 다 `VARCHAR(500)`) |

⚠️ **가장 그럴듯한 후보 하나는 이미 기각돼 있다.** `pose_data` 아카이빙 — `PoseDataPartitionScheduler.java:28`:

> 아카이빙 없음(완전 폐기). **S3 이전은 개인정보보호법 제21조 "지체없이 파기" 취지에 안 맞아 제외.**

즉 "대용량 시계열을 S3 로 내린다"는 서사는 **쓸 수 없다.** 남는 건 프로필 이미지 / 운동 영상 업로드 쪽이다.

| 축 | 평가 |
|---|---|
| (가) 기능 필요성 | **중** — 프로필 이미지는 *컬럼이 이미 있으니* 기능 신설이 아니라 **빈칸 채우기**다. 다만 앱에 업로드 UI 가 없어 프론트 작업이 동반된다 |
| (나) 서사 | **상** — "왜 DB BLOB 이 아니라 오브젝트 스토리지인가", 원본/썸네일 분리, 수명주기 정책. DB 축과 그대로 이어진다 |
| (다) 키워드 | **중~상** |
| (라) 깊이 | **상** — 아래 |
| (마) 비용 | **8~14h 추정** (프론트 업로드 UI 제외). 프리티어 범위, 콘솔 작업 있음 |

**(라)가 강한 이유** — presigned URL 로 클라가 S3 에 직접 올리면 **"DB 행은 없는데 객체는 올라간 / 객체는 없는데 행은 있는" 정합성 문제**가 생긴다. 이건 **이미 구현한 outbox 와 같은 구조의 문제**다([`outbox-reliable-messaging.md`](./outbox-reliable-messaging.md)). "같은 문제를 다른 자원에서 다시 만났고, 같은 도구로 풀었다/다르게 풀었다"는 면접 서사가 된다. 그냥 서버 경유 업로드로 끝내면 이 깊이는 안 나온다.

### 3-2. OAuth2 🔶

> 📌 **2026-08-08 추가** — "한다면 무엇이 걸리는가"는 [`oauth-implementation-considerations.md`](./oauth-implementation-considerations.md) 로 분리했다. ⚠️ 그 조사에서 **아래 표의 판단 하나가 틀렸음이 드러났다**: `refresh_token` 테이블이 있어 *"토큰 저장소는 재사용 가능 — 비용을 낮춘다"* 고 봤지만, **재발급 엔드포인트가 통째로 없어서**(컨트롤러 grep 0건) 회전 로직은 0 에서 시작한다. 아래 (마) 비용 10~13h 는 그만큼 낮게 잡혀 있다.

**현 상태 — 스키마가 소셜 전용 계정을 막고 있다.**

| 사실 | 근거 | 함의 |
|---|---|---|
| `members.password VARCHAR(255) **NOT NULL**` | `mysql/schema.sql:12` | 소셜 전용 계정을 **만들 수 없다.** nullable 마이그레이션 vs 더미 패스워드 중 택1 강제 |
| `email VARCHAR(100) **UNIQUE** NOT NULL` | `mysql/schema.sql:11` | 같은 이메일로 소셜 로그인할 때 **충돌 지점이 정확히 여기** |
| `refresh_token` 테이블 존재 | `mysql/schema.sql:30~` | 토큰 저장소는 재사용 가능 — 이건 비용을 낮춘다 |
| provider / social 컬럼 없음 | grep 0건 | 신설 필요 |

| 축 | 평가 |
|---|---|
| (가) 기능 필요성 | **0** — 지금 인증은 동작한다. 순수 추가다 |
| (나) 서사 | **하** — DB 축과 무관. 굳이 잇는다면 계정 병합의 트랜잭션·유니크 제약 정도 |
| (다) 키워드 | **최상** (⚠️ 미측정, §6) |
| (라) 깊이 | **중** — 라이브러리가 대부분 처리한다. 깊이가 나오는 건 딱 두 곳: ① **기존 email/password 계정과 소셜 계정의 충돌** (위 `NOT NULL`·`UNIQUE` 제약이 그대로 걸린다) ② refresh token 회전·저장 |
| (마) 비용 | **10~13h 추정** + 외부 콘솔(앱 등록·리다이렉트 URI) — 이 부분은 **압축되지 않는다**([`28`](../tasks/28-remaining-work-plan.md) §3) |

**결론**: (가)가 0 이므로 (라)로만 정당화된다. 그런데 (라)의 실체는 OAuth 자체가 아니라 **계정 충돌 처리**다. 그래서 이 항목은 *"소셜 로그인을 붙였다"* 가 아니라 **"기존 계정과 충돌할 때 자동 병합 / 거부 / 명시적 연동 중 무엇을 왜 골랐는가"** 를 산출물로 잡을 때만 값이 있다. 그게 아니면 시간만 쓰고 남는 게 없다.

### 3-3. 푸시 알림 (FCM) ❌

알림 기능 자체가 없다. 만들려면 **"무엇을 알릴지"부터** 정해야 하는데:

- 세션 타임아웃 → 이미 스케줄러가 조용히 처리, 알릴 가치 낮음
- 리포트 완료 → **precompute-on-write 라 즉시 생성**된다. 알릴 시차가 없다

게다가 실사용자가 0 이라 **받을 사람이 없다.** (가)·(라) 둘 다 0.

### 3-4. 결제 ❌ / 검색(Elasticsearch) ❌

- **결제**: 도메인에 유료 기능이 없다. 만들면 억지고, 면접에서 "왜 붙였나"에 답이 안 나온다
- **검색**: 운동 종목이 3개(스쿼트·런지·플랭크, 그중 분석 지원은 스쿼트뿐) 규모다. ES 에 넣을 데이터가 없다. 관리자 회원 검색은 **MySQL + QueryDSL 로 충분**하고 그건 이미 [#3 항목](../tasks/28-remaining-work-plan.md)에 있다

### 3-5. Redis — 이 문서가 다루지 않는다

[`redis-introduction.md`](./redis-introduction.md) 가 **CLOSED(도입 보류 박제, 2026-05-25)** 이고 T1~T5 트리거 발생 시 재검토로 정해져 있다. **이 문서는 그 결정을 뒤집지 않는다.** 관리자 페이지 도입 시 카탈로그 캐싱이 트리거에 해당하는지는 *그 문서의 기준으로* 판단할 일이다.

⚠️ **다만 문서 간 충돌을 박제해 둔다**: [`portfolio-benchmark.md`](./portfolio-benchmark.md) 는 Redis 를 **"채울 키워드(서류용)"** 로 지목했고, `redis-introduction.md` 는 **"근거 없는 도입은 면접에서 들킴"** 으로 보류했다. 두 문서가 반대 방향을 가리킨다 — 이 충돌은 아직 해소되지 않았다.

## 5. 추천

**1순위 — S3 (프로필 이미지 + presigned URL 직접 업로드).** 근거 셋:
1. 코드에 **이미 자리가 비어 있다**(`W004`, `profile_image_url`) — 새 개념을 안 들여온다
2. **DB 축과 이어진다** — "왜 DB 에 안 넣는가"가 그대로 질문거리
3. **outbox 와 같은 구조의 정합성 문제**를 다른 자원에서 다시 만난다 → 기존 강점과 연결되는 유일한 후보

**2순위 — OAuth2, 조건부.** 계정 충돌 처리를 산출물로 못 잡으면 하지 않는 게 낫다.

**하지 않기** — 푸시·결제·검색.

⚠️ **두 개 다 하면 18~27h** 로 [#3(관리자 페이지) 전체](../tasks/28-remaining-work-plan.md)와 맞먹는다. **외부 통합은 1개만 하는 걸 권한다** — "다양성 0"이라는 지적은 1개로 해소되고, 2개째부터는 같은 종류의 신호가 중복된다.

## 6. 정직 단서

- ⚠️ **(다) JD 등장 빈도는 측정하지 않았다.** 채용공고를 세어본 적이 없고 인상에 기반한 순위다. **뒤집힐 수 있고, 뒤집히면 S3 vs OAuth2 결론도 흔들린다**
- **"외부 통합 0개가 약점"이라는 진단 자체**도 [`25-portfolio-strategy.md`](../tasks/25-portfolio-strategy.md)의 자체 판단이고 채용 담당자에게 확인받은 게 아니다
- S3 비용 8~14h 는 **프론트 업로드 UI 를 제외한 값**이다. 이 프로젝트는 프론트도 본인 몫이라 실제로는 더 든다
- **AWS 프리티어 잔여 여부를 확인하지 않았다.** EC2 실험([`27-implementation-gaps.md`](../tasks/27-implementation-gaps.md) §4)에서 이미 사용한 이력이 있다
- 시간 추정은 전부 **추정이고 실측이 아니다**
