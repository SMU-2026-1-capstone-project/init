# 글루 코드 경량화 — orjson 스왑이 프로세스 1개 처리량을 올리나 (2026-09-02)

작성일: 2026-09-02
상태: 🟢 **N=1·N=3 둘 다 완료, N=3은 8판씩(17판)으로 재확인까지 끝남.** N=1(박스 61% 사용,
여유 있음)에서는 rps +7.86%(226.2 → 244.0), p50 −6.88% — 16판 전부 방향 일관·안 겹침.
**N=3(박스 96% 포화, 실배포 조건)에서는 rps +1.09%, p50 −2.78%로 폭은 확 줄지만, 8판씩
재확인한 결과 이번엔 통계적으로도 확실하다**(Welch t=13.24 / −11.29) — §5-1 참고.
**"8% 빨라진다"는 N=1 한정 문장이고, 실배포 체감은 "작지만 확실하게 1~3% 수준"이 정직하다.**

---

## 0. 한 줄

프로세스 1개가 9.5~9.8 vCPU에서 막히는 원인(GIL)은 프로세스 분리로만 우회했고, **파이썬 구간
자체를 줄이는 길은 안 가봤다** — 여기서 가봤다. `json.dumps/loads` + 기본 응답 직렬화를
`orjson`(Rust 코어)으로 바꿨더니 **같은 프로세스 1개가 8% 더 처리한다.**

---

## 1. 왜 — 손 안 대던 자리

`pose.py`의 요청 경로는 파싱 → 검증 → (MediaPipe 추론) → 직렬화 순이다. MediaPipe는 C++이라
GIL을 놓지만, 앞뒤의 순수 파이썬 글루 코드(JSON 파싱·Pydantic 검증·base64 디코드·응답 직렬화)는
GIL에 그대로 걸린다. `per-process-ceiling-cause.md`는 이 글루 코드를 "줄이는 길이 별도로
열린다"고만 적어두고 실행하지 않았다 — `pose.py`가 팀원 코드라 면적을 최소화하려던 판단이었다.

이번엔 실제로 줄여서, 프로세스 1개의 처리량 천장(9.5~9.8 vCPU) 자체가 움직이는지 쟀다.

---

## 2. 뭘 바꿨나 — 면적 2파일

- `ai-server/requirements.txt`: `orjson==3.10.18` 추가
- `ai-server/app/api/endpoints/pose.py`:
  - `router`에 `default_response_class=ORJSONResponse` — 기본 응답 직렬화 경로
  - `_landmarks_to_json`: `json.dumps` → `orjson.dumps(...).decode()`
  - BACK_BENT 판정부: `json.loads`/`json.JSONDecodeError` → `orjson.loads`/`orjson.JSONDecodeError`
  - 측정용 raw 응답 분기: `JSONResponse` → `ORJSONResponse`

**판정 로직은 한 줄도 안 건드렸다.** 160 pytest 전부 통과(52 subtests 포함).

## 5. N=3 재검증 (2026-09-02, 두 번째 라운드) — 🔴 효과가 확 줄어든다

**왜 다시 쟀나**: §4는 프로세스 1개 조건이다. 실배포는 N=3(`entrypoint.sh`, `AI_WORKER_COUNT=3`).
프로세스가 늘수록 요청당 GIL 대기가 늘어나는 효과(`per-process-ceiling-cause.md` §9-4)와
겹칠 수 있어서, N=1의 +7.86%를 그대로 실배포에 인용하면 안 된다는 게 §5(구판)의 경고였다.

### 무대

proc-count-sweep과 같은 방식(`run_sweep.sh`)을 재사용했다 — 프로세스 K개 = rig K개, 세션·풀을
K등분해서 각자 자기 서버 하나를 몬다.

| | |
|---|---|
| 박스 | `c7i.4xlarge` 1대(16 vCPU), N=1 판과 다른 인스턴스(같은 날) |
| 부하 | 합계 세션 160(53×3) · 합계 풀 201(68×3) · 3.0fps · 판당 90초 · **프로세스 3개 고정** |
| 팔 | **main** vs **orjson** — 9라운드(버림 1 + 4×2), ABAB로 교대해 시간 편향 최소화 |
| 계측 | `run_arms.py`에 이미 내장된 `CpuSampler`(1초 간격 `/proc` 샘플링)를 이번엔 실제로 읽었다 |

### 결과

| | main | orjson | 차이 |
|---|--:|--:|--:|
| rps(3프로세스 합), n=4 | 380.8 (cv 1.20%) | 387.0 (cv 1.51%) | **+1.62%** |
| p50(3프로세스 평균) | 408.9ms | 401.9ms | -1.71% |
| AI CPU 합(vCPU) | 15.18 (cv 0.11%) | 15.25 (cv 0.14%) | **+0.44%** |
| 박스(16 vCPU) 대비 | 94.9% | 95.3% | — |
| rps/vCPU(효율) | 25.09 | 25.39 | +1.17% |

```
rps    +1.62%   산포 합 2.71% 보다 작다 → 이 4판만으론 우연과 구분 안 됨 (Welch t=1.67)
p50    -1.71%   산포 합 3.34% 보다 작다 → 마찬가지로 산포 안 (Welch t=-1.46)
AI CPU +0.44%   산포 합 0.25% 의 약 1.8배 → 작지만 방향은 확실 (Welch t=5.01)
```

🔑 **왜 N=1(+7.86%)보다 훨씬 작아지나 — 박스가 이미 거의 다 찼기 때문이다.** N=1은 박스의
61%만 썼다(§4 아래 결과 연결 — `ai-glue-code-orjson` N=1 무대는 61%). N=3은 이미 95% 근처를
쓰고 있어서, 요청 하나의 처리 비용을 줄여도 그걸 밀어넣을 빈 코어가 남아 있지 않다. proc-count-sweep이
밝힌 "N=3에서 박스 98% 포화"와 같은 자리다 — orjson이 코드 레벨에서 하는 일(글루 코드 축소)은
그대로지만, **그 절약분을 처리량으로 바꿀 여유 자체가 없다.**

**결론(4판 시점, §5-1로 갱신됨)**: 프로세스 1개(여유 있는 조건)에서는 크게(+7.86%), 실배포
N=3(포화 조건)에서는 미미하게(+1.62%, 이 4판만으론 통계적으로 불확실) 돕는다. 판 수를
늘려서 확실히 하는 게 다음 순서였다 — §5-1.

## 5-1. N=3, 8판씩 재확인 (2026-09-02, 세 번째 라운드) — 🟢 작지만 이제 확실하다

**왜 다시 쟀나**: §5의 4판은 방향(orjson이 근소 우위)은 맞았지만 Welch t=1.67로 우연과 못
갈랐다. 판을 8판씩(버림 1 + 16판 = 17라운드)으로 늘려 재확인했다 — 무대·부하 조건은 §5와
동일, **다른 EC2 인스턴스**(같은 `c7i.4xlarge`지만 박스 캘리브레이션이 달라 절대값은
§5와 직접 비교 못 한다 — 라운드 안 상대 비교만 유효, `round-to-round-nonreproducibility.md`
가 이미 경고한 자리).

| | main | orjson | 차이 |
|---|--:|--:|--:|
| rps(3프로세스 합), n=8 | 414.98 (cv 0.15%) | 419.49 (cv 0.18%) | **+1.09%** |
| p50(3프로세스 평균) | 359.2ms | 349.2ms | **-2.78%** |
| AI CPU 합(vCPU) | 15.40 (cv 0.08%) | 15.44 (cv 0.08%) | +0.25% |
| rps/vCPU(효율) | 26.95 | 27.17 | +0.83% |
| 박스 대비 | 96.2% | 96.5% | — |

```
rps    +1.09%   산포 합 0.32% 의 3.4배   Welch t=13.24   ← 명확히 유의
p50    -2.78%   산포 합 1.00% 의 2.8배   Welch t=-11.29  ← 명확히 유의
AI CPU +0.25%   산포 합 0.16% 의 1.6배   Welch t=6.35    ← 유의
```

🔑 판을 늘리니 판 간 산포가 확 줄었다(rps cv 1.2~1.5% → 0.15~0.18%) — main 8판 최댓값(415.84)이
orjson 8판 최솟값(417.92)보다 여전히 작아 16판 전체가 안 겹친다.

**최종 결론**: N=3(실배포 조건)에서 orjson 효과는 **작지만 통계적으로 확실하다** — 처리량
+1.09%, 지연 -2.78%. §5의 "불확실하다"는 판정은 판 수 부족 때문이었지 방향이 틀렸던 게
아니었다. "orjson으로 8% 빨라진다"는 여전히 N=1 한정 문장이고, 실배포에서 정직하게 말할 수
있는 문장은 **"처리량은 소폭(1%대), 지연은 그보다 뚜렷하게(3%대) 개선되고, 둘 다 통계적으로
확인됐다"**이다.

## 6. 이 판이 확정한 것과 안 한 것

- ✅ **글루 코드 경량화가 처리량을 올린다 — 박스 여유에 비례한다.** N=1(박스 61%)에서 +7.86%,
  N=3(박스 96%)에서 +1.09% — 둘 다 통계적으로 확실(§5-1로 N=3도 확정)
- ✅ **판정 로직 무변경** — 면적 2파일, pytest 160판 통과
- ✅ **N=3 CPU 사용량도 확인함** — orjson이 CPU를 살짝 더 쓰면서(+0.25%) 처리량은 더 늘려
  (+1.09%) rps/vCPU 효율이 +0.83% 개선. "천장 자체가 움직였다"기보다 "같은 포화 상태에서
  효율이 조금 낫다"가 정확한 표현
- 🔴 **더 큰 글루 코드 경량화(Pydantic 검증 스킵, 배치 등)는 안 건드렸다** — orjson은 그중
  가장 싸고 안전한 한 수였다
- 🔴 **N=1의 CPU 사용량은 아직 안 걷었다** — §4는 rps·p50만 봤다. "9.5→? vCPU" 형태로 직접
  비교하려면 N=1도 CpuSampler로 다시 재야 한다

## 7. 덤 — 측정 중 잡은 버그

`run_arms.py`가 `--remote-target` 없이(이 판처럼 동거 라운드로) 돌면 `AI` 전역변수가 끝까지
`None`으로 남아 `wait_health()`가 매판 예외를 삼키고 "기동 실패"만 찍는다 — 서버는 실제로
떠서 `/health`가 200을 주는데도 그렇다. R10-b(`--remote-target` 추가, #649)가 non-remote
분기의 `AI` 할당을 빠뜨린 회귀. 커밋 [`5638a915`](https://github.com/Shadowfit/init/commit/5638a91549c81b730fd225b1e7eacd7fa60df299)로 고쳐서 이 판에 반영했다 — main에는 아직 안 올라갔다.
