## 1. 기능 정의

트레이너(또는 물리치료 전문가)가 담당 사용자의 운동 세션을 **실시간으로 지켜보며**, 위험 자세·피로 징후를 세션이 끝나기 전에 파악할 수 있게 하는 기능. 원 브레인스토밍의 "위험 자세가 반복될 경우 트레이너에게 리포트 전달"을 사후 배치에서 실시간 관찰로 격상한 버전.

**관계 형태는 1:1** — 각 배정 관계는 트레이너 한 명이 담당 사용자 한 명의 세션을 보는 것. (여러 사용자를 동시에 보는 대시보드로 확장할 수도 있지만, 그건 "1:1 구독을 여러 번" 하는 것과 같아 N:N 브로드캐스트 조율([`multiuser-realtime-sync.md`](./multiuser-realtime-sync.md) §2)이 필요한 문제와는 다르다.)

> ✅ **확정(2026-08-30, 사용자 confirm)**: "1:1"은 **배정 관계 하나하나가 1:1**이라는 뜻이지, 트레이너가 사용자 한 명만 담당한다는 뜻이 아니다 — **사용자당 담당 트레이너는 1명(유니크), 트레이너 한 명은 여러 사용자를 담당할 수 있다**(물리치료사·코치가 여러 회원을 보는 현실적 모델). `trainer_assignments` 테이블은 이 방향으로 구현됐다(`user_id`에 유니크 제약, `trainer_id`엔 없음 — §8 세션1).

## 2. 왜 SSE인가 — 후보 기술 비교

| 후보 | 채택 여부 | 이유 |
|---|---|---|
| **gRPC(-Web)** | ❌ | 트레이너 클라이언트는 브라우저 — gRPC는 브라우저 네이티브 지원 없음. gRPC-Web은 프록시(Envoy 등)가 별도로 필요하고, 그마저 이 케이스처럼 server-streaming만 필요하면 굳이 그 복잡도를 감수할 이유가 없음. (참고: [`multiuser-realtime-sync.md`](./multiuser-realtime-sync.md)의 양방향 케이스는 gRPC-Web이 bidi-streaming 자체를 지원 안 해 원천 배제됨) |
| **WebSocket** | ❌(과함) | 이 기능은 **서버→트레이너 단방향**. 양방향이 필요 없는데 WebSocket을 쓰는 건 "실시간=무조건 WebSocket"이라는 흔한 오판 |
| **WebFlux + SSE** | ❌(불필요) | 현재 규모(DAU 1,000, 동시 세션 67.5)에서는 리액티브 스택 전체 전환(JPA→R2DBC 포함)의 이득이 없음 — 스택 전체 재작성 대비 이득 없음 |
| **Spring MVC + `SseEmitter`** | ✅ | 브라우저 `EventSource`로 네이티브 지원, 기존 Spring MVC(블로킹, JPA) 스택 위에 그대로 추가 가능, 별도 프록시·인프라 불필요 |

## 3. 필요한 기술 구조

```
사용자(프레임 폴링, 기존 그대로) → AI서버 → gRPC 콜백(SavePoseDataBatch, 기존 그대로)
                                              │
                                              ▼
                                    PoseDataService에 중계 훅 추가
                                              │
                                              ▼
                          트레이너 연결 레지스트리에서 담당 emitter 조회
                                              │
                                              ▼
                              SseEmitter.send() → 트레이너 브라우저(EventSource)
```

**AI 서버·기존 프레임 폴링 경로는 코드 한 줄도 안 바뀐다** — 이미 나오는 콜백 데이터를 저장과 별개로 한 번 더 중계하는 것뿐.

### 3.1 중계 세분화 수준 — rep 단위(이 문서의 기본안) vs 프레임 단위(정밀 확장)

위 §3 구조는 **`SavePoseDataBatch`에 얹어가는 rep 단위 중계**다. `pose.py`의 `state.current_rep_frames`가 프레임을 버퍼링하다 rep이 완성(각도가 앉음→섬 왕복)돼야 gRPC로 한꺼번에 전송되므로, 트레이너는 **rep 하나(2~3초)가 끝나야 그 결과를 한 번에** 받는다 — 진행 중인 움직임의 실시간 관전이 아니라 "완료된 rep 리플레이"에 가깝다.

**"rep이 끝나기 전에 프레임 단위로 실시간 관전"이 요구사항이 되면**, 중계 지점을 버퍼링 이전(프레임이 분석되는 그 순간)으로 끌어올려야 한다. 단, 기존 `SavePoseDataBatch`를 프레임마다 부르면 DB 쓰기도 프레임마다 일어나 **원래 배치 설계(rep당 20~30행 한 번에 쓰기)의 효율이 깨진다.** 그래서 실제 구현은 **두 경로를 분리**하는 것이 맞다:

```
프론트 → AI서버 /pose → MediaPipe 분석
                              ├─(기존, 안 바뀜) current_rep_frames 버퍼링 → rep 완성 시 배치 gRPC → DB 저장
                              └─(신규) 프레임마다 "현재 각도·국면"만 담은 가벼운 알림 → Spring → 트레이너 SSE
```

이러면 DB 쓰기 패턴(배치 효율)은 그대로 두고 트레이너만 프레임 단위로 실시간 관전할 수 있다. **이 신규 경로가 §8 구현 계획에는 아직 없다** — §8은 rep 단위(기존 콜백에 얹는 안)를 기준으로 추정한 것이고, 프레임 단위로 확장하면 별도 gRPC 콜(또는 스트리밍 RPC) 설계·구현이 추가로 필요하다(추정 미포함).

**"위험 자세 즉시 경고"는 누구에게 경고하느냐로 답이 갈린다**:
- **운동 중인 사용자 본인**에게 경고 → 이미 지금 구조로 된다. 프론트가 330ms마다 `/pose`에 보내고 그 응답을 바로 받으므로, AI서버가 그 응답에 "위험" 플래그만 넣으면 끝 — Spring도 gRPC도 거치지 않는다.
- **트레이너(다른 화면)**에게도 즉시 알려야 한다면 → 위 프레임 단위 중계 경로가 그대로 필요하다.

즉 이 기능은 "즉시성"의 범위를 어디까지 잡느냐(rep 단위로 충분한가, 프레임 단위가 필요한가, 대상이 트레이너뿐인가 사용자 본인도 포함인가)에 따라 규모가 달라진다 — §8은 **rep 단위(가장 작은 범위)** 기준이다.

> ✅ **확정 (2026-08-30, 사용자 confirm)**: **rep 단위로 진행한다.** 프레임 단위 확장(위 신규 경로)은 보류 — "트레이너가 지연 없이 실시간으로 보는 것"이 이 기능의 핵심 가치라는 근거가 따로 없는 한 착수하지 않는다. §8의 구현 계획(17~19h)이 그대로 이 기능의 범위다.

## 4. 난이도·리스크 분해

CRUD와 다른 종류의 어려움이 새로 생긴다 — "요청 하나 처리하고 끝"이 아니라 **연결을 오래 유지하는 것 자체**가 실패 모드를 만든다:

| 항목 | 내용 |
|---|---|
| 연결 생명주기 | 트레이너가 화면을 꺼도 서버가 그 연결을 정리해야 함 (`onCompletion`/`onTimeout`/`onError`) |
| 백프레셔 | AI가 트레이너 클라이언트보다 빠르게 결과를 낼 때 어떻게 밀어낼지(큐잉 vs 드롭) 결정 필요 |
| 권한 체크 | 아무 트레이너나 아무 세션이나 못 보게 — 🔴 **정정(2026-08-30)**: `Member.role` 필드는 이미 있었다(USER/ADMIN, `VARCHAR(20)`). 실제로 없던 건 `TRAINER` 값과 "누가 누굴 담당하는가"를 기록하는 배정 관계였다 — 세션1에서 해결(아래 §8) |
| 인스턴스 확장 시 | 나중에 인스턴스를 늘리면 "어느 인스턴스가 이 트레이너 연결을 들고 있나" 문제 — [`ai-sticky-routing.md`]와 같은 종류지만 **1:1이라 훨씬 단순한 버전** |

**[`multiuser-realtime-sync.md`](./multiuser-realtime-sync.md)와 비교**:

| | 트레이너 모니터링(SSE) | 다중사용자 동기화(WebSocket) |
|---|---|---|
| 관계 형태 | 1:1 | N:N |
| 방향 | 단방향 | 양방향 |
| 새 인프라 컴포넌트 | 없음(기존 Spring MVC 위에 추가) | Redis(현재 이 프로젝트에 없음) 신규 도입 필요 |
| 추정 공수(Claude 병행) | ≈17~19h | ≈27~35h |
| 혼자 감당 가능성 | 가능 | 리스크 큼 |

## 5. 포지셔닝과의 정합성

이 프로젝트는 "한 기능을 DB·인프라 레벨까지 깊게 판다"는 방향으로 포지셔닝돼 있다([[project_db_portfolio_direction]]). 이 기능은:
- DB 축은 아니지만(새로운 실시간 시스템 축을 연다), **범위가 1:1로 통제 가능**해 다중사용자 동기화만큼 방향을 크게 벗어나지 않는다
- "연결 생명주기·백프레셔·권한 체크"라는, 지금 프로젝트에 완전히 없던 새로운 종류의 엔지니어링 판단을 보여줄 수 있어 순수 CRUD(Goal·추천)보다 차별화 효과가 크다
- 기존 브레인스토밍("전문가 연계형 보조 서비스")의 자연스러운 심화라 완전히 새 기획을 얹는 것도 아니다
