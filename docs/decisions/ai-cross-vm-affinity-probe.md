## 0. 한 줄

**프로덕션 코드는 0줄도 안 바뀐다.** `session_id % N`으로 백엔드를 고르는 로직은
`ai-sticky-routing-probe.md`에서 이미 정확성·배정 균형까지 검증됐다 — 거기선 백엔드
셋이 **같은 박스의 다른 포트**였다. 이번엔 그 셋을 **다른 박스(진짜 네트워크 경계)**로
바꿨을 때도 같은 결론이 서는지, 그리고 그 위에 **VM 하나가 죽으면 다른 VM 세션은
안전한가**(장애 격리)를 하나 더 본다. `ai-horizontal-scaling.md` §5-1의 추천(클라이언트
사이드 LB)이 "논리적으로 그럴듯하다"에서 "2대로 실제로 확인했다"로 넘어가는 게 이
실험의 유일한 목적이다.

---

## 1. 왜 이 캐비엇이 값이 있나

`ai-sticky-routing-probe.md`가 이미 답한 건 "해시 라우팅 규칙 자체가 옳은가"다(nolease 0,
배정 균형 53/53/54). **안 답한 건 "그 규칙이 네트워크 경계를 넘어서도 그대로 서는가"다**:

- 같은 박스에서는 `127.0.0.1:포트`로 붙어 지연이 사실상 0이었다. VM이 다르면 진짜
  TCP 왕복·DNS/IP 해석이 들어간다 — 어피니티 규칙 자체엔 영향 없어야 하지만, **안
  재봤다는 사실은 남는다.**
- **장애 격리는 아예 새로운 질문이다.** 프로세스 3개짜리 판은 프로세스를 죽이는 실험을
  안 했다 — N 스윕·per-process-ceiling-cause 전부 "정상 동작 중 처리량"만 쟀다. VM
  분리가 실제로 주는 이득(한 VM 장애가 다른 VM 세션에 안 번짐)은 **한 번도 실측된 적
  없다** — `ai-horizontal-scaling.md` 전체가 이 이득을 전제로 ㄴ안을 추천하는데, 정작
  그 전제 자체가 미검증이다.

## 2. 무엇을 재는가 / 안 재는가

| | |
|---|---|
| **잰다 ①** | 세션 N개를 클라이언트가 `session_id % 2`로 VM A/B에 나눠 열었을 때, 모든 프레임이 **항상 배정된 VM으로만** 가는가(`nolease` 0) |
| **잰다 ②** | 🆕 VM A를 강제로 내렸을 때, **VM A에 배정된 세션만** 실패하고 **VM B 세션은 계속 정상 처리**되는가 |
| **안 잰다** | 처리량·성능 비교 — 이건 사이징 질문이 아니라 **정확성·격리** 질문이다. 처리량은 이미 다른 축(N 스윕 등)이 답했다 |
| **안 잰다** | Spring `grpc-java` 리졸버/LoadBalancer의 실제 구현 — `ai-sticky-routing-probe.md`와 같은 이유로 범위 밖(파이썬 클라이언트가 흉내만 낸다) |
| **안 잰다** | 죽은 VM 위 세션의 **복구**(재부착) — 이건 별개 질문이고, 지금은 "다른 세션이 안 다치는가"만 본다. 복구까지 보려면 이 판 다음에 재부착 왕복을 얹는 후속판이 필요하다 |

## 3. 설계

### 3-1. 무대 — 최소 구성

프로세스 내부 다중화(N=3)는 이미 답이 나와 있어서 이 판에서 또 재현할 필요가 없다 —
VM마다 **워커 1개**면 충분하다(어피니티 로직 자체엔 워커 수가 안 걸린다).

| | |
|---|---|
| VM A, VM B | `c7i.large`(2 vCPU) 각 1대 — 워커 1개짜리 목적엔 4xlarge가 과하다, 최소 사양 |
| 부하기 | 별도 `c7i.large` 1대(대상 관측에서 부하기 자원 경합을 뺀다 — R13/R14와 같은 이유) |
| 세션 · fps | 합계 **20세션 · 3.0fps** — 정확성·격리 확인이 목적이라 N 스윕만큼 큰 규모 불필요 |
| 판당 시간 | 짧게 — 세션 시작 확인 + 프레임 몇 장 + (②만) 강제 종료 후 확인, 총 60~90초 |

### 3-2. 팔 둘 — 실은 하나의 판을 2단계로

정적 사전분할/해시 비교(ㄱ↔E)는 이미 닫힌 질문이라 재현하지 않는다. 대신 **정확성**과
**격리**를 순서대로 본다:

| 단계 | 무엇 |
|---|---|
| **① 정확성** | 20세션을 `session_id % 2`로 VM A/B에 나눠 열고, 각 세션이 프레임 몇 장을 보낼 때마다 **어느 VM이 응답했는지**(HTTP 응답의 서버 식별 — `/health`처럼 VM별로 다른 값을 주는 임시 엔드포인트나, 프레임 응답에 실린 워커 식별자 재사용) 기록한다 |
| **② 격리** | ①이 정상 배정된 상태에서 **VM A의 ai-server 컨테이너를 강제 종료**한다. 그 직후 VM B에 배정된 세션들의 프레임 요청이 **여전히 성공**하는지, VM A에 배정됐던 세션들만 실패(연결 거부/타임아웃)로 떨어지는지 확인한다 |

### 3-3. 판정선 (값 보기 전에 못박는다)

| # | 물음 | 판정 |
|---|---|---|
| **ㄱ 정확성** | ①에서 `nolease`/오배정이 0인가 | 0이 아니면 VM 간에서 해시 라우팅이 깨진다는 뜻 — `session_id % 2` 계산이나 클라이언트 쪽 주소 매핑부터 재점검 |
| **ㄴ 격리** | ②에서 VM B 세션의 성공률이 VM A 종료 **전후로 변하지 않는가** | 변하면(예: VM B 세션도 같이 실패하거나 지연이 튀면) "VM을 분리하면 장애가 격리된다"는 `ai-horizontal-scaling.md`의 전제 자체가 흔들린다 — 공유 자원(같은 서브넷의 네트워크 포화 등)이 있는지부터 확인 |
| **ㄷ VM A 세션의 실패 모양** | 타임아웃인가 즉시 거부(connection refused)인가 | 이건 판정이 아니라 **기록** — 다음 후속판(재부착 복구)의 설계에 그대로 쓰인다 |

**"성공률이 변했다/안 변했다"의 기준은 20세션 중 몇 개가 실패했는지 그대로 세는 것**이다
— 이 규모(20세션)에서는 %가 아니라 **절대 개수**로 보고한다(임의 % 기준을 안 만든다,
[[feedback_no_arbitrary_threshold_values]]).

## 4. 만든 것 — 코드 변경 0, 전부 load-test harness

`ai-sticky-routing-probe.md`의 `sticky_rig.py`를 베이스로 두 가지만 바꾼다:

| 무엇 | `sticky_rig.py`(기존) | 이 판(신규) |
|---|---|---|
| 백엔드 주소 | `127.0.0.1:포트` 3개 | **VM A/B의 실제 IP**:고정포트 2개 |
| 추가 기능 | 없음 | ② 단계용: 특정 VM의 컨테이너를 SSH로 내리는 오케스트레이터 훅 |

⚠️ **ai-server 코드는 안 건드린다** — `session_id % 2`는 rig(클라이언트) 쪽 로직이고,
서버는 그냥 평소처럼 gRPC/HTTP를 받는다.

## 6. 이 실험이 답하지 못하는 것 (미리 박제)

- **복구(재부착)** — VM A가 죽은 뒤 그 위 세션들을 VM B(또는 재기동된 VM A)로 되살리는
  것은 이 판의 범위가 아니다. 이 판은 "VM B가 안전한가"만 본다
- **처리량/사이징** — 이미 다른 축이 답했다(§2)
- **실제 Spring `grpc-java` 리졸버 구현** — `ai-sticky-routing-probe.md`와 같은 이유로
  범위 밖
- **동시에 여러 VM이 죽는 경우** — 이 판은 VM 하나만 내린다
- **네트워크 파티션(VM은 살아있는데 연결만 끊기는 경우)** — 이 판은 "컨테이너 종료"만
  본다. 진짜 네트워크 단절은 다른 실패 모양을 낼 수 있다(타임아웃 vs 즉시 거부, §3-3의
  ㄷ이 이 구분의 씨앗이다)
