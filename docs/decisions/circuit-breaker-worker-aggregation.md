## 0. #556의 주장

워커 3개(`session_id % 3` 라우팅, 883f508 채널 풀)가 사실상 독립 프로세스인데 Resilience4j
`CircuitBreaker`(`aiServer`, `ExerciseAnalysisService.java:168-169`) 하나가 셋의 실패율을 합산한다.

- 워커 1개만 죽어도 실패율이 올라가 멀쩡한 2개로 가는 호출까지 같이 막힐 수 있다
- 반대로 1개가 죽어도 나머지 2개가 실패율을 희석해 서킷이 안 열릴 수도 있다

이 두 시나리오 모두 **"워커 3개가 서로 독립적으로 죽고 산다"**를 전제한다. 이 문서는 그 전제
자체를 이미 있는 실측(`ai-channel-pool-hardening.md` §2-4)으로 다시 본다.

## 1. 이미 있는 실측이 이 전제를 반쯤 무너뜨린다

`ai-channel-pool-hardening.md` §2-4(2026-08-26, `loadtest/measure_ai_worker_kill_recovery.sh`,
워커 1개 SIGKILL, 7회 측정)의 결론:

> **워커 1개만 죽여도 컨테이너 전체(워커 3개 다)가 같이 재기동된다.** `entrypoint.sh`의
> `wait -n; exit $?`가 의도적으로 그렇게 설계돼 있고, 실측(다운타임 평균 25.3초, 범위
> 17.3~35.3초)이 코드 추론이 아니라 재현으로 확인했다.

즉 **"크래시(SIGKILL/프로세스 종료)" 실패 모드에서는 워커 3개가 독립적으로 죽지 않는다** —
하나가 죽으면 셋 다 17~35초간 같이 죽어 있다가 같이 돌아온다. 이 모드에서는:

- #556이 걱정하는 "1개 죽어도 나머지 2개가 희석" 시나리오가 **성립하지 않는다** — 죽을 때 셋 다
  같이 죽으므로 희석할 "멀쩡한 2개"가 없다.
- "1개 죽으면 나머지 2개도 같이 막힌다"는 **버그가 아니라 사실과 일치하는 동작**이다 — 실제로
  셋 다 죽어 있으니 서킷이 셋 다에 대해 열리는 것이 맞는 판단이다.

**결론: 크래시 실패 모드만 놓고 보면, 지금의 "합산된 하나의 서킷브레이커"가 오히려 정확한
모델이다.** 워커별로 쪼개는 것이 이 모드에서는 실익이 없다 — 쪼개봐야 3개가 동시에 열리고
동시에 닫힐 뿐이다.

## 2. 그런데 #556의 진짜 사정거리는 "크래시"가 아닐 수 있다

§1의 실측은 **"죽는다(process exit)"** 케이스만 재현했다. `entrypoint.sh`의 `wait -n`은 **프로세스
종료**에만 반응한다 — 워커가 죽지 않고 그냥 느려지거나 멈춘(hang, livelock) 경우는 감지하지
못한다. 이 경우는 §1의 "셋 다 같이 죽는다"가 적용되지 않는다:

- 워커 1개가 GIL 경합·검출기 부하 등으로 **살아있지만 느려진** 상태([[project_r6_gil_vs_cache_ride_along]]가
  같은 축의 미확정 원인을 다룬다)라면, 그 워커로 가는 요청만 타임아웃(`GRPC_CALL_TIMEOUT_SECONDS=5s`)이
  나고 나머지 2개는 정상 — 이게 #556이 실제로 걱정할 만한 유일한 시나리오다.
- 이 시나리오는 **한 번도 재현·측정된 적이 없다** — §1의 실측도, 다른 어떤 문서도 "워커 1개만
  느려지는" 조건을 만든 적이 없다.

## 2-1. 🔴 실측(2026-08-26, JUnit) — hang 시나리오, 그런데 §2가 예상한 것과 다른 결과

§2가 "재현된 적 없다"고 적은 hang 시나리오를 실제로 실행해봤다. `application.yml`의
`resilience4j.circuitbreaker.instances.aiServer` 설정(COUNT_BASED, window=10, minCalls=5,
threshold=50%)을 그대로 복제한 순수 `CircuitBreakerRegistry` 단위 테스트(Docker·gRPC·세션
불필요 — 검증 대상이 Resilience4j 자체의 결정론적 동작이라 네트워크 재현이 필요 없었다).

**시나리오 A — 균등 라운드로빈** (채널 0·1·2가 정확히 1/3씩, 채널1만 항상 실패):

```
call#0~14 (채널 0,1,2 반복) → 서킷 상태: 전 구간 CLOSED
정상 워커(0,2) 호출: 10건 전부 성공, 차단 0건
```

**서킷이 한 번도 열리지 않았다.** 이유는 산수다 — 3채널 중 1개만 항상 실패하면 실패율은
33%로, 임계값 50% 아래다. 즉 **§0이 걱정한 "1개 죽어도 나머지 2개가 희석"이 실제로는 정반대
방향으로 더 나쁘게 일어난다** — 희석되는 건 정상 워커 보호가 아니라 **hang 워커에 대한
서킷 차단 자체**다. 채널1로 가는 모든 호출은 서킷의 보호 없이 **매번 5초(`GRPC_CALL_TIMEOUT_SECONDS`)
풀로 타임아웃**되고, 이게 영원히 반복된다.

**시나리오 B — 클러스터** (최근 10건 중 6건이 채널1로 몰림, 세션이 한 워커에 쏠려 시작하는
경우를 흉내냄):

```
call#0,1(ch1) call#2(ch0) call#3(ch1) call#4(ch2)→OPEN
call#5~9: 서킷 OPEN 유지
정상 워커(0,2) 호출 중 CallNotPermitted 로 차단: 2건 (call#7 ch0, call#9 ch2)
```

**이 경우엔 §0이 걱정한 시나리오가 그대로 재현된다** — 정상 워커로 가는 호출이 실제로 막힌다.

**결론**: #556의 우려는 **트래픽 분포에 따라 갈린다.** 세션이 균등 분산되면(가장 흔한 경우로
추정) 서킷은 절대 안 열려 hang 워커가 무방비로 방치되고, 세션이 한 워커에 몰리면(부하 패턴에
따라 가능) 정상 워커까지 막힌다. **어느 쪽이든 "지금 설정이 맞다"는 결론은 아니다** — 균등
분산 쪽이 특히 나쁜데, "서킷이 열려서 문제"가 아니라 **"절대 안 열려서" 문제**이기 때문이다.
§0의 원래 우려(정상 워커 차단)보다 §2-1 시나리오 A(무방비 hang)가 더 조용하고 늦게 발견될
위험이 크다 — 서킷 지표(OPEN 이벤트)에 아무것도 안 찍히므로 관측으로도 안 보인다.

## 3. 정리 — 실패 모드별 현재 상태

| 실패 모드 | 측정 여부 | #556과의 관계 |
|---|---|---|
| 워커 크래시(프로세스 종료) | ✅ 측정됨(§1, 실컨테이너 SIGKILL 7회) | 합산 방식이 이미 맞다 — 손댈 이유 없음 |
| 워커 hang(생존, 균등 트래픽) | ✅ 측정됨(§2-1 시나리오 A, Resilience4j 단위 테스트) | **서킷이 절대 안 열린다** — hang 워커가 무기한 무방비, #556이 걱정한 것과 다른 방향의 실제 문제 |
| 워커 hang(생존, 트래픽 클러스터) | ✅ 측정됨(§2-1 시나리오 B) | #556이 걱정한 그대로 재현 — 정상 워커 차단 |

**세 모드 다 확인됐다.** 남은 것은 "재현이 되는가"가 아니라 "실제 운영 트래픽이 균등에 가까운가
클러스터에 가까운가"인데, 이건 배포 전이라 관측 데이터 자체가 없다(`slo-baseline.md`와 같은 공백).

## 4. 추천 (결정 아님)

**시나리오 A(무방비 hang)가 시나리오 B(정상 워커 차단)보다 더 나쁜 실패 모드라고 본다** — B는
최소한 서킷 OPEN 이벤트로 관측되고 10초 후 `HALF_OPEN`으로 자동 회복을 시도하지만, A는 아무
지표도 안 남긴 채 hang 워커로 가는 모든 세션이 매번 5초씩 태우는 것을 무기한 반복한다. 이건
"워커별로 서킷을 쪼갤지"와는 별개로 **"서킷을 유지하되 hang을 다른 방식으로도 잡을지"**를
같이 봐야 한다는 뜻이다.

1. **워커별 서킷 분리**(#556이 원래 제안한 것) — A·B 둘 다 고친다. `CircuitBreakerRegistry`에
   `"aiServer-" + channelIndex` 같은 키로 3개를 따로 만들면 된다. 비용은 낮다(레지스트리 키만
   바뀜) — §1이 "손댈 이유 없다"고 한 크래시 모드에서도 손해는 없다(3개가 동시에 열리고 닫히는
   것은 그대로 유지된다).
2. **hang 자체를 별도로 감지**(예: 워커별 마지막 성공 응답 시각을 헬스체크에 반영) — 서킷 분리와
   별개로, "그 워커로 새 세션을 안 보낸다"는 판단을 서킷의 실패율 임계값보다 빠르게 내릴 수 있다.
   범위가 이 문서보다 크다.
3. **현행 유지** — §1 근거(크래시 모드는 이미 맞다)만으로는 부족하다. §2-1이 hang 모드의 실제
   위험(특히 시나리오 A)을 보였으므로, "손대지 않는다"를 유지하려면 그 근거가 별도로 필요하다.

**이전 초안(§3·§4 구판)은 "hang이 미측정이라 손대지 말자"였다 — 지금은 측정됐고, 결과가 더
나쁜 쪽으로 나왔으므로 그 추천은 철회한다.** 1번(워커별 분리)이 비용 대비 두 모드를 동시에
고치므로 이 시점의 추천에 가장 가깝지만, **최종 착수 여부는 사용자 확인이 필요하다**
([[feedback_user_decides_not_claude]]) — 이 문서는 추천만 하고 ✅ 표시는 하지 않는다.

## 5. 열린 질문 / 미검증

- [ ] **실제 운영 트래픽이 균등/클러스터 중 어느 쪽에 가까운지** — §2-1의 두 시나리오는 둘 다
      인위적 극단값(완전 균등 vs 6/10 쏠림)이고, 실제 세션 시작 패턴을 반영한 것이 아니다.
      배포 전이라 이 자체가 미확정.
- [ ] `aiCircuitBreaker()`가 세 종류의 RPC(추출·시작·중단)를 하나로 묶는 것(`:166-167`, 채널
      풀 이전부터의 설계)과, 채널 풀 도입 이후 워커 3개를 하나로 묶는 것은 **서로 다른 두 개의
      "합산"이다.** 이 문서는 후자만 다뤘다 — 전자(RPC 종류별 분리가 필요한지)는 범위 밖.
- [ ] §2-1의 두 테스트는 순수 Resilience4j 단위 테스트다 — 실제 gRPC deadline 예외
      (`DEADLINE_EXCEEDED`)가 이 breaker에 어떻게 기록되는지(성공/실패 판정 로직,
      `ExerciseAnalysisService`의 수동 `onSuccess`/`onError` 연동)까지 재현하지는 않았다.
      메커니즘(합산 여부·임계값 산수)은 실제 코드와 동일하지만, 실제 gRPC 스택을 통한 end-to-end
      재현은 아니다.
