## A. 코드 결함 — 둘은 같은 결함의 양면이다

두 지적은 따로 왔지만 **하나의 습관**을 가리킨다: 예외를 뭉뚱그려 한 코드로 답한다. 한쪽은
DB 예외를, 다른 한쪽은 gRPC 상태를 뭉갠다. 그리고 그 결과로 **`feedback-batch-retransmission.md`
축 C 표(79~84행)가 종이 위에서만 성립한다.**

### A-1. `FeedbackLogService.java:130` — `DataIntegrityViolationException` 전부를 `SESSION_NOT_FOUND` 로

```java
} catch (DataIntegrityViolationException e) {
    // 위 존재검사(:67)와 이 INSERT 사이에 세션이 사라진 경우다
    throw new BusinessException(ErrorCode.SESSION_NOT_FOUND);
}
```

주석은 «세션 소멸» 하나만 상정하지만 `catch` 는 그 상위 타입을 전부 받는다. FK 위반이 아닌
제약 위반·값 범위 초과·데이터 잘림도 전부 「세션이 사라졌다」로 AI 에 보고된다.

그 다음이 문제다 — 축 C 표는 `SESSION_NOT_FOUND` 를 받으면 **버퍼를 버린다.** 즉 우리 쪽
값 오류 한 건이 «세션이 없어졌으니 다 버려라» 로 둔갑해 **정상 이벤트까지 폐기시킨다.**

**추천**: 원인 체인에서 FK 위반(MySQL 1452 / SQLState 23000)일 때만 `SESSION_NOT_FOUND` 로
변환하고, 나머지는 원래 예외로 전파한다. → `INTERNAL` 로 나가고 축 C 의 「그 외」 행이 받는다.

### A-2. `ExerciseGrpcService.java:133` — 모든 `BusinessException` → `INVALID_ARGUMENT`

```java
} catch (BusinessException e) {
    responseObserver.onError(io.grpc.Status.INVALID_ARGUMENT
            .withDescription(e.getErrorCode().name() + ": " + e.getErrorCode().getMessage())
            .asRuntimeException());
}
```

**축 C 표는 `SESSION_NOT_FOUND` 와 `INVALID_ARGUMENT` 를 다른 행으로 두고 처리를 갈랐다.
그런데 와이어에서는 둘 다 `INVALID_ARGUMENT` 다.** 구분은 오직 description 문자열 앞머리
(`SESSION_NOT_FOUND: …`)에만 있다.

표대로 구현하려면 AI 가 `e.details()` 를 문자열 파싱해야 한다. 그건 계약이 아니라 관습이고,
메시지 문구가 바뀌면 조용히 깨진다. **표가 전제하는 「1단계가 만들어준 구분」은 아직 와이어에
없다.**

**추천**: `SESSION_NOT_FOUND` 를 `Status.NOT_FOUND` 로 가른다. 한 줄이고, 그러면 표가 그대로
사실이 된다. (`NOT_FOUND` 는 gRPC 규약상으로도 이 상황에 맞다 — 지금 매핑은 «클라이언트가
잘못된 인자를 보냈다» 라고 말하고 있는데 사실이 아니다.)

> 대안으로 `google.rpc.ErrorInfo` 를 trailer 에 싣는 방법이 있으나, 지금 필요한 구분은 두
> 갈래뿐이라 표준 상태코드로 충분하다. 갈래가 늘면 그때 옮기면 된다.

## B. 문서 내부 모순 — 한 문서가 두 곳에서 다르게 말한다

### B-1. `feedback-type-detector.md` — 「좌우 비대칭」이 범위 밖이면서 동시에 argmax 축이다

| 위치 | 뭐라고 하는가 |
|---|---|
| 60~64행 (곁가지) | `KNEE_IN`/`KNEE_OUT` 은 정면 촬영 전제 문제라 **«이 문서의 범위 밖»** |
| 104~105행 (추천안 ㄷ) | argmax 축 = 「무릎 깊이 · 상체 기울기 · **좌우 비대칭**」 |

범위 밖이라고 밀어낸 축이 추천안의 세 축 중 하나로 들어와 있다. 정답지는 **측면** 영상이라
(V4 헤더) 좌우 벌어짐이 애초에 안 보이고, 열린 질문 2 는 정면 촬영 보장 여부를 «확인 안 했다»
로 남겨뒀다. 즉 **보장되지 않은 입력 전제 위에 축 하나가 얹혀 있다.**

이대로 구현하면 카메라 투영 차이가 결함으로 분류될 수 있다. 이건 임계값 문제가 아니라 축이
성립하느냐의 문제다.

**추천**: ㄷ 의 축 목록에서 좌우 비대칭을 빼고 **두 축(깊이·기울기)으로 시작**한다. 정면 촬영을
온보딩이 보장한다는 것이 확인되면 그때 축을 추가한다. 두 곳의 말이 같아진다.

> 이건 #244 에서 고친 `07-api-design.md` 의 결함과 같은 모양이다 — 정정문과 본문이 서로 다른
> 계약을 말하고 있었다. 이 repo 의 문서 드리프트는 계속 이 방향으로 난다.

### B-2. `feedback-type-detector.md:43` — 코드펜스 언어 누락 (markdownlint MD040)

설명용 블록이라 ```` ```text ```` 이면 된다. 한 줄.

## C. 새로 뚫린 구멍 — 「열린 질문」으로 승격할 것

아래 다섯은 **문서에 없던 갈림길**이다. 넷은 축 C 표(재전송 정책)의 귀결이고, 하나는 감지기다.
공통점: 표는 각 행의 **처리**를 정했지만 그 처리의 **부작용**을 안 적었다.

### C-1. `INVALID_ARGUMENT` 한 건이 버퍼 전체를 죽인다 (문서 82행)

표: 「버퍼를 버리고 에러 로그. 우리 코드 버그라 재시도가 못 고친다」.

A-2 는 «버퍼 전체» 를 보내므로, `rep_number=0` 이나 모르는 유형 **한 건**이 섞이면 같은 버퍼의
**정상 이벤트가 전부 함께 폐기된다.** `FeedbackLogServiceTest.saveBatch_invalidFeedbackType_
throwsAndInsertsNothing` 이 「전체가 저장 안 됨」을 이미 계약으로 못박고 있어, 이 조합은
설계대로 동작하면서 데이터를 잃는다.

**결정 필요**: (ㄱ) 무효 건만 격리하고 유효분은 재전송 / (ㄴ) 전체 폐기를 유지하되 허용 손실
범위와 모니터링을 명시. 추천은 (ㄱ) — 「우리 코드 버그」의 대가를 사용자 데이터로 치를 이유가 없다.

### C-2. 「그 외」 무기한 재전송 = poison batch (문서 84행)

표: 「버퍼 유지 — 잃는 것보다 낫다」. 상한이 없다.

영구 오류가 한 건 끼면 그 이벤트가 **모든 세트에서 영원히 재전송**되고, 새 이벤트가 쌓일수록
payload 와 비용이 단조 증가한다. A-2 의 「자연 상한」 논리(53~54행)는 «성공하면 비운다» 를
전제하는데, 이 행은 영원히 성공하지 않는 경우를 만든다.

**결정 필요**: 재시도 가능 상태 allowlist / 최대 시도 횟수 또는 TTL / dead-letter 중 무엇을 둘지.
**임계값은 비워둔다** — 세트 경계 간격 실측(문서 118~120행의 미검증 항목)이 먼저다.

### C-3. `is_final` 이 실패하면 다음 기회가 없다 (문서 74~75행, 열린 질문 3)

문서는 «비정상 종료(앱 강제 종료)» 만 열린 질문에 뒀다. 그런데 **정상 종료인데 마지막 RPC 가
`UNAVAILABLE`/`DEADLINE_EXCEEDED` 로 실패하는 경우**가 안 적혀 있다. 이때도 다음 세트 경계가
없고, 프로세스가 내려가면 메모리 버퍼가 사라진다.

즉 A-2 의 ✅ 「자기 치유」는 **세션 중간에만** 참이다. 마지막 배치에는 치유 경로가 없다.

**결정 필요**: 마지막 배치만 동기 재시도를 허용할지 / 영속 outbox 로 올릴지 / 허용 손실로 둘지.
열린 질문 3 과 합쳐 한 항목으로 다루는 편이 낫다.

### C-4. handoff 예시가 전송 전에 버퍼를 비운다

`events_buffer` 를 백그라운드 전송 **전에** 비우면, 그 전송이 실패해도 실패분이 다음 배치에
안 들어간다 — A-2 의 전제(«성공하면 비운다»)와 반대다.

**추천**: 「전송 성공 응답을 받은 뒤에만 비운다. 전송 중에는 스냅샷을 뜨고 버퍼 소유권은
유지한다」를 문서에 못박는다. 결정이 아니라 **표현 수정**에 가깝다.

> 버퍼 **상한**을 지금 정하라는 지적도 함께 왔으나, 그건 문서 121~122행이 이미 「실측 아님」으로
> 적어둔 것이라 D 로 보낸다(아래).

### C-5. argmax 점수 계산 규칙이 정규화 말고도 비어 있다 (문서 78행)

문서는 «축 간 정규화» 를 열린 질문 1 로 이미 세워뒀다. 그런데 그것 말고도 결과를 바꾸는
선택이 셋 더 비어 있다:

- **집계 방식** — 기울기를 rep 구간의 «최대 또는 평균» 중 무엇으로 (문서 48~49행이 둘을 병기)
- **부호/절댓값** — 정답지보다 덜 기운 것도 편차로 셀 것인가
- **동점 처리** — 두 축의 편차가 같을 때

원시 편차와 정답지 대비 상대 편차는 **같은 rep 에서 다른 축을 고를 수 있다.** 지금 상태로
구현하면 구현자마다 분류 결과가 달라진다.

**추천**: 열린 질문 1 을 「축 간 정규화」에서 **「argmax 계산 규칙 일체(집계·부호·정규화·동점)」**
로 넓힌다. 새 숫자를 만드는 게 아니라 **계산 순서를 못박는 일**이라 ㄴ(정답지 확장) 전에도 할 수 있다.

## D. 대응 불필요 — 근거를 남기고 닫는다

### D-1. 「B-2 는 비차단이 아니다 / `time.sleep(5/15/35초)`」 — **사실이 아니다**

그런 상수는 코드에 없다. 실재하는 유일한 동기 대기는
`spring_client.py:29` 의 `_COMPLETE_BACKOFF_SECONDS = (1.0, 3.0)` 이고, 이는 **`CompleteAnalysis`
전용**이다(3회 시도, worst-case 총 4초). `ReportFeedbackBatch` 와는 다른 호출이고, B-2 의 골자는
애초에 **재시도 타이머·스레드를 만들지 않는다** 이므로 sleep 자체가 등장하지 않는다.

남길 알맹이 하나: 문서가 **`ReportFeedbackBatch` 를 어느 스레드가 부르는지 명시하지 않았다.**
「실시간 경로를 막지 않는다」가 참이려면 그 호출부가 어디인지 적혀야 한다. 한 문장이면 된다.

### D-2. 「`HIP_HIGH` 제외를 측정 뒤로 미뤄라」 — **문서가 이미 그렇게 적어뒀다. 다만 인용된 수치는 틀렸다**

문서 미검증 항목 2 가 이미 이렇게 적고 있다:

> ①의 «MediaPipe 지터가 3.5° 에 가깝다» 는 일반적 관찰이지 이 프로젝트에서 측정한 값이 아니다.
> 깊이 축을 실제로 버릴지는 이 수치를 재보고 정하는 편이 낫다

리뷰가 근거로 든 «기준 데이터의 최저 무릎각이 재실행에서 95.4°~96.7° 로 변동» 은 **실재하지
않는 수치다.** #242(`reference-jitter-2026-08-16`)가 잰 것은 무릎각이 아니라 `sync_rate`
(95.51~95.79, 폭 0.28점)이고, `min_knee=95.39` 는 매 판 고정된 **사용자 입력값**이다. 96.7 은
어디에도 없다.

**다만 지적의 취지는 유효하고, 지금은 닫을 수 있게 됐다.** #242 가 같은 영상 10회 재실행에서
**정답지 score 가 101.66~108.70(폭 7.04)** 로 흔들린다는 것을 보였다 — 추출이 판마다 다르다는
사실 자체는 측정됐다. 같은 rig(`measure_reference_jitter.py`, 머지됨)에 **판별 `min_knee` 를
한 칸 더 기록**하면 「지터 3.5°」의 진위가 바로 나온다.

**→ 후속 측정 이슈로 등록했다: [#256](https://github.com/Shadowfit/init/issues/256).** 결과가
3.5° 보다 작으면 ①의 결론(깊이 축 폐기)이 뒤집히고, ㄷ 이 「실질 1종 분류」가 될 위험도 같이
해소된다. 임계값을 새로 만드는 일이 아니라 **이미 적힌 3.5° 가 참인지 재는 일**이다.

### D-3(참고). 버퍼 상한 — 문서 121~122행이 이미 미검증으로 적어둠

「한 세션의 이벤트 수가 수십 건」이 실측이 아니라는 것은 문서가 먼저 적었다. 감지기가 rep 단위로
판정한다는 전제(`feedback-type-detector.md` ①)가 깨지면 이 상한도 깨진다는 연결까지 적혀 있다.
**감지기 결정 전에 상한을 정하는 것은 순서가 뒤집힌 일이라 지금은 안 정한다.**
