## 0. 이 실험이 답하려는 것

지금까지 실측은 REST(가입·로그인·그룹 API)와 WS(핸드셰이크·이벤트 발행)를 따로 쟀다. §1-1이 "WS가 Tomcat 스레드풀을 HTTP 커넥터와 공유한다"를 코드 사실로 확정했고, §9-4는 "WS 버스트만으로는 busy_threads가 M=8~11까지만 올라갔다(풀 200에 한참 못 미침)"까지 갔다. 아직 안 본 것: **같은 순간에 REST 트래픽(가입·로그인·그룹생성/초대수락)까지 얹었을 때** 두 축이 같은 풀을 두고 실제로 부딪히는 지점이 §9-4가 멈춘 곳보다 가까이 있는가.

## 1. 실제 코드 흐름 재구성

## 2. 스코프 경계 (재확인)

- 인프라 확장(마스터-슬레이브·ProxySQL·대기열)은 여전히 스코프 밖 — `project_load_test_scope_staging`에서 이미 확인받은 전제, 이번 문서에서 다시 열지 않는다.
- 단일 인스턴스. 환경(로컬/AWS)은 기존 관행을 따른다 — 로컬(2코어)에서 먼저 시도하고, 판별 분산이 크면(다른 동시 세션 간섭 등, [[project_loadtest_env_constraint]]) AWS로 옮긴다. 이건 `group-websocket-heartbeat.md` §6-4와 같은 판단이라 이 문서에서 별도 분기로 열지 않았다.

## 3. 미확정 분기점 (사용자 확인 필요)

### 3-1. AI 프레임 루프(`/pose`) 포함 여부

`POST /exercises/sessions`는 gRPC로 AI 서버까지 이어진다. "풀 유저저니"라는 이름 그대로면 이후 330ms 주기 `/pose` 폴링까지 포함해야 완전하다.

| 옵션 | 내용 | 트레이드오프 |
|---|---|---|
| A. 세션 시작까지만 | `/pose` 루프 제외 | 그룹 WS+REST 축에만 집중, 기존 실측(§1·§9·§11)과 같은 해석 경계 안에 있음. "진짜 풀 여정"에는 못 미침 |
| B. `/pose` 루프까지 포함 | AI 프레임 처리까지 실측 | AI 축(GIL 천장, [[project_ai_ceiling_gil_n3_closed]])과 그룹 WS 축이 한 실험에 섞여 병목 원인 분리가 어려워짐. `ai-worker-routing-load-imbalance.md`가 이 얽힘의 일부(sessionId%3 분산)를 이미 별도로 다루는 중인데, 그 문서 자체가 "동시성 강제 UX가 아직 없어 지금 실측할 순서가 아니다"(§4)로 멈춰 있음 |

**추천**: A. 두 축을 한 실험에 섞으면 "무엇이 원인인가"를 가르기 어려워진다([[feedback_tps_over_dau_justification]]의 "원인으로 닫는다" 원칙과 충돌). AI 축은 이미 GIL N=3으로 닫혀 있고, ai-worker-routing 쪽은 선행 질문(그룹 동시-시작 UX)이 아직 안 풀렸다.

> ✅ **확정 (2026-09-01, 사용자 confirm)**: A — 세션 시작까지만.

### 3-2. 부하 모델 — 1회성 라운드 vs 반복 정상상태

§9는 "그룹 G개가 각자 한 번씩 접속+발행"(closed, 1-shot)이었다.

| 옵션 | 내용 | 트레이드오프 |
|---|---|---|
| A. 1회성 | N개 그룹이 전체 여정을 한 번씩 밟고 끝 | §9와 같은 성격이라 비교축이 유지됨. 설계가 단순 |
| B. 반복 정상상태 | 가입은 1회, 이후 접속-발행-이탈을 그룹들이 반복 재생 | 실제 운영에 더 가깝지만 세션 관리·종료 조건 설계가 커짐. 정상상태 부하는 대기열 등 인프라 확장과 더 맞물리는 주제라 `project_load_test_scope_staging`이 "그다음"으로 미뤄둔 결정 사안에 가까움 |

**추천**: A. 이유는 위 표에 적은 대로 — B는 이번 문서의 스코프(②단계, 아직 인프라 확장 이전)를 넘어선다.

> ✅ **확정 (2026-09-01, 사용자 confirm)**: A — 1회성 라운드.

### 3-3. 측정 축 — 그룹 수(G) 재스윕 vs 고정 규모 반복

§9는 G를 축으로 스윕했다(150→300연결). 이번 실험의 새 변수는 "REST 트래픽이 WS 옆에 동시에 있다"는 것 자체다.

| 옵션 | 내용 | 트레이드오프 |
|---|---|---|
| A. 고정 규모 + 반복판 | §9와 같은 규모(G=100×M=3=300연결)에 고정, 5판 반복 | REST 유무 차이만 §9와 직접 비교 가능. 새 경계는 못 찾음 |
| B. 규모도 다시 스윕 | G를 §9보다 더 올려(예: 150~200) Tomcat 풀 200 근처까지 노려봄 | §9-4가 "새로 열린 질문"으로 남겨둔 "실제 풀 고갈 지점"에 처음 닿을 수 있음. 다만 이 갈래는 §1-1이 "최소 목적은 달성했다"고 이미 낮은 우선순위로 닫아둔 지점이라 이번 문서의 목적(REST+WS 동시 경합)과는 별개 질문이 섞임 |

**추천**: A를 먼저(§9 대비 REST 추가분의 순수 효과를 본다), 결과가 흥미로우면(예: pending>0이나 지연 급증 관측) 그때 B로 규모를 올린다 — 확정 전 스윕(관측 없는 사전 확정)은 이 프로젝트 방법론과 안 맞는다(`group_ws_handshake_concurrency.js` 주석과 동일 원칙).

> ✅ **확정 (2026-09-01, 사용자 confirm)**: A — G=100×M=3(300연결) 고정, 5판 반복. 흥미로운 결과가 나오면 그때 규모를 다시 스윕한다.

## 7. 구현 경과 (2026-09-01) — 스크립트 작성 중 발견한 제약 두 가지

설계 확정 후 스크립트를 짜면서 코드로 확인된 제약이 둘 나왔다. 조용히 우회하지 않고 여기 남긴다([[feedback_decision_doc]]).

1. **인증 경로 rate limit(#394)이 로컬 300계정 동시 생성을 막는다.** `AuthRateLimitProperties`(`application.yml` `security.rate-limit`, 기본 활성화)가 IP 하나당 `/member/signup`·`/member/login` 각각 60건/60초로 막는다 — §9-1이 AWS에서 이미 겪은 것과 같은 벽이다. 계정 생성은 이 실험의 측정 대상이 아니라 조건이므로, 스크립트는 계정 준비(가입·로그인·온보딩)를 페이싱(기본 50건/60초)해서 순차로 끝내고, **동시성 창은 WS 접속 → 세션 시작(REST) → 이벤트 발행(WS) 구간에만** 건다. 이 구간만으로도 §0의 질문("REST가 WS 옆에 동시에 있다")에는 답이 된다 — 세션 시작 자체가 Tomcat 스레드를 잡는 REST 호출이라서다.
2. **세션 재사용이 안 된다.** `SessionService.createSession`은 회원 하나당 `IN_PROGRESS` 세션이 있으면 409를 던진다(`SessionService.java:102`). `endSession`을 불러도 status는 AI의 `CompleteAnalysis` 콜백이 와야 바뀌는데, 이 실험은 AI 루프를 스코프 밖에 뒀으므로(§3-1) 그 콜백이 영영 안 온다 — 계정을 재사용하면 2판째부터 전원이 409를 받는다. 그래서 **판(rep)마다 계정 300명을 새로 만든다.** 이건 "1회성 라운드를 5번 반복한다"는 §3-2 확정과도 맞는 선택이다 — 대가는 총 소요 시간(계정 1,500명 × 페이싱, 로컬에서 대략 30~40분)이 늘어난다는 것.

**상태**: 스크립트 작성·문법 검증(`python -m py_compile`, `--help`) 완료. 로컬 Docker 데몬이 이 세션에서 꺼져 있어 실제 서버 대상 스모크런은 아직 안 함 — 다음 실행 시 최초 1판을 `--groups 2 --members-per-group 3 --reps 1` 정도로 작게 먼저 돌려 API 계약(필드명·상태코드)이 실측 시점 코드와 맞는지 확인부터 하는 게 안전하다.

> 🔴 **정정 (2026-09-02)**: 이 절이 "아직 안 함"이라고 적어둔 뒤, 실제로는 스모크런과 본실행이 둘 다 끝났다(§8). 이 문서가 실행 사실을 못 따라간 드리프트였다 — 산출물(`loadtest/results/group-full-user-journey-2026-09-01/`, `-run.log`)이 이미 워킹트리에 있었는데 이 절만 안 갱신됐다.

## 8. §7 실행 결과 (2026-09-01) — 실패율이 예상보다 훨씬 높다

### 8-1. 스모크런 — 통과

`--groups 2 --members-per-group 3 --reps 1`(6명, `run-1d6fa57d.json`): **6/6 성공, 실패 0**. API 계약(상태코드·필드명)이 실측 시점 코드와 맞는다는 것부터 확인하고 본실행으로 넘어갔다 — §7이 남겨둔 안전장치가 실제로 그대로 지켜졌다.

**실패 합계 747/1500(49.8%), 전부 타임아웃.** §9(WS 단독, 300연결, 실패 0건)와 정면으로 다른 결과 — REST(세션 시작)를 WS 옆에 얹으니 §9-4가 "미해결"로 남겨둔 지점을 실제로 건드렸다.

`ws접속 실패`·`세션시작 추가 실패`·`발행 추가 실패` 열은 원본 JSON엔 없던 계산이다 — 각 스테이지의 `n`(그 스테이지까지 도달해 지연을 기록한 인원)을 단계별로 빼서 **어느 스테이지에서 떨어져 나갔는지**를 복원했다.

### 8-3. 스테이지별로 갈라보니 나온 것 세 가지

1. **발행(WS 이벤트 echo) 단계는 5판 전부 추가 탈락 0명.** 세션 시작까지 통과한 사람은 전원 발행까지 성공했다 — §9가 이미 확인한 "WS 브로드캐스트 자체는 이 규모에서 건강하다"와 일치한다. 실패는 전부 **WS 핸드셰이크**(스크립트 소켓 타임아웃 5초) 아니면 **세션 시작 REST**(`urllib` 타임아웃 10초) 둘 중 하나에서 난다.
2. **HikariCP 풀(15)이 Tomcat 풀(200)보다 훨씬 자주, 훨씬 일찍 신호를 낸다.** `hikaricp_connections_pending`은 5판 **전부**(9~195) 0보다 컸다 — 풀 크기가 15뿐이라 pending>0 자체가 이미 "15개 전부 사용 중, 대기 발생"을 뜻한다. 반면 `tomcat_busy`(cap 200)는 5판 중 2판(2, 4)만 상한을 찍었다. `JwtHandshakeInterceptor.beforeHandshake()`(WS 핸드셰이크마다 DB 조회 2회)와 `POST /exercises/sessions`(세션 시작) 둘 다 Hikari 커넥션과 Tomcat 스레드를 동시에 문다 — 그런데 **Hikari가 더 작은 풀이라 먼저, 더 자주 병목이 된다는 것이 이번 데이터의 방향성**이다.
3. **판2 vs 판4가 이 방향성을 가장 깨끗하게 보여준다.** 둘 다 `tomcat_busy=200(상한)`으로 **동일**한데, `hikari_pending`은 195 대 9로 **21배** 차이 나고, 성공률도 43.7% 대 85.0%로 크게 갈린다. Tomcat 압력이 같은 상태에서 Hikari 압력만 다른 두 판을 우연히 얻은 셈이라, §1-3(seq 락 경합)이 InnoDB 카운터로 원인을 확정했던 것과 결이 비슷한 비교축이 하나 나온다 — 다만 그건 **설계된 통제 실험**이었고 이건 **사후에 발견한 우연한 매칭**이라 증거 강도가 다르다는 건 분명히 해둔다.

### 8-4. 못 갈랐다 — 판1이 이 이야기를 깨뜨린다

판1은 성공률이 가장 낮은데(3.0%) `tomcat_busy=65`·`hikari_pending=31`로 두 풀 다 판2·3·5보다 여유 있었다 — 위 §8-3의 "풀 압력이 클수록 실패가 는다"는 방향성과 맞지 않는다. 게다가 판1의 탈락은 압도적으로 **WS 핸드셰이크 단계**(226/291, 78%)에 몰려 있다 — 세션 시작 단계가 아니다.

**가설(미확인)**: 판1은 이 실행에서 처음 도는 300명 동시 버스트다 — JIT 컴파일·JPA 메타모델·1차 커넥션풀 채우기 등 이 JVM 인스턴스가 아직 한 번도 안 겪은 "콜드 스타트" 비용이 첫 번째로 DB를 건드리는 스테이지(WS 핸드셰이크, 세션 시작보다 코드 순서상 먼저 옴)에 그대로 얹혔을 가능성이 있다. **이 가설은 확인되지 않았다** — 검증하려면 "워밍업 판을 하나 버리고(이미 [[feedback_measure_design_needs_repeats]]가 원칙으로 요구하는 것과 같은 방향) 그다음부터 재는" 재실행이 필요하다.

**결론 — 원인 분리는 절반만 닫혔다**:
- ✅ **확정에 가까움**: 실패는 발행이 아니라 핸드셰이크·세션시작 두 DB 접촉 스테이지에서만 나며, HikariCP 풀(15)이 Tomcat 풀(200)보다 먼저·더 자주 포화 신호를 낸다(전자는 5/5판, 후자는 2/5판).
- 🔴 **미확인**: (a) 판1 콜드스타트 가설, (b) Hikari 풀을 실제로 키웠을 때 성공률이 따라 오르는지(진짜 인과 vs 상관) — 이 둘은 기존 데이터를 아무리 더 파도 안 나온다. §1-3처럼 **한 레버만 바꾸는 통제 재실행**(예: `maximum-pool-size`만 올리고 나머지 조건 동일하게 재현, 워밍업 판 1개 버림)이 다음 단계다.

> 🔴 이 재실행은 로컬 Docker가 지금 꺼져 있고(계정 1,500명 페이싱 포함 왕복 30~40분 규모, [[project_load_test_scope_staging]]) 이미 §9-1·9류의 실측 비용을 반복하는 일이라, 진행 여부·환경(로컬 vs AWS)은 추천이며 결정이 아니다 — 사용자 확인 후 실행한다.

## 9. pool=30 통제 재실행 — 사후 발견 (2026-09-03), §8-4를 안 풀고 더 복잡하게 만든다

### 9-1. 이 결과가 어떻게 발견됐나 — 또 한 번의 문서 드리프트

§8-4가 요청한 재실행("Hikari `maximum-pool-size`만 올리고 나머지는 동일하게 재현")은 **사실 이미 2026-09-02 02:51~03:52에 실행되어 있었다** — `loadtest/results/group-full-user-journey-pool30-run.log` · `loadtest/results/group-full-user-journey-2026-09-02/run-161258be.json`(+ 사전 스모크런 `run-0f2ba638.json`, 6명 100% 성공)이 워킹트리에 이미 있었는데 이 문서에는 전혀 반영되지 않았다. §7이 이미 한 번 자인한 것과 같은 종류의 드리프트다(§7 말미 "🔴 정정" 참고) — **실행이 문서를 두 번 앞질렀다.** `docker-compose.yml`의 `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE` env(§8-4가 근거로 남긴 "재빌드 없이 값을 바꿀 수 있게" 손잡이)가 이미 이 재실행을 위해 추가돼 있었다는 것도 같은 흔적이다.

**단, §8-4가 요청한 설계를 완전히 따르진 않았다** — "워밍업 판 1개를 버리고 그다음부터 잰다"는 조건은 이 재실행에도 적용되지 않았다(5판 전부 그대로 집계). 즉 이건 §8-4가 제안한 실험의 **부분 실행**이지 완전한 통제 재현이 아니다.

### 9-2. 방법 — 바뀐 건 pool 크기 하나뿐

같은 스크립트(`measure_group_full_user_journey.py`), 같은 규모(G=100×M=3, 300연결, 5판) — `HIKARI_POOL_SIZE=30`(기본 15 대비 2배)만 바꿨다. §3-3에서 확정한 설계(고정 규모 반복)를 그대로 따른다.

### 9-3. 결과 — 집계는 방향이 맞다

### 9-5. 새로 눈에 띈 것 — baseline jvm_threads가 판이 진행될수록 대체로 커진다

부하를 걸기 전 기준값(`baseline.jvm_threads`)이 52 → 85 → 63 → 154 → 173 순으로, 완전한 단조증가는 아니지만 판4~5에서 뚜렷하게 뛴다. **판 사이에 뭔가(스레드·커넥션·WS 세션 등)가 정리되지 않고 누적되고 있을 가능성**을 시사한다 — 이건 §8-4의 "판1 콜드스타트" 가설과는 반대 방향의 새 가설이다(콜드스타트는 "처음이 나쁘다"인데, 이건 "뒤로 갈수록 기준선 자체가 오염된다"는 쪽). **미확인** — 이 문서의 다른 가설들과 마찬가지로 검증 안 됐다.

### 9-6. 결론 — §8-4는 안 풀렸다, 오히려 경쟁 가설이 하나 늘었다

- **살아남은 것**: 풀을 키우면 **집계** 실패율은 준다는 방향성. 실패가 발행이 아니라 핸드셰이크·세션시작에서 대부분 난다는 것(판2의 6명 예외를 빼면 대체로 유지).
- **무너진 것**: "hikari_pending이 판별 성공률을 설명하는 변수"라는 §8-3의 핵심 메커니즘. pool=30 데이터에서 방향이 뒤집혔다.
- **새로 생긴 것**: baseline jvm_threads 누적 가설(§9-5), 판별 host 간섭 가능성([[project_loadtest_env_constraint]] — 이 재실행 시각 02:51~03:52에 다른 동시 세션이 있었는지는 이 문서 범위에서 확인 안 됨).
- **여전히 미확인**: §8-4의 판1 콜드스타트 가설(이번 재실행에서도 워밍업 판을 버리지 않아 그대로 남음), Hikari 풀 크기와 성공률의 진짜 인과관계.

**다음 단계로 필요한 것(추천, 미확정)**: 지금까지 두 번의 실행(pool=15, pool=30) 모두 "워밍업 판 버리기"를 실제로 안 했다 — §8-4가 스스로 요구한 조건을 아직 한 번도 충족 못 했다. 판별 변수(pending, jvm_threads, 판 순서)가 서로 얽혀 있어 지금 데이터를 더 들여다봐도 안 풀린다 — [[feedback_measure_design_needs_repeats]]가 요구하는 대로 **워밍업 판을 명시적으로 버리고, 이 dev 박스의 동시 세션 여부를 실행 전후로 확인해 기록하는** 세 번째 통제 재실행이 다음 단계다. 진행 여부·시점은 사용자 확인 후.

## 10. 세 번째 통제 재실행 설계 — AWS, 확정 전 (2026-09-03)

§9가 남긴 문제를 두 갈래로 나눠 각각 원인을 짚었다 — **설계 결함 하나, 환경 결함 하나.** 사용자 확인(2026-09-03)으로 **둘 다 고치고 AWS로 옮긴다**가 방향으로 정해졌다. 이 절은 그 설계를 박제한다 — **아직 실행 전이다.** EC2는 실비용 인프라라 착수 전 별도 confirm이 필요하다([[feedback_user_decides_not_claude]], [[project_unattended_aws_round_recipe]]).

### 10-1. 설계 결함 — pool=30은 애초에 근거 없는 값이었다

`application.yml`의 `maximum-pool-size: 15` 주석이 인용하는 plateau(`pool 10→100%, 20→100%(plateau)`, `commit-count-and-mysql-metrics.md` 4차)는 **로컬이 아니라 EC2**(medium×2+small×2)에서 나온 값이다. 그런데 §8·§9의 pool=15 vs pool=30 비교는 **로컬 i3-6100(물리 코어 2개)**에서 돌았다 — plateau 근거와 다른 호스트에서, 게다가 그 plateau 상단(20)조차 넘는 미검증 값(30)으로 비교한 것이다. §9-4가 본 "pending과 성공률의 관계가 역전됨"이 진짜 병목 메커니즘 붕괴가 아니라 **plateau 밖 값 + 호스트 불일치**가 만든 잡음일 가능성이 이 시점에서 더 크다.

**고침**: 미검증 극단값(30) 대신, **이미 EC2에서 검증된 plateau 경계 안**에서 고른다 — **pool=15(현재 프로덕션 기본값) vs pool=20(plateau 상단, 그 이상은 실익 없음이 이미 확인됨)**. 새 변수를 만들지 않고 기존 근거 안에서만 비교하므로, 이번엔 "pool을 (검증된 범위 안에서) 키우면 이 WS+REST 혼합 워크로드에도 도움되는가"에 오염 없이 답할 수 있다.

### 10-2. 환경 결함 — 로컬 dev 박스의 동시 세션 간섭

§9-5의 "판이 진행될수록 baseline jvm_threads가 대체로 커진다"는 관측은 [[project_loadtest_env_constraint]]가 이미 경고해온 패턴(이 dev 박스에 다른 Claude Code 세션이 동시에 붙어 있을 수 있다, [[project_concurrent_sessions]])과 결이 같다. 이 문서 §2가 애초에 세워둔 기준("판별 분산이 크면 AWS로 옮긴다")이 지금 충족됐다고 본다.

**고침**: 전용 EC2 인스턴스로 옮긴다 — 다른 세션과 공유하지 않는 한, 이 변수 자체가 사라진다.

### 10-3. 확정된 설계 (2026-09-03, 사용자 confirm — 방향만. 실행은 별도 confirm)

| 항목 | 값 | 비고 |
|---|---|---|
| 환경 | AWS EC2, 전용 인스턴스 | `commit-count-and-mysql-metrics.md`류 절차 재사용([[project_unattended_aws_round_recipe]]) — 부트스트랩은 커밋 SHA로, 종료 확인 필수 |
| pool 값 | **15 vs 20** (2점 비교) | plateau 안쪽, EC2 근거와 정합 |
| 판 수 | **6판**, 1판(워밍업) 버림 — 2~6판만 집계 | §8-4가 원래 요구한 조건, 지금까지 두 번 다 안 지켜짐 |
| 규모 | G=100×M=3(300연결) 고정 | §3-3 확정 그대로 |
| 스크립트 | `measure_group_full_user_journey.py` (변경 없음, `HIKARI_POOL_SIZE` env로 pool만 스윕) | |
| 호스트 상태 기록 | 실행 전후 다른 프로세스·세션 유무를 로그에 남긴다 | §9-5류 오염을 사후에 다시 의심하지 않기 위한 최소 조치 |

### 10-4. 아직 안 정해진 것

- 인스턴스 스펙(medium×2+small×2 재사용 여부, 아니면 다른 조합) — 비용·조달은 실행 confirm 시점에 같이 정한다.
- pool=15 vs 20 비교로도 §9-4의 역전 현상이 재현되면(즉 plateau 안에서도 방향이 안 맞으면), §8-3의 "hikari_pending이 핵심 변수"라는 가설 자체를 폐기해야 할 수 있다 — 그건 이번 재실행 결과가 나온 뒤에 판단한다.
