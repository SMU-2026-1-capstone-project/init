## 1. 문제 정의 — 실측으로 이미 나온 사실

`group-websocket-capacity-deep-dive.md` §9-3, AWS `c7i.xlarge` 실측(300연결):

> 소켓을 정리할 때 WS Close 프레임 없이 TCP를 그냥 끊었다(`sock.close()`, 실제 모바일 클라이언트의 "네트워크가 갑자기 끊김"과 같은 조건). 스크립트의 3초 대기 안에는 150연결에서 +96, 300연결에서 +162 스레드가 안 돌아왔다 — 1~2분 뒤 수동으로 확인하니 베이스라인으로 돌아와 있었다. 즉 서버가 "정상 종료 프레임 없이 끊긴 연결"을 감지하는 데 **3초보다 훨씬 오래(3초와 60~120초 사이 어딘가) 걸린다.**

지금 `GroupSocketHandler`·`GroupSocketRegistry`엔 이 감지를 앞당길 장치가 전혀 없다 — TCP 스택(OS 레벨 RST/FIN 또는 커널 기본 keepalive, 보통 2시간 단위)에만 의존한다. 이게 실제로 문제가 되는 지점:

- **`broadcast()`가 "죽었지만 아직 안 치워진" 세션에도 전송을 시도한다** — `GroupSocketRegistry.send()`가 `IOException`을 받아야 비로소 정리하는데, TCP가 끊김을 알아채기 전까진 그 시도 자체가 계속 발생한다(단, #623 이후엔 세션 전용 스레드로 격리돼 있어 다른 멤버 전달을 막지는 않는다).
- **그룹 인원 수가 실제보다 부풀어 보인다** — 클라이언트가 "그룹에 지금 N명 접속 중"을 보여주는 기능이 생기면, 죽은 세션이 안 치워진 채로 N에 들어간다.
- **재연결 흐름과 충돌 가능성** — 같은 유저가 네트워크 끊김 직후 곧바로 재접속하면, 죽은 세션이 아직 레지스트리에 남아 있는 짧은 창(window) 동안 `register()`가 그룹당 `Map<String, Entry>`에 세션 ID로 구분되니 실제 충돌은 없지만(세션 ID가 다름), 같은 그룹에 유령 세션 하나가 더 떠 있는 상태가 된다.

**이 문제의 크기는 아직 정량화 안 됨** — "60~120초 사이 어딘가"라는 폭 넓은 추정치뿐이고, 그 창에서 실제로 위 세 가지가 어느 정도 해를 끼치는지는 측정한 적 없다.

## 2. 옵션

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. WS 프로토콜 ping/pong | 서버가 주기적으로 `PingMessage` 전송, `handlePongMessage()`로 응답 확인, 타임아웃 시 강제 close | RFC 6455 표준 — 클라이언트 라이브러리 대부분이 pong을 자동 응답(앱 코드 변경 불필요할 수 있음). Spring `TextWebSocketHandler`가 `handlePongMessage()` 이미 지원 | 서버가 클라이언트마다 스케줄된 작업(타이머)을 들고 있어야 함 — `GroupSocketRegistry`가 이미 세션마다 전용 스레드(#623)를 쓰는데, 여기에 세션마다 스케줄러까지 얹으면 리소스 축이 하나 더 늘어남 |
| B. 애플리케이션 레벨 heartbeat | 클라이언트가 주기적으로 `{"type":"PING"}` 같은 텍스트 프레임 전송, 서버는 마지막 수신 시각을 세션마다 기록하고 배치로 타임아웃 스캔 | 클라이언트·서버 둘 다 로직이 단순하고 명시적 — 기존 `handleTextMessage()`의 `type` 분기 구조에 자연스럽게 얹힘 | 클라이언트(프론트) 쪽 구현이 반드시 필요 — 서버 단독으로 못 끝냄. 이 문서·repo 범위가 백엔드라 프론트 협조 필요 여부부터 확인해야 함 |
| C. TCP-level keepalive (`SO_KEEPALIVE`) | OS 소켓 옵션으로 커널이 주기적으로 프로브 | 애플리케이션 코드 변경 없음 | 기본 간격이 보통 2시간 — 커스텀하려면 OS/커널 파라미터 조정 필요(컨테이너 환경에서 신뢰성 낮음). Tomcat NIO 커넥터가 이 값을 노출하는지도 확인 안 됨. 근본적으로 이 문제를 앞당기기엔 부적합한 도구 |
| D. 도입 안 함(현행 유지) | TCP FIN/RST + 기본 keepalive에만 의존 | 코드 추가 없음, 지금 5개 갈래(§1-1~§1-5) + 백프레셔(#623) 모두 닫힌 상태를 그대로 유지 | "60~120초 사이 어딘가"라는 감지 지연이 그대로 남음 — 얼마나 해로운지 모른 채 방치 |

**A와 B 중에서 고른다면 A(WS 표준 ping/pong)가 이 프로젝트 구조와 더 맞다** — 백엔드만으로 완결되고, 이미 `TextWebSocketHandler`를 쓰고 있어 `handlePongMessage()` 오버라이드 하나로 수신 쪽은 끝난다. 다만 이건 추천이지 결정이 아니다.

## 3. 설계값 (확정, 2026-08-30 사용자 confirm)

| 항목 | 값 | 근거 |
|---|---|---|
| ping 주기 | 30초 | 최대 감지 지연 ~90초 — 지금(60~120초)보다 확실히 개선되면서 트래픽 부담은 완만. 그룹 운동 세션은 앱이 포그라운드+카메라 활성 상태로만 유지되는 연결이라 배터리 부담이 상대적으로 작다는 전제 |
| timeout 유예 | 연속 2회 미응답 시 종료 | 네트워크가 일시적으로 흔들리는 모바일 클라이언트(React Native/Expo)를 감안해 1회 즉시 종료(오탐 위험)를 피함 → 최대 감지 지연 ≈ 30초 × 2 + α ≈ 90초 |
| 스케줄러 구조 | `GroupSocketRegistry` 공유 단일 `ScheduledExecutorService` | 이미 들고 있는 세션 맵을 주기적으로 순회하며 ping 전송·마지막 pong 시각 검사. 스레드 1개로 끝남 — #623의 세션별 전용 스레드(전송 격리 목적)와는 다른 목적이라 재사용하지 않음. 세션마다 개별 타이머를 두면 §9에서 이미 확인된 "연결마다 스레드 하나" 자원 축을 또 반복하게 됨 |
| 정량화 선후 | **먼저 실측** | §9-3의 "60~120초 사이 어딘가"라는 폭을 좁히는 실험을 구현 전에 먼저 진행. §6에서 설계 |

## 4. 포지셔닝·기회비용

- **DB 깊이 서사와의 접점**: 없음 — `multiuser-realtime-sync.md` §4가 이미 지적한 대로 그룹 WS 자체가 DB 쿼리·인덱스·트랜잭션 축과는 별개다. heartbeat는 그중에서도 가장 "흔한 실시간 기능 상식"에 가까운 소재라 차별화 효과는 낮다.
- **이미 닫힌 5개 갈래 + 백프레셔와의 관계**: §1-1~§1-5, §9는 전부 "지금 짠 코드가 설계대로 동작하나"를 검증하는 성격이었다. heartbeat는 이들과 달리 **아직 없는 기능을 새로 추가**하는 것이라 성격이 다르다 — "검증"이 아니라 "신규 구현".
- **공수**: 옵션 A 기준 대략 세션 1~2개(2~4h) 규모로 보임 — `GroupSocketHandler`에 `handlePongMessage()` 추가, 스케줄러 컴포넌트 하나, 관련 유닛/통합 테스트. `multiuser-realtime-sync.md` §7의 다른 세션들(3~5h)과 비슷한 크기.

## 6. 정량화 실험 설계 (실행 전 — 이 절도 사용자 확인 필요)

**목적**: §9-3의 "3초와 60~120초 사이 어딘가"라는 폭을 반복 실측으로 좁힌다. heartbeat 구현 전에 하는 이유는 §3에서 정한 대로 — 도입 효과("90초로 줄어든다")를 주장하려면 "지금이 정확히 얼마인가"라는 비교 기준선이 있어야 하기 때문.

**§9-3 대비 정밀도를 올려야 하는 지점**: 그때는 범용 `jvm_threads_live`(다른 스레드와 섞임)를 3초 간격으로만 확인하고, 그 다음은 "1~2분 뒤 수동 확인"이라 실제 감지 시각을 못 좁혔다. 이번엔:

1. **직접 신호 계측**: `GroupSocketRegistry`에 Micrometer 게이지(`group_ws_active_sessions`, 전체 그룹 합산 활성 세션 수) 하나를 새로 노출한다 — 이 프로젝트가 이미 Prometheus/Grafana 관측 스택을 갖췄고(§1-1의 `tomcat.threads.*` 선례와 같은 종류), 범용 스레드 수 대신 "이 레지스트리가 실제로 몇 개를 들고 있는가"를 직접 읽는 게 목적에 더 맞는다.
2. **세밀한 폴링**: 비정상 종료(WS Close 프레임 없이 raw `sock.close()`, §9-3과 동일 기법) 직후부터 게이지를 **0.5초 간격**으로 최대 180초까지 폴링하며, 값이 베이스라인으로 떨어지는 첫 시점을 기록한다.
3. **반복**: 5회([[feedback_measure_design_needs_repeats]]) — 판마다 새 세션으로 접속·비정상 종료·감지시각 기록을 반복해 중앙값·범위를 본다.
4. **환경**: 이건 처리량이 아니라 "OS/JVM이 끊김을 인지하는 타이밍"이라 §9처럼 버스트 용량이 필요 없다 — 로컬(2코어 공유)에서 먼저 시도하고, 판별 분산이 크면(다른 동시 세션 간섭 등, [[project_loadtest_env_constraint]]) AWS 격리 인스턴스로 옮긴다.

**산출물**: `loadtest/measure_group_ws_disconnect_detection_lag.py` + 결과 JSON. 결론에 따라 §3의 값(30초/2회 → 최대 감지 지연 ~90초 추정)이 "TCP만 썼을 때보다 얼마나 개선되는가"를 수치로 뒷받침한다.
