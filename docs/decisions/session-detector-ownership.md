## 0. 이 문서가 여는 것

2026-08-11 측정([`thread-collision-2026-08-11`](../../loadtest/results/thread-collision-2026-08-11/))이
#164 의 캐비엇 둘을 닫으면서 **선택지가 4개에서 2개로 줄었다.**

| 원래 4안 | 판정 |
|---|---|
| ㄱ. `static_image_mode=True` | ❌ **탈락.** 트래킹을 버리면 매 프레임 탐지기가 돈다 — 프레임당 비용이 오르는데, 이 시스템의 병목이 바로 그 비용이다 |
| ㄴ. 검출기를 **세션별**로 보관 | ✅ 후보 |
| ㄷ. 세션을 **스레드에 고정** | ✅ 후보 |
| ㄹ. 감수 + 관측 | ❌ **탈락.** 실사용 페이스에서 검출률 손실이 **41~63%p** 로 확인됐다. 감수할 크기가 아니다 |

**남은 질문은 하나다 — «세션» 이라는 상태를 무엇에 붙일 것인가.**

## 1. 지금 구조 (왜 깨지는가)

```python
# mediapipe_detector.py:105-115
_thread_local = threading.local()          # 검출기가 «스레드» 에 붙어 있다

def get_detector():
    detector = getattr(_thread_local, "detector", None)
    if detector is None:
        detector = PoseDetector()          # static_image_mode=False → 직전 프레임 기준 트래킹
        _thread_local.detector = detector
    return detector
```

```python
# pose.py:45-52 — def 핸들러라 FastAPI 가 스레드풀에서 돌린다
@router.post("", response_model=PoseResponse)
def detect_pose(req: PoseRequest): ...
```

**트래킹 상태가 «세션별» 이 아니라 «스레드별» 이다.** 그런데 요청은 아무 idle 스레드나 집어가므로,
그 스레드가 직전에 본 것이 다른 세션이면 트래킹이 깨진다.

측정으로 확인된 것: **한가할수록 심하다.** 3fps 면 요청 사이에 스레드가 idle 로 반납되고 다음 요청이
아무 스레드나 집어가서 충돌률 44~78%. 포화 상태에서는 방금 반납한 스레드를 곧바로 다시 집어 ~0%.
**그리고 3fps 가 실사용 값이다**(`exercise.tsx:150`, `session_state.py:47`).

## 2. 두 안

### ㄴ. 검출기를 세션에 붙인다

```python
_detectors: dict[int, PoseDetector] = {}   # session_id → 검출기
_locks: dict[int, threading.Lock] = {}     # 🔴 락이 «필요하다» (§3-1)

def get_detector_for(session_id): ...
```

스레드는 아무나 와도 되고, **«그 세션 담당» 검출기를 찾아서** 쓴다.

### ㄷ. 세션을 스레드에 붙인다

```python
# 세션마다 워커 1개. 그 세션의 프레임은 항상 같은 스레드에서 처리된다.
_workers: dict[int, ThreadPoolExecutor] = {}   # max_workers=1
```

검출기는 **스레드 로컬 그대로 둔다.** 스레드가 세션 전용이면 스레드 로컬이 곧 세션 로컬이 된다.

## 3. 비교

| 축 | ㄴ (검출기→세션) | ㄷ (세션→스레드) |
|---|---|---|
| 충돌 제거 | ✅ | ✅ |
| **같은 세션 프레임이 겹칠 때** | 🔴 **락 필요** (§3-1) | ✅ **자동 직렬화** — 워커가 하나라 줄을 선다 |
| **MediaPipe 객체가 스레드를 옮겨도 되는가** | 🔴 **미검증 전제 위에 선다** (§3-2) | ✅ **질문 자체가 안 생긴다** |
| 메모리(검출기) | 세션당 1개 | **세션당 1개 (동일)** — 스레드가 세션 전용이므로 |
| 메모리(스레드) | 스레드풀 그대로 | 세션당 스레드 1개 추가 |
| 코드 변경 위치 | `mediapipe_detector.py`(조회 경로) + 생명주기 | `pose.py`(실행 경로) + 워커 관리 |
| 세션 생명주기 관리 | **필요** — 종료 시 `close()`, 비정상 종료 시 누수 | **필요** — 종료 시 executor 종료 |
| 동시 실행 수 제한 | FastAPI 리미터가 그대로 해준다 | 🔴 **직접 해야 한다** (§3-3) |
| 백프레셔 관측 | 별도 설계 필요 | ✅ **세션별 큐 길이가 그대로 지표** |
| 아키텍처 정합 | 상태의 주인이 «세션» 이 된다 | 상태와 **실행 단위**가 둘 다 «세션» 이 된다 |

### 3-1. 🔴 ㄴ 은 락이 «필요하다»

같은 세션의 프레임 두 개가 동시에 처리 중일 수 있다 —
클라이언트에 **백프레셔가 없기 때문**이다([`architecture-review-2026-08-11.md`](./architecture-review-2026-08-11.md) 결함 ⑥:
`exercise.tsx:195` 의 `setInterval` 에 in-flight 가드가 없어, 응답이 늦으면 다음 요청이 그대로 나간다).

그 둘이 같은 `PoseDetector` 를 동시에 부르면 **지금보다 나쁜 상태**가 된다 —
MediaPipe Pose 는 thread-safe 하지 않다(`mediapipe_detector.py:105` 주석이 명시).
→ 세션당 락이 필요하고, 락을 걸면 결국 **세션 내 직렬화**다. ㄷ 가 공짜로 주는 것을 손으로 만드는 셈이다.

### 3-2. 🔴 ㄴ 의 미검증 전제 — «검출기가 스레드를 옮겨 다녀도 되는가»

현행 코드 주석은 *"MediaPipe Pose 는 thread-safe 하지 않으므로 **호출 스레드마다 분리**"* 라고 적는다.

«thread-safe 하지 않다» 는 보통 **«동시 호출이 안전하지 않다»** 는 뜻이고, 그렇다면 락으로 직렬화한 뒤
서로 다른 스레드에서 순차 호출하는 것은 괜찮아야 한다. **그런데 그것을 확인한 적이 없다.**
MediaPipe 내부 그래프가 스레드 어피니티를 요구하면 ㄴ 은 조용히 깨진다.

> **이것이 두 안의 결정적 차이다.** ㄴ 은 이 전제 위에 서고, ㄷ 는 **그 질문을 회피한다**(항상 같은 스레드).
> §5 에서 이 전제를 재는 방법을 적는다 — **결정 전에 재야 한다.**

### 3-3. 🔴 ㄷ 는 동시 실행 수를 «직접» 제한해야 한다

세션마다 워커를 두면 FastAPI 의 anyio 스레드 리미터 **밖으로 나간다.**
세션 20개면 워커 20개가 동시에 CPU 를 다툴 수 있고, 그러면 **CPU 초과 구독**으로 전체가 느려진다
(측정에서 스레드 16 이 8 보다 느렸던 그 모양 — [`ai-recalibrate-2026-08-11`](../../loadtest/results/ai-recalibrate-2026-08-11/) §2 [C]).

→ **세션당 워커 1개 + 전역 세마포어(≈ 물리 코어 수)** 조합이 필요하다.
이건 부담이기도 하지만, **입장 제한(P3)이 붙을 자연스러운 자리**이기도 하다.

## 4. 메모리 — 두 안이 «같다»

처음엔 ㄴ 이 «세션당 검출기» 라 메모리를 더 쓴다고 봤는데, **틀렸다.**
ㄷ 도 스레드가 세션 전용이므로 스레드 로컬 검출기가 결국 **세션당 1개**가 된다. 차이는 스레드 스택뿐이고 작다.

⚠️ 다만 **양쪽 다 «세션 수 × 검출기» 를 들고 있어야 한다는 부담은 같다.**
MediaPipe 인스턴스 1개의 실제 메모리는 **아직 안 쟀다** — 박스에 컨테이너 7개고 OOM 전적이 있으므로
(⑤), 채택 전에 재는 것이 맞다.

## 5. 결정 전에 재야 할 것 두 개

기존 rig([`measure_thread_collision.py`](../../loadtest/measure_thread_collision.py))를 조금 고치면 둘 다 된다.

| # | 무엇 | 어떻게 | 무엇이 갈리나 |
|---|---|---|---|
| **M1** | **검출기가 스레드를 옮겨도 되는가** (§3-2) | 세션별 검출기 + 락으로 직렬화하되, **매번 다른 스레드에서** 호출한다. 검출률이 «전용 스레드» 팔과 같은지 본다 | **깨지면 ㄴ 이 탈락**하고 ㄷ 로 확정된다 |
| **M2** | **`PoseDetector` 1개의 실제 메모리** | 인스턴스를 N개 만들며 RSS 증가를 잰다 | 세션 상한(P3)의 메모리 쪽 근거가 된다 |

**M1 이 이 문서의 급소다.** 결과에 따라 비교가 아니라 결론이 된다.

## 6. 추천 (결정 아님)

**M1 이 통과하든 안 하든 ㄷ 를 권한다.** 근거는 셋이다.

1. **미검증 전제가 없다.** ㄴ 은 M1 에 걸려 있고, ㄷ 는 그 질문을 회피한다.
2. **락이 필요 없다.** 세션 내 직렬화가 구조적으로 따라온다 — 클라 백프레셔(⑥)를 안 고쳐도 안전하다.
3. **아키텍처 방향과 일치한다.** [`architecture-review-2026-08-11.md`](./architecture-review-2026-08-11.md) 가
   «상태의 소유 단위가 틀렸다» 로 진단했고, ㄷ 는 **상태와 실행 단위를 둘 다 세션에 붙인다.**
   나중에 스트림 전환(연결 = 세션)으로 갈 때도 **같은 방향**이라 버려지지 않는다.

**대가는 §3-3 하나** — 동시 실행 수를 직접 제한해야 한다. 그런데 그건 **어차피 P3(입장 제한)에서 해야 할 일**이라
새 부담이라기보다 **두 작업이 같은 자리에서 만나는 것**에 가깝다.

⚠️ 반대로 ㄴ 을 고를 이유: **코드 변경이 `mediapipe_detector.py` 한 파일에 갇힌다.**
`pose.py` 의 실행 경로를 안 건드리므로 면적이 작다([[feedback_minimize_python_changes]]).
M1 이 통과하고 «지금은 면적을 최소화하고 싶다» 면 ㄴ 이 합리적이다.
