## 0. 배경 — 이미 반쯤 닫혀 있었다

`ai-coresidency-capacity.md` §1이 Q5를 처음 정의했다: *"관측 스택을 같이 올리면 얼마를 더
먹나 — 2026-08-08에 obs를 분리한 이유가 이것인데, 비용을 숫자로 적은 적이 없다."*

2026-08-18 세션분산 라운드가 **쓰기 경로(HTTP 세션 시작·저장) 기준**으로 이미 답했다 —
처리량 차이 **−0.05%**(판 간 산포보다 작음), 관측 스택 CPU **1% 미만**. 그런데 그 문서 §H5가
스스로 못박는다: *"AI 부하 기준 Q5는 그대로 빈칸이다 — 두 부하는 병목이 다르다."*

**이 문서가 그 빈칸 하나를 설계한다.**

### 왜 병목이 다를 수 있는가

쓰기 경로는 MySQL 커밋(fsync·락 대기)이 병목이라 CPU 여유가 있다 — 관측 스택이 CPU를 조금
더 써도 병목(디스크 I/O)과 안 겹친다. AI 경로는 다르다 — `ai-process-ceiling-cause.md` §8이
이미 실측으로 확정했듯 **AI 프로세스가 GIL로 CPU를 거의 포화시킨다**(rho≥0.939, 순수 파이썬
경로가 정확히 1.04 vCPU에서 막힘). CPU가 이미 병목인 워크로드에서는 `docker stats`·
`mysqld_exporter`의 스크레이프 자체가 같은 자원(CPU 사이클, cgroup 스케줄러 큐)을 놓고 AI와
경쟁한다 — 쓰기 경로의 "1% 미만"이 그대로 옮겨진다는 보장이 없다.

## 1. 새로 만들 게 없다 — 팔 D가 이미 rig에 있다

`ai-coresidency-capacity.md` §3의 팔 설계(A 유휴 동거·B ghz 부하·C 캡·**D = C + 관측 스택**)에서
**팔 D는 이미 코드로 존재한다**:

```
# loadtest/results/coresidency-2026-08-15/coresidency_sweep.sh:183
D) $SSH "cd $REPO_DIR && docker compose -f docker-compose.yml -f docker-compose.cap.yml --profile obs up -d" ;;
```

`--profile obs`가 올리는 서비스는 `docker-compose.yml`에 고정돼 있다 — `prometheus`(v3.1.0)·
`grafana`(v11.5.1)·`mysqld-exporter`(v0.16.0), 셋 다 `profiles: ["obs"]`.

**즉 이 실험은 "새 rig을 만드는 일"이 아니라 "기존 8레벨 라틴 방격 스윕에 팔 D를 켜서 다시
돌리는 일"이다.** 2026-08-16 라운드가 팔 D를 뺀 이유는 기술적 장애물이 아니라 **비용**이었다
(§3 후술).

### 부하 경로 (§2에서 이미 확정된 것, 그대로 재사용)

```
부하기 ──POST /api/v1/pose (8000, AI_PUBLIC_TOKEN)──> AI 컨테이너
                                                        │ rep 완성 시
                                                        ↓ gRPC SavePoseDataBatch
                                                     Spring ──> MySQL
```

`load_ai.py`(AI 프레임 부하) + ghz `SavePoseDataBatch`(Spring·MySQL 부하, rep 상태기계에
안 기대는 별도 갈래) — 둘 다 §2가 이미 확정한 대로, **정한 비율**이지 실사용 비율이 아니라는
단서도 그대로 물려받는다.

## 2. 판정 기준 — 축소한 격자

원 설계의 8레벨(부하 크기 스윕) × 팔(C/D) 전체를 다시 도는 것은 Q5 하나에 답하기엔 과하다 —
그게 "+19판·+42분"의 정체다(전체 스윕에 팔 D를 끼워 넣는 견적). Q5가 묻는 것은 "몇 %인가" 하나고,
이건 **부하 크기 스윕이 아니라 팔 C↔D 대조 하나**로 충분하다.

| | 값 |
|---|---|
| 부하 수준 | **하나만 고정** — 8레벨 스윕의 plateau 근방(팔 B가 267.6~316.5 fps로 포화되던 그 수준). CPU 경합이 가장 뚜렷할 지점이라 관측 스택 비용도 가장 잘 보인다. 낮은 부하에서 재면 "차이 없음"이 나와도 그게 관측 스택이 싸서인지 애초에 CPU가 안 바빠서인지 못 가른다 |
| 팔 | **C**(캡 있음, obs 없음) vs **D**(캡 있음, obs 있음) — [#212](https://github.com/Shadowfit/init/issues/212)·[#214](https://github.com/Shadowfit/init/issues/214) 적용 상태를 그대로 쓴다. 캡 없는 A/B 조합은 이 질문에 안 필요하다 |
| 반복 | **팔당 최소 3판, 순서 반전**(C D / D C / C D) — [[feedback_measure_design_needs_repeats]]. 원 라운드가 "팔 A가 2시간에 걸쳐 +16% 흘렀다"는 걸 실측으로 확인한 바로 그 문서라, 판 순서와 팔을 분리 안 하면 같은 함정에 걸린다 |
| 지표 | AI 처리량(fps, `load_ai.py` 자체 카운터) · AI CPU%(`docker stats`) · (있으면) `frame_path` 계측 구간별 지연 |
| 게이트 | 8레벨 스윕이 쓰던 것과 동일 — 검출 성공률 단언, setup_fail 0 |

이 정도 축소면 **3~4판 × 판당 수 분 = 총 20~30분** 규모로 예상된다(8레벨 전체 스윕 대비
"+19판·+42분"보다 훨씬 작다) — 단 이 견적은 계산일 뿐 실측이 아니다. 실제 판 길이는
`coresidency_sweep.sh`의 판당 지속시간 설정을 확인해야 정확해진다.

## 3. 비용 대비 가치 — 정직하게, 착수 안 하는 것도 선택지다

**이 갭이 지금 막고 있는 결정은 없다.** `ai-coresidency-capacity.md`의 다른 다섯 질문(Q1~Q4,
그리고 §6의 "2라운드 판정")은 전부 닫혔고, 이 프로젝트의 실제 배포(`docker-compose.prod.yml`)는
관측 스택을 `--profile obs`로 이미 분리해서 운영 중이다 — 즉 "관측 스택을 상시 켜둘지 말지"
결정은 이미 "필요할 때만 켠다"로 나 있고, 이 실험은 그 결정을 재확인하거나 뒤집는 게 아니라
**숫자를 하나 채우는 것**이다.

값어치가 있는 경우:
- **포트폴리오 서사** — "AI CPU가 이미 GIL로 포화된 워크로드에서 관측 오버헤드를 실측으로
  검증했다"는 문장은 근거 없이 "관측 스택은 가볍다"고 적힌 곳(있다면)을 실측으로 바꾼다
- **운영 판단** — 부하가 실제로 plateau 근처까지 올라가는 상황(장애 대응 중 관측 스택을 평소보다
  세게 볼 때 등)에서 "관측 자체가 AI를 더 죽이는가"에 실측으로 답할 수 있다

값어치가 낮은 경우:
- 쓰기 경로 결과(−0.05%, 1% 미만)가 이미 "관측 스택은 싸다"는 사전을 강하게 세워뒀다 —
  AI 경로에서 그 사전이 크게 틀릴 개연성 자체가 낮다(다르다면 "얼마나 다른가"의 문제지
  "다른가 아닌가"는 아닐 가능성이 높다)
- AWS 라운드 하나를 새로 여는 고정비(부트스트랩·시딩·리허설)가 실제 측정 시간(20~30분)보다
  크다 — 다른 라운드(예: [`ai-worker-load-soak-experiment.md`](./ai-worker-load-soak-experiment.md))에
  **얹어서** 돌릴 수 있으면 고정비를 나눠 낼 수 있지만, 단독 라운드로 열면 배보다 배꼽이 크다

**추천: 단독 라운드로 열지 말고, 다음에 같은 스펙(캡 있는 c7i.4xlarge 또는 동등 박스)의 EC2가
뜰 때 從 항목으로 얹는다.** [`AWS-RIDE-ALONG.md`](../../loadtest/AWS-RIDE-ALONG.md) §1 從 R9로
이미 그렇게 등록돼 있다 — 이 문서는 그 등록의 실행 설계이지, 새로 인프라를 켤 근거는 아니다.
