## 0. 한 줄 요약

**«심사» 방향은 맞다. 그런데 심사 흐름은 테이블·API·권한이 붙는 일이고, 그걸 만드는 동안 구멍이 열려 있으면 안 된다.**

그래서 이 문서는 하나를 둘로 나눈다:

| | 무엇 | 크기 |
|---|---|---|
| **1단계 (핫픽스)** | 가입이 `role` 을 **무시**하게 한다 — 서버가 `USER` 로 고정 | 실질 한 줄 |
| **2단계 (설계)** | 관리자가 되는 **정식 경로**를 만든다 — 아래 §2 의 선택 | 스키마 + API + 권한 |

1단계는 2단계의 일부다. **어떤 심사 흐름을 고르든 «가입 시 자기 부여» 는 없어져야 하므로**, 1단계를 먼저 내는 것이 2단계의 어떤 선택도 막지 않는다.

> 🔴 **지금 관리자가 되는 경로는 이 취약점 하나뿐이다.** `grep` 으로 확인했다 — `role` 을 쓰는 곳은 `MemberService:66`(로그인 시 읽기)과 `:107`(가입 시 쓰기)뿐이고, **승격 API 도 시딩도 없다.** 즉 1단계를 내는 순간 **관리자를 새로 만들 방법이 사라진다.** §3(부트스트랩)이 같이 가야 하는 이유다.

## 1. 지금 무슨 일이 일어나는가

```
POST /member/signup  { ..., "role": "ADMIN" }        ← permitAll (application.yml:109)
  → MemberService:107   .role(dto.getRole())          ← 검증 없음
  → CustomUserDetails:25  "ROLE_" + role              ← ROLE_ADMIN 이 만들어진다
  → @PreAuthorize("hasRole('ADMIN')")                 ← 통과한다
```

가드 5곳(`AdminMember`·`AdminSession`·`AdminExercise`·`AdminStats`·`Exercises`)이 **정상 동작하는데도** 무의미하다. 공격자가 그 가드가 요구하는 권한을 **스스로에게 부여**하기 때문이다. 특히 `AdminMemberController` 는 전체 회원의 email·username 을 반환한다.

> ⚠️ **아직 실제로 뚫어보지는 않았다.** 위는 코드 3곳을 이어 읽은 판정이다([#138](https://github.com/Shadowfit/init/issues/138) 의 「미검증」 절). 1단계를 낼 때 **재현 테스트를 같이 쓰는 것**이 이 판정을 확정하는 방법이다.

## 2. 2단계 — 심사 흐름의 모양 (선택지)

네 안 모두 **가입은 항상 `USER`** 라는 전제를 공유한다. 다른 것은 «그다음에 어떻게 올라가나» 뿐이다.

| | 모양 | 스키마 | 신규 API | 이력 | 비고 |
|---|---|---|---|---|---|
| **ㄱ** | **별도 신청 테이블** `admin_access_request`(member_id·status·reason·requested_at·reviewed_by·reviewed_at) | 테이블 1 | 신청 1 + 조회 1 + 승인/거부 1 | ✅ 누가 언제 무엇을 승인했는지 남음 | 사용자가 말한 «심사» 에 가장 가깝다 |
| **ㄴ** | **members 에 플래그** `admin_requested`·`admin_requested_at` | 컬럼 2 | 신청 1 + 승인 1 | ❌ 거부 이력·심사자가 안 남음 | 가볍지만 «심사» 의 핵심(누가 승인했나)이 빠진다 |
| **ㄷ** | **초대 코드** — 관리자가 코드를 발급, 그 코드로만 ADMIN 가입 | 테이블 1 | 발급 1 + (가입에 코드 필드) | 🔶 코드 사용 이력은 남음 | 왕복이 없어 단순. 다만 **심사가 아니라 사전 승인**이다 |
| **ㄹ** | **승격 API 만** — 신청 개념 없이 기존 관리자가 지정 | 없음 | 승격 1 | 🔶 감사 로그를 따로 붙이면 남음 | 가장 작다. 관리자가 «누구를 올릴지» 를 이미 알고 있을 때만 성립 |

### 무엇을 «권한» 으로 두고 무엇을 «상태» 로 둘지

**`UserRole` 에 `PENDING_ADMIN` 같은 값을 추가하는 안은 넣지 않았다.** `role` 은 권한이고 신청은 상태다. 섞으면 `hasRole()` 판정이 «심사 중» 을 어떻게 볼지 매번 물어야 하고, 그 판단이 5곳에 흩어진다. 지금 enum 이 `USER`·`ADMIN` 둘뿐인 것은 지켜야 할 단순함이다.

### 추천

**ㄱ (별도 신청 테이블).** 사용자가 말한 «서버가 심사» 를 그대로 표현하고, **거부 이력과 심사자가 남는다** — 권한 부여는 나중에 «누가 이 사람을 올렸나» 를 물을 일이 생기는 영역이라 이력이 값을 한다. ㄴ 은 그 이력이 빠져서 «심사» 라고 부르기 애매하고, ㄹ 은 신청 개념이 없어 사용자 방향과 다르다.

다만 **ㄹ 이 압도적으로 작다.** 관리자가 팀원 2~3명뿐이고 앞으로도 그럴 거라면, 신청·승인 왕복은 쓰이지 않는 기능이 된다. 🔶 **이건 «앞으로 관리자가 몇 명이 될 것인가» 에 달렸고, 그건 내가 모른다.**

## 3. 부트스트랩 — 첫 관리자는 누가 승인하나

**어떤 안을 골라도 «승인할 관리자» 가 먼저 있어야 한다.** 지금은 0명이다.

| | 방법 | 평가 |
|---|---|---|
| **ㄱ** | **수동 SQL 1회 + 문서화** — `UPDATE users SET role='ADMIN' WHERE email=?` | 🟢 **추천.** 면적 0, 시크릿이 코드에 안 남는다. «최초 1회는 손으로» 는 흔한 운영 패턴이다 |
| **ㄴ** | 시딩 마이그레이션에 관리자 계정 | 🔴 **비추천.** 비번 해시를 시드에 박으면 **모든 배포가 같은 관리자 계정을 갖는다** — `.env.example` 의 `JWT_SECRET` placeholder 와 같은 함정이고, 취약점을 다른 취약점으로 바꾸는 것이다 |
| **ㄷ** | 환경변수 이메일이 첫 로그인 시 자동 승격 | 🟡 가능하지만 «환경변수를 아는 사람이 관리자» 라 결국 시크릿 관리 문제로 되돌아온다 |

## 4. 1단계를 먼저 내는 것에 대해

**2단계 없이 1단계만 내면 관리자를 새로 만들 수 없다.** 그래도 먼저 내는 것을 추천하는 이유:

- 개발 DB 에는 이미 관리자 계정이 있을 것이다(관리자 API 를 만들고 테스트했으므로). **기존 관리자는 영향을 받지 않는다** — 이미 `role='ADMIN'` 인 행은 그대로다
- 운영 DB 는 **아직 없다**([`../19-deployment.md`](../19-deployment.md) §1 — 배포 호스트 미정). 지금은 «만들 수 없어서 곤란한» 상황 자체가 안 생긴다
- 2단계는 며칠이 걸리는데, 그동안 구멍을 열어두는 것과 «새 관리자를 SQL 로 만들어야 하는 불편» 을 저울질하면 후자가 싸다

**1단계 구성** (제안):

| | 내용 |
|---|---|
| `MemberRequestDto` | `role` 필드 제거. 고정을 «필드가 없다» 는 사실로 보장한다 |
| `MemberService.signup` | `.role(dto.getRole())` 호출 제거 → `Member` 의 `@Builder.Default UserRole.USER` 가 적용된다 |
| 프론트 | `login.tsx:226` 의 `role: 'USER'` 와 `types/auth.ts` 의 `SignupRequest.role` 제거. **안 지워도 깨지지는 않는다**(Spring Boot 는 기본적으로 `FAIL_ON_UNKNOWN_PROPERTIES` 를 끈다) — 구버전 앱 호환을 위해 서버는 무시하는 쪽이 맞다 |
| 테스트 | ① `role:"ADMIN"` 을 보내도 저장된 권한이 `USER` 인지 ② 그 계정으로 관리자 API 가 403 인지. **②가 [#138](https://github.com/Shadowfit/init/issues/138) 의 「미검증」 을 닫는다** |
