## 2. 범위 — ✅ A·B·D 확정, C 보류 (2026-08-04)

| # | 화면 | 상태 | 근거 |
|---|---|:--:|---|
| A | **회원 목록** | ✅ **구현 대상** | 필터·정렬 조합이 가장 많아 QueryDSL 근거가 가장 셈 |
| B | **세션 목록** | ✅ **구현 대상** | 운영 관점에서 실사용 가치(실패·타임아웃 세션 추적) |
| C | 운동/영상 관리 | ⏸ **보류** | 등록 API만 있음 — 목록·수정·삭제 3개를 추가해야 CRUD가 완성된다 |
| D | **대시보드 통계 위젯** | ✅ **구현 대상** | 조건 고정 집계 — QueryDSL 대상은 아니나(아래) **집계 비용이라는 별개 축** |

**자르는 기준을 "QueryDSL 대상이냐"로 잡지 않았다.** 그 기준이면 D 가 먼저 잘리는데, D 는 다른 이유로 남는다.

- **A·B** — §4-1 에서 넣은 인덱스 2종이 정확히 이 둘의 기본 진입 쿼리(`users(created_at)` / `exercise_sessions(status, start_time)`)를 겨냥한 것이다. 인덱스 근거와 짝이 맞는다
- **D** — 목록은 `LIMIT 20` 이라 인덱스만 타면 20건만 만지고 끝나지만, **집계는 조건에 걸린 행을 전부 만져야 답이 나온다.** 인덱스로 범위를 줄여도 줄어든 범위 전체를 읽는다. 그래서 목록에는 없는 결정이 따라온다 — 매번 세느냐 / 사전집계 테이블을 두느냐 / 캐시에 TTL 을 거느냐. 셋 다 **정합성을 얼마나 포기하느냐**의 문제고, "관리자 대시보드 숫자는 몇 분 늦어도 된다"가 그 근거가 된다
- **C** — 동적 조건이 있어 QueryDSL 대상이긴 하나 본질은 CRUD 추가다. 인덱스 축에도 집계 축에도 닿지 않는다. 얻는 것이 기능 완결성뿐이라 뒤로 뺐다

> ⏸ 는 폐기가 아니라 **분리**다. A·B 를 끝내면 공통 페이징 DTO·QueryDSL 배선·예외 처리가 이미 서 있으므로 **C 는 그 위에 얹는 비용으로 줄어든다.** 그때 #4 CD·#5 외부 통합과 같은 시간대에 놓고 다시 견주는 편이 낫다.

### 2-1. D 의 측정은 이 프로젝트에서 성립한다

합성 데이터의 고질적 한계는 값 분포가 균일해 **선택도가 현실과 다르다**는 것이고, 그래서 §4-1 의 읽기 이득은 시간 수치를 내지 못하고 `EXPLAIN` 계획 변화까지만 근거로 삼았다.

**집계 비용은 이 한계에 덜 걸린다.** 비용이 "몇 행을 만졌나"에 거의 비례하고 그 값이 무엇인지에는 크게 좌우되지 않기 때문이다. 즉 **D 는 시간 수치를 낼 수 있는 첫 항목**이 될 수 있다.

> 단, 조건이 붙는다 — 집계 *결과값*(평균 싱크율 75.00 같은)은 합성 템플릿의 산물이라 아무 의미가 없다. 낼 수 있는 것은 **소요 시간과 접근 방식**뿐이다.

❌ **스코프 밖**: 관리자 계정 관리(가입·권한 부여), 감사 로그(audit log), 공지/QnA 관리, 통계 CSV 내보내기. 전부 "있으면 좋지만 없어도 화면이 성립"한다.

## 4. ⚠️ 진짜 난점 — 기존 인덱스가 관리자 조회에 하나도 안 듣는다

`mysql/schema.sql`의 인덱스를 전부 확인한 결과:

| 인덱스 | 선두 컬럼 |
|---|---|
| `idx_session_member_starttime (member_id, start_time)` | `member_id` |
| `idx_session_member_exercise_status_start (member_id, exercise_id, status, start_time)` | `member_id` |
| `idx_session_member_status (member_id, status)` | `member_id` |
| `idx_session_timestamp (session_id, timestamp_sec)` | `session_id` |
| `users` 테이블 | **보조 인덱스 없음** (PK + username/email UNIQUE만) |

**모든 세션 인덱스가 `member_id` 선두다.** 이는 지금까지의 모든 조회가 "내 데이터"였기 때문에 올바른 설계였다. 그런데 관리자 목록은 **`member_id` 조건 없이 전체를 훑으며 상태·기간으로 거른다** → 위 복합 인덱스는 선두 컬럼이 안 맞아 **전혀 타지 않는다.** 회원 목록도 `users`에 보조 인덱스가 없어 정렬·필터가 전부 풀스캔 + filesort가 된다.

> 이건 QueryDSL로 해결되는 문제가 **아니다.** 쿼리 빌더는 SQL을 조립할 뿐 실행 계획을 바꾸지 않는다. ([`querydsl-adoption.md`](./querydsl-adoption.md) §4-2 ⑤ — 동적 조립 위험 중 QueryDSL이 못 고치는 항목)

**게다가 조합 수만큼 곱해진다.** 회원 목록 필터 5개면 가능한 쿼리가 32가지이고, 각각 실행 계획이 다르다. 인덱스가 없으면 32가지 전부가 인덱스 없이 돌고, 인덱스를 추가해도 **일부 조합만** 타게 된다 — "어떤 필터 조합에서만 느리다"는 형태의 문제가 나온다. 아래 대응안을 고를 때 "모든 조합을 커버하는 인덱스는 없다"를 전제로 판단할 것.

**대응 선택지**

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| **ㄱ ← ✅ 채택 (2026-08-03)** | 관리자 전용 인덱스 추가 — `(status, start_time)`, `users(created_at)` | 쓰기 경로에 인덱스 유지 비용 추가. 세션 INSERT는 이 프로젝트의 **핵심 쓰기 축**이라 공짜가 아님 |
| ㄴ. 인덱스 없이 감수 | 관리자 트래픽은 극소(관리자 몇 명) | 데이터가 쌓이면 관리자 화면만 느려짐. 운영상 허용 가능 여부 판단 필요 |
| ㄷ. 목록을 기간 필수로 제한 | "최근 30일" 같은 기본 기간 강제 | **반환 행 수만 줄어들 뿐 스캔 범위는 그대로다** — `start_time` 선두 인덱스가 없으면 전체를 훑은 뒤 기간으로 거른다. 정렬·전송 비용은 줄지만 근본 해결이 아니라 ㄱ의 보조책 (초기 서술은 "스캔 범위를 구조적으로 제한"이었으나 오류 — 외부 리뷰로 정정) |

**포폴 관점 메모**: 이 항목은 "동일 테이블에 **읽기 주체가 둘**(사용자 축 vs 관리자 축)이면 인덱스 전략이 갈린다"는 서사가 된다. QueryDSL 도입보다 이쪽이 면접에서 훨씬 무겁다.

### 4-1. ✅ ㄱ 채택 — 실측 근거 (2026-08-03, **rig 결함 정정 후 재측정 2026-08-04**)

> 🔴 **이 절은 2026-08-04 에 통째로 갱신됐다.** 초판(08-03)의 rig 에 방법론 결함 3건이 있었고, 외부 리뷰([PR #104](https://github.com/Shadowfit/init/pull/104) CodeRabbit)로 발견해 고친 뒤 다시 쟀다. **읽기 결론은 유지되고 쓰기 결론은 뒤집혔다.** 무엇이 왜 틀렸는지는 §4-2 에 남긴다 — 같은 실수를 반복하지 않기 위해서다.

**박힌 코드**: `mysql/schema.sql`

```sql
INDEX idx_session_status_starttime (status, start_time)   -- exercise_sessions
INDEX idx_users_created_at (created_at)                   -- users (보조 인덱스 최초)
```

**컬럼 순서 근거** — `status` 는 등치, `start_time` 은 범위·정렬이다. 등치를 선두에 둬야 매칭 행이 한 덩어리로 뭉치고 그 안에서 `start_time` 이 정렬돼 있어, 범위 탐색과 `ORDER BY` 가 둘 다 인덱스 순서를 그대로 쓴다. 뒤집으면 날짜마다 status 가 섞여 있어 범위에 걸린 것을 전부 읽고 나서 걸러야 한다. 기존 `idx_session_member_exercise_status_start` 도 같은 규칙(등치 3 → 범위 1)이라, 이번 인덱스는 새 원칙이 아니라 **`member_id` 가 빠진 자리에서 다음 등치 컬럼이 선두가 된 것**이다.

`users` 에 다른 필터(페르소나·레벨·온보딩)를 넣지 않은 이유는 전부 enum/boolean 이라 **선택도가 낮아 선두로 세울 값이 없어서**다.

**실험**: [`../../loadtest/measure_admin_index.sh`](../../loadtest/measure_admin_index.sh) — 회원 20만 / 세션 100만 스크래치 테이블. before 상태에 **실테이블의 기존 세션 인덱스 3종을 전부** 재현해 "관리자 인덱스만 없는 상태"를 비교 대상으로 삼았다.

#### ✅ 읽기 — 실행 계획이 바뀐다 (채택의 실제 근거)

| 쿼리 | | `type` | `key` | `rows` | `filtered` | `Extra` |
|---|---|---|---|---|---|---|
| 회원 목록 | before | `ALL` | — | 199,430 | **11.11%** | Using where; **Using filesort** |
| | after | `range` | `idx_..._users_created_at` | **99,715** | **100%** | Using index condition; **Backward index scan** |
| 세션 목록 | before | `index` | `idx_..._member_exercise_status_start` | 995,392 | **8.33%** | Using where; Using index; **Using filesort** |
| | after | `range` | `idx_..._status_starttime` | **272,976** | **100%** | Using index condition; **Backward index scan** |

세 가지가 핵심이다:

- **`filesort` 가 사라졌다** — 인덱스 순서가 곧 정렬 순서라 백워드 스캔으로 `ORDER BY ... DESC` 가 해결된다
- **`filtered` 가 8~11% → 100%** — 읽은 행의 90% 를 버리던 것이 전부 정답이 됐다
- **`rows` 가 줄었다** — 세션 99.5만 → 27.3만, 회원 19.9만 → 10.0만

> **세션 목록 before 가 `ALL` 이 아니라 `index` 인 것에 주의.** 초판은 `ALL` 이라 적었으나 그건 rig 가 기존 인덱스 하나를 빠뜨려 만든 그림이었다(§4-2). 실제로는 옵티마이저가 **`idx_..._member_exercise_status_start` 를 커버링 인덱스로 삼아 전수 스캔**한다 — `member_id` 선두라 탐색에는 못 쓰지만 필요한 컬럼이 다 들어 있어 테이블 접근은 피한다. **"인덱스를 하나도 못 탄다"가 아니라 "탐색에 못 쓰고 전수 스캔용으로만 쓴다"** 가 정확한 서술이고, 개선의 의미는 그대로다 — 99.5만 건 전수 스캔 + filesort 에서 27.3만 건 범위 스캔 + 정렬 불필요로 바뀌었다.

> ✅ **`rows` 를 이번에는 직접 비교한다.** 초판은 before 측정 후 쓰기 라운드가 같은 테이블에 행을 추가해 after 가 더 큰 테이블에서 실행됐으므로 비교를 금지했다. 재측정 rig 는 쓰기를 **별도 쌍둥이 테이블**로 보내므로 `sessions_scale`·`users_scale` 이 두 시점에 크기가 같다. 초판의 그 단서는 해소됐다.

#### 🔴 쓰기 — 방향조차 관측되지 않는다 (초판 결론 철회)

세션 INSERT 20,000행 × 12라운드(워밍업 4라운드 폐기), 인덱스 유무만 다른 쌍둥이 테이블에 **라운드 교대**로 적재. 단위 ms:

| | min | p50 | avg | max |
|---|---|---|---|---|
| 인덱스 없음 | **993** | 2,878 | 2,884 | 5,888 |
| 인덱스 있음 | 1,241 | **1,995** | **2,237** | **3,983** |

**min 만 "인덱스 없음"이 빠르고 p50·avg·max 는 전부 "인덱스 있음"이 빠르다.**

이건 인덱스가 INSERT 를 빠르게 한다는 뜻이 아니다 — **그럴 수 없다.** B+tree 를 하나 더 유지하는 비용은 0보다 크다. 그러므로 이 표가 말하는 것은 하나뿐이다: **이 환경의 노이즈가 인덱스 유지비용보다 훨씬 커서 신호를 완전히 덮는다.**

근거는 표 안에 있다. **조건이 같은 쪽 내부의 편차**를 보면 된다.

- 인덱스 없음: 993 ~ 5,888ms — 같은 조건인데 **5.9배**
- 인덱스 있음: 1,241 ~ 3,983ms — **3.2배**

측정하려는 차이보다 조건 내부 편차가 크면, 어느 통계량을 고르느냐에 따라 결론이 뒤바뀐다. 실제로 min 을 고르면 "+25% 느려진다"가 나오고 p50 을 고르면 "31% 빨라진다"가 나온다. **둘 다 이 데이터로 정당화되므로 둘 다 쓰면 안 된다.**

원인은 환경이다 — i3-6100 2물리코어에 MySQL 이 동거해 라운드마다 CPU 경합이 다르게 걸린다([`./load-test-glossary.md`](./load-test-glossary.md) 의 환경 한계와 동일 계열).

> **초판(08-03)은 여기서 "느려지는 방향은 일관된다(네 지점 전부 after 가 크다)"고 썼다. 철회한다.** 그 일관성은 rig 결함이 만든 인공물이었다(§4-2). 지금 말할 수 있는 것은 **"인덱스 유지비용은 구조적으로 0보다 크지만, 이 환경에서는 그 크기를 관측할 수 없다"** 까지다.

**그럼에도 ㄱ 을 유지하는 근거** — 채택 근거는 애초에 쓰기가 아니라 읽기였다. 위 실행 계획 변화는 rig 결함과 무관하게 재현됐고, 쓰기 쪽에서 새로 알게 된 것은 "비용이 없다"가 아니라 "**이 장비로는 못 잰다**"이다. 비용의 존재는 구조로 알고 크기는 모른다 — 그 상태로 채택하는 것이 정직한 선택이며, 크기가 의사결정을 바꿀 상황(쓰기 지연이 실제 문제로 관측될 때)이 오면 그때 분리된 환경에서 잰다.

#### 🔴 측정하지 않은 것

1. **AWS 분리 배포 재검증** — 이 프로젝트는 커넥션 풀 사이징에서 **로컬 결론이 EC2 2대 환경에서 반전된 전례**가 있다([`./pose-ingest-downsampling.md`](./pose-ingest-downsampling.md) §5-1(7)).
   > 🔴 **초판은 여기서 "얻을 것은 배수의 정밀도뿐이라 미루지 않았다"고 적었다. 그 근거는 약해졌다.** 재측정 결과 배수가 아니라 **방향조차 안 나오기** 때문이다. 즉 분리 환경에서 재는 것은 정밀도를 높이는 일이 아니라 **처음으로 신호를 얻는 일**이다. 그럼에도 채택은 유지한다 — 근거가 읽기이고, 쓰기 비용의 크기는 현재 어떤 결정도 바꾸지 않기 때문이다. **미측정임을 알고 채택하는 것과, 쟀다고 믿고 채택하는 것은 다르다.**
2. **읽기 시간 수치** — 합성 데이터가 단일 템플릿 복제라 `status` 분포가 균일하다(COMPLETED 50% / FAILED 25% / IN_PROGRESS 25%). 실제로는 COMPLETED 가 대부분이고 FAILED 는 소수일 텐데, 인덱스 효용은 선택도에 달려 있어 **옵티마이저 카디널리티 추정이 현실과 달라진다.** 그 위에서 잰 ms 는 "빨라졌다"의 근거가 못 되므로 `EXPLAIN` 계획 변화까지만 근거로 삼았다
3. **필터 조합별 커버리지** — §4 본문대로 "모든 조합을 커버하는 인덱스는 없다". 이번 두 인덱스는 **각 화면의 기본 진입 쿼리**(기간+최신순 / 상태+기간+최신순)를 겨냥한 것이고, 나머지 조합이 어떤 계획을 타는지는 측정하지 않았다

#### ㄷ 은 어떻게 되나

**폐기하지 않되 단독으로 쓰지 않는다.** ㄱ 이 스캔을 줄이고 ㄷ 이 전송·정렬 대상을 줄이는 조합이면 각자 제 역할을 한다. 다만 ㄷ 을 단독으로 넣으면 **"고쳤다"는 착각**을 만든다 — 반환 행이 줄어 측정상 개선이 보이지만 스캔 범위는 그대로라, 테이블이 커지면 같은 문제가 돌아온다. 이 문서 자신이 초기 서술에서 그 함정에 빠졌다가 외부 리뷰로 정정한 이력이 있다(§4 표).

### 4-2. 측정 장치(rig) 결함 3건 — 무엇이 왜 틀렸나 (2026-08-04)

> **용어**: 여기서 *측정 장치(rig)* 는 실험을 돌리는 판 전체 — 스크립트 + 스크래치 테이블 + 시딩 데이터 + 측정 절차 — 를 가리킨다. **결과가 틀린 것과 결과를 만든 장치가 틀린 것은 다르다.** 아래는 후자이고, 그래서 숫자를 다시 해석하는 게 아니라 장치를 고쳐 다시 쟀다.

초판(08-03)의 측정 스크립트에 결함 3건이 있었다. [PR #104](https://github.com/Shadowfit/init/pull/104) 의 CodeRabbit 리뷰로 발견해 고치고 다시 쟀다. **셋 다 "결과가 나오긴 나오는데 틀린 것을 재고 있던" 종류**라, 실행이 성공했다는 사실만으로는 드러나지 않았다.

| # | 결함 | 그래서 무엇이 왜곡됐나 |
|:--:|---|---|
| 1 | rig 의 before 테이블에 실테이블 세션 인덱스 3종 중 하나(`idx_..._member_exercise_status_start`)가 빠졌다 | **before 의 INSERT 가 실제보다 싸게 나온다** → 인덱스 추가 비용이 과장된다. 동시에 **읽기 before 가 `ALL` 로 잡혀** "인덱스를 하나도 못 탄다"는 그림이 만들어졌다. 실제 before 는 커버링 인덱스 전수 스캔(`index`)이다 |
| 2 | before/after 를 **같은 테이블에서 순차 측정** | before 측정 라운드가 32만 행을 추가하므로, after 는 **더 큰 테이블 + 다른 버퍼풀 상태**에서 실행된다. 인덱스 유무와 테이블 크기가 함께 변해, 관측된 차이를 인덱스 비용으로 단정할 수 없다 |
| 3 | 실패해도 계속 진행(`set -e` 없음) + 결과 파일이 `/tmp` 고정 경로 | DB 명령이 실패해도 스크립트가 굴러가, **이전 실행의 잔여 파일로 그럴듯한 요약을 찍을 수 있다.** 측정 스크립트에서 이건 틀린 결과보다 나쁘다 — 틀렸다는 신호조차 없다 |

**#1 과 #2 는 방향이 같다.** 둘 다 after 를 불리하게 만든다. 초판이 관측한 *"네 지점 전부 after 가 크다"* 는 일관성은 **두 편향이 같은 쪽으로 겹쳐 만든 인공물**이었을 가능성이 높다. 실제로 교란을 걷어내자 그 일관성이 사라졌다.

**고친 방식**

- **#1** — 실테이블 세션 인덱스 3종을 전부 재현
- **#2** — 같은 행에서 출발하는 **쌍둥이 테이블**(`sessions_noidx` / `sessions_idx`)을 만들어 인덱스 유무만 다르게 하고, **라운드를 교대로** 돌려 시간 드리프트(백그라운드 부하·버퍼 상태 변화)가 양쪽에 똑같이 걸리게 했다. 부수 효과로 `sessions_scale` 이 쓰기에 오염되지 않아 **`rows` 비교가 가능**해졌다
- **#3** — `set -euo pipefail` + `mktemp -d` 전용 작업 디렉터리(종료 시 삭제)

**남는 교훈** — 이 장치의 초판은 *"워밍업을 통제했고, min/p50/avg/max 를 다 내고, 분포 겹침을 스스로 판정한다"* 는 점에서 **측정 위생을 꽤 신경 쓴 스크립트였다.** 그런데도 틀렸다. 통계 처리를 아무리 조심해도 **비교군 구성이 틀리면 그 정성은 전부 무의미**하다는 것이 요점이다. 이 프로젝트의 [`load-test-strategy.md`](./load-test-strategy.md) §7.6 *"1차 측정은 무효 — 워밍업 미통제"* 와 같은 계열의 실패이되, 층이 한 단계 더 아래다.

## 5. 페이징 방식 — 관리자 화면은 keyset이 정답이 아닐 수 있음

[`querydsl-adoption.md`](./querydsl-adoption.md) §4에서 keyset 페이징을 QueryDSL의 강점 근거로 들었으나, **관리자 화면에 한정하면 재고가 필요하다.**

| 방식 | 관리자 화면 적합성 |
|---|---|
| **offset 페이징** | 관리자는 "5페이지로 점프", "전체 1,234건 중" 같은 **총건수·임의 페이지 이동**을 기대한다. keyset은 이걸 구조적으로 못 한다 |
| **keyset 페이징** | 무한 스크롤·피드에 적합. 관리자 테이블 UI와는 궁합이 나쁨 |

🔶 **제안**: 관리자 목록은 **offset + `COUNT(*)`** 로 가고, keyset은 §T2(리포트 히스토리, 모바일 무한스크롤)에서 다룬다. "관리자 = keyset"을 억지로 붙이면 UI 요구와 싸우게 된다.

> 정직 단서: 이 판단은 관리자 UI가 **테이블 + 페이지네이션**이라는 전제 위에 있다. 무한 스크롤로 만들 거라면 뒤집힌다.
