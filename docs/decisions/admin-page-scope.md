## 0. 한 줄 요약

관리자 화면 후보 4개 중 **A 회원 목록 · B 세션 목록으로 범위를 확정**했다(§2, 2026-08-04). 둘 다 **필터 4개 이상**이라 QueryDSL 채택 근거가 성립한다. 다만 이 작업의 진짜 난점은 쿼리 빌더가 아니라 **기존 인덱스가 전부 `member_id` 선두라 관리자 조회에 하나도 듣지 않는다는 것**(§4)이고, 그건 §4-1 에서 인덱스 2종 추가로 처리했다.

**그 인덱스가 어디까지 듣는지를 §4-3 에서 조합별로 쟀다(2026-08-04).** 인덱스는 **모든 조합의 정렬 비용을 없앴지만**(filesort 제거), 스캔을 줄인 것은 가입일이 걸린 경우뿐이다. 그리고 남은 비용은 목록이 아니라 **총건수 쿼리**에 있다 — `LIMIT` 이 없어 대부분의 조합에서 20만 행을 전부 센다.

**그 총건수는 감수하기로 했다(㉮, 2026-08-06).** 프론트를 만든다는 것이 확정돼(§8-6) "총건수가 애초에 요구사항이 아닐 수 있다"는 갈래가 사라졌고, 남은 갈래(페이지 번호 vs 무한 스크롤)는 **되돌리는 비용이 비대칭**이라 기다리지 않는다 — 이미 만들어 둔 offset+count 를 유지하고, 뒤집히면 keyset 을 얹는다. 근거와 그 판단의 구멍(스캔 폭은 쟀지만 **시간은 안 쟀다**)은 §4-3 "2026-08-06" 절.

| # | 화면 | 상태 | 근거 |

**자르는 기준을 "QueryDSL 대상이냐"로 잡지 않았다.** 그 기준이면 D 가 먼저 잘리는데, D 는 다른 이유로 남는다.

- **A·B** — §4-1 에서 넣은 인덱스 2종이 정확히 이 둘의 기본 진입 쿼리(`users(created_at)` / `exercise_sessions(status, start_time)`)를 겨냥한 것이다. 인덱스 근거와 짝이 맞는다
- **D** — 목록은 `LIMIT 20` 이라 인덱스만 타면 20건만 만지고 끝나지만, **집계는 조건에 걸린 행을 전부 만져야 답이 나온다.** 인덱스로 범위를 줄여도 줄어든 범위 전체를 읽는다. 그래서 목록에는 없는 결정이 따라온다 — 매번 세느냐 / 사전집계 테이블을 두느냐 / 캐시에 TTL 을 거느냐. 셋 다 **정합성을 얼마나 포기하느냐**의 문제고, "관리자 대시보드 숫자는 몇 분 늦어도 된다"가 그 근거가 된다
- **C** — 동적 조건이 있어 QueryDSL 대상이긴 하나 본질은 CRUD 추가다. 인덱스 축에도 집계 축에도 닿지 않는다. 얻는 것이 기능 완결성뿐이라 뒤로 뺐다

> ⏸ 는 폐기가 아니라 **분리**다. A·B 를 끝내면 공통 페이징 DTO·QueryDSL 배선·예외 처리가 이미 서 있으므로 **C 는 그 위에 얹는 비용으로 줄어든다.** 그때 #4 CD·#5 외부 통합과 같은 시간대에 놓고 다시 견주는 편이 낫다.

### 2-1. D 의 측정은 이 프로젝트에서 성립한다

합성 데이터의 고질적 한계는 값 분포가 균일해 **선택도가 현실과 다르다**는 것이고, 그래서 §4-1 의 읽기 이득은 시간 수치를 내지 못하고 `EXPLAIN` 계획 변화까지만 근거로 삼았다.

**집계 비용은 이 한계에 덜 걸린다.** 비용이 "몇 행을 만졌나"에 거의 비례하고 그 값이 무엇인지에는 크게 좌우되지 않기 때문이다. 즉 **D 는 시간 수치를 낼 수 있는 첫 항목**이 될 수 있다.

> 단, 조건이 붙는다 — 집계 *결과값*(평균 싱크율 75.00 같은)은 합성 템플릿의 산물이라 아무 의미가 없다. 낼 수 있는 것은 **소요 시간과 접근 방식**뿐이다.

❌ **스코프 밖**: 관리자 계정 관리(가입·권한 부여), 감사 로그(audit log), 공지/QnA 관리, 통계 CSV 내보내기. 전부 "있으면 좋지만 없어도 화면이 성립"한다.

## 4. ⚠️ 진짜 난점 — 기존 인덱스가 관리자 조회에 하나도 안 듣는다

`mysql/schema.sql`의 인덱스를 전부 확인한 결과:

| 인덱스 | 선두 컬럼 |
|---|---|
| `idx_session_member_starttime (member_id, start_time)` | `member_id` |
| `idx_session_member_exercise_status_start (member_id, exercise_id, status, start_time)` | `member_id` |
| `idx_session_member_status (member_id, status)` | `member_id` |
| `idx_session_timestamp (session_id, timestamp_sec)` | `session_id` |
| `users` 테이블 | **보조 인덱스 없음** (PK + username/email UNIQUE만) |

**모든 세션 인덱스가 `member_id` 선두다.** 이는 지금까지의 모든 조회가 "내 데이터"였기 때문에 올바른 설계였다. 그런데 관리자 목록은 **`member_id` 조건 없이 전체를 훑으며 상태·기간으로 거른다** → 위 복합 인덱스는 선두 컬럼이 안 맞아 **전혀 타지 않는다.** 회원 목록도 `users`에 보조 인덱스가 없어 정렬·필터가 전부 풀스캔 + filesort가 된다.

> 이건 QueryDSL로 해결되는 문제가 **아니다.** 쿼리 빌더는 SQL을 조립할 뿐 실행 계획을 바꾸지 않는다. ([`querydsl-adoption.md`](./querydsl-adoption.md) §4-2 ⑤ — 동적 조립 위험 중 QueryDSL이 못 고치는 항목)

**게다가 조합 수만큼 곱해진다.** 회원 목록 필터 5개면 가능한 쿼리가 32가지이고, 각각 실행 계획이 다르다. 인덱스가 없으면 32가지 전부가 인덱스 없이 돌고, 인덱스를 추가해도 **일부 조합만** 타게 된다 — "어떤 필터 조합에서만 느리다"는 형태의 문제가 나온다. 아래 대응안을 고를 때 "모든 조합을 커버하는 인덱스는 없다"를 전제로 판단할 것.

**대응 선택지**

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| **ㄱ ← ✅ 채택 (2026-08-03)** | 관리자 전용 인덱스 추가 — `(status, start_time)`, `users(created_at)` | 쓰기 경로에 인덱스 유지 비용 추가. 세션 INSERT는 이 프로젝트의 **핵심 쓰기 축**이라 공짜가 아님 |
| ㄴ. 인덱스 없이 감수 | 관리자 트래픽은 극소(관리자 몇 명) | 데이터가 쌓이면 관리자 화면만 느려짐. 운영상 허용 가능 여부 판단 필요 |
| ㄷ. 목록을 기간 필수로 제한 | "최근 30일" 같은 기본 기간 강제 | **반환 행 수만 줄어들 뿐 스캔 범위는 그대로다** — `start_time` 선두 인덱스가 없으면 전체를 훑은 뒤 기간으로 거른다. 정렬·전송 비용은 줄지만 근본 해결이 아니라 ㄱ의 보조책 (초기 서술은 "스캔 범위를 구조적으로 제한"이었으나 오류 — 외부 리뷰로 정정) |

**포폴 관점 메모**: 이 항목은 "동일 테이블에 **읽기 주체가 둘**(사용자 축 vs 관리자 축)이면 인덱스 전략이 갈린다"는 서사가 된다. QueryDSL 도입보다 이쪽이 면접에서 훨씬 무겁다.

### 4-1. ✅ ㄱ 채택 — 실측 근거 (2026-08-03, **rig 결함 정정 후 재측정 2026-08-04**)

> 🔴 **이 절은 2026-08-04 에 통째로 갱신됐다.** 초판(08-03)의 rig 에 방법론 결함 3건이 있었고, 외부 리뷰([PR #104](https://github.com/Shadowfit/init/pull/104) CodeRabbit)로 발견해 고친 뒤 다시 쟀다. **읽기 결론은 유지되고 쓰기 결론은 뒤집혔다.** 무엇이 왜 틀렸는지는 §4-2 에 남긴다 — 같은 실수를 반복하지 않기 위해서다.

**박힌 코드**: `mysql/schema.sql`

```sql
INDEX idx_session_status_starttime (status, start_time)   -- exercise_sessions
INDEX idx_users_created_at (created_at)                   -- users (보조 인덱스 최초)
```

**컬럼 순서 근거** — `status` 는 등치, `start_time` 은 범위·정렬이다. 등치를 선두에 둬야 매칭 행이 한 덩어리로 뭉치고 그 안에서 `start_time` 이 정렬돼 있어, 범위 탐색과 `ORDER BY` 가 둘 다 인덱스 순서를 그대로 쓴다. 뒤집으면 날짜마다 status 가 섞여 있어 범위에 걸린 것을 전부 읽고 나서 걸러야 한다. 기존 `idx_session_member_exercise_status_start` 도 같은 규칙(등치 3 → 범위 1)이라, 이번 인덱스는 새 원칙이 아니라 **`member_id` 가 빠진 자리에서 다음 등치 컬럼이 선두가 된 것**이다.

`users` 에 다른 필터(페르소나·레벨·온보딩)를 넣지 않은 이유는 전부 enum/boolean 이라 **선택도가 낮아 선두로 세울 값이 없어서**다.

**실험**: [`../../loadtest/measure_admin_index.sh`](../../loadtest/measure_admin_index.sh) — 회원 20만 / 세션 100만 스크래치 테이블. before 상태에 **실테이블의 기존 세션 인덱스 3종을 전부** 재현해 "관리자 인덱스만 없는 상태"를 비교 대상으로 삼았다.

#### ✅ 읽기 — 실행 계획이 바뀐다 (채택의 실제 근거)

| 쿼리 | | `type` | `key` | `rows` | `filtered` | `Extra` |
|---|---|---|---|---|---|---|
| 회원 목록 | before | `ALL` | — | 199,430 | **11.11%** | Using where; **Using filesort** |
| | after | `range` | `idx_..._users_created_at` | **99,715** | **100%** | Using index condition; **Backward index scan** |
| 세션 목록 | before | `index` | `idx_..._member_exercise_status_start` | 995,392 | **8.33%** | Using where; Using index; **Using filesort** |
| | after | `range` | `idx_..._status_starttime` | **272,976** | **100%** | Using index condition; **Backward index scan** |

세 가지가 핵심이다:

- **`filesort` 가 사라졌다** — 인덱스 순서가 곧 정렬 순서라 백워드 스캔으로 `ORDER BY ... DESC` 가 해결된다
- **`filtered` 가 8~11% → 100%** — 읽은 행의 90% 를 버리던 것이 전부 정답이 됐다
- **`rows` 가 줄었다** — 세션 99.5만 → 27.3만, 회원 19.9만 → 10.0만

> **세션 목록 before 가 `ALL` 이 아니라 `index` 인 것에 주의.** 초판은 `ALL` 이라 적었으나 그건 rig 가 기존 인덱스 하나를 빠뜨려 만든 그림이었다(§4-2). 실제로는 옵티마이저가 **`idx_..._member_exercise_status_start` 를 커버링 인덱스로 삼아 전수 스캔**한다 — `member_id` 선두라 탐색에는 못 쓰지만 필요한 컬럼이 다 들어 있어 테이블 접근은 피한다. **"인덱스를 하나도 못 탄다"가 아니라 "탐색에 못 쓰고 전수 스캔용으로만 쓴다"** 가 정확한 서술이고, 개선의 의미는 그대로다 — 99.5만 건 전수 스캔 + filesort 에서 27.3만 건 범위 스캔 + 정렬 불필요로 바뀌었다.

> ✅ **`rows` 를 이번에는 직접 비교한다.** 초판은 before 측정 후 쓰기 라운드가 같은 테이블에 행을 추가해 after 가 더 큰 테이블에서 실행됐으므로 비교를 금지했다. 재측정 rig 는 쓰기를 **별도 쌍둥이 테이블**로 보내므로 `sessions_scale`·`users_scale` 이 두 시점에 크기가 같다. 초판의 그 단서는 해소됐다.

#### 🔴 쓰기 — 방향조차 관측되지 않는다 (초판 결론 철회)

세션 INSERT 20,000행 × 12라운드(워밍업 4라운드 폐기), 인덱스 유무만 다른 쌍둥이 테이블에 **라운드 교대**로 적재. 단위 ms:

| | min | p50 | avg | max |
|---|---|---|---|---|
| 인덱스 없음 | **993** | 2,878 | 2,884 | 5,888 |
| 인덱스 있음 | 1,241 | **1,995** | **2,237** | **3,983** |

**min 만 "인덱스 없음"이 빠르고 p50·avg·max 는 전부 "인덱스 있음"이 빠르다.**

이건 인덱스가 INSERT 를 빠르게 한다는 뜻이 아니다 — **그럴 수 없다.** B+tree 를 하나 더 유지하는 비용은 0보다 크다. 그러므로 이 표가 말하는 것은 하나뿐이다: **이 환경의 노이즈가 인덱스 유지비용보다 훨씬 커서 신호를 완전히 덮는다.**

근거는 표 안에 있다. **조건이 같은 쪽 내부의 편차**를 보면 된다.

- 인덱스 없음: 993 ~ 5,888ms — 같은 조건인데 **5.9배**
- 인덱스 있음: 1,241 ~ 3,983ms — **3.2배**

측정하려는 차이보다 조건 내부 편차가 크면, 어느 통계량을 고르느냐에 따라 결론이 뒤바뀐다. 실제로 min 을 고르면 "+25% 느려진다"가 나오고 p50 을 고르면 "31% 빨라진다"가 나온다. **둘 다 이 데이터로 정당화되므로 둘 다 쓰면 안 된다.**

원인은 환경이다 — i3-6100 2물리코어에 MySQL 이 동거해 라운드마다 CPU 경합이 다르게 걸린다([`./load-test-glossary.md`](./load-test-glossary.md) 의 환경 한계와 동일 계열).

> **초판(08-03)은 여기서 "느려지는 방향은 일관된다(네 지점 전부 after 가 크다)"고 썼다. 철회한다.** 그 일관성은 rig 결함이 만든 인공물이었다(§4-2). 지금 말할 수 있는 것은 **"인덱스 유지비용은 구조적으로 0보다 크지만, 이 환경에서는 그 크기를 관측할 수 없다"** 까지다.

**그럼에도 ㄱ 을 유지하는 근거** — 채택 근거는 애초에 쓰기가 아니라 읽기였다. 위 실행 계획 변화는 rig 결함과 무관하게 재현됐고, 쓰기 쪽에서 새로 알게 된 것은 "비용이 없다"가 아니라 "**이 장비로는 못 잰다**"이다. 비용의 존재는 구조로 알고 크기는 모른다 — 그 상태로 채택하는 것이 정직한 선택이며, 크기가 의사결정을 바꿀 상황(쓰기 지연이 실제 문제로 관측될 때)이 오면 그때 분리된 환경에서 잰다.

#### 🔴 측정하지 않은 것

1. **AWS 분리 배포 재검증** — 이 프로젝트는 커넥션 풀 사이징에서 **로컬 결론이 EC2 2대 환경에서 반전된 전례**가 있다([`./pose-ingest-downsampling.md`](./pose-ingest-downsampling.md) §5-1(7)).
   > 🔴 **초판은 여기서 "얻을 것은 배수의 정밀도뿐이라 미루지 않았다"고 적었다. 그 근거는 약해졌다.** 재측정 결과 배수가 아니라 **방향조차 안 나오기** 때문이다. 즉 분리 환경에서 재는 것은 정밀도를 높이는 일이 아니라 **처음으로 신호를 얻는 일**이다. 그럼에도 채택은 유지한다 — 근거가 읽기이고, 쓰기 비용의 크기는 현재 어떤 결정도 바꾸지 않기 때문이다. **미측정임을 알고 채택하는 것과, 쟀다고 믿고 채택하는 것은 다르다.**
2. **읽기 시간 수치** — 합성 데이터가 단일 템플릿 복제라 `status` 분포가 균일하다(COMPLETED 50% / FAILED 25% / IN_PROGRESS 25%). 실제로는 COMPLETED 가 대부분이고 FAILED 는 소수일 텐데, 인덱스 효용은 선택도에 달려 있어 **옵티마이저 카디널리티 추정이 현실과 달라진다.** 그 위에서 잰 ms 는 "빨라졌다"의 근거가 못 되므로 `EXPLAIN` 계획 변화까지만 근거로 삼았다
3. ~~**필터 조합별 커버리지**~~ → **✅ 해소 (2026-08-04, §4-3).** 회원 목록 6개 조합을 쟀다. 결과는 예측과 두 군데가 어긋났다 — 검색어 단독도 인덱스를 **정렬용으로는** 쓰고, 진짜 풀스캔은 목록이 아니라 **총건수 쿼리**에서 난다. (세션 목록 B 쪽 조합은 여전히 미측정)

#### ㄷ 은 어떻게 되나

**폐기하지 않되 단독으로 쓰지 않는다.** ㄱ 이 스캔을 줄이고 ㄷ 이 전송·정렬 대상을 줄이는 조합이면 각자 제 역할을 한다. 다만 ㄷ 을 단독으로 넣으면 **"고쳤다"는 착각**을 만든다 — 반환 행이 줄어 측정상 개선이 보이지만 스캔 범위는 그대로라, 테이블이 커지면 같은 문제가 돌아온다. 이 문서 자신이 초기 서술에서 그 함정에 빠졌다가 외부 리뷰로 정정한 이력이 있다(§4 표).

### 4-2. 측정 장치(rig) 결함 3건 — 무엇이 왜 틀렸나 (2026-08-04)

> **용어**: 여기서 *측정 장치(rig)* 는 실험을 돌리는 판 전체 — 스크립트 + 스크래치 테이블 + 시딩 데이터 + 측정 절차 — 를 가리킨다. **결과가 틀린 것과 결과를 만든 장치가 틀린 것은 다르다.** 아래는 후자이고, 그래서 숫자를 다시 해석하는 게 아니라 장치를 고쳐 다시 쟀다.

초판(08-03)의 측정 스크립트에 결함 3건이 있었다. [PR #104](https://github.com/Shadowfit/init/pull/104) 의 CodeRabbit 리뷰로 발견해 고치고 다시 쟀다. **셋 다 "결과가 나오긴 나오는데 틀린 것을 재고 있던" 종류**라, 실행이 성공했다는 사실만으로는 드러나지 않았다.

| # | 결함 | 그래서 무엇이 왜곡됐나 |
|:--:|---|---|
| 1 | rig 의 before 테이블에 실테이블 세션 인덱스 3종 중 하나(`idx_..._member_exercise_status_start`)가 빠졌다 | **before 의 INSERT 가 실제보다 싸게 나온다** → 인덱스 추가 비용이 과장된다. 동시에 **읽기 before 가 `ALL` 로 잡혀** "인덱스를 하나도 못 탄다"는 그림이 만들어졌다. 실제 before 는 커버링 인덱스 전수 스캔(`index`)이다 |
| 2 | before/after 를 **같은 테이블에서 순차 측정** | before 측정 라운드가 32만 행을 추가하므로, after 는 **더 큰 테이블 + 다른 버퍼풀 상태**에서 실행된다. 인덱스 유무와 테이블 크기가 함께 변해, 관측된 차이를 인덱스 비용으로 단정할 수 없다 |
| 3 | 실패해도 계속 진행(`set -e` 없음) + 결과 파일이 `/tmp` 고정 경로 | DB 명령이 실패해도 스크립트가 굴러가, **이전 실행의 잔여 파일로 그럴듯한 요약을 찍을 수 있다.** 측정 스크립트에서 이건 틀린 결과보다 나쁘다 — 틀렸다는 신호조차 없다 |

**#1 과 #2 는 방향이 같다.** 둘 다 after 를 불리하게 만든다. 초판이 관측한 *"네 지점 전부 after 가 크다"* 는 일관성은 **두 편향이 같은 쪽으로 겹쳐 만든 인공물**이었을 가능성이 높다. 실제로 교란을 걷어내자 그 일관성이 사라졌다.

**고친 방식**

- **#1** — 실테이블 세션 인덱스 3종을 전부 재현
- **#2** — 같은 행에서 출발하는 **쌍둥이 테이블**(`sessions_noidx` / `sessions_idx`)을 만들어 인덱스 유무만 다르게 하고, **라운드를 교대로** 돌려 시간 드리프트(백그라운드 부하·버퍼 상태 변화)가 양쪽에 똑같이 걸리게 했다. 부수 효과로 `sessions_scale` 이 쓰기에 오염되지 않아 **`rows` 비교가 가능**해졌다
- **#3** — `set -euo pipefail` + `mktemp -d` 전용 작업 디렉터리(종료 시 삭제)

**남는 교훈** — 이 장치의 초판은 *"워밍업을 통제했고, min/p50/avg/max 를 다 내고, 분포 겹침을 스스로 판정한다"* 는 점에서 **측정 위생을 꽤 신경 쓴 스크립트였다.** 그런데도 틀렸다. 통계 처리를 아무리 조심해도 **비교군 구성이 틀리면 그 정성은 전부 무의미**하다는 것이 요점이다. 이 프로젝트의 [`load-test-strategy.md`](./load-test-strategy.md) §7.6 *"1차 측정은 무효 — 워밍업 미통제"* 와 같은 계열의 실패이되, 층이 한 단계 더 아래다.

### 4-3. ✅ 필터 조합별 인덱스 커버리지 — 측정 완료 (2026-08-04)

A 회원 목록 구현(§3-A 필터 5) 후 측정했다. §4-1 "측정하지 않은 것" 3번의 해소다.

**출발 사실: 인덱스를 넣었다는 것이 모든 조회가 빨라졌다는 뜻이 아니다.** 추가한 것은 `users(created_at)` 하나뿐이고, 그건 **가입일 범위·정렬 전용**이다. 필터 5개의 부분집합 32가지 중 대부분은 이 인덱스와 무관하다 — 라는 것이 측정 전 서술이었고, **절반만 맞았다.**

**실험**: [`../../loadtest/measure_admin_filter_explain.sh`](../../loadtest/measure_admin_filter_explain.sh) + [`AdminMemberExplainCaptureTest`](../../backend/src/test/java/com/shadowfit/repository/member/AdminMemberExplainCaptureTest.java). 회원 20만, `mysql/schema.sql` 원본을 DB 이름만 바꿔 적용한 스크래치 DB. MySQL 8.0.46.

#### 측정 장치 — SQL 을 손으로 쓰지 않았다

초판 절차의 1번은 *"`show-sql` 은 값이 `?` 로 찍히니 바인딩된 값이 보이는 도구를 쓰거나 **손으로 채워야 한다**"* 였다. **손으로 채우면 그 순간 이 측정의 전제가 무너진다** — 재는 대상이 "앱이 보내는 쿼리"가 아니라 "내가 쓴 쿼리"가 되기 때문이다.

대신 실제 `MemberQueryRepositoryImpl` 을 MySQL 상대로 실행하고 **서버 general log 에 도착한 SQL** 을 그대로 `EXPLAIN` 에 걸었다. Connector/J 는 기본값(`useServerPrepStmts=false`)에서 값을 클라이언트 측에서 채워 보내므로 로그에 완성된 SQL 이 남는다. 이 전제가 깨지면(`?` 가 남으면) 스크립트가 멈춘다.

이 선택이 실제로 값을 했다. 손으로 썼으면 **`lower()` 를 안 씌웠을 것**이다 — 아래 발견 ④가 거기서 나왔다.

```sql
-- 캡처된 검색어 조회 (b). QueryDSL containsIgnoreCase 의 산물
select ... from users m1_0
where lower(m1_0.username) like '%kim%' escape '!'
   or lower(m1_0.email) like '%kim%' escape '!'
order by m1_0.created_at desc, m1_0.id desc limit 0,20
```

#### 결과 — 조합 6종 × (목록 / 총건수)

`idx_users_created_at` **있음**:

| 조합 | 목록 쿼리 | 총건수(count) 쿼리 |
|---|---|---|
| (a) 가입일만 | `range` / 99,127 / ICP + Backward scan | `range` / 99,127 / **Using index** |
| (b) 검색어만 | `index` / **20** / Backward scan | 🔴 `ALL` / 198,255 |
| (c) 가입일+검색어 | `range` / 99,127 / ICP + Backward scan | 🔴 `ALL` / 198,255 |
| (d) 조건 없음 | `index` / **20** / Backward scan | `index` / 198,255 / Using index |
| (e) 페르소나만 | `index` / **20** / Backward scan | 🔴 `ALL` / 198,255 |
| (f) 가입일+페르소나 | `range` / 99,127 / ICP + Backward scan | 🔴 `ALL` / 198,255 |

`idx_users_created_at` **없음**(같은 SQL, 인덱스만 제거 후 `ANALYZE`):

| 조합 | 목록 쿼리 | 총건수 쿼리 |
|---|---|---|
| (a)~(f) 전부 | `ALL` / 198,255 / **Using filesort** | `ALL` / 198,255 (단 (d)만 `username` UNIQUE 를 커버링 스캔) |

#### ① 예측이 틀린 곳 — "검색어는 인덱스를 못 탄다"는 절반만 맞다

예측 표는 검색어·페르소나 단독 조합을 **🔴 못 탄다**로 적었다. 실제로는 `key=idx_users_created_at` 이 잡힌다.

**둘 다 맞다. 인덱스의 용도가 두 개인데 하나만 봤던 것이다.**

- **탐색**(WHERE 로 범위를 좁히는 것) — 예측대로 못 쓴다. 선행 와일드카드도, 인덱스 없는 enum 도 좁힐 수단이 없다
- **정렬**(ORDER BY 를 인덱스 순서로 대체) — **쓴다.** `ORDER BY created_at DESC` 가 인덱스를 거꾸로 읽는 것과 같아서, 필터가 뭐든 `filesort` 가 사라진다

인덱스 제거 표에서 (b)·(e) 가 `ALL` + `Using filesort` 로 돌아가는 것이 그 증거다. **`key` 칸에 인덱스 이름이 찍혔다고 "탐색에 썼다"가 아니다** — §4-1 에서 세션 목록 before 를 `ALL` 로 잘못 읽었던 것과 같은 계열의 오독이고, 이번엔 방향이 반대다.

#### ② `rows=20` 은 측정이 아니라 낙관적 추정이다 — 실측으로 확인

(b)·(d)·(e) 의 `rows=20` 은 *"20건만 읽으면 끝난다"* 로 읽힌다. **아니다.** 옵티마이저는 "최신순으로 훑다 보면 `LIMIT 20` 이 금방 찬다"고 **가정**할 뿐, 필터에 몇 건이 걸리는지 모른다.

핸들러 카운터로 **실제로 읽은 행 수**를 셌다(시간이 아니라 건수라 이 장비의 한계를 타지 않는다):

| 검색어 | 매칭 행 | `EXPLAIN` 의 `rows` | **실제 읽은 인덱스 행**(`Handler_read_prev`) |
|---|---:|---:|---:|
| `kim` (시딩 1%) | 2,000 | 20 | **2,578** |
| `zzzznomatch` | 0 | 20 | **200,000** |

**0건 매칭이면 20만 행을 전부 읽는다. `EXPLAIN` 은 그때도 `rows=20` 이라고 말한다.** 관리자가 오타를 내거나 없는 이름을 치는 것은 드문 일이 아니고, 그게 최악의 경우다.

> 🔴 **이 프로젝트에서 `EXPLAIN` 의 `rows` 를 근거로 쓸 때 걸리는 첫 반례다.** §4-1 은 `rows` 감소(99.5만→27.3만)를 개선 근거로 삼았는데, 거긴 `range` 라 범위가 실제로 좁혀진 경우였다. **`ORDER BY ... LIMIT` 로 잡힌 `type=index` 의 `rows` 는 같은 의미가 아니다.**

#### ③ 진짜 문제는 목록이 아니라 총건수 쿼리다

예측 표에는 **count 쿼리가 아예 없었다.** 필터별로는 나눴는데 쿼리 종류로는 안 나눈 것이고, 재보니 느린 쪽이 거기였다.

한 페이지 요청은 쿼리 **2개**를 쏜다(§7 — 총건수는 목록과 같은 조건을 재사용). 그런데:

- **목록**은 `LIMIT 20` 이 있어서 옵티마이저가 인덱스 순서로 빠져나갈 길이 있다
- **총건수**는 `LIMIT` 도 `ORDER BY` 도 없다. 조건에 맞는 행을 **전부 세야** 하므로 가입일 범위가 안 걸리면 **20만 행 풀스캔 외에 방법이 없다**

인덱스 추가로 개선된 count 는 (a) 하나뿐이다. 나머지 5개는 인덱스 유무와 무관하게 `ALL` 이다. **"관리자가 검색창에 이름을 치는 순간 20만 행 풀스캔"이라는 초판 서술은 맞았는데, 이유가 예측과 다르다** — 목록이 아니라 총건수가 그렇다.

#### ④ `lower()` 가 접두 검색 전환을 막는다 — 그리고 그 `lower()` 는 불필요하다

초판이 "측정 후 갈릴 수 있는 결정"으로 적어둔 것: *검색어가 문제면 접두 검색(`LIKE 'kim%'`)으로 바꿔 인덱스를 태울지.* **지금 코드로는 그것만으로 안 된다.**

`containsIgnoreCase()` 가 `lower(username) like ...` 를 만드는데, **컬럼에 함수를 씌우면 접두 검색이어도 인덱스를 못 탄다.** `lower(username)` 의 정렬 순서는 인덱스에 저장돼 있지 않다.

그런데 이 DB 의 컬레이션은 `utf8mb4_unicode_ci` 다 — **`_ci` 는 이미 대소문자를 무시한다.** 확인:

| 쿼리 | 결과 |
|---|---:|
| `WHERE username LIKE '%kim%'` | 2,000 |
| `WHERE username LIKE '%KIM%'` | 2,000 |
| `WHERE lower(username) LIKE '%kim%'` | 2,000 |

**즉 `lower()` 는 결과를 바꾸지 않으면서 인덱스 사용 가능성만 막고 있다.** QueryDSL 의 `containsIgnoreCase` 가 DB 컬레이션을 모른 채 방어적으로 씌운 것이다. `contains()` 로 바꾸면 동작은 같고 접두 검색 전환의 길이 열린다.

> ⚠️ **컬레이션 의존이라는 것은 그대로 남는다.** `_bin` 이나 `_as_cs` 컬레이션으로 바꾸면 대소문자 구분이 살아나 동작이 조용히 달라진다. 바꾼다면 그 전제를 코드 주석과 테스트로 못박아야 한다.

##### ✅ 적용함 (2026-08-04) — 그리고 테스트가 운영과 갈리는 것을 발견했다

`contains()` 로 바꾸고 **"대소문자를 무시한다"를 단언하는 테스트를 붙였더니 실패했다.**

원인은 코드가 아니라 **테스트 DB** 였다. 이 프로젝트의 테스트는 H2(MySQL 모드)를 쓰는데, **H2 는 문자열 비교가 기본적으로 대소문자를 구분한다.** 즉:

| | `contains()` 이전 | 이후 |
|---|---|---|
| 운영 MySQL(`_ci`) | 무시 | 무시 |
| 테스트 H2(기본) | 무시 (`lower()` 가 코드에 있었으니) | 🔴 **구분** |

**`lower()` 가 두 환경의 차이를 덮고 있었다.** 걷어내는 순간 그 차이가 드러난 것이고, 테스트를 안 붙였으면 **운영과 다르게 동작하는 채로 초록불이 떴을 것이다.**

고친 방식은 테스트 H2 를 운영 컬레이션에 맞추는 것이다 — `jdbc:h2:...;IGNORECASE=TRUE`. 이건 편의 설정이 아니라 **운영 재현**이다. MySQL 의 `_ci` 도 그 컬럼의 모든 문자열 비교에 걸리므로, H2 를 대소문자 무시로 두는 편이 오히려 실제에 가깝다.

> **이 건이 남긴 것** — 걷어낸 것은 불필요한 `lower()` 하나였는데, 그게 **테스트와 운영의 규칙 차이를 가리는 뚜껑**이기도 했다. "결과를 바꾸지 않는 코드"가 정말 아무것도 안 하는 것은 아니다.

#### 인덱스가 실제로 한 일 (정리)

| | 인덱스가 고친 것 | 인덱스가 못 고친 것 |
|---|---|---|
| 목록 쿼리 | **6/6 조합에서 `filesort` 제거.** 가입일이 걸린 3개는 스캔도 198,255→99,127 로 절반 | 저선택도 필터 + `LIMIT` 조합의 최악 케이스(②) |
| 총건수 쿼리 | (a) 가입일만 — `ALL` → `range` + 커버링 | **나머지 5개 전부 `ALL` 그대로**(③) |

**채택(ㄱ) 판단은 유지된다.** 다만 근거의 서술이 바뀐다 — *"기간 조회가 빨라진다"* 가 아니라 **"모든 조합에서 정렬 비용이 사라지고, 기간이 걸린 경우에만 스캔도 준다"** 가 정확하다.

#### 🔴 측정하지 않은 것 · 이 결과의 한계

1. **시간(ms)** — 내지 않았다. §4-1 "측정하지 않은 것" 2번과 같은 이유다. 위 표는 전부 계획(`EXPLAIN`)과 **건수**(핸들러 카운터)이고, 둘 다 시계를 안 쓴다
2. **값 분포** — `created_at` 이 365일 균등, 페르소나가 4분할 균등이다. 실제 서비스는 최근 가입이 몰리고 페르소나도 치우친다. **`range` 냐 `ALL` 이냐는 선택도에 달려 있으므로, 위 결과는 "이 분포에서는 이렇게 고른다"까지다**
3. **32가지 중 6가지만** 쟀다. 나머지는 위 원리(탐색용 조건이 `created_at` 뿐 / count 에는 `LIMIT` 이 없다)로 설명되지만 **관측은 아니다**
4. **AWS 재측정은 이 항목에서 불필요하다** — 풀 사이징 때 로컬 결론이 EC2 에서 뒤집힌 전례가 있으나, 그건 **시간을 쟀기** 때문이다. `EXPLAIN` 은 옵티마이저의 선택이라 코어 수·경합과 무관하다. 옮겨도 같은 시딩 스크립트면 같은 분포라 **같은 답이 나온다.** 재측정이 의미를 갖는 시점은 장비를 바꿀 때가 아니라 **실사용 데이터가 쌓여 분포가 진짜가 될 때**다
   > 단서: MySQL 8.0 의 코스트 모델은 페이지가 메모리에 있을 확률을 반영하므로, 버퍼풀 크기가 크게 다르면 경계선 케이스는 갈릴 수 있다. 위 결과 중 경계선에 가까운 것은 (c)·(f) 목록 쿼리다

측정이 끝났으므로 아래는 선택지가 아니라 **판단 대기** 상태다. 다만 아직 아무것도 정하지 않는다.

| # | 쟁점 | 선택지 |
|:--:|---|---|
| 1 | **총건수 쿼리**(③) — 필터 조합 대부분에서 20만 행 풀스캔 | ㉮ 감수(관리자 트래픽 극소) / ㉯ 총건수를 근사·상한으로 바꿈(`LIMIT 1001` 후 "1000+ 건") / ㉰ keyset 페이징으로 전환해 총건수 자체를 없앰 — 단 §5 가 "관리자 UI 는 총건수·페이지 점프를 기대한다"고 offset 을 택한 근거와 정면 충돌 |
| 2 | ~~**`lower()` 제거**(④)~~ → ✅ **완료 (2026-08-04, issue #105)** | `contains()` 로 바꿨다. **이것만으로 빨라진 쿼리는 없다** — 선행 와일드카드가 그대로라 여전히 인덱스 탐색은 못 한다. 접두 검색 전환(3번)의 선결 조건을 치운 것뿐이다. 대가로 대소문자 무시가 코드에서 사라져 컬레이션 의존이 됐고, 그 전제는 테스트로 잡는다(아래) |
| 3 | **검색어 요구사항**(②) — 0건 매칭 시 20만 행 | 접두 검색으로 축소 / 전문 검색(FULLTEXT) / 기간 필터를 검색과 함께 강제(§4 ㄷ안의 재등장 — 다만 여기선 스캔 범위를 실제로 줄인다) |

**세 개 다 "지금 고쳐야 하는가"가 먼저다.** 관리자 트래픽은 구조적으로 극소이고(관리자 몇 명), 20만 행 스캔은 이 규모에서 체감되지 않을 수 있다. **문제의 존재를 아는 것과 지금 고치는 것은 다르다.**

#### 🔴 1번은 단독으로 결정할 수 없다 — 프론트 결정에 매달려 있다

**총건수 쿼리가 존재하는 이유는 성능이 아니라 UI 다.** `PageResponse` 의 `totalPages` 는 `ceil(totalElements / size)` 로 계산되고([`PageResponse.java:28`](../../backend/src/main/java/com/shadowfit/dto/common/PageResponse.java)), 그게 있어야 `[1][2][3]…[62]` 와 "전체 1,234건 중"을 그릴 수 있다. **페이지 번호를 그리지 않는다면 그 쿼리는 존재할 이유가 없다.**

그런데 **그 화면은 아직 없다.** 현재 구현된 것은 API 하나뿐이고(`GET /admin/members`), `frontend/` 에 관리자 화면은 없다. 그리고 **만들지 여부 자체가 미결**이다 — §8 열린 질문 6번(*"관리자 화면의 프론트를 만들 것인가, API만 만들고 Swagger로 시연할 것인가"*).

§5 가 offset 을 택한 근거도 *"관리자는 총건수·페이지 점프를 기대한다"* 였고, 같은 절이 단서를 달아뒀다 — *"이 판단은 관리자 UI가 테이블 + 페이지네이션이라는 전제 위에 있다."* **그 전제가 아직 확정이 아니다.**

| §8-6 프론트 결정 | 1번(총건수)에 미치는 영향 |
|---|---|
| **안 만듦** (Swagger 시연) | 페이지 번호 UI 가 없다 → 총건수가 **요구사항이 아닐 수 있다.** 그러면 ㉰(keyset)가 억지가 아니라 자연스러운 선택이 되고, §5 결정도 함께 재검토 대상이 된다 |
| **만듦** (테이블 + 페이지네이션) | §5 판단대로 offset 유지. ㉮(감수) / ㉯(근사 표기) 중에서 고른다 |
| **만듦** (무한 스크롤) | §5 가 스스로 밝힌 대로 **뒤집힌다** → keyset |

> **그러므로 순서는 §8-6 → 1번이다.** 지금 1번을 먼저 정하면 아직 없는 화면의 요구사항을 추측해서 쿼리를 고치는 것이 된다. 반대로 §8-6 이 정해지면 1번은 대부분 따라 나온다.
>
> 2번(`lower()`)·3번(검색어)은 이 의존이 없다 — 화면 형태와 무관하게 검색 기능은 남는다.

##### ✅ 2026-08-06 — §8-6 이 절반 풀렸다: ㉮(감수)로 간다

**"관리자 프론트를 만든다"가 확정됐다**(§8-6). 위 표의 첫 행(**안 만듦**)이 사라졌으므로 남은 것은 **페이지 번호냐 무한 스크롤이냐** 하나다. 그런데 그 답을 기다리지 않고 1번을 **㉮(감수)** 로 정한다. 근거는 셋이다.

1. **되돌리는 비용이 비대칭이다.** offset+count 는 이미 구현·측정·테스트까지 끝나 있다. 나중에 무한 스크롤로 정해지면 keyset 을 *얹으면* 되고, 그때 count 는 호출부에서 안 부르면 그만이다. 반대로 지금 지웠다가 페이지 번호로 정해지면 다시 만들어야 한다. **모르는 쪽으로 미리 움직이는 것이 손해다**
2. **감수의 근거가 "드무니까"가 아니다.** 관리자 트래픽이 극소인 건 맞지만 그건 회피 논리다. 실제 근거는 **20만 행 풀스캔이 실측된 값이고, 그 값이 이 화면의 SLA 안에 들어온다는 것**이다 — 다만 시간은 아직 안 쟀다(아래 ⚠️)
3. **㉯(근사 표기)는 UI 가 정해지기 전엔 설계할 수 없다.** "1000+ 건"이 허용되는지는 화면이 결정한다

⚠️ **감수의 정직한 구멍**: 20만 행 풀스캔이 *몇 ms* 인지는 재지 않았다. §4-3 은 `EXPLAIN`(옵티마이저의 선택)만 봤고 시간은 로컬 2코어 동거 환경이라 신뢰하지 않기로 한 값이다([`../tasks/../decisions/load-test-strategy.md`](./load-test-strategy.md) 전제). **"감수 가능"은 스캔 폭이 유계(20만 행 고정, 데이터가 늘면 같이 는다)라는 구조적 근거이지 시간 근거가 아니다.** 실사용 데이터가 쌓이면 이 판단은 재검토 대상이다.

**이 결정으로 §4-3 의 열린 3건 중 1번이 닫힌다.** 2번은 이미 완료(#105), 3번(검색어 요구사항)만 남는다.

### 4-4. ✅ B 세션 목록 — 조인 있는 조회, 측정 완료 (2026-08-04)

B 를 구현했다(§3-B 필터 4). **A 에서 쟀던 것을 그대로 적용할 수 없다** — 조인이 생겼기 때문이다.

**실험**: [`measure_admin_filter_explain.sh`](../../loadtest/measure_admin_filter_explain.sh)(A 용 rig 를 확장) + [`AdminSessionExplainCaptureTest`](../../backend/src/test/java/com/shadowfit/repository/exercise/AdminSessionExplainCaptureTest.java). 회원 20만 / 세션 100만(FAILED 25만) / 운동 3종. 같은 스크래치 DB 에서 A 도 재측정했고 **A 결과는 전부 동일했다**(회귀 없음).

#### A 와 무엇이 다른가

| | A 회원 목록 | B 세션 목록 |
|---|---|---|
| 대상 | `users` 단일 | `exercise_sessions ⋈ users ⋈ exercises` |
| 겨냥 인덱스 | `idx_users_created_at (created_at)` — **단일, 범위만** | `idx_session_status_starttime (status, start_time)` — **복합, 등치+범위** |
| 검색어 위치 | 읽는 테이블에 그대로 | **조인 너머**(`users.username`) |
| 규모 가정 | 20만 | 100만 |

**인덱스가 더 잘 들을 것으로 보인다.** A 의 `created_at` 은 단일 컬럼이라 §4-3 ① 처럼 정렬용으로만 널리 쓰였는데, B 는 `(status, start_time)` 이라 상태 등치로 좁힌 뒤 그 안이 기간·정렬 순서다. §4-1 이 스크래치 테이블에서 이미 그 그림을 봤다(`index`/995,392 + filesort → `range`/272,976 + 백워드 스캔).

**단 그건 상태 필터가 걸렸을 때다.** 안 걸리면 선두 컬럼이 비어 A 와 같은 상황이 된다.

#### 🔴 코드로 예측이 안 되는 것 — 드라이빙 테이블

검색어가 조인 너머에 있어서, 옵티마이저가 **어느 테이블부터 읽을지**를 고른다.

- 세션부터 읽고 회원을 붙여 거를 것인가
- 회원을 먼저 걸러 그 회원들의 세션을 찾을 것인가

**둘의 비용은 필터 조합에 따라 뒤집힌다.** 검색어가 좁고(회원 몇 명) 상태 필터가 넓으면 회원부터가 유리하고, 반대면 세션부터가 유리하다. A 에는 없던 변수이고 **코드만 봐서는 알 수 없다** — §4-3 에서 예측 2건이 틀렸던 것과 같은 이유다.

#### 총건수 — A 보다 나쁠 것으로 보인다

§4-3 ③ 에서 드러난 문제가 여기서 커진다. 세션 100만 행을 세면서 검색어가 걸리면 회원 조인까지 탄다.

구현에서 **조인을 조건부로 붙여 일부 덜어냈다**([`SessionQueryRepositoryImpl#countOf`](../../backend/src/main/java/com/shadowfit/repository/exercise/SessionQueryRepositoryImpl.java)) — 개수를 세는 데는 거르는 데 쓰이는 조인만 있으면 되므로, `exercise` 는 항상 빼고 `member` 는 검색어가 있을 때만 붙인다. **다만 이건 조인을 줄인 것이지 `LIMIT` 이 없다는 근본을 바꾸지 못한다.**

> ⚠️ **이 최적화의 효과도 미측정이다.** "조인을 빼면 싸다"는 구조적으로 맞지만 크기는 모른다. 옵티마이저가 애초에 그 조인을 무시했을 가능성도 있다(세는 데 안 쓰이는 조인은 제거 대상이다).

#### 결과 — 조합 5종 × (목록 / 총건수)

인덱스 **있음**. 목록은 조인 3단이라 드라이빙 테이블만 적었다(`s`=세션, `m`=회원).

| 조합 | 목록 쿼리 | 총건수 쿼리 |
|---|---|---|
| (a) 상태만 | `s` `ref`/433,236 · 🔴 **temporary+filesort** | `s` `ref`/433,236 · Using index |
| (b) 상태+기간 | `s` `range`/126,658 · Backward scan + 🔴 **temporary+filesort** | `s` `range`/126,658 · Using index |
| (c) 검색어만 | `s` `ALL`/994,944 · 🔴 temporary+filesort | **`m`** `ALL`/198,255 → `s` `ref`/4 |
| (d) 상태+검색어 | `s` `ref`/433,236 · 🔴 temporary+filesort | **`m`** `ALL`/198,255 → `s` `ref`/4 |
| (e) 조건 없음 | `s` `ALL`/994,944 · 🔴 temporary+filesort | `s` `index`/994,944 · Using index |

인덱스 **없음**: 목록은 (a)~(e) 전부 `s` `ALL`/994,944 + temporary+filesort. 총건수는 `member_id` 선두 인덱스들로 커버링 전수 스캔.

#### ① 예측이 틀렸다 — 인덱스가 정렬을 못 없앤다

§4-4 초안은 *"인덱스가 A 보다 잘 들을 것"* 이라고 썼다. **탐색은 맞았고 정렬은 틀렸다.**

A 에서는 인덱스가 6/6 조합의 `filesort` 를 없앴다(§4-3 ①). B 에서는 **5/5 조합 전부 `Using temporary; Using filesort` 가 남는다.** 인덱스 유무와 무관하다.

**범인은 조인이다.** (b) 를 보면 증거가 한 줄에 다 있다:

```
type=range  key=idx_session_status_starttime  Backward index scan;  Using temporary; Using filesort
```

**백워드 인덱스 스캔으로 순서대로 읽어놓고, 그 순서를 버리고 다시 정렬한다.** 세션을 읽은 뒤 `exercises` 와 해시 조인을 하는데(`Using join buffer (hash join)`), 해시 조인은 입력 순서를 보존하지 않으므로 정렬을 다시 해야 한다.

> 🔴 **정렬을 깨는 그 테이블은 3행짜리다.** `exercises` 는 운동 종목 마스터라 행이 세 개뿐인데, 100만 행 위에서 얻은 인덱스 순서를 무효로 만든다. 비용이 큰 조인이라서가 아니라 **조인이 있다는 사실 자체**가 순서 보존을 막는다.

#### ② 드라이빙 테이블이 목록과 총건수에서 **정반대**다

같은 `WHERE` 인데 계획이 갈린다. (c)·(d) 를 보면:

| | 먼저 읽는 테이블 | 왜 |
|---|---|---|
| **목록** | **세션** — 회원은 `eq_ref PRIMARY` 로 붙임 | `ORDER BY start_time DESC LIMIT 20` 이 세션 컬럼이라, 세션부터 읽어야 정렬·LIMIT 을 다룰 수 있다 |
| **총건수** | **회원** — 세션은 `ref`/4 로 찾음 | 정렬도 LIMIT 도 없으니 자유롭다. 회원 19.8만을 훑어 `kim` 2천 명을 찾고, 그 회원들의 세션만 인덱스로 집는 편이 싸다 |

**이게 "코드만 봐서는 모른다"고 적어둔 그 지점이다.** 답은 "둘 중 하나"가 아니라 **"쿼리 종류에 따라 둘 다"** 였다.

#### ③ `member_id` 선두 인덱스가 총건수에서 되살아난다 — §4 서술 정정

§4 본문은 이렇게 적었다:

> 관리자 목록은 `member_id` 조건 없이 전체를 훑으며 상태·기간으로 거른다 → 위 복합 인덱스는 선두 컬럼이 안 맞아 **전혀 타지 않는다.**

**B 의 총건수 쿼리에서는 이게 틀리다.** (c)·(d) 의 계획을 보면 `idx_session_member_exercise_status_start` 와 `idx_session_member_status` 를 `ref`(rows=4)로 쓴다.

이유는 조인이다. **회원부터 몰면 `member_id` 가 조건으로 생긴다.** 쿼리에 `member_id` 를 안 썼어도 조인 조건이 그 역할을 한다 — `WHERE s.member_id = m.id` 이므로, 회원 하나가 정해질 때마다 `member_id` 등치 조건이 서는 것이다.

> §4 의 서술은 **"관리자가 `member_id` 를 필터로 주지 않는다"** 는 뜻으로는 맞다. 하지만 **"그래서 그 인덱스들이 안 쓰인다"** 로 이어지지는 않는다. 조인이 들어오면 선두 컬럼이 다시 채워진다.

#### ④ 총건수의 조건부 조인은 의도대로 작동한다

구현에서 `countOf()` 가 `exercise` 조인을 항상 빼고 `member` 는 검색어가 있을 때만 붙이도록 했다. **계획으로 확인된다** — 총건수 쿼리 5개 중 `exercises` 가 등장하는 것은 하나도 없고, `users` 는 검색어가 있는 (c)·(d) 에만 나온다.

> ⚠️ **다만 "그래서 빨라졌다"는 말할 수 없다.** 옵티마이저가 세는 데 안 쓰이는 조인을 스스로 제거했을 수도 있어서, 안 붙였을 때와 붙였을 때를 나란히 재야 알 수 있다. **그건 재지 않았다.**

#### ⑤ A 와 반대로, 검색어 조합에서는 **목록이 더 비싸다**

A 에서는 총건수가 병목이었다(§4-3 ③). B 의 (c) 검색어만 조합은 뒤집힌다:

- 목록: 세션 99.4만 전수 스캔 + 조인 + 정렬
- 총건수: 회원 19.8만 스캔 + 매칭 회원당 인덱스 조회

**총건수가 목록보다 싸다.** 목록이 `ORDER BY ... LIMIT` 때문에 세션부터 읽어야 하는 데 묶여 있어서다.

#### 인덱스가 실제로 한 일 (정리)

| | 고친 것 | 못 고친 것 |
|---|---|---|
| 목록 | 상태가 걸린 조합에서 스캔 99.4만 → 43.3만(상태만) / 12.7만(상태+기간), `filtered` 2.78~25% → 100% | **정렬 — 5/5 조합에서 temporary+filesort 그대로**(①) |
| 총건수 | (a)·(b) 커버링 인덱스로 좁힘 | 검색어가 걸리면 계획이 회원 주도로 바뀌어 인덱스와 무관해짐 |

**채택(ㄱ) 판단은 유지된다.** 상태 필터가 걸린 조합에서 스캔이 실제로 줄었고, 그건 관리자 화면의 기본 진입 경로다. 다만 **A 에서 얻은 "정렬 비용이 사라진다"는 이득은 B 에 없다.**

#### 🔴 측정하지 않은 것 · 한계

1. **시간(ms)** — §4-3 과 같은 이유로 내지 않았다
2. **값 분포** — `status` 가 COMPLETED 50 / FAILED 25 / IN_PROGRESS 25 로 균일하다. 실제로는 COMPLETED 가 대부분이고 FAILED 는 소수일 것이다. **드라이빙 테이블 선택은 선택도에 민감하므로 A 보다 이 단서가 무겁다** — FAILED 가 1% 로 떨어지면 (d) 의 계획이 뒤집힐 수 있다
3. **`CANCELLED` 은 시딩하지 않았다** — issue #106 때문에 코드에서 도달할 수 없는 값이라, 있는 척하면 측정이 현실보다 좋아 보인다
4. **조건부 조인의 효과 크기**(④) — 방향은 확인했고 크기는 모른다
5. **16조합 중 5개만** 관측. 정렬 키를 `AVG_SYNC_RATE`·`TOTAL_REPS` 로 바꾼 경우도 안 쟀다 — 둘 다 인덱스가 없어 더 나쁠 것으로 보이나 **예측이다**

##### 4번의 원인은 확인했다 — 두 조인 중 `exercises` 만 범인이다

"조인이 정렬을 깬다"까지는 ① 에서 봤지만, **조인이 둘인데 어느 쪽인지**는 안 나왔다. 하나씩 떼고 같은 조건(`status='FAILED'` + 시작시각 최신순 20건)으로 다시 걸었다.

| 쿼리 | `Extra` |
|---|---|
| 조인 2개 (현재 구현) | 🔴 `Using temporary; Using filesort` |
| **`exercises` 조인만 제거** | 🟢 **`Backward index scan`** — 정렬 사라짐 |
| 조인 전부 제거 | 🟢 `Backward index scan` |

**`users` 조인은 정렬을 안 깬다.** `eq_ref`(PK 단건 조회)라 세션 한 행마다 회원 하나를 집는 중첩 루프이고, **읽는 순서가 그대로 유지**된다. 반면 `exercises` 는 `hash join` 이라 입력을 버퍼에 모았다가 내보내므로 순서가 사라진다.

> **3행짜리 마스터 테이블 조인 하나가 100만 행 위에서 얻은 인덱스 순서를 무효로 만든다.** 조인의 실행 비용이 커서가 아니라 **조인 방식(해시)** 때문이다. 회원 조인은 20만 행짜리인데 멀쩡하다 — 크기가 아니라 방식의 문제다.
>

>
> **그리고 이건 "㉯ 로 가자"가 아니다.** 운동명을 애플리케이션에서 채우면 조인은 사라지지만 조회가 두 단계로 나뉘고 캐시 무효화가 생긴다. **비용을 옮기는 것이지 없애는 것이 아니다.**

## 5. 페이징 방식 — 관리자 화면은 keyset이 정답이 아닐 수 있음

[`querydsl-adoption.md`](./querydsl-adoption.md) §4에서 keyset 페이징을 QueryDSL의 강점 근거로 들었으나, **관리자 화면에 한정하면 재고가 필요하다.**

| 방식 | 관리자 화면 적합성 |
|---|---|
| **offset 페이징** | 관리자는 "5페이지로 점프", "전체 1,234건 중" 같은 **총건수·임의 페이지 이동**을 기대한다. keyset은 이걸 구조적으로 못 한다 |
| **keyset 페이징** | 무한 스크롤·피드에 적합. 관리자 테이블 UI와는 궁합이 나쁨 |

🔶 **제안**: 관리자 목록은 **offset + `COUNT(*)`** 로 가고, keyset은 §T2(리포트 히스토리, 모바일 무한스크롤)에서 다룬다. "관리자 = keyset"을 억지로 붙이면 UI 요구와 싸우게 된다.

> 정직 단서: 이 판단은 관리자 UI가 **테이블 + 페이지네이션**이라는 전제 위에 있다. 무한 스크롤로 만들 거라면 뒤집힌다.

> 🔴 **2026-08-04 추가 — 이 단서의 무게가 커졌다.** §4-3 ③ 에서 `COUNT` 쿼리가 대부분의 필터 조합에서 20만 행 풀스캔인 것이 관측됐다. 즉 **offset 을 택한 대가가 한 화면 비용의 대부분**이다. 게다가 그 전제(테이블 UI)는 아직 확정이 아니다 — 관리자 프론트를 만들지 자체가 §8-6 에서 미결이고, 현재 `frontend/` 에 관리자 화면은 없다. **§8-6 이 정해지기 전에는 이 절의 offset 판단도 잠정이다.**

> ✅ **2026-08-06 — 잠정을 유지한 채로 진행한다.** 프론트를 만든다는 것은 확정됐지만(§8-6) **테이블+페이지 번호인지 무한 스크롤인지는 여전히 미정**이라, 이 절의 전제는 아직 확정되지 않았다. 그래도 offset+`COUNT(*)` 를 **그대로 둔다** — 이미 구현·측정이 끝나 있고, 무한 스크롤로 정해지면 keyset 을 얹으면서 count 호출을 빼면 되는 방향이라 되돌리는 비용이 작기 때문이다. 판단 근거 전체는 §4-3 의 "2026-08-06" 절에 적었다. **즉 이 절은 "확정"이 아니라 "뒤집힐 때까지 유효"다.**
