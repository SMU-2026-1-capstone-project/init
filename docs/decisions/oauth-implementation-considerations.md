# Decision: OAuth2 소셜 로그인 — 붙이려면 무엇을 먼저 정해야 하나

작성: 2026-08-08
상태: 🔶 **미결정** — 이 문서는 선택지와 근거만 제시한다. 결정은 사용자 confirm 후 박제.

배경: 사용자 질문 **"oauth 할려면 뭐를 고려해야하니"** (2026-08-08).
선행 문서 [`external-integration-candidates.md`](./external-integration-candidates.md) §3-2 는 **"할지 말지"** 를 다뤘고(결론: 🔶 조건부, 계정 충돌 처리를 산출물로 잡을 때만), 이 문서는 그 다음 질문 — **"한다면 무엇이 걸리는가"** — 를 코드와 대조한다. **이 문서는 "하자"는 뜻이 아니다.** §3-2 의 조건부 판정은 그대로 살아 있다.

---

## 0. 요약 — 걸림돌은 `password NOT NULL` 이 아니었다

선행 문서는 OAuth2 의 스키마 장애물을 `members.password NOT NULL` 로 지목했다. 맞지만 **가장 큰 것이 아니다.** 코드를 보면 더 깊은 게 셋 더 있다:

| # | 발견 | 근거 | 왜 더 큰가 |
|---|---|---|---|
| 1 | **인증 식별자 전체가 email 에 묶여 있다** | `JwtUtil.java:52-53`, `MemberController.java:56,65` | 이메일을 안 주는 소셜 계정이 존재한다(§2-1). 그러면 토큰 subject 도, URL 도 만들 수 없다 |
| 2 | **refresh token 재발급 엔드포인트가 없다** | 컨트롤러 전체 grep 0건 | 선행 문서는 *"refresh_token 테이블 존재 → 비용을 낮춘다"* 고 봤는데, **저장만 하고 쓰는 코드가 없다.** 회전 로직은 0 에서 시작 |
| 3 | **클라이언트가 Expo(React Native) 네이티브 앱이다** | `frontend/app.json`, `services/api.ts:27` | Spring Security 의 `oauth2Login` (서버 리다이렉트 방식)이 그대로는 안 맞는다(§1) |

`password NOT NULL` 은 이 셋에 비하면 마이그레이션 한 줄이다.

## 1. 첫 번째 분기 — 플로우를 어디서 돌릴 것인가

**이게 제일 먼저 갈린다.** 나머지 결정이 전부 여기에 딸려 온다.

현재 서버는 완전 STATELESS 이고 `oauth2Login` 설정이 없다(`SecurityConfig.java:40-42`). 클라이언트는 브라우저가 아니라 **네이티브 앱**이다.

### (A) 서버 주도 — Spring Security `oauth2Login`

```
앱 → 브라우저 열기 → 백엔드 /oauth2/authorization/kakao → 카카오 → 백엔드 콜백 → 딥링크로 JWT 전달
```

| 항목 | 평가 |
|---|---|
| client secret | **서버에만** 둔다 (안전) |
| Spring 지원 | `spring-boot-starter-oauth2-client` 가 거의 다 해준다 |
| 걸리는 곳 | 마지막에 **JWT 를 앱으로 되돌릴 방법**이 필요하다 — 딥링크(`shadowfit://`) 리다이렉트, 그런데 토큰을 URL 에 실으면 로그·브라우저 히스토리에 남는다. 실무는 1회용 code 를 딥링크로 주고 앱이 그걸 교환하는 형태 |
| STATELESS 와의 충돌 | `oauth2Login` 은 authorization request 를 세션에 저장한다. 지금 `SessionCreationPolicy.STATELESS` 이므로 **`AuthorizationRequestRepository` 를 쿠키 기반으로 갈아끼워야 한다** — 이건 실제 작업량이다 |

### (B) 앱 주도 — 네이티브 SDK/AuthSession + 백엔드 검증

```
앱이 카카오 SDK 로 로그인 → id_token(또는 access_token) 획득
→ POST /member/oauth/kakao {token} → 백엔드가 검증 → 우리 JWT 발급
```

| 항목 | 평가 |
|---|---|
| 백엔드 변경 | **엔드포인트 1개 추가**로 끝난다. STATELESS 를 안 건드린다 |
| 검증 책임 | 백엔드가 **직접** 해야 한다 — id_token 이면 JWKS 로 서명·`iss`·`aud`·`exp` 검증, access_token 이면 제공자 API 로 조회. **여기를 대충 하면 "아무 토큰이나 주면 로그인되는" 취약점**이 된다 |
| client secret | 앱에 넣지 않는다(PKCE / 네이티브 SDK) |
| 면접 서사 | 오히려 (A)보다 낫다 — *"라이브러리가 해주는 걸 붙였다"* 가 아니라 *"토큰 검증에서 무엇을 확인해야 하는지"* 를 말할 수 있다 |

> **추천은 (B)** — 클라이언트가 네이티브 앱이고, 현재 STATELESS 구조를 안 깨며, 검증 로직이 남는 산출물이기 때문. **단 확정 아님.**

## 2. 스키마 — 실제로 손대야 하는 곳

### 2-1. `email` 이 인증의 척추다 (가장 큰 문제)

| 사실 | 근거 |
|---|---|
| JWT subject 가 email | `JwtUtil.java:52` — `.setSubject(member.getEmail())` |
| claim `userId` 에도 email 이 들어간다 | `JwtUtil.java:53` — 이름이 `userId` 인데 값은 email (별도 정리 대상) |
| 탈퇴 URL 이 email | `MemberController.java:56` — `@DeleteMapping("/{email}")` |
| 온보딩 조회 URL 도 email | `MemberController.java:65` |
| `email UNIQUE NOT NULL` | `Member.java:27-28` |

**그런데 소셜 제공자는 이메일을 보장하지 않는다:**
- **카카오** — 이메일은 *선택 동의* 항목이고, 사업자 검수 전에는 아예 못 받는다. 사용자가 동의를 빼면 **이메일이 안 온다**
- **Apple** — *Hide My Email* 을 켜면 `@privaterelay.appleid.com` 릴레이 주소가 온다. 실주소가 아니고, 사용자가 나중에 끊을 수 있다
- **Google** — 대체로 온다

→ **결정 필요**: 이메일 없는 계정을 허용할 것인가?
- **허용 안 함** — "이메일 동의는 필수" 로 막는다. 제일 싸다. 대신 카카오에서 이탈이 생기고, Apple 릴레이 주소가 `email` 컬럼에 그대로 들어간다
- **허용함** — 식별자를 email 에서 **내부 id 또는 `(provider, provider_user_id)`** 로 옮겨야 한다. 그러면 위 표의 5곳이 전부 바뀐다. 정공법이고, 사실 **email 을 URL path 에 노출하는 현재 설계 자체가 개선 대상**이라 겸사겸사 정리된다. 다만 프론트 4개 파일도 같이 바뀐다

### 2-2. `password NOT NULL`

`Member.java:30-31` / `mysql/schema.sql:12`. 소셜 전용 계정은 비밀번호가 없다.

- **nullable 로 마이그레이션** — 정직하다. 대신 `login()` 의 `passwordEncoder.matches()`(`MemberService.java:60`)가 `null` 을 만나면 어떻게 되는지 확인·방어 필요. **로컬 로그인 경로로 소셜 계정을 뚫으려는 시도를 반드시 막아야 한다** → 상세 및 미검증 사항은 §3-0(2)
- **랜덤 더미 비밀번호** — 마이그레이션이 없다. 대신 "이 계정은 소셜 전용"이라는 정보가 스키마에서 사라진다

### 2-3. `username UNIQUE`

`Member.java:24-25`. 소셜 닉네임은 중복이 흔하다("홍길동" 둘). 지금 구조면 **두 번째 사람의 가입이 그냥 실패**한다.

→ UNIQUE 를 풀 것인가, 충돌 시 suffix 를 붙일 것인가(`홍길동_a3f1`), 가입 중에 닉네임을 입력받을 것인가.

### 2-4. 신설 필요

**공존을 켠다면 이건 선택이 아니라 전제다** (§3-0(4)).

`provider` / `provider_user_id` 컬럼 또는 별도 `social_account` 테이블. **UNIQUE 는 `(provider, provider_user_id)` 복합**이어야 한다 — provider 별로 id 네임스페이스가 다르므로 `provider_user_id` 단독 UNIQUE 는 틀렸다.

별도 테이블로 빼면 **한 계정에 여러 소셜을 연결**할 수 있고, 이게 §3 의 "명시적 연동" 정책과 맞물린다.

## 3. 계정 충돌 — 선행 문서가 "여기가 산출물"이라고 지목한 지점

### 3-0. 전제 — 공존은 가능하다. 다만 이 스키마에선 "연동"만 가능하다

*(2026-08-08 추가. 사용자 질문 "oauth 하고 아이디비번 로그인하고 같이 공존할 수 있니")*

**결론부터: 가능하고, 그게 표준이다.** 그리고 **어려운 축이 아니다** — 갈리는 건 인증(누구인지 확인)뿐이고, 그 뒤는 **이미 하나로 합쳐져 있다.** 어느 경로로 들어오든 `JwtUtil` 로 같은 JWT 를 발급하면 `JwtAuthFilter.java:45` 이후는 완전히 동일하다. 인가·권한·기존 API 는 손댈 게 없다.

문제는 "가능한가"가 아니라 **공존을 켜면 무엇이 강제되는가**다. 넷이다.

#### (1) `email UNIQUE` 가 선택지를 하나 없앤다 ⚠️

공존 방식은 원래 둘이다 — **같은 사람에게 계정 하나(연동)** vs **수단별로 별개 계정**. 그런데 `Member.java:27-28` 의 `unique = true` 때문에 **같은 이메일로 두 행을 만들 수 없다.**

→ **이 스키마에서 공존은 자동으로 "계정 연동"을 뜻하고, 아래 §3 의 충돌 정책 결정을 피할 수 없다.** 별개 계정으로 도망갈 수 없다. 이게 §3 이 선택이 아니라 **전제**인 이유다.

#### (2) 소셜 계정이 로컬 로그인 창구에 그대로 노출된다

`MemberService.login()`(`MemberService.java:57-62`)은 이메일로 회원을 찾고 **곧바로** 비번을 대조한다. 소셜로만 가입한 사람의 이메일이 여기 들어오면:

- `password` 를 nullable 로 풀었다면 → `BCryptPasswordEncoder.matches(raw, null)` 은 **false 를 반환**한다(빈 인코딩값 방어). 뚫리지는 않는다
- 대신 사용자는 **`LOGIN_INPUT_INVALID`("비밀번호가 틀렸습니다")** 를 받는다 — **비밀번호를 만든 적조차 없는데도.**

→ "이 계정은 카카오로 가입되어 있습니다" 안내가 필요하고, 그건 (4)의 정보에 걸려 있다.

#### (3) 반대 방향도 막혀 있고, 역시 이유를 안 알려준다

`signup()`(`MemberService.java:96-98`)은 이메일이 있으면 `USERID_DUPLICATION` 을 던진다. 소셜 가입자가 나중에 비번 계정을 만들려 하면 그냥 "중복"으로 막힌다.

게다가 **비밀번호 변경·재설정 엔드포인트가 이 프로젝트에 없다**(컨트롤러 grep 0건). "소셜로 가입 → 나중에 비번 설정" 경로는 **지금 아예 존재하지 않고**, 공존을 제대로 하려면 그것도 신설 대상이다. §2-2 의 `password` 결정이 여기까지 번진다.

#### (4) "이 계정은 무엇으로 로그인 가능한가"를 저장할 곳이 없다

`Member` 에 provider 계열 컬럼이 0개다. (2)·(3)의 안내가 전부 이 정보에 걸려 있으므로, **공존을 켜면 §2-4 는 선택이 아니라 전제**가 된다.

#### 곁들여 결정할 것 — 계정 열거(account enumeration)

(2)의 안내 문구는 보안과 맞바꾸는 것이다. *"이 이메일은 카카오 가입자"* 라고 알려주면 **공격자도 그 이메일의 가입 여부를 알게 된다.** 실무는 대체로 UX 를 택하지만, **택했다는 사실을 알고 택해야** 한다.

> ⚠️ **미검증** — `BCryptPasswordEncoder.matches()` 가 `null` 인코딩값에 false 를 준다는 것은 **라이브러리 동작에 대한 지식**이고 이 프로젝트에서 테스트로 확인하지 않았다. `PasswordEncoderConfig.java:10-11` 이 `BCryptPasswordEncoder` 를 쓰는 것까지만 확인했다. **nullable 로 풀 거라면 여기는 반드시 테스트로 박아야 한다 — 뚫리면 소셜 계정 전체가 비번 로그인으로 열린다.**

### 3-1. 충돌 정책 세 갈래

같은 이메일로 이미 로컬 가입한 사용자가 소셜 로그인을 시도할 때. `email UNIQUE`(`Member.java:27`) 가 여기서 그대로 터진다.

| 정책 | 동작 | 위험 |
|---|---|---|
| **자동 병합** | 이메일이 같으면 기존 계정에 소셜을 붙인다 | ⚠️ **계정 탈취 경로다.** 제공자가 이메일 소유를 검증하지 않았다면(또는 `email_verified` 를 확인 안 하면) 공격자가 남의 이메일로 소셜 계정을 만들어 로그인할 수 있다. 하려면 **`email_verified` 확인이 필수** |
| **거부** | "이미 가입된 이메일입니다" | 안전하지만 사용자가 막힌다. 그 사람은 자기 계정에 못 들어간다 |
| **명시적 연동** | 기존 비밀번호로 로그인시킨 뒤 "계정 연결하시겠습니까" | 안전 + 사용자도 통과. **구현이 가장 무겁다** (연동 대기 상태를 어디 둘지) |

**면접에서 값이 나오는 건 이 표를 아는 것 자체가 아니라, 셋 중 하나를 고르고 나머지 둘을 왜 버렸는지 말하는 것.**

역방향도 있다: 소셜로 먼저 가입한 사람이 나중에 비밀번호를 설정하려 할 때. 이건 §2-2 와 직결된다.

## 4. 토큰 — 지금 상태에서 드러나는 구멍 3개

OAuth 를 붙이면 **로그인 경로가 늘어나므로** 아래가 지금보다 더 아프게 드러난다. 셋 다 **OAuth 없이도 이미 있는 문제**이고, 2026-08-08 각각 이슈로 등록했다 — **#135 / #136 / #137**.

### 4-1. 재발급 엔드포인트가 없다 ⚠️ (이슈 #135)

- 로그인 시 refresh token 을 만들어 DB 에 저장한다 (`MemberService.java:70-77`)
- **그런데 그걸 access token 으로 바꿔주는 API 가 없다** — 컨트롤러 전체 grep 0건
- 프론트는 401 이 뜨면 **재발급 시도 없이 즉시 강제 로그아웃**한다 (`services/api.ts:63-70`)

→ 지금 refresh token 은 **발급·저장·삭제만 되고 쓰이지 않는다.** 선행 문서 §3-2 가 *"토큰 저장소는 재사용 가능 — 이건 비용을 낮춘다"* 고 쓴 건 **테이블만 보고 판단한 것**이고, 회전 로직은 0 에서 시작한다. 그 문서의 비용 추정(10~13h)은 이만큼 낮게 잡혀 있을 수 있다.

### 4-2. 한 사람당 refresh token 이 1개다 (이슈 #136)

```java
@Id
@Column(name = "member_id")   // RefreshToken.java:14-16
private Long memberId;
```

PK 가 `member_id` 라 **회원당 1행**이다. 폰과 태블릿에서 동시에 로그인하면 나중 것이 앞의 것을 덮어쓴다. 지금은 재발급 경로가 없어서(§4-1) 증상이 안 보이지만, 재발급을 붙이는 순간 **먼저 로그인한 기기가 조용히 튕긴다.**

→ 기기별 다중 세션을 지원할지 결정 필요. 지원한다면 PK 를 토큰 id 로 바꾸고 `member_id` 는 인덱스로.

### 4-3. 블랙리스트가 인메모리다 (이슈 #137)

```java
private final Map<String,Long> blacklist = new ConcurrentHashMap<>();  // JwtBlacklist.java:11
```
