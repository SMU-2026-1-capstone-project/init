# 프로세스당 천장의 원인 — GIL·이벤트 루프·스레드풀 상한을 가르는 판

작성일: 2026-08-23
상태: 🟢 **1단계 완료 (2026-08-23) — 답은 «ㄴ 단일 이벤트 루프» 다.**
요청 시간의 **44.7%** 가 이벤트 루프에서 소모된다(`wait` 22.0% + `post_loop` 22.7%).
앱 후처리는 **1.1%**([결과](../../loadtest/results/ceiling-cause-stage1-2026-08-23/README.md)).
🔴 **ㄱ(GIL)은 여전히 못 갈랐다** — 루프가 느린 이유가 「할 일이 많아서」인지 「GIL 을 못
잡아서」인지 이 판은 구분하지 않는다.
대상: [從 R10-a](../../loadtest/results/frame-path-r10a-2026-08-23/README.md) 가 「천장은 프로세스당」까지
확인하고 **원인을 못 가른 자리**. 프로세스 분리는 후보를 **한꺼번에** 우회한다.
연관: [`./ai-receive-path-scaling.md`](./ai-receive-path-scaling.md) §10·§13 ·
[`./r10-loadgen-topology.md`](./r10-loadgen-topology.md) ·
[`./ai-sticky-routing.md`](./ai-sticky-routing.md)(세로가 어디까지 가는지가 이 문서에 달렸다)

## 0. 한 줄

**조작으로 가르려던 것을 접고 계측으로 간다.** 쓸 수 있는 조작(프로세스 분리)이 후보를 동시에
우회하기도 하지만, 더 큰 이유는 따로 있다 — **지금 계측의 두 구간(`wait`·`post`)이 각각
«이벤트 루프» 와 «스레드풀» 을 같이 담고 있어서, 어떤 조작을 해도 그 표로는 안 갈린다.**

🔑 **먼저 통을 가르고, 그래도 안 갈리면 그때 조작한다.**

## 2. 코드와 데이터를 다시 읽고 찾은 것 넷

### 2-1. 핸들러가 **동기**라 스레드풀에서 돈다

`ai-server/app/api/endpoints/pose.py:50` 이 `async def` 가 아니라 **`def`** 다. 그 자리에
이유도 적혀 있다 — *「MediaPipe 추론, OpenCV 변환, Spring 콜백 gRPC가 모두 동기 블로킹이라
`async def`로 두면 이벤트 루프를 점유해 다른 요청을 굶긴다」*.

**그 threadpool 에 상한이 있다.** anyio 4.14.2 의 asyncio 백엔드가
`limiter = CapacityLimiter(40)` 로 기본값을 박는다(설치본 소스에서 확인).
🔴 **이 저장소에는 그 값을 바꾸는 손잡이가 없다** — `main.py`·`config.py` 어디에도 없다.

### 2-2. 🔑 `inflight_handler` 는 **스레드 점유가 아니다**

`frame_path.py` 를 읽으면 짝이 이렇다:

```
enter_handler()  ←  mark_handler_in()      핸들러 첫 줄
leave_handler()  ←  http.response.start    미들웨어 send_wrapper
```

**그 사이에 FastAPI 의 응답 직렬화(Pydantic 검증 + JSON 인코딩)가 있고, 그건 스레드가 아니라
이벤트 루프에서 돈다.** 즉 **스레드를 이미 반납한 요청도 계속 세어진다.**

🟢 **그래서 「상한이 40 인데 105~113 이 찍혔다」는 모순이 아니다** — 계측 구간이 넓은 것이다.
§10 이 「상한이 실제로 걸렸는지 안 봤다」로 열어둔 자리가 이렇게 닫힌다.

### 2-3. 🔑 그 초과분이 신호였다 — **GIL 노브가 꼬리를 바꿨다**

R10-a 의 B 계열 10판을 팔로 갈라 다시 세면:

| 팔 | 평균 동시 | p95 | **최대** | rps |
|---|--:|--:|--:|--:|
| **B** (GIL 기본 0.005) | 23.7 | 32~46 | **105~113** | 271 |
| **B@0.0005** (1ms) | 18.5 | 23 | **36~40** | 270 |

🔴 **처리량은 같은데 꼬리가 3배 다르다.** 그리고 B@0.0005 의 최대가 **정확히 36~40** —
anyio 상한과 붙는다.

읽으면: **짧은 양자 → 이벤트 루프가 자주 스케줄됨 → 응답 직렬화 대기열이 안 쌓인다.**
총 처리량은 그대로. **이건 ㄴ(단일 이벤트 루프) 쪽 증거다.**

> ⚠️ **그래서 「GIL 간격은 레버가 아니다」를 좁혀야 한다** — 정확히는 **«처리량의»** 레버가
> 아니다. 대기열 모양은 바꾼다. R10-a 결과 문서는 처리량만 보고 판정했다.

### 2-4. 🔑 지금 구간 정의는 **둘 다 «섞인 통»** 이다

`_spans_of` 를 읽으면:

```
wait    = t_asgi_in  → t_handler_in    이벤트 루프 디스패치 + 스레드풀 큐   ← 섞임
post    = t_inferred → t_response      앱 후처리 + 스레드 반납 + 루프 직렬화 ← 섞임
```

**`wait` 24.92ms(23.3%)도 `post` 28.48ms(26.7%)도 ㄴ 과 ㄷ 을 같이 담는다.**
🔴 **그래서 어떤 조작을 하든 이 표로는 둘이 안 갈린다.** 이것이 설계를 바꾼 이유다.

## 4. 설계 — **계측 셋, 조작은 조건부**

### 4-1. 계측 셋

| | 무엇 | 가르는 것 | 면적 |
|---|---|---|---|
| **①** | **anyio limiter 를 직접 샘플** — `borrowed_tokens` · `statistics().tasks_waiting` | 🔑 **ㄷ 를 직접.** 대기가 0 이면 상한은 안 걸려 있다 | 샘플러 |
| **②** | **`t_handler_out`**(핸들러 마지막 줄) 추가 → `post` 를 **`post_app`** 과 **`post_loop`** 로 가른다 | 🔑 **ㄴ 을 직접.** 루프에서 보낸 시간이 숫자로 나온다 | 타임스탬프 1개 |
| **③** | **loop lag** — 사이드카가 `sleep(0.05)` 하고 실제 경과를 잰다 | ㄴ 보강 (②와 독립) | 사이드카 |

🔴 **GIL 카나리아는 뺐다.** 초판 설계에 있었는데 **자기가 재려는 자원을 쓰고**, ②가 같은
질문에 더 직접 답한다. ㄱ 은 **ㄴ·ㄷ 이 지워지고 남는 것**으로 다룬다(§6).

⚠️ `wait` 도 섞인 통이지만(§2-4) **①이 그 절반을 대신 답한다** — 스레드풀 대기가 0 이면
`wait` 은 전부 루프 디스패치다.

### 4-2. 순서 — 게이트로 간다

| 단계 | 무대 | 무엇 | 왜 |
|---|---|---|---|
| ~~**0**~~ | ✅ **했다 (로컬)** | ①의 **계측기 검증** — [결과](../../loadtest/results/anyio-limiter-probe-2026-08-23/README.md) | 🟢 `total_tokens=40` 런타임 확인 · `tasks_waiting` 관측됨 · 동시 40 초과면 걸린다 |
| ~~**1**~~ | ✅ **했다** | ①②③ 켜고 기준 조건 1팔 × 6판 | [결과](../../loadtest/results/ceiling-cause-stage1-2026-08-23/README.md) — **ㄴ 지지** |
| **2** | 🟡 **순위가 내려갔다** | 상한 스윕 20/40/80/160 | ①이 **95.5% 표본에서 대기 0** 이라 주된 제약이 아니다. **다만 최대 120 대기·borrowed 40 표본 5%** 라 «없다» 도 아니다 |

🔴 **0단계가 2단계를 없앨 수 있다던 기대는 틀렸다 (2026-08-23 정정).**
프로브는 **구조**를 확인했지 **AI 서버에서 걸렸는지**는 안 봤고, 그건 로컬로 볼 수 없다
([결과 §3](../../loadtest/results/anyio-limiter-probe-2026-08-23/README.md)). 🟢 대신 **계측 ①의 코드가 검증됐고**(`probe.py` 의 샘플러를 그대로
옮기면 된다) **1단계의 판정선이 날카로워졌다**(§6).

## 6. 판정선 — 실행 전에 박는다

> 🔑 **0단계가 이 표를 날카롭게 했다** — R10-a 는 `inflight_http` **160** 인데
> `inflight_handler` 평균이 **18~24**(그마저 과다 계수)다. **차이 ~140 이 ASGI 와 핸들러
> 사이에 있고**, 그것이 **스레드풀 큐면 ㄷ · 루프 디스패치 대기면 ㄴ** 이다.
> **`tasks_waiting` 한 값이 그것을 가른다.**
> ⚠️ 그리고 프로브가 보여줬듯 **중앙값이 아니라 최대·분포**를 남겨야 한다 — 80 동시에서
> `waiting` 이 p50 0 · 최대 39 로 오갔다.

| ① 스레드풀 대기 | ② `post_loop` | ③ loop lag | 결론 |
|---|---|---|---|
| **있다**(tasks_waiting > 0 상시) | — | — | 🟢 **ㄷ 스레드풀 상한** → 2단계로 스윕 |
| 0 | **크다** | **크다** | 🟢 **ㄴ 단일 이벤트 루프** |
| 0 | 작다 | 작다 | 🟡 **ㄱ 또는 ㄹ** — 남은 시간이 `infer`·`post_app` 에 있다면 **계산 자체**이고, GIL 은 그 위에서 논해야 한다 |
| 0 | 크다 | **작다** | 🔴 **설계 결함** — ②와 ③이 같은 것을 재야 하는데 갈렸다. 정의부터 다시 |

**「크다/작다」의 기준**: 같은 조건 6판의 **판 간 산포**와, 그 값이 `total`(≈107ms)에서
차지하는 비율. 🔴 **절대 임계값을 미리 박지 않는다**([[feedback_no_arbitrary_threshold_values]]) —
산포는 이 라운드가 스스로 준다.

### 무엇이 나오면 내가 틀린 것인가

- **①이 「대기 있음」인데 상한을 올려도 처리량이 안 오르면** → §2-2 의 읽기가 틀렸거나 상한이
  병목이 아니면서도 대기가 생기는 구조다
- 🔴 **①이 「대기 0」이면 산수가 안 닫힌다** — 스레드 40 × 핸들러 ~107ms 는 **374 rps** 인데
  실측이 **271** 이다. 대기가 0 인데 유효 동시성이 40 에 못 미친다면 **ㄴ 이나 ㄹ 이고,
  그 경우 `wait` 24.92ms 의 정체를 ②③이 답해야 한다**
- **`post_app` 이 `post` 의 대부분이면** → §2-3 의 「루프 직렬화 대기열」 해석이 틀렸다.
  꼬리 차이는 다른 데서 온 것이다
- **②를 넣었더니 `total` 이 눈에 띄게 늘면** → 계측이 재려는 것을 바꾼 것이다(앵커 필요)

## 7. 필요한 코드 변경 — 셋, 전부 계측 뒤

> ✅ **셋 다 들어갔다 (2026-08-23).** 아래는 실제로 넣은 모양이다.

| | 무엇 | 서비스 경로 영향 |
|---|---|---|
| **①③** | 🔑 **한 태스크로 합쳤다** — `sample_pool()` 이 20ms 마다 limiter(`total_tokens`·`borrowed`·`tasks_waiting`)를 읽고, **자기가 늦게 깬 만큼**을 loop lag 으로 같이 남긴다. 어차피 `sleep` 하므로 관측 비용이 하나로 묶인다 | `FRAME_PATH_METRICS` 켜졌을 때만 뜨고, lifespan 이 취소한다 |
| ② | `mark_handler_out()` + `_spans_of` 에 `post_app`·`post_loop` | 꺼져 있으면 즉시 반환(기존 `mark_*` 와 같다) |

🔴 **②를 「반환마다 한 줄」이 아니라 «얇은 래퍼 + `try/finally`» 로 넣었다** — `_detect_pose`
안에 **반환이 열 개**이고 예외 경로도 있다. 어느 쪽으로 끝나도 스레드는 반납되므로
**한 자리에서 찍어야 짝이 맞는다.**

⚠️ **최대와 분포를 남긴다** — 0단계 프로브에서 대기가 p50 0 · 최대 39 로 오갔다.
`thread_pool.waiting` 은 중앙값이 아니라 **분포 전체**다.

⚠️ **`post` 는 지우지 않고 남긴다** — R10-a 값과 비교가 되어야 한다. `post_app + post_loop`
합이 `post` 와 맞는지가 그 자체로 검산이다.

⚠️ ai-server 코드 변경이다([[feedback_minimize_python_changes]]) — 면적은 **계측 모듈 안 셋 +
핸들러 1줄**이고, 셋 다 **꺼져 있으면 아무것도 안 한다.**

🔴 **①은 손잡이가 아니라 관측이다.** 상한을 «바꾸는» 코드는 2단계로 갈 때 따로 넣는다 —
가지 않으면 안 넣는다.

- **`post_loop` 가 정말 직렬화인지 구분 못 한다** — 스레드 반납 후 루프에 도달하기까지의
  스케줄 대기도 거기 들어간다. ③이 그 부분을 따로 본다
- ~~**ㄱ(GIL)을 «직접» 재는 수단이 이 설계에 없다.**~~ → 🟢 **생겼다 (2026-08-23,
  [#507](https://github.com/Shadowfit/init/pull/507)).** 일 없는 스레드가 1ms 자고 깨며 늦게 깬 만큼을
  담는다(`GIL_PROBE_INTERVAL`). 깰 때 GIL 을 다시 잡아야 하므로 남는 것은 타이머 해상도와
  **GIL 재획득 대기** 뿐이다. 🔑 **루프 지체와의 «차» 가 요점이다** — 둘 다 늦으면 GIL,
  루프만 늦으면 루프가 일이 많은 것. 로컬 검증에서 무부하 0.394ms(2,133표본) 대 GIL 경합
  23.194ms(**131표본**)였고, **표본 수가 주저앉는 것 자체가 두 번째 신호다.**
  🔴 **아직 안 돌렸다** — 계측은 붙었고 이 판에 쓴 적은 없다. 설계는
  [`./per-process-ceiling-cause.md`](./per-process-ceiling-cause.md) 축 5
- **두 번째 천장(14.5 vCPU)은 범위 밖이다.** 이 문서는 «프로세스당 천장» 만 가른다
- **free-threaded 파이썬(3.13+ nogil)은 안 본다** — mediapipe 휠 유무부터 미확인이고,
  인터프리터를 바꾸면 측정 조건이 통째로 달라진다

## 11. ~~다음 판~~ ✅ **했다** — `post_loop` 안을 가른다

> 🟢 **결과 (2026-08-23)**: [`post-loop-breakdown-2026-08-23`](../../loadtest/results/post-loop-breakdown-2026-08-23/README.md).
> **주범은 Pydantic 응답 검증**이다 — 떼면 `post_loop` **20.32 → 9.75ms(−52%)**. 인코딩은 −9%.
> 🔴 **그런데 처리량은 −5.28% 다.** 이유가 §11-5 에 있다 — **`post_loop` 는 요청 시간의 4.6%**
> 이고, **79~81% 가 계측 밖**이다.
> 🔴 **§11-2 의 검산 가설이 틀렸다** — 비용이 «옮겨간» 게 아니라 «사라졌다».
> `model_dump()` 0.02ms ↔ `serialize_response` 10.57ms 로 **500배 다르다.**
> 🔑 **처리량이 왜 안 따라왔는지도 나왔다 (§3-1)** — 세 팔의 **rps/vCPU 가 1.72% 안에**
> 모인다(rps 산포는 9.1%). 팔은 «요청당 CPU 비용» 을 하나도 못 바꿨고, 바뀐 것은
> **프로세스가 끌어오는 CPU** 뿐이다(8.91 ↔ 9.94 vCPU). 즉 **«프로세스당 천장» 은
> 고정값이 아니라 루프/스레드풀 분배에 따라 11% 움직인다.** 🔴 왜 그런지는 안 답했다 —
> 후보 ㄱ(GIL)이 거기 있을 수 있고 [#507](https://github.com/Shadowfit/init/pull/507) 프로브가 물을 자리다.

1단계가 **`post_loop` 19.94ms(22.7%)** 를 찾았지만 **그 안이 무엇인지는 안 봤다.**
`def` 핸들러가 값을 돌려준 뒤 `http.response.start` 까지 FastAPI 가 하는 일은 넷이다:

| | 무엇 | |
|---|---|---|
| **A** | 스케줄 대기 — 스레드가 값을 돌려준 뒤 루프가 그 태스크를 다시 잡을 때까지 | 큐 |
| **B** | **Pydantic 응답 검증** — `response_model=PoseResponse` | 일 |
| **C** | **`jsonable_encoder` + `json.dumps`** | 일 |
| **D** | `send(http.response.start)` 까지의 잔여 | 일 |

### 11-1. 🔑 A 는 이미 답이 나와 있다

`loop_lag` 이 재는 것이 **「준비된 콜백이 얼마나 늦게 도는가」** 이고, A 가 바로 그것이다.

```
post_loop  19.94 ms
loop_lag   p50 2.00 ms      ← A
──────────────────────────
B+C+D      ≈ 17.94 ms  (post_loop 의 90%)
```

🟢 **A 는 작다. 남는 것은 «루프가 하는 일» 이다.** 그래서 이 판이 물을 것은 **B 냐 C 냐**로
좁혀진다.

⚠️ **추정이다** — `loop_lag` 은 샘플러의 재개 지연이고 요청 태스크의 재개 지연과 **같은 큐지만
같은 값은 아니다.** 이 판이 그것도 같이 확인한다.

### 11-2. 팔 셋 — 계약을 «측정용으로» 벗긴다

| 팔 | 무엇 | 빠지는 것 |
|---|---|---|
| **R** | 현행 — `response_model=PoseResponse` | 기준 |
| **N** | `response_model` 제거, 핸들러가 dict 반환 | **B**(검증). C 는 남는다 |
| **J** | 핸들러가 `JSONResponse` 를 직접 반환 | **B+C 대부분** — FastAPI 는 `Response` 인스턴스를 그대로 통과시킨다 |

**판정**

| | 결론 |
|---|---|
| R → N 이 산포를 넘어 줄면 | 🟢 **B — Pydantic 응답 검증이 주범** |
| N → J 가 산포를 넘어 줄면 | 🟢 **C — JSON 인코딩이 주범** |
| 둘 다 안 줄면 | 🔴 **A 이거나 D** — `loop_lag` 추정이 틀렸거나 잔여가 크다 |

🔴 **팔 N·J 는 응답 계약을 바꾼다. 측정용 팔이지 채택안이 아니다.**
프론트는 `sync_rate`·`rep_count`·`landmarks` 를 읽으므로 **그 필드가 같은 값으로 나가는지**를
팔마다 확인해야 한다(rig 이 응답을 파싱하므로 깨지면 판이 무효로 뜬다).

### 11-3. 판

| | |
|---|---|
| 무대 | `c7i.4xlarge` 1대 · **160세션 · 3.0fps** · 판당 90초 · 풀 201 · 계측 ON |
| 배열 | **3팔 × 4반복 = 12판 + 버림 1 = 13판** (블록마다 세 팔이 한 번씩) |
| 소요 | 판당 ~100초 → **약 22분** |
| 조건 | **응답 바디 크기를 같이 남긴다** — 인코딩 비용이 거기 비례한다. 랜드마크 33개 × 5필드다 |

### 11-5. 🔑 판이 열어놓고 간 것 — 계측이 요청의 20% 만 본다

리틀의 법칙을 ASGI 구간에 적용하니:

```
rps × total 평균 = ASGI 안에 있는 요청 수
R  354.5 × 91.6ms = 32개      세션 160 → 밖에 128개
클라 지연 443.6ms 중 ASGI 구간은 91.6ms = 21%
```

🔴 **요청 160개 중 ASGI 안에는 30개 안팎뿐이다.** `t_asgi_in` 은 미들웨어가 도는 시점이고,
그 앞의 **소켓 accept · HTTP 파싱 · 바디 수신**은 uvicorn 이 **이벤트 루프에서** 한다 —
**계측 밖이다.**

**그래서 1단계의 「루프 관여 44.7%」도 과소평가였다** — 그 44.7% 는 ASGI 구간 안에서의 비율이고,
ASGI 밖까지 넣으면 루프의 몫은 더 크다. **다음 판이 물을 것은 그 구간이다.**

### 11-4. 이 판이 못 하는 것

- **D(잔여)를 따로 못 뗀다** — J 팔에서도 `send` 는 돈다. B·C 가 지워지고 남는 것이 D 다
- **채택안을 안 낸다.** 「C 가 주범」으로 나와도 `orjson` 을 쓸지는 **별개 결정**이고
  의존성이 는다(현재 requirements 에 없다)
- **ㄱ(GIL)은 여전히 안 갈린다** — B·C 가 파이썬 코드라 GIL 을 잡지만, 이 판은
  「무엇이 오래 걸리나」만 답한다

## 12. 다음 판 — **ASGI «앞»** 을 잰다

§11-5 가 남긴 것: **요청 160개 중 ASGI 안에는 30개뿐이고 130개가 그 밖에 있다.**
클라 지연 443.6ms 중 계측이 보는 것은 **21%** 다.

### 12-1. 경계를 정확히 긋는다

`t_asgi_in` 은 **미들웨어 `__call__` 진입**이다. ASGI 규약상 그 시점에는 **요청줄과 헤더가
이미 파싱**돼 있고 **바디는 아직 안 읽었다**(`receive()` 로 나중에 읽는다).

| | 어디 | 계측 |
|---|---|---|
| TCP 연결 수립 · 커널 accept 큐 | 🔴 **밖** | 없음 |
| uvicorn accept · 프로토콜 생성 · **요청줄/헤더 파싱** | 🔴 **밖** | 없음 |
| **바디 수신(~40KB base64)** · 라우팅 · 스레드 디스패치 | ✅ 안 (`wait`) | 19.78ms |

🟢 **그래서 「바디가 커서 느리다」는 이미 답이 나와 있다** — 바디 수신은 `wait` 안에 있고
그 전체가 22% 다. **밖에 있는 130개는 «연결이 아직 앱에 안 닿은 것»** 이다.

### 12-2. 🔴 그런데 예전 판정 하나가 잘못 읽혔다 — 그것부터 고친다

[`ai-receive-path-scaling.md` §2-4](./ai-receive-path-scaling.md) 가 keep-alive 를 두 번 재고
**「풀 소진으로 무효」** 로 닫았다:

```
ka_1  keep-alive  479.82 RPS  nolease 38,347  ❌
url_1 urllib      348.95 RPS  nolease      0  ✅
```

**`nolease` 는 «풀 소진» 이 아니다.** 코드를 보면 `PoolT.lease()` 는 용량을 안 본다 —
`self._detectors.get(session_id)` 가 없으면 `None` 이고, 핸들러 메시지도
*「세션 …에 배정된 분석기가 없습니다 (StartAnalysis 먼저 호출 필요)」* 다
(`mediapipe_detector.py:230` · `pose.py:136`). 즉 **세션이 안 붙은 것**이지 자리가 없는 게 아니다.

🔴 **그리고 38,400 요청 중 38,347 이 nolease 다 — 99.86% 가 즉시 반려됐다.**
**480 RPS 는 처리량이 아니라 «빨리 실패한 것»** 이다.

> **그래서 「keep-alive 가 +38%」라는 근거는 없다.** 그 수치를 인용하면 안 된다.
> 이 판의 **선결 과제는 그 사본이 왜 세션을 못 붙였는지**이고, **rig 결함일 가능성이 높다.**

### 12-3. 계측 둘 — 클라 한 쪽, 서버 한 쪽

| | 무엇 | 답하는 것 |
|---|---|---|
| **⑥** | **부하기가 `connect()` 시간을 따로 잰다** — `http.client.HTTPConnection` 으로 바꿔 연결 수립과 요청 전송을 분리 | 🔑 **연결 수립이 얼마인가.** 클라 쪽이라 서버 변경 0 |
| **⑦** | **listening 소켓의 accept 큐 깊이**를 샘플 (`ss -tln` 의 `Recv-Q`) | **연결이 밀리는가** — 밀리면 uvicorn 의 accept 가 못 따라가는 것 |

⑥이 핵심이다. `urlopen` 은 **요청마다 새 TCP 연결**이라 354 RPS = **초당 354개 연결**이고,
그 비용은 지금 **아무 데도 안 잡힌다.**

### 12-4. 팔 둘 — 단, 순서가 있다

```
0단계   세션 등록을 고친다 — nolease 가 0 인 keep-alive 사본을 먼저 만든다
        🔴 여기서 안 되면 판을 안 돈다. 예전 두 판이 여기서 무효였다
1단계   팔 K(keep-alive) ↔ 팔 U(새 연결)  ·  ⑥⑦ 을 켜고
```

| | 결론 |
|---|---|
| `connect_ms` 가 크고 K 가 U 보다 빠르면 | 🟢 **연결 수립이 병목** — 실제 앱은 keep-alive 라 **「동시 116명」에 조건이 붙는다** |
| `connect_ms` 가 작은데 130개가 여전히 밖이면 | 🔴 accept 큐(⑦)를 본다 — uvicorn 의 accept 루프 |
| 둘 다 작으면 | 🔴 **부하기 쪽이다** — 160 스레드가 같은 박스에서 도는 구조 자체를 의심해야 한다 |

🔑 **마지막 칸이 중요하다.** §11 의 「밖에 130개」는 **클라 지연에서 서버 구간을 뺀 값**이라,
그 130개가 **서버 큐인지 부하기 스레드 대기인지 아직 안 갈렸다.** ⑥이 그것을 가른다 —
`connect()` 가 클라 쪽 대기까지 포함하기 때문이다.

### 12-5. 판

| | |
|---|---|
| 무대 | `c7i.4xlarge` 1대 · **160세션 · 3.0fps** · 판당 90초 · 풀 201 · 계측 ON |
| 배열 | 버림 1 + `K U U K K U U K` = **9판** (위치 합 K=18 · U=18) |
| 소요 | 약 **15분** |
| 선결 | **0단계(세션 등록)** — 이게 안 서면 판을 안 돈다 |

### 12-6. 이 판이 못 하는 것

- **커널 accept 큐와 uvicorn accept 루프를 못 가른다** — ⑦은 「밀린다」까지만 답한다
- **채택안을 안 낸다** — keep-alive 가 빠르다고 나와도 **그건 클라이언트 쪽 사실**이고,
  서버가 할 일은 따로다
- **ㄱ(GIL)은 여전히 안 갈린다**
