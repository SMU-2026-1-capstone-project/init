## 0. 한 줄

`POST /pose` 는 **공유 토큰 하나**만 보고 `session_id` 는 클라이언트가 준 정수를 그대로 믿는다.
그리고 **이 갭은 Spring 쪽에서 닫을 수 없다** — 콜백이 도착하는 시점엔 공격자의 프레임과 본인의
프레임이 **구분 불가능**하기 때문이다.

---

## 1. 사실 (코드 + 2026-08-12 실행 관찰)

### 1-1. 두 홉 모두 신원을 안 묻는다

| 홉 | 확인하는 것 | 확인하지 않는 것 |
|---|---|---|
| ① 클라 → AI HTTP | `AI_PUBLIC_TOKEN` 문자열 일치 (`middleware/auth.py:44-53`) | **호출자가 누구인지** |
| ① AI 내부 | `session_id` 가 레지스트리에 **존재하는지** (`pose.py:88-93`) | **그 세션이 이 호출자 것인지** |
| ③ AI → Spring | `INTERNAL_API_TOKEN` (`InternalAuthInterceptor`) | **누가 AI 에게 시켰는지** |
| ③ Spring 내부 | `sessionRepository.existsById()` (`PoseDataService.java:68`) | **그 세션의 주인** |

`AI_PUBLIC_TOKEN` 은 **앱 번들에 배포되는 값**이고, `session_id` 는 AUTO_INCREMENT 순차 정수라
추측 가능하다.

### 1-2. 오늘 이 경로를 실제로 밟았다

세션 1902 검증(#192) 중 `AI_PUBLIC_TOKEN` **하나만** 붙여 `session_id=1902` 로 프레임을 POST 했고,
AI 는 **사용자 신원을 한 번도 묻지 않고** 받아 처리했다. 거절 사유는 «권한 없음» 이 아니라
«가시성 부족» 이었다 — 즉 **인가 판정 자체가 경로에 없다.**

⚠️ **미검증**: 남의 세션에 꽂아보지는 않았다(내 세션으로만 확인). 다만 위 표대로 **그것을 막는 코드가
양쪽 어디에도 없다.**

### 1-3. 대조 축은 이미 다 갖춰져 있다

없는 것은 데이터가 아니라 **연결**이다.

- Spring 은 세션 주인을 안다 — `exercise_sessions.member_id`
- 소유권 검증 **선례도 이미 있다** — `SessionService.java:363` 이 `endSession` 에서
  `session.getMember().getId().equals(currentMemberId)` 로 막고 `ACCESS_DENIED` 를 던진다
- 즉 REST 경로(`/sessions/{id}/end`)는 막혀 있는데 **AI 경유 경로만 뚫려 있다.** 같은 자원에 대해
  문은 잠갔고 창문은 열어둔 모양이다

## 2. 왜 Spring 쪽 대조만으로는 못 닫나 (핵심)

`ai-auth-token-flow.md` §5-4 는 후보 (b) 로 *"Spring 이 `(sessionId → memberId)` 를 기억해두고
콜백에서 대조"* 를 든다. **이것만으로는 닫히지 않는다.**

공격은 **없는 세션을 만드는 것이 아니라 있는 세션에 끼어드는 것**이다:

```
피해자가 정상적으로 세션 1902 를 시작  (Spring: 1902 → member 7 로 이미 안다)
공격자가 session_id=1902 로 프레임 주입
AI 가 1902 상태에 누적 → rep 완성 → SavePoseDataBatch(1902, ...)
Spring: "1902 는 member 7 것이 맞다" → 통과 ✅
```

콜백에 실려 오는 것은 **세션 번호뿐**이고, 그 번호는 진짜다. **Spring 이 대조할 「주장된 신원」이
애초에 존재하지 않는다.** 대조란 두 값을 맞춰보는 것인데 한쪽이 비어 있다.

> **결론: 신원은 채널 ①에서 포착돼야 한다.** 거기서 안 잡으면 그 뒤 어느 지점에서도 복구할 수 없다.
> (b) 는 «없는 세션 번호» 나 «세션 삭제 후 도착한 콜백» 같은 다른 종류만 막는 보조 방어다.

## 3. 선택지

### (a) I2 — 세션 단위 단기 토큰 (기존 문서의 안)

Spring 이 세션 시작 시 단기 토큰을 발급하고 클라가 `/pose` 에 실어 보내면 AI 가 검증한다.

| | |
|---|---|
| 장점 | 채널 ①에서 신원이 생긴다 = 근본 해결. 이미 «예고된 전환» 이다(2026-05-24 결정 로그) |
| 비용 | AI 에 **검증 수단이 현재 0** — 자체검증이면 키 배포, introspection 이면 프레임마다 왕복 |
| 미결정 | 검증 방식·만료 시간이 그 문서 §7 에 그대로 열려 있다 |

### (b) Spring 콜백 대조

**§2 의 이유로 단독 채택 불가.** (a)/(d) 와 함께라면 **심층방어로 가치 있다** — 세션이 삭제된 뒤
도착한 콜백(#87 고아 행 창)도 같이 막힌다.

### (c) 감수 박제

서버간 채널을 신뢰 경계 안으로 간주하고 «지금은 안 막는다» 를 명시적으로 기록.

| | |
|---|---|
| 장점 | 비용 0. 실제 사용자 규모를 생각하면 합리적일 수 있다 |
| 단점 | **면접에서 「왜 안 막았나」를 반드시 받는다.** 다만 «모르고 안 한 것» 과 «알고 감수한 것» 은 완전히 다르게 들린다 |
| 조건 | 감수하려면 **공격 표면과 피해 범위를 적어둬야** 한다. 그게 없으면 감수가 아니라 방치다 |

### (d) 세션 nonce — I2 의 경량판 ⭐ (이 문서가 추가하는 안)

토큰 체계를 새로 만들지 않고, **세션당 무작위 비밀값 하나**를 세 곳에 흘린다.

```
Spring: 세션 생성 시 nonce 생성 → ① 응답으로 클라에 반환
                                  ② StartAnalysis 로 AI 에 전달 (AI 가 세션 상태에 보관)
클라  : POST /pose 에 nonce 동봉
AI    : 보관값과 대조 → 불일치면 거절
```

| | |
|---|---|
| **신규 인프라 0** | JWT 라이브러리도, 키 배포도, introspection 왕복도 없다. **문자열 비교 하나** |
| **만료가 자연스럽다** | 세션이 끝나면 AI 가 상태를 버리므로 nonce 도 같이 죽는다 → §7 의 «만료 몇 분?» 이라는 **근거 없는 숫자를 정할 필요가 없다** |
| **기존 자리에 얹힌다** | `SessionState` 에 필드 하나, `ExercisesResponseDto` 에 필드 하나 |
| 비용 | **proto 변경**(`AnalyzeRequest`·`ReattachRequest` 에 필드 추가) → 양쪽 동시 배포 필요 |
| 비용 | 재부착(`ReattachAnalysis`) 때 nonce 를 다시 실어줘야 한다 — 안 하면 이어하기가 깨진다 |
| 한계 | **전송 구간이 평문이면 도청으로 무력화된다** → [#148](https://github.com/Shadowfit/init/issues/148)(릴리스에서 AI 직결이 평문 HTTP) 과 **묶어서 봐야 한다** |
| 한계 | 자기 세션 nonce 를 아는 사람이 자기 데이터를 오염시키는 것은 못 막는다(그건 위협 모델 밖) |

## 4. 추천 (결정은 사용자)

**(d) + (b)** 를 추천한다.

1. **(d) 가 채널 ①에서 신원을 만든다** — §2 가 요구하는 유일한 조건을 만족하면서, (a) 가 미결로
   남긴 «검증 방식·만료» 두 질문을 **설계상 소멸**시킨다(세션 수명 = 토큰 수명)
2. **비용이 I2 보다 훨씬 작다** — AI 에 JWT 검증 수단이 0인 상태를 그대로 두고 갈 수 있다
3. **(b) 를 얹으면 심층방어가 된다** — #87 의 고아 행 창도 같은 검사로 덮인다
4. **(a) 로 가는 길을 막지 않는다** — 나중에 I2 를 채택하면 nonce 자리에 세션 토큰이 들어가고
   대조 지점은 그대로다. 즉 **버리는 작업이 아니다**

**단, #148 을 함께 처리하지 않으면 (d) 의 효과가 반감된다.** 평문 구간에서는 nonce 가 도청 가능하다.
둘을 한 작업 단위로 묶는 것을 권한다.

**(c) 도 여전히 정당한 선택지다.** 실사용자가 없는 단계에서 «알고 감수한다» 를 근거와 함께 박제하는
것은 방치와 다르다. 다만 그 경우 §1-2 의 관찰과 §2 의 논증을 **감수 문서에 그대로 옮겨 적어야** 한다.

## 5. 채택 시 검증 방법

이 결함은 «되는지» 가 아니라 «막히는지» 를 봐야 하므로 정상 경로 테스트로는 증명되지 않는다.

| 검증 | 방법 |
|---|---|
| 남의 세션 주입이 막히는가 | 계정 A 로 세션 생성 → **계정 B 의 nonce**(또는 nonce 없음)로 A 세션에 `/pose` → 거절 확인 |
| 본인 경로가 안 깨지는가 | 정상 세션 한 판 완주 (오늘 세션 1902 절차 재사용) |
| 재부착이 안 깨지는가 | 세션 진행 중 `ReattachAnalysis` 후 같은 nonce 로 계속 전송 |
| Spring 대조가 도는가 | 세션 삭제 후 도착한 콜백이 거절되는지 (#87 창) |

## 6. 정직하게 비어 있는 것

- **교차 사용자 주입을 실제로 재현하지 않았다.** §1-2 는 «내 세션에 신원 없이 넣었다» 까지다.
  재현은 계정 2개로 5분이면 되므로, 착수 전에 **먼저 재현해 두는 것**을 권한다 — 안 그러면
  «막았다» 의 before 가 없다
- **nonce 의 길이·생성 방식**은 정하지 않았다. 근거 없이 숫자를 박지 않는다
- **피해 규모가 미측정**이다. 남의 세션을 오염시키면 리포트·통계가 틀어지지만, 그 «틀어짐» 이
  사용자에게 어떻게 보이는지는 확인하지 않았다
- **#148 의 실제 배포 형태**(릴리스 빌드가 어떤 스킴으로 AI 를 부르는지)는 이 문서에서 확인하지 않았다

### 7-1. (b) — 지금 (proto 무관, 충돌 0)

`PoseDataService.savePoseDataBatch` 가 **세션이 `IN_PROGRESS` 가 아니면 배치를 버린다.**

- **무엇을 닫나**: 세션이 `COMPLETED`/`FAILED`/`CANCELLED` 로 끝난 뒤 도착한 배치. 예전엔

  세션에.
- **정상 경로를 안 깬다**: `endSession` 은 endTime 만 찍고 status 는 IN_PROGRESS 로 둔다.
  사용자가 종료를 눌러도 늦게 오는 정상 배치는 IN_PROGRESS 를 만나 통과한다. 걸리는 것은
  `CompleteAnalysis` **이후**뿐이다.
- **던지지 않고 조용히 버린다**: [#280](https://github.com/Shadowfit/init/pull/280) 의 데드락
  재시도가 붙어 있어, 던지면 AI 가 **영영 거절될 배치를 재시도**한다. 종료 세션 배치는 주입이면
  버리는 게 맞고 정상 지연이면 무의미하므로 두 경우 다 드롭이 옳다.
- **관측**: `shadowfit.pose.batch.rejected`(status 태그). 0 이 아니면 «종료 직전 경합» 이거나
  «종료 후 주입» 인데 **둘을 여기서 못 가른다** — 콜백에 «주장된 신원» 이 없어서다. 그게 (d)가
  필요한 이유이기도 하다.

🔴 **이것은 #187 을 «닫지» 않는다.** 공격의 본체는 **진행 중인(IN_PROGRESS)** 남의 세션에
끼어드는 것이고, 그건 이 가드를 그대로 통과한다. (b) 는 §2 가 말한 대로 «종료 후 창» 하나만
닫는 **심층방어**다. 본체는 (d)가 채널 ① 에서 신원을 세워야 막힌다.

### 7-2. (d) — 뒤에 (#295 머지 후, proto 는 그때)

세션 nonce 를 채널 ① 에 세운다. **2단계**로 — ① «nonce 오면 검증, 없으면 통과»(compat)로 넣고,
② 프론트가 동봉하기 시작하면 강제. 안 그러면 머지 순간 프론트가 못 따라와 모든 세션이 깨진다.
proto 는 #295 가 정리된 뒤에 건드린다(AI 파일 넷의 충돌을 피한다).

### 7-2-1. 🟢 (d) 1단계 구현 (2026-08-22) — compat 까지

**넣은 것**: Spring 이 세션 생성 시 비밀값을 만들어 ① REST 응답 ② `AnalyzeRequest`/
`ReattachRequest` 로 흘리고, AI 가 세션 상태에 보관했다가 `POST /pose` 동봉값과 대조한다.

| 자리 | 무엇 |
|---|---|
| `SessionNonceGenerator` | 128비트 · URL-safe Base64 22자 · 패딩 없음 |
| `V8__add_session_nonce.sql` | `exercise_sessions.session_nonce VARCHAR(64) NULL` |
| `Session` | 필드 + **`@ToString` 에서 제외** (엔티티 통째 로깅으로 새는 자리를 막는다) |
| proto | `AnalyzeRequest.session_nonce = 6` · `ReattachRequest.session_nonce = 7` |
| AI | `SessionState.session_nonce` · 두 핸들러가 보관 · `pose.py` 가 `compare_digest` 로 대조 |

#### 설계 문서가 놓쳤던 것 — 클라에 돌려줘야 하는 응답이 **셋**이다

문서 §3-(d)는 «`ExercisesResponseDto` 에 필드 하나» 라고 적었는데, 실제로는
**`ActiveSessionResponseDto`(진행 중 세션 조회)** 가 빠져 있었다. 앱이 죽었다 살아나면 그
경로로 세션을 복구하는데, 거기서 nonce 를 안 주면 **복구된 세션은 2단계에서 `/pose` 를
영영 못 부른다.** 재부착 응답까지 셋 다 실어준다.

#### 거절 응답은 «세션 없음» 과 구분되지 않는다

🔴 «세션은 있는데 네 것이 아니다» 라고 답하면 공격자가 `session_id` 를 훑어 **살아있는
세션을 열거**할 수 있다 — 막으려던 것의 절반을 응답으로 되돌려주는 셈이다. 구분은 서버
로그에만 남기고, 응답은 존재하지 않는 세션과 같은 모양으로 준다. 테스트가 이 성질을 직접
고정한다(`test_거절이_없는_세션과_구분되지_않는다`).

#### 1단계가 통과시키는 것 (의도된 구멍)

- 요청이 nonce 를 **안 보내면** 통과 — 프론트가 아직 동봉하지 않는다
- 세션에 보관값이 **없으면**(배포 전 시작) 통과 — V8 이 NULL 을 허용하는 이유

**즉 이 단계는 아직 아무도 막지 않는다.** 배선과 계약만 세운다. 실제 차단은 프론트가 동봉을
시작한 뒤 2단계에서 켠다.

### 7-3. §6 의 «재현 먼저» 는 부분만 했다

로컬 스택으로 재현하려 했으나 **AI 컨테이너에 `AI_PUBLIC_TOKEN` 이 안 걸려 있어 fail-closed**
상태였고(모든 요청 401), MySQL 이 느려(register 2분 타임아웃) 교차사용자 주입까지는 못 갔다.
확정된 것은 **정적 사실**이다 — 막는 코드가 인증·핸들러 어디에도 없다(§1-1 표). 동적 재현
(«남의 세션에 꽂았을 때 어디까지 오염되나»)은 깨끗한 격리 환경이 필요하고, (d) 착수 전으로 남긴다.
