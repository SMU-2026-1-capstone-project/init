## 0. 한 줄 요약

**해시는 하나의 개념이 아니라 목적이 다른 네 갈래다.** 갈래를 잘못 고르면 함수가 "느리거나 약한" 게 아니라 **틀린 답을 낸다.** 2026-08-06 에 그걸 겪었다 — 오류 검출용 `CRC32` 를 값 분산에 썼더니, 시딩 데이터에 **없어야 할 규칙**이 생겨 측정이 무의미해졌다(§4).

## 1. 네 갈래 — 목적이 다르면 다른 함수다

| 갈래 | 목적 | "좋다"의 기준 | 대표 |
|---|---|---|---|
| ① **오류 검출** | 전송·저장 중 **깨졌는지** 알아채기 | 버스트 오류 검출 보장, 하드웨어로 저렴 | CRC32, Adler-32 |
| ② **값 분산** | 키를 버킷에 **고르게 흩뿌리기** | 균등성, 입력 구조에 안 휘둘림, 빠름 | MurmurHash3, xxHash, FNV-1a, SipHash |
| ③ **무결성·신원** | 내용이 **같은지** 증명, 위조 방지 | 충돌 저항성 | SHA-256, SHA-3, BLAKE2/3 |
| ④ **비밀번호** | 유출돼도 **되돌리기 어렵게** | **의도적으로 느림**, 메모리 요구 | bcrypt, scrypt, Argon2, PBKDF2 |

> 🔴 **①과 ②를 섞는 것이 흔한 사고다.** 둘 다 "정수를 뱉는 빠른 함수"처럼 보이지만, ①은 **깨진 걸 알아채는 것**이 목적이라 균등 분산을 보장하지 않는다. §4 가 그 사례다.
>
> 🔴 **③을 ④에 쓰는 것도 흔한 사고다.** SHA-256 은 빠른 게 장점인데, 비밀번호에서는 그 빠름이 **공격자에게 유리**하다. 초당 수십억 번 시도할 수 있게 된다.

## 2. 갈래별 목록

### ① 오류 검출 (체크섬)

| 함수 | 출력 | 메모 |
|---|--:|---|
| **CRC32** | 32bit | 이더넷 프레임, ZIP·PNG·gzip. **GF(2) 위에서 선형** — 그래서 하드웨어로 싸고 버스트 오류를 수학적으로 보장해 잡는다. 그리고 **그 선형성 때문에 값 분산에는 못 쓴다**(§4) |
| Adler-32 | 32bit | zlib. CRC32 보다 빠르지만 짧은 입력에서 약하다 |

### ② 값 분산 (비암호학적 해시)

| 함수 | 메모 |
|---|---|
| **MurmurHash3** | 해시 테이블·샤딩의 사실상 표준. 빠르고 균등 |
| **xxHash / XXH3** | 현존 최고 속도급. 대용량 스트림에 강함 |
| FNV-1a | 극단적으로 단순. 짧은 키에 쓸 만함 |
| CityHash / FarmHash | 구글. 긴 문자열에 최적화 |
| **SipHash** | **키를 받는** PRF. 외부 입력이 키가 될 때 **HashDoS** 를 막는다 — Rust `HashMap`·Python `dict` 기본값 |

> ⚠️ **MySQL 8.0 에는 이 갈래의 내장 함수가 없다.** `CRC32`·`MD5`·`SHA1`·`SHA2` 넷뿐이다. 그래서 SQL 안에서 값 분산이 필요하면 **③의 함수를 빌려 쓰게 된다**(§3).

### ③ 무결성·신원 (암호학적 해시)

| 함수 | 출력 | 상태 |
|---|--:|---|
| MD5 | 128bit | 🔴 **깨졌다** — 충돌 생성 2004, chosen-prefix 2009. 보안 용도 금지 |
| SHA-1 | 160bit | 🔴 **깨졌다** — SHAttered 2017, chosen-prefix 2020. Git 도 이전 중 |
| **SHA-256 / 512** (SHA-2) | 256/512bit | ✅ 현재 표준 |
| SHA-3 (Keccak) | 가변 | ✅ 다른 구조(스펀지). SHA-2 가 깨져서 나온 게 **아니다** — 설계 다양성 확보용 |
| BLAKE2 / BLAKE3 | 가변 | ✅ SHA-2 급 안전성에 훨씬 빠름 |

> 📌 **"깨졌다"는 충돌을 **의도적으로** 만들 수 있다는 뜻이다.** 공격자가 없는 용도(파일 중복 탐지, 값 분산, 캐시 키)에서는 MD5 도 여전히 멀쩡히 동작한다 — §4 에서 MD5 를 쓴 이유가 그것이다. **그 판단은 "공격자가 있는가"로만 갈린다.**

### ④ 비밀번호 (의도적으로 느린 KDF)

| 함수 | 저항하는 것 |
|---|---|
| PBKDF2 | 반복 횟수로 느리게. FIPS 인증이 필요할 때 |
| **bcrypt** | cost factor 로 느리게. 메모리는 적게 씀 → **GPU 공격에 상대적으로 약함** |
| scrypt | **메모리 하드** — GPU/ASIC 병렬화를 어렵게 |
| **Argon2** (id) | 2015 Password Hashing Competition 우승. 시간·메모리·병렬도를 따로 조절. **신규 프로젝트 권장** |

## 3. MySQL 안에서 값 분산이 필요할 때

내장이 ③밖에 없으므로 관용 패턴은 이렇다:

```sql
-- 128비트 중 상위 32비트만 정수로 꺼내 나머지 연산
CONV(SUBSTRING(MD5(key), 1, 8), 16, 10) % N
```

- `SUBSTRING(...,1,8)` — 16진 8자리 = 32비트. 더 가져오면 `CONV` 가 `BIGINT` 범위를 넘겨 포화된다
- `MD5` 대신 `SHA1`·`SHA2` 도 같은 형태로 쓸 수 있다 (§4 에서 셋 다 통과)

⚠️ **MySQL 의 `PARTITION BY HASH(expr)` 는 이것과 무관하다** — 내부 해시를 쓰므로 위 식과 결과가 다르다.

## 4. 실측 — 왜 CRC32 가 실패했나 (2026-08-06)

### 사고 경위

부하 시딩에서 세션 상태를 `ELT(1 + (n % 4), ...)` 로 정했는데, `member_id` 도 `1 + (n % 200000)` 이라 **둘이 같은 `n` 의 함수**였다. `200000 % 4 == 0` 이라 회원의 모든 세션이 같은 상태가 됐다([issue #109](https://github.com/Shadowfit/init/issues/109)).

고치려고 `CRC32(CONCAT('st', n)) % 4` 로 바꿨는데 **그것도 틀렸다.**

### 검사 방법

시딩의 `n` 은 등차수열이고, **한 회원의 세션은 정확히 200,000 간격**에 있다. 그래서 두 가지를 본다:

1. **오프셋 상관** — `n` 과 `n+k` 의 값이 같은 비율. 무작위면 `0.25`
2. **균등성** — 값별 개수의 표준편차. **표본은 `n=0..199,999`(20만)** 이고, 무작위면 버킷 하나의 개수는 `Binomial(200000, 0.25)` 라 σ ≈ √(200000 × 0.25 × 0.75) ≈ **194**

> ⚠️ **아래 표와 §4 본문의 다른 수치는 표본 수가 다르다.** 표는 20만(σ 기대 194)이고, "값별 개수가 정확히 250,000 × 4" 라는 관측은 **시딩 테이블 100만 행**(σ 기대 433)에서 나온 것이다. 섞어 읽지 말 것.

### 결과

| 함수 | n vs n+1 | n vs n+2 | **n vs n+200,000** | 개수 σ |
|---|--:|--:|--:|--:|
| **CRC32** | **0.0044** | **0.4100** | 🔴 **0.0000** | 🔴 **0** |
| MD5 | 0.2508 | 0.2490 | 0.2524 | 160 |
| SHA-1 | 0.2506 | 0.2487 | 0.2493 | 229.3 |
| SHA2-256 | 0.2514 | 0.2533 | 0.2476 | 159 |
| *(무작위 기대)* | *0.25* | *0.25* | *0.25* | *≈194* |

### 읽는 법

**`n vs n+200,000 = 0.0000` 이 결정적이다.** 회원의 연속된 세션이 **절대 같은 상태가 될 수 없다**는 뜻이다. 종속이 사라진 게 아니라 **방향만 뒤집혔다** — 전에는 "항상 같음", 후에는 "항상 다름". 둘 다 인공적이다.

**개수 σ = 0 도 신호였다.** 20만 표본에서 CRC32 의 네 버킷이 정확히 같은 개수였다 — 무작위라면 σ ≈ 194 만큼 흔들려야 하는데 0 이다. **너무 깨끗한 것이 이상한 것이다.**

같은 일이 실제 시딩(100만 행)에서도 보였다. **표본이 다르므로 기대값도 다르다:**

| 표본 | 함수 | 버킷별 개수 | 기대 σ | 관측 σ |
|---|---|---|--:|--:|
| 100만 | CRC32 | `250,000 × 4` (오차 0) | 433 | 🔴 **0** |
| 100만 | MD5 | 250,426 / 250,358 / 249,554 / 249,662 | 433 | **395** |

MD5 쪽의 ±450 안팎 흔들림이 **정상**이고, CRC32 의 오차 0 이 비정상이다.

원인은 §2 ①에 적은 그대로다 — CRC32 는 GF(2) 위에서 선형이라 **등차 입력의 구조가 하위 비트에 그대로 남는다.** 네트워크 오류 검출에서 장점인 성질이 여기서는 정확히 약점이 됐다.

> 📌 **교훈은 "CRC32 는 나쁘다"가 아니다.** 이더넷은 지금도 CRC32 를 쓰고 그건 옳은 선택이다. 교훈은 **"목적이 다른 갈래에서 함수를 빌려오면 조용히 틀린다"** 는 것이고, 그걸 알아채려면 §4 처럼 **분산 자체를 검사해야 한다.** 시딩 데이터를 만들고 "해시 썼으니 됐지" 하고 넘어갔다면 §4-4 의 결론이 통째로 잘못된 채 남았을 것이다.

### 이 실측의 한계

- **`% 4` 만 봤다.** 버킷 수가 다르면(예: `% 3`, `% 16`) 결과가 다를 수 있다 — 특히 CRC32 는 2의 거듭제곱 나머지에서 구조가 잘 드러난다
- **입력이 `'st' + 연속 정수` 하나뿐이다.** 일반적인 해시 품질 벤치마크가 아니다
- **BLAKE2·MurmurHash·xxHash 는 안 쟀다** — MySQL 내장이 아니라 이 실험에 넣을 수 없었다

## 5. 이 프로젝트에서 실제로 쓰는 것

| [`OutboxPublisher.java:77`](../../backend/src/main/java/com/shadowfit/service/Exercise/OutboxPublisher.java) | `UUID.randomUUID()` 앞 8자 | — | ✅ 같음 (publisher 식별) |
| [`measure_admin_filter_explain.sh:134`](../../loadtest/measure_admin_filter_explain.sh) | **MD5** → `% 4` | ② (③을 빌림) | ✅ 공격자 없는 용도. §4 로 검증함 |

**그 외에는 해시를 쓰지 않는다.** JWT 서명은 라이브러리 안쪽이라 여기 세지 않았다.

### BCrypt 에 대한 단서

Spring Security 기본값 strength 10 을 그대로 쓰고 있다. **틀린 선택은 아니지만 최선도 아니다** — §2 ④에 적었듯 bcrypt 는 메모리를 적게 써서 GPU 공격에 Argon2 보다 약하다.

⚠️ **바꾸자는 제안이 아니다.** 이 프로젝트에서 재본 적이 없고(해시 시간·공격 비용 모두), 비밀번호 해시 교체는 기존 사용자 마이그레이션 경로가 필요하다. **"기본값을 썼다"는 사실만 기록해둔다.**

## 6. 고르는 법 (요약)

```text
비밀번호인가?            → ④ Argon2id (신규) / bcrypt (기존·Spring 기본)
공격자가 충돌을 노리는가? → ③ SHA-256 이상. MD5·SHA-1 금지
값을 버킷에 흩뿌리는가?   → ② MurmurHash3·xxHash
                            (MySQL 안이면 MD5/SHA2 를 빌려 쓰되 §4 처럼 검사할 것)
깨졌는지만 알면 되는가?   → ① CRC32
```

**그리고 어느 갈래든, 분산이 중요하면 쓰기 전에 §4 의 두 검사(오프셋 상관·개수 σ)를 돌릴 것.** 오늘 그걸 안 했으면 두 번 틀린 채로 넘어갔다.
