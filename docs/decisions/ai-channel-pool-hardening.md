## 1. 배경/문제

`ExerciseAnalysisService.java`의 3-프로세스 채널 풀(`session_id % 3` 라우팅)에 문서화되지 않은 갭이
둘 있다: ① 채널이 가리키는 AI 프로세스가 죽으면 그 세션이 그냥 갇힌다(재배치 없음), ② 풀 크기·포트
매핑이 Java 상수와 `entrypoint.sh`의 포트 배정 양쪽에 손으로 동기화돼 있어 이미 한 번 어긋난 이력이
있다(주석 77-81행). 둘 다 "고칠지 말지·어떻게 고칠지"에 선택지가 여럿이라 분기점으로 문서화한다.

이 문서는 **1박스·N프로세스** 스코프다. `ai-sticky-routing.md`는 **여러 박스**로 수평확장할 때의
스티키 라우팅을 다루며, 그 §8 ㉰(장애 재배치)는 아직 미결정으로 열려 있다 — 이 문서가 그 결정을
대신하지 않는다. 다만 아래에서 드러나는 것처럼 두 스코프가 **같은 메커니즘(ReattachAnalysis)을
재사용할 여지**가 있어, 여기서 나온 답이 그쪽 결정에 참고가 될 수 있다.

## 2. 현재 보유 자원·제약 (실측·코드 근거)

### 2-1. 문제 ① 장애 재배치 없음 — 그런데 복구 경로는 이미 있다

- `session_state.py:1-6`: AI 세션 상태는 **프로세스 로컬 in-memory**(reference 각도 시퀀스, 누적
  프레임, rep 카운터). `StartAnalysis`에서 생성, `StopAnalysis`/`CompleteAnalysis` 직후 제거된다.
  프로세스가 죽으면 이 상태는 100% 소실된다.
- **그런데 이미 이 소실을 복구하는 RPC가 있다** — `ReattachRequest`(exercise.proto:89-99):
  `reference_poses`, `persona`, `initial_rep_count`, `elapsed_sec`를 **Spring이 DB에서 읽어 채워
  보낸다.** 주석: "AI는 기준 좌표를 보관하지 않는다." 즉 **AI 프로세스 쪽 상태는 Spring이 가진
  정보만으로 어느 프로세스에서든 재구성 가능**하다는 것이 이미 설계돼 있다.
- 지금 `ReattachAnalysis`는 **클라이언트 재연결**(앱이 백그라운드에서 돌아오는 등) 용도로만
  호출된다 — "채널이 가리키던 프로세스가 죽었을 때"의 장애 감지·전환 트리거로는 안 쓰인다.
- gRPC 호출 실패는 `withDeadlineAfter` 타임아웃과 Resilience4j `CircuitBreaker`
  (`aiCircuitBreaker()`)로 감지는 되지만, 실패 후 "다른 채널로 재시도"하는 로직은 없다 —
  서킷브레이커는 장애를 감지·격리할 뿐 재배치하지 않는다.

### 2-2. 문제 ② 풀 크기·포트 매핑 하드코딩

- `AI_CHANNEL_POOL_SIZE = 3`(Java 상수)과 AI 서버 포트 배정(8585/8586/8587, `entrypoint.sh`)이
  서로 다른 파일·다른 언어에서 손으로 맞춰야 하는 두 값이다.
- 채널 인덱스 `i`가 반드시 `basePort + i`와 짝을 맞춰야 하는데, 처음 구현 시 이게 어긋나
  세션 6개가 전부 프로세스 0으로 몰린 버그가 실제로 났다(`ExerciseAnalysisService.java` 77-81행
  주석). 지금은 고쳐졌지만, 프로세스 수를 바꾸는 다음 변경에서 같은 클래스의 실수가 재발할 수 있는
  구조는 그대로다.

### 2-3. 스케일 — 지금 안 급한 이유

- 현재 정본 목표(DAU 1,000·피크 동시 67세션)에서 이 갭들은 **아직 한 번도 실제 장애로 터진 적
  없다.** 포트 매핑 버그는 배포 전 개발 중 잡혔다.

### 2-4. 🔴 실측(2026-08-26, 로컬): "재배치"의 전제 자체가 틀렸다

`loadtest/measure_ai_worker_kill_recovery.sh`로 워커 1개(포트 8001)만 SIGKILL — 결과가
§3-1 ㄴ안의 설계 전제를 뒤집는다.

- `docker inspect`로 확인: `RestartCount: 0 → 1`, `StartedAt`이 kill 직후로 찍힘 —
  **워커 1개만 죽여도 컨테이너 전체(워커 3개 다)가 같이 재기동된다.** entrypoint.sh의
  `wait -n; exit $?`(의도적 설계, "일부만 살아있는 상태를 정상으로 보이게 두지 않기 위해")가
  실제로 그렇게 동작하는 것을 코드 추론이 아니라 실측으로 확인.
- 다운타임(kill → nginx `/health` 200 재확인): **7회 측정, 평균 25.3초(표준편차 5.4초,
  범위 17.3~35.3초)** — 워커 0/1/2를 번갈아 죽여도(각 2~3회씩) 전부 컨테이너 전체 재기동으로
  이어졌다. 그 동안 nginx는 워커 인덱스와 무관하게 계속 502 — **3개 세션 몫이 아니라 그
  컨테이너의 모든 세션이 같이 끊긴다.**
  ⚠️ **첫 1회(고립 실행, 17.3초)가 최솟값이고, 이어붙인 6회(10초 간격 연속 실행,
  23.4~35.3초)는 더 느리고 편차도 컸다** — 연속 재기동이 시스템에 부하를 남겨 후속 측정을
  오염시켰을 가능성이 있다(교란 변수, [[feedback_measure_design_needs_repeats]]). 즉 25.3초는
  "연속 장애" 조건의 평균이지 "고립된 단발 장애"의 평균이 아닐 수 있다 — 실서비스에서
  장애가 연속으로 안 겹친다면 17초 쪽이 더 대표값에 가까울 수 있다. 이 구분을 가르려면
  판 사이 대기 시간을 늘려 재측정해야 한다(미실행).
- **결론: ㄴ안("다른 살아있는 채널로 재배치")은 성립하지 않는다.** 재배치할 살아있는
  형제 채널이 없다 — 하나가 죽으면 셋 다 죽어 있는 17~35초 창이 생길 뿐이다. 진짜 물어야 할
  질문은 "어느 채널로 옮길까"가 아니라 **"이 창이 끝난 뒤, 끊겼던 세션들이
  `ReattachAnalysis`로 자동 복구되는가, 아니면 IN_PROGRESS에 갇힌 채 방치되는가"**다.

## 3. 선택지

### 3-1. 문제 ① 장애 재배치

🔴 **§2-4 실측으로 ㄴ안의 원래 표현("다른 살아있는 채널로")은 폐기 — 재배치할 살아있는 채널이
없다는 게 확인됐다.** 아래는 그 실측을 반영해 다시 쓴 선택지다 — 셋 다 "~17초 창이 끝난 뒤
무엇을 하는가"를 다룬다.

| # | 선택지 | 한 줄 |
|---|---|---|
| ㄱ | **현상 유지** | 컨테이너가 재기동돼도 세션은 그냥 끊긴 채로 둔다(사용자가 앱을 다시 열어야 복구) |
| ㄴ | **재기동 후 ReattachAnalysis 자동 호출** | Spring이 gRPC 호출 실패(`UNAVAILABLE`)를 감지하면, ~17초 뒤 컨테이너가 healthy로 돌아왔을 때 같은 채널로 `ReattachAnalysis`를 자동 재호출해 상태 복구 — "다른 채널로"가 아니라 "같은 채널이 살아나면" |
| ㄷ | **프론트가 재연결 로직으로 흡수** | Spring/AI는 안 건드리고, 프론트가 기존에도 앱 재개(포그라운드 복귀) 시 `ReattachAnalysis`를 부르던 경로를 gRPC 에러 발생 시에도 타도록 확장 |

### 3-2. 문제 ② 풀 크기·포트 매핑

| # | 선택지 | 한 줄 |
|---|---|---|
| A | **환경변수 단일 소스** | `AI_PROCESS_COUNT` 같은 값을 배포 스크립트/컴포즈 파일 한 곳에서 정의해 Java(`application.yml` 인터폴레이션)와 `entrypoint.sh` 양쪽이 같은 값을 읽게 함 |
| B | **동적 디스커버리** | Spring이 시작 시 고정 포트 범위를 순회하며 헬스체크로 살아있는 AI 프로세스를 찾아 채널 풀을 자동 구성 |
| C | **정합성 검증만 추가** | 하드코딩·이원 관리는 그대로 두되, 배포 스크립트에 Java 상수와 실제 포트 배정을 diff하는 검증 스텝을 추가해 사람 실수를 배포 전에 잡음 |

## 4. 트레이드오프 표

### 4-1. 문제 ①

| 선택지 | 장점 | 단점 | 리스크 | 구현 비용 |
|---|---|---|---|---|
| ㄱ 현상 유지 | 코드 변경 0 | 컨테이너 재기동 ~17초 동안 **그 컨테이너의 모든 세션**이 끊기고, 그 뒤로도 사용자가 직접 앱을 재개해야만 복구(프론트가 이미 그 경로로 Reattach를 부르므로 자동 복구는 안 됨) | 장애 빈도가 안 측정돼 있어 "얼마나 자주 겪는지" 모름(다운타임 자체는 §2-4로 1회 확인) | 0 |
| ㄴ 재기동 후 자동 Reattach | 새 메커니즘 발명이 아니라 **기존 RPC 재사용** — Spring이 이미 상태 재구성 재료(DB)를 갖고 있음. ~17초 뒤 자동 복구라 사용자가 앱을 다시 열 필요가 없음 | 실패 감지 후 "얼마나 기다렸다 재시도할지"(재기동 시간과 맞물림), "몇 번까지 재시도할지" 결정 필요. Spring 쪽에 재시도 상태기계를 새로 짜야 함 | 재기동이 17초보다 오래 걸리는 경우(부하·이미지 크기 등) 재시도 타임아웃을 잘못 잡으면 조기 포기 | 중간 — gRPC 클라이언트 재시도 로직 + 통합테스트 |
| ㄷ 프론트 재연결 확장 | Spring/AI 코드 변경 없음 — 프론트의 기존 재개(foreground) 경로만 넓힘 | 앱이 포그라운드에 있는 동안(방금 끊긴 걸 바로 알아야 함) gRPC 에러를 프론트까지 전달하는 경로가 지금 있는지 확인 필요 | 백그라운드 상태에서 끊기면 여전히 사용자가 앱을 열 때까지 미복구 | 낮음~중간 — 프론트 에러 핸들링 확장 |

### 4-2. 문제 ②

| 선택지 | 장점 | 단점 | 리스크 | 구현 비용 |
|---|---|---|---|---|
| A 환경변수 단일 소스 | 이원 관리를 일원화 — 값이 하나면 어긋날 여지가 사라짐 | 여전히 "값이 바뀌면 재배포·재시작 필요"라는 정적 구성 방식 | 배포 스크립트 자체를 안 건드리는 실수는 여전히 가능(그러나 최소 두 곳을 손으로 맞추는 것보다 안전) | 낮음 |
| B 동적 디스커버리 | 프로세스 수 변경 시 코드/설정 변경 없이 자동 반영 — 매핑 오류를 구조적으로 제거 | 헬스체크 폴링·재시도 로직 필요, Spring이 AI보다 먼저 뜨는 시점의 처리 필요 | 새 실패 모드(디스커버리 자체의 오작동) 추가 | 높음 |
| C 정합성 검증만 | 최소 변경으로 재발 방지 | 근본 원인(이중 관리)은 그대로 | 검증 스텝을 깜빡하고 배포 스크립트를 우회하면 무력화 | 매우 낮음 |

## 5. 추천

- **문제 ①**: §2-4 실측 이후 **아직 추천을 안 세운다.** ㄴ(재기동 후 자동 Reattach)이 여전히
  방향으로는 유력하지만, 1회 측정(다운타임 17.3초)만으로 "이게 자주 겪는 문제인지"를 판단하긴
  이르다 — 로컬 1회 kill은 재현성·부하 상태에서의 편차를 안 본다. 착수는 6번의 미결 질문에
  달려 있다.
- **문제 ②**: **A(환경변수 단일 소스)**를 추천. B는 지금 스케일(프로세스 3개 고정)에 비해
  과설계이고, C는 근본 원인을 안 없앤다. A가 비용 대비 가장 확실하게 재발을 막는다.

## 6. 미결 질문

- **실제 장애 빈도는 여전히 모른다.** §2-4는 "죽으면 무슨 일이 일어나는가"(다운타임·블라스트
  반경)에 답했을 뿐, "얼마나 자주 죽는가"에는 안 답했다 — 로컬 개발 이후 프로덕션에서 AI
  프로세스가 자발적으로(OOM 등) 죽은 사례가 실제로 있는지 확인 필요.

## 결정 로그

- 2026-08-26: **문제 ②는 A(환경변수 단일 소스)로 확정, 구현 완료.** `AI_WORKER_COUNT` 하나가
  `docker-compose.yml`의 `shadowfit-backend`(`AI_CHANNEL_POOL_SIZE`로 전달)와 `shadowfit-ai`
  양쪽 환경변수의 공통 소스가 됐다. `entrypoint.sh`는 이 값으로 워커 수·포트(base+인덱스)를
  산술 유도하고, Spring `ExerciseAnalysisService`는 `ai.channel-pool-size` 프로퍼티로 받아
  `aiChannelPoolSize` 필드에 주입한다(더 이상 상수 아님). `nginx-ai/default.conf`는 반복문이
  없는 정적 설정이라 완전 자동화 대신 **워커 0~9 자리를 미리 다 열어두는 방식**을 택했다 —
  `AI_WORKER_COUNT`가 10을 넘지 않는 한 nginx 파일은 더 이상 손댈 필요가 없다. 이 상한을
  넘기면 이 파일에 줄을 추가해야 한다는 경고 주석을 남겼다.
