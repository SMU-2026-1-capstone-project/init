## 0. 이 문서가 여는 것

`realmysql-experiments.md:105-106` 에 이 프로젝트에서 가장 많이 인용되는 수가 있다:

> payload **1,716.8 KB → 22.4 KB (−98.7%)**, warm 쿼리 **12.1ms → 1.5ms (8x, −87%)**

이건 **쿼리 레벨** 값이다. 사용자가 겪는 건 리포트 API 의 응답시간이고, 거기엔 직렬화·집계·네트워크가 얹힌다. 「쿼리에서 8배였던 게 API 에선 몇 배인가」를 답한 적이 없다.

그런데 착수 전 코드를 읽다가 **더 큰 것이 나왔다.**

### 0-1. 🔴 정상 경로에선 이 쿼리가 돌지 않는다

`ReportService.resolveDetailedAnalysis`(`ReportService.java:90-110`) 는 이 순서다:

1. `report.detailed_analysis` 가 차 있으면 **그걸 파싱해서 반환하고 끝난다**
2. 비어 있거나 구버전 형식일 때만 `poseDataRepository.findFramesBySessionId(...)` 로 **pose_data 를 스캔한다**

1번을 채우는 건 precompute-on-write(`SessionService.applyComplete`)다. 즉 **정상적으로 완료된 세션의 리포트는 pose_data 를 읽지 않는다.** projection 쿼리는 지금 **폴백 경로 전용**이다.

이게 사실이면 결론이 하나 따라온다:

> **정상 경로에서 projection 이 API 응답시간에 기여하는 몫은 0 이다.** −98.7% 를 «리포트가 빨라진 이유» 로 인용해 온 문장들은 조건이 빠져 있다.

이 문서는 그 조건을 실측으로 확정한다. **`realmysql §②(b)` 의 수를 부정하는 게 아니라 그 수가 사는 자리를 좁힌다** — «3.47배» 를 인용한 13곳에 조건을 단 커밋(`0d68b52`)과 같은 작업이다.

### 0-2. 그때 잰 프로젝션과 지금 프로젝션이 다르다

2026-06-02 측정은 **3컬럼** 시절이다. 지금 `PoseFrameProjection` 은 **4컬럼**이다:

| 컬럼 | 상태 |
|---|---|
| `timestampSec`, `syncRate` | 원래 있음 |
| `repNumber` | 이슈 #78 로 추가 |
| `smoothedKneeAngle` | §4-ㄹ 로 추가 |
| ~~`feedbackMessage`~~ | 이슈 #80 으로 **제거** |

컬럼이 바뀌었으니 −98.7% 는 **그 시점 프로젝션의 값**이다. 여전히 `joint_coordinates`(2.3KB)를 안 싣는다는 핵심은 유지되므로 배수가 크게 흔들리진 않겠지만, **«현재 값» 으로 인용해 온 것 자체가 검증된 적 없다.**

## 1. 측정으로 답할 질문

| # | 질문 | 왜 이게 질문인가 |
|---|---|---|
| Q1 | 정상(precompute) 경로에서 projection 이 응답시간에 기여하는가 | §0-1 대로면 **0** 이어야 한다. 0 임을 재는 것이 이 실험의 1차 산출물 |
| Q2 | 폴백 경로에서 projection 의 API 레벨 델타는 얼마인가 | 쿼리 8배가 API 에선 몇 배로 줄어드는가 |
| Q3 | 줄어든 몫은 어디로 갔나 | 직렬화·집계·프레임워크. «어디가 지배적인가» 가 답 |
| Q4 | precompute 자체의 API 레벨 델타는 얼마인가 | 실제로 읽기 경로를 고친 건 projection 이 아니라 이쪽일 가능성 |
| Q5 | 4컬럼 프로젝션의 payload 절감률이 여전히 −98.7% 인가 | 컬럼이 2개 늘고 1개 빠졌다 |

**Q1 이 이 실험의 급소다.** 「최적화를 했다」는 누구나 말하고, **「그 최적화가 지금 어느 경로에서만 사는지 안다」** 가 이 프로젝트 성격에 맞는 산출물이다.

## 2. 팔 설계

세 팔이 필요하다. 두 팔로는 projection 의 몫과 precompute 의 몫이 섞인다.

| 팔 | 경로 | 성격 |
|---|---|---|
| **P** | precompute 적중 (`detailed_analysis` 있음) | **현재 정상 경로.** pose_data 미조회 |
| **J** | 폴백 + projection (`detailed_analysis` 비움) | 현재 코드의 폴백 경로 |
| **F** | 폴백 + 전체 엔티티 조회 | **반사실.** projection 이 없었다면의 세계 |

- **J vs F** = projection 의 API 레벨 기여 (Q2)
- **P vs J** = precompute 의 API 레벨 기여 (Q4)
- **P 의 존재 자체** = Q1 의 답

> ⚠️ **팔 F 는 지금 코드에 없다.** `findFramesBySessionId` 하나뿐이고 전체 엔티티를 읽는 리포트 경로는 제거됐다. 측정 전용 경로를 만들어야 하고, 그 방법은 §7 미결정이다. **프로덕션 코드에 측정용 분기를 상주시키지 않는다** — 이 실험의 산출물은 코드 변경이 아니라 판단 근거다.

팔 J·F 를 만들려면 `detailed_analysis` 를 비워야 한다. 이건 **데이터를 고치는 것**이므로 대상 세션을 따로 만들고 원본을 건드리지 않는다(§6).

## 3. 측정 지표 — 걷는 것과 보는 것을 나눈다

[[feedback_measure_design_needs_repeats]] 원칙대로, **API 를 때리는 것**과 **그 안에서 무슨 일이 일어나는지 보는 것**은 별개 장치다. 이게 없으면 Q3(«줄어든 몫이 어디로 갔나»)를 아예 못 답한다.

### 3-1. 거는 쪽 — HTTP

- 리포트 API 응답시간 p50/p99, 요청당 응답 바이트
- ⚠️ **읽기 부하 장치가 없다.** `loadtest/ghz/` 는 gRPC **쓰기**용이다. HTTP 읽기 측정 장치는 새로 만들어야 하고, 무엇으로 만들지는 §7 미결정

### 3-2. 보는 쪽 — 계층 분해

Q3 는 이게 없으면 답이 안 나온다. 요청 하나를 층으로 쪼갠다.

| 층 | 측정 방법 |
|---|---|
| DB 쿼리 자체 | `SET profiling=1` / `SHOW PROFILES` — wall-clock 오염 회피(§5) |
| DB→앱 전송 바이트 | `Bytes_sent` 세션 변수 델타 |
| 앱 내부(집계·직렬화) | API 총시간 − DB 쿼리 시간 |

세 번째는 뺄셈이라 정밀하지 않다. **정밀한 분해가 필요하면 프로파일러가 필요하고, 그건 이번 범위 밖이다** — 이번엔 «지배적인 층이 어디인가» 까지만 본다.

### 3-3. 곁다리

- `EXPLAIN` — 팔 J·F 의 실행계획이 컬럼 수 말고 다른 데서 갈리지 않는지 확인
- 버퍼풀 카운터 — 워밍업이 실제로 됐는지 확인용(§5)

## 4. 반복 설계

팔이 3개라 **라틴 방격이 성립한다** — 온라인 DDL 실험(팔 2개, 위치 상쇄 배열로 대체)보다 조건이 좋다.

| 단 | 내용 |
|---|---|
| 버림 | **팔당 1판.** 팔 하나만 버리면 다른 팔의 첫 판이 여전히 «첫 판» 이다 |
| 본 측정 | 팔당 3판, 라운드마다 순서 회전 (P→J→F, J→F→P, F→P→J) |

DDL 실험과 달리 **판마다 재시딩이 필요 없다** — 읽기는 상태를 안 바꾼다. 그래서 반복이 싸고, 판 수를 늘리는 게 실제로 가능하다.

## 5. 환경과 알려진 오염원

[[project_loadtest_env_constraint]] 대로 이 머신의 절대치는 무의미하다. 이번에 **특히** 위험한 오염원이 둘 있다.

**ⓐ 워밍업.** 같은 쿼리가 cold 721ms → warm 12ms 였다(`realmysql §②(b)` 캐비엇). **60배다.** 워밍업을 통제 못 하면 팔 간 차이가 통째로 묻힌다. 판마다 동일한 워밍업 절차를 밟고, 그 절차를 rig 에 박는다.

**ⓑ wall-clock 오염.** projection 실험 **첫 시도가 이 함정에 빠져 2x 로 나왔고**, `SET profiling` 으로 재측정해 진짜 배수를 찾은 전례가 있다(`realmysql §0`). 이번엔 API 레벨이라 응답시간이 ms 단위 이상이므로 HTTP 측정엔 덜 치명적이지만, **§3-2 의 DB 층 측정엔 그대로 해당한다.**

절대 시간을 «운영에서 N ms» 로 인용 금지. **팔 간 상대 배수까지만.**

## 6. 가설과 반증 조건

| # | 가설 | **무엇이 나오면 틀린 것인가** |
|---|---|---|
| H1 | 팔 P 는 pose_data 를 조회하지 않는다 | 팔 P 에서도 `findFramesBySessionId` 가 실행됨 (= precompute 가 안 먹고 있다) |
| H2 | 팔 J < 팔 F (projection 이 API 에서도 이긴다) | 차이가 없음 |
| H3 | API 레벨 배수 < 쿼리 레벨 8배 | 같거나 더 큼 |
| H4 | 팔 P 가 셋 중 가장 빠르다 | J 나 F 가 더 빠름 |
| H5 | 4컬럼 프로젝션의 payload 절감률 ≈ −98.7% | 유의하게 다름 |

**H1 이 반증되면 이 문서의 §0-1 전제가 무너진다** — 그 경우 결과는 «조건을 좁혔다» 가 아니라 **«precompute 가 기대대로 안 걸리고 있다»** 는 결함 발견이 되고, 그건 문서가 아니라 이슈로 가야 한다([[feedback_troubleshooting_to_issues]]).

**H3 이 반증되면**(API 배수가 쿼리 배수보다 크면) 그건 측정 오류를 먼저 의심할 신호다. 하위 층의 개선이 상위 층에서 증폭될 구조적 이유가 없다.

> 임계값은 적지 않는다. 「API 델타 N% 이상이면 유의미」 같은 기준은 지금 근거가 없다([[feedback_no_arbitrary_threshold_values]]). **값을 관측해서 적는 것까지가 범위**다.

## 7. 알려진 함정 체크리스트 (착수 전 확인)

- [ ] 🔴 **합성 rig 로는 현재 프로젝션 쿼리를 못 돌린다** — `seed_pose_scale.sh:15-16` 이 자기 헤더에 경고해 뒀다: `rep_number` 없음, `smoothed_knee_angle` 없음. **프로젝션이 읽는 4컬럼 중 2개가 합성 테이블에 없다**(이슈 #153). 대상 테이블 선택이 §8 미결정 1번인 이유
- [ ] **다운샘플 R≈5 로 세션당 행 수가 변했다** — 원 측정은 «세션 750행» 조건(2026-06-02)이고, 그 뒤 PR #53 이 대표추출을 넣었다. 같은 조건이 아니다
- [ ] **팔 F 용 경로를 프로덕션에 남기지 말 것** — §2 주의
- [ ] **`detailed_analysis` 를 비우는 건 데이터 변경이다** — 전용 세션을 만들고 실 데이터를 건드리지 않는다
- [ ] **구버전 형식 폴백에 걸리지 않게** — `ReportService.java:96-99` 는 파싱은 되지만 필드가 빈 경우도 재계산으로 흘린다. 팔 P 가 의도치 않게 폴백으로 새면 P 와 J 가 같은 걸 재게 된다. **팔 P 에서 폴백 경고 로그가 안 찍히는지 판마다 확인**
- [ ] **워밍업 절차를 rig 에 박을 것** — §5-ⓐ
- [ ] **응답 DTO 크기는 projection 과 무관하다** — −98.7% 는 **DB→앱** payload 지 **앱→클라이언트** 가 아니다. API 응답 바이트가 안 변하는 건 정상이며, 그걸 «효과 없음» 으로 읽지 말 것

## 8. 의식적으로 안 할 것

| 안 함 | 이유 |
|---|---|
| projection 을 걷어내기 | 폴백 경로에선 여전히 유효하다. 이 실험은 **조건을 적는 것**이지 되돌리는 게 아니다 |
| 읽기 전용 replica 도입 | 2026-08-10 판정: 읽기가 쓰기를 방해한다는 증거 0건, read-your-writes 정면 충돌. 그리고 **복제는 처리량 장치지 단일 쿼리 지연 장치가 아니다** — 이 실험 결과가 나빠도 답이 아니다 |
| 앱 내부 정밀 프로파일링 | 프로파일러 도입이 필요. 이번엔 «지배적 층» 까지만(§3-2) |
| 「응답 N ms 이하」 목표 세우기 | 근거 없는 임계값 |
| 값 분포 의존 실험 | 합성 rig 카디널리티 균일 한계([[project_synthetic_data_distribution_limit]]) |

## 9. 미결정 (사용자 confirm 필요)

- [ ] **대상 테이블** — ⓐ 실 `pose_data`(컬럼 일치, 볼륨 작음, 파티션 걸려 있음) ⓑ 합성 `pose_data_scale`(볼륨 큼, **컬럼 2개 없어서 시더 수정 선행**). ⓐ 는 조건이 맞지만 «대용량에서의 값» 이 아니고, ⓑ 는 반대다. **둘 다 하는 것도 선택지**이고 그 경우 ⓐ 를 본 측정, ⓑ 를 스케일 확인으로 둔다
- [ ] **팔 F 를 어떻게 만들지** — 테스트 전용 리포지터리 메서드 / Spring 프로파일 분기 / rig 에서 raw SQL 로 대체. 마지막 안은 API 레벨이 아니게 되므로 Q2 를 못 답한다
- [ ] **HTTP 부하 장치** — 단건 반복(curl/스크립트)이면 p99 를 못 만들고, 동시 부하면 도구 신규 도입(k6 등)이다. **Q1~Q4 는 단건 반복으로도 답이 되므로** 동시 부하가 꼭 필요한지부터 판단할 것
- [ ] **결과를 어디에 박을지** — `realmysql-experiments.md §②(b)` 카드에 조건을 다는 형태 vs `loadtest/results/projection-e2e-<날짜>/` 에 rig 와 함께. 후자가 최근 관례이고, §②(b) 에는 포인터만 다는 게 드리프트가 적다
- [ ] **온라인 DDL 스윕이 끝난 뒤로 미룰지** — 지금 같은 머신에서 8판이 돌고 있다. 병행하면 두 측정이 서로를 오염시킨다. **이 실험은 스윕 종료 후 착수가 맞다**
