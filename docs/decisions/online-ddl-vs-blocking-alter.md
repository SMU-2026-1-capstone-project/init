## 0. 이 문서가 여는 것

`realmysql-experiments.md:140` 에 **답이 반쯤 적힌 채 실행되지 않은 문장**이 있다:

> `ALTER TABLE ... PARTITION BY RANGE(...)` = **5,767초(96분)** copy-to-tmp 풀 리빌드. → 운영이면 처음부터 파티션 테이블 or **`pt-osc`/`INPLACE` 무중단**

앞의 96분은 실측이고, 뒤의 「무중단」은 **권고**다. 이 문서는 뒷문장을 실측으로 바꾼다.

착수 근거가 되는 사실 두 개:

1. **아픔이 이미 있다** — 96분 동안 테이블이 잠긴 실측 기록. 실험의 before 를 새로 만들 필요가 없다.
2. **완전한 공백은 아니다** — `mysql/migrations/2026-08-07-consolidate-session-member-indexes.sql:99` 에 `ALGORITHM=INPLACE, LOCK=NONE` 실사용이 있고, 같은 파일 56~58줄엔 «인덱스 DDL 은 INSTANT 가 아니다» 는 판단까지 적혀 있다. 즉 갭은 *「온라인 DDL 을 모른다」가 아니라 「제일 아팠던 DDL 에 그걸 안 써봤다」* 다.

## 1. 측정으로 답할 질문

| # | 질문 | 왜 이게 질문인가 |
|---|---|---|
| Q1 | 그 96분 동안 **정말 쓰기가 막혔나** | 지금은 "테이블 락"이라고 적혀 있을 뿐 차단 구간을 잰 적이 없다 |
| Q2 | `pt-osc` 로 같은 DDL 을 걸면 **얼마나 더 걸리나** | 무중단은 공짜가 아니다. 그 대가의 크기가 값 |
| Q3 | `pt-osc` 의 「무중단」은 **진짜 0초 차단인가** | 컷오버 `RENAME` 순간엔 락이 있다. 0 이 아닌 그 값이 핵심 산출물 |
| Q4 | 진행 중 **일반 DML 이 느려지나** | 트리거 오버헤드. "무중단이지만 느려짐"은 다른 종류의 비용 |
| Q5 | **디스크가 얼마나 더 필요한가** | 복사 방식은 원본+사본. 운영에서 이것 때문에 못 쓰는 경우가 실재 |

Q3 가 이 실험의 급소다. 「무중단 도구를 써봤다」는 누구나 말할 수 있고, **「무중단이라 부르는 것의 실제 차단 시간을 쟀다」** 가 이 프로젝트 성격에 맞는 산출물이다.

## 2. 팔 설계

대상 DDL 은 **96분 baseline 과 같은 문장이어야** 비교가 성립한다 (`measure_partition.sh:16-33` 의 `PARTITION_DDL` 그대로).

### 사전 확인 (측정 아님, 1분)

**D0. `ALTER ... PARTITION BY ..., ALGORITHM=INPLACE, LOCK=NONE`**

먼저 이걸 던져본다. **실패가 예상되는 시도**이고, 실패 자체가 실험의 전제를 세운다 — MySQL 이 이 DDL 을 INPLACE 로 못 한다고 거절해야 "그래서 외부 도구가 필요하다"가 성립한다. 만약 **성공하면 이 실험의 절반이 무의미해진다**(도구 없이 무중단 가능). 그 경우 팔 B·C 는 «필요 없는 도구» 를 재는 셈이 되므로 설계를 재검토한다.

> 이 한 줄을 먼저 던지지 않고 도구부터 붙이면, 나중에 "그냥 INPLACE 로 됐는데?" 한 마디에 실험 전체가 무너진다.

### 본 측정

| 팔 | 방식 | 성격 |
|---|---|---|
| **A** | `ALTER TABLE ... PARTITION BY` (그대로) | baseline. 96분의 재현 + 차단 구간 실측 |
| **B** | `pt-online-schema-change` | 트리거 기반. 원본에 INSERT/UPDATE/DELETE 트리거 3개를 걸고 청크 복사 |
| **C** | `gh-ost` | binlog 기반. 트리거 없음 대신 row-based binlog 를 읽어 따라잡음 |

**팔 C 는 실행 가능 여부부터 미검증이다.** `gh-ost` 가 `PARTITION BY` 를 alter 로 받는지, 파티션 테이블 자체에 제약이 있는지 확인하지 않았다. 못 쓰는 것으로 밝혀지면 **그것이 결과**다 — 「도구마다 적용 범위가 다르고, 이 DDL 엔 pt-osc 만 됐다」는 판정도 산출물이다. 억지로 넣어서 팔 수를 채우지 않는다.

## 3. 측정 지표 — 걷는 것과 보는 것을 나눈다

[[feedback_measure_design_needs_repeats]] 원칙대로, **DDL 을 거는 것**과 **그동안을 관측하는 것**은 별개 장치다. 관측 장치가 없으면 팔 B·C 는 그냥 "오래 걸렸다"로만 남는다.

### 3-1. 거는 쪽

- DDL wall-clock (초). 분 단위라 `date` 오버헤드는 무시 가능 — projection 실험에서 sub-100ms 를 오염시켰던 그 함정([`realmysql §4-②(b)`](../portfolio/realmysql-experiments.md))은 여기선 해당 없다.

### 3-2. 보는 쪽 — 백그라운드 writer

DDL 이 도는 동안 **별도 세션이 `pose_data_scale` 에 계속 쓴다.** 이게 없으면 Q1·Q3·Q4 를 아예 못 잰다.

- 초당 1회 이상 단건 INSERT, 각 시도의 **시각·성공여부·소요 ms** 를 기록
- 산출: ① **최대 연속 실패/정지 구간**(=실질 차단 시간) ② 진행 중 DML latency 분포 ③ 총 성공 건수
- ⚠️ writer 자체가 ms 단위를 재므로 **여기선 왕복 오버헤드가 오염원이다.** `docker exec` 왕복으로 재지 말고 컨테이너 안에서 도는 루프로 찍을 것

### 3-3. 곁다리 지표

| 지표 | 출처 | 왜 |
|---|---|---|
| 디스크 피크 | `pose_data_scale*.ibd` + `#sql-*` 파일 크기 | Q5. `measure_partition.sh:58` 의 `IBD()` 재사용 |
| binlog 증가량 | `SHOW BINARY LOGS` 전후 델타 | 청크 복사가 binlog 를 탄다 → **복제 지연의 원인**. 3순위 복제 실험의 예고편 |
| 락 실물 | `performance_schema.data_locks` / `metadata_locks` | 컷오버 순간에 무엇이 잡히는지. §0 백본과 같은 방식 |

binlog 델타는 지금 안 봐도 되는 지표처럼 보이지만, **복제 실험에 그대로 물린다.** 걷어두고 안 본 지표를 나중에 붙였더니 증명 하나·반증 하나가 나온 전례가 있다(`commit-count-and-mysql-metrics.md`).

## 4. 반복 설계 — 「팔당 1판」을 피하는 법

1억 행에서 팔당 1판씩 돌리면 **팔의 효과와 판 순서가 분리되지 않는다.** 그런데 1억 행 1판이 90분 이상이고, 판마다 테이블을 원상복구(=재시딩 ~16분)해야 해서 반복이 현실적으로 불가능하다.

→ **2단으로 쪼갠다.**

| 단 | 규모 | 판 수 | 성격 |
|---|---|---|---|
| **1단 (본 측정)** | 1,000만 행 (~1.1GB 예상) | 팔당 3판 + **버림판 1** | 통계가 서는 곳. 라틴 방격으로 순서 배치 |
| **2단 (확인)** | 1억 행 | 팔당 1판 | 축소 규모의 결론이 스케일에서도 유지되는지 **확인만**. 반복 없으므로 «측정» 이라 부르지 않는다 |

- **버림판**: 첫 판은 버린다. 페이지 캐시·버퍼풀 상태가 판마다 다르고, 첫 판이 그걸 가장 크게 탄다.
- **라틴 방격**: A→B→C, B→C→A, C→A→B 로 라운드를 돌려 판 순서 효과를 팔에서 분리한다.
- **초기화**: 판마다 `DROP TABLE` 후 재시딩. 파티션이 걸린 테이블에 같은 DDL 을 다시 걸 수 없고, 앞 판이 남긴 파일 상태가 다음 판을 오염시킨다.
- 2단은 축소 규모의 배수가 스케일에서 유지되는지만 본다. 1억 행 재검증을 **일부러 축소 서브셋으로 대체한 전례**가 이미 있다([`realmysql §4-②(d)` AWS 재검증](../portfolio/realmysql-experiments.md)) — 같은 판단이다.

## 5. 환경 — 왜 이번엔 로컬이어도 되나

[[project_loadtest_env_constraint]] 는 «i3-6100 동거 환경에선 절대치 무의미» 다. 그런데 이 실험은 **RPS 천장이 아니라 DDL 소요와 차단 여부**를 잰다.

- 로컬로 가는 근거: ① 1차 산출물인 **「차단되나/안 되나」는 이진 사실**이라 하드웨어 독립이다 ② 같은 머신 안의 **팔 간 상대 배수**는 유효하다 ③ **비교 대상인 96분 baseline 자체가 로컬 실측**이라(`realmysql:103` "로컬 실측 ~85분", `:140` 5,767초) 조건이 맞는다
- 그 대가로 못 쓰는 것: **절대 소요 시간을 「운영에서 N분 걸린다」로 인용 금지.** "이 하드웨어에서 A 대비 B 가 몇 배" 까지만
- ⚠️ **알려진 편향 하나를 미리 박아둔다**: 2물리코어에서 writer 를 동시에 돌리면 CPU 경합이 생기고, **트리거·청크 복사로 CPU 를 더 쓰는 팔 B 가 구조적으로 불리하게 나온다.** 팔 B 가 느리게 나와도 그 일부는 환경 탓이며, 이 편향의 크기는 이번 설계로 분리할 수 없다

AWS 로 올릴지는 §9 미결정.

## 6. 가설과 반증 조건

가설만 적고 반증 조건을 안 적으면 나중에 결과를 가설에 맞춰 읽게 된다.

| # | 가설 | **무엇이 나오면 틀린 것인가** |
|---|---|---|
| H1 | 팔 A 는 DDL 전 구간 쓰기 차단 | writer 성공률이 0 으로 안 떨어짐 (= 부분 차단이거나 안 막힘) |
| H2 | 팔 B 총 소요 > 팔 A | 팔 B 가 더 짧게 끝남 |
| H3 | 팔 B 의 차단은 컷오버 순간에 국한 | 진행 중에도 긴 정지 구간이 관측됨 |
| H4 | 팔 B 진행 중 DML latency 상승 (트리거) | 평상시와 차이 없음 |
| H5 | 팔 B 디스크 피크 ≈ 원본 2배 | 그보다 훨씬 작거나 큼 |

**H1 이 반증되면 이 실험의 전제가 무너진다** — 96분 동안 안 막혔다면 고칠 아픔이 없다. 그 경우 결과는 「무중단 도구를 붙였다」가 아니라 **「96분을 아픔이라 부른 게 틀렸다」** 는 정정이 되고, 그것도 정직한 산출물이다.

> 임계값은 적지 않는다. "차단 N초 이하면 무중단으로 인정" 같은 기준은 지금 근거가 없다([[feedback_no_arbitrary_threshold_values]]). 이번엔 **값을 관측해서 적는 것**까지가 범위이고, 합격선을 정하는 건 그 다음 일이다.

## 7. 알려진 함정 체크리스트 (착수 전 확인)

- [ ] 🔴 **시더 정의가 실 테이블과 어긋나 있다** — `seed_pose_scale.sh:9-27` 헤더 경고(#153). `is_correct` 있음/`rep_number`·`smoothed_knee_angle` 없음. DDL 비용 실험이라 결론은 안 바뀌지만, **행 크기가 다르므로 「현재 `pose_data` 의 값」으로 인용 금지**. 이 경고를 결과 문서에 그대로 승계할 것
- [ ] **디스크 여유** — 팔 B·C 는 사본을 만든다. 1억 행 ~11GB → 최소 22GB 여유. 1단(1,000만 행)에선 문제없으나 2단에서 걸릴 수 있음
- [ ] **원본에 트리거 없어야 함** — pt-osc 는 트리거를 새로 건다. 기존 트리거가 있으면 실패
- [ ] **binlog 형식** — gh-ost 는 row-based 필요. `mysql:8.0` 기본값이 ROW 이지만 `docker-compose.yml:33` command 에 binlog 관련 지정이 없으므로 **실제 값을 확인**할 것 (`SHOW VARIABLES LIKE 'binlog_format'`)
- [ ] **percona-toolkit / gh-ost 설치 위치** — 컨테이너 안에 없다. 호스트에 설치할지 별도 컨테이너로 붙일지 결정 필요
- [ ] **PK 가 복합** — `PRIMARY KEY (id, created_at)`(`seed_pose_scale.sh:45`). pt-osc 의 청크 인덱스 선택이 단일 PK 전제와 다를 수 있음
- [ ] **실 `pose_data` 는 대상이 아니다** — 이미 파티션이 걸려 있고(`PoseDataPartitionScheduler`) 같은 DDL 을 다시 걸 수 없다. 대상은 `pose_data_scale` 전용
- [ ] **writer 를 컨테이너 안에서 돌릴 것** — §3-2 오염 주의

## 8. 의식적으로 안 할 것

| 안 함 | 이유 |
|---|---|
| real-JSON 1억 행(~230GB) 대상 | 이미 같은 이유로 회피 판정됨 — "시간·비용 리스크가 커서 예측 불가"([`realmysql §4-②(d)`](../portfolio/realmysql-experiments.md) AWS 재검증). 더미 JSON 이어야 96분 baseline 과도 조건이 맞는다 |

| 도구 3종 세트 채우기 | gh-ost 가 이 DDL 에 안 되면 안 되는 대로 적는다 |
