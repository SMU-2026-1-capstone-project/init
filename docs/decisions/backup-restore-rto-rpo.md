## 0. 이 문서가 여는 것

경력기술서 §6「비어 있는 것」에 이렇게 적혀 있다:

> **백업/복구 (RTO·RPO)** — **미착수.** 배포 문서에 TODO 로 남아 있습니다

무중단 DDL 과 **정확히 같은 모양의 공백**이다. 그쪽은 96분([조건](../portfolio/realmysql-experiments.md#drop-partition-625x))이라는 아픔이 실측으로 있고 「pt-osc
쓰면 된다」가 권고로만 있었다. 이쪽은 아픔조차 없다 — **한 번도 잃어본 적이 없어서 되찾는 데
얼마나 걸리는지 모른다.**

지금 이 프로젝트가 백업에 대해 말할 수 있는 것은 「binlog 가 켜져 있다」뿐이고, 그건 사실이지
능력이 아니다. 이 문서는 그걸 **시간(RTO)과 손실 창(RPO)** 으로 바꾼다.

착수 근거 두 개:

1. **무대가 이미 있다** — 1,000만 행 시더·백그라운드 writer·정지 구간 측정 장치가
   `online-ddl-2026-08-09/_rig.sh` 에 전부 있다. 백업 실험이 필요한 것과 **같은 부품**이다
2. **부분 실측이 이미 하나 있다** — `probe_import_speed.txt` 에 「스냅샷 11s / 1,033MB,
   파일 복원 39s(3회 평균)」이 남아 있다. 시딩 대체안으로 잰 것이지만 **물리 복사 계열의
   하한선**이라 이 실험의 팔 하나가 이미 반쯤 측정돼 있다

## 1. 측정으로 답할 질문

| # | 질문 | 왜 이게 질문인가 |
|---|---|---|
| Q1 | 전부 잃었을 때 **다시 쓰기를 받기까지 몇 분**인가 | RTO 의 정의 그 자체. 지금 이 값이 없다 |
| Q2 | 논리(`mysqldump`) vs 물리 백업의 **복구 시간** 차이 | 백업은 밤에 하지만 **복구는 장애 중에 한다.** 급한 쪽은 복구다 |
| Q3 | 백업 중 **서비스가 멎는가** | `--single-transaction` 은 「잠금 없이 뜬다」고 **적혀 있을 뿐**이다. 잰 적이 없다 |
| Q4 | **PITR 이 실제로 되는가** | 「binlog 켜져 있으니 된다」는 지금 권고문이다. 사고 직전 시각으로 실제 복원해 봐야 안다 |
| Q5 | **RPO 는 얼마인가** | 마지막 백업 이후 손실 창. binlog 로 어디까지 좁혀지나 |

**Q3 와 Q4 가 급소다.**

「백업 떠봤다」는 누구나 말할 수 있다. 이 프로젝트 성격에 맞는 산출물은
**「백업이 서비스를 몇 초 멈추는지 쟀다」** 와 **「사고 직전 시각으로 실제로 되돌려 검증했다」**
다. 무중단 DDL 에서 Q3(「무중단」의 실제 차단 시간)이 급소였던 것과 같은 자리다.

## 2. 팔 설계

### 사전 확인 (측정 아님)

**D0. 지금 무엇이 켜져 있나**

```sql
SHOW VARIABLES LIKE 'log_bin';                   -- binlog 자체
SHOW VARIABLES LIKE 'binlog_format';             -- ROW 여야 PITR 이 안전하다
SHOW VARIABLES LIKE 'gtid_mode';                 -- 꺼져 있으면 PITR 절차가 포지션 기반으로 달라진다
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';-- 보존 기간 = RPO 의 상한
SHOW VARIABLES LIKE 'server_id';
```

🔴 **`log_bin` 이 꺼져 있으면 Q4·Q5 가 통째로 성립하지 않는다.** 그 경우 「PITR 불가」가
결과이고, 켜는 것은 별도 결정이다. `docker-compose.yml:33` 의 command 에 binlog 지정이
없으므로 **기본값을 실제로 확인**하는 것이 이 단계다(무중단 DDL 설계 §7 이 같은 이유로
`binlog_format` 확인을 걸어둔 것과 같은 항목).

**D1. XtraBackup 이 이 서버에 붙는가**

Percona XtraBackup 은 MySQL 마이너 버전을 따라간다. 현재 서버는 **8.0.46**(2026-08-13 로컬
확인)이고 컨테이너 안에 도구가 없다. 버전이 안 맞으면 붙지 않는다.

> **못 붙는 것으로 밝혀지면 그것이 결과다** — 「물리 백업 도구는 서버 버전에 묶인다」는
> 판정도 산출물이고, 그때 팔 B 는 MySQL Shell 병렬 덤프로 교체하거나 뺀다. 억지로 넣어서
> 팔 수를 채우지 않는다. (무중단 DDL 의 gh-ost 항목과 같은 구조)

### 본 측정

| 팔 | 방식 | 성격 |
|---|---|---|
| **A** | `mysqldump --single-transaction` | 논리. 이식성 최고, 복구는 INSERT 재생 |
| **B** | **XtraBackup** (D1 통과 시) | 물리. 페이지째 복사 + redo 적용 |
| **C** | 파일 스냅샷 (`FLUSH TABLES FOR EXPORT` + `.ibd` 복사) | 테이블 단위. **전체 백업이 아니라 하한선 참조** — 이미 부분 실측 있음 |

각 팔에서 재는 것:

| 지표 | 왜 |
|---|---|
| 백업 소요 | 밤에 도는 쪽. 덜 급하다 |
| **복구 소요** | **장애 중에 도는 쪽. 이게 RTO 다** |
| 산출물 크기 | 보관 비용 · 전송 시간 |
| **백업 중 writer 정지·지연** | Q3. `_rig.sh` 의 writer 장치를 그대로 쓴다 |
| 복구 후 검증 | 행수 + 체크섬. **「복구됐다」와 「복구가 끝났다」는 다르다** |

### PITR 시나리오 (팔이 아니라 시나리오, 팔 A·B 각각에 얹는다)

```
T0  백업을 뜬다
T1  writer 가 계속 쓴다 (각 행에 시각이 남는다)
T2  «사고» — 대량 DELETE 한 방
T3  백업 복원 + binlog 를 T2 직전까지 재생
검증  T2 직전 행이 있고, 사고 이후 상태가 아닌가
```

**여기서 재는 것은 시간만이 아니다.** 「T2 직전」을 어떻게 특정하는가 — GTID 인가 포지션인가
시각인가 — 가 실제 운영에서 사람이 막히는 지점이고, 그 절차를 밟아보는 것 자체가 산출물이다.

## 3. 무대

**새로 만들지 않는다.** 무중단 DDL rig 의 부품을 그대로 쓴다 — 그래서 싸다.

| 부품 | 출처 | 용도 |
|---|---|---|
| `seed_scale` (1,000만 행) | `_rig.sh` | 백업 대상. #197 로 `SESSIONS` 가 진짜 손잡이가 됐다 |
| `writer.sql` + `start_writer`/`stop_writer` | 같은 rig | Q3 의 정지 구간 측정 |
| `writer_summary` (정지·p50·최대간격) | 같은 rig | 같은 지표 규약 |
| 디스크 샘플러 | 같은 rig | 백업 사본이 만드는 피크 |

🔴 **복구 대상은 반드시 별도 데이터 디렉터리(또는 별도 컨테이너)다.** 원본에 덮어쓰는 복구는
실험이 아니라 사고다. 이 한 줄이 이 문서에서 제일 중요한 안전 규칙이다.

## 4. 판 설계

조건당 1판이면 **조건과 실행 순서가 원리적으로 분리되지 않는다**([[feedback_measure_design_needs_repeats]]).
무중단 DDL 스윕과 같은 규약을 쓴다:

- **버림판을 팔당 1판** — 첫 판은 페이지 캐시·버퍼풀 상태를 가장 크게 탄다
- 본판은 팔 수 × 3, 위치 합을 맞춘 배열
- 매 판 **같은 초기 상태**에서 시작한다 (시딩 또는 황금 원본 복원)

⚠️ 백업/복구는 **디스크 캐시에 특히 민감하다.** 복구 직후 그 파일이 페이지 캐시에 남아
다음 판의 백업이 빨라지는 오염이 있을 수 있다. 판 사이에 캐시를 어떻게 다룰지는 §9 미결정.

## 5. 로컬인가 EC2인가

**둘 다 필요하고, 나누는 기준이 있다.**

| 질문 | 어디서 | 왜 |
|---|---|---|
| Q4 「PITR 이 되는가」 | **로컬** | **이진 사실이라 하드웨어 독립.** 절차가 성립하는지는 노트북에서 답난다 |
| Q3 「백업이 서비스를 멈추는가」 | **로컬** 먼저 | 정지의 유무는 메커니즘. 크기는 EC2 |
| Q1·Q2 「몇 분인가」 | **EC2** | 백업·복구는 **디스크 성능이 지배**한다. 로컬 값을 「운영에서 N분」으로 옮기면 거짓이다 |

무중단 DDL 문서 §5 와 같은 논리다 — 되는가/안 되는가는 싸게 로컬에서, 얼마나는 EC2 에서.
**로컬에서 절차가 안 서면 EC2 에 올릴 이유가 없다.**

## 6. 가설과 반증 조건

측정 **전에** 적는다. 무엇이 나오면 내가 틀린 것인가.

| # | 가설 | 반증 조건 |
|---|---|---|
| H1 | `--single-transaction` 은 서비스를 사실상 안 멈춘다 | writer 정지 구간이 유의미하게 크면 **반증**. 특히 시작 시점의 잠금 구간을 볼 것 — 「잠금 없음」이 아니라 「잠깐 있음」이면 그 값이 산출물이다 |
| H2 | 물리 백업이 논리보다 **복구가** 빠르다 | 복구 시간이 겹치면 반증. 이 규모에선 차이가 안 날 수도 있고, **그러면 「이 규모에선 mysqldump 로 충분」이 결론**이다 |
| H3 | PITR 로 사고 직전까지 되돌릴 수 있다 | 못 되돌리면 **결함**이다 → 이슈([[feedback_troubleshooting_to_issues]]) |
| H4 | RPO 의 하한은 binlog 동기화 주기에 지배된다 | 백업 주기가 더 지배적이면 반증 |
| H5 | 복구 시간은 데이터 크기에 선형 | 안 그러면 어디서 꺾이는지가 새 질문 |

> **임계값은 적지 않는다.** 「RTO N분 이하면 합격」 같은 기준은 지금 근거가 없다
> ([[feedback_no_arbitrary_threshold_values]]). 이번 범위는 **값을 관측해서 적는 것**까지고,
> 합격선을 정하는 건 그 다음 일이다.

## 7. 알려진 함정 체크리스트 (착수 전)

- [ ] 🔴 **복구는 별도 데이터 디렉터리에** — §3 의 안전 규칙. 원본 덮어쓰기 금지
- [ ] **binlog 가 실제로 켜져 있는지** — `docker-compose.yml` command 에 지정이 없다. D0 에서 확인
- [ ] **XtraBackup 버전 ↔ 서버 8.0.46** — 컨테이너 안에 도구가 없다. 호스트/별도 컨테이너 결정 필요
- [ ] **디스크 여유** — 원본 + 백업 사본 + 복구본 = **2~3배**. 1,000만 행이면 여유롭지만 1억 행이면 걸린다
- [ ] **`mysqldump` 출력 형태** — stdout·파일·압축 중 무엇으로 재는지가 크기·시간을 바꾼다. **조건으로 고정**할 것
- [ ] **파티션 테이블 상호작용** — 실 `pose_data` 는 월별 RANGE 파티션이다. 백업/복구가 파티션 정의를 보존하는지 확인
- [ ] **writer 를 컨테이너 안에서** — 왕복 오버헤드가 정지 구간 측정을 오염시킨다(DDL rig 와 같은 이유)
- [ ] **시더 정의가 실 테이블과 어긋남**(#153) — 행 크기가 다르므로 **「현재 `pose_data` 의 값」으로 인용 금지**. 이 경고를 결과 문서에 승계
- [ ] **PITR 사고 재현이 진짜 파괴적이다** — 대상 테이블·컨테이너를 실수로 헷갈리지 않게 이름을 분리할 것

## 8. 의식적으로 안 할 것

| 안 함 | 이유 |
|---|---|
| RDS 자동 백업·스냅샷 | 매니지드는 **다른 실험**이다. 이 프로젝트는 컨테이너 MySQL 이고, 그 판단은 [`mysql-vs-postgresql.md`](./mysql-vs-postgresql.md) 의 「박스 밖으로 뺄 거냐」와 함께 다뤄야 한다 |
| 「RTO 합격선」 정하기 | 근거 없는 임계값 |
| 실 `pose_data` 에 적용 | 복구 실험은 파괴적이다. 대상은 실험용 테이블 |
| 백업 암호화·오프사이트 전송 | 별건이고 더 비싸다. 이 문서는 **되찾는 시간**만 다룬다 |
| 도구 3종 세트 채우기 | XtraBackup 이 안 붙으면 안 붙는 대로 적는다 |

## 9-1. 미결정 추천안 (2026-08-13)

§9 의 체크박스는 **확정 전까지 비워 둔다.** 이 절은 각 항목의 트레이드오프와 추천을 적을
뿐이고, 결정은 사용자가 한다([[feedback_user_decides_not_claude]]).

### 확정된 것 (2026-08-13 사용자 confirm)

| 항목 | 결정 |
|---|---|
| **규모** | **더미 JSON 1억 행**(~24GB) 본 측정 + **real-JSON 소규모(~1~2GB) 대조 1판** |

**왜 이 조합인가.** 급소로 지목된 Q3·Q4 는 규모에 안 민감하다 — Q4「PITR 이 되는가」는
이진 사실이고 Q3「멎는가」는 잠금 메커니즘이다. 규모에 민감한 것은 Q1·Q2 인데, Q1 은 GB
선형이라 외삽이 가능하다(풀스캔이 412만→1억 행에서 선형임을 이미 확인했다).

🔴 **문제는 Q2 다.** `mysqldump` 는 행을 SELECT 해서 뽑으므로 **off-page 저장을 탄다.**
더미 JSON(~115B)은 인라인이고 real-JSON(~2.3KB)은 overflow 페이지로 나간다. 즉 **더미로만
재면 논리 백업의 불리함이 실제보다 작게 나온다** — 인덱스 실험이 더미에서 660배, real-JSON
에서 9,000배로 **과소평가됐던 것과 같은 함정**이다([조건](../portfolio/realmysql-experiments.md#index-9000x) · [`one-pager.md`](../portfolio/one-pager.md) ①표).
그래서 real-JSON 축소 대조 1판으로 그 위험만 닫는다. ②(d) 가 1억 행 대신 52.5만 행
real-JSON 으로 축소 재현했던 수법과 같다.

⚠️ **real-JSON 도 값 분포는 균일하다**(`_pose_template` 단일 템플릿 복제). 크기만 현실적일
뿐이므로 분포 의존 결론은 여기서도 못 낸다([[project_synthetic_data_distribution_limit]]).

### ① 팔 B — XtraBackup vs MySQL Shell 병렬 덤프

| | XtraBackup | MySQL Shell 병렬 덤프 |
|---|---|---|
| 성격 | **물리** (페이지째 복사 + redo 적용) | **논리** (병렬 SELECT/INSERT) |
| 서버 버전 결합 | 🔴 강함 — 마이너 버전을 따라간다 | 느슨함 |
| 설치 | 컨테이너에 없음, 별도 필요 | 컨테이너에 없음, 별도 필요 |
| **Q2 에 답하나** | ✅ **답한다** | 🔴 **답하지 못한다** |

**추천: XtraBackup 우선. D1 실패 시 MySQL Shell 로 교체하되 «Q2 미답» 을 박제한다.**

핵심은 **팔 A(`mysqldump`)가 이미 논리**라는 점이다. 팔 B 를 MySQL Shell 로 바꾸면
**논리 ↔ 논리(병렬)** 대조가 되어 §1 의 Q2「논리 vs 물리 복구 시간 차이」가 **질문 자체로
성립하지 않는다.** 대체 자체는 괜찮지만, 그때 답이 바뀐 사실을 숨기면 안 된다 — 「물리 백업
도구는 서버 버전에 묶여 이 서버엔 못 붙였다」가 §2 가 말한 대로 **그 자체로 산출물**이다.

⚠️ **MySQL Shell 을 팔 D 로 «추가» 하는 안은 추천하지 않는다.** 논리 백업 안의 직렬↔병렬
대조는 그 자체로 흥미롭지만 팔이 늘면 판 수가 늘고, §8 이 「도구 3종 세트 채우기」를 안
하기로 이미 정했다.

### ② 팔 C(파일 스냅샷) 포함 여부

**추천: 포함한다. 단 «RTO 표에 나란히» 가 아니라 «Q3 의 대조군» 으로.**

`FLUSH TABLES FOR EXPORT` 는 **테이블을 명시적으로 잠근다.** 그래서 값이 두 겹이다:

1. **하한선 참조** — 파일 복사가 이론상 제일 빠른 경로다(설계 §2 가 말한 용도)
2. ⭐ **계측의 양성 대조군** — H1 은 「`--single-transaction` 은 사실상 안 멈춘다」인데,
   **안 멈춘다는 관측은 「계측이 정지를 못 잡은 것」과 구분되지 않는다.** 명백히 잠그는 팔이
   같은 rig 에 있으면 「이 계측은 정지를 실제로 잡는다」가 증명된다. 무중단 DDL 에서 팔 A 가
   69초 정지를 잡아낸 덕에 팔 B 의 30~364ms 를 믿을 수 있었던 것과 같은 구조다.

🔴 **전체 백업이 아니므로 A·B 와 같은 표에 놓지 않는다.** 별도 절로 분리하고 「테이블 단위
하한선」이라고 명시한다. 판 수도 버림 없이 1판이면 충분하다(빠르고, 재는 것이 시간이 아니라
잠금의 유무다).

### ③ 판 사이 캐시 처리

| 안 | 비우는 것 | 문제 |
|---|---|---|
| 그대로 | — | 🔴 복구본이 페이지 캐시에 남아 **다음 판 백업이 빨라진다**(§4 가 경고한 그것) |
| `drop_caches` | OS 페이지 캐시 | InnoDB 버퍼풀은 그대로 남는다 — 절반만 통제 |
| **컨테이너 재시작 + `drop_caches`** | 버퍼풀 + OS 캐시 | 판당 ~30초 추가 |

**추천: 컨테이너 재시작 + `drop_caches` 둘 다.**

§4 가 이미 「매 판 **같은 초기 상태**에서 시작한다」를 규약으로 정했고, 같은 절에서 백업/복구가
「디스크 캐시에 **특히** 민감」하다고 스스로 경고했다. 절반만 비우는 것은 그 경고를 무시하는
것이다. 비용은 8판 기준 **약 4분**이라 무시할 만하다.

⭐ **그리고 이 통제가 실제로 먹었는지는 버림판이 말해준다** — 버림판과 본판 1 의 값이 크게
다르면 캐시 통제가 안 된 것이다. 버림판을 「그냥 버리는 판」이 아니라 **통제의 검증 장치**로
쓴다.

⚠️ `drop_caches` 는 호스트 권한이 필요하다. 러너가 root 로 도니 EC2 에선 되지만, **로컬
Windows/Docker Desktop 에선 안 된다** — 로컬 단계에선 컨테이너 재시작만으로 가고, 그 차이를
조건에 적는다.
