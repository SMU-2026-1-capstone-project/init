## 0. 이 문서가 여는 것

2026-08-14 에 **물리 8코어에서 동시 156세션**을 실측했다. 가정 피크 67 의 2.3배라
「용량은 해결됐다」로 읽히기 쉽다. 그런데 그 값에는 조건이 하나 붙어 있다 —
**AI 컨테이너만 있는 박스**에서 난 값이다.

실제 배포는 그렇지 않다. `docker-compose.prod.yml` 은 **MySQL·Spring·AI 를 한 호스트**에
올린다(관측 스택은 profile 로 분리). 그러면 156 은 내려간다. **얼마나 내려가는지는 안 쟀다.**

> **그래서 지금은 「수평확장이 필요한가」에 답할 수 없다.**
> 동거 값이 120 이면 100 동접은 한 대로 끝나고 수평은 «성능» 이 아니라 **«가용성» 결정**이 된다.
> 40 이면 반대다. **같은 질문에 정반대 답이 나오는데 그걸 가르는 숫자가 없다.**

이 문서는 그 숫자 하나를 만든다.

## 2. 🔴 기존 rig 으로는 못 잰다 — 새로 만들어야 하는 이유

[`loadtest/measure_ai_concurrency.py`](../../loadtest/measure_ai_concurrency.py) 가 이미 있고
08-14 의 156 을 낸 물건이다. 그런데 **이 실험에는 쓸 수 없다.**

```python
from app.core.mediapipe_detector import get_detector   # rig:50
```

**검출기를 프로세스 안에서 직접 부른다.** 컨테이너도, FastAPI 도, gRPC 도 안 거친다.
그건 의도였다 — 「프레임당 추론 비용」은 환경에 안 묶이는 양이라 그렇게 재야 옮겨 쓸 수 있다.

하지만 **동거는 정확히 «환경» 에 관한 질문**이다. 컨테이너 경계·cgroup·네트워크 스택이
빠지면 잴 대상 자체가 없다. 그래서 이 실험의 부하는 **실제 서비스 경로**여야 한다:

```
부하기 ──POST /api/v1/pose (8000, AI_PUBLIC_TOKEN)──> AI 컨테이너
                                                        │ rep 완성 시
                                                        ↓ gRPC SavePoseDataBatch
                                                     Spring ──> MySQL
```

프론트 → AI HTTP 직결(분기 H2)이 실제 프레임 경로이므로 **그 경로에 건다.**

> 🔴 **초판은 여기에 «Spring·MySQL 부하는 AI 부하의 결과로 자연히 따라온다» 고 적었다.
> rig 을 짜면서 실측으로 반증됐다** (2026-08-15, [rig README §2](../../loadtest/results/coresidency-2026-08-15/README.md)).
> 합성 인체의 무릎 각도가 **86.95° ~ 124.30°** 라 rep 상태기계의 «서있음»(≥155°) 문턱에
> 30° 이상 모자란다 — **rep 이 영원히 0 이고, 따라서 `SavePoseDataBatch` 가 한 번도 안 나간다.**
> 검출은 30/30 으로 멀쩡하다. 기존 rig 이 단언한 것이 «검출» 뿐이라 아무도 몰랐다.
>
> → **부하를 두 갈래로 나눈다**(사용자 결정): AI 는 프레임으로, Spring·MySQL 은 **기존 ghz
> `SavePoseDataBatch` rig** 으로 **동시에** 건다. rep 에 안 기대므로
> [#196](https://github.com/Shadowfit/init/issues/196)·[#192](https://github.com/Shadowfit/init/issues/192)
> (둘 다 열린 이슈)에 막히지 않는다.
> **대가**: 두 부하의 비율이 «생겨난» 값이 아니라 **«정한» 값**이다. 실사용의 프레임↔적재 비는
> 이 실험이 답하지 않는다 — 결과 문서에 이 문장을 그대로 넣는다.

> ⚠️ **그래서 이 rig 은 `measure_ai_concurrency.py` 를 대체하지 않는다.** 저쪽은 «프레임당 비용»,
> 이쪽은 «동거 상태의 서비스 용량» 이다. 두 값을 같은 표에 올리지 않는다.

## 3. 팔 설계

무대는 **한 박스**다. 팔은 그 박스에 무엇이 같이 사는가로 갈린다.

| 팔 | 구성 | 성격 |
|---|---|---|
| **A** | AI + Spring + MySQL, 캡 없음, **ghz 부하 없음** | **유휴 동거 기준선.** 🔴 초판의 «AI 단독» 은 성립할 수 없어 2026-08-16 에 재정의됐다(§3-1) |
| **B** | A 와 **같은 구성** + **ghz 부하** | 현행 `docker-compose.prod.yml` 이 «일하는» 상태. Q1·Q2 |
| **C** | AI + Spring + MySQL, **캡 있음** | [#212](https://github.com/Shadowfit/init/issues/212)·[#214](https://github.com/Shadowfit/init/issues/214) 적용. Q3 |
| **D** | C + 관측 스택(`--profile obs`) | Q5. **선택** — 라운드가 길어지면 뺀다 |

### 3-0. 🔴 팔 A 재정의 (2026-08-16) — 「AI 단독」은 이 부하기로 성립하지 않는다

초판의 팔 A 는 **AI 컨테이너만 띄우고** 재는 것이었다. 그런데 이 rig 의 부하기는 세션을
**Spring 을 통해** 연다(`load_ai.py:107` → `POST /exercises/sessions`). 프레임이 수락되려면
세션 전용 검출기 자리가 있어야 하고, 그 자리는 gRPC `StartAnalysis` 가 만들며, 그것을 부르는
것은 Spring 이기 때문이다. **Spring 을 내리면 팔 A 의 전 판이 `setup_fail` 이다**
([#222](https://github.com/Shadowfit/init/issues/222)).

**세 안 중 (a) 를 채택한다** (2026-08-16 사용자 결정):

| 안 | 내용 | 판정 |
|---|---|---|
| **(a)** | 팔 A 를 «B 와 같은 구성 + **ghz 부하 없음**» 으로 재정의 | ✅ **채택** |
| (b) | 부하기가 AI 의 세션 시작을 직접 부른다 | ✗ 실물 경로가 아니게 된다 |
| (c) | 팔 A 를 빼고 08-14 의 156 을 그 자리에 쓴다 | ✗ rig 간 비교가 된다 — §3-1 이 막으려던 바로 그것 |

**대가 두 개를 그대로 적어둔다.**

1. **§3-1 의 산출물이 순수하지 않아진다.** A 에 MySQL·Spring 이 유휴로 얹히므로
   A↔156 의 차이는 «서비스 경로 오버헤드» 가 아니라 **«경로 오버헤드 + 유휴 동거 비용»** 이고,
   이 라운드는 그 둘을 **안 가른다.** 결과 문서에 이 문장을 그대로 넣는다.
2. **[#223](https://github.com/Shadowfit/init/issues/223)(ghz 부하 미배선)이 «품질 캐비엇» 에서
   «선행 조건» 으로 승격된다.** (a) 이후 A 와 B 를 가르는 것은 ghz 하나뿐이라, 그것이 없으면
   두 팔이 **같은 조건**이다. 스윕이 그 상태를 시작 전에 거부한다
   (`coresidency_sweep.sh` `assert_arms_distinguishable`) — 「같은 것을 두 번 재고 표는 정상」이
   #201·#202 와 같은 부류라 사후 주의가 아니라 원천에서 막는다.

> 📌 **이 결함은 「무엇을 재는가」를 바꾼 것이지 rig 의 버그가 아니었다.** 초판이 «AI 단독» 을
> 팔로 세울 수 있다고 본 전제는, 부하가 **실제 서비스 경로여야 한다**(§2)는 이 문서 자신의
> 요구와 애초에 양립하지 않았다. §2 를 쓰는 순간 팔 A 는 이미 불가능했다.

### 4-1. 從 — 메모리 유도식의 «공식 밖 몫» ([#229](https://github.com/Shadowfit/init/issues/229))

**이 라운드에 얹으면 추가 비용이 거의 0 이다.** 이미 동시 세션을 ramp 하며 `docker stats` 로
컨테이너별 메모리를 걷는다 — 필요한 것은 **걷은 값을 유도식과 대조하는 것뿐**이다.

검출기 풀 상한 공식이 **검출기만** 센다(`memory_ceiling()`):

```
상한 = (컨테이너 한도 − 기본 RSS 100.5MB) ÷ 검출기 98.7MB
```

그리고 코드 자신이 *"프레임 버퍼·base64 임시·파이썬 힙·gRPC 는 **미측정**이라 안 뺐다"* 고
경고한다. 그래서 공식에 **딱 맞추면 풀이 세션을 거절하기 전에 컨테이너가 OOM 으로 죽고**,
이 프로젝트가 전제로 삼는 비대칭 실패(«덜 받아짐»=안전)가 **«죽음»=위험으로 뒤집힌다.**

| 세션 수 N 에서 볼 것 | 무엇을 답하나 |
|---|---|
| N=0(기동 직후) RSS | 기본 RSS **100.5MB** 가 지금도 맞는가 (M2 실측값, x86 미검증) |
| `RSS − (100.5 + 98.7×N)` | **공식 밖 몫.** 이게 «여유분» 의 근거가 된다 |
| 그 몫이 N 에 비례하는가 | 비례하면 «세션당 상수», 아니면 «고정 오버헤드» 로 공식에 넣는다 |

🔴 **지금은 숫자를 못 적는다.** 여유를 «몇 %» 로 할지 근거가 없어 `docker-compose.prod.yml`·
`.env.example`·`19-deployment.md` 는 **경고만** 달아뒀다([[feedback_no_arbitrary_threshold_values]]).
이 從 이 그 빈칸을 채운다.

⚠️ **팔 A~D 전부에서 걷는다.** 캡이 걸린 팔(C·D)에서는 «한도에 얼마나 붙었나» 가 같이 보이고,
그게 [#212](https://github.com/Shadowfit/init/issues/212) 의 CPU 캡 값과 **같은 라운드에서**
답해지는 자리다.

🔴 **검출률을 처리량과 같은 급으로 둔다.** [#164](https://github.com/Shadowfit/init/issues/164) 가
검출률 30% → 95.6% 로 고친 전례가 있고([`pool-verify-2026-08-11`](../../loadtest/results/pool-verify-2026-08-11/README.md)),
그건 **처리량 지표에 안 잡히는 고장**이었다. CPU 를 뺏겨 프레임이 밀리면 같은 종류의 붕괴가
다시 날 수 있다 — **처리량만 보면 「느려졌네」로 읽고 넘어간다.**

### 4-2. 🆕 자기 프로브 — 「서버가 느린 것」과 「부하기가 느린 것」을 가른다 (2라운드)

1라운드 결과를 검산하면 plateau 가 **세션수 ÷ p50** 으로 오차 2% 안에 맞는다:

| | p50 | N ÷ p50 | 실측 plateau |
|---|---:|---:|---:|
| A 120 | 412.6ms | 290.8 | 286.8 |
| A 160 | 555.2ms | 288.2 | 284.9 |
| B 120 | 440.2ms | 272.6 | 267.8 |
| C 120 | 476.8ms | 251.7 | 249.0 |

부하기가 3fps 를 **페이싱**하므로(`load_ai.py:154` — 밀린 만큼은 버린다) 왕복지연이 간격
333ms 를 넘는 순간부터 처리량이 그 나눗셈으로 **자동 결정**된다.

📌 **그래서 이 rig 이 재는 「천장」은 RTT 가 333ms 를 넘는 지점이고, 그 RTT 가 어디서
났는지는 클라이언트 시계 하나로 원리적으로 안 갈린다.**
[#250](https://github.com/Shadowfit/init/issues/250) 의 CPU 샘플러가 「부하기 CPU 는 안
붙었다」를 보여줘도, 파이썬 스케줄링·큐잉으로 RTT 는 늘 수 있다. **샘플러만으로는 절반이다.**

→ 판마다 **대상 박스에서 1세션짜리 프레임 프로브**를 같이 돌린다(로컬 루프백).
부하기 p50 이 413ms 인데 로컬이 50ms 면 큐는 **부하기 쪽**이고, 둘 다 413ms 면 **서버**다.
부하 +3 req/s · 앱 변경 0 · 측정 시간 +0.
⚠️ 대가: 프로브가 검출기 슬롯 1개와 RSS ~107MiB 를 먹는다. **팔 A~C 전부에서 같이 돌므로**
그 비용은 팔 간 대조에서 상쇄된다. 조건 칸에 적는다.

**✅ 코드 반영 (2026-08-17)** — `coresidency_sweep.sh` 의 `setup_probe`·`start_probe`·`stop_probe`.
설계에서 정하지 않았던 것 셋이 짜면서 정해졌다:

| 정한 것 | 왜 |
|---|---|
| **부하기(`load_ai.py`)를 그대로 재사용**하고 대상 박스로 밀어 넣는다(`$SSH "cat > …"`) | 프로브를 따로 짜면 세션 개설 경로(온보딩 `preferredUrl` 같은 함정)가 두 벌이 된다. 자산은 크기로 대조해 «반쯤 간 파일» 을 막는다 |
| **`--dur 0` = SIGTERM 까지** | 프로브는 «판이 끝날 때» 같이 끝나야 하는데 그 시각을 미리 못 정한다 — 부하기 계정 준비가 세션 수에 비례해 길어져(160세션이면 20초 초과) 측정창 시작이 판마다 다르다. `kill -9` 면 그 판의 서버 시계가 통째로 사라진다(요약을 끝에 한 번 쓴다) |
| **부하기의 warm 창으로 잘라서** 요약 | 프로브는 판보다 먼저 시작해 «부하 없는 구간» 을 같이 담는다. 안 자르면 «서버가 빠르다» 로 치우친다. `window` 칸에 `warm`·`full`·`no_overlap`·`empty` 를 갈라 적고, **겹치지 않으면 백분위를 안 적는다** |

🔴 **계정 네임스페이스를 갈랐다**(`--user-prefix probe`). 안 그러면 프로브가 부하기의 0번
세션과 같은 계정을 쓰고, «회원당 활성 세션 1개» 제약에 걸려 **둘 중 하나가 조용히 빠진다.**
`reset_sessions` 도 `probe%` 를 같이 푼다 — SIGTERM 종료는 «닫고 나가는» 경로를 못 탈 수 있다.

## 5. 판 설계

- **버림판 팔당 1** — 첫 판은 컨테이너 워밍업·버퍼풀·JIT 를 가장 크게 탄다
- 본판 **팔당 3판**, 위치 합을 맞춘 배열(각 팔이 판 순서 1·2·3 에 한 번씩)
- 판 사이 **AI 컨테이너만 재기동 + 從 부하가 넣은 행 정리** (🔴 2026-08-16 뒤집힘 — 아래 5-1)
- 판당 부하는 **동시 세션 ramp**로 포화점을 찾는다. 고정 부하로는 「천장」이 안 나온다.
  레벨은 1라운드 **20 · 40 · 60 · 80 · 120 · 160**(§5-2) → 2라운드 **+ 90 · 100**(§5-3)
- 🆕 **교대 단위는 «팔» 이 아니라 «레벨»**, 레벨 순서는 라운드마다 뒤집는다, 앵커 판을 넣는다
  (2라운드 — §5-3. [#251](https://github.com/Shadowfit/init/issues/251)·[#252](https://github.com/Shadowfit/init/issues/252))

📌 팔이 4개(A~D)면 12판 + 버림 4판이다. **D 를 빼면 9판 + 버림 3판**으로 준다.
1라운드는 팔 A·B·C 라 **9판 + 버림 3판 = 12판**(스윕 단위)이었고, 관측으로는 54 + 3 = **57행**이다.

### 5-1. 🔴 「스택 재기동」이 「AI 만 재기동」으로 뒤집혔다 ([#246](https://github.com/Shadowfit/init/issues/246))

초판은 *「판 사이 같은 초기 상태 — 스택 재기동 + `pose_data` 정리」* 였다. **rig 은 그렇게
안 한다** — `coresidency_sweep.sh` `reset_between()` 은 `shadowfit-ai` 만
`docker compose restart` 하고, `pose_data` 는 從 부하 시드 범위(`GHZ_SESS_LO~HI`)만 지운다.
탑승 전 [`../../loadtest/AWS-RIDE-ALONG.md`](../../loadtest/AWS-RIDE-ALONG.md) §4 대조에서 잡혔고,
**rig 쪽이 맞다고 판정해 설계를 고친다**(다른 3건은 반대로 rig 을 고쳤다 — [#245](https://github.com/Shadowfit/init/pull/245)).

| | 왜 |
|---|---|
| AI 는 **재기동해야 한다** | 세션 상태가 AI 프로세스 메모리에 있다(`ai-server/app/core/session_state.py:243`). 안 내리면 앞 판 세션이 검출기 풀 자리를 물어 `nolease` 가 **앞 판 탓으로** 난다 |
| MySQL·Spring 은 **안 내린다** | 매 판 내렸다 올리면 판당 비용이 크게 늘고, **버퍼풀·JIT 재워밍업 자체가 판마다 다른 조건**이 된다 |

⚠️ **대가 — 판을 건너 누적되는 상태가 남는다.** MySQL 버퍼풀·Spring JIT 이 그것이고,
**얼마나 누적되는지는 안 쟀다**(위 판단은 비용 논증이지 측정이 아니다). 라틴 방격 배열이
그 누적을 팔에 **균등하게 흩는 것**까지만 한다 — 없애지는 못한다. 결과 문서에 이 문장을 넣는다.

⚠️ 판 사이 `pose_data` 정리를 從 부하 시드 범위로 한정해도 되는 근거는 **«AI 경로는 합성
인체라 rep 이 0 이어서 적재가 없다»**(§2 실측)에 기대고 있다. rep 이 생기는 rig 으로 바뀌면
이 한정도 같이 깨진다.

### 5-2. 레벨을 4개에서 6개로 — 20 · 40 · 60 · 80 · 120 · 160

초판 격자 `20/40/80/160` 은 **단독 156 을 감싸도록** 잡은 것이다. 그런데 이 실험의 가설
H1 은 *「동거하면 내려간다」* 이므로, 내려간 천장이 **40~80 사이면 포화점을 낀 관측점이
위아래 한 개씩뿐**이라 천장을 구간으로밖에 못 적는다. **격자가 상단에 치우쳐 있었다.**

→ 40~80 구간에 60 을, 80~160 구간에 120 을 넣는다. 최고 레벨 160 은 그대로 둔다
(從 부하 19 req/s 의 유도가 «160세션 × 0.12» 라 최고 레벨이 바뀌면 그 값도 바뀐다).

⚠️ **6레벨도 «정한» 값이다** — 천장 위치를 모르는 상태에서 해상도를 올린 것이지 측정에서
나온 격자가 아니다. 결과의 조건 칸에 이 유도를 그대로 적는다.

| | 4레벨 | **6레벨** |
|---|---|---|
| 판당 | 4 × (DUR 90s + 앞뒤 pad 5s×2) ≈ 6.7분 | ≈ **10분** |
| 12판 | ≈ 100분 | ≈ **2시간** |
| 라운드 전체(부트스트랩·preflight·리허설 포함) | ≈ 3시간 | ≈ **3.5시간** |

`TIMEOUT_CORES=21600`(6시간, `../../loadtest/aws/run_all.sh:124`) 안에 들어간다.

> 대안 2개를 안 골랐다. **정찰판 후 확정**(팔 A 버림판으로 천장을 먼저 보고 격자를 정함)은
> 라운드가 2단이 되어 무인 1회의 이점을 잃고, **격자 유지**는 가장 싸지만 가장 그럴듯한
> 시나리오(천장이 40~80)에서 정확히 못 짚는다.

🔴 **그 걱정이 한 칸 위에서 그대로 재현됐다** — 천장이 실제로는 **80~120** 사이였고,
6레벨에도 그 구간에 점이 없어 1라운드는 「80 초과 120 미만」까지만 말한다. → §5-3 이 8레벨로 넓힌다.

### 5-3. 🆕 2라운드 판 설계 — 시간 축을 팔 축에서 떼고, 천장을 점으로 (2026-08-16 확정)

1라운드가 못 닫은 셋(H1 · 부하기 천장 · H3)의 **뿌리 둘이 판 설계에 있다.**

| 바꾸는 것 | 왜 | 시간 |
|---|---|---|
| **① 교대 단위 «팔» → «레벨»** — `A_20 → B_20 → C_20 → A_40 → …` | [#251](https://github.com/Shadowfit/init/issues/251). 지금은 한 팔이 6레벨을 다 돈 뒤 다음 팔로 가서 **같은 레벨의 팔 간 대조점이 13~27분** 떨어진다. 그 사이 처리량이 **분당 0.09~0.35%** 흐른다(팔 A: 12분 266.0 → 82분 282.9 → 108분 308.6 fps). 대조 간격이 **~4분**이 된다 | +4분 |
| **② 캡을 `docker update --cpus` 로 토글** | ①의 전제. 지금 팔 전환은 compose override 로 **컨테이너를 재생성**한다(`coresidency_sweep.sh:111-118`). 전환이 9 → 54회가 되면 **재생성 위치가 팔마다 달라져 새 교락**이 된다. `docker update` 는 재기동이 없다 | 전환 ~1초 |
| **③ 캡 적용 단언** ✅ 코드 반영 08-17 | [#253](https://github.com/Shadowfit/init/issues/253). 캡이 안 물리면 **팔 C ≡ 팔 B** 인데 표는 정상이다. 전환마다 `NanoCpus` 를 `.env` 기대값과 대조하고, 팔 A·B 에서는 **0 이어야 한다**는 반대 단언도 건다. 관측값은 `caps.tsv` 에 남긴다 — 캡은 **측정 조건**이다 | ~1초 |
| **④ 레벨 순서 라운드마다 «치환»** ✅ 코드 반영 08-17 | [#252](https://github.com/Shadowfit/init/issues/252). 아홉 블록 전부 오름차순이라 블록 안 추세가 **120·160**(= plateau 를 정의하는 자리)에 얹힌다. 🔴 **반전으로는 안 고쳐진다** — 오름/내림/오름이면 레벨↔평균위치 상관이 **여전히 1.000** 이다. 회전(shift 2)으로 **0.361** 까지 내린다 | 0 |
| **⑤ 앵커 판 4개** (라운드마다 + 끝, 동일 조건 B@80) ✅ 코드 반영 08-17 | ①이 팔 간 간격을 줄여도 **드리프트 자체는 남는다.** 그것을 보정 대상이 아니라 **측정값**으로 남긴다. 끝에 하나를 더 둬야 **전 구간을 감싼다**. 첫 앵커 앞에 그 팔의 버림판을 먼저 돌려 **워밍업이 계열 첫 점을 오염시키는 것**을 막는다 | +11분 |
| **⑥ 레벨 90 · 100 추가 → 8레벨** | 천장이 「80 초과 120 미만」 구간으로만 짚혔다. **최고 160 은 그대로 둔다** — `GHZ_RPS` 유도가 «160세션 × 0.12» 라 최고 레벨이 바뀌면 從 부하 값도 바뀐다 | +40분 |

| **⑩ 부하기 코어 팔(§T)** ✅ 코드 반영 08-17 | 🔴 라운드 간 +17.7% 의 원인이 «부하기 구성» 인지 «대상 박스 물리 호스트 개체차» 인지 **둘이 같이 바뀌어 안 갈린다**. 같은 세션·같은 호스트에서 `taskset -c 0-1`(2코어) ↔ 제한 없음을 **붙여서** 대조한다. 쌍의 순서는 반복마다 뒤집는다 | +26분 |

**판 수**: 본판 3팔 × 3라운드 × 8레벨 = 72 + 버림 3 + **앵커 4** + **§T 12** = **91판**.
판 주기 실측 128.5초(1라운드 57판 / 7,323초)로 **스윕 ≈ 3h20m**(팔 전환 포함),
리허설·preflight·collect 포함 **인스턴스 가동 ≈ 3h40m**. `TIMEOUT_CORES=21600`(6시간) 안이다.

⚠️ **④의 대가** — 내림차순 블록은 **160세션이 첫 판**이라 워밍업을 가장 큰 판이 뒤집어쓴다.
버림판 레벨을 그 블록의 첫 레벨에 맞춰야 한다(현재는 `$LEVELS` 첫 값 고정 — `:447`).

⚠️ **①이 §5-1 을 흔들지 않는다** — 판 사이 재기동 정책(AI 만)은 그대로다. ②가 없으면
①이 그 정책을 깨뜨린다(팔 전환마다 MySQL·Spring 재생성)는 것이 ②를 붙인 이유다.

⚠️ **`docker update --cpus` 가 이 구성에서 실제로 물리는지 아직 안 해봤다.** 로컬 확인이
2라운드의 선행 조건이고, 안 되면 ①을 «전환 45회 추가 × 재생성»(+23분)으로 되돌려야 한다.

## 6. 가설과 반증 조건

| # | 가설 | **무엇이 나오면 틀린 것인가** | 1라운드 판정 |
|---|---|---|---|
| H1 | 동거하면 동시 세션이 **내려간다** | B 가 A 와 사실상 같다 (= 동거 비용이 무시할 수준) | 🔴 **판정 불가** — A 가 흐른다([#251](https://github.com/Shadowfit/init/issues/251)) |
| H2 | 뺏는 주체는 **AI 자신**이다 — 코어를 주는 대로 먹으므로 | 포화 시 AI cgroup CPU 가 지배적이지 않다 | ✅ **지지** — AI 869~893% vs 옆 둘 합 0.17 vCPU |
| H3 | 캡을 걸면 **총 용량은 줄지만 다른 서비스가 산다** | C 에서 Spring p99·MySQL 지표가 B 와 차이 없다 (= 캡이 아무것도 안 지킴) | 🔴 **자료 없음** — 그 열이 생성되지 않았다([#254](https://github.com/Shadowfit/init/issues/254)) |
| H4 | 검출률은 **처리량보다 먼저** 무너진다 | 포화까지 검출률이 평탄하다 | ❌ **반증** — 57행 전부 `detect_pct` 100.00, 대신 지연이 간다 |
| H5 | 관측 스택 비용은 **한 자릿수 %** | D 가 C 대비 두 자릿수 % 내려간다 | — 미측정(팔 D 제외) |

🔴 **H3 의 반증 조건이 「Spring p99·MySQL 지표」인데 rig 이 그 둘을 안 걷는다**(§4 표).
그래서 1라운드가 「캡 축은 닫혔다」고 적은 것은 정확히는 **「AI 처리량이 캡한 만큼 깎였다」**
(CPU 90.8% → 처리량 92.9%)이고, [#212](https://github.com/Shadowfit/init/issues/212) 가 실제로
물은 **«캡이 옆을 지키는가» 는 아직 안 답해졌다.** Q3 이 절반만 닫힌 것이 이 뜻이다.

**H3 이 반증되면 [#212](https://github.com/Shadowfit/init/issues/212) 의 전제가 흔들린다** —
캡이 지키는 게 없다면 캡 값을 정하는 일 자체가 다른 문제가 된다. 그것도 산출물이다.

> 임계값은 적지 않는다. 「동시 N세션 이상이면 합격」 같은 기준은 지금 근거가 없다
> ([[feedback_no_arbitrary_threshold_values]]). 이번 범위는 **값을 관측해 적는 것**까지다.

## 7. 로컬인가 EC2인가

🔴 **로컬로는 Q1 을 못 답한다.** 개발 장비는 i3-6100 2물리코어에 MySQL+백엔드가 이미
동거 중이라([[project_loadtest_env_constraint]]) **동거 실험의 대조군인 「단독」을 만들 수 없다.**
팔 A 가 성립하지 않으면 §3-1 의 분리가 통째로 무너진다.

그리고 이 실험이 답해야 하는 것은 **「c7i.4xlarge 급에서 156 이 얼마가 되나」** 다. 그 박스가
아니면 옮겨 쓸 수 없다.

→ **EC2 1대.** 08-14 와 같은 타입(c7i.4xlarge)이어야 156 과 비교가 성립한다.
부하기를 같은 박스에 두면 그것이 또 경합 변수가 되므로 **부하기는 별도 소형 인스턴스**다.

## 12. 🔴 그 사이에 2라운드가 이미 돌아 있었다 — 그리고 절대값이 안 재현된다 (2026-08-16b)

|---|---:|---:|---:|

| B | 267.6 (89.2) | **315.0 (105.0)** | **+17.7%** |
| C | 248.6 (82.9) | **291.2 (97.1)** | +17.1% |

**팔 대조는 닫혔다.**

  조건에서 **동거 비용은 잡음 크기**다. 1라운드의 −0.8/−6.2/−13.3% 는 팔 효과가 아니었다.
- ⭐ **드리프트가 사라졌다** — 팔 A r1 315.3 → r2 316.5 → r3 **317.7 fps = +0.8%**

  **이 무대에서는 크기가 무너졌다.**

  (ok 72,162 / fail 1) — «옆이 논 판» 이 아니다.

### 12-1. 🔴 그런데 「부하기가 천장이었다」는 실측이 지지하지 않는다

가장 먼저 떠오르는 설명 — *「2 vCPU 부하기가 프레임을 덜 먹여서 1라운드가 낮았다」* — 은
**배제된다.** 그랬다면 1라운드의 **AI CPU 가 낮아야** 하는데:

| | 1라운드 | 2라운드 |
|---|---:|---:|
| 팔 B AI CPU | **869.3%** | **869.0%** |
| 팔 B 처리량 | 267.6 fps | **315.0 fps** |
| fps / AI vCPU | 30.78 | **36.25** |

**AI 는 같은 CPU 를 쓰고 프레임을 17.7% 덜 처리했다** — 그 CPU 를 «일이 아닌 데» 썼다는 뜻이다.
그리고 부하기 CPU 는 4 vCPU 중 **0.68 만**(포화선 400%, 관측 최대 67.6%) 썼다.

남은 후보는 둘이고 **같이 바뀌어서 안 갈린다** — ① 부하기 2→4 vCPU 의 **송신 패턴**,
② 라운드 사이 정지→시작으로 인한 **대상 박스의 물리 호스트 변경**. 상세·약한 갈림은
[2라운드 결과 §5](../../loadtest/results/coresidency-aws-b-2026-08-16/README.md).

📌 **그래서 [#250](https://github.com/Shadowfit/init/issues/250) 은 «계측 축» 만 닫혔다** —
부하기 CPU 는 천장이 아니었다는 것까지가 사실이고, **무엇이 +17.7% 를 만들었는지는 열려 있다.**

⭐ **그리고 이것이 §4-2 를 강화한다.** 부하기 CPU 가 «안 붙었다» 는 관측만으로는
**「부하기 구성이 결과를 안 움직인다」를 못 말한다** — 실제로 안 붙었는데 움직였다.
대상 쪽 독립 시계(**자기 프로브**)가 없으면 이 축은 계속 안 갈린다.

### 12-2. 이 발견이 §11 을 어떻게 바꾸나

| §11 항목 | 바뀐 우선순위 |
|---|---|
| ⑨ H3 판정 열 ([#254](https://github.com/Shadowfit/init/issues/254)) | 🔴 **최우선.** 2라운드도 이 열이 없어 H3 는 **세 라운드째 못 닫혔다** |
| ⑥ 레벨 90·100 | 🔴 **최우선.** 천장이 여전히 80(100%)~120(88%) 사이다 |
| 🆕 **라운드 간 절대값 비재현** | 🔴 **새 최우선 — ⑩(§T)이 그 절반을 가른다.** 같은 코드·격자·인스턴스 타입에서 천장 환산이 89.2 → 105.0세션으로 움직였다. **앵커 판(⑤)의 값이 여기서 올라간다** — 라운드 내부뿐 아니라 **라운드 간** 기준점이 된다 |
| ⑧ 자기 프로브 | 🟡 **유지** — 12-1 이 그 필요를 강화했다 |
| ③ 캡 단언 ([#253](https://github.com/Shadowfit/init/issues/253)) | 🟡 유지. 두 라운드 재현됐으나 비용이 ~0 |
| ④ 레벨 순서 반전 | 🟢 유지(비용 0) |
| ①② 레벨 단위 교대 + `docker update` | 🟢 **강등.** 드리프트가 +0.8% 로 줄어 **가장 비싼 변경의 근거가 약해졌다** |
| ⑦ 샘플러 보강 | 🟡 유지 + [#255](https://github.com/Shadowfit/init/issues/255)(종료 샘플 음수) 반영 |
| 무대 | **부하기 `c7i.xlarge` 를 기본으로.** 단 12-1 때문에 «2 vCPU 가 나빴다» 가 아니라 «조건을 고정한다» 가 이유다 |

🔴 **1라운드 헤드라인(「동거 천장 89.2세션」)은 인용하지 않는다** — 절대값은 라운드를 건너
재현되지 않는다. 팔 간 비교와 메모리 식은 재현된다.
