## 2. 다시 조립한다면

**두 개만 바꾸면 나머지가 따라온다.**

### ① 프레임 경로를 스트림으로

```
폰 ══연결 1개 = 세션 1개══▶ AI 인스턴스
```

| 얻는 것 | |
|---|---|
| **끊김이 이벤트가 된다** | 지금은 클라가 요청을 멈춰도 서버가 모른다 → 좀비 세션. `PoseDataOrphanMonitor` 와 `lastActiveAt` 의 존재 자체가 이 문제를 겪은 증거다 |
| **상태의 주인이 명확해진다** | 연결 수명 = 세션 수명 |
| **서버가 먼저 말할 수 있다** | 지금 피드백은 **다음 프레임 응답을 기다린다**(최대 330ms 지연). 스트림이면 rep 완성·피드백·TTS 를 즉시 민다 |
| **base64 팽창 제거** | binary frame → payload 약 25% 감소 |
| **백프레셔** | ⑥ 이 자연스러운 기본형으로 해결된다 |

**구간별 선택**: 폰→AI 는 **WebSocket**(RN 내장 API. gRPC-Web 은 bidi 를 제대로 지원하지 않고 RN 네이티브 gRPC 는 생태계가 얇다),
AI↔Spring 은 **gRPC 유지**. 스키마가 필요하면 기존 `exercise.proto` 를 WS 위에 바이너리로 실으면 된다.

#### 🔴 이 문서를 쓰며 정정한 것 둘

1. **«WS 면 #164 가 구조적으로 사라진다» 는 과장이었다.**
   MediaPipe 추론은 blocking CPU 작업이라 `async def` 핸들러에서 직접 돌리면 **이벤트 루프를 막는다.**
   결국 `run_in_executor` 로 빼야 하고, **그러면 다시 스레드풀이라 검출기가 다시 스레드에 붙는다.**
   WS 는 #164 를 **고칠 수 있게 해줄 뿐** 자동으로 고치지 않는다 — 진짜로 풀려면 «연결마다 전용 워커» 까지 가야 한다.
2. **«무중단 배포 가능» 도 반대에 가깝다.**
   연결이 세션에 묶이면 배포할 때 그 연결을 끊어야 하고 drain 이 «가장 긴 세션» 만큼 걸린다.
   정확히는 — **지금은 조용히 깨지고, 스트림이면 명시적으로 끊긴다.** 후자가 낫지만 «무중단» 은 아니다.

#### 트레이드오프

| | |
|---|---|
| **재연결 로직을 클라가 짜야 함** | 🔴 모바일에서 제일 큰 비용. 셀↔와이파이·백그라운드 전환 |
| **관측 모델 재설계** | 🔴 관측 1차가 **요청 단위 correlation id** 로 만들어져 있다. 스트림은 «연결 단위 + 메시지 단위» 라 안 맞는다 |
| 테스트·디버깅 | curl 로 못 찌른다. 기존 `measure_*.sh` rig 가 안 통한다 |
| LB·프록시 | idle timeout 을 세션 길이에 맞춰야 한다. 기본값이면 조용히 끊긴다 |
| 에러 모델 | HTTP 상태 코드가 없다. 애플리케이션 레벨 프로토콜이 필요하다 |

> **성능이 이유라면 근거가 약하다** — 전송·인코딩 비용은 **측정된 적이 없다.**
> **구조가 이유라면 충분하다.** 그래서 «성능 최적화» 가 아니라 **«상태 모델 정정»** 으로 불러야 정직하다.

### ② 세션을 «AI 인스턴스에 배정된 것» 으로 명시

Spring 이 세션 시작 시 인스턴스를 배정하고 그 매핑의 진실 출처가 된다.

- outbox 통보 대상이 결정된다 (지금 outbox 는 **단일 gRPC 대상을 전제**한다)
- 인스턴스 사망 시 **명시적** 재배정 + reattach (지금은 조용한 유실)
- drain 이 가능해진다
- 입장 제한([`32-deferred-items.md P3`](../tasks/32-deferred-items.md))이 자연스럽게 여기 붙는다

> ⚠️ **억지로 stateless 로 만들면 안 된다.** BlazePose 트래킹은 본질적으로 stateful 이고
> `static_image_mode=True` 로 없애면 매 프레임 탐지기가 돌아 **비용이 오른다.**
> 상태를 없애는 게 아니라 **주인을 정하는 것**이 답이다.

> 🔵 **2026-08-26 갱신 — 이 항목은 이후 [`ai-sticky-routing.md`](./ai-sticky-routing.md)(2026-08-23)가
> 훨씬 깊게 편 자리다.** 여기 4줄은 **회고의 압축본**이고, 실제 트레이드오프·추천은 그 문서
> §5-1(㉮ 엔드포인트 — 추천 ㄱ Spring 이 알려준다)·§5-2(㉯ 매핑 위치 — 추천 ㄴ 세션 테이블
> 컬럼)·§5-3(㉰ 장애 재배치 — 추천 ㄴ `ReattachAnalysis` 재사용)·§8(결정 체크박스, 미확정)에
> 있다. **이 항목이 그 문서에 안 실린 것 하나** — 위 넷째 줄 「입장 제한이 자연스럽게 여기
> 붙는다」([`32-deferred-items.md P3`](../tasks/32-deferred-items.md)) — 는 `ai-sticky-routing.md`
> 어디에도 없다. Spring 이 세션↔인스턴스 매핑의 진실 출처가 되면(§5-2 ㄴ 채택 시), 인스턴스별
> 활성 세션 수를 세는 재료가 그 컬럼에서 바로 나오므로 입장 제한(P3)이 **㉯의 부산물**이 된다 —
> 이건 `ai-sticky-routing.md` §8 결정에 추가할 가치가 있는 연결이다.
>
> 🔗 **관련 소규모 선례**: [`ai-channel-pool-hardening.md`](./ai-channel-pool-hardening.md)
> 문제①(1박스·N프로세스 스코프)이 같은 `ReattachAnalysis` 재사용 패턴으로 「채널이 가리키는
> 프로세스가 죽으면 세션이 갇힌다」는 문제를 이미 분석해뒀다(2026-08-26, 결정 대기) — 그 문서
> 자신이 "결과를 §8 ㉰(여러 박스 장애 재배치)에 참고 사례로 반영할지"를 미결로 열어뒀다.

**배포 1대가 병목이다.** 운영 점수는 «운영 중인 것» 이 없으면 구조적으로 못 올리고, 확장성도 거기 묶여 있다.

### 다만 — 목적지에 맞는지는 별개다

확장성·운영 점수는 **실제로 운영해야** 오르는데, 이 프로젝트의 목적지는 **취업 포트폴리오지 운영이 아니다.**
§4 가 «더 높은 성능 숫자» 를 잘랐듯, 운영 점수 올리기도 같은 함정일 수 있다.

> **확장성을 3에서 6으로 올리는 것보다 «왜 3인지 정확히 아는 것» 이 낫다.**

## 5. 면접 답변 (E4)

### Q. 설계에서 아쉬운 점은?

> "AI 서버가 세션 상태를 메모리에 들고 있는데, 그걸 전제한 설계가 없습니다.
> 그래서 재시작하면 분석 결과가 유실되고, 무중단 배포가 안 되고, 스케일아웃이 안 되고,
> 검출기가 세션이 아니라 스레드에 붙는 문제까지 생깁니다 — **네 개가 별개로 보이지만 원인이 하나**입니다.
> 상태의 소유 단위를 «프로세스» 가 아니라 «연결» 로 옮기는 게 정답이라고 봅니다."

### Q. 이거 확장 되나요?

> 🔄 **2026-08-26 갱신** — 병목의 정체가 그 사이 갈렸다. "추론 CPU 가 병목"이 아니라
> **GIL**이었다(2026-08-24 직접 계측, ρ=0.939 · 순수 파이썬 경로가 1코어 벽을 못 넘음).
> 그래서 프로세스를 3개로 쪼갰고(883f508), 로컬 대조에서 처리량 1.30배(270.7→352.6 rps,
> CPU 9.52→14.50 vCPU)를 얻었다 — 2배가 아니라 1.30배이고, 14.5 vCPU 근처의 두 번째
> 천장은 아직 안 쟀다.
>
> "안 됩니다"는 지금도 대체로 맞다 — 어피니티가 없어서 **여러 박스**로 인스턴스를 늘리면
> 프레임이 상태 없는 쪽으로 가는 문제는 그대로다(`ai-sticky-routing.md`). 다만 이건 설계·
> 실행 둘 다 아직 안 했다 — 필요 계산이 "DAU 1,000·피크 67세션은 지금 구조로 버틴다"로
> 나와서 **착수 자체가 미결정**이다. "확장 되나요?"의 정직한 답은 이제 "1박스 안에서
> 프로세스를 늘리는 세로 확장은 이미 했고 1.3배를 얻었다. 여러 박스로 가는 가로 확장은
> 설계는 서 있지만(스티키 라우팅·세션-인스턴스 매핑·장애 재배치, 셋이 묶여서 따로 못
> 정한다) 필요성이 아직 안 나와서 안 했다"다."

### Q. 이 좌표를 왜 저장하세요?

> ⚠️ **지금 답이 약하다.** 1억 행을 쓰고 안 읽고 지운다. [`32-deferred-items.md P5`](../tasks/32-deferred-items.md) Tier 0 을 만들면 화면으로 답이 된다.
