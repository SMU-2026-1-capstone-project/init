## 0. 한 줄 요약

**지금 배포된 `maximum-pool-size: 15` 는 «c=100 이라는 한 점»에서만 검증된 값이다. 이 실험은 그 점을 곡선으로 바꾼다.**

§5-1(8) 은 c=100 을 고정해놓고 풀만 흔들어 cliff 가 10~15 사이임을 좁혔다. 그런데 **동시성을 바꾸면 그 절벽이 움직이는지는 안 봤다.** 움직인다면 "풀=15" 는 고정 상수가 아니라 **예상 동시성의 함수**이고, 그 사실 자체가 지금 코드에 박힌 값의 성격을 바꾼다.

> ⚠️ **기대치를 미리 낮춰 적는다.** 이 실험이 "15 는 틀렸다"로 끝날 가능성은 낮다고 본다. 실제로 바뀌는 건 결론이 아니라 **근거의 강도**다 — 한 점에서 나온 값이 곡선 위의 값이 된다. 그게 이 실험의 정직한 값어치이고, 그 이상으로 팔지 않는다.

### 🔴 예측이 빗나간 방향이 §0 과 다르다 — 근거의 강도가 아니라 «비교 가능성» 이 바뀌었다

|---|---|---|

| R=1 (옛 코드 상당) | **98.3** | 6,740ms |

RPS 1.7배 · p99 4.9배. **지난번 47% 붕괴가 재현되지 않은 것은 측정이 틀려서가 아니라 코드가 바뀌어서다.**

> 즉 *"절벽이 c 를 따라 움직이는가"* 는 **답이 안 나온 게 아니라, 이 부하 수준에서는 질문이 성립하지 않게 됐다.**
>
> 🔴 **정정 (2026-08-08)**: 초판은 여기에 *"다운샘플이 병목을 DB 쓰기에서 **백엔드 CPU** 로 옮겨놨기 때문 — 백엔드 p90 128%, MySQL p90 53%"* 라고 적었다. **그 두 수치는 커밋된 원본에 없다** — `metrics/` 10종이 전부 백엔드 것이고 **MySQL 지표는 수집조차 안 됐다.** 스윕 중 백엔드 `system_cpu` 는 **0.51~0.56** 으로 포화가 아니었다. **«병목이 백엔드 CPU» 는 근거 없이 내린 결론이었고, 철회한다.**
>
> 확실한 것은 **옛 코드(R=1) 구간에서는 CPU 가 실제로 포화였다는 것**(`system_cpu` **1.00**, 획득 대기 7.01초)뿐이다. 지금 코드에서 무엇이 ~205 RPS 를 막고 있는지는 **미상**이고, 1순위 용의자는 **부하기 커넥션 1개**다(ghz 14판 전부 `"connections": 1` — 미검증, 결과 [README §2-2](../../loadtest/results/pool-cliff-2026-08-08/README.md)).

### 풀은 포화됐지만 무너지지 않았다 — 단, 포화한 쪽은 `pool=5` 다

> 🔴 **2026-08-08 정정.** 초판은 여기에 *"`active` 가 상한 20 에 붙고 `pending` 96, 획득 대기 7.28초"* 라고 적었다. **셋 다 스윕 밖 구간(R=1 대조군·v1)의 값**이었다 — 시계열 전체 창의 최댓값을 스윕의 값으로 인용한 것이다. 판별로 정렬한 실제 값은 아래와 같다. 경위는 결과 [README §5 ④](../../loadtest/results/pool-cliff-2026-08-08/README.md).

| 판 | RPS | active | pending | 획득 최대 | timeout |
|---|---|:--:|:--:|---|:--:|
| c100 · **pool=20** | 203.9 | **2** | **0** | 0.001초 | 0 |
| c100 · **pool=5** | 208.9 | **5**(=상한) | **95** | 0.957초 | 0 |

**이렇게 갈라 보는 쪽이 근거가 강하다.** `pool=20` 에서 풀은 **놀고 있고**(20개 중 2~3개, 대기 0), `pool=5` 에서는 **포화다**(상한에 붙고 95개 대기). **그런데 RPS 가 같다.** 풀 상태가 이 정도로 갈리는데 처리량이 안 변하면 병목은 커넥션이 아니다.

포화 쪽에서도 `timeout_total` 은 **0** 이다. 커넥션 1건당 작업이 짧아(5행 INSERT) 최대 0.96초 대기가 30초 한도에 한참 못 미치고 큐가 빠진다. **포화 ≠ 붕괴** 는 살아남는다.

### 실행 중 틀린 것 3건 (전문은 결과 [README §5](../../loadtest/results/pool-cliff-2026-08-08/README.md))

① 부하기를 백엔드와 같은 2 vCPU 박스에 뒀다 — **이 문서가 obs 분리 이유는 §4 에 적었으면서 부하기 위치는 검토하지 않았다**(설계 누락). ② warm 백엔드와 cold 백엔드를 풀 차이로 오독했다 — §4-1 이 "지난번 함정"을 3개나 적어뒀는데 정작 `load-test-strategy.md` 의 cold JVM 경고는 안 옮겨왔다. ③ ②를 근거로 v1 스윕 10판 전부 폐기라고 선언했다(결론은 v2 와 동일했고, 보존해 대조용으로 쓴다).

## 1. 이미 아는 것 / 모르는 것

> 🔴 **실행 후 주석 (2026-08-08)**: 아래 두 표는 **배치당 25행을 쓰던 코드**의 측정이라 현재 코드와 직접 비교할 수 없다(§0-1). 설계 시점의 근거로서 그대로 보존한다.

**아는 것** — c=100 고정, 풀만 변화 (§5-1(8), 분리 배포 실측):

| pool | RPS | p99 | 실패 |
|---|---|---|---|
| 10 | 5.9 | 19,825ms | **937/2000 (47%)** |
| **15** | 199.8 | 1,529ms | 0 |
| 20 | 191.8 | 1,432ms | 0 |
| 30 | 188.3 | 1,326ms | 0 |

10 → 15 에서 RPS 가 **34배** 뛴다. 경사가 아니라 절벽이라 cliff 다. 그리고 15 위로는 늘려도 이득이 없다.

**아는 것 2** — pool 10 vs 30 을 여러 c 에서 (§5-1(7)):

| c | pool=10 | pool=30 |
|---|---|---|
| 10 | RPS 191.0 / 실패 0 | RPS 202.6 / 실패 0 |
| 30 | RPS 211.1 / 실패 0 | RPS 203.9 / 실패 0 |
| 50 | RPS 104.3 / **실패 0** | RPS 187.0 / 실패 0 |
| 100 | RPS 5.9 / **실패 47%** | RPS 188.3 / 실패 0 |

**여기가 이 실험의 씨앗이다.** c=50 에서 pool=10 은 **실패는 0인데 RPS 가 절반**이다. c=100 에서야 무너진다. 즉 **열화는 c=50 에서 이미 시작됐고 c=100 에서 붕괴로 완성된다** — 절벽이 c 를 따라 이동하고 있다는 정황이 이미 데이터에 있다.

**모르는 것**: c=30·50·70 각각에서 cliff 가 **몇 번 풀에 있는가**. 위 표는 pool 을 10 과 30 두 점만 봤기 때문에 그 사이를 알 수 없다.

## 2. 🔴 먼저 정해야 할 것 — "무너졌다"의 정의

**이게 설계의 핵심이고, 여기서 결과가 갈린다.** §5-1(8) 은 c=100 에서 실패율 47% 라는 극적인 신호가 있어 정의를 따질 필요가 없었다. 그런데 c=50 에서는 **실패 0 인데 RPS 는 절반**이다.

| 정의 | c=50·pool=10 판정 | 성격 |
|---|:--:|---|
| **ㄱ 실패(DeadlineExceeded) 발생** | 정상 | 보수적. c=50 엔 cliff 가 **없다**고 나온다 |
| **ㄴ plateau RPS 의 90% 미만** | **무너짐** | 열화를 잡는다. c=50 에도 cliff 가 있다 |
| ㄷ p99 가 SLO 초과 | — | **SLO 가 아직 없다**(28-remaining-work-plan 미결) |

> ✅ **확정 (2026-08-08, 사용자 confirm): ㄴ + ㄱ 병기.** 주 판정은 ㄴ(각 c 에서 pool 을 충분히 키웠을 때의 plateau RPS 를 기준선으로 삼고, 그 90% 미만이면 cliff 아래로 본다), 실패율은 보조 지표로 같이 적는다. ㄱ 만 쓰면 "c=50 엔 절벽이 없다"는 결론이 나오는데, 위 표를 보면 **그건 절벽을 못 본 것이지 없는 게 아니다.**
>
> ⚠️ 90% 는 임의로 고른 숫자다. 근거가 있는 값이 아니라 **판정선을 미리 못박아 사후에 유리하게 고르지 않으려는 장치**다. 문서에 그렇게 적는다.

ㄷ 를 못 쓰는 게 곁가지로 하나 드러난다 — **이 프로젝트엔 아직 SLO 가 없다.** 관측 스택을 세우고도 "얼마면 나쁜가"가 없다는 미결과 같은 자리다.

## 3. 측정 설계

### 3-1. 격자 vs 이분탐색

전수 격자(c 5개 × pool 6개 = 30 run)는 **붕괴 구간에서 비싸다.** c=100·pool=10 이 RPS 5.9 였는데, `-n 2000` 이면 그 한 판에만 **약 5.6분**이 든다. 붕괴 쪽으로 갈수록 더 느려진다.

> 🟢 **추천: c 별 이분탐색.** 각 c 에서 pool 을 이분으로 좁힌다(범위 5~20). run 수가 30 → **약 15** 로 준다.
>
> 판수가 c 마다 다르다 — **아래쪽 c 는 싸게 끝난다.** c=10·20 은 양 끝점(pool=5·20)이 둘 다 멀쩡하면 *"이 구간엔 절벽 없음"* 으로 2판에 종료된다. 반대로 c=100 은 이분을 끝까지 돌아 4판쯤 든다.
>
> ⚠️ 이분탐색은 **cliff 가 단조롭다(작은 풀일수록 나쁘다)는 가정**에 의존한다. §5-1(7) 의 c=5 이상현상처럼 비단조 구간이 나오면 가정이 깨진다. 그래서 **각 c 마다 양 끝점(pool=5, pool=20)을 먼저 재서 단조성을 확인**하고 들어간다.

### 3-2. 파라미터

| | 값 | 근거 |
|---|---|---|
| c | **10 · 20 · 30 · 50 · 100** | 🔴 초안(30·50·70·100)에서 **현실 구간 10·20 을 추가하고 70 을 뺐다** — 아래 §3-2-1 |
| pool 탐색 범위 | 5 ~ 20 | 15 가 20/30 과 동급이므로 상한 20 이면 충분. 하한 5 는 이론 공식값(§5-1(6)) |
| 요청 수 | `-n 2000` | 지난번과 동일 — 종료 아티팩트 제거. ⚠️ 붕괴 구간은 한 판 5분+ |
| warmup | **c=3** | 🔴 지난번 교훈. warmup 동시성이 테스트 풀보다 크면 잔여 정체가 새어든다(§5-1(7) c=5 아티팩트). 최소 pool(5)보다 작게 고정 |
| 데이터 | pose_data 375만 행 | 지난번과 동일 조건이라야 비교 가능 |
| 리셋 | run 마다 `DELETE ... WHERE session_id` | `ceiling.ps1` 방식 |

### 3-2-1. 🔴 c 사다리 정정 — 초안은 «갈 일 없는 구간»만 재고 있었다

초안은 c 를 **30·50·70·100** 으로 잡았다. 지난번 측정과 비교하기 쉽다는 이유였는데, **목적과 어긋난다.**

`c` 는 사람 수가 아니라 **같은 순간에 서버가 처리 중인 요청 수**다. 사용자는 rep 이 끝날 때마다 배치를 보내고 그 사이엔 서버를 놓아주므로, **한 사람은 시간의 일부만 c 에 잡힌다.** 즉 c=100 을 만들려면 동시에 운동 중인 사람은 그보다 훨씬 많아야 한다.

이 프로젝트가 박아둔 환산([`./load-test-strategy.md`](./load-test-strategy.md) §4.2):

```
DAU 1,000 × 1.5세션/일 = 1,500세션/일 → 피크 동시 ~67세션
```

**그런데 «동시 세션 67» 은 «c=67» 이 아니다.** 67명이 동시에 운동 중이어도 각자 쉬는 구간이 있어 같은 순간의 in-flight 요청은 그보다 한참 적다. 같은 문서 §4.4 도 *"DAU 1,000 으로는 throughput 스토리 못 만듦"* 이라고 적어놨다.

> ⚠️ **정확한 환산 배수는 못 박는다.** rep 간격을 실측한 적이 없고 R 도 아직 합성 가정치(R=25)라, "세션 N개 = c 얼마"를 계산할 근거가 없다([`./load-test-strategy.md`](./load-test-strategy.md) §7). 확실한 건 **방향뿐**이다 — c=100 은 이 앱의 목표 규모에서 이미 **과부하 구간**이다.

**그래서 사다리를 이렇게 바꾼다:**

| 사다리 | 재는 것 | 판정 |
|---|---|---|
| ~~30·50·70·100~~ | 과부하 구간만 | ⚠️ *"우리가 실제로 있는 자리"* 가 통째로 빠진다 |
| **10·20·30·50·100** | 현실 구간 + 과부하 구간 | 🟢 채택 (2026-08-08, 사용자 confirm) |

**70 을 뺀 이유**: 50 과 100 사이를 촘촘히 보는 것보다 아래쪽을 여는 게 목적에 맞고, 판수를 늘리지 않기 위해서다.

**10·20 은 싸다.** 붕괴가 안 나므로 판당 수십 초에 끝난다 — 판수는 늘어도 시간은 별로 안 는다. 그리고 이 두 레벨이 **결론의 성격을 바꾼다**: *"현실 부하 구간에서는 절벽이 아예 안 보인다"* 를 데이터로 말할 수 있으면, 그게 `pool=15` 라는 현재 값의 진짜 근거가 된다.

> 🔴 **거꾸로, 10·20 에서도 절벽이 보이면 그건 훨씬 큰 사건이다** — 현재 배포된 값이 현실 부하에서 위태롭다는 뜻이 된다. 그 경우를 대비해 판정선(§2)을 **미리** 정해뒀다.

### 3-3. 산출물

- **표**: c × cliff 위치 (이 실험의 본체)
- **그래프**: 붕괴 순간의 pending·acquire 곡선 — 아래 §4 구성이면 **덤으로 같이 나온다**

## 4. 인프라 — 3대를 추천하는 이유

| 인스턴스 | 스펙 | 역할 |
|---|---|---|
| DB | `t4g.medium` (2vCPU/4GB) | self-managed MySQL. 버퍼풀 768M, **컨테이너 `--memory` 3GB** |
| App | `t4g.medium` (2vCPU/4GB) | 백엔드 + ghz. DB 와 같은 VPC 사설망 |
| **obs** | `t4g.small` (2vCPU/2GB) | **Prometheus + Grafana. 이번에 추가** |

> 🟢 **3대를 추천하는 진짜 이유는 비용이 아니라, «수치냐 그래프냐» 딜레마가 사라지기 때문이다.**
>
> 로컬(2코어 동거)에서는 관측 스택을 켜면 측정이 오염돼 둘 중 하나를 골라야 했다([`../../monitoring/README.md`](../../monitoring/README.md)). **분리 배포에서는 obs 가 자기 인스턴스에 있으므로 App·DB 의 코어를 전혀 안 먹는다** — cliff 수치와 붕괴 그래프를 **같은 판에서 동시에** 얻는다. README 가 *"관측 스택만 다른 장비에서 띄우는 게 맞다"* 고 적어둔 그 구성이다.
>
> App 에 얹으면(2대 구성) Prometheus·Grafana 가 ghz·백엔드와 2vCPU 를 다퉈, **로컬에서 피하려던 오염이 그대로 재발한다.** 3대째 값은 시간당 약 30원이다.

⚠️ **지표 포트를 인터넷에 열지 않는다.** obs 는 같은 VPC 사설망에서 App 의 9090 을 긁고, Grafana 만 내 IP 로 제한한 SG 로 연다. `monitoring/README.md` 가 *"9090 을 노출하는 순간 whitelist 가 그대로 뚫린다"* 고 경고한 그 지점이다.

### 4-1. 🔴 지난번 함정 — 되풀이하지 않으려고 적는다

§5-1(7) 이 방법론적 함정으로 남긴 것:

1. **호스트 RAM 만 올리고 컨테이너 cgroup 캡을 안 풀면 그대로 OOM 재발.** t4g.small(1.8GB)에서 버퍼풀 2G 를 복붙해 인스턴스가 응답불능 → 재생성. 이후에도 `--memory` 1.2GB 캡 때문에 exit 137 이 두 번 더. **이번엔 처음부터 t4g.medium + 버퍼풀 768M + `--memory` 3GB 로 시작한다**
2. **EBS 20GB 가 시딩 중 가득 참** → **이번엔 처음부터 50GB**
3. **warmup 동시성 오염** → §3-2 대로 c=3 고정

## 6. 이 실험이 답하지 못하는 것 (미리 박제)

- **절대 RPS 는 여전히 참고용이다.** 프로덕션 RDS 가 아니라 self-managed MySQL on EC2 이고, 페이로드도 실제와 다른 합성 JSON 이다([[project_synthetic_data_distribution_limit]] 와 같은 결의 한계)
- **cliff 가 왜 그 자리인지**는 안 나온다. 위치만 나온다. 원인(DB 코어 포화 vs 락 대기 vs 네트워크)을 가르려면 별도 측정이 필요하다
- **c=200 이상**은 안 본다. DAU 1,000 가정에서 현실성이 낮고, 판당 시간이 폭발한다
- **pool 11~14 의 c=100 정밀화**는 이 실험의 목적이 아니다 — §5-1(8) 이 *"비용 대비 실익 낮음"* 으로 이미 기각했고, 그 판단을 뒤집을 새 근거는 없다. 이번에 c=100 을 다시 재면 부산물로 좁혀질 수는 있다

> ✅ **실행 후 대조 (2026-08-08)**: 네 줄 중 **1·3은 그대로 맞았고**(절대 RPS 는 여전히 참고용, c>100 은 안 봤다), **2는 절반만 뒤집혔다** — *"cliff 가 왜 그 자리인지는 안 나온다"* 고 적었는데 **자리 자체가 없었다.** 대조군이 답한 것은 *"왜 (옛 코드와 달리) 절벽이 안 보이나"* 까지고(다운샘플 R=5 가 풀을 병목에서 빼냈다), 🔴 **«그럼 지금 병목은 무엇이냐» 는 여전히 미답이다** — 초판이 이 괄호에 *"CPU 병목"* 이라고 적은 것은 §0-1 에서 철회했다. **4는 무의미해졌다** — 정밀화할 절벽이 없다.
>
> 🔴 **미리 못 박은 한계 하나가 빠져 있었다**: 이 문서는 **"측정 대상 코드가 지난 실험 이후 바뀌었는지"** 를 한 번도 묻지 않았다. §1 을 "이미 아는 것"으로 놓고 시작한 것 자체가 그 누락이다. 다음 재측정 설계에는 *"직전 측정과 코드가 같은가"* 를 §1 에 넣는다.
