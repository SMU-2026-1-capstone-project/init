## 0. 한 줄 요약

**«구조를 갈아엎어야 하나» 의 답은 «한 곳만» 이다.** Spring 은 무상태라 대수를 늘릴 수 있고
DB 는 아직 천장 아래다. 막는 것은 **AI 의 세션 상태가 프로세스 메모리에 있다**는 사실 하나다
([`session_state.py:286`](../../ai-server/app/grpc/session_state.py) `SessionStateRegistry` — `threading.Lock` + 프로세스 로컬 dict).

그리고 그 상태의 **모양**이 답을 좁힌다. 상태가 «카운터» 였다면 외부화(ㄱ)가 정석이지만,
여기 있는 것은 **프레임마다 갱신되는 누적 윈도우**다. 그래서 🟢 **ㄴ(세션 어피니티 + 최소 체크포인트)**
를 추천한다 — 게다가 이 저장소는 그 체크포인트에 쓸 **재부착 경로를 이미 갖고 있다**(`ReattachAnalysis`, #74).

🔴 **gRPC 는 «고려사항» 이 아니라 «작업 항목» 이다**(§5). HTTP/2 는 커넥션을 오래 쓰기 때문에
L4 로드밸런서 뒤에서는 **요청이 아니라 커넥션 단위로** 붙는다 — 어피니티를 설계하기도 전에
원치 않는 어피니티와 쏠림이 먼저 생긴다.

## 1. 언제 필요한가 — 숫자로

가정식은 [`ai-receive-path-scaling.md:236-245`](./ai-receive-path-scaling.md) 의 복원식을 그대로 쓴다.
**이 식의 `p=0.18`(피크 1시간 집중도)은 어디에도 안 적혀 있던 가정을 역산으로 복원한 값**이라,
아래 표의 «필요 대수» 는 그 가정 위에 있다.

```
피크 동시 세션 = DAU × 1.5(세션/일) × 0.18(피크 집중도) × 0.25(세션 15분/60)
               = DAU × 0.0675
```

| DAU | 피크 동시 | AI 필요 대수 (배포 구성 천장 **89~105세션/대**) | 판정 |
|---:|---:|---|---|
| 1,000 (현 가정) | **67** | 1대 | ✅ 지금 구조로 버틴다 (67 < 89) |
| 5,000 | 338 | 4대 (338 ÷ 89~105) | 🔴 **2대째부터 성립 안 함** |
| 10,000 | **675** | **7~8대** | 🔴 같은 벽, 더 크게 |

> 천장 **89~105세션/대**는 [#385](https://github.com/Shadowfit/init/issues/385) 가 정정한 **배포 구성**의 값이다.
> 예전에 인용되던 156세션은 **AI 단독 박스**(in-process rig · HTTP 없음 · 동거 없음) 값이라 여기 쓰면 안 된다.

**즉 벽은 «성능» 이 아니라 «대수를 못 늘린다» 이다.** 박스를 키우는 것으로는 상수배만 벌고,
그 상수배도 [#385](https://github.com/Shadowfit/init/issues/385) 가 보인 대로 생각보다 작다.

## 2. 지금 상태 — 사실만

### 2-1. 무엇이 «세션 상태» 인가

[`session_state.py`](../../ai-server/app/grpc/session_state.py) 의 `SessionState` 가 들고 있는 것:

| 필드 | 성격 | 확장 관점에서의 의미 |
|---|---|---|
| `current_rep_frames` (`deque(maxlen=60)`) | **프레임마다 갱신되는 누적 윈도우**. 원소가 `PerRepFrame`(랜드마크 **JSON 문자열** 포함) | 🔴 외부화 비용이 여기서 결정된다 |
| `reference_angles` | 세션 시작 시 1회 적재, 이후 읽기만 | 공유 캐시로 빼기 **쉬운** 부분 |
| `rep_count` · `rep_state` | 분석기 상태 머신 | **체크포인트의 본체** — 재부착이 이미 복원한다 |
| `session_nonce` | 소유권 비밀값 (#187 (d)) | 프레임을 받는 **모든** 인스턴스가 볼 수 있어야 검증이 산다 |
| 유입 데드라인(`accept_frame`) | 세션당 3.33fps 상한 (`MIN_FRAME_INTERVAL_SEC = 0.300`) | 인스턴스가 갈리면 **상한도 갈린다**(#162 와 같은 결) |

⚠️ **세션당 상태 크기는 미측정이다.** 프레임 하나가 랜드마크 JSON(부하 rig 기준 ~2KB)을 들고
60개까지 쌓이므로 «100KB 대» 라는 산술은 나오지만, 그 산술을 값으로 쓰면 안 된다 —
[#229](https://github.com/Shadowfit/init/issues/229) 가 «AI 메모리 유도식이 검출기만 센다(프레임 버퍼·파이썬 힙 미측정)» 로
열어둔 자리가 정확히 이것이다.

### 2-2. 경로마다 프로토콜이 다르다 — 이게 설계를 가른다

| 경로 | 프로토콜 | 지금 | N대가 되면 |
|---|---|---|---|
| 프론트 → AI (**프레임**, 세션당 800~1,350회 [#92](https://github.com/Shadowfit/init/issues/92)) | **HTTP POST** ([`pose.py:49`](../../ai-server/app/api/endpoints/pose.py) · [`sync.py:40`](../../ai-server/app/api/endpoints/sync.py)) | 한 대로 감 | **세션 소유 인스턴스로 가야 함** |
| Spring → AI (**제어**: Start/Stop/Reattach) | **gRPC** | 주소가 환경변수 하나 ([#285](https://github.com/Shadowfit/init/issues/285)) | **소유 인스턴스로 정확히** 가야 함 |
| AI → Spring (콜백) | gRPC | 한 대로 감 | Spring 은 무상태 → **분배만** 되면 됨 |

🔴 **두 방향이 같은 인스턴스로 모여야 한다.** 프레임은 프론트에서, 제어는 Spring 에서 오는데
둘 다 «그 세션을 들고 있는 한 대» 를 찾아야 한다. 지금은 한 대뿐이라 이 요구가 안 보인다.

### 2-3. 🔴 확인: gRPC 프록시는 지금 **아예 없다** (2026-08-28)

`nginx-ai/default.conf` 에 `grpc_pass` 가 없다 — nginx-ai 는 HTTP 프레임 경로(`/pose`)만
처리하고 gRPC 는 그 앞을 아예 안 거친다. `docker-compose.yml:104` 의
`AI_SERVER_HOST: shadowfit-ai` 가 Spring 이 gRPC 로 붙는 유일한 주소이고, 컨테이너 이름을
Docker 내장 DNS 로 직접 찾아간다. 즉 §5-1 이 필요하다고 말하는 「요청 단위 분배」가
**아직 착수 전이 아니라 그 자리 자체가 비어 있다.**

## 3. 세 안

### ㄱ. 상태 외부화 — AI 를 진짜 무상태로

세션 상태를 공용 저장소(Redis 등)에 두고, 어느 인스턴스가 프레임을 받아도 읽어서 처리한다.

| | |
|---|---|
| 좋은 점 | 라우팅이 **필요 없다**. 인스턴스가 죽어도 세션이 안 죽는다. 오토스케일이 자연스럽다 |
| 🔴 대가 | **프레임마다 read-modify-write** 가 붙는다. 피크 675세션 × 3.33fps ≈ **2,250 RMW/s**, 그때마다 위 누적 윈도우를 왕복해야 한다 |
| 🔴 정합성 | 같은 세션의 프레임이 두 인스턴스에 동시에 닿으면 윈도우 갱신이 경합한다 — 지금 `threading.Lock` 이 하던 일을 **분산 락**이 대신해야 하고, 그건 프레임 경로에 붙는다 |
| 완화 | 상태를 쪼개 «윈도우는 로컬, 요약만 외부» 로 가면 비용이 준다. **다만 그건 사실상 ㄴ 의 변형이다** |

### ㄴ. 🟢 세션 어피니티 + 최소 체크포인트

세션 id 로 인스턴스를 **결정적으로** 고르고(해시 링), 상태는 지금처럼 로컬에 둔다.
대신 «죽었을 때 이어붙일 최소한» 만 밖에 남긴다.

| | |
|---|---|
| 좋은 점 | **프레임 경로가 지금과 같다** — 추론 앞에 네트워크 왕복이 안 붙는다. 코드 변경 면적이 작다(상태 구조를 안 건드린다) |
| 좋은 점 | **복구 경로가 이미 있다** — `ReattachAnalysis`([#74](https://github.com/Shadowfit/init/issues/74))가 rep 카운트 복원까지 한다. 「인스턴스 사망 = 세션 전멸」이 아니라 「재부착 + 진행 중 rep 손실」로 떨어진다 |
| 🔴 대가 | **라우팅이 인프라 작업이 된다**(§5). 그리고 그 라우팅이 **두 경로 모두**에 필요하다 |
| 🔴 대가 | 세션 길이가 15분이라 **리밸런싱이 즉시 안 된다** — 대수를 늘려도 기존 세션은 옮겨가지 않는다(해시 링이 바뀌면 오히려 끊긴다). 스케일아웃 효과가 «다음 세션부터» 나타난다 |
| 열린 것 | 체크포인트를 **어디까지** 남길지 (rep 카운트만 / 진행 중 윈도우까지). 후자면 ㄱ 의 비용이 부분적으로 돌아온다 |

### ㄷ. 상태를 클라이언트로

프론트가 세션 컨텍스트를 들고 매 호출에 실어 보낸다. 서버는 완전 무상태.

| | |
|---|---|
| 좋은 점 | 서버 쪽이 가장 단순해진다 |
| 🔴 대가 | **신뢰 경계가 무너진다.** [#187](https://github.com/Shadowfit/init/issues/187) 계열(남의 세션에 끼어들기)이 그대로 커지고, `session_nonce` 로 막아둔 것이 «클라가 보낸 상태를 믿는다» 로 되돌아간다 |
| 🔴 대가 | 페이로드가 는다 — 프레임마다 윈도우를 실어 보내면 유입 대역이 배로 뛴다 |
| 판정 | ❌ **이 프로젝트에서는 후보가 아니다.** 위 둘은 트레이드오프지만 이건 이미 닫은 결정(#187)을 되돌린다 |

## 4. 🟢 추천 — ㄴ, 근거 셋

1. **상태의 모양이 정한다.** 외부화가 정석인 것은 상태가 작고 원자적일 때다. 여기 있는 것은
   프레임마다 갱신되는 **누적 윈도우**라, ㄱ 는 추론 앞에 왕복과 분산 락을 얹는다 —
   [`ai-receive-path-scaling.md`](./ai-receive-path-scaling.md) 가 재던 «수신 경로의 천장» 을 스스로 낮추는 방향이다.
2. **복구 원시함수가 이미 있다.** ㄴ 의 가장 큰 약점은 «인스턴스가 죽으면 그 위 세션이 죽는다» 인데,
   재부착([#74](https://github.com/Shadowfit/init/issues/74))이 그 자리를 절반 막아 둔다. **없는 것을 만드는 게 아니라 용도를 넓히는 일**이다.
3. **유입 상한이 예산을 만든다.** `MIN_FRAME_INTERVAL_SEC = 0.300` 이 세션당 3.33fps 를 강제하므로
   세션당 부하가 위로 안 튄다 — 해시 링의 «한 노드에 몰림» 이 그만큼 덜 위험하다.

> ⚠️ 이 추천은 **지금 상태 구조**를 전제한다. 만약 나중에 윈도우를 서버가 안 들고 있어도 되게
> (예: rep 판정을 프레임 단위 순수 함수로) 바꾸면 ㄱ 가 다시 매력적이 된다. 그때 이 문서를 다시 열 것.

## 5. 🔴 gRPC 가 만드는 작업 항목

«어차피 로드밸런서 뒤에 두면 되지» 가 gRPC 에서는 성립하지 않는다.

| # | 무엇 | 왜 |
|---|---|---|
| 1 | **요청 단위 분배가 필요하다** | gRPC 는 HTTP/2 커넥션을 오래 쓴다. L4 LB 는 **커넥션**을 고르므로, 채널 하나가 한 인스턴스에 못 박히고 나머지는 논다. 클라이언트 사이드 LB(리졸버) 또는 Envoy·Linkerd 급 프록시가 **전제**다 |
| 2 | **세션 id 를 라우팅 키로 승격** | 어피니티는 그 위에 얹으면 된다(예: 프록시의 ring-hash). gRPC 쪽은 **메타데이터**에 실으면 되고, 그 배선은 이미 있다(correlation id 를 메타데이터로 흘린다) |
| 3 | 🔴 **프레임 경로는 gRPC 가 아니다** | 프론트→AI 는 **HTTP POST** 이고, 지금 `sessionId` 가 **본문(JSON)** 에 있다. L7 해싱을 하려면 **헤더나 경로로 올려야** 한다 — 작지만 API 변경이고, 프론트와 같이 움직여야 한다 |
| 4 | **«주소 하나» 가정을 깬다** | [#285](https://github.com/Shadowfit/init/issues/285) 가 정리한 `AI_SERVER_HOST` 는 한 곳을 가리킨다. N대가 되면 디스커버리 문제로 바뀐다 — 코드보다 설정 쪽 면적이다 |
| 5 | ~~선결: [#206](https://github.com/Shadowfit/init/issues/206)(deadline 미전파)~~ → ✅ **닫혔다 (2026-08-23)** | 홉이 하나 늘면 예산 미전파의 대가가 커진다 — 프록시가 재시도하면 **뒤에서 일이 두 번 돈다**. 이제 AI→Spring 에 데드라인이 걸리고([#462](https://github.com/Shadowfit/init/pull/462)) 서버는 취소를 본다. 🔶 **다만 그 5초는 «hang 을 잡는 그물» 이지 «예산» 이 아니다** — 앱 경로 실측 p95 가 213ms 인데 5초는 그 20배가 넘는다. 프록시가 끼는 시점에 **예산으로 다시 정해야 한다**(그때 이 표의 이 줄이 다시 열린다) |

### 5-1. 분배 수단 — 클라이언트 사이드 LB vs 프록시(Envoy 등) (2026-08-28 추가)

먼저 층을 정리한다 — **Netty 와 gRPC 는 경쟁 관계가 아니다.** Netty 는 저수준 비동기 I/O
프레임워크고, Spring 쪽 grpc-java 는 기본적으로 Netty 를 트랜스포트로 쓴다(`grpc-netty`).
즉 지금 Spring↔AI 통신은 이미 **"gRPC 위에서 Netty 가 돈다"** 는 조합이라, 여기서 실제로
고를 것은 "Netty 냐 gRPC 냐"가 아니라 **"gRPC 트래픽을 누가 여러 인스턴스에 분배하느냐"**다.

| | 클라이언트 사이드 LB | 프록시(Envoy 등) |
|---|---|---|
| 뭐가 하나 | grpc-java 의 resolver/`LoadBalancer` 가 Spring 프로세스 안에서 직접 라우팅 | 별도 프록시가 앞단에서 요청 단위로 분배 |
| 홉 | 안 늘어남 | 한 홉 더 생김(레이턴시·운영 구성요소 추가) |
| 이 repo 적합성 | 🟢 세션 id 를 메타데이터에 얹기만 하면 됨 — correlation id 를 이미 메타데이터로 흘리는 배선이 있다(§5 표 #2). 면적이 작다 | ring-hash 등 라우팅 로직을 프록시가 대신 해준다. 대신 Envoy 는 **C++** 이라 Netty 와 무관한 별개 컴포넌트가 하나 늘어난다 |
| nginx-ai 와의 관계 | 무관 — nginx-ai 는 그대로 HTTP 프레임 경로(`/pose`)만 맡는다 | **같이 쓴다.** nginx-ai 는 HTTP 프레임 경로를, Envoy 는 gRPC 제어 경로를 맡아 **역할이 겹치지 않는다.** (Envoy 는 일반 L7 프록시라 nginx-ai 를 흡수해 통합할 수도 있지만, 그건 «프록시를 들이니까 김에» 가 아니라 별도 근거가 있어야 할 결정이다) |

🟢 **기울어지는 쪽은 클라이언트 사이드 LB다** — §4 의 추천 근거(복구 원시함수가 이미 있다·
메타데이터 배선이 이미 있다)와 결이 같고, 운영 구성요소를 새로 안 늘린다. **다만 이건
추천이지 결정이 아니다** — §7 체크박스는 그대로 미결정으로 둔다.

#### nginx-ai 와 Envoy 는 "뭘 나눠주냐"가 아니라 "어떻게 아냐"가 다르다 (2026-08-28 추가)

**nginx-ai — 고정된 지도.** `X-AI-Worker` 헤더 값으로 워커별 포트에 매핑하는 표를
config 파일에 **사람이 미리 다 적어뒀다**(§1 인용, `nginx-ai/default.conf`의 워커 0~9 map).
백엔드가 몇 대 살아있는지 nginx는 모른다 — config를 고치고 리로드해야 반영된다.

**Envoy(gRPC 프록시) — 실시간으로 판단.** 두 가지가 다르다:
1. **서비스 디스커버리 + 헬스체크** — 지금 살아있는 백엔드 집합을 스스로 추적한다.
   인스턴스가 죽으면 자동으로 빼고, 뜨면 자동으로 넣는다. nginx-ai처럼 표를 사람이
   안 적는다.
2. **요청 내용을 보고 매번 계산** — gRPC 메타데이터의 session_id 같은 값으로
   ring-hash를 돌려 "이 요청은 어디로" 를 그때그때 정한다. nginx-ai의 map은 헤더 값 →
   고정 포트라는 **정적** 대응인 반면, 이건 **백엔드 집합이 바뀌어도 같은 세션이 최대한
   같은 곳으로 가게** 계산을 다시 한다.

**왜 이 repo에서 아직 nginx-ai만으로 충분한가** — `AI_WORKER_COUNT`(지금 3)가 거의 안
바뀌고 배포 시점에 이미 다 아는 값이라, 고정 지도로 충분하다. gRPC 쪽(§1의 VM 여러 대
시나리오)은 VM이 늘었다 줄었다 할 수 있고(오토스케일 등) 세션마다 다른 VM으로 보내야
하므로, 고정 지도가 아니라 "그때그때 계산"이 필요해진다 — 그 필요가 §5-1의 갈림길(클라이언트
사이드 LB vs Envoy) 자체다.
