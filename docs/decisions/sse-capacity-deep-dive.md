# SSE 캐파시티 깊이 파기 — 트레이너 모니터링이 실제로 어떻게 동작하나

## 0. 이 문서가 여는 것

`trainer-live-monitoring.md` §8은 "캐파시티 실측"을 5~10h짜리 한 줄로만 잡아뒀다. 그런데 이 프로젝트가 다른 축(AI GIL 천장, DB pool sizing, DELETE 파편화)을 팠던 방식은 **"몇 개까지 버티나"가 아니라 "왜 거기서 꺾이는가"**였다([[feedback_tps_over_dau_justification]]). SSE도 같은 기준을 적용하면, "캐파시티 실측"은 사실 성격이 다른 다섯 개의 질문으로 쪼개진다 — 그중 셋은 성능 측정이고 둘은 [`four-axes-depth-experiments.md`](./four-axes-depth-experiments.md) §2가 말하는 **"내가 만든 게 정말 그렇게 동작하나"**를 확인하는 실패 주입에 가깝다.

## 1. 다섯 갈래

### 1-1. 연결당 스레드 모델 — SseEmitter가 정말 async로 도는가

**질문**: Spring MVC(blocking)에서 컨트롤러가 `SseEmitter`를 반환하면 이론상 Tomcat이 요청 스레드를 async dispatch로 반납하고 NIO로 연결만 유지한다. **이 코드에서 실제로 그런가?**

**반증 조건**: 동시 SSE 연결 수를 늘렸을 때 Tomcat 요청 처리 스레드 풀(`server.tomcat.threads.max`) 사용량이 연결 수에 비례해 올라가면 — async dispatch가 이름만 걸려 있고 실제로는 스레드가 잡혀 있다는 뜻. `emitter.send()`를 호출하는 지점(`PoseDataService` 콜백 스레드)이 커넥션 풀·트랜잭션 스레드와 얽혀 있는지도 같이 봐야 한다.

**측정 방법**: 커넥션 수를 스윕하며 Tomcat 스레드풀 사용량·JVM 스레드 덤프를 같이 뜬다. AI 축의 스레드 분해 계측(`ai-process-ceiling-cause.md`)과 같은 패턴.

### 1-2. 캐파시티 천장 — 어디서, 왜 꺾이는가

**질문**: 동시 SSE 연결이 N개일 때 처리량/지연이 꺾이는 지점이 있다면 원인이 (a) Tomcat 커넥터 설정(`maxConnections`), (b) 스레드풀 고갈, (c) 힙(emitter 객체+내부 버퍼 누적) 중 무엇인가.

**반증 조건**: "N개에서 꺾인다"는 관찰 자체는 답이 아니다 — [[project_ai_ceiling_gil_n3_closed]]에서 "16 중 9.5"의 답이 "한 프로세스라서(GIL)"로 갈렸던 것처럼, 여기서도 **셋 중 어느 것을 고쳐야 천장이 올라가는지**가 실제 산출물이다. 힙이 원인이면 커넥터 설정을 늘려도 소용없고, 커넥터 설정이 원인이면 스레드풀을 늘려도 소용없다 — 격리해서 하나씩 반증해야 한다.

**측정 방법**: 커넥터 설정·스레드풀 크기·힙 크기를 각각 고정하고 나머지를 스윕하는 2×2류 격자([[feedback_measure_design_needs_repeats]] — 팔당 반복 필수).

### 1-3. 백프레셔 — 느린 컨슈머가 다른 세션에 영향을 주는가

**질문**: `trainer-live-monitoring.md` §8-5의 현재 계획은 "실패 시 드롭"뿐이다. 트레이너 브라우저가 느리거나 네트워크가 끊기기 직전일 때, `emitter.send()`가 블로킹되면서 **다른 트레이너/세션의 중계까지 지연시키는가**?

**반증 조건**: 느린 컨슈머 1개를 인위적으로 만들어 놓고(예: 응답을 안 읽는 클라이언트) 정상 컨슈머의 지연이 같이 올라가면 — 격리가 안 되고 있다는 뜻. 이건 성능 측정이 아니라 **설계상 격리된다고 가정한 것이 실제로 격리되는지 실패를 주입해서 확인하는 것**이라 [`four-axes-depth-experiments.md`](./four-axes-depth-experiments.md)의 방법론에 가깝다.

### 1-4. 리버스 프록시·타임아웃 상호작용

**질문**: 실제 배포 스택(nginx/ALB 등)이 앞에 있을 때, SSE처럼 오래 열려 있는 HTTP 연결을 프록시가 버퍼링하거나 idle timeout으로 끊지는 않는가.

**반증 조건**: 로컬 실측으로는 절대 안 보인다 — 실제 배포 스택까지 가야 드러나는 항목이라 [[project_unattended_aws_round_recipe]]와 같은 방식의 AWS 실측이 필요하다. 값싸게(1라운드) 확인 가능한 항목이므로 우선순위는 낮아도 순서상 빨리 치울 수 있다.

### 1-5. 재연결·유실 처리

**질문**: 브라우저 `EventSource`는 끊기면 `Last-Event-ID`로 자동 재연결한다. 재연결 사이에 놓친 rep 이벤트를 다시 보내는 로직이 지금 설계엔 없는데, "놓쳐도 그만"으로 둘 근거가 있는가, 아니면 짧은 재생 버퍼가 필요한가.

**반증 조건**: 이건 측정보다 설계 결정에 가깝다 — 트레이너 유스케이스(위험 자세 경고)에서 유실된 이벤트가 놓쳐도 되는 성격인지부터 확인해야 실험 여부가 갈린다.
