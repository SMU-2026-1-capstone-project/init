# Decision: 진행 중 세션이 있는 회원의 탈퇴 처리

상태: **분석/추천 (결정 전)** — 착수는 사용자 confirm 후
작성: 2026-08-03
배경: [이슈 #87](https://github.com/Shadowfit/init/issues/87) 고아 `pose_data` 행 조사 중 발견. "세션 진행 중 탈퇴가 애초에 가능한가"를 확인하다 **서버가 안 막는다**는 것과, 같은 코드베이스의 세션 단건 삭제는 **막고 있다**는 방침 불일치가 드러났다.

## 1. 문제

두 삭제 경로의 방침이 다르다.

| 경로 | 진행 중(IN_PROGRESS)이면 | 근거 |
|---|---|---|
| 세션 1건 삭제 | **거절 (409)** | `SessionService.java:397-399` `SESSION_DELETE_NOT_ALLOWED` |
| 회원 탈퇴 | **그냥 삭제** | `MemberService.java:93-119` — 상태 확인 없음 |

→ *"진행 중인 세션 1건은 못 지우는데, 그 세션을 가진 회원 전체는 지울 수 있다."*

**의도적 차이가 아니다.** 가드는 `9c04205`(개별 세션 삭제 신설)에서 들어왔고 `deleteAccount`는 레포 이관 이후 손대지 않았다. 나중에 생긴 방침이 기존 경로에 소급되지 않은 드리프트다.

### 1-1. 이게 #87과 어떻게 얽히나

#87의 안전 논거가 두 단계로 물러났다:

1. ~~"창이 좁다"~~ → 실측으로 폐기 (p50 58~149ms)
2. "세션 중 탈퇴가 드물다" → 남은 유일한 근거

그런데 2번은 도메인 가정이라기보다 **"막혀야 하는데 안 막힌 것"** 이다. 이 문서의 결정은 #87의 수정안 **ㄹ**에 해당하며, 기존 ㄱ(락)·ㄴ(sweep)이 *"고아가 생긴 뒤"* 를 다루는 것과 달리 **한 단계 상류에서 유입을 줄인다.**

> ⚠️ **완전 대체는 아니다.** `savePoseDataBatch`는 세션의 *존재*만 보고 *상태*는 안 본다. 방금 종료된 세션에 마지막 배치가 뒤늦게 착지하는 경로는 어느 안을 골라도 남는다. 이 결정은 확률을 크게 낮출 뿐이며 ㄱ/ㄴ의 필요성을 없애지 않는다.

## 2. 공통 전제 — 락은 어느 안이든 필요하다

단순히 `existsByMemberIdAndStatus`만 부르면 확인과 삭제 사이에 새 세션이 시작될 수 있어 또 TOCTOU다. `SessionRepository.java:56-57` 주석이 이미 답을 적어뒀다:

> 회원당 활성 세션 1개 제약 — `MemberRepository.findByIdForUpdate`로 잠근 뒤 체크해야 TOCTOU 없이 안전함(단독 호출 시엔 레이스 존재).

`createSession`(`SessionService.java:95`)이 같은 락을 잡으므로, 탈퇴가 이 락을 쥐면 새 세션 생성이 직렬화된다. **필요한 부품은 전부 이미 있다** — `findByIdForUpdate`, `existsByMemberIdAndStatus`, `findIdsByMemberId`.

## 3. A안 — 거절 (409)

```java
memberRepository.findByIdForUpdate(member.getId()).orElseThrow(...);   // createSession 과 같은 락
if (sessionRepository.existsByMemberIdAndStatus(member.getId(), Status.IN_PROGRESS)) {
    throw new BusinessException(ErrorCode.WITHDRAWAL_BLOCKED_BY_ACTIVE_SESSION);  // 신규
}
```

| | |
|---|---|
| 🟢 **기존 방침과 일치** | 세션 단건 삭제(409)와 같은 규칙. "왜 이렇게 했나"에 답이 쉽다 |
| 🟢 **변경 면적 최소** | 락+체크 5줄, 신규 ErrorCode 1개. AI 안 건드림 |
| 🟢 **AI 결합 없음** | gRPC·outbox 경로 무관 |
| 🔴 **탈퇴를 막는다** | "앱 지우려는데 왜 운동을 마쳐야 하나" — 사용자 입장에서 납득이 어렵다 |
| 🔴 **좀비 세션에 갇힘** ⚠️ | 아래 참조 |

### 3-1. 🔴 좀비 세션 문제 — A안의 진짜 약점

앱이 죽거나 네트워크가 끊기면 세션은 `IN_PROGRESS`로 남고, `SessionTimeoutScheduler`가 **예상 운동시간 + 30분 버퍼** 뒤에야 `FAILED`로 걷어낸다(스쿼트 15분 기준 **~45분**).

그 사이 사용자는 **운동 중이 아닌데 탈퇴가 거부된다.** 사용자에게는 원인이 안 보이고, 고객 문의로 직결되는 형태다.

재부착 흐름(#59)으로 앱을 다시 열어 종료할 수는 있지만, (a) 앱을 지우려는 사용자에게 앱을 다시 열라는 요구고 (b) 재부착 자체에 미해결 이슈(#77)가 걸려 있다. **안내 문구로 때울 문제가 아니다** — 아래 셋 중 하나로 실제로 풀어야 한다.

### 3-2. 좀비 세션 완화책

**완화 ①: 이미 타임아웃 기준을 넘긴 세션은 통과시킨다**

`Session.isTimedOutAt(now, bufferMinutes)`가 이미 public 으로 있다(`Session.java:97`). 스케줄러가 아직 안 돌았어도 **기준을 지났으면 좀비로 보고** 탈퇴를 허용한다.

```java
boolean blocking = sessionRepository.findByMemberIdAndStatus(memberId, IN_PROGRESS).stream()
        .anyMatch(s -> !s.isTimedOutAt(now, defaultBufferMinutes));   // 아직 살아있는 것만 막는다
```

- 🟢 비용 0 (메모리 계산), 이미 있는 메서드 재사용
- 🟢 스케줄러 주기(1분)를 안 기다린다
- 🔴 **45분 이내 좀비는 여전히 막힌다** — 앱이 방금 죽은 경우가 정확히 그 케이스다. 부분 해결

**완화 ②: 활동 기반 판정** ⭐

`IN_PROGRESS`라는 *상태값*이 아니라 **데이터가 실제로 흐르는지**로 판단한다. 살아있는 세션은 rep 단위로 3~4초마다 배치가 들어오므로, 마지막 수신이 임계값(예: 60초) 이상 조용하면 죽은 세션이다.

```sql
SELECT MAX(created_at) FROM pose_data WHERE session_id = ?
```

- 🟢 **"운동 중"의 진짜 정의에 맞다.** 상태 플래그는 앱이 죽으면 갱신되지 않지만 데이터 흐름은 거짓말하지 않는다
- 🟢 **좀비 문제가 사실상 사라진다** — 진짜로 운동 중인 사용자만 막힌다
- 🟡 비용: 탈퇴 시 쿼리 1회. `idx_session_timestamp(session_id, timestamp_sec)`가 `created_at`을 커버하지 않아 해당 세션 행을 읽고, `created_at` 조건이 없어 파티션 pruning 도 안 걸린다. 다만 **탈퇴는 드문 경로**라 감수 가능
- 🟡 사용자가 세트 사이에 오래 쉬면 오판 가능 → 임계값을 넉넉히(60초+)
- 🔴 `last_activity_at` 컬럼을 세션에 두는 방식은 **쓰지 말 것** — 배치 저장마다 UPDATE 가 붙어 핫패스에 비용이 얹힌다. 이 결정의 취지(드문 경로에만 비용)와 정반대다

**완화 ③: B안으로 간다**

좀비가 A의 구조적 약점이라면 우회 대신 B를 고르는 것도 답이다.

### 3-3. ⚠️ 완화 ②가 A/B 선택을 바꾼다

**②를 넣으면 A와 B의 차이가 크게 좁혀진다.** 남는 차이는 *"진짜로 운동 중일 때 어떻게 할 것인가"* 뿐이고, 그건 정말 드문 케이스다.

그리고 **②는 B에도 필요하다** — 자동 종료를 할지 말지 판단할 때 같은 신호를 쓰게 된다(죽은 세션은 조용히 마감, 살아있는 세션은 AI 통보 필요). 즉 ②는 A/B 분기와 **독립적으로 값이 있는 작업**이다.

→ **A/B 결정 전에 ②를 먼저 하는 것이 합리적일 수 있다.** 그러면 A의 최대 약점이 사라진 상태에서 분기를 판단하게 된다.

## 4. B안 — 자동 종료 후 탈퇴

진행 중 세션을 먼저 마감(`FAILED`)하고 탈퇴를 진행한다. 타임아웃 스케줄러가 쓰는 경로(`markAsFailedIfStillInProgress`)를 재사용한다.

| | |
|---|---|
| 🟢 **탈퇴가 항상 성공** | 좀비 세션 문제가 원천적으로 없다. 사용자 권리 측면에서도 자연스럽다 |
| 🟢 **기존 경로 재사용** | 세션 마감은 타임아웃 스케줄러와 같은 메서드 |
| 🟡 **AI 상태 통보 필요** | 아래 참조 |
| 🔴 **변경 면적 큼** | AI 연동·실패 정책·테스트까지 |
| 🔴 **방침 불일치가 남는다** | 세션 단건 삭제는 여전히 409로 막는데 탈퇴는 자동 종료 → *두 경로가 여전히 다르다* (단, 이번엔 "의도적 차이"로 설명 가능) |

### 4-1. AI 상태 통보

AI는 세션 상태를 in-memory로 들고 있다(`session_state.py`). 마감을 안 알리면 **삭제된 회원의 세션 상태가 AI 메모리에 남는다.**

- 통보 수단: `StopAnalysis` gRPC
- 🔴 **실패하면?** 탈퇴는 사용자 권리라 AI 응답 실패로 막을 수 없다 → **AI 상태 누수를 감수**하거나 **재시도**해야 한다
- 🟢 **아웃박스가 이미 답을 갖고 있다**: `outbox_events.aggregate_id`에 FK를 걸지 않은 이유가 *"세션 삭제 시 CASCADE로 통보 이력까지 사라진다"*(`mysql/schema.sql:249-252`)였다. 즉 **회원이 지워진 뒤에도 outbox 행이 남아 재시도할 수 있다** — 이 시나리오를 위해 준비된 것처럼 맞아떨어진다
- 🟡 다만 `StopAnalysis` 응답의 `success=false` 처리는 #58에서 이미 문제됐던 지점이라 같이 봐야 한다

### 4-2. 마감을 어느 상태로?

`FAILED`가 자연스럽다(타임아웃과 같은 취급). `COMPLETED`로 하면 precompute-on-write가 돌아 **곧 지울 회원의 리포트를 생성**하는 낭비이자, 실패 가능한 작업을 탈퇴 경로에 끼워 넣는 셈이다.

## 6. 추천 (미confirm)

**완화 ②(활동 기반 판정) → A → (필요 시) B** 순서를 추천한다.

근거:
1. **②는 A/B 분기와 독립적으로 값이 있다**(§3-3). 어느 쪽을 고르든 필요하고, A의 최대 약점(좀비 세션)을 먼저 없애면 분기 판단이 깨끗해진다.
2. **지금 필요한 건 유입 차단이고, A가 그걸 즉시 한다.** #87의 확률 산정에서 지배적 미지수를 없애는 게 목적인데 A로 충분하다.
3. **A는 기존 방침과 일치**해서 방어가 쉽다. B는 두 경로를 다르게 두는 이유를 따로 설명해야 한다.
4. **A→B 승격은 가능하지만 역방향은 어렵다.** B를 먼저 하면 AI 연동이 얽혀 되돌리기 부담이 커진다.

⚠️ **②를 건너뛰고 A만 하는 것은 권하지 않는다.** 그 조합이 §3-1의 "운동 중이 아닌데 탈퇴가 거부되는" 상태를 그대로 남기고, 그건 실사용자가 붙는 순간 문의로 직결된다. ②의 비용(탈퇴 시 쿼리 1회)이 그 위험보다 훨씬 싸다.

**B로 가는 트리거는 그래도 박아둘 것** — 예: "②를 넣었는데도 좀비로 인한 탈퇴 실패가 관측되면", 또는 "진짜 운동 중 탈퇴 시도가 유의미하게 관측되면".
