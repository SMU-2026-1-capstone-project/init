## 0. 한 줄

**從 부하를 아무리 올려도 이 박스에서는 옆이 안 굶는다.** 자원이 남기 때문이다.
H3 를 시험하려면 부하가 아니라 **박스를 바꿔야** 하고, 그보다 먼저 **운영 박스가 몇 코어인지**를
답해야 한다 — 그 답에 따라 H3 는 «중요한 질문» 이거나 «성립하지 않는 질문» 이다.

## 1. 무엇이 관측됐나

2라운드에서 `ghz_*.json` 원문을 사후 회수해 從 부하의 지연 백분위를 얻었다
([결과 §4-1-b](../../loadtest/results/coresidency-aws-b-2026-08-16/README.md)).

| 세션 | 지표 | 팔 B (캡 없음) | 팔 C (캡) | C/B |
|---:|---|---:|---:|---:|
| **120** | p50 / p95 / p99 | 8.81 / 11.00 / 12.33 | 8.71 / 10.99 / 12.25 | 0.99× / 1.00× / 0.99× |
| 160 | p50 / p95 / p99 | 8.87 / 11.29 / 12.45 | 8.77 / 11.20 / 12.41 | 0.99× / 0.99× / 1.00× |

설계 §6 의 H3 반증 조건은 *"C 에서 Spring p99 가 B 와 차이 없다"* 이므로 **문언대로면 반증**이다.
그런데 **팔 B 에서도 옆이 안 아팠다**:

- ghz 달성 **18.9~19.0 rps**(목표 19) — 전 판, 두 라운드
- 성공률 **56,970 / 56,971**
- p99 최악 조건에서도 **11.9~13.9ms**

AI 가 천장을 치고 자기 지연이 p50 500ms 로 늘어나는 동안 Spring 은 계속 12ms 로 쳐냈다.
**지킬 것이 없었으므로 「캡이 지키는가」를 시험한 적이 없다.** H3 는 반증이 아니라 **미시험**이다.

---

## 2. 그래서 從 부하를 올리면 되나 — 계산해 보면 **안 된다**

「부하가 가벼워서 안 아팠으니 올리자」가 자연스러운 다음 수인데, 숫자를 넣으면 안 맞는다.

### 2-1. 從 부하 1 rps 가 옆에 얼마를 쓰나

2라운드 `docker stats` warm 창 평균에서 **팔 A(ghz 없음) ↔ 팔 B(ghz 19 rps)** 를 뺀다.
`100% = 1 vCPU`:

| 컨테이너 | 팔 A | 팔 B | 차 = ghz 몫 | rps 당 |
|---|---|---|---:|---:|
| Spring | 0.5~1.4% | 4.0~8.6% | 약 **5%** | **0.26%** |
| MySQL | 0.8~1.1% | 6.6~7.0% | 약 **5.7%** | **0.30%** |
| 합 | | | 약 **10.7%** | **0.56%** |

### 2-2. 옆이 굶으려면 얼마가 필요한가

박스는 **16 vCPU**, AI 가 plateau 에서 **8.7** 을 쓴다 → **7.3 vCPU 가 남는다.**
옆이 그 7.3 을 다 쓰려면:

```
7.3 vCPU ÷ 0.56%/rps  ≈  1,300 rps
```

**그런데 이 앱의 쓰기 경로 천장은 이미 실측돼 있다 — 649.4 RPS**
(다세션 100세션 조건, [`commit-count-and-mysql-metrics.md:36`](commit-count-and-mysql-metrics.md)).

```
從 부하가 자기 천장(649 rps)까지 가도 옆의 수요 = 649 × 0.56% ≈ 3.6 vCPU
남는 자원                                                    = 7.3 vCPU
                                                    3.6 < 7.3  →  안 굶는다
```

> **결론: 16 vCPU 박스에서는 從 부하를 자기 천장까지 올려도 옆이 굶지 않는다.**
> 부하를 올리는 것으로는 H3 의 조건을 만들 수 없다.

⚠️ **선형 가정을 하고 있다.** rps 당 CPU 가 부하가 커져도 일정하다고 봤는데, 실제로는 경합·
큐잉·그룹 커밋 상각 때문에 달라진다(다세션에서 `fsync/커밋` 이 0.16 으로 상각된 전례가 있다).
**34배 외삽이므로 방향 근거로만 쓰고 값으로 인용하지 말 것.**

### 2-3. 팔 C 의 캡도 애초에 안 물린다

팔 C 는 **Spring 4 · MySQL 4 vCPU** 캡이다. 위 계수로 그 캡이 물리는 지점은

```
Spring 400% ÷ 0.26%/rps ≈ 1,540 rps      MySQL 400% ÷ 0.30%/rps ≈ 1,330 rps
```

둘 다 **649 rps 천장 너머**다. 즉 **이 워크로드에서 팔 C 의 옆 캡은 어떤 현실적 부하에서도
발동하지 않는다.** 팔 C 에서 실제로 물린 것은 **AI 캡(8 vCPU) 하나뿐**이고, 그건 결과가
이미 보여준다(AI 792% ≈ 캡 800%).

## 3. 그러면 H3 는 무엇을 물었어야 했나

[#212](https://github.com/Shadowfit/init/issues/212) 의 원문은 *"AI·MySQL·관측이 서로 코어를
뺏는다"* 였다. **두 라운드가 그 전제의 절반을 이미 반증했다** — 뺏는 것은 AI 한 쪽뿐이고,
옆은 합쳐서 0.16 vCPU 를 쓴다. 서로 뺏는 상황이 아니다.

그렇다면 캡의 값어치는 「이웃 보호」가 아니라 다른 데 있을 수 있다:

| 캡의 후보 값어치 | 시험됐나 |
|---|---|
| ① AI 처리량을 예측 가능하게 깎는다 | ✅ **됐다** — CPU 91.1% → 처리량 92.4%, 두 라운드 재현 |
| ② 이웃을 굶주림에서 보호한다 (H3) | ❌ **조건이 안 생겨 미시험** |
| ③ AI 폭주(버그·무한루프)를 격리한다 | ❌ 시험 안 함. **①·②와 다른 실험**이다 |

③ 이 실은 운영에서 더 자주 쓰이는 논거인데 이 설계에는 없다. 별건으로 열 만하다.

## 4. 선택지

| 안 | 무엇 | 비용 | 답하는 것 | 위험 |
|---|---|---|---|---|
| **ㄱ** | **작은 박스에서 축소 격자** — `c7i.2xlarge`(8 vCPU) 에 같은 3팔, 레벨 축소 | 1~1.5h · 박스가 **더 싸다** | 자원이 실제로 부족한 조건이 생긴다: AI 수요 8.7 + 옆 수요 3.6 = **12.3 > 8** → 경합 발생 | AI 천장 자체가 달라져 2라운드와 직접 비교 불가 |
| **ㄴ** | **從 부하를 649 rps 근처로** (같은 16 vCPU 박스) | +12판 ~1h · 페이로드·부하기 손봐야 함 | §2 계산의 검산. 「그래도 안 굶는다」를 **관측으로** 확인 | 계산이 맞으면 **결과가 «차이 없음» 으로 또 끝난다** |
| **ㄷ** | ㄱ + ㄴ | 2~2.5h | 가장 확실 | 라운드가 길어진다 |
| **ㄹ** | **안 한다** — 「현실 부하·이 박스에서 이웃은 안 아프다」로 닫고 H3 를 접는다 | 0 | 관측 사실만 남긴다 | H3 영구 미시험. 단 **그 사실 자체가 결론**일 수 있다 |
| **ㅁ** | H3 를 **③(폭주 격리)** 으로 갈아끼운다 | 설계부터 | 캡의 실제 운영 값어치 | 새 설계 문서가 필요 |

**추천은 ㄱ 또는 ㄹ 이다** (결정은 사용자).

- **ㄱ 을 고르는 근거**: H3 를 답하고 싶다면 **부하가 아니라 박스를 줄이는 것이 유일하게
  성립하는 조작**이다. 그리고 더 싸다.
- **ㄹ 을 고르는 근거**: 「16 vCPU 에서 이웃은 굶지 않는다」가 **이미 답**이고, 운영이 16 vCPU
  라면 H3 를 시험할 이유가 없다.

**ㄴ 단독은 추천하지 않는다** — 계산이 맞으면 «차이 없음» 이 한 번 더 나오는 데 1시간을 쓴다.

## 5. 🔴 그 전에 답해야 할 것 — 운영 박스가 몇 코어인가

위 선택지는 전부 이 답에 종속된다.

| 운영 박스 | H3 의 지위 |
|---|---|
| **16 vCPU 급** | 남는 자원이 옆 수요보다 크다 → **H3 는 실무적으로 무의미.** ㄹ 이 맞다 |
| **8 vCPU 급** | AI 8.7 + 옆 3.6 = 12.3 > 8 → **경합이 실제로 일어난다.** ㄱ 이 맞고, 그 박스가 곧 시험 무대다 |
| **4 vCPU 급** | AI 혼자 박스를 넘긴다 → 캡보다 **수평 확장·AI 분리**가 먼저 질문이다 |

이 repo 는 지금까지 실측 박스를 **측정용으로만** 띄웠고(임시 생성 → 측정 → 삭제),
**운영 배포 대상 박스 사양이 문서에 없다.** 그래서 이 질문이 미결이다.

⚠️ 임의로 «8 vCPU 로 가정» 하지 않는다 — 그러면 그 가정이 그대로 근거 없는 기준값이 된다.
