## 0. 한 줄

**AI 를 N대로 늘리는 일은 「프록시를 앞에 두는 일」이 아니라 「세션이 어느 인스턴스에 사는지를
누가 정하고 누가 기억하고 누가 따라오는지」를 정하는 일**이고, 그 셋은 따로 못 정한다.

🔴 **그리고 지금은 안 해도 된다** — §1. 이 문서는 **하게 될 때 무엇이 걸려 있는지**를 미리 편다.

## 1. 기본값은 «안 한다» 다 — 두 가지 이유로 (그리고 그것을 뒤집는 조건 하나)

### 1-1. 필요 계산이 이미 나왔다

[`ai-receive-path-scaling.md` §3-ㄹ-1](./ai-receive-path-scaling.md) (2026-08-23):

```
천장     348 RPS ÷ 3fps = 동시 116세션 = 동시에 운동 중인 사람 116명
피크     DAU 1,000 × 1.5세션 × 0.18 × (15분/60) = 67명
```

**안 넘는다.** 🔴 단 두 가지 단서가 붙는다 — 여유는 인용되던 「2.3배」가 아니라 **1.7배**이고,
116 은 **AI 가 혼자 사는 박스**의 값이다. 동거하면 [**89~105세션**](./ai-coresidency-capacity.md)
으로 내려가 여유가 **1.3~1.6배**가 된다.

### 1-2. 세로가 아직 안 끝났다

같은 박스에서 **16 vCPU 중 9.5 만 쓴다.** 원인이 GIL 이면 **프로세스 분리로 같은 박스에서
배수가 나온다** — 그러면 이 문서 전체가 더 미뤄진다.
그것을 가르는 판이 **從 R10-a** 이고([`r10-loadgen-topology.md` §7](./r10-loadgen-topology.md)),
막던 것이 다 닫혀 **박스 하나만 남았다.**

> 📌 **순서 제안** — R10-a 를 먼저 돌리고, 거기서 세로 여지가 안 나오면 이 문서를 연다.
> 가로는 세로보다 비싸다.

### 1-3. 🔴 그런데 목표가 «동접 1,000» 이면 위 둘이 무의미해진다

**이 절은 목표가 아니라 시나리오다.** 정본 기준선은 **DAU 1,000 · 피크 67** 그대로다
([`load-test-strategy.md` §4.2 가정 P1](./load-test-strategy.md), 2026-08-23 confirm).
여기 적는 이유는 **「어디까지 버티나」에 답할 수 있어야** 하기 때문이고, 2026-08-23 대화에서
「DAU 1,000」과 「동접 1,000」이 실제로 한 번 섞였기 때문이다.

**둘은 15배 차이나는 다른 목표다.** 가정 P1 로 환산하면 **동접 1,000 ≈ DAU 14,800** 이고,
거꾸로 DAU 1,000 의 **산술 상한**은 (`p`≤1.0) **375세션**이라 **동접 1,000 은 애초에 안 나온다.**

| | |
|---|---|
| 목표 | 동접 **1,000세션** |
| 천장 | **89~105**(동거) · **116**(AI 전용 박스) |
| 필요 | 🔴 **9~11배** — AI 인스턴스 **10대 안팎** |

#### 그러면 이 문서의 전제가 뒤집힌다

- **§1 의 「기본값은 안 한다」가 무너진다.** 세로(R10-a)가 배수를 줘도 2~3배지 10배가 아니다.
  §8 ㉠(착수 여부)이 **「할지」가 아니라 「언제」**가 된다
- **㉰(장애 재배치)의 무게가 달라진다.** 인스턴스가 10대면 「한 대 죽으면 세션을 잃는다」가
  **상시 발생하는 일**이 된다 — §5-3 에서 「추천 없음」으로 둔 칸이 **먼저 정해야 할 칸**이 된다
- **㉯(매핑)의 계산은 그래도 안 바뀐다** — 0.23 QPS 는 DAU 기준이므로 동접 1,000 이면
  **약 3.4 QPS**. 여전히 컬럼으로 충분하다

#### 🔴 그리고 AI 만의 문제가 아니게 된다

동접 1,000 은 **초당 3,000 프레임**이고, rep 완성마다 들어오는 `SavePoseDataBatch` 쓰기가
**정본 baseline 649 RPS**([`load-test-strategy.md`](./load-test-strategy.md))와 **같은 자릿수**로
붙는다. 그 649 의 천장은 [커밋 fsync 와 락 대기](./pool-cliff-vs-concurrency.md)라
**Spring 을 늘려서 안 움직인다.**

즉 **동접 1,000 을 목표로 삼는 순간 이 문서는 «AI 수평확장 문서» 가 아니라 «쓰기 축까지
같이 다시 계산하는 일» 이 된다.** 그건 이 문서의 범위 밖이고, 별도 결정이 필요하다.

⚠️ **그래서 이 절은 숫자를 «필요 대수» 로 확정하지 않는다** — 「10대 안팎」은 현재 천장으로
나눈 값이고, 세로(R10-a)·#92·박스 분리를 반영하기 전 값이다. 그 셋이 천장을 올리면 대수가
줄어든다. **순서는 §1 그대로다.**

## 2. 이미 한 번 틀렸다 — 「코드 변경 0」 초안

[`ai-receive-path-scaling.md` §2-0](./ai-receive-path-scaling.md) 이 **2026-08-17 에 실제로 띄워보고**
폐기한 안이다:

> *"AI 컨테이너를 2개 띄우고 세션을 반씩 나눠 보낸다. 같은 세션의 프레임은 항상 같은
> 컨테이너로 가므로 문제없다. **코드 변경 0.**"*

`shadowfit-ai2` 를 8001 에 띄우고 5세션 스모크를 돌렸더니 **「20초 안에 분석기가 안 붙었다」**
로 판이 무효였다. Spring 이 1번에 검출기를 붙였는데 프레임이 2번으로 갔고, 2번은 그 세션을
모른다 — **요청은 도달해서 `200 OK` 가 찍히고, 반려는 그 뒤에 난다.**

🔴 **이 문서가 존재하는 이유가 그 실패다.** 「프록시 하나」로 보이는 것이 실제로는 셋이다.

## 3. 오늘 라우팅을 하는 주체는 **없다**

「Spring 이 정한다」는 §2-0 의 문장은 **Spring 이 고른다**는 뜻이 아니다. 고정된 주소가
**두 군데 따로 박혀** 있고, 둘 다 선택지가 하나다.

| 채널 | 주소 출처 | 고르는 행위 |
|---|---|---|
| Spring → AI gRPC (attach) | `backend/src/main/resources/application.yml:132`<br>`address: 'static://${AI_SERVER_HOST:shadowfit-ai}:${AI_SERVER_GRPC_PORT:8585}'` | **없다** |
| 프론트 → AI HTTP (프레임) | `frontend/services/aiService.ts:25`<br>릴리스는 `EXPO_PUBLIC_AI_BASE_URL`, 개발은 Metro 호스트 | **없다** — 빌드 타임에 박힌다 |

**그래서 인스턴스가 둘이 되는 순간 깨지는 지점이 정확히 이것이다 — 두 주소가 서로를 모른다.**

⚠️ 프레임 주소가 **설치본 안에** 있다는 점이 §2-0 이 본 것보다 한 겹 깊다. 그 실험은 부하 rig 이
프레임을 보냈지만, 실제 앱에서는 그 값이 **빌드에 인라인**된다([`ai-auth-token-flow.md`](./ai-auth-token-flow.md) §46).

## 4. 왜 「상태를 Redis 로」 가 답이 아닌가

수평확장의 반사적 답은 «상태를 프로세스 밖으로» 다. [§3-ㄱ](./ai-receive-path-scaling.md) 이
그것을 이미 판정했다:

> 검출기는 애초에 **직렬화가 불가능**하다(MediaPipe 객체) — 상태를 밖에 둬도 **검출기는
> 여전히 프로세스에 묶인다.** 🔴 **부적합.** 검출기가 못 따라오므로 **절반만 푼다**

코드에서도 같은 모양이다 — `ai-server/app/core/mediapipe_detector.py` 의
`lease_detector(session_id)` 가 **프로세스 메모리 풀**에서 빌려주고,
`ai-server/app/api/endpoints/pose.py:127` 이 *「이 registry 가 프로세스 메모리라 재배포로
통째로 날아간다」* 고 적어놨다.

**상태를 못 옮기면 세션을 옮길 수 없고, 세션을 못 옮기면 남는 답은 스티키다.**
그리고 스티키를 하는 순간 **인스턴스끼리 공유할 것이 없어진다** — 각자 자기 세션만 알면 된다.

## 5. 그래서 묶여 있는 결정 셋

셋은 **따로 못 정한다.** ㉮가 정해져야 ㉯의 읽기 빈도가 나오고, ㉯가 있어야 ㉰가 성립한다.

### 5-1. ㉮ 프레임 엔드포인트를 누가 정하나 — **계약이 바뀐다**

| | ㄱ. Spring 이 알려준다 | ㄴ. 프록시가 흡수한다 |
|---|---|---|
| 모양 | 세션 생성 응답에 AI 엔드포인트를 실어 보낸다 | 프론트는 단일 주소로 계속 치고, 앞단이 `session_id` 로 가른다 |
| 프론트 변경 | 🔴 **있다** — 빌드 타임 상수 → 런타임 값 | ✅ 없다 |
| 새 컴포넌트 | 없다 | 🔴 프록시 하나([`reverse-proxy-and-tls.md`](./reverse-proxy-and-tls.md) 와 같은 자리) |
| 어디서 가르나 | Spring 이 이미 attach 하는 자리 | 프록시가 요청 본문/헤더의 `session_id` 를 봐야 한다 |
| 🔴 함정 | 엔드포인트가 바뀌면(재배포) 진행 중 세션이 옛 주소를 든다 | **프록시도 매핑을 알아야 한다** — ㉯가 프록시에서도 읽혀야 하고, 그러면 Spring 전용 저장소로는 부족해진다 |

**추천: ㄱ.** 이유는 둘 — attach 를 하는 자리가 이미 Spring 이라 **매핑의 단일 출처가 하나로 남고**,
프록시 안을 고르면 ㉯가 두 곳에서 읽혀 저장소 선택이 통째로 무거워진다(그때는 Redis 가 실제로
필요해진다, §6).
⚠️ 대신 **프론트 계약 변경이 이 안의 실제 비용**이고, 그건 앱 배포 주기를 탄다.

### 5-2. ㉯ 매핑을 어디 두나

㉮-ㄱ 을 전제하면 읽기 빈도가 이렇게 나온다:

```
쓰기  세션당 1회 — exercise_sessions INSERT 가 어차피 일어난다 → 추가 쿼리 0
읽기  세션당 2~3회 — StopAnalysis · resume · 결과 조회
      1,500세션/일 × 3 × 0.18(피크 집중) ÷ 3600 ≈ 0.23 QPS
```

| | ㄱ. 저장 안 함 (해시) | ㄴ. 세션 테이블 컬럼 | ㄷ. Redis |
|---|---|---|---|
| 모양 | `hash(session_id) % N` 매번 유도 | `exercise_sessions` 에 nullable 컬럼 (V9) | 별도 저장소 |
| 비용 | **0** | 마이그레이션 1개 | 🔴 컨테이너·배포·모니터링 **신규** |
| N 이 바뀌면 | 🔴 **진행 중 세션이 검출기 없는 곳으로 간다.** 롤링 배포마다 발생 | ✅ 기록된 값이 그대로 산다 | ✅ 산다 |
| TTL | — | ❌ 없다 (세션 행에 남는다) | ✅ 있다 |
| 0.23 QPS 에 맞나 | — | ✅ | 🔴 과하다 |

**추천: ㄴ.** 🔴 ㄱ 이 제일 싸 보이지만 **롤링 배포가 곧 N 변경**이라 이 케이스에 안 맞는다 —
검출기는 직렬화가 안 되니 재배치된 세션은 복구도 안 된다. consistent hashing 은 완화지 해결이 아니다.
ㄷ 는 §6.
⚠️ **TTL 이 없는 것은 단점이 아니다** — 「어느 인스턴스에서 돌았나」가 남는 편이 사후 분석에 낫다.

### 5-3. ㉰ 인스턴스가 죽으면

🔴 **스티키는 장애 시 재배치를 못 한다.** 그 인스턴스의 진행 중 세션은 검출기와 함께 사라진다.

**그리고 ㉯를 무엇으로 고르든 이건 안 풀린다** — Redis 에 상태를 넣어도 **검출기는 못 살린다**(§4).
즉 이 칸은 저장소 선택의 문제가 아니라 **재개(resume) 경로의 문제**이고,
[`session-resume-and-ai-state.md`](./session-resume-and-ai-state.md) 가 열어둔 자리와 여기서 만난다.

| | 내용 |
|---|---|
| ㄱ. 그 세션은 잃는다 | 지금 1대에서도 재배포하면 같은 일이 난다(`pose.py:127`). **현상 유지** |
| ㄴ. 다른 인스턴스에서 재개 | 매핑을 새 인스턴스로 갱신하고 검출기를 새로 잡는다. 분석 연속성은 끊긴다 |

⚠️ **추천을 세우지 않는다** — 이 칸은 「분석이 끊겼을 때 사용자에게 무엇을 보이나」라는
**도메인 판단**이 먼저다. 그건 이 문서가 정할 것이 아니다.

## 6. Redis 는 필요한가 — **AI 수평확장만으로는 아니다**

Redis 는 현재 스택에 **없다**(`docker-compose.yml`·`backend/build.gradle`·`application.yml` 어디에도).
지금 캐시는 Caffeine 로컬(`application.yml`, `expireAfterWrite=1h,maximumSize=500`)이다.

AI 가 N대일 때 인스턴스 간 **공유가 필요한 것**을 세어보면:

| | 공유 필요? |
|---|---|
| 세션 ↔ 검출기 리스 | ❌ 스티키니까 인스턴스 로컬 |
| 세션 ↔ 인스턴스 매핑 | ⭕ 필요하지만 **Spring 쪽 값**이다 → §5-2 |
| 참조 데이터 · 스타일 기준 | ❌ 읽기 전용, 인스턴스마다 사본 |
| 토큰 검증 | ❌ 정적 `AI_PUBLIC_TOKEN` |
| Spring 쪽 Caffeine | ❌ **Spring 이 1대면 안 갈라진다** |

**Redis 를 부르는 것은 Spring 축이지 AI 축이 아니다.** 아래 셋 중 하나라도 걸릴 때 들어온다:

1. **Spring 이 2대 이상** — 카탈로그 캐시가 갈라진다([`reference-style-and-caching.md`](./reference-style-and-caching.md)
   가 「Redis 는 수평확장 시」로 이미 적어둔 자리). **이게 제일 먼저 온다**
2. **㉮-ㄴ(프록시)을 고름** — 매핑이 Spring 밖에서도 읽혀야 한다
3. **Spring 이 프레임을 중계하는 구조로 바뀜** — 읽기가 세션당 2~3회에서 **초당 348회**가 된다

🔴 **그리고 Redis 가 못 사주는 것을 분명히 해둔다** — 「Redis 를 넣으면 인스턴스가 죽어도
세션이 산다」는 **이 프로젝트에서 성립하지 않는다**(§4·§5-3).

| Spring | gRPC 채널이 **1개 → N개**. `net.devh:grpc-client-spring-boot-starter:3.1.0` 의 `@GrpcClient` 는 주소를 고정으로 잡으므로, **인스턴스별 채널을 직접 관리하거나 커스텀 리졸버를 붙여야 한다**. ⚠️ 어느 쪽이 되는지는 **미검증** |
| DB | 마이그레이션 **1개**(V9 — 현재 최신 V8). nullable 컬럼 하나 |
| 프론트 | 🔴 **계약 변경** — 프레임 base URL 이 빌드 상수에서 런타임 값으로. 앱 배포 주기를 탄다 |
| 인프라 | 인스턴스 N대 × (검출기 풀 × **98.7MB** 실측). 풀 크기가 곧 RAM 이다 |
| 측정 | 이 변경은 **기능이 아니라 용량**이라, 「됐다」의 근거가 라운드여야 한다 — 최소 2대에서 세션이 갈라져 붙는지 |
