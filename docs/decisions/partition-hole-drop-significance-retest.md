## 0. 이 문서가 하는 일 — 설계가 아니라 재현 계획

2026-08-24 從 R12가 이미 방법론을 확정했다. 조용한 EC2 박스 + rig의 잡음 노브 둘(`WARM_DROP`·
`SETTLE_SEC`)로 팔 안 산포를 9.4배 → 1.9배로 접었고, 그 위에서 라틴 방격 13블록을 돌려
**구멍이 페이지를 +69%(10,032 → 16,920) 늘리는데 DROP 소요는 +13%(17.7 → 21.1ms)만 따라간다**는
결과를 얻었다. 10/13 블록이 같은 방향(구멍 쪽이 느림)이지만, 부호검정 **p=0.092**·Wilcoxon
**p=0.094**로 0.05 문턱을 못 넘었다.

**이 문서가 새로 설계할 것은 거의 없다** — 무대·rig·노브·판정 기준이 전부 R12에서 이미 검증됐다.
바뀌는 건 **블록 수(13 → 30~40)** 하나뿐이다. 그래서 이 문서는 "왜 이만큼 늘려야 하는가"와
"R12와 무엇이 같고 무엇만 다른가"를 명확히 하는 데 집중한다.

## 1. 표본 크기 근거

🔴 **정확한 검정력 계산은 안 했다** — 정규근사나 이항분포 기반 표본 크기 공식을 돌리지 않았다.
아래는 R12 결과 문서(§5)가 이미 적어 둔 어림값을 그대로 옮긴 것이다:

> "필요한 n은 대략 이 산포에서 **팔당 30~40판**(판당 약 70초 → 40~50분)."

직관은 이렇다 — 부호검정에서 10/13(≈77%)이 한 방향이면, 그 비율이 그대로 유지된다고 가정할 때
n을 키우면 이항검정 p값은 단조 감소한다(같은 성공 비율에서 시행 횟수가 늘면 우연으로 이 정도
쏠림이 나올 확률은 줄어든다). 13에서 30으로 늘리면 "10/13"이 "23/30"에 해당하는 비율로
커지는 셈이라 p가 0.05 아래로 갈릴 가능성이 높다는 것이 R12가 어림한 근거이지, 시뮬레이션이나
공식으로 검증한 숫자는 아니다. **이 재실험의 1차 산출물 중 하나는 오히려 "그 어림이 맞았는가"다**
— 30~40판을 돌리고도 여전히 p>0.05면, 그 자체가 "10/13이라는 관측 비율 자체가 방향을 대표하지
못했다"는 신호로 읽어야 한다(§4 판정 참고).

## 2. 무대 — R12를 그대로 쓴다

아래는 전부 R12([결과](../../loadtest/results/q2-partition-quiet-box-2026-08-24/README.md))에서
그대로 가져온다. 이 문서가 다시 설명하지 않는다:

| | 값 | 근거 |
|---|---|---|
| 대상 | **조용한 EC2 박스** — MySQL 하나만 있으면 됨(앱·부하기·AI 무대 불필요) | R12 §6 재현 |
| rig | [`q2_partition_rig.sh`](../../loadtest/results/row-shape-frag-2026-08-24/q2_partition_rig.sh) | R12 §0 |
| 잡음 노브 | `WARM_DROP=1` · `SETTLE_SEC=10` — 이걸 켜야 팔 안 산포가 9.4배 → 1.9배로 접힌다 | R12 §0 표 |
| 스키마·행 수 | `ROWS=50000` · `CHURN=25000` · `KEEP_K=8` | R12 §1 |
| 팔 | `pclean`(FIFO만) vs `pholed`(구멍 뚫림) — 판마다 하나만 DROP(순서 교락 제거) | R12 §1 |
| 블록 순서 | 라틴 방격(C→H / H→C 교대) — 블록마다 무대를 새로 세움 | R12 §1 |
| 게이트 | 행 수·페이지 수 게이트(무대가 안 서면 측정 전에 죽음) — round1이 무효(행0·페이지1)였던 재발 방지 | R12 §3 |
| 판정 지표 | 쌍차(H−C) 부호검정 · Wilcoxon 부호순위 정확검정 | R12 §1 |

**"조용한 박스"의 뜻** — R12가 명시적으로 정의하진 않지만, 재현 조건에서 유추하면 이 rig
말고 다른 서비스(앱·AI·부하기)가 같은 박스에서 돌지 않는 EC2 인스턴스를 뜻한다. 로컬
(i3-6100, [[project_loadtest_env_constraint]])의 팔 안 산포 9.4배가 이 조건 하나로 1.9배까지
줄었다는 것이 R12의 핵심 발견이었다 — **다시 로컬로 돌리면 이 재실험 전체가 무의미해진다.**

## 3. 차이점 — 블록 수 하나

| | R12(2026-08-24) | 이 재실험 |
|---|---:|---:|
| 팔당 블록 수 | **13** | **30~40** |
| 소요(추정) | ~15분 | **40~50분** |
| 그 외 | — | R12와 전부 동일 |

재현 명령도 R12 §6과 같다 — 블록 수만 늘어난 러너로 반복 호출하면 된다:

```bash
# R12와 동일. TARGET을 pclean·pholed로 교대(라틴 방격), 판마다 무대를 새로 세운다.
# 블록 수만 13 → 30~40으로 늘린다(러너 스크립트가 있다면 그 인자, 없으면 반복 호출 횟수).
ROWS=50000 CHURN=25000 KEEP_K=8 WARM_DROP=1 SETTLE_SEC=10 TARGET=pclean \
  bash loadtest/results/row-shape-frag-2026-08-24/q2_partition_rig.sh
```

🔴 **러너 자체가 블록 수를 인자로 받는지는 확인 안 됨** — R12가 13블록을 어떻게 돌렸는지(러너
스크립트 유무)는 결과 문서에 명시가 없다. 착수 시 `q2_partition_rig.sh` 주변에 블록 반복을
관리하는 러너가 있는지 먼저 확인하고, 없으면 반복 호출 + 결과 집계를 감싸는 얇은 스크립트를
새로 만들어야 한다 — 이건 "설계"가 아니라 "누락된 배선"이라 착수 단계에서 처리한다.

## 4. 판정

목표는 단순하다 — 부호검정(또는 Wilcoxon)이 **p<0.05로 갈리는가**, 아니면 **여전히 애매한가**.

| 결과 | 다음 |
|---|---|
| p<0.05, 방향이 R12와 같음(구멍 쪽이 느림) | **확정** — "「DROP 1.8초·DELETE 대비 625배」는 구멍 유무와 무관하게 인용해도 된다"는 R12의 잠정 결론이 통계적으로도 닫힌다. `row-shape-partition-interaction.md` Q2 상태를 "자릿수로는 독립"에서 확정으로 갱신 |
| p<0.05, 방향이 R12와 다름(구멍 쪽이 빠름) | 🔴 **결함 신호** — R12의 방향 관측(10/13)이 우연이었다는 뜻. [[feedback_troubleshooting_to_issues]]대로 이슈 등록 검토 |
| n을 30~40으로 늘려도 여전히 p>0.05 | **"영향 없음"에 가까워진다** — §1의 어림(비율 유지 가정)이 틀렸다는 뜻이기도 하다. 이 경우 "자릿수로는 독립"을 최종 결론으로 굳히고, +13%는 "잡음 안에 있다"로 정리하는 쪽이 정직하다 |

어느 쪽으로 나와도 `row-shape-partition-interaction.md` §3 Q2와 `experiment-inventory.md`의
"남은 것은 p=0.092의 +13%뿐" 문구를 갱신할 근거가 생긴다.
