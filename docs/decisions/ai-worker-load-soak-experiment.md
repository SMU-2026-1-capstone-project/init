## 0. 왜 이 실험인가 — 이전 soak가 못 답한 것

2026-08-26~27에 24시간 **유휴** soak를 돌렸다 — 5분 간격 `RestartCount` 폴링, **자발적 재기동
0회**. 이게 답한 질문은 "트래픽이 전혀 없을 때 자발적으로(OOM 등) 죽는가"이고, 답은 "24시간 안엔
아니다"였다.

`ai-channel-pool-hardening.md` §6의 원래 질문은 그게 아니다 — **"실제 운영 부하(동시 세션 처리
중 메모리 압박)에서 장애 빈도가 얼마나 되는가"**다. 유휴 무사고가 부하 중에도 그렇다는 걸
보장하지 않는다. 컨테이너 캡(`shadowfit-ai mem=20GB·cpus=4`, #570)이 최근에 걸려서, 이제는
"메모리 한도 안에서 압박이 커지면 죽는가"라는 구체적 실패 모드도 새로 생겼다.

## 1. 두 갈래 중 이 문서가 고른 것

| | 자연관찰(가정 피크 동접 유지) | **가속 스트레스 (이 문서)** |
|---|---|---|
| 기간 | ~24시간 | **2~4시간** |
| 답하는 질문 | DAU 1,000 가정 조건에서의 실제 빈도 | 메모리 압박이 커지면 죽는가(가속 조건) |
| 비용 | 큼(24h × 2대) | 작음 |

2026-08-28 사용자 확인으로 **가속 스트레스**를 택했다. 정직하게 적어둔다: 이 실험은
"DAU 1,000에서 몇 번 죽는가"에는 답하지 않는다. 답하는 것은 "동접을 가정치의 N배로 밀면
장애가 나는가·난다면 무슨 모양인가"다 — §6의 원래 질문 전체를 닫지는 못한다.

## 2. 판정 기준

soak와 같은 채널을 그대로 쓴다 — 새 반증조건 표를 만들지 않는다:

| 관측 | 의미 |
|---|---|
| `RestartCount` 증가 | 컨테이너 전체 재기동(entrypoint.sh의 `wait -n` 종료) — soak와 동일 정의 |
| `docker inspect --format '{{.State.OOMKilled}}'` | **soak에는 없던 채널** — 컨테이너 캡(#570)에 의한 OOMKill인지, 워커 내부 예외로 인한 자발 종료인지 구분한다. 원인 분류가 이번 실험의 부가 가치 중 하나 |
| `docker stats`(mem/cpu %) 시계열 | 캡에 얼마나 근접했는지 — 장애가 안 나도 "얼마나 아슬아슬했는가"를 남긴다 |

**"장애 0회"로 끝나도 산출물이 있다** — 캡 대비 최대 메모리 사용률을 실측값으로 남기면,
"이 강도에서는 안전하다"는 하한을 하나 얻는다.

## 4. 🔴 부하 생성 방법 — 아직 없다

**이게 이 실험 고유의 미결이다.** soak는 부하가 아예 없어서 이 문제가 없었다. 기존 rig들을
훑어보면 전부 "짧은 판(수 분) 단위"로 설계돼 있다:

- `read_p99_ec2.js`·`measure_http_write_p99.sh` — k6 `constant-arrival-rate`, 120초 블록. 시간
  단위로 늘릴 수는 있지만(duration만 바꾸면 됨) **AI 경로를 안 건드린다** — 읽기·쓰기(`SavePoseDataBatch`)
  경로고, AI 메모리 압박을 만드는 것은 `POST /exercises/sessions`(→ `sendAnalysisRequestToFastApi`
  → AI 채널 풀) 이후의 세션이다.
- `measure_ai_worker_kill_recovery.sh` — 유도된 kill 복구 시간 측정. 부하 생성이 아니다.
- `ghz/gen_batch_multi.py`·`batch_multi.json` — `SavePoseDataBatch` 페이로드 생성기. 세션 생성
  경로가 아니라 pose_data 쓰기 경로다.

**필요한 것**: 세션을 계속 새로 시작(`POST /exercises/sessions`)해서 AI 채널 풀에 지속적으로
새 분석 요청을 흘려보내는 드라이버. 세션 하나가 끝나거나 타임아웃되면 새로 시작해서 N시간
내내 "동접 X" 를 유지하는 루프가 필요하다 — 지금 이 모양의 rig이 없다.

**확정(2026-08-28): 선택지 2 — 가벼운 bash/python 루프.** k6 확장(선택지 1) 대신, 계정 풀에서
세션을 계속 시작해 목표 동접(§5 — 202.5세션)을 유지하는 단순 루프로 간다.

### 4-1. 🔴 범위 확정 — 세션 시작만, 프레임 스트리밍은 뺀다 (정직하게 적어둔다)

코드를 확인하니 `POST /exercises/sessions`(세션 시작)는 AI 채널 풀에 세션을 **등록**만 한다
(`StartAnalysis` gRPC, 검출기 상태 초기화). **실제 메모리·CPU 압박은 그 다음** — 클라가 계속
`POST /pose`(AI 서버 직행, [`ai-server/app/api/endpoints/pose.py`](../../ai-server/app/api/endpoints/pose.py))로
base64 프레임을 보내야 `lease_detector`가 세션별 MediaPipe 검출기 상태를 들고 추론을 돈다.

**이 실험은 세션 시작(등록)까지만 하고 프레임 스트리밍은 안 한다** — 2026-08-28 사용자가
명시적으로 선택. 즉 AI 채널 풀에 "빈 세션" 202.5개를 계속 유지하는 것이지, 실제 추론 부하를
거는 게 아니다. **정직하게: 이 강도로는 진짜 메모리 압박을 거의 못 만들 가능성이 크다.**
"장애 0회"가 나와도 그건 "빈 세션 등록만으로는 안 죽는다"는 좁은 결론이지, §0가 원래 묻던
"운영 부하(프레임 처리 포함)에서의 장애 빈도"에는 여전히 못 답한다 — 그 갭은 이 라운드가 끝난
뒤에도 남는다(다음 라운드 후보: 프레임 스트리밍까지 포함한 재실험, `measure_ai_concurrency.py`의
합성 이미지 재사용 가능).

설계에 남는 세부 사항(구현 시 정할 것, 이 문서가 지금 확정하는 건 "방식"까지다):

- **동접을 어떻게 맞추는가** — 세션 하나의 생애(시작 → 자연 종료/타임아웃 → 다음 세션 시작)를
  루프가 추적해서, "시작 속도 ≈ 종료 속도"가 되도록 목표치 근처에서 유지. 가장 단순한 형태는
  고정 크기(≈203개) 워커 풀 — 각 워커가 세션 하나를 끝내면 즉시 다음 세션을 시작하는 방식이면
  목표 동접이 자동으로 유지된다(정교한 레이트 제어 불필요).
- **계정 풀** — R14가 겪은 "시더가 member_id 하드코딩" 문제를 피하려면 전용 계정을 충분히
  (동접 수 이상) 미리 만들어둬야 한다.
- **세션 종료 방식** — 자연 타임아웃에 맡길지, 정상 종료 API를 명시적으로 호출할지. 후자가
  "생애 주기"를 더 예측 가능하게 만든다.

## 6. 자동 종료 가드 — 이전 두 실수를 반복하지 않는다

- **soak(2026-08-26)**: `run_all.sh`를 안 거쳐서 자동 종료 가드가 아예 없었다 — 사람이 수동으로
  회수·terminate해야 했다.
- **R14(2026-08-28)**: `run_all.sh`를 거쳤는데 `PHASES`에 `preflight`가 들어가 있어서(부하기
  박스에서 항상 FAIL) → 결과 업로드만 성공 → `FINAL_OK=1` → `AUTO_SHUTDOWN`이 **정상 종료로
  오인**해 인스턴스를 조기 terminate — 부하기 박스를 두 번 잃었다.

이번엔 `run_all.sh`를 쓰되 **`PHASES`에서 `preflight`를 명시적으로 뺀다**(R14가 우회했던 것과
같은 방식). 결과 업로드 성공 여부가 실제 실험 완료를 정확히 반영하는지 실행 전에 한 번 더
확인한다 — 이 항목 자체가 [#587](https://github.com/Shadowfit/init/issues/587)과 별개로
`run_all.sh` 예시 주석의 근본 수정(아직 미착수)이 필요하다는 신호다.
