## 0. 이 문서가 여는 것

분기 I 는 2026-05-24 에 **I1(`INTERNAL_API_TOKEN` 정적 공유) 잠정 채택**으로 닫혔고, 결정 로그에 *"운영 단계에서 I2(세션 단위 단기 토큰) 전환 검토"* 로 적혀 있다. 그 "운영 단계" 판단 기준은 정해지지 않았다.

그 뒤 **I1 의 전제와 다른 선택지들의 비용 평가를 바꾸는 사실 4가지**가 드러났다(§2). 그리고 [#134](https://github.com/Shadowfit/init/issues/134) 가 정리한 선택지 표에는 **I2 가 빠져 있다** — 원 결정이 전환 대상으로 지목한 바로 그 안이다. 이 문서는 그 둘을 합쳐 다시 비교한다.

**이 문서는 결정하지 않는다.** 비교와 추천만 제공한다.

## 1. 지금 상태 (코드 기준, 2026-08-09)

`INTERNAL_API_TOKEN` **하나**가 세 곳에서 세 채널을 지킨다.

| 채널 | 방향 | 인증 |
|---|---|---|
| **①** 프론트 → AI HTTP 8000 (`POST /pose`) | 클라 → 서버 | ~~`EXPO_PUBLIC_INTERNAL_API_TOKEN`~~ → **`EXPO_PUBLIC_AI_PUBLIC_TOKEN`** (ㄱ 적용, §10) |
| **②** Spring → AI gRPC 8585 (`StartAnalysis` 등) | 서버 → 서버 | `ExerciseAnalysisService.java:92` |
| **③** AI → Spring gRPC 6565 (`SavePoseDataBatch` 등) | 서버 → 서버 | `spring_client.py:33` |

세 채널 모두 **같은 값**이고, 검증은 문자열 동등 비교 하나다:

```java
// InternalAuthInterceptor.java:28
if (authHeader == null || !authHeader.equals("Bearer " + internalToken)) {
```

**결과**: 통과한 호출에 "누가 불렀는가" 가 남지 않는다. 호출자 신원이라는 개념 자체가 없다.

## 5. 각 안의 실제 비용

### 5-1. I1 (현행 유지 = #134 ㄹ)

비용 0. 근거는 *"지금 실사용자 0, 내부망 전용"* 이고 **그 자체로 틀리지 않다.** 다만 §2① 때문에 "탈취되면" 이 아니라 "이미 배포돼 있다" 로 서술을 고쳐야 하고, 배포 전 재검토를 **조건이 아니라 차단 항목**으로 박아야 한다.

⚠️ 채널 ①(AI HTTP)은 프론트가 직접 부르는 구조라 **배포되면 외부에 열려 있어야 한다.** 즉 배포 시점에 곧바로 노출되는 채널이다.

### 5-2. ㄱ (값 분리)

`AI_PUBLIC_TOKEN` 을 신설해 채널 ① 에만 쓰고, 채널 ②③ 은 기존 값 유지. **면적이 가장 작고**(환경변수 1개 + AI 미들웨어 상수 1개), §2② 의 횡단을 끊는다.

한계가 분명하다 — 새 토큰도 여전히 번들에 들어가므로 **"누구나 `/pose` 를 호출할 수 있다" 는 그대로다.** 피해를 AI 세션 상태로 한정할 뿐이다. 단독 해결책이 아니라 **다른 안과 조합하는 부품**으로 보는 게 정확하다.

### 5-3. I2 (세션 단위 단기 토큰)

세션 시작 응답(`POST /exercises/sessions`)에 AI 호출용 토큰을 실어 내려주고, AI 미들웨어가 그것을 검증한다. 토큰은 **(회원, 세션, 만료)** 에 묶인다.

- ✅ 클라에 나가는 값이 **세션 스코프 + 단기**라, 유출돼도 그 세션 하나·만료까지다
- ✅ `JWT_SECRET` 을 AI 에 주지 않는다 → §2④ 문제 회피
- ✅ #135(24시간 access token)·#137(휘발 블랙리스트)과 **결합하지 않는다** — 별도 토큰이라 access token 수명·블랙리스트와 무관하다
- ✅ H2(직결)를 유지한다
- ⚠️ 검증 방식을 정해야 한다 — (a) Spring 이 서명한 단기 JWT 를 AI 가 **자체 검증**(AI 에 검증 키 필요 — 여기서도 대칭/비대칭 선택이 따라온다) vs (b) AI 가 Spring 에 **introspection** 왕복(키 불필요, 요청마다 왕복). 프레임마다 POST 하는 경로라 (b)의 지연 비용이 민감할 수 있고 **재본 적 없다**
- ⚠️ 원 분기 I 표는 비용을 *"백엔드 +3h(`AiTokenService`), AI 측 토큰 검증 로직"* 으로 추정했다. **근거 없는 추정치이고 검증되지 않았다**

### 5-4. 소유권 갭은 어느 안으로도 «자동으로» 닫히지 않는다

§2③ 의 갭은 **채널 ③(AI → Spring)** 에 있다. 위 안들은 전부 채널 ①(클라 → AI)의 토큰을 다룬다. AI 가 Spring 을 부를 때는 여전히 서버간 정적 토큰이고, `savePoseDataBatch(sessionId, ...)` 는 그 `sessionId` 가 누구 것인지 묻지 않는다.

닫으려면 **별도 설계가 필요**하다:

- (a) AI 가 콜백에 세션 토큰(또는 그 안의 memberId)을 함께 실어 보내고 Spring 이 대조
- (b) Spring 이 발급 시점의 `(sessionId → memberId)` 를 기억해두고 콜백에서 대조
- (c) 서버간 채널은 신뢰 경계 안으로 간주하고 **명시적으로 감수** 박제

**어느 쪽이든 토큰 선택과 별개의 결정이다.** I2 를 택하면 (a)가 자연스럽게 붙지만 공짜는 아니다.

### 5-5. I3 (사용자 JWT = #134 ㄴ)

소유권 검증까지 한 번에 가는 유일한 안으로 보이지만, §2④ 때문에 **그대로는 순이득이 아닐 수 있다.**

| | 새는 것 | 그걸로 할 수 있는 것 |
|---|---|---|
| 현행 | `INTERNAL_API_TOKEN` | AI HTTP + Spring 내부 RPC |
| I3 + HS256 | `JWT_SECRET` | **임의 회원 위장 → Spring REST 전체** ([#138](https://github.com/Shadowfit/init/issues/138) 과 결합 시 관리자 포함) |

제대로 하려면 **HS256 → RS256/ES256 마이그레이션**이 선행돼야 하고(공개키만 배포), 기존 발급 토큰(최대 24시간)의 롤오버가 딸려온다. 여기에:

- `ai-server` 에 JWT 검증 수단이 **현재 0** — `requirements.txt` 에 라이브러리 없음, `config.py` 에 설정 없음
- `JWT_SECRET` 은 현재 **백엔드에만** 주입된다(`docker-compose.yml:77`) — 배포 구성 변경
- **#135·#137 이 딸려온다**: AI 가 받는 토큰이 24시간짜리이고, 블랙리스트가 Spring 힙에만 있어 **AI 는 로그아웃을 알 수 없다**

### 5-6. ㄷ (직결 철회)

보안 축에서는 가장 깨끗하다(클라가 AI 를 아예 안 부름). 대신 **분기 H 결정을 되돌린다** — H2 채택 사유였던 *"PPT 아키텍처 그대로", "한 홉 절감(~5~30ms)", "base64 페이로드가 백엔드 메모리/GC 를 안 거침"* 이 전부 무효화된다. 백엔드 프록시(BE-01, 폐기됐던 작업)를 되살려야 한다.

프레임마다 ~40KB base64 가 백엔드를 통과하게 되므로, [`ai-load-budget.md`](./ai-load-budget.md) 의 부하 산정도 다시 해야 한다.

## 6. 추천 (⚠️ 결정 아님 — confirm 전)

**단기: ㄱ(값 분리) → 중기: I2(세션 단기 토큰)** 를 추천한다.

근거:

1. **ㄱ 은 가장 싸게 가장 큰 조각을 뗀다.** §2② 의 횡단(앱에서 뽑은 값으로 Spring 내부 RPC 를 치는 경로)이 지금 구조에서 제일 위험한 부분인데, 환경변수 하나 분리로 끊긴다. 다른 어떤 안을 택하든 손해가 아니다
2. **I2 는 §2④ 를 피하면서 신원을 만든다.** I3 의 장점(호출자 신원)은 가져오고 단점(`JWT_SECRET` 확산, #135·#137 결합)은 안 가져온다
3. **I2 는 이미 지정된 방향이다.** 2026-05-24 결정 로그가 *"운영 단계에서 I2 전환 검토"* 로 적어뒀다. 새 방향을 만드는 게 아니라 예고된 전환을 실행하는 것이다
4. **ㄷ 은 되돌리는 비용이 크다.** 분기 H 의 채택 사유 4개를 전부 무효화하므로, 보안만으로 정당화하기엔 파급이 넓다
5. **I3 는 선행 조건(RS256 전환)이 붙는다.** 그 자체로 별도 분기이고, #135·#137 과 묶여 작업 단위가 커진다

**단, 소유권 갭(§5-4)은 위 추천으로 닫히지 않는다.** 별도 결정이 필요하고, 이 문서는 그것을 정하지 않는다.

## 7. 미결정 질문

- **ㄱ 을 지금 할 것인가, I2 와 같이 할 것인가** — 지금 하면 I2 때 다시 손대야 하지만, 면적이 작아 손해가 크지 않다
- **I2 의 검증 방식** — 자체 검증(키 배포) vs introspection(왕복). 후자의 지연 비용 **미측정**
- **I2 토큰의 만료** — 원 문서가 "5분?" 으로 적었으나 근거 없다. 세션 길이(운동 1회)와 재발급 필요성을 함께 정해야 한다
- **소유권 갭(§5-4)의 (a)/(b)/(c)** — 토큰 선택과 별개
- **"운영 단계" 의 정의** — 2026-05-24 결정이 남긴 미정 항목이 그대로다. 배포 시점? 외부 사용자 N 명? §8 참고

## 8. 발동 트리거 — 언제 «지금» 이 되나

I1 유지의 근거는 *"실사용자 0, 내부망 전용"* 이다. 그 전제가 깨지는 시점을 미리 못박아둔다.

| 트리거 | 왜 |
|---|---|
| **앱을 외부에 배포/설치 배포하는 시점** | 채널 ①(AI HTTP)이 외부에 열려야 하므로, 토큰이 «배포된 비밀» 이 된다 |
| **AI gRPC 포트가 컨테이너 밖으로 나가는 시점** | §2② 의 횡단이 실제 도달 가능해진다 |
| **지인 외 사용자가 붙는 시점** | 사용자 격리 필요성이 0 이 아니게 된다 |

⚠️ 세 트리거 중 첫 번째는 **시연 계획에 따라 곧 올 수 있다.** 시연 형태(로컬 실행 vs 설치 배포)에 따라 판단이 갈리므로, 그 형태가 정해지는 시점에 이 문서를 다시 연다.

**바뀐 것**: 채널 ①(프론트 → AI HTTP)만 새 토큰 `AI_PUBLIC_TOKEN` 을 쓴다. 채널 ②③(서버간 gRPC)은 기존 `INTERNAL_API_TOKEN` 을 그대로 쓰고, **그 값은 이제 클라이언트로 나가지 않는다.**

| 파일 | 변경 |
|---|---|
| `ai-server/app/config.py` | `AI_PUBLIC_TOKEN` 필드 신설 (기본 `""`) |
| `ai-server/app/middleware/auth.py:41` | HTTP 검증 대상을 `INTERNAL_API_TOKEN` → `AI_PUBLIC_TOKEN` |
| `frontend/services/aiService.ts:29` | `EXPO_PUBLIC_INTERNAL_API_TOKEN` → `EXPO_PUBLIC_AI_PUBLIC_TOKEN` |
| `frontend/app/(tabs)/exercise.tsx:144` | 폴링 게이트도 같은 env 로 |
| `docker-compose.yml` · `docker-compose.prod.yml` | ai-server 에 `AI_PUBLIC_TOKEN` 주입. prod 는 `:?` 로 필수화 |
| `.env.example` | 항목 추가 + 두 토큰의 성격 차이 명시 |

**Spring 은 변경 없다** — `InternalAuthInterceptor`·`ExerciseAnalysisService` 모두 `INTERNAL_API_TOKEN` 을 그대로 쓴다.

**닫힌 것**: §2② 의 횡단. 앱 번들에서 토큰을 추출해도 그 값으로 Spring 내부 gRPC 4개 RPC 를 칠 수 없다.

**닫히지 않은 것** (그대로 열려 있다):

- `AI_PUBLIC_TOKEN` **도 번들에 인라인된다.** "누구나 `/pose` 를 호출할 수 있다" 는 변함없다 — 피해가 AI 세션 상태로 한정될 뿐이다
- **호출자 신원이 여전히 없다.** → I2 미결정
- **소유권 갭(§5-4)** 그대로. 채널 ③ 은 손대지 않았다

**운영 주의**:

- 미들웨어는 **fail-closed** 다. `AI_PUBLIC_TOKEN` 미설정 시 모든 HTTP 요청이 401 이고, 프론트는 토큰이 없으면 폴링을 시작하지 않는다
- `EXPO_PUBLIC_` 값은 **빌드 시 인라인**되므로 프론트를 **재빌드해야** 새 토큰이 반영된다. 서버만 먼저 배포하면 구 앱이 401 을 받는다
- 두 값을 **같게 설정하면 분리가 무의미하다.** prod compose 에 경고를 달아뒀으나 값이 다른지 **코드로 강제하지는 않는다**

⚠️ **런타임 검증 안 했다.** 컨테이너를 띄워 401/200 을 확인하지 않았고, 프론트 재빌드도 하지 않았다.
