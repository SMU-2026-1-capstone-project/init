## 0. 한 줄 요약

3차가 천장을 **커밋 fsync** 로 규명하면서 미측정 3건을 남겼다. 이 문서는 그 셋을 **한 번의 EC2 라운드**로 묶는다.

| | 항목 | 왜 지금 같이 하나 |
|---|---|---|
| ② | **mysqld_exporter — MySQL 지표 수집** | ③의 **판정 장치**다. 없으면 3차와 같은 처지가 된다 |
| ③ | **커밋 횟수 줄이기** (여러 rep 을 한 트랜잭션으로) | 내구성을 안 깎는 유일한 레버인데 미측정 |
| ④ | **내구성 완화 상태에서 pool 재스윕** | 2차의 «절벽 없음» 이 fsync 에 가려진 것인지 확인 |

**순서가 ②→③→④인 것이 이 설계의 핵심이다.** ③을 처리량(RPS)만으로 판정하면 *"빨라졌다"* 는 알아도 *"fsync 가 줄어서 빨라졌다"* 는 못 말한다. ②가 `Innodb_os_log_fsyncs` 를 주면 **메커니즘이 직접 관측**된다.

## 0-1. ✅ 결과 — 실행 완료 (2026-08-09)

전문: [`../../loadtest/results/commit-count-2026-08-09/`](../../loadtest/results/commit-count-2026-08-09/) · EC2 4대, **23판**(③ 3 + ④ 6 + 후속 5 + 재측정 9), gRPC 실패 0

### 🔴 이 문서가 세운 전제 하나가 무너졌고, 답 하나가 반대로 나왔다

**ㄱ. 3차의 «천장 = 커밋 fsync» 는 조건부였다 — 조건은 «단일 핫세션» 이다**

같은 rig·같은 코드·같은 행수에서 **페이로드만** 바꿨다:

| 페이로드 | 기본 내구성 | 완화 | 완화 배수 | `fsync/커밋` |
|---|---|---|---|---|
| 단일 세션 801 (3차와 같음) | **220.4** RPS | 535.9 | **2.43배** | **0.50** |
| 다세션 901~1000 | **649.4** RPS | 668.6 | **1.03배** | **0.16** |

단일 세션 220.4 는 3차의 231.6 을 재현한다. 다세션은 같은 조건에서 **2.9배**다. 모든 INSERT 가 한 인덱스 리프로 몰리면 커밋이 직렬화돼 **그룹 커밋이 덜 먹고**, 그때만 fsync 가 천장이 된다. → 이슈 [#166](https://github.com/Shadowfit/init/issues/166)

**ㄴ. ③의 답은 «아니오» 가 아니라 «반대» 다**

| 팔 | 평균 rows/s (3판) | 평균 p99 | `fsync/커밋` |
|---|---|---|---|
| **N=1** | **3,915** | **227ms** | 0.154 |
| N=5 | 2,838 (**−27.5%**) | 7,557ms | 0.362 |
| N=10 | 2,665 (**−31.9%**) | 11,280ms | 0.711 |

**커밋을 줄이면 처리량이 떨어지고 p99 가 50배 나빠진다.** 총 fsync 는 오히려 줄었는데(1.9배) 처리량이 떨어졌으니 **fsync 는 구속 조건이 아니다.** 그리고 `fsync/커밋` 이 N 과 함께 오른다 — 커밋을 줄이면 **그룹 커밋에 묶일 상대도 같이 줄어** 레버가 자기 발등을 찍는다.

**ㄷ. 초판은 정반대 답을 냈고, 그 이유는 설계 결함이었다**

초판(팔당 1판)은 «N 클수록 +32%» 를 냈다. 순서를 뒤집자 «N 작을수록 +36%» 가 나왔다 — **두 스윕 다 «나중 판일수록 높다»** 였다. 팔당 1판이면 «팔» 과 «판 순서» 가 같은 축에 겹쳐 **원리적으로 분리가 안 된다.** 이 문서 §3-2 를 쓰면서 그 질문을 한 번도 안 했다. 버림판 + 라틴 방격 3라운드로 다시 재서 위 표를 얻었다.

**ㄹ. ④ — «완화하면 절벽이 나타난다» 의 반대였다**

기본 내구성에서 pool=5 가 이미 plateau 의 **69.2%**(절벽 아래)고, 완화하면 **95.4%**(plateau 안)로 올라온다. fsync 가 처리량 천장을 만드는 게 아니라 **커넥션 점유 시간을 늘려 풀을 병목으로 만든다** — pool 이 넉넉하면(20) 완화 효과가 1.03배, 빠듯하면(5) 1.42배다.

### ✅ 사후 분석 — 걷어두고 안 본 지표에서 증명 하나, 반증 하나

인프라를 **지운 뒤에** `metrics/` 시계열을 판별 시간 창에 붙였다(`analyze_metrics.py`). 추가 비용 0원.

- ✅ **«인덱스 리프 경합» 이 추론에서 직접 증거가 됐다** — `Innodb_row_lock_waits` 증가량이 단일 세션 **8,056** vs 다세션 **0~3**(21판 전부). 그리고 단일 세션에서 내구성을 완화하니 **8,056 → 407 (1/20)** 로 떨어진다. 즉 «완화 2.43배» 의 기제는 *"fsync 를 안 해서"* 가 아니라 **«fsync 를 기다리며 잡고 있던 락을 빨리 놓아서»** 다. 사슬은 `fsync 대기 → 락 보유 연장 → 직렬화` 이고 **같은 행·페이지를 건드릴 때만 성립한다**
- 🔴 **«판 순서 = 버퍼풀 워밍업» 가설은 반증됐다** — `buffer_pool_pages{data}` 가 **첫 판부터 48,526/49,152** 로 이미 가득이었다. 원인은 **미상**으로 되돌린다. 새 후보(시딩 직후 더티 페이지 백로그)는 검증 못 했다

> 📌 **이 절이 이번 라운드의 마지막 교훈이다.** ②를 붙인 이유가 *"없어서 결론을 못 냈다"* 였는데, 이번엔 **있는데 안 봤다** — «버퍼풀이 원인» 이라고 쓸 때 이미 내 손에 그 지표가 있었다. **수집과 확인은 다른 일이다.**

### 착수 전 로컬 프로브가 실제로 값을 했다

§3-1-1 이 EC2 전에 무료로 확인한 3건 중 **2건이 실제로 문제였다**: `Com_commit` 이 앱 경로에서도 0(추측이 틀렸다), `/actuator/metrics` 가 401. 셋째(N=10 메시지 크기 455KB)는 통과했다. **이 셋 중 하나라도 EC2 에서 처음 만났으면 판을 날렸다.**

⚠️ 다만 로컬 프로브가 보여준 «커밋 5배 → fsync 4.9배» 는 **이 라운드에서 재현되지 않았다.** 로컬은 요청을 직렬로 5번 보낸 것이라 그룹 커밋이 안 먹었고, c=100 동시 부하에서는 상각된다. **§3-1-1 의 «전반부가 확인됐다» 는 문장은 그 조건에서만 참이다.**

## 1. 이미 아는 것 / 모르는 것

**아는 것 (3차 실측)**

- c=100·pool=20 고정에서 내구성 설정만 바꿔 **231.6 → 803.1 RPS (3.47배)**. 커밋마다 fsync 2회(redo 플러시 + binlog 동기화), EBS 가 네트워크 디스크
- 세 박스 CPU 전부 유휴(부하기 13~20% · 백엔드 27~37% · MySQL 50~59%) → 병목은 «계산» 이 아니라 «대기»
- `--connections` 1→16 무변화(230.2 / 208.0 / 210.9) → 부하기 아티팩트 아님

**모르는 것**

- 커밋 **횟수**를 줄이면 그 천장이 실제로 올라가는가. 3차는 커밋당 **비용**만 낮춰봤다
- 내구성을 완화해 fsync 가 천장에서 빠진 상태에서 **풀이 다시 병목으로 드러나는가**
- MySQL 내부에서 실제로 무슨 일이 일어나는가 — **지표가 없다**

|---|---|---|---|---|
| **ㄱ** | **클라이언트가 N rep 을 한 요청으로** (`gen_batch.py --reps 25→125`) | **0** (백엔드), 채택 시 ai-server 1곳 | 요청당 rep 수. **저장되는 행은 글자 그대로 동일** | 유실 단위 N rep · 재부착 카운트 |
| ㄴ | 서버가 여러 요청을 모아 그룹 커밋 | 백엔드 신규 컴포넌트(큐·단일 writer·커밋 후 응답) | 커밋 경계만 | ack 의미 · 실패 처리 신설 |
| ㄷ | 실험 전용 플래그로 커밋만 늦춤 | 백엔드(측정용 죽은 코드) | 커밋 경계만 | ④와 충돌 · 안 갈 코드를 잰다 |

### 2-1. ㄱ — 클라이언트가 N rep 을 한 요청으로

**측정 관점**

- 🟢 **백엔드 코드 변경 0.** §1-1 의 «측정 대상이 바뀌었나» 를 다음 회차에 새로 만들지 않는다
- 🟢 **쓰는 행이 글자 그대로 같다 — ✅ 테스트로 검증했다 (2026-08-09).** 다운샘플 윈도우가 리스트 시작점 기준으로 정렬되므로(`PoseDataService.java:173-180`), 25프레임×5요청과 125프레임×1요청은 **행 수뿐 아니라 «어느 프레임이 남았는가» 까지 동일**하다. `PoseDataServiceTest.downsample_isBatchInvariant_whenFramesPerRepIsMultipleOfWindow` 가 이 전제를 고정한다 — 깨지면 ③ 실험이 두 가지를 동시에 바꾸는 것이 되므로 설계가 무너지기 때문이다
- 🔴 **단, 「rep 당 프레임 수가 5의 배수」일 때만 성립한다** (같은 날 발견, `..._isNotBatchInvariant_...` 테스트). ghz rig 는 `--reps 25` 라 성립하지만 **23프레임짜리 rep 5개를 묶으면 행 수부터 25 → 23 으로 달라진다.** §3-2 의 `--reps` 를 5의 배수로 고정하는 것이 이 실험의 **필수 조건**이다
- 🟢 준비가 분 단위다 — `gen_batch.py --reps` 하나
- 🔴 **커밋만 줄지 않는다.** 요청 수가 1/N 이 되면 요청당 `existsById` SELECT 1회와 `UPDATE exercise_sessions` 1회도 같이 1/N 이 된다. **그래서 ②가 필요하다** — `Innodb_os_log_fsyncs/s` 가 고정인 채 rows/s 만 오르면 fsync 로 특정되고, 아니면 특정 못 한다. **처리량만으로는 귀속이 안 된다**
- 🔴 요청 크기가 N배(54KB → N=10 이면 약 540KB). gRPC 기본 수신 한도(4MB) 안이지만 **한도 설정을 실행 전에 확인**해야 하고, «큰 메시지의 역직렬화» 가 새 변수로 들어온다

**채택 관점 — 실제로 ai-server 를 이렇게 바꾸면**

- 🟢 변경 지점이 **1곳**이다 (`ai-server/app/api/endpoints/pose.py:121`)
- 🟢 **모바일 체감 지연이 오히려 준다.** 이 호출은 **프레임 응답 경로 안에서 동기로** 돈다 — rep 이 완성된 프레임의 HTTP 응답이 Spring 왕복을 기다린다. N rep 을 모으면 그 왕복이 1/N 이 된다. 부수 이득이지만 실측하면 값이 있다
- 🔴 **유실 단위가 N rep 이고, 지금 이 호출은 실패를 삼킨다.** `spring_client.py:67-68` 이 `RpcError` 를 **로그만 찍고 재시도하지 않는다.** 「1 rep 조용히 유실」이 「N rep 조용히 유실」이 된다 — 배수가 붙는 쪽이 하필 이미 조용한 결함이다
- 🔴 **재부착 카운트가 뒤로 간다.** 재부착은 DB 의 `MAX(rep_number)` 로 rep 카운트를 복원하는데(`pose.py:112` 주석, 이슈 #59 2단계), **버퍼에만 있고 DB 에 없는 rep 은 복원에서 빠진다.** 앱을 재시작하면 사용자가 실제로 한 횟수보다 적게 나온다
- 🔴 세션 종료·중단 시 **부분 버퍼 flush** 가 필수다(`StopAnalysis`·`CompleteAnalysis`). 안 넣으면 마지막 1~N-1 rep 이 통째로 사라진다
- 🔴 **(2026-08-09 신규 — 측정으로 발견) 저장되는 자세가 달라진다.** 실제 rep 의 프레임 수는 사용자가 얼마나 천천히 앉았는지에 따라 정해지므로 **5의 배수라는 보장이 없다.** 배수가 아니면 다운샘플 윈도우가 **rep 경계를 넘어가고**, 한 윈도우의 대표 프레임이 **서로 다른 두 rep 에서** 뽑힐 수 있다 — 저장되는 `rep_number` 도 그 승자의 것이 된다. 리포트의 «가장 깊게 앉은 순간» 이 어느 rep 의 것인지가 흐려진다는 뜻이다([`./worst-section-rep-resolution.md`](./worst-section-rep-resolution.md) §4-ㄹ 이 저장 시점에 고정한 선택이 바로 이것이다)
  > 📌 **이건 측정 rig 에서는 안 보인다** (`--reps 25` 는 배수라 통과한다). 채택 논의에 들어가서야 보였을 것을, 전제를 테스트로 고정하다가 먼저 만났다
- ⚪ **`last_active_at` 갱신 주기는 위험이 아니다.** N=10 이면 갱신 간격이 대략 30~50초인데 idle 타임아웃은 **10분**이다(`SessionService.java:81`). 여유가 한 자릿수 배가 아니라 열 배 이상이라 이 축은 문제가 안 된다

### 2-2. ㄴ — 서버가 여러 요청을 모아 그룹 커밋

- 🟢 **클라이언트 계약이 안 바뀐다.** proto 0줄, ai-server 0줄. §2-1 의 🔴 세 개(유실 단위·재부착·flush)가 **통째로 없다**
- 🟢 **커밋 횟수«만» 줄인다.** SELECT·UPDATE 는 그대로라 교란이 적어 **처리량만으로도 귀속이 성립**한다 — ②에 덜 의존한다
- 🟢 유실 창이 «N rep»(수십 초)이 아니라 «flush 주기»(밀리초)라 훨씬 작다
- 🟢 풀 압력이 **줄어든다** — 쓰기가 writer 몇 개로 모인다
- 🔴 백엔드 신규 컴포넌트다: 큐 + 단일 writer + **커밋 후 응답 완료**. 커밋이 실패하면 대기 중인 요청 **전부**에 에러를 돌려주는 경로가 새로 필요하다
- 🔴 **ack 의미가 갈린다.** 지금은 «응답 = 커밋 완료» 다. 응답을 먼저 주면 «접수됨» 으로 약해지고, 커밋까지 기다리면 의미는 지키지만 개별 지연이 flush 주기만큼 는다. **어느 쪽이든 결정이 필요하다**
- 🔴 측정 대상 코드를 바꾸는 것이라 §1-1 의 질문을 **다음 회차에 또 만든다**
- 🔴 **이번 라운드에 못 들어간다.** 구현·테스트가 측정 준비보다 크다

### 2-3. ㄷ — 실험 전용 플래그로 커밋만 늦춤

- 🟢 조작이 «커밋 경계» 하나로 셋 중 가장 순수하다
- 🔴 **④와 충돌한다.** 커밋을 늦추려면 트랜잭션을 요청 경계 너머로 열어둬야 하고, 그러면 **커넥션을 점유한 채**가 된다. 풀 사용량이 실험 조건에 따라 달라져 ④의 pool 스윕과 서로 오염된다 — **두 실험을 같은 라운드에 넣을 수 없다**
- 🔴 프로덕션에 안 갈 코드를 재는 것이라, 결과를 «채택하면 이만큼» 으로 옮길 때 한 단계가 빈다
- 🔴 그런데도 백엔드 코드는 바뀐다 — **ㄴ 의 단점(§1-1 재발)은 그대로 지고 ㄴ 의 장점(계약 유지·유실 창 축소)은 하나도 없다**

### 2-4. 🟢 추천 — 측정은 ㄱ, 채택은 열어둔다

**이번 라운드의 목적은 «레버가 존재하는가와 크기» 이지 «무엇을 채택하는가» 가 아니다.** 그 목적에는 ㄱ이 압도적으로 싸고(백엔드 0줄) 조작이 깨끗하다. ㄷ은 ④를 오염시키므로 이번 설계에서 **탈락**이고, ㄴ은 구현이 측정 준비보다 커서 **이번 라운드에 안 들어간다.**

⚠️ **다만 ㄱ 으로 잰 배수를 ㄴ 채택의 기대값으로 그대로 쓰면 안 된다.** ㄱ 은 커밋과 함께 SELECT·UPDATE 도 1/N 로 줄이므로 **상한 쪽으로 치우친 값**이다. ②의 `fsyncs/s` 와 `Com_commit/s` 가 그 둘을 갈라주는 만큼만 «ㄴ 로 옮겨도 남을 몫» 을 말할 수 있다. **결과 문서에 이 문장을 그대로 넣는다.**

📌 **채택 판단은 이 문서가 하지 않는다.** §2-1 의 🔴 세 개(조용한 유실의 N배·재부착 카운트·부분 버퍼 flush)는 성능이 아니라 **정확성** 문제고, 셋 다 [`./session-liveness-vs-elapsed-time.md`](./session-liveness-vs-elapsed-time.md)·이슈 #59 와 얽혀 있다. 크기를 먼저 재고, 그 크기가 이 셋을 고칠 값을 하는지는 별도 결정이다.

## 3. 측정 설계

### 3-1. ② mysqld_exporter — 무엇을 위해 붙이나

현재 [`../../monitoring/prometheus.yml`](../../monitoring/prometheus.yml) 하단은 exporter 를 **의도적으로 뺐다**고 적고 근거를 둘 든다:

> *"loadtest/ 스크립트가 SHOW STATUS 로 직접 떠 왔다. 그 경로가 이미 있으므로 익스포터를 더하는 것은 중복이고, 실험 중 컨테이너를 하나 더 띄우는 비용만 는다."*

🔴 **이 근거는 2026-08-08 에 실패했다.** 분리 배포에서는 `SHOW STATUS` 를 **뜨는 사람이 없었고**, `metrics/` 10종이 전부 `job="shadowfit-backend"` 라 MySQL 쪽을 못 봤다. 그 결과 *"MySQL 은 놀고 백엔드가 탄다"* 는 **수집한 적 없는 지표에 근거한 문장**이 나왔고 철회됐다.

- 「중복」이 성립하는 것은 **손으로 붙어 있는 로컬 단일 박스**에서다. 원격 3대 자동 스윕에서는 «판별로 귀속되는 시계열» 이 필요하고 `SHOW STATUS` 스냅샷은 그걸 못 준다
- 「컨테이너 비용」은 **obs 를 분리한 순간 무의미**해졌다 — DB 박스가 아니라 obs 박스에 뜬다

**볼 지표 (판정에 실제로 쓰는 것만)** — ✅ **2026-08-09 로컬에서 이름·존재·거동까지 확인했다.** 3차가 «수집한 적 없는 지표» 로 결론을 낸 자리라, 이번엔 EC2 에 돈을 쓰기 **전에** 확인한다.

| 지표 | 무엇에 답하나 | 로컬 확인 |
|---|---|---|
| `mysql_global_status_innodb_os_log_fsyncs` | **③의 판정 지표.** 초당 fsync 횟수가 천장인가 | ✅ 존재. 커밋 60회에 806 → 1,021 로 **실제로 반응** |
| `mysql_global_status_handlers_total{handler="commit"}` | 커밋 횟수가 설계대로 1/N 이 됐는가 (조작 검증) | ✅ 존재 |
| `mysql_global_status_threads_running` | ④에서 «풀이 병목» 과 «DB 가 병목» 을 가른다 | ✅ 존재 |
| `mysql_global_status_innodb_row_lock_waits` | 단일 세션 핫스팟이 살아 있는지 | ✅ 존재 |
| `mysql_global_status_buffer_pool_pages{state=…}` | 시딩 규모가 버퍼풀을 넘겼는지 | ✅ 존재 |

> 🔴 **커밋 횟수는 `Com_commit` 이 아니라 `Handler_commit` 으로 센다.** 초안은 `commands_total{command="commit"}` 를 적었는데, 로컬 확인에서 **0 이었다** — `Com_commit` 은 **명시적 `COMMIT` 문만** 세고 autocommit 커밋은 안 센다. 같은 구간에서 `Handler_commit` 은 1,042 로 올라가 있었다.
>
> ✅ **실경로로 확인했다 (2026-08-09).** 초안은 *"앱 경로(`@Transactional`)는 명시적 커밋이라 `Com_commit` 도 오를 것으로 보이지만 확인하지 않았다"* 로 열어뒀는데, **실제로 쏴보니 앱 경로에서도 `Com_commit` 은 +0 이다.** 추측이 틀렸다 — `Handler_commit` 이 선택지가 아니라 **유일한 답**이었다.

⚠️ **카운터 델타에는 배경 활동이 섞인다.** 세션 타임아웃 스케줄러·헬스체크·아웃박스 발행기의 커밋, 그리고 카운터를 읽는 연결 자체의 커밋까지 들어온다. 판이 수천 요청이면 비율상 작지만 **0 이 아니다** — 프로브에서 요청 5건에 `Handler_commit +51` 이 나온 것이 그 예다(대부분이 배경·측정 하네스 몫이다). 판별 절대 횟수가 아니라 **팔 사이의 비**로 읽는다.

⚠️ 익스포터 계정은 `mysql/exporter-user.sql` 로 분리했다(`MAX_USER_CONNECTIONS 3`). 앱 계정과 필요 권한이 교집합 없이 갈리고, 익스포터가 커넥션을 흘려도 피시험 대상보다 먼저 실패하게 만든다.

⚠️ **대시보드 패널은 이번에 안 만든다.** 3차에서 «그래프 만들다 판을 놓치는» 비용을 이미 냈다. Prometheus 쿼리로 판별 값만 뽑고, 패널은 결과가 나온 뒤 필요하면 만든다.

### 3-1-1. ✅ 착수 전 로컬 프로브 — 메커니즘은 이미 보였다 (2026-08-09, 무료)

EC2 에 돈을 쓰기 전에 실경로(실제 MySQL · 실제 gRPC · 실제 `@Transactional`)로 세 가지를 확인했다. 세 가지를 확인하러 갔는데 **네 번째가 딸려 나왔다.**

| 확인 대상 | 결과 |
|---|---|
| N=10 의 요청 크기(455KB)가 gRPC 한도를 통과하는가 | ✅ 통과 (`max-inbound` 설정이 없어 기본값 4MB 에 기대고 있었다) |
| 행 동일성이 H2 단위테스트 밖에서도 성립하는가 | ✅ 25행이 **완전히 동일** |
| 앱 경로가 `Com_commit` 을 올리는가 | 🔴 **안 올린다** (+0) — `Handler_commit` 이 유일한 답 |

**딸려 나온 것 — 같은 행을 쓰면서 fsync 만 5배 갈렸다:**

| 팔 | 요청 | 저장 행 | `Handler_commit` | `Innodb_os_log_fsyncs` |
|---|:--:|:--:|:--:|:--:|
| A (N=1) | 25프레임 × **5요청** | 25 | +51 | **+49** |
| B (N=5) | 125프레임 × **1요청** | 25 | +7 | **+10** |

**행은 글자 그대로 같은데 fsync 는 약 4.9배다.** ③이 세운 가설 — *"커밋 횟수가 fsync 횟수를 정하고, 행 작업량과는 무관하다"* — 의 **전반부가 여기서 이미 확인된다.**

> 🟢 **이건 로컬이지만 인용해도 되는 종류다.** [[project_loadtest_env_constraint]] 가 그은 선이 *"메커니즘·구조는 신뢰 가능, 절대 처리량은 불가"* 인데, «커밋 1회당 fsync 몇 회» 는 박스 성능이 아니라 **구조**다.
>
> 🔴 **동시에, 이것으로 ③을 닫을 수는 없다.** 여기서 안 나온 것이 ③의 후반부다 — *"그래서 **처리량**이 오르는가"*. fsync 가 줄어도 다른 것이 천장이면 rows/sec 는 안 오른다. 그리고 이 박스의 디스크는 EBS(네트워크 디스크)가 아니라 로컬 SSD 라, **fsync 1회의 비용이 rig 와 다르다.** 3.47배라는 3차의 배수가 성립한 조건 자체가 EBS 였다.

### 3-2. ③ 커밋 횟수 스윕

**고정**: c=100 · pool=20 · 내구성 **기본값**(`flush=1`/`sync_binlog=1` — 천장이 fsync 인 상태여야 레버가 보인다) · 다세션 페이로드(`gen_batch_multi.py`, 단일 핫세션 아티팩트 제거) · **총 기록 행 수**

**변수**: 요청당 rep 수 N ∈ **1 · 5 · 10**

| N | `--reps` | 요청당 행 | `-n` | 총 행 |
|:--:|:--:|:--:|:--:|:--:|
| 1 | 25 | 5 | 15,000 | 75,000 |
| 5 | 125 | 25 | 3,000 | 75,000 |
| 10 | 250 | 50 | 1,500 | 75,000 |

🔴 **`--reps` 는 반드시 5(다운샘플 윈도우)의 배수여야 한다.** 배수가 아니면 배치 경계가 «어느 프레임이 남는가» 를 바꿔서(§2-1 의 경계 조건 테스트), 이 실험의 조작이 «커밋 횟수» 하나가 아니게 된다. 위 세 값은 전부 배수다.

**판정** — 세 가지를 같이 본다. 하나만 보면 §2 의 교란을 못 가른다.

1. **rows/sec** (= RPS × 요청당 행) — 레버의 크기
2. **fsyncs/sec** — 고정이면 «커밋이 천장» 확정, 같이 오르면 fsync 가 아니라 다른 것이었다
3. **p99 (요청 단위)** — N 배 커진 요청의 지연. rows/sec 가 올라도 개별 요청이 N 배 느려지면 사용자 관점은 다르다

> 📌 **임계선을 걸지 않는다.** 이 실험의 답은 «몇 % 이상이면 좋다» 가 아니라 «올라가는가 / 무엇이 고정인가» 다. 판정선을 정할 근거가 없는 곳에는 안 넣는다.

### 3-3. ④ 내구성 완화 상태 pool 재스윕

**고정**: c=100 · N=1(3차와 같은 조건) · `innodb_flush_log_at_trx_commit=2`·`sync_binlog=0` (**진단용 설정이고 채택이 아니다**)

**변수**: pool ∈ **2 · 5 · 10 · 20**

**판정**: 기존 확정 기준 그대로 — **plateau(pool=20) 대비 90% + 실패율 병기**. ⚠️ 90% 가 임의값인 것은 [`./pool-cliff-vs-concurrency.md`](./pool-cliff-vs-concurrency.md) §8 에 이미 박혀 있고, 결과 문서에도 다시 적는다.

**대조**: 같은 pool 사다리를 **기본 내구성**에서도 2점(pool 5·20)만 찍는다. «절벽이 완화 상태에서만 나타난다» 를 말하려면 반대편 점이 있어야 한다.

### 3-4. 판 길이와 스크레이프 간격 — 지난 두 결함을 동시에 피하는 조합

3차는 이 둘을 **번갈아 밟았다**:

| 회차 | 선택 | 결과 |
|---|---|---|
| 2차 오전 | `-n 2000` (판 9.6초) | 스크레이프 15초 > 판 길이 → **판당 샘플 0~1개**, 게이지를 판별로 귀속 불가 |
| 3차 저녁 | `-z 60s` | 종료 시 in-flight 강제 취소 → **판당 fail≈100** |

**이번**: `-n` 고정을 유지하되 **판이 60초 이상 되도록 `-n` 을 키우고**, obs 의 `scrape_interval` 을 **5초**로 내린다 → 판당 12샘플 이상 · 종료 아티팩트 0.

⚠️ 3차의 관측 RPS(~230)로 역산한 값이라 **실제 판 길이는 첫 판에서 확인하고 필요하면 `-n` 을 조정**한다. 판이 60초를 못 채우면 그 판은 지표 귀속에 쓰지 않는다.

⚠️ **exporter 전용 MySQL 계정**을 만든다 — `PROCESS`, `REPLICATION CLIENT`, `SELECT ON performance_schema.*`. `shadowfit` 계정 재사용 금지.
⚠️ **지표 포트를 인터넷에 열지 않는다.** 전부 사설망, SG 는 내 IP 만.

## 6. 이 실험이 답하지 못하는 것 (미리 박제)

- **절대 RPS 는 참고용이다.** self-managed MySQL on EC2 + 합성 페이로드. 값 분포도 균일하다([[project_synthetic_data_distribution_limit]])
- **③을 «채택하자» 로 만들지 못한다.** 이 실험은 크기만 잰다. 유실 단위 N rep 과 `last_active_at` 갱신 주기 N배는 [`./session-liveness-vs-elapsed-time.md`](./session-liveness-vs-elapsed-time.md) 의 생존 판정과 얽혀 있고, 그건 별도 결정이다
- **c 를 «동시 사용자 N명» 으로 환산 못 한다.** rep 간격이 여전히 미실측이다
- **N > 10 · pool < 2 · c ≠ 100** 은 안 본다
- **디스크 사양**(gp3 기본값 외)은 이번에도 안 본다
- ④에서 절벽이 나와도 **그 값을 `maximum-pool-size` 의 근거로 쓸 수 없다** — 완화 설정은 채택하지 않은 상태이기 때문이다. 답하는 것은 «2차의 «절벽 없음» 이 어떤 조건 아래의 문장이었나» 까지다
