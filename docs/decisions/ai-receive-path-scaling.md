## 0. 지금까지 지워진 것

| 후보 | 어떻게 지웠나 |
|---|---|
| GIL | R6 — 프로세스/스레드 0.96~1.06x |
| 하드웨어·코어 | R6 — 순수 추론은 **15.2 vCPU** 까지 간다 |
| 검출기 풀 상한 | 풀 = **201** (컨테이너 로그) |
| 부하기 CPU | §T — 코어 4→2 에도 무변화 |
| anyio 워커 한도(40) | 40↔128 교차 4판 — 차이 −0.6%(변동 이내) |
| 부하기 프로세스 수 | 1×160 = **350.85** vs 2×80 = **350.28** (0.2%) |
| AI 프로세스 안의 락 | 프로파일 — 파킹 스택이 `queue.get`(**일감 대기**)이지 락이 아니다 |

**남은 하나: 수신 경로(단일 이벤트 루프).** 348 RPS × 40KB 페이로드를 **한 스레드**가 읽고
파싱해 워커에 넘긴다. 프로파일 3판 중 2판에서 `active+gil` 이었다.

⚠️ **이건 가설이다.** 「워커 앞에서 막힌다」까지가 관측이고, 그 앞이 이벤트 루프라는 것은
소거법의 결론이지 직접 측정이 아니다.

## 1. 구조 — 왜 «워커를 늘리면 되잖아» 가 안 되나

```
uvicorn (단일 프로세스 · 단일 이벤트 루프)   ← Dockerfile:19, --workers 없음
├─ anyio 워커 스레드풀 (기본 40)             ← def detect_pose 가 여기서 돈다
├─ gRPC 서버 스레드 (포트 8585)              ← main.py lifespan 이 띄운다
├─ 검출기 풀 (201)                           ← 프로세스 메모리
└─ 세션 레지스트리                            ← 🔴 프로세스 메모리
```

**`uvicorn --workers N` 을 그냥 켤 수 없는 이유가 셋이고, 큰 순서로 이렇다:**

| # | 걸림돌 | 왜 |
|---|---|---|
| **1** | 🔴 **세션 상태가 프로세스 메모리에 있다** | 워커가 여럿이면 같은 세션의 프레임이 **다른 워커**로 갈 수 있다. 그 워커엔 그 세션이 없다 |
| 2 | **gRPC 서버를 lifespan 이 띄운다** | 워커마다 하나씩 띄워 **같은 포트를 잡으려 든다** |
| 3 | 검출기 풀이 프로세스마다 생긴다 | 메모리가 워커 배수로 는다(개당 98.7MB × 201) |

1번이 본질이다. 2·3번은 배치 문제지만 1번은 **설계 문제**다.

## 2. 먼저 — 확인은 코드를 안 고치고 할 수 있다

🟢 **`uvicorn --workers` 를 건드리기 전에, 가설 확인만 먼저 할 수 있다.**

**AI 컨테이너를 2개 띄우고(8000·8001), 부하기가 세션을 반씩 나눠 보낸다.**
세션 하나의 프레임은 **항상 같은 컨테이너**로 가므로 §1-1 의 문제가 생기지 않는다.

| 결과 | 뜻 |
|---|---|
| 합계가 **~700 RPS** 로 는다 | **확정** — 프로세스당 수신 경로가 천장이다 |
| 합계가 **~350 에 머문다** | 반증 — 천장은 프로세스 밖(호스트 네트워크·커널·부하기)에 있다 |

- **코드 변경 0.** 이미 있는 이미지를 포트만 바꿔 하나 더 띄운다
- 부하기는 `--sessions 80` 짜리 두 프로세스를 서로 다른 `--ai` 주소로 보내면 된다
  (§2-4 에서 이미 2프로세스 부하가 정상 동작하는 것을 확인했다)
- 소요 **약 15분**

🔴 **박스가 살아 있는 동안만 된다.** 로컬 물리 2코어로는 «9.5 vCPU 에서 멈춘다» 는 상태 자체를
만들 수 없다.

## 3. 확인됐다면 — 고치는 길 네 갈래

### ㄱ. 세션 상태를 프로세스 밖으로 (Redis 등) + `--workers N`

| | |
|---|---|
| 장점 | 정공법. 수평 확장의 문 자체가 열린다 |
| 단점 | **가장 크다.** 세션 레지스트리·검출기 소유권이 전부 이 전제 위에 서 있다. 검출기는 애초에 **직렬화가 불가능**하다(MediaPipe 객체) — 상태를 밖에 둬도 **검출기는 여전히 프로세스에 묶인다** |
| 판정 | 🔴 **이 문제를 푸는 방법으로는 부적합.** 검출기가 못 따라오므로 절반만 푼다 |

### ㄴ. 스티키 라우팅 — 앞에 프록시를 두고 `session_id` 로 고정 배분

| | |
|---|---|
| 장점 | **세션 상태를 안 옮겨도 된다.** 같은 세션은 항상 같은 프로세스로 간다 = 지금 구조 그대로 |
| 단점 | 프록시가 하나 는다(§[reverse-proxy-and-tls](./reverse-proxy-and-tls.md) 와 같은 자리). gRPC 포트·검출기 풀 메모리는 여전히 프로세스마다 |
| 비고 | §2 의 확인 실험이 **사실상 이 안의 수동 버전**이다 — 확인이 곧 설계 검증이 된다 |

### ㄷ. 수신 부담 자체를 줄인다 (구조 무변경)

이벤트 루프가 힘든 이유가 **40KB base64 JSON × 348/s** 라면, 그 양을 줄이면 된다.

| 레버 | 크기 | 비고 |
|---|---|---|
| base64 → 바이너리 업로드 | 페이로드 **약 −25%** | base64 는 3바이트를 4자로 부풀린다. 계약 변경 |
| 프레임 수 감소 | [#92](https://github.com/Shadowfit/init/issues/92) — 휴식 중 프레임을 안 보내면 **세션당 800~1,350회** 절약 | 이미 등록된 항목 |
| 해상도 | ❌ **효과 없음** | R7 에서 320x240~960x720 이 추론 시간 무차별로 확인됨 |

| | |
|---|---|
| 장점 | **구조를 안 건드린다.** #92 는 어차피 할 일이다 |
| 단점 | 천장을 **옮길 뿐 없애지 못한다.** 배수가 아니라 상수만큼 |

### ㄹ. 고치지 않는다 — **먼저 「지금 천장이 모자란가」를 묻는다**

🔴 **이 문서에서 가장 중요한 갈래다.**

지금 천장 **348 RPS ÷ 3fps = 동시 116세션**이다. 그런데 이 앱은 **회원당 활성 세션이 1개**이므로
**동시 116세션 = 동시에 운동 중인 사람 116명**이다.

DAU 1,000 가정([[feedback_state_assumption_design_to_it]])에서 **동시에 운동 중인 사람이
116명을 넘는지**가 답이다. 그 숫자를 **아직 세운 적이 없다.**

| | |
|---|---|
| 장점 | 안 필요한 최적화를 안 한다. **비용 0** |
| 단점 | 「용량 천장을 알고도 안 고쳤다」가 아니라 **「필요를 계산해보고 안 고쳤다」** 여야 한다 — 그 계산이 선행 |

## 4. 자원 — 이게 지원축에 무엇을 주나

정직하게: 이 프로젝트의 지원축은 **백엔드(Spring)·DBA** 다([[user_career_target]]).
이 항목은 **AI 축**이라 서류 키워드로는 안 붙는다.

**그런데 서사로는 값이 있다:**

> 「용량 천장을 재고 → 후보를 일곱 개 세워 하나씩 반증하고 → 프로파일로 좁히고 →
> **고치기 전에 필요량부터 계산했다**」

이건 «성능을 올렸다» 보다 강한 이야기다. 특히 §2 의 확인 실험은 **코드를 안 고치고 가설을
가르는 설계**라 그 자체가 사례가 된다.

⚠️ 반대로, ㄱ~ㄷ 을 실제로 **구현**하는 것은 지원축에 거의 기여하지 않는다.
**「확인까지」와 「구현까지」는 다른 결정이다.**

## 7. 정직하게 비어 있는 것

- **「이벤트 루프가 범인」은 소거법의 결론이지 측정이 아니다.** §2 가 그걸 가른다
- **400ms 지연의 소재를 안 쟀다.** 요청당 450ms 중 계산은 14~26ms 인데, 나머지가
  **어디서** 소모되는지는 관측하지 않았다(수신 큐·이벤트 루프·소켓 중 어디인지)
- **동시 운동자 수 상한을 세운 적이 없다**(§3-ㄹ). 이게 없으면 「고쳐야 하나」에 답할 수 없다
- §2-4 에서 **무효판(`nolease` 100%)이 번갈아 난 조건을 규명하지 않았다.** 확인 실험에서
  같은 함정에 빠질 수 있다 — **`nolease` 를 반드시 볼 것**
