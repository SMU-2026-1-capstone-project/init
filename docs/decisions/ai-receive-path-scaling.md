## 0. 지금까지 지워진 것

| 후보 | 어떻게 지웠나 |
|---|---|
| GIL | R6 — 프로세스/스레드 0.96~1.06x |
| 하드웨어·코어 | R6 — 순수 추론은 **15.2 vCPU** 까지 간다 |
| 검출기 풀 상한 | 풀 = **201** (컨테이너 로그) |
| 부하기 CPU | §T — 코어 4→2 에도 무변화 |
| anyio 워커 한도(40) | 40↔128 교차 4판 — 차이 −0.6%(변동 이내) |
| 부하기 프로세스 수 | 1×160 = **350.85** vs 2×80 = **350.28** (0.2%) |
| AI 프로세스 안의 락 | 프로파일 — 파킹 스택이 `queue.get`(**일감 대기**)이지 락이 아니다 |

**남은 하나: 수신 경로(단일 이벤트 루프).** 348 RPS × 40KB 페이로드를 **한 스레드**가 읽고
파싱해 워커에 넘긴다. 프로파일 3판 중 2판에서 `active+gil` 이었다.

⚠️ **이건 가설이다.** 「워커 앞에서 막힌다」까지가 관측이고, 그 앞이 이벤트 루프라는 것은
소거법의 결론이지 직접 측정이 아니다.

## 1. 구조 — 왜 «워커를 늘리면 되잖아» 가 안 되나

```
uvicorn (단일 프로세스 · 단일 이벤트 루프)   ← Dockerfile:19, --workers 없음
├─ anyio 워커 스레드풀 (기본 40)             ← def detect_pose 가 여기서 돈다
├─ gRPC 서버 스레드 (포트 8585)              ← main.py lifespan 이 띄운다
├─ 검출기 풀 (201)                           ← 프로세스 메모리
└─ 세션 레지스트리                            ← 🔴 프로세스 메모리
```

**`uvicorn --workers N` 을 그냥 켤 수 없는 이유가 셋이고, 큰 순서로 이렇다:**

| # | 걸림돌 | 왜 |
|---|---|---|
| **1** | 🔴 **세션 상태가 프로세스 메모리에 있다** | 워커가 여럿이면 같은 세션의 프레임이 **다른 워커**로 갈 수 있다. 그 워커엔 그 세션이 없다 |
| 2 | **gRPC 서버를 lifespan 이 띄운다** | 워커마다 하나씩 띄워 **같은 포트를 잡으려 든다** |
| 3 | 검출기 풀이 프로세스마다 생긴다 | 메모리가 워커 배수로 는다(개당 98.7MB × 201) |

1번이 본질이다. 2·3번은 배치 문제지만 1번은 **설계 문제**다.

## 2. 확인 방법 — 초안이 틀렸고, 실제로 해보고 알았다

### 2-0. ❌ 폐기된 초안 — 「컨테이너 2개에 세션을 반씩」

*"AI 컨테이너를 2개 띄우고 부하기가 세션을 반씩 나눠 보낸다. 세션 하나의 프레임은 항상 같은
컨테이너로 가므로 문제가 없다. **코드 변경 0.**"*

🔴 **틀렸다. 2026-08-17 에 실제로 띄워 보고 알았다.**

`shadowfit-ai2` 를 8001 에 띄우고 5세션 스모크를 돌렸더니 **«20초 안에 분석기가 안 붙었다»**
로 판이 무효였다. 이유는 §1-1 이 **프레임 경로에만** 적용된다고 본 것이 좁았기 때문이다:

> **세션이 어느 AI 에 붙을지는 클라이언트가 아니라 Spring 이 정한다.**
> `AI_SERVER_HOST=shadowfit-ai` — **주소가 하나뿐이다.** 세션 생성 때 Spring 이 그 주소로
> gRPC `StartAnalysis` 를 불러 **1번 컨테이너에** 분석기를 붙인다. 프레임을 2번으로 보내면
> 요청은 도달하지만(로그에 `200 OK` 가 찍힌다) 그 컨테이너엔 세션이 없어 반려된다.

**즉 «코드 변경 0» 이 아니다.** 스티키 라우팅(§3-ㄴ)을 하려면 **Spring 의 attach 경로부터**
어느 인스턴스에 붙일지 고를 수 있어야 한다. 이건 프록시만으로 안 되고 **Spring 이 관여한다.**

### 2-1. 🟢 대체안 — 페이로드만 줄인다 (계산량 고정)

가설이 「단일 이벤트 루프가 **바이트를 읽고 파싱하는 것**이 천장」이면, **보내는 양을 줄이면
천장이 올라가야 한다.**

**같은 160세션·같은 코드로, 프레임만 640x480 → 320x240 으로 바꾼다.**

- 🔑 **R7 이 이 실험을 가능하게 한다** — 해상도는 **추론 시간을 안 바꾼다**(13.7 ↔ 13.7ms).
  즉 **계산량은 고정되고 전송·파싱 바이트만 변한다.** 변수가 하나다
- 실측 축소율: 프레임당 **13,376자 → 5,184자 (39%)**
- 코드 변경 0(진짜로). `frames.json` 축소판 하나면 된다

| 결과 | 뜻 |
|---|---|
| 처리량이 **크게 오른다** | **확정** — 수신·파싱 바이트가 천장이다 |
| **그대로다** | 바이트 양은 아니다. 이벤트 루프 스케줄링·소켓 처리 등 다른 곳 |

⚠️ 이건 §2-0 보다 **약한 확인**이다 — 「프로세스를 늘리면 배수로 는다」를 직접 보는 게 아니라
「부담을 줄이면 는다」를 보는 것이라, 반증이 나와도 이벤트 루프를 완전히 지우지는 못한다.

### 2-2. ✅ 실행 결과 (2026-08-17) — **바이트 양은 천장이 아니다**

160세션 · 90초 · 교차 배열. **`nolease` 로 유효판을 갈랐다**(§2-3).

| 판 | 페이로드 | RPS | p50 | `nolease` | 유효 |
|---|---:|---:|---:|---:|:--:|
| big_1 | 100% | 350.58 | 448.3 | 0 | ✅ |
| big_2 | 100% | 346.43 | 454.0 | 0 | ✅ |
| small_2 | **39%** | **375.76** | 418.2 | 0 | ✅ |
| small_4 | **39%** | **376.42** | 417.6 | 0 | ✅ |
| ~~small_1~~ | 39% | ~~480.38~~ | 14.0 | **38,084** | ❌ |
| ~~small_3~~ | 39% | ~~478.86~~ | 14.1 | **38,254** | ❌ |

**페이로드를 61% 줄였는데 처리량은 348.5 → 376.1, 즉 +7.9% 다.**
두 small 판은 서로 0.2% 안에서 일치한다(변동 대비 효과가 충분히 크다).

→ **반증에 가깝다.** 바이트 양이 천장이면 61% 를 덜어냈을 때 훨씬 크게 올랐어야 한다.
효과는 **실재하지만 작다.**

### 🔑 그래서 레버의 값이 갈린다

| 레버 | 예상 효과 | 근거 |
|---|---|---|
| base64 → 바이너리 (−25% 바이트) | **미미** | 61% 를 덜어도 +7.9% 였다 |
| 해상도 낮추기 | **없음** | R7 (추론 무차별) + 이 실험(바이트 무관) |
| **프레임 «수» 줄이기 ([#92](https://github.com/Shadowfit/init/issues/92))** | 🟢 **비례** | 천장이 **요청 «건수»** 쪽이라면 건수를 줄이는 것만 듣는다 |

**남은 형태는 «크기» 가 아니라 «건당 고정비»** 다 — 요청 하나를 받아 넘기는 데 드는
스케줄링·컨텍스트 전환·ASGI 처리. 크기와 무관한 부분이다. **이것도 아직 직접 측정은 아니다.**

### 2-3. 🔴 곁다리 — rig 이 조용히 무효판을 낸다

이 실험에서만 무효판이 **둘** 나왔고, 앞선 프로세스 수 실험(§2-4)에서도 **셋** 나왔다.
전부 같은 서명이다: **`nolease` 가 요청의 99.6~100% · RPS 480 · p50 14ms.**

**RPS 만 보면 «천장을 뚫었다» 로 읽힌다.** 실제로는 즉시 반려를 초당 480번 받은 것이다.

**원인 가설(확인됨)**: 판 사이 간격이 **세션 정리 주기보다 짧으면** 앞 판 세션이 살아 있는 채로
다음 판이 같은 계정을 재사용해 attach 가 깨진다. `small_3` 을 **80초 쉬고** 다시 돌리니
(`small_4`) **유효판이 나왔다.** 이 실험의 판 간격은 12초였다.

⚠️ **이건 1회 확인이다.** 정확한 주기·조건은 안 쟀다. **이슈로 등록할 것.**

## 3. 확인됐다면 — 고치는 길 네 갈래

### ㄱ. 세션 상태를 프로세스 밖으로 (Redis 등) + `--workers N`

| | |
|---|---|
| 장점 | 정공법. 수평 확장의 문 자체가 열린다 |
| 단점 | **가장 크다.** 세션 레지스트리·검출기 소유권이 전부 이 전제 위에 서 있다. 검출기는 애초에 **직렬화가 불가능**하다(MediaPipe 객체) — 상태를 밖에 둬도 **검출기는 여전히 프로세스에 묶인다** |
| 판정 | 🔴 **이 문제를 푸는 방법으로는 부적합.** 검출기가 못 따라오므로 절반만 푼다 |

### ㄴ. 스티키 라우팅 — 앞에 프록시를 두고 `session_id` 로 고정 배분

| | |
|---|---|
| 장점 | **세션 상태를 안 옮겨도 된다.** 같은 세션은 항상 같은 프로세스로 간다 = 지금 구조 그대로 |
| 단점 | 프록시가 하나 는다(§[reverse-proxy-and-tls](./reverse-proxy-and-tls.md) 와 같은 자리). gRPC 포트·검출기 풀 메모리는 여전히 프로세스마다 |
| 🔴 비고 | **초안은 이 안을 «프록시만 두면 된다» 로 봤는데 틀렸다**(§2-0). Spring 이 attach 대상을 정하므로 **Spring 도 같이 고쳐야 한다** — 안의 크기가 커진다 |

### ㄷ. 수신 부담 자체를 줄인다 (구조 무변경)

이벤트 루프가 힘든 이유가 **40KB base64 JSON × 348/s** 라면, 그 양을 줄이면 된다.

| 레버 | 크기 | 비고 |
|---|---|---|
| base64 → 바이너리 업로드 | 페이로드 **약 −25%** | base64 는 3바이트를 4자로 부풀린다. 계약 변경 |
| 프레임 수 감소 | [#92](https://github.com/Shadowfit/init/issues/92) — 휴식 중 프레임을 안 보내면 **세션당 800~1,350회** 절약 | 이미 등록된 항목 |
| 해상도 | ❌ **효과 없음** | R7 에서 320x240~960x720 이 추론 시간 무차별로 확인됨 |

| | |
|---|---|
| 장점 | **구조를 안 건드린다.** #92 는 어차피 할 일이다 |
| 단점 | 천장을 **옮길 뿐 없애지 못한다.** 배수가 아니라 상수만큼 |

### ㄹ. 고치지 않는다 — **먼저 「지금 천장이 모자란가」를 묻는다**

🔴 **이 문서에서 가장 중요한 갈래다.**

지금 천장 **348 RPS ÷ 3fps = 동시 116세션**이다. 그런데 이 앱은 **회원당 활성 세션이 1개**이므로
**동시 116세션 = 동시에 운동 중인 사람 116명**이다.

DAU 1,000 가정([[feedback_state_assumption_design_to_it]])에서 **동시에 운동 중인 사람이
116명을 넘는지**가 답이다. 그 숫자를 **아직 세운 적이 없다.**

| | |
|---|---|
| 장점 | 안 필요한 최적화를 안 한다. **비용 0** |
| 단점 | 「용량 천장을 알고도 안 고쳤다」가 아니라 **「필요를 계산해보고 안 고쳤다」** 여야 한다 — 그 계산이 선행 |

## 4. 자원 — 이게 지원축에 무엇을 주나

정직하게: 이 프로젝트의 지원축은 **백엔드(Spring)·DBA** 다([[user_career_target]]).
이 항목은 **AI 축**이라 서류 키워드로는 안 붙는다.

**그런데 서사로는 값이 있다:**

> 「용량 천장을 재고 → 후보를 일곱 개 세워 하나씩 반증하고 → 프로파일로 좁히고 →
> **고치기 전에 필요량부터 계산했다**」

이건 «성능을 올렸다» 보다 강한 이야기다. 특히 §2 의 확인 실험은 **코드를 안 고치고 가설을
가르는 설계**라 그 자체가 사례가 된다.

⚠️ 반대로, ㄱ~ㄷ 을 실제로 **구현**하는 것은 지원축에 거의 기여하지 않는다.
**「확인까지」와 「구현까지」는 다른 결정이다.**

## 7. 정직하게 비어 있는 것

- **「이벤트 루프가 범인」은 여전히 소거법의 결론이다.** §2-2 는 그 중 «바이트 파싱» 형태를
  지웠을 뿐, «건당 고정비» 형태는 안 쟀다
- **400ms 지연의 소재를 안 쟀다.** 요청당 450ms 중 계산은 14~26ms 인데, 나머지가
  **어디서** 소모되는지는 관측하지 않았다(수신 큐·이벤트 루프·소켓 중 어디인지)
- **동시 운동자 수 상한을 세운 적이 없다**(§3-ㄹ). 이게 없으면 「고쳐야 하나」에 답할 수 없다
- §2-4 에서 **무효판(`nolease` 100%)이 번갈아 난 조건을 규명하지 않았다.** 확인 실험에서
  같은 함정에 빠질 수 있다 — **`nolease` 를 반드시 볼 것**
