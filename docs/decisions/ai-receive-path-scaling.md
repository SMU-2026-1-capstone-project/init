## 0. 지금까지 지워진 것

| 후보 | 어떻게 지웠나 |
|---|---|
| GIL | R6 — 프로세스/스레드 0.96~1.06x |
| 하드웨어·코어 | R6 — 순수 추론은 **15.2 vCPU** 까지 간다 |
| 검출기 풀 상한 | 풀 = **201** (컨테이너 로그) |
| 부하기 CPU | §T — 코어 4→2 에도 무변화 |
| anyio 워커 한도(40) | 40↔128 교차 4판 — 차이 −0.6%(변동 이내) |
| 부하기 프로세스 수 | 1×160 = **350.85** vs 2×80 = **350.28** (0.2%) |
| AI 프로세스 안의 락 | 프로파일 — 파킹 스택이 `queue.get`(**일감 대기**)이지 락이 아니다 |

**남은 하나: 수신 경로(단일 이벤트 루프).** 348 RPS × 40KB 페이로드를 **한 스레드**가 읽고
파싱해 워커에 넘긴다. 프로파일 3판 중 2판에서 `active+gil` 이었다.

⚠️ **이건 가설이다.** 「워커 앞에서 막힌다」까지가 관측이고, 그 앞이 이벤트 루프라는 것은
소거법의 결론이지 직접 측정이 아니다.

## 1. 구조 — 왜 «워커를 늘리면 되잖아» 가 안 되나

```
uvicorn (단일 프로세스 · 단일 이벤트 루프)   ← Dockerfile:19, --workers 없음
├─ anyio 워커 스레드풀 (기본 40)             ← def detect_pose 가 여기서 돈다
├─ gRPC 서버 스레드 (포트 8585)              ← main.py lifespan 이 띄운다
├─ 검출기 풀 (201)                           ← 프로세스 메모리
└─ 세션 레지스트리                            ← 🔴 프로세스 메모리
```

**`uvicorn --workers N` 을 그냥 켤 수 없는 이유가 셋이고, 큰 순서로 이렇다:**

| # | 걸림돌 | 왜 |
|---|---|---|
| **1** | 🔴 **세션 상태가 프로세스 메모리에 있다** | 워커가 여럿이면 같은 세션의 프레임이 **다른 워커**로 갈 수 있다. 그 워커엔 그 세션이 없다 |
| 2 | **gRPC 서버를 lifespan 이 띄운다** | 워커마다 하나씩 띄워 **같은 포트를 잡으려 든다** |
| 3 | 검출기 풀이 프로세스마다 생긴다 | 메모리가 워커 배수로 는다(개당 98.7MB × 201) |

1번이 본질이다. 2·3번은 배치 문제지만 1번은 **설계 문제**다.

## 2. 확인 방법 — 초안이 틀렸고, 실제로 해보고 알았다

### 2-0. ❌ 폐기된 초안 — 「컨테이너 2개에 세션을 반씩」

*"AI 컨테이너를 2개 띄우고 부하기가 세션을 반씩 나눠 보낸다. 세션 하나의 프레임은 항상 같은
컨테이너로 가므로 문제가 없다. **코드 변경 0.**"*

🔴 **틀렸다. 2026-08-17 에 실제로 띄워 보고 알았다.**

`shadowfit-ai2` 를 8001 에 띄우고 5세션 스모크를 돌렸더니 **«20초 안에 분석기가 안 붙었다»**
로 판이 무효였다. 이유는 §1-1 이 **프레임 경로에만** 적용된다고 본 것이 좁았기 때문이다:

> **세션이 어느 AI 에 붙을지는 클라이언트가 아니라 Spring 이 정한다.**
> `AI_SERVER_HOST=shadowfit-ai` — **주소가 하나뿐이다.** 세션 생성 때 Spring 이 그 주소로
> gRPC `StartAnalysis` 를 불러 **1번 컨테이너에** 분석기를 붙인다. 프레임을 2번으로 보내면
> 요청은 도달하지만(로그에 `200 OK` 가 찍힌다) 그 컨테이너엔 세션이 없어 반려된다.

**즉 «코드 변경 0» 이 아니다.** 스티키 라우팅(§3-ㄴ)을 하려면 **Spring 의 attach 경로부터**
어느 인스턴스에 붙일지 고를 수 있어야 한다. 이건 프록시만으로 안 되고 **Spring 이 관여한다.**

### 2-1. 🟢 대체안 — 페이로드만 줄인다 (계산량 고정)

가설이 「단일 이벤트 루프가 **바이트를 읽고 파싱하는 것**이 천장」이면, **보내는 양을 줄이면
천장이 올라가야 한다.**

**같은 160세션·같은 코드로, 프레임만 640x480 → 320x240 으로 바꾼다.**

- 🔑 **R7 이 이 실험을 가능하게 한다** — 해상도는 **추론 시간을 안 바꾼다**(13.7 ↔ 13.7ms).
  즉 **계산량은 고정되고 전송·파싱 바이트만 변한다.** 변수가 하나다
- 실측 축소율: 프레임당 **13,376자 → 5,184자 (39%)**
- 코드 변경 0(진짜로). `frames.json` 축소판 하나면 된다

| 결과 | 뜻 |
|---|---|
| 처리량이 **크게 오른다** | **확정** — 수신·파싱 바이트가 천장이다 |
| **그대로다** | 바이트 양은 아니다. 이벤트 루프 스케줄링·소켓 처리 등 다른 곳 |

⚠️ 이건 §2-0 보다 **약한 확인**이다 — 「프로세스를 늘리면 배수로 는다」를 직접 보는 게 아니라
「부담을 줄이면 는다」를 보는 것이라, 반증이 나와도 이벤트 루프를 완전히 지우지는 못한다.

### 2-2. ✅ 실행 결과 (2026-08-17) — **바이트 양은 천장이 아니다**

160세션 · 90초 · 교차 배열. **`nolease` 로 유효판을 갈랐다**(§2-3).

| 판 | 페이로드 | RPS | p50 | `nolease` | 유효 |
|---|---:|---:|---:|---:|:--:|
| big_1 | 100% | 350.58 | 448.3 | 0 | ✅ |
| big_2 | 100% | 346.43 | 454.0 | 0 | ✅ |
| small_2 | **39%** | **375.76** | 418.2 | 0 | ✅ |
| small_4 | **39%** | **376.42** | 417.6 | 0 | ✅ |
| ~~small_1~~ | 39% | ~~480.38~~ | 14.0 | **38,084** | ❌ |
| ~~small_3~~ | 39% | ~~478.86~~ | 14.1 | **38,254** | ❌ |

**페이로드를 61% 줄였는데 처리량은 348.5 → 376.1, 즉 +7.9% 다.**
두 small 판은 서로 0.2% 안에서 일치한다(변동 대비 효과가 충분히 크다).

→ **반증에 가깝다.** 바이트 양이 천장이면 61% 를 덜어냈을 때 훨씬 크게 올랐어야 한다.
효과는 **실재하지만 작다.**

### 🔑 그래서 레버의 값이 갈린다

| 레버 | 예상 효과 | 근거 |
|---|---|---|
| base64 → 바이너리 (−25% 바이트) | **미미** | 61% 를 덜어도 +7.9% 였다 |
| 해상도 낮추기 | **없음** | R7 (추론 무차별) + 이 실험(바이트 무관) |
| **프레임 «수» 줄이기 ([#92](https://github.com/Shadowfit/init/issues/92))** | 🟢 **비례** | 천장이 **요청 «건수»** 쪽이라면 건수를 줄이는 것만 듣는다 |

**남은 형태는 «크기» 가 아니라 «건당 고정비»** 다 — 요청 하나를 받아 넘기는 데 드는
스케줄링·컨텍스트 전환·ASGI 처리. 크기와 무관한 부분이다. **이것도 아직 직접 측정은 아니다.**

### 2-3. 🔴 곁다리 — `nolease` 무효판. **처음 읽은 것이 틀렸다**

무효판이 여러 번 났다. 전부 같은 서명이다: **`nolease` 가 요청의 99.6~100% · RPS 480 · p50 13~44ms.**
**RPS 만 보면 «천장을 뚫었다» 로 읽힌다.** 실제로는 즉시 반려를 초당 480번 받은 것이다.

🔴 **정정 (2026-08-17 저녁).** 처음에 `nolease` 를 **「세션이 AI 에 안 붙었다」** 로 읽고
「판 간격이 세션 정리 주기보다 짧아서」라고 적었다. **둘 다 틀렸다.**

rig 이 스스로 답을 적고 있었다:

> *"🔴 nolease 가 있다 — **풀에 자리가 없다.** «용량» 이지 «품질» 이 아니다"*

무효판 로그를 보면 **`setup_fail=0` 이고 「분석기가 안 붙었다」도 0건**이다 — **세션은 정상적으로
붙었다.** `nolease` 는 **검출기 풀에 빈자리가 없어** 프레임이 반려된 것이다.

### 그러면 이게 결함 신호다

풀은 **201**이고 판은 **160세션**이다. 세션당 검출기 하나면 **160 < 201 이라 여유가 있어야 한다.**
그런데 소진됐다는 것은 **앞 판의 리스가 안 풀렸다**는 뜻이다.

[`session-detector-ownership.md`](./session-detector-ownership.md) §8 이 구현 조건으로 못 박은
**「세션 종료 시 `close()`」·「비정상 종료 회수」** 가 바로 이 자리다. 그 안(ㄴ)은 채택 확정이지만
**구현 미착수**다.

⚠️ **미확인**: 왜 keep-alive 팔(§2-4)에서만 소진됐는지 모른다. 리스 해제 경로가 연결 재사용과
얽히는지, 아니면 판 순서·누적 때문인지 **안 갈렸다.**

🔴 **판정에 미치는 영향은 없다.** 이 문서의 모든 판정은 **`nolease=0` 인 유효판만으로** 냈다.
무효판의 «원인» 해석이 바뀐 것이지 «무효였다» 는 사실은 그대로다.

### 2-4. keep-alive 실험 — **답을 못 냈다**

`load_ai.py:57` 은 `urlopen` 이라 **요청마다 새 TCP 연결**을 연다(연결 재사용 없음).
348 RPS = 초당 348개의 새 연결이고, 그 비용은 **요청 크기와 무관**하다 — §2-2 의 「크기는 별
영향 없다」와 잘 맞는다. 그리고 **실제 모바일 클라이언트는 keep-alive 를 쓰므로**, 확인되면
「동시 116명」에 **조건이 붙는다.**

그래서 `http()` 를 스레드별 지속 연결로 바꾼 사본(`load_ai_ka.py`)을 만들어 쟀다.

| 판 | 팔 | RPS | `nolease` | 유효 |
|---|---|---:|---:|:--:|
| ka_1 | keep-alive | 479.82 | 38,347 | ❌ |
| url_1 | urllib | 348.95 | 0 | ✅ |
| url_2 | urllib | 348.17 | 0 | ✅ |
| ka_2 | keep-alive | 480.83 | 38,400 | ❌ |

**keep-alive 판만 전부 풀 소진**으로 무효였다 — 순서가 아니라 **팔로 갈렸다.**
따라서 **이 질문은 답을 못 냈다.** urllib 판 둘은 기준선(348.9 / 348.2)을 재확인했을 뿐이다.

⚠️ 원본 `load_ai.py` 는 **안 건드렸다.** 사본으로만 쟀다.

## 3. 확인됐다면 — 고치는 길 네 갈래

### ㄱ. 세션 상태를 프로세스 밖으로 (Redis 등) + `--workers N`

| | |
|---|---|
| 장점 | 정공법. 수평 확장의 문 자체가 열린다 |
| 단점 | **가장 크다.** 세션 레지스트리·검출기 소유권이 전부 이 전제 위에 서 있다. 검출기는 애초에 **직렬화가 불가능**하다(MediaPipe 객체) — 상태를 밖에 둬도 **검출기는 여전히 프로세스에 묶인다** |
| 판정 | 🔴 **이 문제를 푸는 방법으로는 부적합.** 검출기가 못 따라오므로 절반만 푼다 |

### ㄴ. 스티키 라우팅 — 앞에 프록시를 두고 `session_id` 로 고정 배분

| | |
|---|---|
| 장점 | **세션 상태를 안 옮겨도 된다.** 같은 세션은 항상 같은 프로세스로 간다 = 지금 구조 그대로 |
| 단점 | 프록시가 하나 는다(§[reverse-proxy-and-tls](./reverse-proxy-and-tls.md) 와 같은 자리). gRPC 포트·검출기 풀 메모리는 여전히 프로세스마다 |
| 🔴 비고 | **초안은 이 안을 «프록시만 두면 된다» 로 봤는데 틀렸다**(§2-0). Spring 이 attach 대상을 정하므로 **Spring 도 같이 고쳐야 한다** — 안의 크기가 커진다 |

🟢 **그 «커진 크기» 를 2026-08-23 에 폈다 — [`ai-sticky-routing.md`](./ai-sticky-routing.md).**
묶여 있는 결정이 **셋**이고(프레임 엔드포인트 계약 · 매핑 위치 · 장애 재배치) 따로 못 정한다.
그 문서가 정정한 것 둘 — ① 「Spring 이 정한다」는 **고른다는 뜻이 아니다.** 오늘 라우팅을 하는
주체는 없고 **고정 주소가 두 군데**(여기 `static://` 와 프론트 빌드 상수) 박혀 있다.
② 프레임 주소가 **설치본 안에** 있어서, 이 절이 본 것보다 한 겹 깊다.
🔴 **그 문서도 기본값은 «안 한다» 다** — 아래 ㄹ-1 계산과 從 R10-a 가 먼저다.

### ㄷ. 수신 부담 자체를 줄인다 (구조 무변경)

이벤트 루프가 힘든 이유가 **40KB base64 JSON × 348/s** 라면, 그 양을 줄이면 된다.

| 레버 | 크기 | 비고 |
|---|---|---|
| base64 → 바이너리 업로드 | 페이로드 **약 −25%** | base64 는 3바이트를 4자로 부풀린다. 계약 변경 |
| 프레임 수 감소 | [#92](https://github.com/Shadowfit/init/issues/92) — 휴식 중 프레임을 안 보내면 **세션당 800~1,350회** 절약 | 이미 등록된 항목 |
| 해상도 | ❌ **효과 없음** | R7 에서 320x240~960x720 이 추론 시간 무차별로 확인됨 |

| | |
|---|---|
| 장점 | **구조를 안 건드린다.** #92 는 어차피 할 일이다 |
| 단점 | 천장을 **옮길 뿐 없애지 못한다.** 배수가 아니라 상수만큼 |

### ㄹ. 고치지 않는다 — **먼저 「지금 천장이 모자란가」를 묻는다**

🔴 **이 문서에서 가장 중요한 갈래다.**

지금 천장 **348 RPS ÷ 3fps = 동시 116세션**이다. 그런데 이 앱은 **회원당 활성 세션이 1개**이므로
**동시 116세션 = 동시에 운동 중인 사람 116명**이다.

DAU 1,000 가정([[feedback_state_assumption_design_to_it]])에서 **동시에 운동 중인 사람이
116명을 넘는지**가 답이다. 그 숫자를 **아직 세운 적이 없다.**

| | |
|---|---|
| 장점 | 안 필요한 최적화를 안 한다. **비용 0** |
| 단점 | 「용량 천장을 알고도 안 고쳤다」가 아니라 **「필요를 계산해보고 안 고쳤다」** 여야 한다 — 그 계산이 선행 |

### ㄹ-1. 🟢 그 계산 (2026-08-23) — **안 넘는다. 단 여유가 인용되던 것의 절반이다**

**입력은 넷이고, 셋은 repo 에 있고 하나는 없었다.**

| 값 | 얼마 | 출처 |
|---|---|---|
| DAU | **1,000** | [`load-test-strategy.md`](./load-test-strategy.md) §4.2 «성공 시나리오». ⚠️ 같은 문서 §4.1 의 **냉정한 기본값은 DAU 30~50** 이다 |
| 세션/일/사용자 | **1.5** | 같은 문서 §4.2 |
| 세션 길이 | **15분** | `backend/src/main/resources/application.yml:252` — 「스쿼트 예상시간 15분」 |
| 피크 1시간 집중도 | **~18%** | 🔴 **어디에도 없다.** 아래 역산으로 복원했다 |

**「67」의 감춰진 가정이 그 넷째다.** §4.2 는 `DAU 1,000 × 1.5 = 1,500세션/일 → 피크 동시 ~67`
이라고만 적고 **중간 단계를 안 적었다.** 역산하면 `67 ÷ (1500 × 15/60) = 0.179` —
**피크 1시간에 하루 세션의 18%** 가 몰린다는 가정이다. 그러면 식이 닫힌다:

```
피크 동시 = DAU × 1.5 × p × (L / 60)
          = 1,000 × 1.5 × 0.18 × 0.25 = 67.5   ✓ §4.2 의 67 이 재현된다
```

### 🔴 천장이 하나가 아니다 — 여기가 이 계산의 실제 발견이다

| 천장 | 3fps 환산 | 조건 |
|---|---:|---|
| AI 단독 · in-process | **156세션** | `measure_ai_concurrency.py` — **HTTP 없음 · 동거 없음** |
| HTTP 경로 산술 | **116세션** | 348 RPS ÷ 3fps (이 문서 §3-ㄹ 머리) |
| **동거 + HTTP 실측** | **89~105세션** | P6 1·2라운드 plateau(267.6 fps = 89.2세션 · 2라운드 105.0) |

**배포 구성은 세 번째다** — `docker-compose.prod.yml` 이 MySQL·Spring·AI 를 한 호스트에 올린다.

### 답

**67 < 89. 안 넘는다.** 그런데 여유가 **1.33~1.57배**(89/67 · 105/67)다.

🔴 **여러 문서가 인용하는 «2.3배 여유» 는 156/67 이고, 그 156 은 단독 박스 값이다.**

### 언제 닿나 — 가정 하나만 움직여도 DAU 1,000 안에서 닿는다

| 조건 | 계수 | 89세션에 닿는 DAU |
|---|---:|---:|
| 기본 가정 (p=18% · L=15분) | 0.0675 | **1,319** |
| 세션이 **30분**이면 | 0.135 | **659** |
| 피크가 **25%** 면(저녁 집중) | 0.0938 | **949** |
| 둘 다면 | 0.1875 | **475** |

**그래서 결론은 「고칠 필요 없다」가 아니라 「지금 가정에서만 필요 없다」다.**
세션 길이 15분과 피크 18% 는 **둘 다 실측이 아니다** — 앞의 것은 타임아웃 계산용 예시값이고
뒤의 것은 아무도 적은 적이 없다. **DAU 보다 이 둘이 먼저 흔들린다.**

⚠️ **이 계산은 실측이 아니다.** 실사용 로그가 생기면 세션 길이와 시간대 분포를 **직접 세는 것**이

## 8. 실험 설계 — 「accept 경로가 천장인가」 (2026-08-17 작성, 미실행)

### 8-0. 가설과 판정선 (실행 전에 박는다)

**H: 연결 수락(accept) 경로가 천장이다.**
부하기가 `urlopen` 이라 **요청마다 새 TCP 연결**을 연다. 그 수락이 초당 ~348개로 묶이면
나머지 클라이언트는 **커널 accept 백로그**에서 기다린다.

이 하나로 관측 넷이 동시에 설명된다:

| 관측 | H 로 설명되나 |
|---|---|
| 1세션·로컬 프로브도 452ms | ✅ **같은 백로그에 줄 선다** — 이게 결정적 단서다 |
| 워커가 파킹(일감 큐가 빔) | ✅ 앱 안에는 `348 × 26ms ≈ 9`개만 들어와 있다 |
| CPU 어디도 포화 아님 | ✅ 대기는 커널 큐라 CPU 를 안 쓴다 |
| 페이로드 61%↓ 에 +7.9% | ✅ accept 는 **크기와 무관** |

**판정선은 유도해서 정한다**(임의값 금지 — [[feedback_no_arbitrary_threshold_values]]):
accept 가 유일한 제약이면 그것을 없앴을 때 **다음 제약은 CPU** 다.
R6 실측(순수 추론 15.2 vCPU · 프레임당 ~26ms)에서 **상한은 약 580 RPS** 다.

- **348 → 450 RPS 이상**으로 오르면 **H 지지**(CPU 천장 쪽으로 이동)
- **348 ±10% 에 머물면 H 반증**(연결은 범인이 아니다)
- 그 사이면 **부분 기여** — 몫을 숫자로 적는다

### 8-1. 1단계 — 커널이 이미 세고 있다 (부하기 안 고쳐도 된다, 2분)

**백로그가 넘치면 커널 카운터가 올라간다.** keep-alive 를 만들 필요 없이 **직접 증거**가 나온다.

| 지표 | 무엇 | 어디 |
|---|---|---|
| `ListenOverflows` | 백로그가 꽉 차서 **연결을 버렸다** | `nstat -az TcpExtListenOverflows` |
| `ListenDrops` | 같은 이유의 드롭 | `nstat -az TcpExtListenDrops` |
| 리스닝 소켓 `Recv-Q` / `Send-Q` | **현재 백로그 깊이 / 상한** | `ss -lnt` |

부하 전/후로 카운터를 찍고 **증분**을 본다. 부하 중 `Recv-Q` 도 같이 샘플링한다.

- **증분이 크거나 `Recv-Q` 가 상한에 붙어 있으면** → H **거의 확정**
- **증분 0 이고 `Recv-Q` 가 낮으면** → 백로그는 안 막혔다. H 가 **약해진다** → 2단계로

⚠️ **한계**: 백로그가 «넘치지 않으면서도» 수락이 느릴 수 있다. 그러면 이 단계는 조용하다 —
**반증이 아니라 «증거 없음»** 으로 읽어야 한다.

### 8-2. 2단계 — keep-alive 대조 (몫을 재려면)

`load_ai_ka.py`(오늘 만들어 둠)로 팔을 가른다. **선행 관문이 하나 있다.**

🔴 **풀 소진을 먼저 막아야 한다.** 오늘 keep-alive 판 둘이 `nolease` 100% 로 무효였다.
**우회는 실증됐다** — anyio 실험은 **판마다 컨테이너를 재시작**해서 4판 전부 유효했다.

| 요소 | 값 | 왜 |
|---|---|---|
| 팔 | urllib(현행) ↔ keep-alive | 나머지 전부 고정 |
| 판마다 | **AI 컨테이너 재시작** | 풀 리셋(실증된 우회) |
| 게이트 | **`nolease > 0` 이면 그 판 폐기·재실행** | 오늘 무효판 다섯을 그냥 지나칠 뻔했다 |
| 배열 | 버림 1 + 교차 3쌍 | 라운드 내 추세가 팔에 얹히지 않게 |
| 판당 | 160세션 · 90초 | 기존 라운드와 같은 조건 |
| 소요 | 약 25분 | 재시작·간격 포함 |

### 8-3. 무엇이 나오면 내가 틀린 것인가

- keep-alive 로 바꿨는데 **348 ±10%** → H 반증. 남는 건 앱 안쪽 건당 처리다
- 1단계가 조용한데 2단계에서 처리량이 오르면 → 「백로그」가 아니라 **연결 수립 자체의 비용**
  (소켓 생성·TIME_WAIT 등)이다. 같은 H 의 다른 형태
- **둘 다 아니면** §0 후보 목록을 다시 세워야 한다

### 8-4. 이 실험이 성공하면 바뀌는 것

**「동시 116명」이 실제 용량이 아니게 된다.** 실제 클라이언트는 keep-alive 를 쓴다.
그러면 오늘 잰 천장은 **부하기가 만든 천장**이고, `ai-coresidency-capacity.md` 와
[P6 라운드 README](../../loadtest/results/coresidency-aws-2026-08-17/README.md)의 용량 수치에
**전부 조건이 붙는다.**

⚠️ §T·프로세스 수 실험이 「부하기 아님」을 가리킨 것과 **모순되지 않는다** — 그 둘은 부하기의
**CPU·프로세스**를 흔들었고, 이건 부하기의 **연결 방식**이다. 다른 축이다.

## 9. 실행 결과 (2026-08-17 밤) — **H 반증. accept 큐는 증상이었다**

### 9-1. 1단계 — 백로그는 실제로 길었다

부하 중 uvicorn 리스닝 소켓(`:8000`, 컨테이너 netns):

| 지표 | 값 |
|---|---|
| **`Recv-Q`(백로그 대기 연결 수)** | **132~135 지속** |
| `Send-Q`(상한) | 2048 |
| `ListenOverflows` / `ListenDrops` | **0** (넘치진 않았다) |
| 호스트 `:8000` `Recv-Q` | **0** (호스트는 안 막힘) |
| `TcpPassiveOpens`(90초) | **17,336** — 요청당 거의 1연결 |

그 판은 237 RPS · p50 590ms 였고, **리틀의 법칙이 맞았다**: `133 ÷ 237/s = 561ms ≈ 590ms`.
**지연의 대부분이 accept 큐 대기 시간이었다.**

### 9-2. 2단계 — 그런데 연결을 재사용해도 안 변한다

판마다 컨테이너 재시작(풀 리셋) + `nolease` 게이트 + 교차 배열. **4판 전부 유효**(`nolease=0`).

| 팔 | 판 | RPS | p50 |
|---|---|---:|---:|
| keep-alive | ka_a / ka_b | 270.89 / 253.47 | 576.6 / 615.6 |
| urllib(현행) | url_a / url_b | 267.39 / 261.58 | 590.2 / 601.8 |

**keep-alive 262.2 vs urllib 264.5 → −0.9%.**
사전 판정선은 **「450 RPS 이상이면 H 지지 · 348 ±10% 면 반증」** 이었다 → **반증.**

### 9-3. 그러면 accept 큐 133개는 무엇이었나

**증상이다.** 앱이 한 번에 ~9개만 처리하니 나머지가 커널 큐에 쌓였을 뿐이고,
큐를 없애도(keep-alive) **처리 능력이 그대로라 총량이 안 변했다.**

> **역방향 인과였다.** 「accept 가 느려서 앱이 굶는다」가 아니라
> **「앱이 천천히 가져가서 큐가 길다」** 였다.

🔴 **그리고 이것 때문에 §8-0 의 «관측 넷을 동시에 설명한다» 가 무너진다** — 그 넷은
**H 가 아니어도** 「앱 안 동시 처리가 ~9로 묶임」 하나로 똑같이 설명된다. **설명력이 같으면
증거가 아니다.** 백로그 관측(9-1)은 H 를 지지한 게 아니라 **양쪽과 다 맞는 관측**이었다.

### 9-4. 곁다리 둘

- **판마다 컨테이너를 재시작하면 처리량이 348 → 260~270 으로 −24%.** 검출기 풀이 차갑게
  시작해 판 안에서 검출기를 만들며 돌기 때문으로 보인다(⚠️ 원인 미검증).
  **풀 소진을 피하려고 넣은 우회가 절대값을 바꾼다** — 앞으로 이 우회를 쓰는 판은
  **다른 판과 절대값 비교 불가**다
- **판 순서대로 270.9 → 267.4 → 261.6 → 253.5 (−6.4%) 단조 감소.** 재시작을 해도 무언가
  누적된다. 교차 배열 덕에 팔 판정엔 안 얹혔다. **원인 미상**

### 9-5. 남은 것

| 후보 | 상태 |
|---|---|
| GIL · 하드웨어 · 검출기 풀 · 부하기(코어·프로세스) · anyio 한도 · 락 · 페이로드 크기 · docker-proxy · 호스트 CPU | ❌ |
| **연결 재사용 / accept 경로** | ❌ **9-2** |
| **「앱 안 동시 처리가 ~9로 묶이는 이유」** | 🔶 **미해결. 후보를 다시 세워야 한다** |

⚠️ 「~9」 자체가 **산술 추론**이다(348 × 26ms). 직접 세어본 적이 없다 —
**다음 판의 첫 일은 «동시에 앱 안에 있는 요청 수»를 직접 세는 계측**이다.

## 10. 후보 재정렬 (2026-08-17 밤, 하루 끝)

§9 로 «연결/accept» 가 지워지고 **후보를 다시 세웠다.**

### 10-1. 🔴 1순위 — **GIL. 단 «서비스 경로» 한정**

R6 가 지운 것은 **「순수 추론 루프」의 GIL** 이다 — MediaPipe 는 C++ 안에서 GIL 을 놓는다.
**그런데 서비스 경로에는 추론 말고도 프레임마다 도는 파이썬 코드가 있다**:
JSON 파싱 · Pydantic 검증 · base64 디코드 · 응답 직렬화. **이건 전부 GIL 을 잡는다.**

산술: 프레임당 GIL 구간이 **~2.8ms** 면 `348 × 2.8ms = 0.97 코어` — **GIL 상한(1코어)에 붙는다.**

**그리고 오늘 초반 덤프에 증거가 있었는데 안 읽었다:**

| 스레드 | 상태 |
|---|---|
| MainThread(이벤트 루프) | 3판 중 **2판이 `active+gil`** ← GIL 을 쥐고 있었다 |
| AnyIO 워커 | 전부 `idle` ← **GIL 을 못 쥔 상태** |

이러면 「워커가 논다」의 정체가 **「일이 없어서」가 아니라 「GIL 을 못 얻어서」** 가 된다.
CPU 9.5(파이썬 구간은 1코어 상한 + 추론만 병렬) · 페이로드 축소 효과가 작았던 것(파싱은
GIL 구간의 일부) · keep-alive 무효까지 **하나로 설명된다.**

⚠️ **단 이건 §8 에서 내가 저지른 실수와 같은 종류의 논증이다** — 「여러 관측을 설명한다」는
것만으로는 증거가 안 된다(§9-3). **직접 재야 한다.**

### 10-2. 2순위 — 검출기 획득 경로

풀은 201개지만 **리스 획득 지점에 전역 락·큐**가 있으면 거기서 직렬화된다. 그리고 검출기가
**지연 생성**이라 새 세션마다 MediaPipe 인스턴스를 만든다 — §9-4 의 **「재시작하면 −24%」**
가 그 비용을 시사한다.

### 10-3. 3순위 — 세션별 유입 속도 제어

`accept_frame` 에 데드라인 로직이 있다([#162](https://github.com/Shadowfit/init/issues/162)).
`348 ÷ 160 = 세션당 2.18 fps` 인데 클라는 3 fps 를 노린다. **이 숫자가 우연인지 확인 안 했다.**

## 11. 🔴 도구 한계 — py-spy 로는 더 못 간다

오늘 세 번 썼고 **두 번 무효**였다.

| 시도 | 결과 |
|---|---|
| `py-spy dump` (초반, 재시작 전) | ✅ 정상 — 4~7 워커 busy · MediaPipe 프레임 관측 |
| `py-spy record --idle` | ❌ **스레드당 스택 1개 · 60초 내내 변화 0 · MediaPipe 0건** |
| `py-spy dump` ×30 (재시작 여러 번 후) | ❌ **630 샘플 전부 파킹 · MediaPipe 0건** |

마지막 판은 **244.5 RPS · 검출 100% · `nolease=0`** 으로 멀쩡히 돌던 판이다.
`244 × 26ms = 동시 6.4개` 가 일하고 있어야 하는데 **30번 다 0개를 잡을 확률은 사실상 0** 이다.
**컨테이너를 여러 번 재시작한 뒤로 py-spy 가 제대로 못 붙는 것으로 보인다**(미확인).

→ **1순위(GIL)를 재려면 py-spy 가 아니라 «앱에 붙이는 계측» 이 필요하다.**
