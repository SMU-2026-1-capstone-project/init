## 1. 배경/문제

지금 Spring↔AI-server(FastAPI) 통신은 gRPC다. 사용자가 이걸 WebClient(REST/JSON)와 비교해 판단을
요청했다. 계기는 최근 커밋(883f508, "GIL 병목을 프로세스 3개로 풀고... 세션 라우팅·메모리 버그 3개를
잡는다")에서 AI 서버를 프로세스 3개로 늘렸더니 gRPC 채널의 커넥션 고정 특성 때문에 트래픽이 한
프로세스로만 몰리는 버그가 나왔고, 이를 손으로 짠 채널 풀 라우팅으로 고쳤다는 점이다. 통신 방식
변경은 되돌리기 어려운 분기점이라 즉답 대신 이 문서로 정리한다.

## 2. 현재 보유 자원·제약 (실측 근거)

- **proto**: `backend/src/main/proto/exercise.proto`, RPC 8개(`ExtractReferenceData`,
  `StartAnalysis`, `ReattachAnalysis`, `SavePoseDataBatch`, `CompleteAnalysis`, `StopAnalysis`,
  `ReportFeedbackBatch` 등) **전부 unary** — streaming RPC는 하나도 없다.
- **실시간 고빈도 프레임은 gRPC를 안 탄다** — RN이 `POST /pose`로 AI 서버에 REST 직결한다
  (`exercise.proto:73` 주석). gRPC는 세션 시작/재접속/중단/완료 같은 **저빈도 제어면 + 배치
  결과 전송**에만 쓰인다.
- **채널 고정 버그와 수동 해결책** (`ExerciseAnalysisService.java:66-104`): net.devh
  `@GrpcClient` 단일 채널은 HTTP/2 커넥션 하나를 계속 재사용한다. AI 서버를 3-프로세스로
  분리(SO_REUSEPORT → 포트 분리 8585/8586/8587)해도 이 채널 하나로는 한 프로세스에만
  꽂힌다. 해결책으로 `ManagedChannel` 풀 3개를 직접 만들고 `session_id % 3`
  (`Math.floorMod`)으로 라우팅하는 코드를 프로덕션에 얹었다. 코드 주석에 채널 인덱스와 실제
  gRPC 포트를 잘못 짝지어 세션 6개가 전부 한 프로세스로 몰렸던 실제 버그 이력도 남아 있다
  (77-81행).
- **이 라우팅의 처리량 검증**: `ai-sticky-routing-probe.md`(2026-08-26 완료)가 정적
  사전분할과 `session_id % 3` 해시 라우팅 사이 처리량 차이를 실측 — C(정적) 475.90 rps vs
  E(해시) 478.41 rps, 오히려 해시 쪽이 근소 우위. **채널 풀 수동 라우팅 자체의 처리량 비용은
  없다는 것까지는 닫힌 캐비엇.**
- **더 큰 미결 분기와는 스코프가 다르다**: `ai-sticky-routing.md`(2026-08-23, 아직 미결정)는
  AI 서버를 여러 **박스**로 수평확장할 때의 스티키 라우팅을 다룬다. 이 문서(현재 문서)가 보는
  건 **한 박스 안 3-프로세스** 간 라우팅으로, 별개 분기다.
- **장애 격리·타임아웃은 이미 구현됨**: `withDeadlineAfter`(gRPC deadline), Resilience4j
  `CircuitBreaker`(`ExerciseAnalysisService.java`, `application.yml:269-283`) — 둘 다
  프로토콜에 종속되지 않는 패턴이라 WebClient로 가도 동일하게 재구현 가능하다.
- **WebClient는 현재 프로젝트 어디에도 안 쓰인다** (`*.java` 전체 grep 0건) — 도입 시 완전히
  새로운 의존성·컨벤션이 된다.
- **목표 스케일**: DAU 1,000 가정, 피크 동시 67세션(정본 기준선, `load-test-strategy.md`
  §4.2). 이 규모에서 gRPC 대표 장점인 스트리밍·바이너리 직렬화 효율은 애초에 안 쓰인다 —
  실시간 프레임이 REST로 이미 빠져 있고, gRPC 쪽은 세션당 몇 번 안 되는 저빈도 호출이라
  protobuf 대 JSON 차이가 체감될 스케일이 아니다.

## 3. 선택지

| # | 선택지 | 한 줄 |
|---|---|---|
| ① | **현행 유지** | gRPC + 채널 풀 수동 라우팅(`session_id % 3`) 그대로 |
| ② | **WebClient(REST/JSON) 전면 전환** | 8개 RPC를 REST 엔드포인트로 재구현, 스키마는 OpenAPI/DTO로 관리 |
| ③ | **하이브리드** | 저빈도 제어면(세션 시작/종료)만 REST로, 배치 결과 전송은 gRPC 유지 |
| ④ | **gRPC 유지 + 외부 LB(L4/L7)** | 채널 풀 수동 라우팅 코드를 걷어내고 nginx/Envoy 등에 위임 |

## 4. 트레이드오프 표

| 선택지 | 장점 | 단점 | 리스크 | 구현 비용 |
|---|---|---|---|---|
| ① 현행 유지 | 이미 동작·처리량 실측 완료(§2). proto 스키마 계약이 Java/Python 필드 불일치를 컴파일타임에 잡음(필드 추가 시 양쪽이 어긋나면 빌드가 깨짐) | 채널 고정 라우팅을 수동으로 관리해야 함 — 인덱스/포트 매핑을 손으로 맞추는 지점이라 실제로 버그가 한 번 났음(§2). gRPC 특유 장점(스트리밍)은 이 구조에서 안 씀 | AI 서버 인스턴스 수가 바뀌면 `AI_CHANNEL_POOL_SIZE`·포트 매핑을 다시 손으로 맞춰야 함 | 0 (이미 완료) |
| ② WebClient 전환 | HTTP/1.1·요청 단위라 표준 L4 LB로 자연 분산 — 채널 고정 문제 자체가 안 생김. curl 등으로 디버깅 쉬움 | proto가 강제하던 스키마 계약 소실(OpenAPI를 별도로 관리해야 함). 8개 RPC·양쪽 DTO 전량 재작성. 이미 검증된 구조를 처음부터 재검증해야 함 | 마이그레이션 중 회귀. REST에서 세션 라우팅 문제가 다른 형태로 재발할 가능성(미검증) | 높음 — 스키마 계약 대체, 8개 엔드포인트 재구현, 재부하테스트 |
| ③ 하이브리드 | 리스크가 큰 배치 전송 경로는 안 건드리고 저빈도 제어면만 바꿔 위험 축소 | 프로토콜 두 개를 동시에 운영(클라이언트·모니터링·에러 모델 이원화). 아키텍처 일관성이 깨져 서사가 흐려짐 | 절반만 이득 보고 채널 라우팅 문제는 배치 경로에 그대로 남음 | 중간이지만 이득 대비 낭비 |
| ④ gRPC + 외부 LB | 수동 채널 풀 코드 제거. LB가 헬스체크·장애 격리를 표준적으로 처리 | 새 인프라 컴포넌트 추가(배포·운영 부담 증가) | LB가 gRPC 세션 스티키니스를 지원하는지, 이 프로젝트 인프라(현재 LB 없음)에 맞는지 미검증 | 중간 — 코드는 걷어내지만 인프라 구성이 새 분기점 |

## 5. 추천

**① 현행 유지**를 추천한다.

이유:
- `ai-sticky-routing-probe.md`가 오늘(2026-08-26) 이미 "정적 사전분할과 해시 라우팅 사이
  처리량 차이 없음"을 실측으로 닫았다 — ①의 유일한 단점(수동 라우팅)이 처리량 비용으로
  이어지지 않는다는 것까지 확인된 상태다.
- gRPC를 정당화하는 축은 이 프로젝트에서 처음부터 "성능"이 아니라 **폴리글랏(Java↔Python)
  스키마 계약**이었고, 이건 지금도 유효하다.
- DAU 1,000 스케일에서는 gRPC의 대표 이점(스트리밍, 바이너리 직렬화)도, WebClient의
  대표 이점(표준 LB 자연 분산)도 둘 다 체감 차이가 크지 않다 — 즉 ②로 가도 "손해"는 작지만
  "이득"도 뚜렷하지 않은데, 전환 비용(§4)만 확실히 크다.

단, 포트폴리오/면접 서사를 짤 때 **"gRPC가 스트리밍이라 빠르다"는 프레임은 사실과 다르다** —
이 프로젝트의 RPC는 전부 unary이고 실시간 프레임은 REST로 빠져 있다. 정직한 프레임은
**"스키마 계약 이득 vs 채널 고정 비용을 실측으로 겪고 라우팅 코드로 해결"**이다.
