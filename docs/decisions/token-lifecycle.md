## 1. 코드로 확인했다 — 세 이슈 모두 「정적 판독·미재현」이었다

| 이슈 | 주장 | 확인 |
|---|---|---|
| #135 | 재발급 API 가 없다 | ✅ `RefreshTokenRepository` 의 커스텀 메서드는 `deleteByMemberId` · `deleteByToken` **둘뿐**. **토큰으로 조회하는 메서드가 없다** → DB 대조 경로가 구조적으로 불가능 |
| #136 | PK 가 `member_id` 라 회원당 1행 | ✅ [`RefreshToken.java:14-16`](../../backend/src/main/java/com/shadowfit/model/member/RefreshToken.java) — `@Id @Column(name="member_id")`, `@GeneratedValue` 없음. 로그인마다 새 빌더 → `save()` |
| #137 | 블랙리스트가 프로세스 힙 | ✅ [`JwtBlacklist.java:11`](../../backend/src/main/java/com/shadowfit/global/security/jwt/JwtBlacklist.java) — `ConcurrentHashMap`, 외부 저장소 없음 |

⚠️ **여전히 런타임 재현은 안 했다.** 위는 «코드가 그렇게 생겼다» 까지이고, «두 기기 로그인 후 행이 1개다» 나 «재기동 후 토큰이 되살아난다» 를 실제로 돌려보지 않았다. #136 의 조용한 UPDATE 는 Spring Data JPA 의 `isNew` 판정에 근거한 추론이다.

### 1-1. 이슈 셋에 없던 것 — 확인 중에 나왔다

**ㄱ. refresh token 이 DB 에 평문으로 있다.** [`RefreshToken.java:18-19`](../../backend/src/main/java/com/shadowfit/model/member/RefreshToken.java) 의 `token` 은 `length=512` 짜리 평범한 문자열 컬럼이다. **DB 덤프가 유출되면 그 자체로 쓸 수 있는 자격증명**이다. 비밀번호는 `passwordEncoder` 로 해싱하면서 refresh token 은 안 한다 — 같은 테이블 근처에서 기준이 갈린다.

이건 #137 의 저장소 선택과 직접 얽힌다. 블랙리스트를 DB/Redis 로 옮기면 **access token 원문도 같은 성질의 저장물**이 되므로, 해싱 여부를 **그때 같이 정해야 한다**(지금은 힙에만 있어 덤프 대상이 아니다).

**ㄴ. 로그아웃이 «요청자» 가 아니라 «본문» 을 믿는다.** [`MemberController.java:41-45`](../../backend/src/main/java/com/shadowfit/controller/MemberController.java) 는 `@AuthenticationPrincipal` 없이 본문의 `accessToken`·`refreshToken` 을 그대로 받고, [`MemberService.java:84`](../../backend/src/main/java/com/shadowfit/service/Member/MemberService.java) 가 소유권 확인 없이 `deleteByToken` 한다.

> 📌 **[#138](https://github.com/Shadowfit/init/issues/138) 과 같은 형태다** — «요청자에게서 받아야 할 것을 본문에서 받는다». 다만 **심각도는 훨씬 낮다**: 남의 토큰을 지우려면 그 토큰을 이미 알아야 하고, 알면 지우는 것보다 쓰는 게 낫다. 별도 이슈로 올릴 정도는 아니라고 보지만, **재발급을 붙일 때는 소유권 확인이 필수**라 그 작업에 자연스럽게 딸려온다.

**ㄷ. `refresh_token` 테이블에 만료 컬럼이 없다.** 7일 수명이 JWT 안에만 있다. 회원당 1행이라 무한 증식은 없지만, «만료된 행 정리» 나 «언제 발급됐나» 를 DB 만 보고는 알 수 없다.

>
> 스키마 변경 없음. 지금 코드가 이미 그렇게 동작하므로 **바꾸는 것은 동작이 아니라 «명시성»** 이다 —
> 조용한 `merge` 를 **의도된 교체**로 바꾸고, 프론트에 «다른 기기에서 로그인되어 로그아웃됩니다» 안내를 넣는다.

**이것부터다.** 나머지 둘의 «무엇을 무효화하나» 가 여기서 갈린다.

| | ㄱ-1 «1인 1세션» 을 정책으로 박제 | ㄱ-2 기기별 다중 세션 허용 |

| 코드 | 로그인 시 «기존 세션 만료» 를 명시(현재는 조용한 UPDATE) | 발급·조회·삭제 전부 다건 기준으로 |
| 프론트 | **필요** — 사용자에게 보이는 동작이라 안내가 있어야 한다 | 불필요 |
| 로그아웃 | 그대로 | «이 기기만» vs «전체» 를 나눠야 한다 |
| 정직성 | 지금 코드가 이미 그렇게 동작한다 — **문서만 없다** | 지금 코드와 다르다 |

⚠️ **다기기가 요구사항인지 확인된 바 없다**(#136 미검증 항목). 요구사항이 아니면 이건 결함이 아니라 **정책 미문서화**로 축소된다.

## 3. 분기 ㄴ — 블랙리스트를 어디에 두나 (#137)

### 3-0. 🔄 #135 가 들어가면서 이 분기의 전제가 바뀌었다 (2026-08-09)

§5 가 «#135·#136 이 노출 창을 줄인 뒤에 고른다» 고 미뤄뒀던 그 시점이다. 무엇이 달라졌나:

| | 전 | 후 |
|---|---|---|
| 로그아웃 | 본문의 토큰으로 행 삭제(0행일 수 있었다) | **요청자 기준으로 확실히 삭제** → 갱신 경로가 끊긴다 |
| access 수명 | 24시간 고정 (줄이면 재로그인) | **줄일 수 있다** — 재발급이 생겼으므로 |
| 블랙리스트가 막는 것 | 로그아웃 후 24시간 | 로그아웃 후 **남은 access 수명** |

📌 **즉 블랙리스트의 가치가 access 수명의 함수가 됐다.** 수명이 짧아질수록 «이 토큰을 만료 전에 죽인다» 로 버는 시간이 줄고, 어느 지점부터는 **저장소를 고민할 대상 자체가 사라진다.**

🔴 **그런데 수명을 지금 줄이면 안 된다.** 프론트에 재발급 호출이 **없다** — `authStore.ts` 가 refresh 를 `SecureStore` 에 저장만 하고 `/member/reissue` 를 부르는 곳이 0건이며, `api.ts:63-70` 은 401 을 받으면 곧바로 `forceLogout` 이다. 지금 수명을 줄이면 **사용자가 그 주기로 로그아웃된다 — 오늘보다 나빠진다.**

> **선행 순서: 프론트 재발급 연동 → access 수명 단축 → #137 저장소 재판정.**
> 아래 선택지는 그 순서를 전제로 «어느 방향으로 갈 것인가» 를 정하는 것이다.

### 3-0-1. ✅ **확정 (사용자, 2026-08-09): ㄴ-4 블랙리스트를 없앤다** → ✅ **구현 완료 (2026-08-10)**

> ## ✅ **착수 조건 셋이 모두 닫혔다**
>
> | 순서 | 무엇 | 상태 |
> |:--:|---|---|
> | 1 | **프론트 재발급 연동** — `/member/reissue` 호출 + 401 재시도 | ✅ **완료** (`c4dee2c`, `api.ts` `reissueOnce`) |
> | 2 | **access 수명 단축** — 24시간 → **1800초(30분)** | ✅ **완료** (사용자 결정 2026-08-10, §3-0-2) |
> | 3 | **`JwtBlacklist` 제거** | ✅ **완료** — 파일 삭제 + `JwtAuthFilter`·`SecurityConfig`·`MemberService` 배선 제거 |
>
> 원문(참고): *"지금 지우면 오늘보다 나빠진다. 수명을 안 줄인 채 지우면 로그아웃한 토큰이
> 최대 24시간 살아 있다."* — 그래서 순서를 지켰고, 1이 먼저 끝난 뒤에 2·3 을 같이 넣었다.

#### 3-0-1-1. 🔴 구현하면서 나온 것 — 로그아웃 요청 본문이 통째로 죽었다

블랙리스트를 걷어내니 `LogOutRequestDto` 의 **두 필드 모두 쓰이는 곳이 0** 이 됐다.

| 필드 | 블랙리스트 제거 전 | 제거 후 |
|---|---|---|
| `refreshToken` | **이미 0건** — §1-1-ㄴ 수정으로 «요청자 기준 삭제» 가 되면서 사용처가 사라졌다 | 0건 |
| `accessToken` | 블랙리스트 등록 하나뿐 | **0건** |

`@NotBlank` 두 개가 «아무 데도 안 쓰는 값을 필수로 요구» 하는 상태였다. **✅ 본문을 통째로
제거**(사용자 결정 2026-08-10) — DTO 삭제, 컨트롤러는 `@AuthenticationPrincipal` 만 받는다.
프론트도 같이 고쳤다(`authService.logout()` 무인자, `types/auth.ts` 의 `LogoutRequest` 삭제).

> 📌 **§1-1-ㄴ 을 고칠 때 이미 절반이 죽어 있었는데 못 봤다.** 그때 바꾼 것은 «무엇을 믿는가»
> 였고, 그 결과로 «본문이 필요 없어졌다» 는 한 걸음 뒤의 결론이라 같이 안 잡혔다. 죽은 필드는
> 기능이 사라질 때가 아니라 **사용처가 마지막으로 없어질 때** 세어야 한다.

#### 3-0-1-2. 🔶 남겨진 것 — refresh 평문 저장이 갈 곳을 잃었다

§1-1-ㄱ(refresh token 이 DB 에 평문)은 *"저장소 결정(ㄴ 분기)에 딸려 처리되는 것이 자연스럽다"*
고 §6 에 적혀 있었다. **그런데 ㄴ-4 는 «저장하지 않는다» 라서 딸려갈 자리가 없다.**
access 는 이제 아예 저장되지 않지만 **refresh 는 여전히 평문으로 `refresh_token.token` 에 있다.**
이 항목은 **독립 항목으로 남는다** — [#185](https://github.com/Shadowfit/init/issues/185) 로 등록(2026-08-10).

> 🔴 **조사 중 나온 것: 그냥 해싱하면 안 된다.** `MemberService.java:155`(유예 경로)가 저장된
> 토큰을 **클라에 그대로 돌려준다** — 저장값이 «대조용» 이 아니라 «다시 발급해줄 원본» 으로도
> 쓰인다는 뜻이다. 대조하는 두 자리(`:153`·`:159`)는 `matches()` 로 바꾸면 되지만 `:155` 는
> 설계 결정이 필요하다(유예 경로에서 새 토큰을 발급할지 / 유예를 없앨지 / 암호화로 갈지).
> **§4-4 가 유예를 만든 이유와 정면으로 얽힌다.**

### 3-0-2. ✅ **확정 (사용자, 2026-08-10): access 수명 30분 (1800초)**

> **이것은 측정값이 아니라 약속(threshold)이다.** 아래가 그 이유를 그대로 적고 있고, 확정하면서
> 성격이 바뀌지 않는다 — 세션 길이 분포도 SLO 도 사용 로그도 없어 유도할 근거가 없다.
> `application.yml:196`(`JWT_EXPIRATION_TIME` 기본값)과 `.env.example` 에 반영.
>
> ⚠️ **`.env.example` 의 주석이 두 군데 틀려 있었고 같이 고쳤다** — 단위가 «ms» 로 적혀 있었으나
> 실제는 **초**(`JwtUtil:77` `plusSeconds`)이고, 옛 기본값 86400 을 «1시간» 이라고 적어놨는데
> 실제로는 **24시간**이었다. 값을 고치러 갔다가 설명이 틀린 것을 발견한 경우다.
>
> 🔶 **미확인**: 운동 세션이 30분을 넘으면 그 도중에 재발급이 끼어든다. 401 재시도 경로가 이미
> 있어 자동 복구되는 것이 설계지만, **실제 운동 흐름에서 돌려본 적은 없다.**

ㄴ-4 의 대가가 **정확히 이 값**이다. 로그아웃 후 무방비 구간이 곧 access 수명이다.

⚠️ **이 프로젝트에 이 값을 유도할 데이터가 없다.** 세션 길이 분포도, SLO 도, 사용 로그도 없다. 그래서 이건 측정으로 나오는 baseline 이 아니라 **약속(threshold)** 이고, 정할 때 그렇게 적어야 한다 — [[feedback_no_arbitrary_threshold_values]] 가 금지하는 것은 «근거 없는 값» 을 근거 있는 것처럼 쓰는 것이지, 정책값을 정책값이라고 밝히고 두는 것이 아니다.

판단 축은 둘뿐이다: **짧을수록** 로그아웃 후 무방비 구간이 짧아지고, **길수록** 재발급 호출이 줄어든다(서버 부하·클라 복잡도).

### 3-0-3. 선택지 원문 — ㄴ-4 블랙리스트를 없앤다

수명이 짧아지면 «로그아웃 토큰을 만료 전에 죽이는» 장치 자체를 안 두는 선택이 생긴다. 갱신은 refresh 폐기로 이미 막히고, 남는 것은 **이미 발급된 access 의 잔여 수명**뿐이다.

이 프로젝트가 [#138](https://github.com/Shadowfit/init/issues/138) 을 «검증 추가» 가 아니라 **«필드 제거»** 로 닫은 것과 같은 형태다 — 문제를 푸는 대신 **없앤다.**

- ✅ 재기동 부활이 **사라진다** (잃을 상태가 없다)
- ✅ 다중 인스턴스 동기화 문제도 **사라진다** — [#137](https://github.com/Shadowfit/init/issues/137) 이 «수평 확장을 막는 요소» 라고 적은 그 항목이 없어진다
- ✅ 인증된 **모든 요청**에서 맵 조회가 빠진다
- ❌ 로그아웃한 access 가 **잔여 수명 동안 유효하다.** 기기를 잃어버린 직후 로그아웃해도 그 시간만큼은 못 막는다
- ⚠️ «로그아웃» 의 의미가 «서버가 즉시 끊는다» 에서 «갱신이 끊기고 곧 만료된다» 로 바뀐다 — **사용자에게 설명 가능한 동작이어야 한다**

### 3-1. 먼저: Redis 재검토 트리거 T4 가 이미 걸렸을 수 있다

## 4. 분기 ㄷ — 재발급의 회전 정책 (#135)

> ## ✅ **확정 (사용자, 2026-08-09): ㄷ-3 회전 + 재사용 탐지**
> ## ✅ **탐지 구현은 (a) 버전 카운터** — §4-1
>
> 재발급 때 access·refresh 를 **둘 다** 새로 발급하고, 폐기된 구본이 다시 오면 **탈취로 보고 세션을 끊는다.**

| | ㄷ-1 재발급만 | ㄷ-2 회전(rotation) | ㄷ-3 회전 + 재사용 탐지 |
|---|---|---|---|
| 동작 | refresh 로 access 만 새로 | 재발급 때 refresh 도 교체·구본 폐기 | 구본이 다시 오면 **해당 계정 전 세션 무효화** |
| 탈취 대응 | 없음 — refresh 7일 내내 유효 | 창이 좁아짐 | 탈취를 **탐지**한다 |
| 구현 | 조회 + 검증 + 발급 | + 교체 트랜잭션 | + 「폐기됨」 상태 보존 → **만료 컬럼·상태 컬럼 필요**(§1-1-ㄷ) |
| ㄱ 의존 | 낮음 | 중간 | **높음** — 「전 세션 무효화」가 ㄱ-2 에서만 의미를 가진다 |

### 4-1. ㄱ-1 과 ㄷ-3 이 부딪힌다 — 그래서 버전 카운터다

재사용 탐지는 **«폐기된 R1»** 과 **«애초에 없던 R1»** 을 구분해야 한다. 그런데 ㄱ-1 은 PK 가 `member_id` 라 **회원당 행이 하나**여서, R2 가 R1 을 덮어쓰면 그 구분이 사라진다. **두 결정을 그대로 합치면 탐지가 성립하지 않는다.**

| | 방법 | 대가 |
|:--:|---|---|
| **(a)** ✅ | **버전 카운터** — 행에 `token_version`, refresh JWT 에 같은 값을 claim 으로. 들어온 JWT 의 version < 행의 version 이면 폐기된 구본 | 컬럼 1개 추가. **행은 1개 유지**, 모든 세대 탐지 |
| (b) | `previous_token` 컬럼 | **한 세대만** 탐지. 평문 토큰이 하나 더 쌓인다(§1-1-ㄱ) |
| (c) | 폐기 토큰 별도 테이블 | 무한 증식 → 정리 스케줄러 |

**(a) 확정.** PK 변경이 아니라 **컬럼 추가**라 ㄱ-1 의 «마이그레이션 없음» 을 거의 유지하고, 폐기 토큰 원문을 저장하지 않아 평문 저장 면적이 안 늘어난다.

```
refresh_token
  member_id      PK       ← 그대로
  token          VARCHAR  ← 그대로
  token_version  BIGINT   ← 추가

재발급:  JWT.ver == row.ver ?
          예    → ver+1, 새 access·refresh 발급
          아니오 → 탈취 → 행 삭제 + access 블랙리스트 + 재로그인 강제
```

### 4-2. 🔴 정정 — 재발급에서 「요청자 기준 소유권 확인」은 성립하지 않는다

선택지를 낼 때 *"refresh 소유권 확인(본문 아닌 요청자 기준)"* 이라고 적었는데 **틀렸다.**

**재발급은 access token 이 만료된 상태에서 불린다.** 그게 이 엔드포인트의 존재 이유다. 따라서 `JwtAuthFilter` 를 통과할 수 없고, `SecurityContext` 에 요청자가 없다 — 엔드포인트가 **whitelist(permitAll)에 들어가야 한다.**

그래서 신원은 **refresh JWT 자신의 서명**에서 나온다:

```
1. refresh JWT 서명 검증        ← 위조 불가. 여기가 신뢰의 근거
2. subject(email) 로 member 조회
3. row.token == 제시된 토큰 ?   ← 폐기 여부
4. row.version == JWT.ver ?     ← 재사용 탐지 (§4-1)
```

**#138 형태가 아니다.** #138 은 *서명되지 않은 본문 필드*(`role`)를 믿은 것이고, 여기는 *서버가 서명한 토큰*의 claim 을 믿는 것이다. 서명 검증이 곧 소유권 증명이다.

⚠️ 반면 **로그아웃은 다르다** — 그쪽은 인증된 경로라 `SecurityContext` 에 요청자가 있는데도 본문을 믿는다(§1-1-ㄴ). 거기는 요청자 기준으로 바꾸는 게 맞다.

### 4-3. 감수한 대가 — 「탈취」와 「낡은 기기」를 구분하지 못한다

ㄱ-1 은 행이 하나뿐이라 **둘 다 «옛 토큰이 도착했다» 로 똑같이 보인다.** 구분할 정보가 없다.

| | 동작 | 대가 |
|---|---|---|
| ✅ **보수적** (채택) | 탈취로 간주 → 세션 무효화 + 재로그인 | **낡은 기기의 시도가 현재 세션을 끊는다** |
| | 관대 | 단순 401 거절 | 탐지를 넣은 의미가 사라진다 |

ㄷ-3 을 고른 취지가 «탈취를 탐지한다» 이므로 보수적 쪽. 1인 1세션이면 사용자가 이미 «다른 기기 로그인 시 로그아웃» 을 전제로 하므로 재로그인이 정책 안에 있다.

📌 **이 대가를 테스트에 드러내 뒀다** — `TokenReissueIntegrationTest.secondLogin_invalidatesFirstSession` 이 «두 번째 기기 세션까지 끊긴다» 를 단언한다. 뒤집으려면 `MemberService.reissue` 의 (3) 분기 하나만 바꾸면 되고, 그 단언이 같이 바뀐다.

### 4-4. 구현하면서 나온 것 — 설계에 없던 결함 하나

🔴 **로그인이 유예창을 열어줬다.** 처음엔 로그인도 `rotate()` 를 타게 했는데, 그러면 앞 기기 토큰이 정확히 «직전 세대 + 유예 안» 조건에 걸린다 → **앞 기기가 재발급으로 새 세션의 refresh token 을 받아간다.** 1인 1세션을 세워놓고 정확히 반대로 동작한다.

`replaceForNewLogin()` 을 따로 두고 **`rotated_at` 을 비운다**. 유예는 «재발급 응답을 못 받은 재시도» 를 위한 것이고 로그인에는 그런 재시도가 없다.

> 📌 **테스트를 쓰다 잡혔다.** 설계 검토에서는 안 보였고, 두 결정(유예·1인 1세션)이 각각은 맞는데 겹치는 자리에서만 나오는 종류였다. §4-1 의 제약(ㄱ-1 × ㄷ-3)과 같은 형태가 한 번 더 나온 셈이다.

🔴 **에러 코드가 응답에 안 실린다.** `REFRESH_TOKEN_REUSED`(A006)를 만들었지만 `ErrorResponseDto` 는 `status`·`message`·`timestamp` 만 싣는다. **프론트는 A004(단순 무효)와 이걸 문자열로만 가를 수 있다.** 응답에 `code` 를 넣는 것은 전 에러 응답의 계약 변경이라 이 작업 범위 밖으로 뒀다 — 별도 판단이 필요하다.

⚠️ **whitelist 가 두 벌이다.** `main` 과 `test` 의 `application.yml` 이 각각 목록을 들고 있어 한쪽만 고치면 인증 경계가 갈린다. `/member/reissue` 를 main 에만 넣었다가 통합테스트가 전부 401 로 떨어져 알았다 — **테스트가 먼저 깨지는 방향**이라 조용히 지나가지는 않는다.
