## 0. 한 줄 요약

**Redis 를 "캐시"로 넣으면 실익이 거의 없고 얕게 읽힌다. 이 코드베이스에서 Redis 가 정당한 자리는 캐시가 아니라 «상태» 다.**

이유는 하나다 — `JwtBlacklist` 가 `ConcurrentHashMap` 이라([`JwtBlacklist.java:11`](../../backend/src/main/java/com/shadowfit/global/security/jwt/JwtBlacklist.java)), **서버를 재시작하면 로그아웃된 토큰이 되살아난다.** 액세스 토큰 TTL 이 86,400초(24시간)이므로(`application.yml:169`) 부활 창은 **최대 24시간**이다. 이건 성능 개선 후보가 아니라 **결함**이고, 캐시 논의와는 급이 다르다.

반대로 **읽기 캐시 자리는 이미 Caffeine 이 먹고 있다**(3종). 그걸 Redis 로 바꾸는 건 지금 손해다.

## 1. 현재 지형 — 이미 있는 것과 이상한 것

**이미 있다**: Caffeine 로컬 캐시 3종 (`application.yml:63-71`)

| 캐시 | 대상 | 쓰기 경로 |
|---|---|---|
| `exercises` | 운동 마스터 | 있음(`AdminExerciseService.updateThresholds`) → `@CacheEvict` 병행 |
| `exerciseReferences` | 기준 좌표 | 신규 운동 등록 시만 |
| `feedbackTemplates` | 피드백 문구 | **없음**(순수 카탈로그) |

설정은 `expireAfterWrite=1h, maximumSize=500, recordStats`. **`recordStats` 가 켜져 있어 Micrometer 가 히트율을 이미 내보낸다** — 2026-08-08 관측 스택([28-remaining-work-plan](../tasks/28-remaining-work-plan.md) §2-6)이 서 있으므로 **"캐시가 실제로 먹히는가"를 그래프로 확인할 수단이 이미 있다.** 도입 전후 비교의 근거가 공짜로 생긴 상태다.

> 🔴 **이상한 것 1건**: `ErrorCode.java:73` 에 `REDIS_CONNECTION_FAILURE(500, "I001", "캐시 서버 연결에 실패했습니다.")` 가 **이미 선언돼 있는데 참조하는 코드가 없다.** 과거에 Redis 를 전제하고 만들었다가 안 쓴 흔적으로 보인다. 도입하면 자리를 찾고, 안 하면 지우는 게 맞다 — 지금은 **죽은 코드**다.

## 3. ㄱ `JwtBlacklist` — 왜 1순위인가

### 3-1. 실재 / 잠재 분류

이 프로젝트가 동시성에서 쓴 것과 **같은 분류**([`portfolio-benchmark.md`](./portfolio-benchmark.md) §2.1)를 그대로 적용한다.

| 실패 | 분류 | 조건 |
|---|:--:|---|
| **재시작하면 블랙리스트 전소** → 로그아웃된 토큰이 **최대 24시간** 부활 | 🔴 **실재** | 인스턴스 1대에서도 참. **지금 그렇다** |
| 인스턴스 A 에서 로그아웃 → B 에서는 통과 | 🟡 **잠재** | 수평확장 시 발동. 현재 단일 인스턴스라 미발동 |

**두 번째가 #4 와 직접 엮인다** — CD 로 무중단 롤링 배포를 하면 그 순간 두 버전이 동시에 뜬다. 즉 *"수평확장 안 하니까 괜찮다"* 가 **배포 방식만으로도 깨진다.**

### 3-2. 왜 이게 면접에서 다르게 읽히나

[`portfolio-benchmark.md`](./portfolio-benchmark.md) §1 이 확인한 바: Redis 는 **"있어야 정상"인 국밥 키워드**이고, *"다수 Redis 글이 메커니즘만 쓰고 부하검증을 TODO 로 남긴다"*.

| 서사 | 읽히는 방식 |
|---|---|
| "조회가 느려서 Redis 캐시 붙였습니다" | 단골. **변별력 없음** |
| "무상태 서버라고 해놓고 **로그아웃 상태만 인스턴스 로컬에** 있었습니다. 재시작하면 24시간짜리 토큰이 부활합니다" | **결함 발견 → 근거 있는 도입.** 이 프로젝트가 이미 잘하는 것(정직한 실재/잠재 분류)과 같은 결 |

즉 ㄱ 은 **서류 키워드(Redis)와 면접 깊이를 동시에** 준다. ㄷ 만 하면 키워드는 채우지만 국밥에 머문다.

### 3-3. 🔴 진짜 어려운 지점 — 여기서 결정이 필요하다

**Redis 가 죽으면 인증을 어떻게 할 것인가.** 이게 이 항목의 핵심이고, 답이 갈린다.

| 안 | 동작 | 대가 |
|:--:|---|---|
| **ㄱ-1 fail-open** | Redis 장애 시 블랙리스트 검사 스킵, 토큰 통과 | 가용성 유지. **로그아웃이 샌다**(보안 구멍) |
| **ㄱ-2 fail-close** | Redis 장애 시 전면 401 | 안전. **Redis 가 SPOF 가 되어 전체 서비스 정지** |
| **ㄱ-3 2단 (로컬 폴백)** | Redis 우선, 장애 시 기존 Caffeine/로컬맵으로 열화 | 복잡도 증가. 열화 중엔 잠재 결함이 되살아남 |

`ErrorCode.I001` 이 이미 있다는 건 **누군가 이 갈림길을 예상은 했다**는 뜻이지만, 정책은 어디에도 안 적혀 있다. **이 선택 자체가 면접 재료**다 — "Redis 넣었습니다" 보다 "가용성과 보안 중 무엇을 버렸고 왜인지" 가 훨씬 세다.

> 🟢 추천: **ㄱ-1 fail-open + 경보**. 근거 — 이 서비스에서 로그아웃 우회의 실제 피해(24h 창, 개인 운동 기록)보다 전면 인증 불능의 피해가 크다. 단 **이건 추천이고, 감수하는 위험을 문서에 박는 조건**이다.

## 4. ㄴ `RefreshToken` — 2순위이되 조건부

현재 `RefreshToken` 은 `member_id` 를 PK 로 한 **MySQL 테이블**이고 만료 컬럼이 없다(`RefreshToken.java`). 즉 **TTL 을 DB 가 아니라 앱이 관리**한다.

- Redis 로 옮기면 `SET key val EX 604800` 한 줄로 만료가 인프라 책임이 된다 — 리프레시 토큰은 **본질적으로 TTL 있는 휘발성 상태**라 자리가 맞다
- 🔶 **다만 ㄱ 과 묶어야 의미가 있다.** ㄴ 만 하면 "DB 로도 되는 걸 Redis 로 옮겼다"가 되고, 그건 §3-2 의 국밥 서사다
- ⚠️ 리프레시 토큰이 Redis 에만 있으면 **Redis 유실 = 전 사용자 재로그인**. §3-3 과 같은 갈림길이 여기도 있다

## 5. ㄷ 관리자 대시보드 — 왜 «보류» 를 추천하나

숫자는 확실하다([`admin-page-scope.md`](./admin-page-scope.md) §4-5): `b` 상태별 분포 **425ms**, `e` 활성 회원 **0.63s**, 둘이 대시보드 비용의 **98%**. 캐싱하면 즉시 빨라진다.

**그런데 그 앞에 미결이 있다.** §4-5 의 **집계 전략(㉲)이 아직 열려 있다.** 순서를 뒤집으면 이렇게 된다:

> 캐시는 **느린 쿼리를 숨긴다.** 집계 테이블·요약 컬럼이 정답인 자리에 TTL 캐시를 먼저 얹으면, 느린 쿼리가 가려진 채로 굳고 나중에 걷어내기 어려워진다.

이 프로젝트는 이미 **precompute-on-write** 로 같은 문제를 푼 전례가 있다([`report-read-path.md`](./report-read-path.md) §6). 대시보드에서만 캐시로 도망가면 **서사가 어긋난다.**

🔶 **권고 순서**: 집계 전략(㉲) 결정 → 그래도 남는 비용이 있으면 그때 캐시. 관리자 화면은 정합성 요구가 낮아(TTL 1~5분 감수 가능) **결정만 되면 구현은 싸다.**

## 6. ㄹ 카탈로그 3종을 Redis 로? — ❌

- 카탈로그는 **쓰기가 거의 없고 데이터가 작다**(`maximumSize=500`). 로컬 캐시가 **네트워크 홉 0** 이라 Redis 보다 빠르다
- 바꾸면 **모든 조회에 왕복이 생긴다** — 순수 손해
- 🔶 수평확장 시 인스턴스별 캐시 불일치가 생기지만, `expireAfterWrite=1h` 라 **최대 1시간 뒤 자동 수렴**하고 대상이 카탈로그라 피해가 작다
- ✅ 이로써 [`reference-style-and-caching.md`](./reference-style-and-caching.md) §1 의 *"캐시 백엔드(로컬 vs Redis) 🔶 열림"* 은 **"카탈로그는 로컬 유지"** 로 닫자는 게 이 문서의 추천이다

## 7. 자원 · 비용 · 추정

| 항목 | 내용 |
|---|---|
| 의존성 | `spring-boot-starter-data-redis`. **Caffeine 과 공존 가능** — `CacheManager` 를 나누면 되고 기존 3종을 갈아엎을 필요 없다 |
| 로컬 | `docker-compose.yml` 에 redis 컨테이너 1개. ⚠️ **2물리코어 제약** — 부하 실험과 동거하면 측정이 오염된다([`load-test-strategy.md`](./load-test-strategy.md)). 관측 스택처럼 **profile 분리**를 검토할 것 |
| AWS | ElastiCache 는 프리티어 없음 → **EC2 위 redis 컨테이너**로 시작이 현실적. ⚠️ 호스트 RAM 만 올리고 `docker --memory` 캡을 안 풀면 그대로 OOM 인 전례가 있다 |
| 검증 | 히트율·연결 수는 Micrometer 가 자동 노출 → **§1 의 관측 스택에 그대로 붙는다.** 대시보드 패널 추가만 |

[28-remaining-work-plan](../tasks/28-remaining-work-plan.md) §5-1 이 Redis 를 **"추정 없음"** 으로 적어둔 것을 이 문서도 유지한다. 근거 없는 숫자를 채우지 않는다는 §6 원칙 그대로다. **착수를 결정하면 그때 범위를 확정해 추정한다.**
