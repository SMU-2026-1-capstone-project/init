## 0. 이 문서가 있는 이유

재고표가 이 항목을 **한 줄**로 들고 있다 — *"DELETE 파편화 자체는 닫혔다… 이 **조합**은 안 봤다"*.

그런데 **무엇을 재는지가 정의돼 있지 않다.** 「행 모양」이 무엇이고 「상호작용」이 무엇인지, 무엇이 나오면 무엇이 정해지는지가 없다. 이 문서는 **그 한 줄을 잴 수 있는 형태로 푸는 것**이 전부다. 값은 안 낸다.

🔴 **무대(로컬/EC2)부터 정하지 않는다.** 질문이 서면 그때 «로컬로 되는가» 가 자동으로 갈린다([[feedback_state_assumption_design_to_it]] 의 반대 실수를 피한다 — 무대를 먼저 잡고 질문을 맞추지 않는다).

## 1. 무엇이 이미 닫혔나

[2026-08-09 판](../../loadtest/results/delete-fragmentation-2026-08-09/README.md)이 **소량 반복 DELETE 의 파편화 누적**을 닫았다.

| 삭제 모양 | 점유 페이지 | 재구축본 대비 |
|---|---|---|
| **FIFO**(오래된 것부터) | 1,348 에서 **3회전 내내 고정** | **−11%**(더 조밀) |
| **구멍 뚫기**(살아남는 행이 섞임) | 1,348 → **1,668 계단 한 번**, 이후 평탄 | +11% |

계단은 **구멍 밀도와 무관**했다(FAILED 비율 1%→20%, 20배 올려도 동일).

🔴 **그 판은 `outbox_events` 행 모양으로 쟀다.** 그리고 그 사실을 스스로 미검증으로 적어뒀다:

> `pose_data` 는 행 모양(`joint_coordinates` JSON)이 훨씬 커 **페이지당 행 수가 다르고**, 삭제가 **살아있는 파티션 안에서** 일어나 **파티션 DROP 과의 상호작용**이 있다. **둘 다 재지 않았다.**

즉 미검증은 **둘**이고, 이 문서는 그 둘을 각각 질문으로 만든다.

## 2. 「행 모양」이 무엇인가 — 실측 (2026-08-24, 로컬)

| | 값 |
|---|--:|
| `ROW_FORMAT` | **Dynamic** |
| `innodb_page_size` | 16,384 B |
| `joint_coordinates` 길이 (표본 20,000행) | 평균 **2,076 B** (2,069~2,083, 사실상 고정) |
| 클러스터드 인덱스 | 4,988 MB = **319,201 페이지** |
| 실제 행수 (`COUNT(*)`) | **1,587,214** |
| **페이지당 행** | **4.97** |
| 행당 바이트 | **3,295 B** |

### 여기서 나오는 두 사실

1. **한 페이지에 행이 5개도 안 들어간다** — `outbox_events` 판(1,348페이지에 200,000행 ≈ **페이지당 148행**)과 **약 30배** 차이다. 파편화의 «계단» 이 페이지 단위 현상이라면, **페이지당 행 수가 다르면 계단의 크기·유무가 달라질 수 있다.**
2. 🟢 **off-page 가 아니다 — 확인했다** (2026-08-24). `Dynamic` 은 행이 페이지의 약 절반(≈8,126 B)을 넘으면 큰 컬럼을 오프페이지로 민다. 행이 **3,295 B 로 그 아래**이고, 결정적으로 **버퍼풀에 이 테이블의 `BLOB` 페이지가 하나도 없다**:

   ```sql
   SELECT page_type, COUNT(*) FROM information_schema.INNODB_BUFFER_PAGE
    WHERE table_name LIKE '%pose_data%' GROUP BY page_type;
   -- INDEX  126,163   (BLOB 0)
   ```

   **Q1 의 전제는 무너지지 않는다.**

### 🔴 `table_rows` 를 믿으면 22% 틀린다

초판은 행당 크기를 `data_length / table_rows` 로 냈고 **4,235 B** 가 나왔다. 그런데 `information_schema.tables.table_rows` 는 **InnoDB 의 추정치**다 — 여기서는 **1,234,977** 로, 실제(`COUNT(*)` = 1,587,214)보다 **22% 낮다.** 실제 행수로 다시 나누면 **3,295 B** 다.

> 이 rig 계열은 «페이지당 행 수» 가 곧 질문이므로, **추정치를 쓰면 질문 자체가 흔들린다.** 착수 시 `COUNT(*)` 를 쓸 것.

> ⚠️ **이 수치는 합성 시드 기준이다.** `joint_coordinates` 가 2,069~2,083 B 로 거의 고정인 것은 **템플릿 복제**이기 때문이고, 실사용 분포는 다를 수 있다([[project_synthetic_data_distribution_limit]]).

## 3. 질문 둘 — 각각 무엇이 나오면 무엇이 정해지나

### Q1. 페이지당 행 수가 두 자릿수 다르면, 파편화 계단도 달라지는가 — ✅ **닫혔다 (2026-08-24)**

> 🟢 **답: 안 달라진다.** 페이지당 행이 148 → 4.4 로 30배 줄어도 FIFO 는 누적 없음, 구멍 뚫기는
> **계단 한 번 뒤 평탄**이고 크기가 **+25.7% ↔ 08-09 의 +24%** 로 사실상 같다.
> **→ 08-09 결론을 `pose_data` 로 인용해도 된다.** [결과](../../loadtest/results/row-shape-frag-2026-08-24/README.md)
>
> 판정선은 **결과에서 유도**했다 — FIFO 팔의 진동 폭 **±2.3%** 가 이 무대의 잡음이고, 구멍 계단은 그 **11배**다.

**재는 것**: `pose_data` 행 모양으로 08-09 판을 **그대로 재현**한다(FIFO ↔ 구멍 뚫기, 회전 3번). 지표도 같다 — 점유 페이지 수, 재구축본 대비.

| 결과 | 뜻 |
|---|---|
| 계단이 **비슷한 비율**(+24% 안팎) | 파편화 계단은 **행 모양과 무관**하다 → 08-09 결론을 `pose_data` 로 **확장 인용해도 된다** |
| 계단이 **크게 다르다** | 08-09 결론은 **`outbox_events` 조건부**다 → 그 문서 4곳의 인용에 조건을 달아야 한다 |
| 계단이 **없다** | 페이지당 행이 적으면 구멍이 페이지를 통째로 비워 재사용된다는 뜻 → 오히려 **좋은 소식**이고 그 이유를 적어야 한다 |

### Q2. 삭제가 «살아있는 파티션» 안에서 일어나면 DROP 과 무엇이 겹치는가 — 🔴 **이 박스로는 못 가른다 (2026-08-24)**

> **구멍은 페이지를 +69~84% 늘린다**(같은 50,000행: 16,921~18,455 ↔ 10,032). **그런데 DROP 소요가 그걸 안 따라간다** —
> 팔 안 산포(pholed 7.6배 · pclean 2.8배)가 팔 간 차이보다 커서 **두 팔이 완전히 겹친다.**
> 페이지가 제일 많던 판이 **제일 빨랐다**(18,455페이지 · 530 ms). [결과](../../loadtest/results/row-shape-frag-2026-08-24/README.md)
>
> 🔴 **§4 의 「상대비교까지 로컬」이 틀렸다** — 상대비교조차 안 된다. **조용한 박스(EC2 從)가 필요하다.** rig 은 완성돼 있다.
>
> 🔴 **덤으로 교락 하나를 찾았다**: 한 판에서 파티션 둘을 연달아 DROP 하면 **먼저 한 쪽이 느리다**(부호가 뒤집힌다).
> 「DROP 1.8초」 류 인용이 **첫 DROP 이었는지 둘째였는지**에 의존한다 — 그 조건은 어디에도 기록돼 있지 않다.

08-09 판에는 **파티션이 없었다.** `pose_data` 는 월별 RANGE 파티션이고, 운영에서 두 삭제가 **동시에** 존재한다:

- **DROP PARTITION** — 보존정책(`PoseDataPartitionScheduler`). 만료 파티션을 통째로 버린다
- **행 단위 DELETE** — 세션 삭제(`SessionService.java:392,404`)·탈퇴(`PoseDataCleanupService.java:35`). **살아있는 파티션 안**에서 구멍을 뚫는다

**재는 것**: 구멍이 뚫린 파티션과 안 뚫린 파티션의 **`DROP PARTITION` 소요**를 대조한다.

| 결과 | 뜻 |
|---|---|
| DROP 소요가 **같다** | 두 삭제는 **독립**이다 → 이 항목은 «상호작용 없음» 으로 닫힌다. [«DROP 은 1.8초 · DELETE 대비 625배»](../portfolio/realmysql-experiments.md) 를 구멍 유무와 무관하게 인용할 수 있다 |
| 구멍 뚫린 쪽이 **느리다** | 보존정책의 비용이 **사용자 삭제량에 의존**한다 → 운영 서술을 고쳐야 한다 |

🔑 **Q2 가 이 항목의 본체다.** Q1 은 기존 결론의 이식 가능성을 묻지만, Q2 는 **이 프로젝트에만 있는 조합**(파티셔닝 + 애플리케이션 삭제)을 묻는다.

## 4. 무대 — 로컬로 되는가

| | 로컬로 되나 | 근거 |
|---|:--:|---|
| **Q1** | 🟢 **된다** | 재는 것이 **점유 페이지 수**(구조 지표)다. 08-09 판도 로컬이었고 절대 시간을 안 썼다 |
| **Q2** | 🟡 **절반** | «DROP 소요» 는 **시간**이라 이 박스에서 절대값이 안 나온다([[project_loadtest_env_constraint]]). 다만 **구멍 유무 두 팔의 비**는 로컬 상대비교로 읽을 수 있다. 자릿수까지 말하려면 EC2 |

**권고**: Q1 → Q2(로컬 상대) 까지 로컬로 하고, **차이가 나올 때만** EC2 로 올린다. 차이가 없으면 그 자체로 닫히므로 EC2 가 필요 없다.

## 5. 🔴 정직하게 비어 있는 것

- ~~off-page 여부를 안 봤다~~ → ✅ **확인했다 (2026-08-24, §2-2)** — `BLOB` 페이지 0. Q1 의 전제는 성립한다
- **행 길이가 사실상 고정이다**(2,069~2,083 B). 실사용에서 분포가 넓으면 파편화 모양이 달라질 수 있는데, 이 rig 으로는 **그 축을 못 만든다**
- **삭제 패턴이 실제로 무엇인지 안 셌다.** 세션 삭제·탈퇴가 얼마나 자주·얼마나 많이 지우는지 모른다 — 「구멍 밀도」를 어디에 맞출지의 근거가 없다. 08-09 판은 밀도 무관을 보였으므로 **당장은 문제가 아니지만**, `pose_data` 에서도 무관한지는 Q1 이 답한다
- **판정선에 숫자가 없다.** «비슷한 비율» 을 무엇으로 가를지 안 정했다 — 08-09 판의 산포를 먼저 봐야 하고, 그 전에 임계를 박으면 임의값이 된다([[feedback_no_arbitrary_threshold_values]])
- **반복 설계를 안 적었다.** 착수 시 버림판·위치 균형을 정할 것([[feedback_measure_design_needs_repeats]])
