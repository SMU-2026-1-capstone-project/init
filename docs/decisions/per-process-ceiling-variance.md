## 0. 왜 이 자리인가

2026-08-23(`post-loop-breakdown-2026-08-23/README.md` §3-1)이 응답 생성 팔 셋(R=model·N=dict·
J=JSONResponse)을 대조하다가 곁다리로 발견한 것:

> rps는 팔마다 9.1% 벌어지는데 **rps/vCPU는 1.72% 안에 모인다.** 팔은 «요청당 CPU 비용»을 하나도
> 못 바꿨다 — 바뀐 것은 **프로세스가 실제로 끌어오는 CPU**뿐이다(R 9.46 · N 8.91 · J 9.94 vCPU,
> **11%** 차).

그 문서 자신이 §3-1 끝에 적어 뒀다:

> 🔴 **왜 팔에 따라 끌어오는 CPU가 달라지는지는 이 판이 안 답한다.** 후보 ㄱ(GIL)이 거기 있을
> 수 있고, 그것이 [#507](https://github.com/Shadowfit/init/pull/507) 프로브가 물을 것이다 —
> **아직 안 돌렸다.**

**그 "아직 안 돌렸다"가 여전히 사실이다.** #507(GIL 지연 프로브 `GIL_PROBE_INTERVAL` + 널 핸들러
`POSE_NULL_HANDLER`)은 병합됐고 §8(`ceiling-cause-stage2-2026-08-24`)에서 F/Z/C 세 팔로
**전체 GIL 점유율(`rho`≥0.939)**을 이미 확정했다 — 그런데 §8은 응답 모드를 R/N/J로 나누지
않았다(고정 모드 하나로 F/Z/C만 갈랐다). 즉 "GIL이 전체 천장을 지배한다"는 답과 "GIL이 R/N/J
사이 11% 차이의 원인이다"는 답은 **서로 다른 질문**이고, 후자는 아직 아무도 안 쟀다.

`docs/decisions/experiment-inventory.md`의 §3 표 3번 줄이 이 갭을 "새로 열림 (2026-08-23)"으로
그대로 들고 있다 — 실행 미착수 상태로 5일째다.

## 1. 가설 — 그리고 반증 조건

### 가설 A. GIL 경합이 R/N/J 사이에서 다르다

R(Pydantic 검증, `serialize_response`가 모델을 통째로 재구성)이 순수 파이썬 연산을 더 오래
GIL을 쥔 채로 돌린다면, 같은 이벤트 루프를 쓰는 다른 스레드(MediaPipe 추론을 기다리는 스레드
등)의 GIL 재획득 대기가 그만큼 늘어야 한다. 그런데 §3-1의 관측은 **R이 오히려 CPU를 적게
끌어온다**(9.46) — J(9.94)보다 낮다. J는 인코딩을 스레드로 미는 팔이라 스레드풀 경합이 더
크다(§5, `infer` +56%)는 게 이미 §5에서 관측돼 있다. 그러니 가설 A를 세우려면 방향을 정확히
적어야 한다: **"검증(R)이 GIL을 더 오래 쥔다"가 아니라 "스레드풀에 일을 더 미는 팔(J)일수록
GIL 재획득 대기가 늘어난다"** 쪽이 §5와 부합한다.

### 가설 B. GIL과 무관하다 — 스레드풀 경합만으로 설명된다

§5가 이미 관측한 "J는 스레드풀 `waiting=0` 비율이 92%→72%로 떨어지고 그 여파로 `infer`가
+56% 늘어난다"는 사실 하나로 CPU 끌어옴의 차이가 전부 설명될 수 있다 — 스레드가 더 붐빌수록
컨텍스트 스위치·스케줄링 오버헤드로 "일한 시간당 wall-clock CPU 소비"가 달라지는 것은 GIL
경합 없이도(순수 OS 스케줄러 수준에서도) 일어난다. 이 경우 GIL 프로브의 `rho`는 R/N/J 사이에서
**안 갈려야** 한다.

### 반증 조건 표

| 관측 | 판정 |
|---|---|
| GIL 프로브의 `rho`(또는 재획득 대기)가 R < N < J 순으로 벌어지고 그 격차가 CPU 끌어옴 격차(8.91→9.94)와 방향·크기가 맞는다 | **가설 A 지지** — GIL 경합이 11% 차이의 실체 |
| `rho`가 R/N/J 사이에서 §8의 팔 간 산포(F↔C −0.86%) 수준 안에 모인다 — 즉 사실상 평평하다 | **가설 A 반증, 가설 B 지지** — 순수 스레드풀 스케줄링/경합 문제. GIL 총량은 이미 §8이 답했으니(ρ≥0.939) 이 실험은 "그 총량이 R/N/J 사이에서 재분배되는가"에만 답하면 된다 |
| `rho`가 팔 순서와 무관하게 흔들린다(산포가 커서 방향도 안 잡힌다) | 판정 불가 — 표본 부족. §8과 같은 규모(13판)로도 안 갈리면 이 질문은 이 rig의 해상도 밖일 수 있다 |

**어느 쪽으로 나와도 산출물이 있다.** 특히 가설 B가 맞으면 "GIL이 병목의 만능 설명이 아니다 —
스레드풀 배분도 독립적으로 천장을 흔든다"는 것이 GIL 결론(§8)에 실제로 새 정보를 더한다.

## 2. 무대 — 새로 만들 게 거의 없다

이미 있는 것 둘을 **교차**시키기만 하면 된다 — 지금까지 한 번도 같이 안 돌았다:

| 축 | 이미 있는 구현 | 커밋/PR |
|---|---|---|
| 응답 모드(R/N/J) | `ai-server/app/config.py`의 `RESPONSE_MODE`, `pose.py`의 `_RESPONSE_MODE`/`_RESPONSE_MODEL` 분기 | `5a4c878`(post-loop-breakdown 판이 쓴 커밋) |
| GIL 프로브 | `GIL_PROBE_INTERVAL`(기본 0=끔) — 일이 없는 별도 스레드가 1ms 자고 깨며 지연을 담는다 | [PR #507](https://github.com/Shadowfit/init/pull/507), §8이 F/Z/C로 이미 씀 |

**팔 = 두 축의 곱** — 최소 3×2 = 6팔(R/N/J × 프로브 켬/끔). 프로브 끔 팔은 §8의 C처럼
"프로브 자체가 공짜인가"를 이 조합에서도 재확인하는 용도로 남기거나, 이미 §8이 F↔C
−0.86%(산포 안)로 확정했으니 **꺼도 되면 3팔(R/N/J, 프로브 항상 켬)로 줄여도 된다** — 그러면
§3-1의 원판(12판, 버림 1 + R N J J N R R N J J N R)과 거의 같은 규모로 프로브만 얹는 셈이라
가장 싸다.

| | 값 |
|---|---|
| 박스 | `c7i.4xlarge`(§8·post-loop-breakdown과 동일 스펙 — 절대값 비교 가능) |
| 부하 | 160세션 · 3.0fps · 판당 90초 · 풀 201(§3-1 원판과 동일 — 조건 안 바꾸면 원판과 나란히 놓을 수 있다) |
| 팔 | **R·N·J**(프로브 항상 켬) — 최소 구성. 여유 있으면 §8처럼 켬/끔 6팔로 늘려 "프로브가 팔별로 다르게 공짜인가"까지 검산 |
| 판 배열 | 라틴 방격 또는 순서 반전, 버림 1(§3-1·§8 관례 그대로) |
| 걷는 지표 | `cpu.ai.mean`(vCPU, §3-1과 같은 지표) · GIL 프로브의 지연 분포(§8과 같은 지표, 평균·p99·표본수) · 스레드풀 `waiting=0` 비율(§5가 이미 건 것) |

## 3. 가치 판단 — 정직하게

- **GIL 총 점유율 질문(ρ≥0.939)에는 아무것도 안 더한다** — 그건 §8이 이미 답했고 이 실험은
  그 값을 다시 안 잰다.
- **더할 수 있는 것은 "그 점유율이 응답 모드 사이에서 재분배되는가" 하나뿐이다.** 이게 맞으면
  "직렬화 방식 선택이 GIL 경합을 통해 처리량에 영향을 준다"는, 튜닝에 실제로 쓸 수 있는 지식이
  된다(예: 스레드풀에 일을 미는 방식을 피해야 한다는 근거). 안 맞으면(가설 B) "GIL은 이미 닫힌
  질문이고, 남은 11% 변동은 스레드풀 스케줄링의 잡음성 특성"이라는 것도 나름의 결론이다 — 둘
  다 이후 판단(§7 안 할 것 후보 — 예: 스레드풀 크기 튜닝을 고려할지)에 쓸 수 있다.
- **정직한 하한**: 11%는 크지 않은 신호고(§8의 GIL 반증 판정선이 1.7~2배였던 것과 비교하면
  이 자리는 원래 "미세조정" 급 질문이다), 표본을 §3-1과 같은 규모(12~13판)로 늘려도 신호 대
  잡음비가 낮아 반증 조건 표의 세 번째 갈래("판정 불가")로 떨어질 가능성이 낮지 않다. **착수
  전에 이 실험이 우선순위표에서 어디 있는지부터 판단할 것** — GIL 결론 자체는 이미 프로덕션
  판단(N=3 프로세스, `proc-count-sweep-2026-08-24`)에 반영됐고, 이 11%는 그 판단을 안 바꾼다.
