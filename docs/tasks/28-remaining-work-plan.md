### 1-1. 채점 중 정정된 것 (같은 오류 반복 방지용)

### 1. 이슈 #59 — 세션 재개 (17~24h / 11~17h) ⚠️ 크로스 레포

설계는 [`session-resume-and-ai-state.md`](../decisions/session-resume-and-ai-state.md)에 있고 **A+B 선호가 이미 표명**돼 있다(확정은 §6 항목별 confirm 후).

| 하위 작업 | 시간 |
|---|:--:|
| **선결**: 클라 복귀 시 실제 호출 확인 (`frontend/app/(tabs)/exercise.tsx`) | 1h |
| 문서 §6 항목별 결정 | 1h |
| A — 조용한 실패를 명시적 실패로 (에러코드·응답) | 2~3h |
| B — 재부착 엔드포인트 `POST /sessions/{id}/resume` | 4~6h |
| proto `rep_number` 추가 + `pose_data` 컬럼 + `PoseDataService` 반영 | 3~5h |
| ai-server — `StartAnalysis`에 `completed_reps` 주입 수용 | 3~4h |
| 테스트 | 3~4h |

🔶 **축소 옵션**: rep 카운트 복원을 포기하면(재개 시 rep 0부터) proto·스키마·ai-server 변경이 빠져 **8~12h**. 대신 "이어서 하는데 횟수가 초기화"라 UX가 반쪽.

⚠️ 이 목록에서 **유일하게 Spring 밖(FastAPI·proto)을 건드리는 항목**이다.

### 2. 종목 가드 (2~3h / 0.5~1h) — 가장 싼 항목

`data.sql`에 런지·플랭크가 시드돼 있는데 `SessionService.createSession`은 `EXERCISE_NOT_FOUND`만 확인하고 **종목 가드가 없다.** 사용자가 런지 세션을 시작할 수 있고 조용히 빈 결과가 나온다.

- `exercises.analysis_supported` 컬럼 + 엔티티 필드 + `createSession` 검증 + `ErrorCode` + 테스트
- 효과: **"껍데기"가 "의도적 제한"으로 바뀐다.** 시연 리스크 제거

**추가 잔여물** 🔶: 플랭크는 rep 개념이 없어 `total_reps`를 `hold_seconds` 의미로 재사용할지가 미결 — [`23-ai-tasks-detail.md:106`](./23-ai-tasks-detail.md)에 "결합 인터페이스 합의 사항"으로 기록돼 있다. 이건 AI 영역이 아니라 **Spring 스키마 설계 문제**다.

### 3. 관리자 페이지 + QueryDSL (25~37h / 10~16h) — 최대 덩어리

범위·필터는 [`admin-page-scope.md`](../decisions/admin-page-scope.md), 기술 결정은 [`querydsl-adoption.md`](../decisions/querydsl-adoption.md).

| 하위 작업 | 시간 |
|---|:--:|
| 의존성 + `JPAQueryFactory` 빈 | 1h (빌드 검증 완료라 삽질 없음, §7-3) |
| **인덱스 3안 결정 + 적용** | 3~6h |
| 회원 목록 (조건 5 + 정렬 + 페이징 + count) | 6~8h |
| 세션 목록 (회원 조인) | 5~7h |
| 운동/영상 목록 + 수정 + 삭제 | 4~6h |
| 대시보드 통계 5종 | 4~6h |
| 공통 페이징 DTO·예외·Swagger | 2~3h |

🔶 **+5~10h**: 인덱스 실험(`EXPLAIN` 비교, 조합별 측정)까지 하면. 하면 포폴 산출물이 하나 더 생긴다.

### 4. CD + 배포 문서 (7~13h / 5~9h)

**목표를 "상시 운영"이 아니라 "필요할 때 5분 안에 띄울 수 있는 상태 + 파이프라인"으로 잡는다.** 상시 구동은 MySQL+Spring+FastAPI를 한 대에 올려야 해서 [[feedback_ec2_container_memory_cap]] 문제가 재현되고 비용도 든다. 켜져 있지 않아도 파이프라인과 문서가 있으면 "돌아간다"는 증명이 된다.

- GitHub Actions: build → 이미지 push → EC2 배포 (4~8h)
- secrets·환경변수 정리, 운영용 compose (2~3h) / 배포 문서 (1~2h)

### 5. OAuth2 (10~13h / 6~9h) — 서류 키워드 효과 최대

현재 외부 통합 **0개**([`27-implementation-gaps.md`](./27-implementation-gaps.md) §3). 구현 %에는 기여가 0이지만 서류 통과율에는 가장 크게 기여한다.

가장 까다로운 지점은 **기존 email/password 계정과 소셜 계정의 충돌 처리**다. 여기서 시간이 갈린다.

### 6. Prometheus + Grafana (5~7h / 2~4h) — 조건부

현재 `docker-compose.yml`에 MySQL·backend·ai만 있고 `micrometer-registry-prometheus`도 없다. 커스텀 메트릭 3종 + outbox lag가 **`/actuator/metrics` 스냅샷 조회만** 가능한 상태.

**착수 조건 🔶**: 남은 실험(소량 DELETE 파편화 / 관리자 인덱스 3안 비교)을 **하기로 정할 때만.** 안 하면 값이 없다.

가장 아까운 사례: 풀 사이징 실험에서 pool=10·c=100이 47% 타임아웃으로 붕괴한 걸 실측했는데, 그 순간의 커넥션 대기·활성 수 그래프가 없어 **결과 수치만 있고 과정이 없다.**

## 3. 시간이 줄지 않는 것

Claude 병행 배율이 항목마다 다른 이유. 아래는 **0% 압축**된다.

| 항목 | 왜 |
|---|---|
| **사용자 결정** | #59 §6 confirm, 인덱스 3안 선택 — 대신할 수 없음 |
| **외부 콘솔 작업** | OAuth 앱 등록, EC2 프로비저닝, GitHub secrets 입력 |
| **빌드·테스트 실행** | `gradlew test` ≈ 1분 30초 × 반복. 시도 횟수가 늘면 오히려 증가 |
| **부하·인덱스 측정** | 걸리는 만큼 걸림 |
| **PR 리뷰 대기** | CodeRabbit 반영 커밋 이력 있음 → 전체에 **+10~20%** 잡는 게 안전 |
| **본인의 코드 이해** | §6 참고 |

→ 그래서 배율이 보일러플레이트 많은 #3은 ~2.3x, 콘솔·크로스레포 비중이 큰 #1·#4는 ~1.4~1.5x로 갈린다.

## 6. 정직 단서 (추정의 한계)

- **시간은 전부 추정이다.** 코드 규모와 기존 패턴을 보고 잡았고 실측이 아니다.
- **#59는 선결 조사 전까지 정확해지지 않는다.** 클라가 복귀 시 `POST /exercises/sessions`를 다시 부르고 있다면 증상 자체가 달라지고(세션 row 중복) 범위가 바뀐다.
- **%는 기능 개수 기반 근사**다. 작업량 가중은 추정이다.
- **Claude 병행 배율은 "사용자가 검토한다"를 전제**로 한 값이다. 생산량이 2배면 검토 부담도 2배다. 실제로 이 계획을 세운 세션에서 AI 측 오류 2건(빌드 경로 리스크 오판, Spring/AI 채점 경계 혼동)이 사용자 지적으로 정정됐다.
- ⚠️ **포폴 고유 리스크**: 면접에서 "왜 이렇게 했나요"에 답해야 한다. 이해하지 못한 코드가 쌓이면 아낀 시간을 그 자리에서 잃는다. 특히 **처음 쓰는 기술(QueryDSL)** 은 작성이 빨라도 설명 책임이 남는다.
  - 권고 분업: 반복 보일러플레이트는 전량 위임 / **QueryDSL 목록 API는 첫 1개만 함께 만들고 나머지는 직접** / #59·인덱스 3안은 조사·정리만 위임하고 결정·구현은 직접. 이 경우 배율 ~1.5x(전체 40~65h)로 떨어지지만 면접에서 무너질 구간이 안 생긴다.
