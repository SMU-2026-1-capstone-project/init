# ADR-0009: 스키마 마이그레이션 이력 추적에 Flyway를 도입한다

작성일: 2026-08-07
상태: Accepted
근거 문서: [`../decisions/schema-migration-tracking.md`](../decisions/schema-migration-tracking.md)

## Context

dev DB의 실제 스키마가 `schema.sql`과 2건 벌어져 있어(이슈 #115) `UPDATE ... SET last_active_at`이 `Unknown column`으로 실패했다. 마이그레이션은 SQL 파일로 존재했지만 **어느 파일이 어느 인스턴스에 적용됐는지 추적할 수단이 없었다** — "누가 언제 적용했는지"를 알 방법이 `CREATE_TIME`(ALTER로도 갱신되어 근거로 약함) 같은 간접 추정뿐이었다. 이 항목은 원래 2학기 계획(Week 1, OP-04)에 이미 예정돼 있었는데, 실제 결함이 먼저 터지면서 "할까 말까"가 아니라 "지금 당길까 2학기까지 미룰까"가 실질 질문이 됐다.

## Decision

**Flyway를 도입**하고, 착수 시점은 **CD(#4) 착수 직전**으로 앞당긴다 — CD가 붙으면 "배포는 자동, 스키마 적용은 수동"이라는 불일치가 배포마다 재발하는 구조가 되므로 그 전에 넣는 게 싸다. `schema.sql`은 지우지 않고 유지한다(initdb·`SchemaEnumConsistencyTest`·관리자 필터 실측 rig 세 곳이 이걸 참조해 지우면 깨진다) — `V1__baseline.sql`로 현재 스키마를 캡처하되, 신규 설치(initdb)와 기존 인스턴스(Flyway) 중 어느 쪽을 정본으로 삼을지는 구현 시점에 정한다. 선행 조건으로 이미 있던 수동 마이그레이션 3건의 적용 여부를 먼저 확인했다(baseline을 먼저 찍으면 미적용분이 "적용됨"으로 영구히 잘못 기록되므로) — 실측 결과 3건 모두 이미 반영돼 있었다. **드리프트 탐지(손으로 바꾼 스키마를 감지하는 것)는 이번엔 채택하지 않는다** — 기각이 아니라, Flyway를 넣어도 여전히 안 보이는 구멍이지만 지금 아프다는 근거가 없어 별건으로 열어둔다.

## Consequences

- 얻는 것: 스키마 변경 이력이 `flyway_schema_history` 한 줄로 추적된다 — 이번 검증 과정에서 그 부재(`CREATE_TIME`으로만 추정해야 했던 것)를 직접 체감한 것 자체가 도입 근거를 한 번 더 보여줬다. CD가 붙기 전에 "배포는 자동, 스키마는 수동"이라는 재발 구조를 막는다. 백엔드 신입 채용 시그널로서 비어 있던 자리(마이그레이션 도구)가 채워진다.
- 감수하는 것: `schema.sql`과 Flyway 마이그레이션 파일이 당분간 공존한다 — 신규 설치와 기존 인스턴스 중 어느 쪽이 정본인지는 구현 시점까지 미정으로 남겨뒀고, 그 불확실성이 작업 시간 추정 폭(4~7h)의 원인이다. 드리프트 탐지는 이 결정으로 풀리지 않는다 — 손으로 스키마를 바꾸는 경로는 여전히 안 보인다.
- 다음에 영향받는 결정: 드리프트 탐지 도입 여부는 이 결정과 별개로 열려 있다 — 실제로 아픈 사례가 나오면 그때 다시 연다.

## Alternatives considered

- ㄴ(드리프트 탐지 도구 병행 도입) — Flyway의 대안이 아니라 별개 문제다(Flyway를 넣어도 손으로 바꾼 DB는 여전히 안 보인다). 지금 아프다는 근거가 없어 별건으로 열어두고 이번엔 채택하지 않았다.
- ㄷ(도구 없이 수동 마이그레이션 디렉터리 컨벤션만 문서화) — 이미 실패한 전례가 있다. PR #102가 정확히 이 방식이었는데, 마이그레이션 파일마다 "Flyway가 없어 기존 인스턴스는 이 디렉터리가 담당한다"는 문구가 이미 적혀 있었는데도 실제로 빠뜨렸다 — 문서 부재가 원인인 사고가 아니었다.
- 2학기 Week 1까지 착수를 미루기 — dev DB가 이미 한 번 실제로 깨진 전력이 있고(수동 적용 3건으로 즉시 해결되긴 했다), CD 착수 순서상 먼저 넣는 게 나중에 넣는 것보다 싸다고 판단해 앞당겼다.
