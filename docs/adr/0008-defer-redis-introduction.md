# ADR-0008: Redis 도입을 보류하고 재검토 트리거 5개를 박제한다

작성일: 2026-05-25
상태: Accepted
근거 문서: [`../decisions/redis-introduction.md`](../decisions/redis-introduction.md)

## Context

백엔드 채용 신호 측면에서 Redis는 흔한 키워드지만, "도입하면 좋을 것 같다"는 추정만으로 넣으면 면접에서 근거를 캐물었을 때 들킨다. MySQL만으로 정말 부족한지를 엄격하게 증명해야 도입이 정당화된다는 평가 프레임을 세우고 — 정확성/일관성(MySQL로 원천 불가능한 의미가 있는가), 성능 한계(측정 결과가 SLO를 초과해 캐싱 외 방법이 없는가), 확장성 강제(단일 인스턴스 가정이 이미 깨졌는가) 세 기준 중 하나라도 실제 코드의 한계나 측정 데이터로 충족해야 한다는 원칙 위에서 — 현재 코드의 Redis 후보 use case 7개(JwtBlacklist, AI session_state, 페르소나 캐시, 분산 락, rate limiting 등)를 하나씩 검증했다.

## Decision

**Redis 도입을 보류한다.** 7개 후보 전부 세 기준(정확성/성능/확장성) 중 어느 것도 측정 데이터로 증명하지 못했다 — "예측 부족함(가설)"만으로는 도입 근거로 인정하지 않는다는 이 문서 자신의 엄격성 원칙에 따라 전부 미증명으로 판정했다. 대신 재검토 트리거 5개를 명시적으로 박제한다 — T1(다중 Spring 인스턴스 운영 시작), T2(AI session_state 외부화 분기가 D1에서 D2로 격상), T3(baseline 측정 후에도 SLO 위반이 지속), T4(JWT 재시작 시 토큰 무효화 실패로 인한 보안 사고), T5(Rate limiting 기능 도입이 별도로 결정됨). 이 중 하나라도 실제로 발생하면 이 문서를 재오픈한다.

## Consequences

- 얻는 것: "Redis가 있어야 정상"이라는 채용 시그널 압박에 흔들리지 않고, 정직한 MySQL 단일 baseline 위에서 서사를 세울 수 있다. 재검토 조건을 미리 5개로 못박아둬 나중에 "왜 안 넣었나"를 임의로 재해석하지 않게 한다.
- 감수하는 것: 채용 시그널로서 Redis 키워드 자체는 못 채운다 — 이건 서류 단계 필터링 리스크로, 이 프로젝트가 별도 문서(`portfolio-benchmark.md`)에서 다루는 트레이드오프다. 후속 문서(`redis-adoption.md`, 2026-08-08)가 같은 질문을 다시 열었는데, 그 사이 T4의 유력 후보였던 `JwtBlacklist` 자체가 코드에서 사라졌다(별도 결정 `token-lifecycle.md`가 access token TTL을 24시간→30분으로 줄여 문제 자체를 없앴다) — 트리거 목록도 시간이 지나며 전제가 바뀔 수 있다는 걸 보여준 사례다.
- 다음에 영향받는 결정: AI session_state 외부화(T2)는 이 문서가 아니라 `ai-backend-coupling.md` 분기 D의 소관으로 명시적으로 남겨뒀다. 후속 재검토(`redis-adoption.md`)는 아직 사용자 확정 전이라 이 결정을 대체하지 않는다.

## Alternatives considered

- 추천 B(제한적 도입 — AI session_state 외부화만 우선 검토) — 그 결정은 이 문서가 아니라 `ai-backend-coupling.md` 분기 D의 소관이다. 이 문서에서 그 격상을 권고하는 것 자체가 다른 문서의 의사결정 경계를 침범한다고 판단해 기각했다.
- 추천 C(어필 우선 도입) — "도입하면 좋을 것 같다"는 가설만으로 근거를 세우는 것으로, 이 문서 자신이 세운 엄격성 원칙(측정 데이터 필요, 추정 거부)에 정면으로 위배돼 명시적으로 배제했다.
