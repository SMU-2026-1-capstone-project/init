# ADR-0007: 다음 세션 강도·볼륨 추천을 규칙 기반 단일 API로 구현(BE-08)

작성일: 2026-08-30
상태: Accepted
근거 문서: [`../decisions/recommendation-algorithm.md`](../decisions/recommendation-algorithm.md)

## Context

리포트 기능(`GET /reports/sessions/{id}`)이 순수 읽기 집계라 "데이터를 소비하는" compute/write 경로가 없다는 문제 제기가 있었다. 과거 운동 기록을 읽어 다음 운동을 추천하면 이 경로가 채워진다. BE-08 원안은 "운동 종목 3개를 골라 루틴을 짜는" 추천이었는데, 이 프로젝트가 실제로 분석 가능한 운동이 스쿼트뿐인 squat-first 제약과 정면 충돌해 스코프부터 다시 정해야 했다.

## Decision

**스코프는 A(같은 운동의 강도·볼륨 추천 — progressive overload)만 지금 채택**하고, B(운동 종목 루틴 추천)는 2학기 운동 확장 이후로 보류한다. **알고리즘은 규칙 기반**(협업 필터링·LLM 배제)을 채택한다. 규칙 임계값(평균 동기화율 85%/60% 경계, 최근 N=3세션 평균)은 실사용자 데이터가 없어 다른 값을 정당화할 근거도 없다는 것을 인정한 채 **미검증 잠정치로 명시하고 그대로 채택**한다. 콜드스타트 기본값은 `Member.workoutLevel`(5단계)을 `12-persona-difficulty.md`의 난이도 공식이 쓰는 시작 `level`(STARTER=1 … EXPERT=9)로 매핑한다. API는 `GET /recommendations/next-session` 단일 엔드포인트로 확정한다. 세션 이력 조회는 신규 인덱스도 캐싱도 도입하지 않는다 — 최근 N개 세션 조회를 실측하니 기존 `idx_session_member_status_start`가 역순 스캔으로 이미 상수 비용(계정 세션 수와 무관하게 0.4ms대, 읽은 행 3개)이라 최적화할 여지 자체가 없었다. 구현은 어디에도 상태를 쌓지 않는 순수 함수(매 호출마다 재계산)로 한다.

## Consequences

- 얻는 것: 리포트(읽기 전용)에 이어 "과거 데이터를 읽어 계산해 소비하는" compute 경로가 생겨 백엔드 깊이가 늘어난다. 규칙 기반이라 결정적이고 근거를 한 줄로 설명할 수 있다. 인덱스·캐싱 도입 여부를 실측으로 먼저 확인한 뒤 "필요 없다"고 정직하게 닫아, 근거 없는 최적화를 피했다.
- 감수하는 것: 임계값(85%/60%, N=3)과 콜드스타트 매핑(5단계) 둘 다 **실사용자 데이터 없이 정한 잠정치**임을 코드·문서에 명시적으로 남겼다 — 실사용자 데이터가 쌓이면 재조정 대상이다. 구현 중 `Session.difficultyLevel`이 세션 생성 흐름에서 실제로 채워지지 않는(항상 기본값 1) 것을 발견해, "직전 난이도"를 DB에서 가져오는 대신 프로필 기반 시작 level + 최근 3세션 평균을 매 호출 재계산하는 방식으로 설계를 조정했다 — 세션 생성 흐름 자체는 이 결정의 범위 밖으로 손대지 않았다.
- 다음에 영향받는 결정: 스코프 B(종목 루틴 추천)는 2학기 운동 확장이 선행돼야 다시 열 수 있는 별개 결정이다. 임계값 재조정은 실사용자 데이터 확보가 선행조건이다.

## Alternatives considered

- 협업 필터링(CF) — 사용자가 사실상 0명이라 협업할 대상 자체가 없어 인위적인 선택이 된다.
- LLM 기반 추천 — 강도·볼륨처럼 결정적이어야 하는 값에 비결정적 호출을 쓰는 건 과하고, 이 프로젝트의 다른 기능(BE-03)이 이미 LLM 자리를 맡고 있어 중복이다.
- 원안 API 형태(`/today`·`/weekly`, 종목 3개 전제) — 스코프 A(강도·볼륨 단일 추천)와 형태가 안 맞아 폐기하고 단일 엔드포인트로 재설계했다.
- 신규 세션 이력 인덱스 도입 — 설계 시점엔 "인덱스 설계 여지가 있다"고 예상했으나 실측(`EXPLAIN ANALYZE`, 1,680세션 계정)에서 기존 인덱스가 이미 최적임이 확인돼 기각.
- 캐싱 도입 — 원본 쿼리 비용이 사실상 0(0.4ms대)이라 캐시로 아낄 게 없고, `@CacheEvict` 누락 등 stale 버그 위험만 추가돼 보류.
