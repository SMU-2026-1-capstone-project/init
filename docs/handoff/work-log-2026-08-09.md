## 1. #143 — 프레임 수로 시간을 재는데 fps 계약이 없다

`rep` 판정 경로에 시간이 **프레임 개수**로 인코딩된 상수가 3개 있는데, 그 개수를 초로 되돌리는 fps 가정이 상수마다 달랐다.

| 상수 | 값 | 주석이 가정한 fps |
|---|---|---|
| `MIN_REP_FRAMES` | 4 | 3fps |
| `MAX_BOTTOM_FRAMES` | 15 | **3fps** ("3fps 기준 5초") |
| `MAX_REP_FRAMES` | 60 | **10fps** ("10fps × 6초") |

같은 스트림을 3fps / 10fps 로 다르게 환산하고 있었고, 그 fps 는 코드로 강제돼 있지 않다(`session_state.py:19-21` 주석이 스스로 인정).

### 재현이 내 예측을 뒤집었다

이슈 본문에 *"10fps 면 `MAX_BOTTOM_FRAMES` 가 1.5초가 되어 정상 rep 이 버려진다"* 고 적었다. 실제로 재보니 **임계는 0.5초**였다 — 예측이 1초 관대했다.

| 바닥 체류 | 3fps (현재) | 10fps | 30fps |
|---|---|---|---|
| 0.5s | ✅ 1 | ❌ 0 | ❌ 0 |
| 2.0s | ✅ 1 | ❌ 0 | ❌ 0 |

30fps 에서는 **멈춤 없는 스쿼트조차** 집계되지 않는다.

### 📌 원인 — 상수 이름이 재는 것을 오해하게 만들었다

`MAX_BOTTOM_FRAMES` 는 «바닥 체류» 를 재지 않는다. bottom 진입이 `smoothed ≤ 100°`, 이탈이 `≥ 150°` 라 **하강·상승의 밴드 통과 구간이 통째로 예산에 포함된다.** 계측하니 bottom 구간 ≈ **체류 + 1.1초** 였고, 10fps 에서는 체류가 0 이어도 15프레임 예산 중 11이 이미 나간다.

주석의 *"실제 바닥 체류는 1초 내외라 5배 여유"* 는 **체류만** 계산에 넣은 것이다. 이름이 «bottom frames» 라서 그 계산이 자연스러워 보였다.

> 이 오해는 수정 방향에도 영향이 있다 — `timestamp_sec` 기반 초 단위로 바꿔도 **상수 값을 다시 정해야 한다.** 15프레임 → 5초로 환산만 해서는 밴드 통과가 예산에 포함되는 문제가 그대로다.

**재현 방법**: 프론트 `intervalMs` 를 바꾸는 대신, 시간으로 정의한 스쿼트 1회를 fps 만 바꿔 샘플링해 분석기에 먹였다. 호출 순서는 기존 하니스 `test_streaming_rep_counting.py:_count_reps` 를 그대로 썼다. 스크립트는 커밋하지 않았다 — 회귀 테스트로 넣을지 **미결정**.

## 2. #144 — 같은 드리프트 방향이 또 나왔다

`projection` 개선 배수가 문서마다 `8x` / `29~41x` 로 갈렸다. 추적하니 **둘 다 맞았다** — 서로 다른 스케일의 두 측정이다.

| | 8x | 29~41x |
|---|---|---|
| 일시·환경 | 2026-06-02, 로컬 | **2026-07-15, AWS EC2** |
| 테이블 | 412만 행 | **1억 행 (~230GB)** |
| payload | −98.7% | −98.7% (동일) |

배수가 커진 이유도 원본에 있다 — 버퍼풀은 2GB 그대로인데 테이블이 25배 커져 작업셋 비율이 나빠졌고, projection 이 회피하는 off-page 랜덤 I/O 가 그만큼 늘었다. **결론이 뒤집힌 게 아니라 강화됐다.**

문제는 반영 누락이었다. 원본 2곳(`realmysql-experiments.md`·`interview-qa-kandl.md`)은 둘 다 기록했는데, **요약 5곳이 412만 행 시절 값에 멈춰 있었다** — `FINAL-REPORT.md` 같은 대외 문서에 프로젝트 최대 실측이 안 들어가 있었다.

### 📌 배수보다 위험한 게 같이 빠져 있었다

원본이 달아둔 캐비엇이 **요약 5곳 어디에도 없었다**:

> 이 쿼리는 세션 종료 시 precompute 가 세션당 한 번 도는 것이고, 비동기라 사용자는 이 지연을 원래 못 느낀다. "리포트가 빨라졌다" 로 말하면 부정확.

그런데 `problem-solving-log.md:128` 은 이 항목을 **🔴 헤드라인**으로 달아뒀다. 캐비엇 없이 배수만 들고 나가면 *"그 조회를 사용자가 언제 하나요?"* 한 마디에 무너진다.

**[`문서 드리프트는 한 방향`] 패턴 그대로다** — 수치·기능 표는 맞고 **보장·조건·한계**가 빠지는 방향으로만 어긋난다. 오늘로 이 패턴의 사례가 하나 더 쌓였다.

**조치**: 5개 문서 7곳을 두 측정 병기 + 캐비엇 동반으로 수정. **미커밋** (§6 참조).

## 4. #134 — 비교표의 축이 선택지를 왜곡하고 있었다

«내부 서비스 토큰이 앱 번들에 들어간다» 이슈를 파다 두 가지가 더 나왔다.

### 4-1. 소유권 갭 — 토큰을 고쳐도 남는 층

`InternalAuthInterceptor:28` 이 하는 일은 **문자열 동등 비교 하나**다. 통과한 호출에 "누가 불렀는가" 가 남지 않으므로, downstream 이 소유권을 검사하고 싶어도 **비교할 대상이 없다.** 노출된 4개 RPC 전부 `request.sessionId` 를 그대로 신뢰한다(`savePoseDataBatch`·`reportFeedbackBatch` 는 `existsById` 만, 나머지 둘은 그마저 없다).

이게 왜 중요하냐면 — **#134 의 옵션 4개 중 ㄴ(사용자 JWT)만 이 갭을 닫는다.** 비교표가 «토큰이 새는가» 축만 보고 있어서 ㄱ·ㄷ 이 실제보다 완결적으로 보였다.

### 4-2. HS256 — «검증 키» 가 곧 «서명 키» 다

표의 ㄴ 비용이 *"AI 가 JWT **검증 키**를 알아야 하고"* 로 적혀 있었는데, 실제 서명은 **HS256 대칭**(`JwtUtil.java:29,57`)이다. 즉 ㄴ 을 그대로 적용하면 **AI 가 임의 사용자 JWT 를 발급할 수 있게 된다.**

| | 새는 것 | 그걸로 할 수 있는 것 |
|---|---|---|
| 현행 | `INTERNAL_API_TOKEN` | AI HTTP + Spring 내부 RPC |
| ㄴ + HS256 | `JWT_SECRET` | **임의 회원 위장 → Spring REST 전체** |

«근본적» 이라는 평가는 소유권 축에서는 맞지만, 키 배포 방식을 함께 정하지 않으면 **blast radius 가 오히려 커진다.**

### 4-3. 선택지 하나가 통째로 빠져 있었다

비교 문서를 쓰려고 `ai-backend-coupling.md` 를 열어보니 **§5-γ 에 이미 «분기 I: 인증 토큰 흐름» 이 있었다.** 2026-05-24 에 I1 잠정 채택 + *"운영 단계에서 **I2**(세션 단위 단기 토큰) 전환 검토"* 로 결정 로그까지 남아 있다.

**그런데 #134 의 옵션 표에 I2 가 없다** — 원 결정이 전환 대상으로 지목한 바로 그 안이다.

> 📌 새 이슈를 쓸 때 **기존 결정 문서를 안 열었다.** 그래서 이미 이름 붙은 분기를 새 이름(ㄱ~ㄹ)으로 다시 만들었고, 그 과정에서 안 하나를 잃었다.

**조치**: 분기 I 를 [`ai-auth-token-flow.md`](../decisions/ai-auth-token-flow.md) 로 이관. `ai-backend-coupling.md §5-γ` 는 이관 안내 + 이력으로 남겼다(두 곳에 현행 진실을 두지 않기 위해).

### 4-4. ㄱ(값 분리) 채택·적용

사용자 confirm 후 적용. 토큰 **값**을 둘로 나눴다 — HTTP 는 `AI_PUBLIC_TOKEN`, gRPC 양방향은 `INTERNAL_API_TOKEN`. **내부 토큰은 이제 클라이언트로 나가지 않는다.** Spring 무변경.

**회귀 테스트 신설** — 내부 토큰으로 HTTP 를 통과할 수 없음을 잠갔다. 미들웨어가 다시 `INTERNAL_API_TOKEN` 을 보거나 fallback 을 넣으면 깨진다. (`test_auth_middleware` 8/8, ai-server 전체 통과)

**닫히지 않은 것**: `AI_PUBLIC_TOKEN` 도 번들에 인라인되므로 «설치본을 가진 누구나 `/pose` 호출 가능» 은 그대로다. 피해가 AI 세션 상태로 한정될 뿐이고, 호출자 신원을 만드는 I2 는 **미결정**.

⚠️ **런타임 미검증** — 컨테이너 기동·프론트 재빌드로 401/200 을 확인하지 않았다.

## 5. 곁가지 — DAU 1,000 은 이미 답이 나와 있었다

*"실험을 많이 하는데 DAU 1,000 을 위한 것인가"* 라는 질문이 나왔다. 확인해보니 **질문의 전제가 이미 해소돼 있었다.**

`load-test-strategy.md:89` 가 2026-05-31 에 *"DAU 1,000 으로는 throughput 스토리 못 만듦 → «대용량 누적 데이터에서의 쿼리 최적화» 로 포지셔닝해야 방어됨"* 이라고 못박았고, §4.6 이 지정한 대체 스토리 3개는 **셋 다 구현·실측까지 끝나 있다**(projection −98.7% / precompute / 파티션 TTL 625x).

즉 답은 «포지셔닝을 바꿔야 한다» 가 아니라 «이미 바꿔놨고 증거가 있다» 였다.

부수로 확인한 것 — **DAU 1,000 은 문서 자신의 «잘 됐을 때» 열보다 위다.** 퍼널 역산(DAU = MAU 의 10~20%)하면 MAU 5,000~10,000 이 필요한데, 문서의 낙관 열은 MAU ~3,000 / DAU ~500 이다. 규모를 키워 방어하는 방향은 이미 닫혀 있다.

## 6. 사고 — 동시 세션과 인덱스 경합

ㄱ 작업만 브랜치를 파서 커밋했는데 **의도치 않은 파일 15개가 섞였다.**

- `git add` 직후 `git diff --cached --stat` 으로 확인했을 때는 **정확히 14개**(333 insertions)
- 커밋된 것은 **29개**(546 insertions)

즉 `add` 와 `commit` **사이에 다른 프로세스가 `loadtest/results/**` 를 인덱스에 올렸고**, `git commit` 이 인덱스 전체를 커밋하면서 함께 들어갔다. 이어서 내가 만들지 않은 커밋(`c83a7a3`, #151)이 같은 브랜치에 올라왔고, 워킹트리에도 본 적 없는 파일(`analyzer_registry.py` 등)이 생겼다 — **다른 세션이 같은 저장소에서 동시에 작업 중이었다.**

### 📌 남는 교훈

- **스테이징 시점의 확인은 커밋 시점을 보장하지 않는다.** 경로를 명시해 커밋했어야 했다 (`git commit -- <paths>`)
- **동시 작업 중에는 히스토리를 다시 쓰지 않는다.** `reset`/`rebase` 로 쪼개면 다른 세션 작업이 유실될 수 있어, 사용자 판단으로 **A(그대로 둔다)** 를 택했다. 내용 손실은 없고 커밋 위생만 어긋난 상태다

## 7. (다른 트랙) 관리자 운동 종목 CRUD — 「남은 건 3개」가 5개였다

**① 등록 API 는 애초에 없었다.** `exercisesRepository.save()` 호출이 **0건**이다. 운동 3행은 Flyway `V2__seed_master_data.sql:26-33` 의 `REPLACE INTO` 로만 들어온다. 문서가 "등록 API"로 본 것은 `POST /exercises/{id}/reference`(`ExercisesController.java:33`)로 보이는데, 그건 **이미 있는 행**에 기준 좌표를 붙이는 것이라 등록이 아니다. 남은 것은 3개가 아니라 **5개**였다.

**② "A·B 와 같은 패턴이라 새 설계가 없다"도 삭제에는 해당하지 않았다.** FK 정책이 세 갈래다(`V1__baseline.sql`):

| 참조 테이블 | 정책 | 삭제 시 |
|---|---|---|
| `exercise_references`(`:83`)·`exercise_feedback_templates`(`:278`) | `ON DELETE CASCADE` | 같이 지워짐 |
| **`exercise_sessions`**(`:110`) | **CASCADE 없음** | **FK 제약으로 실패** |

**✅ 하드 삭제 + 409 거부 (사용자 결정).** 소프트 삭제(`active` 플래그)는 미채택. 이 규칙은 새로 만든 게 아니라 **스키마가 이미 내린 결정**이고, 코드가 한 일은 그걸 500 대신 409(W011)로 옮긴 것이다 — 그래서 마이그레이션이 없다.

### 📌 원인 — 파일 위치로 「있다/없다」를 판정했다

`AdminExerciseController.java` 와 `ExercisesController.java` 에 운동 관련 POST 가 **있긴 있어서** "등록은 됐다"로 넘어갔다. `save()` 호출을 세어봤으면 5분에 드러날 것이었다. [[project_doc_drift_pattern]] 이 말하는 *"파일 위치가 아니라 계약으로 판정하라"* 의 사례가 하나 더 늘었다.

### 곁가지 — `analysisSupported` 를 열면서 드러난 것

등록·수정 DTO 에서 이 플래그를 뺐다가(세션이 실제로 열리는 문이라) 전용 엔드포인트로 분리했다: `PATCH /admin/exercises/{id}/analysis-support`.

**켤 때만 가드**: 기준 좌표 0건이면 400(W012). 그게 분석의 실제 입력이라, 비어 있으면 ai-server 가 *"sync_rate는 0으로 계산됨"* 을 **경고만 하고 진행해** 결과가 전부 0 인 — **실패로도 안 보이는** 상태가 된다.

⚠️ `@CacheEvict` 가 여기서는 선택이 아니다. 이 플래그를 읽는 것이 `SessionService.java:107` 의 `findByIdCached`(Caffeine 1h)라, 없으면 **꺼도 1시간 열려 있다.**

## 8. #147 — 거절 로직은 원래 있었고, 값이 도달을 못 했다

§7 의 `analysis-support` 를 붙이다 발견해 이슈로 등록했다. **`ai-server` 가 `exercise_id` 를 받아놓고 무시한다** — `exercise_servicer.py:73`·`:126` 이 `exercise_type = "squat"` 로 하드코딩. 즉 런지를 켜면 세션은 열리고 **런지 동작이 스쿼트 기준으로 채점된다.** 에러가 아니라 **조용히 틀린 점수**다.

### 📌 두 번 정정했다 — 둘 다 내가 낸 안이 틀린 것이었다

**정정 1 — ㄷ안의 판정 기준.** 처음엔 `EXERCISE_ANGLES`(`constants.py:22`)로 판정하면 된다고 적었다. 틀렸다. 그건 각도 **정의** 표라 `deadlift`·`pullup` 이 들어 있는데, **rep 카운팅은 그 표를 안 탄다** — `squat_analyzer._extract_raw_metrics`(`:60-88`)가 무릎 랜드마크를 하드코딩해 센다. 각도 표로 통과시키면 데드리프트가 무릎으로 rep 을 세는, **정확히 없애려던 그 실패**가 다시 생긴다. 기준은 **분석기 보유 여부**여야 했다.

**정정 2 — 「선행 과제」가 아니었다.** 레지스트리(`_analyzers`)가 HTTP 엔드포인트 모듈에 있는 걸 두고 *"`core/` 로 옮기는 것이 선행"* 이라 적었는데 **과장이었다.** 그냥 import 하면 됐고 순환 참조도 안 생긴다(`pose.py:18-19` 가 `app.grpc.*` 를 import 하지만 그쪽은 servicer 를 import 하지 않는다). 그대로 뒀으면 *"리팩터링부터 해야 한다"* 로 읽혀 착수가 불필요하게 무거워 보였을 것이다. 이슈 코멘트에 취소선으로 정정했다.

### 구현 — 새로 만든 게 아니라 도달하게 했다

거절은 원래 두 곳에 있었다(`pose.py:71-75` 의 `미지원 운동`, `angle_calculator.py:29` 의 `ValueError`). `StartAnalysis` 가 두 줄 위에서 `"squat"` 을 넣어 **도달을 못 했을 뿐**이다.

**거절 방식이 두 진입점에서 다르고, 그게 의도다:**

| | 방식 | 근거 |
|---|---|---|
| `StartAnalysis` | `abort(INVALID_ARGUMENT)` | Spring 의 `onNext` 가 `success` 를 **안 읽는다**(`ExerciseAnalysisService.java:244-247`). `success=False` 는 삼켜져 세션이 IN_PROGRESS 로 남는다 |
| `ReattachAnalysis` | `success=False` | Spring 이 실제로 읽어 W009 로 옮기는 경로가 이미 있다 |

### 📌 고치면서 새 부작용을 만들었고, 같이 고쳤다

`abort` 는 Spring 의 `onError` 로 가는데 거기서 `cb.onError` 가 **서킷브레이커에 실패로 기록**된다. 그런데 `INVALID_ARGUMENT` 는 *"AI 가 아프다"* 가 아니라 *"이 요청이 틀렸다"* 다 — 관리자가 잘못 켠 종목을 사용자가 몇 번 시도하는 것만으로 서킷이 열려(`sliding=10`·`min=5`·`threshold=50%`) **정상 스쿼트 세션까지 10초간 막힌다.**

`INVALID_ARGUMENT` 만 `releasePermission` 으로 집계에서 뺐다. `UNAVAILABLE`·`DEADLINE_EXCEEDED` 는 그대로 뒀다 — 넓게 잡으면 **진짜 장애를 서킷이 못 본다.**

> 이게 이날 두 번째 「고치다 만든 것」이다. 다만 앞의 둘(정정 1·2)은 **내는 단계**에서 잡혔고 이건 **넣는 단계**에서 잡혔다.

### ⚠️ 남은 한계 — 매핑이 ai-server 안에 있다

`_EXERCISE_ID_TO_TYPE = {1: "squat"}` 이라 **DB 의 id 를 파이썬에 적어둔 셈**이다. 시드가 바뀌면 조용히 틀린다. 제대로 하려면 Spring 이 종목 코드를 실어 보내야 하는데 `exercises` 에 코드 컬럼이 없고 `name` 이 한국어라 **마이그레이션이 따라온다** — 별도 결정으로 남겼다.

다만 **틀리는 방향은 안전한 쪽**이다. 표에 없는 id 는 거절되므로 *"되던 게 안 되는"* 쪽으로 틀리지 *"안 될 게 되는"* 쪽으로는 안 틀린다.

⚠️ **런지로 실제 세션을 돌려 재현하지 않았다.** 전부 정적 판독이고 #147 에 미검증으로 적었다.
