## 0. 판정

**백업은 두 팔 다 서비스를 «사실상 안 멈춘다». 갈리는 것은 되돌리는 시간이고, 자릿수가 다르다**
(배수는 §3 때문에 인용하지 않는다).

| | **A** `mysqldump` (논리) | **B** XtraBackup (물리) | **C** 파일 스냅샷 (대조군) |
|---|---|---|---|
| 판 수 | 3 (+버림판 1) | 3 (+버림판 1) | 1 |
| 백업 소요 | 168~178s | **139~144s** | 2s |
| 산출물 | **5,682 MB** | 10,367 MB | 10,245 MB |
| **복구 소요** | **1,282~1,304s (약 21분)** | **8~9s** ⚠️ §3 | 미측정(대조군) |
| **최대 쓰기 정지** | **42~126 ms** | 244~296 ms | **2,692 ms** |
| p50 쓰기 지연 | 2~4 ms | 11~13 ms | 5 ms |
| 복구 검증 | 행수·체크섬 일치 | 행수·체크섬 일치 | — |

원문 [`backup/backup.tsv`](backup/backup.tsv).

- **H1 「`--single-transaction` 은 사실상 안 멈춘다」 — 지지된다.** 팔 A 의 최대 정지가 42~126ms 다
- **H2 「물리가 논리보다 복구가 빠르다」 — 지지된다. 다만 배수는 인용 불가**(§3)
- **팔 C 가 계측의 양성 대조군 역할을 했다** — 같은 rig 에서 명백히 잠그는 팔이 2,692ms 로
  찍혔다. 그래서 A 의 42~126ms 는 **「계측이 못 잡았다」가 아니라 「실제로 안 멈췄다」** 로 읽힌다.
  이 구분을 세우려고 C 를 넣었고(설계 §9-1 ②), 실제로 값을 했다

## 1. Q1·Q2 — RTO

| 질문 | 답 |
|---|---|
| **Q1** 전부 잃었을 때 다시 쓰기를 받기까지 | **팔 A 로 약 21분** (1억 행 · m6i.xlarge · gp3 200GB 기준) |
| **Q2** 논리 vs 물리 복구 시간 차이 | **자릿수가 다르다.** 단 팔 B 값은 하한선이다(§3) |

🔴 **절대 시간을 「운영에서 N분」으로 인용하지 않는다.** 하드웨어 종속이다(설계 §5). 인용할
때는 **인스턴스 타입·디스크·행 수를 같이 붙인다.**

**산출물 크기는 반대 방향이다** — 논리 덤프 5,682MB 는 물리 백업 10,367MB 의 **55%** 다.
「물리가 모든 면에서 낫다」가 아니라 **보관 비용 ↔ 복구 시간의 교환**이다.

백업 처리량으로 환산하면 팔 B 는 10,244MB / 140s ≈ **73MB/s** 로, 이 볼륨의 상한
(gp3 125MB/s)과 같은 자릿수다. **백업 쪽은 디스크가 지배한다**는 설계 §5 의 전제가 맞았다.

## 2. Q3 — 백업이 서비스를 멎게 하는가

writer 는 초당 5회(`WRITER_GAP_MS=200`)로 쓰면서 정지 구간을 200ms 해상도로 본다.

- 팔 A — **42~126ms.** `--single-transaction` 은 시작 시점에만 짧게 잡고 이후엔 MVCC 로 읽는다
- 팔 B — **244~296ms.** `LOCK INSTANCE FOR BACKUP` 이 있지만 DML 을 막지 않는다
- 팔 C — **2,692ms.** `FLUSH TABLES ... FOR EXPORT` 로 3초를 잠갔고 그대로 잡혔다

**세 팔 모두 `errors=0`** 이다. 쓰기가 실패한 게 아니라 **지연됐다가 통과**했다.

## 3. 🔴 팔 B 의 「복구 9초」는 RTO 가 아니라 하한선이다

**이 절이 이 문서에서 제일 조심해야 할 곳이다.**

`restore_arm_b` 는 ① prepare ② `cp -a` 로 datadir 붓기 ③ 서버 기동 + ready 대기를 다 감싼다
([`../backup-restore-2026-08-13/backup_sweep.sh:162`](../backup-restore-2026-08-13/backup_sweep.sh)).
그런데 로그를 보면 **prepare 만 3초**다(`08:48:24` → `08:48:27`,
[`backup/r2_B_xb.log`](backup/r2_B_xb.log)). 남은 ~6초에 **10.4GB 복사 + 컨테이너 기동 + ready
대기**가 전부 들어갔다.

**물리적으로 불가능하다:**

| | 값 |
|---|---|
| 복사량 | 10,367 MB (읽기 + 쓰기가 **같은 볼륨**) |
| 볼륨 상한 | gp3 200GB · **125 MB/s** · 3,000 IOPS (실측 `describe-volumes`) |
| 필요한 최소 시간 | ≈ 166초 |
| 실측 | 9초 (prepare 3초 포함) |

즉 `cp` 가 **페이지 캐시까지만 쓰고 반환**했다(RAM 15GB > 10.4GB, `cp` 는 fsync 하지 않는다).
읽기 쪽도 방금 만든 백업이라 캐시에 있었다. **팔 A 는 InnoDB 를 거쳐 실제로 내려쓰므로 두 팔이
같은 기준으로 측정되지 않았다.**

→ **「1,294초 vs 9초 = 143배」를 그대로 인용하면 과대다.** 팔 B 값은 **「캐시가 다 받아준
경우의 하한선」** 으로만 쓴다. 판정 방향(물리가 논리보다 빠르다)은 바뀌지 않는다 — 캐시를
빼도 166초 이상 vs 1,294초라 여전히 자릿수가 다르다.

이슈: [#201](https://github.com/Shadowfit/init/issues/201).

## 4. G5 — 「복구되는가」가 닫혔다

```
원본 (행수 체크섬): 100000000 62281922
복구 (행수 체크섬): 100000000 62281922
판정: 일치
```

[`backup/G5_xtrabackup_restore.txt`](backup/G5_xtrabackup_restore.txt).

**G2 가 남긴 단서를 이걸로 닫는다.** 사전 확인에서 XtraBackup 은 `perl binary not found.
Skipping the version check` 를 찍은 채 돌았고(도구 8.0.35 ↔ 서버 8.0.46), 그때 판정은
「붙는다 ≠ 호환이 검증됐다」였다. **1억 행을 복구해서 체크섬이 맞았으므로 이제 「복구된다」다.**

본 측정 9판의 `verify` 칸도 전부 일치다. 형식은 `일치(100003365 ∈ [100002701,100003373])`
— writer 가 계속 쓰는 중이라 **백업 시점의 행수는 구간으로만 정해진다.** 그 구간 안에 들어오면
일치다.

## 5. RPO — binlog 는 어디까지 좁히나

EC2 에서도 게이트를 다시 밟았다(로컬 통과 이력을 재사용하지 않는다).

| | 값 |
|---|---|
| `binlog_format` / `binlog_row_image` | `ROW` / `FULL` |
| `gtid_mode` | **OFF → PITR 은 포지션 기반**(파일명 + 오프셋) |
| `binlog_expire_logs_seconds` | 2,592,000 (30일) = **RPO 상한** |
| **PITR** | 백업 `binlog.000036 @ 532366` → 사고 직전 **20,500행으로 정확히 복원** |

[`backup/G1_binlog.txt`](backup/G1_binlog.txt) · [`backup/G3_pitr.txt`](backup/G3_pitr.txt).

**사고(대량 DELETE)는 재생되지 않았고 그 직전까지만 돌아왔다.** RPO 의 하한은 백업 주기가
아니라 **binlog 가 살아 있는 한 「사고 직전」** 이다 — 단 binlog 가 같은 디스크에 있으면
디스크를 통째로 잃을 때 같이 잃는다(§7).

## 8. 미검증 · 한계

- 🔴 **팔 B 복구 시간(§3)** — 캐시 흡수분이 빠져 있다. 재측정 전까지 배수 인용 금지
- 🔴 **real-JSON 축소 대조 1판이 안 돌았다.** 설계 §9-1 의 확정된 규모는 «더미 1억 행 본 측정
  **+ real-JSON 소규모(~1~2GB) 대조 1판**» 이었는데, rig 에 그 팔이 없다(`backup_sweep.sh` ·
  `run_all.sh` 어디에도 real 무대가 없다). **하필 그 대조가 막으려던 것이 Q2 다** —
  `mysqldump` 는 행을 SELECT 해서 뽑아 off-page 저장을 타므로, 더미 JSON(~115B, 인라인)으로만
  재면 **논리 백업의 불리함이 실제보다 작게 나온다**(인덱스 배수가 더미 660배 ↔ real-JSON
  9,000배로 과소평가됐던 것과 같은 함정). 즉 **§1 의 21분은 real-JSON 에서 더 나빠질 값**이다
- **팔 A 복구는 단일 스레드 재적재**다. MySQL Shell 병렬 덤프(설계 §9-1 ①)는 이번 범위 밖이라
  **「논리 백업의 복구는 21분」이 아니라 「`mysqldump` + `mysql` 재적재는 21분」** 이다
- **binlog 를 별도 볼륨에 두는 구성은 안 봤다.** 지금 구성은 datadir 과 같은 디스크다
- **값 분포 한계** — 무대가 단일 템플릿 복제라 카디널리티가 균일하다. 백업/복구는 전량 처리라
  분포 의존이 적지만, R1 의 0행은 **「구조는 있다」까지만** 말한다
- **`DROP_CACHES=1` 은 판 사이에만** 건다. 판 안에서 생기는 캐시 효과는 그대로다 (§3 이 그 사례)
