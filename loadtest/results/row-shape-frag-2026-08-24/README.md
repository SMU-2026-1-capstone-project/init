# Q1 — 행 모양이 30배 달라도 파편화 계단은 같다 (2026-08-24, 로컬)

[설계 §3 Q1](../../../docs/decisions/row-shape-partition-interaction.md) — *"페이지당 행 수가 두 자릿수 다른데 파편화 계단도 같은가"*.

- rig: [`pose_frag_rig.sh`](./pose_frag_rig.sh) · 로그: [`arm-fifo.log`](./arm-fifo.log) · [`arm-hole.log`](./arm-hole.log)
- 대조: [08-09 판](../delete-fragmentation-2026-08-09/README.md) (`outbox_events` 행 모양)

---

## 0. 한 줄

**바뀌지 않는다.** 페이지당 행이 **148 → 4.4** 로 30배 줄어도 FIFO 는 누적이 없고, 구멍 뚫기는 **계단 한 번 뒤 평탄**이며 그 크기(**+25.7%**)가 08-09 의 **+24%** 와 사실상 같다. **08-09 결론을 `pose_data` 로 인용해도 된다.**

---

## 1. 결과

| | 08-09 (`outbox_events`) | **이 판 (`pose_data` 모양)** |
|---|---|---|
| 페이지당 행 | ≈148 | **≈4.4** |
| **FIFO** | 1,348 **고정**(3회전) | 1,347~1,412 **진동**, 추세 없음 (초기 1,380 → 종료 1,411, **+2.2%**) |
| **구멍 뚫기** | 1,348 → **1,668 계단 한 번**(+24%) 후 평탄 | 1,380 → **1,735 계단 한 번**(**+25.7%**) 후 평탄 |
| OPTIMIZE 대비 (FIFO) | **−11%** (더 조밀) | **−10.2%** (더 조밀) |

### 구멍 팔의 계단 모양

```
사이클  1     2     3     4 …… 24
페이지 1544  1672  1736  1736 …… 1735     ← 3사이클에 올라가고 그 뒤 완전 평탄
```

08-09 이 «계단 한 번 후 평탄» 이라 적은 것과 **모양까지 같다.**

---

## 2. 판정선을 결과에서 유도했다

설계는 *"판정선에 숫자가 없다 — 08-09 산포를 먼저 봐야 하고, 그 전에 임계를 박으면 임의값이 된다"* 로 비워뒀다([[feedback_no_arbitrary_threshold_values]]). 이 판이 그 바닥을 준다:

**FIFO 팔의 진동 폭 = 1,347~1,412 = ±2.3%** — 이 무대의 잡음이다. 구멍 팔의 계단은 **+25.7%** 로 그 **11배**다. 잡음과 구분이 되고도 남는다.

> 🔑 이 유도가 이 판의 부수 산출이다. 「비슷한 비율인가」를 **미리 정한 임계가 아니라 같은 무대의 산포**로 가른다.

## 3. 무대

| | |
|---|---|
| 테이블 | **`pose_frag`** — `pose_data` 스키마 복제(자체 테이블, 실 테이블 안 건드림) |
| JSON | **실 `pose_data` 의 행을 그대로** 가져와 넣는다(길이 2,072 B) |
| 행당 | 3,294~4,245 B · 페이지당 **약 4.4행** |
| 규모 | 6,700행 · 사이클당 840행(12.5%) · 24사이클 = **3회전** |
| 구멍 | 1/8 이 `keep_flag=1` 로 남는다 |

### 🔑 행 수가 아니라 **페이지 수**를 맞췄다

08-09 는 200,000행 → 1,348페이지였다. 같은 **행 수**로 하면 이 행 모양에서는 **4만 페이지**가 되어 무대가 30배 커진다. 질문이 「페이지당 행 수가 다르면 계단이 다른가」이므로 **무대(페이지)를 같게 두고 행 모양만 바꾸는 것**이 맞다 → 6,700행 ≈ 1,380페이지.

---

## 4. rig 이 두 번 틀렸다 — 스모크가 잡았다

1. 🔴 **`ANALYZE TABLE` 을 안 하고 `data_length` 를 읽었다.** InnoDB 는 그 값을 통계에서 가져오므로 갱신 전엔 무의미하다 — 첫 스모크가 **「행당 16 B · 1페이지」** 라는 값을 내고 «성공» 으로 끝났다. 08-09 rig 의 `snapshot()` 은 매번 `ANALYZE` 를 먼저 한다
2. **purge 대기가 없었다.** 지운 행이 안 치워졌으면 점유 페이지가 과대로 잡힌다. 08-09 의 `wait_purge()` 를 같은 자리에 넣었다

> 어제 [`uk-index-bufferpool`](../uk-index-bufferpool-2026-08-23/) 판의 `HAVING` 사고와 **같은 계열**이다 — 지표가 무의미한데 판은 초록으로 끝나는 모양. 본판 전에 스모크를 태워서 잡혔다.

## 5. 🔴 미검증 · 안 한 것

- **FIFO 진동 폭이 08-09(완전 고정)보다 크다**(±2.3%). 페이지당 행이 5개뿐이라 한 페이지의 증감이 비율로 크게 보이는 것으로 **보이지만 안 갈랐다**
- **반복 1판**이다. 팔당 한 번씩이고 위치 균형도 없다([[feedback_measure_design_needs_repeats]])
- **JSON 길이가 사실상 고정**(2,072 B)이다 — 합성 시드라 분포 축을 못 만든다([[project_synthetic_data_distribution_limit]])
- **Q2(파티션 상호작용)는 손도 안 댔다.** 이 판의 `pose_frag` 에는 **파티션이 없다** — 설계가 «본체» 라고 부른 쪽은 그대로 열려 있다
- **구멍 밀도를 1/8 하나만** 봤다. 08-09 는 1%~20% 를 훑어 «밀도 무관» 을 보였는데, 이 행 모양에서도 무관한지는 **안 봤다**
