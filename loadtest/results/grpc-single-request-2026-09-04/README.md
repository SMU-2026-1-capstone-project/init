# gRPC `SavePoseDataBatch` — 무부하(c=1) 단일요청 지연

배경: [#676](https://github.com/Shadowfit/init/issues/676). `slo-baseline.md §4-2`가 gRPC 정책적 실패 게이트를
보류한 이유가 이것이다 — 지금까지 이 RPC의 유일한 실측(`§4-0`, commit-count-2026-08-09)은
**c=100 동시 부하** 조건(p50 429ms · p95 447ms · p99 488~1,047ms)뿐이고, "무부하 단일요청이
얼마나 걸리나"는 이 저장소에 값이 없었다. 그 값을 이 라운드가 채운다.

🔴 **§4-0(c7i.4xlarge, AI:MySQL:Spring=8:4:4)과 인스턴스 크기가 다르다.** vCPU 계정 한도(32,
당시 다른 세션이 동시에 pool-sizing 3대 구성을 띄우고 있어 24 사용 중이었다) 때문에 c7i.4xlarge를
못 띄우고 4vCPU로 축소했다. **이 축소가 결과를 왜곡할 이유는 딱히 없다** — c=1 무부하 조건은
컨테이너가 서로 자원을 다툴 일이 없어서(동시 요청이 없다) CPU 캡 크기 자체보다 "이 박스에 다른
경쟁 프로세스가 없는가(quiet box)"가 더 중요하고, 그 조건은 지켜졌다(전용 신규 인스턴스, 다른
부하 없음). 다만 엄밀하게는 재현 시 c7i.4xlarge로도 한 번 더 확인하는 편이 안전하다.

## 해석

**§4-0의 429~1,047ms는 이 RPC 자체의 비용이 아니라 c=100 동시성이 만든 대기(락 경합·풀 대기 등)였다**
— 무부하 단일요청은 p50 1.91ms, p99 3.78ms로 **c=100 대비 약 110~250배 낮다**. 이 RPC 하나의
순수 처리 비용은 `latency-perception.md §1`의 "즉시감"(30~100ms) 기준에도 여유 있게 들어간다.

이건 [#676](https://github.com/Shadowfit/init/issues/676)이 제기한 우려(*"rep마다 TTS 응답을 막는
동기 호출이 100ms 즉시감 예산을 매번 넘기는 것 아니냐"*)의 **절반**에 답한다 — RPC 자체는 느리지
않다. 답하지 못하는 나머지 절반은 아래.

## 🔴 이 라운드가 안 답하는 것 — 실사용 동시성 하의 대기시간

이 라운드는 **c=1**(요청 하나가 끝나야 다음이 나간다)이라 "동시에 다른 사용자가 rep을 끝내고
있을 때"를 전혀 모사하지 않는다. `pose.py:359`의 이 호출은 **동기 블로킹**이라, 여러 사용자의
rep 완료가 겹치면 그만큼 커넥션 풀·MySQL 락에서 대기가 생길 수 있다 — 그리고 §4-0의 c=100
숫자가 보여주듯 그 대기는 결코 작지 않다.

이 질문에 답하려면 c=100(인위적 최대 동시성, 원래 pool-sizing/처리량 실험용)도 c=1(이 라운드)도
아닌, **가정 P1에서 유도한 도착률**(write_p99·read_p99_ec2가 쓰는 것과 같은 열린 루프 방식,
`docs/decisions/load-test-strategy.md §4.2`)로 "실사용 피크 근처에서 이 동기 호출이 rep→TTS 예산을
얼마나 갉아먹나"를 재는 **별도 실험**이 필요하다. 이번 라운드의 스코프가 아니다 — 필요하면
후속 이슈로 남긴다.
