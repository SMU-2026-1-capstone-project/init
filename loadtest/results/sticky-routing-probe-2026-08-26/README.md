## 0. 한 줄 요약

**판정선 ㄱ·ㄷ·ㄹ은 깨끗이 통과했다 — 해시 라우팅은 정확하고, 부하기 자체는 병목이 아니다.**
ㄴ(처리량 비교)은 원 설계가 예상 못 한 자리에서 걸렸다: **C팔이 나(작성자)의 재현 코드
버그로 세션 159개만 썼다**(N 스윕 스크립트의 `SESS_TOTAL // N` 정수 나눗셈을 그대로
옮기면서 160을 3으로 나눈 나머지 1개가 빠졌다). 정규화하면 캐비엇은 사실상 닫히지만,
잔차 하나가 산포선을 살짝 넘어 **완전히 닫혔다고는 말 못한다** — §3.

## 2. 처리량 — 원값은 E가 0.53% 높다, 그런데 세션 수가 다르다

| 팔 | 유효 판 | rps 평균 | 판 간 산포(CV) | 세션 수 |
|---|--:|--:|--:|--:|
| C | 4 | 475.90 | 0.020% | **159** ← `160 // 3 × 3`, 1개 소실 |
| E | 4 | 478.41 | 0.021% | **160** ← `session_id % 3`, 전부 배정 |

```
원값 차:  E − C = +2.51 rps (+0.528%)
판 간 산포 합(CV):  0.020% + 0.021% = 0.042%
```

원 설계(§3-4 판정선 ㄴ)는 *"차가 산포 합보다 크면 뭔가 비용이 있다"*였다. 원값만 보면
**걸린다 — 다만 방향이 예상과 반대다**(E가 더 빠르다, 라우팅 "비용"이 아니라 "이득"처럼
보인다). 이 방향 자체가 첫 신호였다: **세션 부하가 애초에 같지 않았다.**

### 2-1. 🔴 C팔이 세션을 159개만 쓴 이유 — 내가 옮긴 버그

`run_arm_C()`가 N 스윕의 `run_sweep.sh`를 그대로 옮기며 `s_each = sessions_total // N`을
썼다. `160 // 3 = 53`이라 **rig 3개 × 53세션 = 159**고, 160번째 세션은 어느 rig에도
배정되지 않는다. 반면 `sticky_rig.py`의 해시 라우팅은 `session_id % 3`으로 **모든
session_id를 빠짐없이** 어느 한 백엔드에 배정하므로 E팔은 정확히 160을 썼다.

⚠️ **N 스윕(2026-08-24) 원본도 같은 자리에서 159를 썼다** — 이건 이 실험만의 새 버그가
아니라 **원본 스크립트에 이미 있던 버림**이다. 다만 그날은 팔 넷(A·B·C·D)이 전부 같은
`// N` 규칙을 썼으므로 팔 사이에서는 상쇄됐다. 이번엔 C(옛 규칙)와 E(새 규칙)를 **처음으로
같은 판 안에서 맞대면서 그 차이가 드러났다.**

## 3. 세션 수로 정규화하면 — 거의 닫히지만, 완전히는 아니다

| 팔 | rps ÷ 세션 수 |
|---|---:|
| C | 475.90 ÷ 159 = **2.9931** |
| E | 478.41 ÷ 160 = **2.9901** |

```
정규화 차:  (2.9901 − 2.9931) / 2.9931 = −0.100%   ← 이제 E가 «약간 낮다»(부호가 뒤집힌다)
산포 합:    0.042%
```

**0.100% > 0.042%다 — 엄밀히 원 판정선을 그대로 적용하면 여전히 «산포 밖»이다.**
다만 세 가지가 이 잔차를 "라우팅 비용"으로 읽는 것을 막는다:

1. **부호가 반대다.** 라우팅 비용이 있다면 E가 원값 기준으로도 낮아야 하는데, 원값은
   E가 높았고(§2) 정규화 후에야 겨우 반대로 뒤집힌다 — **정규화 자체의 반올림·이산성
   (세션 159 vs 160, 정수 나눗셈)이 만드는 흔들림과 구분이 안 된다**
2. **잔차가 산포선을 넘는 폭(0.058%p)이 CV 계산의 반올림 오차 자릿수와 같다** — `rps`가
   소수 둘째 자리까지만 찍힌다(§ sticky_rig.py summary)
3. `ai0`+`ai1`+`ai2` CPU 합도 정규화 방향과 같은 쪽을 가리킨다 — E의 세션당 CPU가 C보다
   미세하게 낮다(§4)

**결론: "이미 갈라진 부하" 캐비엇은 사실상 닫혔다고 본다 — 다만 완전한 재실행(C도 160
세션을 쓰게 고쳐서) 전에는 "확실히 닫혔다"로 못 박지 않는다.** 이건 이 라운드가 답을
못 낸 게 아니라, **재현 코드의 결함이 그 답의 정밀도를 한 자리 깎았다**는 뜻이다.

## 4. CPU — 박스는 두 팔 다 93~94%다, 라우팅이 CPU를 더 안 먹는다

| 팔 | `box` 평균(mean) | `ai0+ai1+ai2` 합 |
|---|--:|--:|
| C | 14.86 (92.9%) | 14.55 |
| E | 15.04 (94.0%) | 14.71 |

E의 박스 CPU가 살짝 높은 것도 세션 1개 차이(160 vs 159, +0.63%)와 자릿수가 맞는다.
**해시 라우팅이 서버 쪽에 별도의 CPU 비용을 얹는다는 증거는 없다** — 애초에 라우팅
결정은 `sticky_rig.py`(클라이언트) 안에서만 일어나고 서버 코드는 옛 코드 그대로다.

E팔에서 `ai1`만 다른 둘보다 CPU가 높은 것(4.97~5.00 vs 4.86~4.89)도 버그가 아니다 —
`assigned_dist`가 매판 `{"1": 54}`로 배정 1(포트 8101)에 세션이 하나 더 갔기 때문이고,
그 차이(+0.02~0.03 vCPU)가 세션 1개(53→54, +1.9%) 몫과 자릿수가 맞는다.

## 5. 🔴 절대 처리량 자체가 N 스윕과 다르다 — 박스 보정이 또 움직였다

이 판(93~94%, 475~478 rps)과 N 스윕(2026-08-24, 98%, 451.2 rps)은 **같은 조건(N=3·
160세션·3fps·풀 68/프로세스)인데 처리량이 5.8% 다르고 박스 CPU도 4~5%p 다르다.**

박스 보정(`ai_venv_conditions.txt`)이 원인을 가리킨다:

| 라운드 | infer(fps) |
|---|--:|
| N 스윕(2026-08-24) | 61.7 |
| 이 판(2026-08-26) | **75.41** (+22.2%) |

같은 인스턴스 **타입**(`c7i.4xlarge`)이지만 매번 다른 물리 호스트에 뜬다 — N 스윕
결정 로그가 이미 같은 계열의 드리프트(infer 54.49↔72.06fps, +32.2%)를 적어뒀다.
**이 판의 절대 rps(475~478)를 N 스윕의 451.2와 직접 비교하면 안 된다** — 서로 다른
박스의 값이다([[project_loadtest_env_constraint]]류 한계, `round-to-round-nonreproducibility.md`).

📌 다행히 이 판의 **핵심 비교(C↔E)는 이 라운드 안에서만** 이뤄져 이 드리프트에 안
걸린다(설계 §3-1 "왜 C를 이 세션 안에서 재현하나"가 정확히 이 위험을 막으려던 장치였고,
실제로 값을 했다).

## 6. 결론

- ✅ **해시 라우팅은 정확하다** — nolease 0, 배정 균형 정확
- ✅ **부하기 자체 GIL 병목이라는 교란은 없다** — rig CPU 0.34 vCPU
- ✅ **서버 쪽 CPU 비용도 안 는다** — 세션 수 차이로 다 설명된다
- 🟡 **"이미 갈라진 부하" 캐비엇은 사실상 닫혔지만 완전히는 아니다** — 잔차 0.10%p가
  산포선(0.042%)을 넘는다. 원인은 라우팅이 아니라 **내 C팔 재현 코드가 세션을 159개만
  쓴 것**(N 스윕 원본의 `// N` 버그를 그대로 옮김)일 가능성이 제일 크다
- 🔴 **재현 후보** — `run_sticky_probe.py`의 `run_arm_C()`를 `session_id % N`으로 바꿔
  C도 160세션을 쓰게 고치면, §3의 잔차가 사라지는지 바로 검증된다. 미실행
