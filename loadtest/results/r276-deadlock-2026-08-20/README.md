## 0. 한 줄

**세 조건이 «동시에» 성립할 때만 난다** — ① `uk_pose_event` 가 있고 ② 서로 **다른** 키가
③ **같은 파티션**에 동시에 들어갈 때. 셋 중 하나만 빠져도 **0%** 다.

> 🔴 **정정 (2026-08-23) — ②가 틀렸다.** 조건은 «서로 다른 **키**» 가 아니라 «서로 다른 세션의
> **중복**» 이다. [AWS 라운드](../r276-newkeys-aws-2026-08-23/README.md)가 이 문서에 없던 팔
> (`new_keys_only` = uk 있음 + 중복 0 + 같은 파티션)을 돌려 **960시도에 0** 을 얻었고, 그 팔은
> 같은 파티션에 **40배 더 많은 행**(8,000 대 200)을 넣고도 0 이다(대조군은 같은 라운드에서 42.8%).
>
> **왜 이렇게 적혔나**: 아래 §1 의 `same_partition` 팔은 «신규 키만» 팔이 **아니다** — 최종 행수
> 200(= 8워커 × 25행)이 그 증거다. 워커당 40문이 글자 그대로 같은 25행이라 2문째부터 전부
> 중복이고, **워커끼리만** 키가 다르다. 그 «워커끼리 다르다» 를 «다른 키가 다툰다» 로 적었다.
> [이슈 08-17 코멘트](https://github.com/Shadowfit/init/issues/276)의 서술(«다른 세션의 중복»)이
> 맞았고, 이 문서가 그것을 넓게 다시 쓴 것이 오류다.
>
> ①·③ 과 §2-ㅁ(다투는 자리 = `PRIMARY` supremum)은 **그대로 유효하다.** 실사용 함의도 바뀐다 —
> **정상 트래픽은 이 데드락을 안 만들고**, 열리는 것은 재전송이 원본과 겹치는 순간이다.

🔴 **다투는 자리는 `PRIMARY` 의 supremum 이고, 거기에 X 락을 쥐게 만드는 것이 `uk_pose_event` 다**
— 잠금 원문으로 확인했다(§2-ㅁ). 이슈 제목은 자리를 맞게 짚었다. 그리고 🔴 **이슈가 기대한 완화는 성립하지 않는다** —
파티션이 월 단위라 실사용의 동시 사용자는 **전부 같은 파티션**에 들어간다(§2-ㄴ).

## 2. 판정

### ㄱ. 「중복이 동시에」가 조건인가 → ❌ **중복만으로는 안 난다**

`single_session` 은 **8워커가 100% 중복을 때린다**(최종 행수 25 = 워커 하나 몫). 이슈의 서술대로면
여기가 가장 심해야 하는데 **960시도에 데드락 0** 이다.

중복은 `ON DUPLICATE KEY UPDATE` 로 **접힌다** — 새 행이 안 들어가니 삽입 자리를 다툴 일이 없다.
이슈 본문의 *"c=1 에서는 조용히 삼킨다"* 가 c=8 에서도 그대로다. **동시성이 아니라 «새 키인가» 가 가른다.**

### ㄴ. 파티션이 갈리면 줄어드는가 → ✅ **사라진다. 🔴 그런데 실사용은 안 갈린다**

`diff_partition` 은 960시도에 **0** 이다. 파티션마다 인덱스 트리가 따로라, 다툴 자리 자체가 없다.
**줄어드는 정도가 아니라 사라진다.**

🔴 **그런데 이 팔은 실사용 조건이 아니다.** rig 주석이 *"실사용은 `created_at` = 세션 시작 시각이라
날짜별로 흩어진다"* 라고 적어둔 것은 **틀렸다** — 흩어지는 것은 **날짜**이고, 파티션은
**월 단위**(`p2026_01` … `p2026_12`)다. **동시에 운동 중인 사람은 정의상 같은 순간에 있으니
같은 달에 있고, 따라서 같은 파티션에 있다.**

즉 **실사용 조건은 `diff_partition` 이 아니라 `same_partition` 팔이다.** 「실사용에선 흩어져서
덜하겠지」라는 완화 기대는 **이 판이 지운다**. `diff_partition` 이 답한 것은
「기제가 파티션 지역성이다」이지 「실사용은 안전하다」가 아니다.

### ㄷ. 시도당 확률 p → **0.3750** (§3 에서 재시도 횟수를 유도한다)

### ㄹ. 🔴 멱등 키가 원인인가 → ✅ **필요조건이다**

`no_uk` 는 `same_partition` 과 **페이로드가 글자 그대로 같고** `uk_pose_event` 만 없다.
결과는 **960시도에 0** 이다.

**이 0 이 강한 이유는 일의 양에 있다.** 키가 없으면 중복이 안 걸려 행이 실제로 쌓인다 —
`no_uk` 는 **8,000행**을 넣었고 `same_partition` 은 **200행**이다. 즉 같은 파티션 끝에
**40배 더 많이** 밀어넣고도 데드락이 0 이다.

**이 팔이 반증하는 것**은 *"삽입이 인덱스 끝에 몰리는 것만으로 난다"* 쪽이다. 그게 전부라면
삽입이 40배인 `no_uk` 가 **더** 심했어야 한다. 키가 있어야 난다.

⚠️ **단 「그러니 다투는 자리도 유니크 키다」로 이어가면 틀린다.** 이 README 가 한 번 그렇게
적었고(이슈 코멘트에도 나갔다), 잠금 원문이 그것을 지웠다 — §2-ㅁ. **필요조건과 다투는 자리는
같은 것이 아니다.**

### ㅁ. 🔴 그럼 다투는 자리는 어디인가 → **`PRIMARY` 의 supremum 이다**

[`innodb-status.md`](./innodb-status.md) 에 `LATEST DETECTED DEADLOCK` 원문이 있다.
두 트랜잭션이 **대칭**이다:

```
*** (1) HOLDS THE LOCK(S):
RECORD LOCKS ... index PRIMARY of table `shadowfit`.`pose_data_r276` /* Partition `p2026_05` */
  lock_mode X          ← heap no 1 = supremum
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index PRIMARY ... /* Partition `p2026_05` */
  lock_mode X insert intention waiting     ← 같은 supremum
```

`uk_pose_event` 는 **잠금 목록에 한 줄도 안 나온다.** 둘 다 같은 파티션(`p2026_05`) `PRIMARY` 의
supremum 에 X 를 쥔 채, 서로의 **insert intention** 을 기다린다 — insert intention 은 다른
트랜잭션의 X 와 충돌하므로 그대로 순환이다.

**두 사실을 같이 놓아야 그림이 맞는다:**

| 실측 | 말하는 것 |
|---|---|
| `no_uk` 팔 0% (삽입 40배) | 키가 **없으면** 그 X 락이 안 생긴다 → **키는 필요조건** |
| 잠금 원문이 `index PRIMARY` supremum | 다투는 **자리**는 유니크 키가 아니다 |

즉 **`uk_pose_event` 의 중복 검사가 `PRIMARY` supremum 에 X 락을 쥐게 만들고, 그 X 락이 서로의
삽입을 막는다.** 키가 없으면 순수 삽입이라 insert intention 끼리는 서로 충돌하지 않아 0% 다.

> ⚠️ **여기까지가 실측이다.** 「중복 검사의 어느 단계가 그 X 를 잡는가」(배치 안 앞선 행의 중복
> 처리인지, 검사 자체인지)는 **원문이 말해주지 않는다** — 잠금 목록은 결과만 보여준다.
> 그리고 이 한 쌍은 **데드락 한 건**의 원문이다(그 판에서 여러 건이 났다).

## 3. 재시도 횟수 — 임의값을 넣지 않기 위한 유도

p = 0.3750(같은 파티션 · 키 있음 · 이 부하). **시도가 독립이라는 가정** 아래 n회 재시도 후
잔여 실패율은 p^(n+1):

| 재시도 n | 총 시도 | 잔여 실패율 |
|---|---|---|
| 0 (지금) | 1 | **37.5%** |
| 1 | 2 | 14.1% |
| 2 | 3 | 5.3% |
| 3 | 4 | 2.0% |
| 4 | 5 | 0.74% |
| 5 | 6 | 0.28% |

⚠️ **이 표는 유도이지 약속이 아니다.** 어디서 끊을지는 SLO 가 정할 일이고, 여기엔 그 선이 없다.

🔶 그리고 **독립 가정이 양쪽으로 틀렸을 수 있다.** 재시도는 경합을 *더* 만들고, 첫 시도가
데드락이었다는 사실 자체가 「그 순간 동시 삽입이 몰려 있다」는 정보다. 반대로 **재시도의 두 번째
시도는 원본이 이미 들어가 있으면 중복이 되어 §2-ㄱ 의 «접히는» 경로로 간다** — 그쪽은 0% 였다.
두 힘이 반대 방향이고 **어느 쪽이 이기는지는 안 쟀다.**

## 4. 🔴 미검증 · 이 판에서 말하면 안 되는 것

1. **절대 비율을 일반화하지 말 것.** 로컬 2물리코어에 MySQL·부하가 동거하고, payload 를
   작은 JSON 으로 줄였다(실제 ~2KB). 37.5% 와 34.8% 가 겹친 것은 **우연일 수 있다** —
   두 판은 박스·부하기·경로(gRPC↔직접 SQL)가 전부 다르다. 팔 간 상대비교만 신뢰할 것.
2. **`no_uk` 에는 교락이 하나 딸려 있다** — 키가 없으면 행이 쌓여 삽입 일이 40배다. 그래서 이 팔의
   판정은 **한 방향으로만** 쓴다: 「0 이 나왔으니 키가 필요조건」은 강하고(일이 더 많은데도 0),
   「키가 있으면 항상 난다」는 이 팔이 말하지 않는다.
3. **잠금 «자리» 는 읽었고(§2-ㅁ), «어느 단계가 잡는가» 는 아직이다.** 원문은 결과(누가 무엇을
   쥐고 무엇을 기다리는가)만 보여준다 — 중복 검사의 어느 지점이 `PRIMARY` supremum 에 X 를
   잡는지는 안 나온다. 그리고 읽은 것은 **데드락 한 쌍**이다(같은 판에서 여러 건이 났다).
4. **배치 안 행 순서 고정(이슈 고치는 방향 2)은 안 쟀다.** 이 rig 은 모든 워커가 같은 순서로 넣는데도
   37.5% 가 났다 — 🔶 「순서를 고정하면 준다」에 **불리한 정황**이지만 직접 반증은 아니다.
5. **`INSERT IGNORE` 대안(고치는 방향 3)도 안 쟀다.**
6. **재시도 간격의 효과는 안 쟀다** — 이 rig 은 간격 0 이다.
7. **워커 수 스윕이 없다.** p 는 8워커에서의 값이다.
