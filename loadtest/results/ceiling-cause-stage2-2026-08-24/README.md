### 2-1. 🟢 프로브는 공짜다 (F↔C)

`263.7 ↔ 266.0` = **−0.86%**, C 팔 자신의 산포(3.09%) **안**이다. CPU 도 9.20↔9.30.
🔑 **C 팔이 없었으면 F 의 GIL 값을 못 믿는다** — 초당 1,000번 GIL 을 집는 관측이
자기가 만든 값을 보고 있을 수 있어서다. 그 가능성이 닫혔다.

### 2-2. 🔴 Z 팔은 이 표에서 «천장» 을 말하지 않는다

서버가 부하를 전부 소화했을 뿐 **포화한 적이 없다.** 설계 §8-3 이 이 칸을 실행 전에
「판정 보류」로 박아뒀고, 정확히 거기 걸렸다. 천장은 §4 의 스윕이 따로 찾았다.

## 3. 🔑 답 ① — GIL 총 점유율 `rho` = **0.939**

### 3-1. 왜 이 값이 필요했나

`main` 스레드 CPU 는 **루프 몫만** 준다. 워커의 파이썬 몫을 못 읽어서 「GIL 총 점유가
1코어 상한에 붙었나」에 답을 못 했다. 성립하는 계산은 이것뿐이다:

```
P(대기 ≈ 바닥) = P(깰 때 GIL 이 놀고 있었다) = 1 − rho
```

**보유 구간 길이와 무관하게** 성립하고, **모든 스레드**의 점유를 포함한다.

⚠️ **평균 기반 모델은 먼저 접었다.** 「대기 ~ uniform(0, 5ms)」로 `rho = mean/2.5` 를 쓰면
F 는 0.61 로 그럴듯한데 **Z 가 0.12** 로 나와 `main` 하한(0.38)과 모순된다. 요청당 main 이
0.78ms 라 5ms 양자에 닿을 일이 없기 때문이다 — **짧은 파이썬 구간은 선점되기 전에 스스로
GIL 을 놓는다.** 🔑 **포화를 못 본 Z 팔이 모델을 하나 깎았다.**

### 3-2. 값

| 팔 | 바닥 근처(≤0.15ms) | 전체 | **`rho`** |
|---|--:|--:|--:|
| **F** | 2,211 | 36,540 | **0.939** |
| **Z** | 42,728 | 67,099 | 0.363 |

🔴 **이 `rho` 는 하한이다** — 오래 기다린 표본은 그만큼 표본을 적게 낳으므로(늦게 깨면
그 창의 표본 수가 준다) 낮게 나온다. **높으면 강한 증거, 낮으면 약한 증거.**
0.939 는 실행 전 판정선 `rho ≳ 0.9` 를 **경계가 아니라 확실히** 넘는다.

### 3-3. 분포 — 꼬리가 한 양자에 붙는다

| 구간 | 바닥 p50 | 부하 p50 | 부하 p99 | 부하 max |
|---|--:|--:|--:|--:|
| **F** | 0.077 ms | **1.172 ms** | **5.62 ms** | 93.4 ms |
| **Z** | 0.077 ms | **0.083 ms** | 2.93 ms | 61.7 ms |

- **F 의 p99 = 5.62ms 는 정확히 한 GIL 양자**(기본 `switch interval` 5ms)다
- 🔑 **Z 의 p50(0.083)이 무부하 바닥(0.077)과 같다** — **계산을 빼면 중앙값에서 경합이
  사라진다.** F 의 1.17ms 가 «계산 경로가 GIL 을 쥐어서» 라는 직접 대조다
- ⚠️ **max 93ms(≈19 양자)는 «한 양자를 기다린 것» 이 아니다** — 여러 대기자 뒤에 줄 선 것이라
  따로 읽어야 한다

## 4. 🔑 답 ② — 순수 파이썬 경로가 **1.04 vCPU** 에서 막힌다

널 핸들러는 유입 상한을 우회하므로 fps 를 올릴 수 있다.

| 제시 | 실측 rps | `cpu.ai` | `cpu.rig` | 클라 p50 |
|--:|--:|--:|--:|--:|
| 960 | 959.1 | 0.87 | 0.48 | 38.6 ms |
| 1,920 | **1,165.8** | **1.04** | 0.55 | 131.8 ms |
| 3,840 | **1,158.1** | **1.04** | 0.55 | 132.8 ms |

제시를 2배 더 올려도 **rps 도 CPU 도 안 움직인다.** 부하기는 0.55 vCPU 라 한계가 아니다.

🔑 **MediaPipe 를 통째로 뺐는데 16 vCPU 박스에서 1코어를 못 넘는다.** 이것이 GIL 벽 자체다.


검산 — 요청당 GIL 구간:

| | rps | 파이썬 CPU | 요청당 |
|---|--:|--:|--:|
| 현행(F) | 263.7 | ~1 코어 | **3.8 ms** |
| 널(Z) | 1,160 | 1.04 코어 | **0.86 ms** |

§10-1 이 어림한 **«프레임당 ~2.8ms»** 와 같은 자리다. 차 ~2.9ms 가 디코드·분석·직렬화 몫이다.
**프로세스를 쪼개면 1.30배가 나온 이유가 GIL 이 프로세스당 하나라서**로 설명된다.

요청당 비용(팔 대조):

```
cpu.ai / rps   F 34.9 mvCPU   Z 0.95 mvCPU   ← 널 경로는 현행의 2.7%
main   / rps   F 1.89 ms      Z 0.78 ms      ← 루프가 요청당 1.11ms 를 더 쓴다
```

⚠️ **그 1.11ms 는 응답 직렬화 «단독» 이 아니다** — Z 는 디코드·분석·콜백까지 같이 빠졌다.
[`post_loop` 판](../post-loop-breakdown-2026-08-23/README.md)의 −52% 와 같은 것을 다른 각도에서 짚은 것으로 읽되,
한 값에 여럿이 섞여 있다.

## 6. 이 판이 확정한 것과 안 한 것

- ✅ **원인은 GIL** — `rho` ≥0.939 · 순수 파이썬 경로 1코어 천장, **독립된 두 갈래가 일치**
- ✅ **§10-1 의 산술이 맞았다** — `main` 0.50 은 «하한» 이고 총량은 1코어에 붙는다
- ✅ **프로브는 관측 비용이 측정 한계 아래**(F↔C −0.86%, 산포 안)
- 🔴 **「몇 개로 쪼개나」는 안 답했다** — 근거는 1.30배 하나뿐이다. **다음 판**
- 🔴 **Z 팔은 격자에서 천장을 못 봤다** — 제시 부하에 막혔다(§2-2). 스윕이 따로 답했다
- 🔴 **`rho` 는 팔당 1판** — 판 간 산포를 모른다. 0.939 가 판정선에서 멀어 결론은 서지만,
  **걸치는 값이었으면 판정 보류로 갔어야 한다**

## 7. 정직하게 비어 있는 것

- **`rho` 의 판 간 산포를 모른다.** 분포 측정이라 1판으로 갔고, 그래서 **「0.939 ± ?」를 못 쓴다**
- **워커의 파이썬 몫을 «직접» 은 못 쟀다.** `rho` 는 총량만 주고 스레드별로 안 쪼갠다 —
  `workers` 8.57 vCPU 중 얼마가 파이썬인지는 여전히 미측정
- **박스 보정에 비교 대상이 없다.** 이 박스는 `cpu 17,376,033 iter/s` · `infer 54.49 fps`
  (python 3.12.13)로 기록됐지만, **어제 박스는 보정을 안 걷었다** — 같은 조건에서
  **276.9 ↔ 354.5 rps(−22%)** 인 이유를 아직 못 가른다([#498](https://github.com/Shadowfit/init/issues/498))
- **판마다 uvicorn 을 새로 띄운다** → 검출기 풀이 매 판 차게 시작한다. 팔에는 공통이라
  판정엔 안 얹히지만 **다른 라운드의 rps 와는 눈금이 다르다**(§9-4 가 −24% 로 실측)
- **`switch interval` 을 안 흔들었다** — 이 판은 기본값(5ms) 하나만 봤다
