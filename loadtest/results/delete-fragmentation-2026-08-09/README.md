# 소량 DELETE 반복의 파편화 누적 측정 — 2026-08-09

대상: [`docs/decisions/outbox-reliable-messaging.md`](../../../docs/decisions/outbox-reliable-messaging.md) §4-1-2 가
"(a) 주기 DELETE 로 시작" 을 채택하면서 **"소량 반복 DELETE 의 파편화 누적은 미검증"** 으로 남겨둔 항목.

스크립트: [`../../measure_delete_fragmentation.sh`](../../measure_delete_fragmentation.sh) · 로그: [`S2.log`](S2.log)

---

## 0. 한 줄 요약

**소량 DELETE 반복은 파편화를 «무한 누적» 시키지 않는다 — 대신 한 번의 계단이 있다.**

| 삭제 모양 | 점유 페이지 | 재구축본(1,507) 대비 |
|---|---|---|
| **FIFO** (오래된 것부터 통째로) | 1,348 에서 **3회전 내내 고정** | **−11%** (더 조밀하다) |
| **구멍 뚫기** (살아남는 행이 섞임) | 1,348 → **1,668 계단 한 번**, 이후 평탄 | +11% |

그리고 **그 계단은 구멍 밀도와 무관하다** — FAILED 비율을 1% → 20% 로 **20배** 올려도 같은 1,668 이다.
즉 대가는 «구멍이 있는가/없는가» 로 한 번 치르고 끝나지, 구멍이 늘수록 커지지 않는다.

다만 이 결론에는 **범위 제한(§5)**, **실험 설계 오류 1건(§4)**, **내 1차 판단 정정 1건(§1-1)** 이 붙는다.

## 1. 대상 테이블 — 두 테이블 다 해당된다 (내 1차 판단을 정정)

### 1-1. 🔴 처음에 «pose_data 는 해당 없음» 이라고 적었고, 그게 틀렸다

이 항목은 문서·메모리 4곳에 `pose_data` 로 적혀 있다. 처음엔 **"`pose_data` 는 이미 RANGE 파티션이라
(`V1__baseline.sql:209`) TTL 이 `DROP PARTITION` 이고, 소량 DELETE 로 지울 일이 없다"** 고 판단해
대상에서 뺐다. **파티션은 TTL 축을 닫았을 뿐이고, 소량 DELETE 축은 그대로 열려 있다.**

코드에 소량 반복 DELETE 경로가 셋 있다:

| 경로 | 위치 | 규모 |
|---|---|---|
| 사용자의 세션 삭제 | `SessionService.java:404` → `deleteBySessionIdIn` | **세션 1건 ~750행** (`:392` 주석) |
| 회원 탈퇴 | `MemberService` → `PoseDataCleanupService.java:35` | 회원의 전 세션 |
| 고아 행 sweep | `PoseDataOrphanMonitor.java:28` | **아직 세기만 한다** |

그리고 셋째가 결정적이다 — `PoseDataOrphanMonitor.java:28-29` 가 이렇게 적어뒀다:

> *"DELETE 의 파편화가 이 프로젝트에서 미검증이다. 그래서 **고치기 전에 세는 것**이 먼저다.
> 이 클래스가 sweep 으로 승격되면 같은 쿼리에 `DELETE` 만 붙이면 된다."*

**즉 고아 행 sweep 승격이 바로 이 미검증 항목에 막혀 있다.** 잴 것이 없기는커녕, 이 실험을
기다리고 있던 코드가 있었다.

### 1-2. 메모리의 전제 한 줄은 실제로 틀렸다

메모리 `project_pending_delete_fragmentation_experiment` 는 시나리오를
*"`pose_data` **세션 종료 시** 750행 정도의 소량 DELETE"* 로 적었다.
**다운샘플은 저장 «전» 에 걸린다**(`PoseDataService.java:78` — `downsample()` 후 `batchUpdate`).
줄어든 행은 애초에 INSERT 되지 않으므로 삭제되지도 않는다.

다만 **«~750행» 이라는 숫자 자체는 맞다** — 그 규모의 DELETE 는 다운샘플이 아니라
**사용자의 세션 삭제**(`SessionService.java:392,404`)에서 나온다. 행 수는 맞고 메커니즘이 틀린 것이다.

### 1-3. 그런데 측정은 `outbox_events` 모양으로 했다

`outbox_events` 는 파티션이 없고 §4-1-2 가 "(a) 주기 DELETE 로 시작" 을 **결정으로 채택**해둔 상태라,
이 실험이 직접 걸리는 자리다. 그래서 행 모양은 `outbox_events` 를 복제해 썼다.

**`pose_data` 쪽으로 어디까지 옮겨 읽을 수 있는가**는 §5-1 에 따로 적는다 — 삭제 «모양» 이 다르다.

## 2. 판정 기준 (측정 전에 고정)

| 관측 | 판정 |
|---|---|
| 점유 페이지가 초기 안정화 후 더 자라지 않음 | 누적 없음 → "(a) 주기 DELETE" 방어됨 |
| 사이클에 대해 **단조 증가** | 누적 있음 → (b) 파티션 에스컬레이션 근거 |

**숫자 임계값은 두지 않았다.** 이 프로젝트에 이 지표의 baseline 이 없어서 임계를 만들면 근거 없는 약속이 된다.
판정은 «추세» 로만 한다.

### 무엇을 «파편화» 로 볼 것인가

DELETE 후 `.ibd` 가 안 줄어드는 것은 파편화가 아니라 InnoDB 의 정상 동작이다. 비워진 페이지는 free list 로
가고 이후 INSERT 가 재사용한다. 따라서 판정은 "파일이 줄어드는가" 가 아니라 **"비워진 공간이 재사용되는가"** 다.

## 3. 결과

### 3-1. S1 «실제 규모» — 이 규모에선 잴 수가 없다

DAU 1,000 · outbox 는 세션당 1행 · `SENT` 7일 보존 → 정상상태 ~7,000행, 사이클당 ~1,000행, 30사이클.

| | 값 |
|---|---|
| 실데이터 | 클러스터 1.52MB + 인덱스 0.25MB ≈ **1.8MB** |
| `.ibd` 파일 | **7MB** — 4배가 InnoDB 초기 할당 |
| 30사이클 후 파일 | 9MB → 9MB (변화 없음) |

테이블 전체가 **~100페이지**라 익스텐트(1MB) 아래로는 신호가 안 잡힌다.
이건 «파편화가 없다» 가 아니라 **«이 규모에선 파편화가 문제될 크기 자체가 아니다»** 이고,
그래서 메커니즘 유무는 S2 로 따로 봤다.

### 3-2. S2 «메커니즘» — 200,000행 고정, 25,000행씩 24사이클 (전체 3회전)

| 사이클 | 행수 | 클러스터 페이지 | 바이트/행 | 파일MB |
|---|---|---|---|---|
| 적재후 | 200,000 | 1,315 | 107.7 | 36 |
| 1 | 200,000 | **1,348** | 110.4 | 40 |
| 2 · 3 · 4 · 8 · 12 · 16 | 200,000 | **1,348** | 110.4 | 44 |
| 20 | 200,000 | 1,412 | 115.7 | 44 |
| 24 | 200,000 | **1,348** | 110.4 | 44 |
| *(참고)* OPTIMIZE 후 | 200,000 | *1,507* | *123.5* | *36* |

**첫 사이클에 +2.5%(1,315→1,348) 한 번 오르고, 이후 23사이클 완전 평탄.** → **누적 없음.**

⚠️ **사이클 20 의 1,412 는 추세가 아니다.** 다음 측정(24)에서 1,348 로 돌아왔다.
`STATS_SAMPLE_PAGES=200` 추정치의 노이즈이거나 purge 타이밍이며, **이 한 점을 근거로 쓰면 안 된다.**

### 3-3. S3 «구멍 뚫기» — 삭제 대상이 `WHERE status='SENT'` 뿐, FAILED 는 남는다

S2 와 같은 규모(200,000행 고정 · 25,000행/사이클 · 16사이클 = 2회전)에서 삭제만 바꿨다.
FAILED 비율을 **1% / 5% / 20%** 세 판으로 쓸어, 값 하나가 아니라 «구멍 밀도에 대한 반응» 을 봤다.

| 사이클 | S2 (구멍 0%) | 1% | 5% | 20% |
|---|---|---|---|---|
| 적재후 | 1,315 | 1,315 | 1,315 | 1,315 |
| 1 ~ 8 | 1,348 | 1,348 | 1,348 | 1,348 |
| 12 | 1,348 | **1,668** | **1,668** | **1,668** |
| 16 | 1,348 | 1,540 | 1,668 | **1,667** |
| *(참고)* OPTIMIZE | *1,507* | *1,507* | *1,507* | *1,507* |

**① 구멍이 있으면 계단이 한 번 생긴다.** 1,348 → 1,668 (**+24%**). S2 에서는 이 계단이 없었다.

**② 그 계단은 구멍 밀도와 무관하다.** 16사이클 시점의 FAILED 행 수는
1% 판 4,000행 vs 20% 판 **80,000행(전체의 40%)** 로 20배 차이인데, 페이지는 1,540 vs 1,667 —
익스텐트 2개 차이로 **분해능 근처**다(아래 ③). InnoDB 가 페이지를 병합 임계까지 눌러 담고 나면
그 아래로는 구멍이 더 많아도 달라질 것이 없는 것으로 보인다.

**③ ⚠️ 이 지표는 익스텐트 단위로 양자화돼 있다.** 관측값이 1315 · 1348 · 1412 · 1540 · 1668 인데
차이가 **64 / 128 페이지 = 정확히 1MB / 2MB 익스텐트**다. 분해능이 64페이지(≈1,348 의 4.7%)이므로
**이 폭 안의 오르내림을 추세로 읽으면 안 된다.** 1% 판의 1,668 → 1,540 하강도 익스텐트 2개다.

**④ 계단 이후 더 쌓이지 않는다.** 12 → 16 사이클 평탄. 최악값 1,668 도 재구축본(1,507) 대비 **+11%** 로 묶여 있다.

## 4. 🔴 설계 오류 — OPTIMIZE 를 «하한» 으로 둔 것이 틀렸다

처음 설계는 `OPTIMIZE TABLE` 후 크기를 «같은 행 수의 이상적 하한» 으로 놓고
`사이클후 / 하한` 을 **파편화 배수**로 출력했다. 실측이 이걸 뒤집었다.

| | 클러스터 페이지 |
|---|---|
| 24사이클 후 | 1,348 |
| **OPTIMIZE 후** | **1,507 (+12%)** |

**재구축한 쪽이 더 크다.** AUTO_INCREMENT 순차 삽입은 리프 페이지를 거의 꽉 채우는 반면,
InnoDB 의 정렬 인덱스 재구축(`OPTIMIZE` = `ALTER TABLE … FORCE`)은 페이지마다 여유를 남긴다.
즉 **이 워크로드에서 OPTIMIZE 는 «조밀하게 다시 담기» 가 아니다.**

그래서 스크립트가 출력하던 **「파편화 배수 0.89x」는 해석 불가 값**이다 — "하한보다 좋다" 가 아니다.
배수 출력을 걷어내고 OPTIMIZE 는 «재구축하면 어떻게 되는가» 참고값으로만 남겼다.

> 부수 확인: 파일 크기와 페이지 수가 **반대 방향으로 움직였다**(OPTIMIZE 후 파일 44→36MB, 페이지 1348→1507).
> `file_size` 를 주 지표에서 뺀 판단이 이걸로 뒷받침된다.

### 4-1. 1차 실행에서 잡은 계측 결함 2건

| 결함 | 증상 | 조치 |
|---|---|---|
| `wait_purge` 가 절대 임계(`≤5`) | 이 서버는 idle 에서도 History list length 가 6~12 → 사이클마다 60초 헛돎(11분 실행시간의 전부) | 시작 시점 «바닥값» 을 재두고 거기로 복귀하는지로 판정, 상한 20초 + 타임아웃 시 **경고 출력** |
| `STATS_SAMPLE_PAGES` 기본값 20 | ~100페이지 테이블에서 «OPTIMIZE 후 페이지가 줄어든» 앞뒤 안 맞는 값 | 실험 테이블에 `STATS_SAMPLE_PAGES=200` |

## 5. ⚠️ 이 결론이 덮지 못하는 것

### 5-1. 삭제 «모양» 이 두 가지고, S2 는 그중 하나만 쟀다

| | 모양 | 해당 |
|---|---|---|
| **FIFO** — 가장 오래된 N행을 통째로 | S2 가 잰 것 | `outbox_events` 의 `SENT` 정리 (거의) |
| **구멍 뚫기** — 살아남는 행을 사이사이 남기고 | **S3** (§3-3) | `outbox_events` 의 `FAILED` 90일 보존이 섞인 경우 · **`pose_data` 의 세션 단위 삭제** |

`pose_data` 가 구멍 뚫기인 이유: 세션 하나의 행들은 동시에 진행되는 다른 세션들과 섞여 INSERT 되므로
id 상 연속이 아니다. 그걸 `WHERE session_id IN (…)` 로 통째로 지우면 흩어진 구멍이 된다.
**즉 `pose_data` 에 옮겨 읽을 수 있는 것은 S2 가 아니라 S3 다.**

### 5-2. S3 로도 안 닫히는 것

- **S3 은 2회전(16사이클)까지만 봤다.** S2 는 3회전(24사이클)에서 평탄을 확인했지만 S3 의 평탄 구간은
  12·16 두 점뿐이다. "계단이 한 번뿐" 은 이 두 점에 기대고 있다.
- **계단이 언제 생겼는지 모른다.** 측정점이 4사이클 간격이라 9~12 사이라는 것까지만 안다.
- **행 크기가 다르다.** 측정은 `outbox_events` 모양(≈108 B/행)으로 했는데 `pose_data` 는
  `joint_coordinates` JSON 이 들어가 훨씬 크다. 페이지당 행 수가 달라지면 구멍 하나가 붙잡는
  공간의 비중도 달라진다 — **`pose_data` 행 모양으로는 재지 않았다.**
- **파티션이 섞인다.** `pose_data` 의 DELETE 는 살아있는 파티션 안에서 일어나고, 그 파티션은
  나중에 통째로 DROP 된다. 즉 파편화가 쌓여도 **수명 상한이 파티션 주기**다 — 무한 누적이 아니다.
  이 상호작용은 측정하지 않았다.

### 그 외 한계

- **합성 데이터**라 payload 길이가 균일하다. 다만 실제 outbox 도 payload 가 `{"sessionId": N}` 한 종류라
  이 축에서는 합성 한계가 실물과 거의 같다 — 단 `correlation_id` 는 실제로 NULL 이 아닐 수 있고 여기선 전부 NULL 이다.
- **시간은 재지 않았다.** 2물리코어에 MySQL 이 다른 컨테이너와 동거하므로 무의미하다. 크기(페이지)만 봤다 —
  이 지표는 CPU 경합의 영향을 받지 않는다.
- S2 의 200,000행은 **실제 규모가 아니다**(실제는 ~7,000행). 메커니즘을 보기 위해 키운 값이다.

## 6. 이 결과가 문서에 미치는 것

`outbox-reliable-messaging.md:251` 은 *"'DELETE 로 충분하다' 고 단정해 쓰지 않는다"* 로 적혀 있다.
이 실험은 그 문장을 **일부만** 풀어준다.

| | 이전 | 이후 |
|---|---|---|
| FIFO 소량 DELETE 의 파편화 누적 | 미검증 | **측정됨 — 누적 없음**, 재구축본보다 11% 조밀 (§3-2) |
| `FAILED` 보존이 섞인 구멍 뚫기 | 미검증 | **측정됨 — 계단 +24% 한 번, 이후 평탄** (§3-3) |
| 구멍 밀도가 올라가면 악화되는가 | 미검증 | **측정됨 — 20배 올려도 동일** (§3-3 ②) |
| 실제 규모(~7,000행)에서의 위험 | 미검증 | **잴 수 있는 크기가 아님** (§3-1) |
| `pose_data` 행 모양(큰 JSON)에서도 같은가 | 미검증 | **여전히 미검증** (§5-2) |
| 파티션 DROP 과 섞였을 때 | 미검증 | **여전히 미검증** (§5-2) |

**"DELETE 로 시작" 은 방어된다. 다만 «파편화가 아예 없다» 가 아니라 «한 번 계단을 밟고 거기서 멈춘다» 이고,
그 계단 폭(+24%)은 재구축본 대비 +11% 안에 있다.**

재현:

```bash
bash loadtest/measure_delete_fragmentation.sh S1        # 실제 규모
bash loadtest/measure_delete_fragmentation.sh S2        # FIFO 메커니즘 (~12분)
bash loadtest/measure_delete_fragmentation.sh S3 100    # 구멍 1%  (~8분)
bash loadtest/measure_delete_fragmentation.sh S3 20     # 구멍 5%
bash loadtest/measure_delete_fragmentation.sh S3 5      # 구멍 20%
```

정리:

```bash
docker exec -e MYSQL_PWD=… shadowfit-mysql mysql -uroot \
  -e 'DROP TABLE shadowfit.outbox_frag, shadowfit.nums;'
```
