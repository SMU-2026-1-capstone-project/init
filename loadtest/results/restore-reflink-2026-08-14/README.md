## 0. 판정

**진단이 맞았다. 그리고 팔 B 의 복구는 9초가 아니라 약 174초(2.9분)다.**

| | `--reflink=never` (교정) | `--reflink=auto` (기존 = 대조군) |
|---|---|---|
| 판 수 | 3 (+버림 1) | 3 |
| prepare | 4~5s | 4~5s |
| **`cp` (붓기)** | **166s** (4판 전부 166) | **2s** |
| **디스크 소비** | **10,409~10,410 MB** | **0 MB** |
| 기동 | 2s | 2s |
| **복구 합계** | **173~174s** | **9s** |
| 복구 직후 `sync` | 5~15 ms | 12~19 ms |
| 행수 검증 | 전판 일치 | 전판 일치 |
| 체크섬 | 일치 | 일치 |

- **`auto` 판이 b 라운드의 9~10초를 그대로 재현했다.** 같은 무대·같은 아티팩트에서 플래그
  하나로 9s ↔ 174s 가 갈린다 — 원인이 reflink 라는 것이 **대조군으로 확정**됐다
- **디스크 소비가 0MB 다.** 「복사했다」는데 볼륨이 1바이트도 안 줄었다. 시간이 아니라
  **이 칸이 결정적**이었다 — `sync` 는 두 모드 다 한 자릿수 ms 라 아무것도 못 가른다
- **`cp` 166초가 4판 전부 동일하다.** 편차가 없다는 것 자체가 「디스크 상한에 붙어 있다」는 뜻이다

## 1. 🔴 §3 의 반증 논증이 예측까지 맞췄다

본 측정 README [§3](../backup-restore-aws-2026-08-13/README.md) 은 「9초는 물리적으로 불가능하다」를
이렇게 논증했다 — 10,367MB 를 gp3 125MB/s 로 부으려면 **≈166초**가 필요하다.

**실측이 166초다.**

| | 값 |
|---|---|
| 실제 쓴 양 | 10,409 MB |
| `cp` 소요 | 166 s |
| 쓰기 처리량 | 62.7 MB/s |
| **읽기+쓰기 합** | **125.4 MB/s** ← gp3 상한 **125 MB/s** |

읽기와 쓰기가 **같은 볼륨**에서 일어나므로 둘을 합쳐야 볼륨 처리량이다. 그 합이 상한과
같은 자리에 떨어졌다 — 이 구간은 **디스크가 지배한다**(설계 §5 의 전제)는 것이 다시 확인됐다.

## 2. 되찾은 배수 — 143배가 아니라 **약 7배**

| | 팔 A `mysqldump` | 팔 B XtraBackup |
|---|---|---|
| 복구 | 1,223~1,230 s | **173~174 s** |
| | 약 20.5분 | **약 2.9분** |

**팔 A ÷ 팔 B ≈ 7.1배.** 초판이 적었던 **143배는 철회**한다(그 값의 분모가 실제로는 복사를
안 한 시간이었다).

**판정 방향은 안 바뀐다** — 물리가 논리보다 빠르다. 자릿수가 하나 줄었을 뿐이고, 이제
**두 값이 같은 기준**(둘 다 디스크에 실제로 내려간 상태)에서 재졌다.

복구 직후 `sync` 가 교정 판에서도 **5~15ms** 다. 166초 동안 쓰기가 이미 다 내려갔다는 뜻이라,
**173~174초는 그 자체로 내구성을 포함한 값**이다. #201 이 팔 B 에 대해 물은 것이 여기서 닫힌다.

## 3. reflink 복구는 **틀린 값이지만 깨진 데이터는 아니다**

`auto` 판도 **행수·체크섬이 전부 일치**했다(`xb_r3_B`→`254366807`, `xb_r6_B`→`2695667686`,
b 라운드가 기록한 값과 동일). XFS reflink 는 CoW 라 **읽으면 같은 내용이 나오고, 나중에
어느 쪽을 고쳐도 서로 안 망가진다.**

그래서 이 결함은 **「복구가 실패한다」가 아니라 「복구 시간이 거짓말을 한다」** 다. 조용히
틀리는 부류라 더 나쁘다 — 검증 칸이 전부 «일치» 라서 **표만 보면 아무 문제가 없어 보인다.**

다만 **운영 의미로는 복구본이 아니다.** 백업 아티팩트와 같은 extent 위에 서 있으므로
「백업본과 독립한 사본으로 되돌렸다」는 RTO 의 전제를 만족하지 않는다.

## 5. 미검증 · 한계

- 🔴 **아티팩트가 이미 prepare 된 상태였다.** b 라운드가 복구하면서 in-place 로 적용했다.
  그래서 여기 `prepare_s`(4~5s)는 초판의 3s 와 **같은 것을 재지 않는다.** 다만 두 값이
  같은 자릿수라 합계 판정(≈174s)은 흔들리지 않는다
- **읽기와 쓰기가 같은 볼륨**이다. 실제 재해 복구는 백업이 다른 매체(S3·다른 볼륨)에 있어
  이 값과 다르다 — 이 166초는 **「같은 디스크 안에서 붓는」** 조건의 값이다
- **writer 가 없다.** b 라운드의 복구는 writer 가 도는 중이었다. 경합 상대가 없으니
  이번 값이 약간 유리한 쪽이다
- **팔 A 는 재측정하지 않았다.** 팔 A 는 reflink 를 안 타므로(InnoDB 재적재) b 라운드 값을 그대로 쓴다
- **real-JSON 무대의 팔 B 는 교정하지 않았다.** 그쪽 아티팩트(1.9GB)는 남아 있으나 §2 의
  배수 판정에 필요한 것은 더미 무대 쪽이다
