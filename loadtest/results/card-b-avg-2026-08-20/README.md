## 0. 한 줄

**두 평균은 기제가 예측하는 자리에서만, 그리고 거기서는 예외 없이 갈렸다** — 불균일 200/200,
균일 0/2,002. 그리고 곡선 쿼리는 커버링 인덱스로 **6.7배** 빨라지는데 🔴 **읽은 행 수는 완전히 같다**.

---

## 1. 두 평균 — 「다르더라」가 아니라 「여기서만 다르다」

한 rep 의 프레임은 같은 `sync_rate` 를 공유하는데 다운샘플로 **rep 마다 남은 행 수가 다르다.**
그래서 그냥 `AVG(sync_rate)` 는 **프레임 가중**이 되고, AI 가 쓰던 **rep 가중**과 어긋난다.

| 세션 모양 | 세션 수 | 갈린 세션 | 최대 \|차이\| | 평균 \|차이\| |
|---|---|---|---|---|
| **균일**(rep 당 행 수 같음) | 2,002 | **0** | **0.000000** | 0.000000 |
| **불균일** | 200 | **200 (전부)** | **0.082569** | 0.082569 |

가장 크게 갈린 세션들(예: `68531`, rep 당 4~30행):

```
frame_weighted  73.917431   ← 프레임 가중 (그냥 AVG)
rep_weighted    74.000000   ← rep 가중 (GROUP BY 로 rep 을 먼저 접음)
diff            -0.082569
```

🔴 **이 판의 핵심은 «균일 쪽 0» 이다.** 「다르더라」만 보이면 우연과 구분이 안 된다.
설명이 맞다면 rep 당 행 수가 같은 세션에서는 **반드시** 같아야 하고, 2,002개 전부 그랬다.
한 건이라도 갈렸으면 설명이 틀린 것이었다.

> ⚠️ 값(0.082569)은 시드가 만든 것이다. 불균일 200개는 [#204 §5](../report-query-explain-2026-08-19/README.md)
> 가 이 카드를 위해 **일부러 넣은** 세션이라(rep 당 3~30) **실사용 다운샘플이 만든 분포가 아니다.**
> 여기서 선 것은 **「구조가 그렇게 되면 갈린다」와 「안 그러면 안 갈린다」** 까지다.

## 2. 곡선 쿼리의 비용 — 커버링 인덱스 있음/없음

`SELECT rep_number, AVG(sync_rate), COUNT(*) ... WHERE rep_number>0 GROUP BY rep_number`

| 팔 | 판별 ms | **중앙값** | 핸들러 | tmp |
|---|---|---|---|---|
| **with_cover** | 6,906 · 7,393 · 6,696 | **6,906.2ms** | **3,175,688** | 2 |
| **no_cover** | 43,248 · 45,992 · 73,654 | **45,992.1ms** | **3,175,688** | 2 |

**6.7배.** 그런데 🔴 **핸들러가 소수점 하나 안 틀리고 같다.**

계획이 이유를 준다:

```
with_cover:  -> Index scan on pose_data using idx_report_cover   (rows=1.23e+6)
no_cover:    -> Table scan on pose_data                          (rows=1.23e+6)
```

**읽는 «행 수» 는 같고 읽는 «폭» 이 다르다.** 커버링 인덱스는 5컬럼짜리 좁은 구조라 필요한
페이지가 훨씬 적다. 반면 테이블 스캔은 행마다 `joint_coordinates` JSON 을 포함한 본체를 지난다
([#204 §2-ㄴ](../report-query-explain-2026-08-19/README.md) 이 «행당 4페이지» 로 잰 그 비용).

> 🔴 **카드 C 와 같은 교훈의 다른 얼굴이다.** 거기서는 핸들러가 선형인데 시간이 2차식이었고
> (비싼 것 = 비교 횟수), 여기서는 핸들러가 **동일**한데 시간이 6.7배다(비싼 것 = 읽는 폭).
> **읽은 «행 수» 는 비용의 대리 지표로 못 쓴다** — 두 판이 서로 다른 방식으로 그것을 보여줬다.

## 3. 🔴 덤 — 로컬 DB 가 «배포 스키마» 가 아니었다

이 판을 돌리다 발견했다. `idx_report_cover` 가 로컬 `pose_data` 에 **남아 있었다.**
이 인덱스는 **어느 마이그레이션에도 없다** — [#204](../report-query-explain-2026-08-19/README.md)
라운드의 arm C 가 만든 뒤 안 지워진 것이다.

즉 **그 라운드 이후 `pose_data` 를 건드린 측정은 전부 「arm C 상태」를 잰 것**이고, 이 판의
첫 실행도 그랬다(6.2~7.8초가 나왔는데 그게 커버링 있는 값이었다).

- 지금은 rig 이 두 상태를 **다 재고**, 끝나면 **인덱스 없는 상태**(= 마이그레이션이 정의하는 상태)로 둔다
- 되살리려면: `ALTER TABLE pose_data ADD INDEX idx_report_cover (session_id, rep_number, timestamp_sec, sync_rate, smoothed_knee_angle);` (150만 행에 1~2분)

## 4. 🔴 미검증 · 말하면 안 되는 것

1. **곡선의 «모양» 은 의미 없다.** 합성 데이터라 「몇 번째 rep 부터 무너지나」는 시드가 만든
   모양일 뿐이다. 이슈가 카드 B 에 걸어둔 *"볼륨 추천의 근거가 본인 곡선에서 나온다"* 는
   **실사용 데이터가 있어야** 서는 이야기다.
2. **불균일 200개는 실사용 분포가 아니다**(§1 의 주석).
3. **no_cover 의 산포가 크다** — 43.2 ~ 73.7초. 중앙값을 썼지만 이 팔의 시간은 자릿수까지만 믿을 것.
4. **6.7배는 «읽기 이득» 이고 «채택 근거» 가 아니다.** 커버링 인덱스의 **쓰기 대가**는 여전히
   안 쟀다 — [#205 카드 A 의 남은 반쪽](https://github.com/Shadowfit/init/issues/205)이고
   #204 §4-3 이 *"채택 판단은 여전히 열려 있다"* 로 남겨둔 그대로다.
5. **이 쿼리는 세션 전체를 훑는다**(`WHERE rep_number>0` 만). 실제 화면은 세션 하나를 보므로
   **여기서 잰 것은 «전수 집계» 의 비용**이다. 세션 단위 곡선은 훨씬 싸다 — 안 쟀다.
6. **동시성 없이 혼자 돌았다.**

## 5. 카드로서 남는 문장

- **같은 컬럼을 평균 냈는데 두 시스템이 다른 값을 낸다** — 그리고 **왜 그런지가 구조로 예측되고,
  예측한 자리에서만 일어난다**(불균일 200/200 · 균일 0/2,002)
- 정확성 카드인데 **성능 카드와 열쇠가 같다** — 곡선 쿼리는 커버링 인덱스가 6.7배 준다
- ⚠️ 채택은 **쓰기 대가**를 재야 말할 수 있다
