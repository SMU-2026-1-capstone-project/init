# #164 충돌 빈도 — 스레드풀은 «실제로» 세션을 섞는다, 그런데 **한가할 때만** (2026-08-11)

장비: 개발 장비(i3-6100, 물리 2코어 / 논리 4) · `model_complexity=1` · 프레임당 단독 비용 **79ms**

## 0. 한 줄 요약

**충돌은 실재한다. 그런데 «부하가 높을 때» 가 아니라 «실사용 페이스(3fps)» 에서 심하다 — 이슈의 추측과 정반대다.**

| 조건 | 충돌률 | 검출률(스레드로컬) | 검출률(세션전용) | 손실 |
|---|---|---|---|---|
| **3fps — 실사용** | **44~78%** | **33~55%** | 96% | **+41~63%p** |
| 최대 속도 — 포화 | **0~2.6%** | 94~96% | 96% | +0~2.8%p |

---

## 1. 무엇이 확인됐나

### ✅ #164 의 전제는 사실이다

*"스레드풀 배정이 실제로 세션을 섞는지 확인하지 않았다"* → **섞는다.** 실사용 페이스에서 호출의 44~78% 가
«직전에 다른 세션을 본 스레드» 에 배정된다.

### 🔴 이슈의 추측은 반대였다

이슈는 *"AnyIO 기본 워커 수(40)와 동시 세션 수에 따라 달라진다. **세션 수 < 워커 수면 충돌이 드물 수도 있다**"* 로 적었다.
실제는 반대다 — **워커가 남아돌수록 충돌이 심하다.**

메커니즘(관측에서 유도, 코드로 확증한 것은 아님):

```
3fps  : 세션이 요청 후 ~250ms 쉰다 → 스레드가 idle 로 반납됨
        → 다음 요청은 «아무 idle 스레드나» 집어간다 → 세션↔스레드가 매번 바뀐다 → 충돌 44~78%

최대  : 세션이 안 쉬고 연달아 요청한다 → 방금 반납한 스레드를 곧바로 다시 집는다
        → 세션↔스레드가 사실상 붙는다 → 충돌 0~2.6%
```

> **바쁠수록 안전하고 한가할수록 위험하다.** 그리고 **실사용 조건이 정확히 위험한 쪽**이다 —
> 3fps 는 [`exercise.tsx:150`](../../../frontend/app/(tabs)/exercise.tsx)(`intervalMs=330`)과
> `session_state.py:47`(`MIN_FRAME_INTERVAL_SEC=0.300`, #143)이 강제하는 **실제 값**이다.

### 🔴 피해가 #164 가 보고한 것보다 크다

원 이슈는 «최악의 경우» 로 45% 손실을 적었다. 실사용 페이스에서 **41~63%p** 가 나온다 —
«최악의 경우» 로 적어둔 값이 실은 **평시에 가깝다.**

### 세션 수가 늘어도 안 나빠진다

2 → 4 → 8 세션에서 손실이 단조 증가하지 않는다(+41 → +63 → +45%p). 즉 이건 **부하 문제가 아니라
배정 패턴 문제**다. 사용자가 적어도 그대로 발생한다.

## 3. ⚠️ 한계 — 인용 전에 반드시 볼 것

1. **판별 반복이 없다.** 같은 설정을 두 번 돌렸더니 2세션·3fps 충돌률이 **75.6% → 43.6%** 로 흔들렸다.
   **개별 값을 인용하지 말 것. 방향(3fps ≫ 최대)만 두 번 재현됐다.**
2. **합성 인체다.** #164 의 세 번째 캐비엇은 **여전히 열려 있다** — 실제 카메라 프레임에서 트래킹이
   얼마나 버티는지는 다를 수 있다.
3. **HTTP 를 안 태웠다.** `run_in_threadpool` 을 직접 썼다. 실제 FastAPI 는 요청 파싱·base64 디코딩이
   더 붙어 스레드 점유 시간이 길어지므로 **충돌 패턴이 달라질 수 있다.**
4. **개발 장비(물리 2코어)다.** 충돌률은 CPU 속도에 의존한다(느릴수록 in-flight↑).
5. **대조군도 96% 지 100% 가 아니다.** 각 팔의 첫 프레임들이 콜드라 ~4% 는 구조와 무관한 바닥이다.
6. **메커니즘은 관측에서 «유도» 한 것**이지 anyio 의 스레드 재사용 정책을 코드로 확인한 것이 아니다.

## 4. 🔴 이 rig 가 두 번 틀렸다 — 그 과정을 남긴다

같은 실수를 다시 하지 않기 위해 기록한다. 둘 다 «그럴듯한 결과» 를 냈고, 검산이 아니었으면 통과했다.

| 판 | 무엇이 틀렸나 | 무엇이 잡았나 |
|---|---|---|
| **1판** | 사람을 «고르게 벌려» 생성했는데 `scale ≳ 0.92` 조합이 프레임 밖으로 잘려 **단독으로도 0/20**. 손실의 상당 부분이 충돌이 아니라 픽스처였다 | **대조군 검출률이 47~72%** — 전용 검출기면 100% 여야 하는데 안 나왔다 |
| **2판** | 스레드를 `threading.current_thread().name` 으로 셌다. **anyio 워커는 이름이 전부 같아서**(`AnyIO worker thread`) 여러 스레드가 하나로 뭉개지고 충돌률이 과대측정됐다 | **«예상 in-flight 2.84 인데 스레드 1개»** — 물리적으로 불가능한 값 |

1판의 교훈은 `measure_ai_concurrency.py` 가 이미 주석으로 적어둔 것이다 —
*"조용히 다른 경로를 재는 것이 오늘만 세 번 나왔다(#139·#140·#153)."* 네 번째였다.
그래서 이 스크립트는 **`verify_standalone()` 단언과 in-flight 검산을 출력에 상시 포함**한다.

## 5. 이 측정이 바꾸는 것

- **#164 의 우선순위가 올라간다.** «최악의 경우 45%» 가 아니라 **«실사용 페이스에서 40~60%p»** 다.
- **«장비를 올리면 되지 않나» 는 이미 반증됐다**([`../ai-recalibrate-2026-08-11/`](../ai-recalibrate-2026-08-11/) —
  추론이 5.9배 빨라져도 검출률 11/20 은 그대로였다). 여기에 «한가할수록 심하다» 가 더해진다.
- **입장 제한(P3)의 안전계수에 이 손실을 반영해야 한다.** 물리 코어당 16.4세션(상한)은
  «프레임이 안 버려질 때» 의 값이다.
- 해결 방향은 이슈의 **ㄴ(세션별 검출기)** 또는 **ㄷ(세션-스레드 고정)** 으로 좁혀진다.
  ㄱ(`static_image_mode=True`)은 프레임당 비용을 올려 이 워크로드에 안 맞는다.
