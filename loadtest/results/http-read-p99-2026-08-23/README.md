## 0. 한 줄

**평균이 비싼 엔드포인트와 꼬리가 튀는 엔드포인트가 다르다** — `session` 이 p50 은 제일 무거운데 p99 배수는 제일 안정적이고, `calendar` 는 그 반대다.

🔴 **부하기가 대상과 같은 박스에서 돈다.** 2코어에 MySQL·백엔드·AI 가 이미 동거 중인데 k6 까지 얹혔다.

### 1-1. 계정을 왜 새로 만들어 시드했나

시더([`seed_report_rig.sh:38`](../../seed/seed_report_rig.sh))가 `member_id` 를 **1·5·12 로 하드코딩**한다. 그래서 새로 만든 계정에는 읽을 데이터가 없고, 로그인할 수 있는 계정에는 데이터가 없다.

🔴 **시드 회원의 비밀번호를 갈아끼워 «빌려 쓰는» 길은 택하지 않았다** — 남의 계정 자격증명을 만지는 일이다. 대신 **내가 만든 계정에 데이터를 넣었다.**

```bash
# ① API 로 계정 생성 (비밀번호를 내가 안다)
curl -X POST localhost:8080/member/signup -H 'Content-Type: application/json'      -d '{"username":"...","email":"...","password":"...","sex":"MALE","role":"USER"}'

# ② 그 member_id 로 세션·리포트 시드 (시더의 모양을 따르되 member_id 만 내 것으로)
#    이 판은 세션 1,000 · 리포트 1,000 · reference_source='k6load'

# ③ 리포트가 붙은 세션 id 를 뽑아 K6_SIDS 로 넘긴다 (rig 파일 머리 참고)
```

⚠️ **rig 은 이 시드 단계를 자동화하지 않는다.** 지금은 손으로 만든 계정을 `K6_EMAIL`/`K6_PASSWORD` 로 넘기는 형태다 — 다시 돌리려면 위 세 단계를 사람이 밟아야 한다.

## 2. 결과

| 엔드포인트 | avg | p50 | p95 | **p99** | max | p99/p50 |
|---|--:|--:|--:|--:|--:|--:|
| `GET /reports/session/{id}` | 271.6ms | 248.1 | 574.3 | **877.7** | 1.23s | **3.5x** |
| `GET /reports/weekly-summary` | 231.9ms | 206.3 | 491.4 | **873.5** | 1.58s | 4.2x |
| `GET /reports/calendar` | 203.6ms | 179.9 | 411.7 | **922.2** | 1.11s | **5.1x** |
| `GET /reports/daily` | 177.0ms | 151.8 | 387.7 | **706.6** | 1.08s | 4.7x |

### 2-1. p50 은 하는 일의 무게와 맞는다

`daily`(152) < `calendar`(180) < `weekly-summary`(206) < `session`(248).

하루치 목록이 제일 싸고 세션 리포트가 제일 비싸다 — [#204](https://github.com/Shadowfit/init/issues/204) 가 *"비커버링 · 논리 페이지 4.85배"* 로 짚은 그 쿼리가 제일 무거운 자리에 있다.

### 2-2. 🔴 p99 에서 그 순서가 무너진다

`calendar` 는 p50 이 두 번째로 싼데 **p99 는 922ms 로 넷 중 제일 나쁘다.** p99/p50 으로 보면 **`session` 3.5x ↔ `calendar` 5.1x** — **제일 비싼 엔드포인트가 꼬리는 제일 안정적**이다.

즉 「평균이 비싼 것」과 「꼬리가 튀는 것」이 **다른 엔드포인트**다. 이건 절대 성능과 무관하게 읽히는 **상대** 사실이고, 이 판이 노린 산출이다.

🔴 **원인은 안 봤다.** 후보(캘린더가 월 범위를 훑는 모양 · 커넥션 풀 대기 · 이웃 프로세스)를 **하나도 가르지 않았다.**

## 3. 🔴 이 숫자로 하면 안 되는 것

**SLO 판정선(리포트·캘린더 읽기 p99 ≤ 1s)에 대면 안 된다.** 넷 다 1s 아래지만 그건 «통과» 가 아니다.

1. **환경** — 2코어 동거 박스이고 부하기까지 같이 돈다([[project_loadtest_env_constraint]])
2. **문서가 이미 금지했다** — [`slo-baseline.md`](../../../docs/decisions/slo-baseline.md) 가 *"시간 임계(p99 > X)는 이 환경에서 안 쓴다 — 이웃 프로세스가 통과 여부를 정한다"* 고 못박았다. 로컬 숫자를 판정선에 대면 **그 문장을 스스로 어긴다**
3. **16 VU 에 근거가 없다** — 램프 상한을 임의로 골랐다. 「가정 부하」에서 유도한 값이 아니다([[feedback_no_arbitrary_threshold_values]])

판정선 대면은 **EC2 從 라운드** 몫이다([`AWS-RIDE-ALONG.md`](../../AWS-RIDE-ALONG.md) 관례).

## 4. 미검증 · 안 한 것

- **쓰기축은 안 쟀다.** `POST /exercises/sessions` 는 **AI gRPC 세션을 실제로 만든다** — 부하를 걸면 「HTTP 지연」이 아니라 **「AI 동거」를 재게 된다.** 조건 설계가 먼저다
- **반복이 1판뿐이다.** 팔도 순서도 없어 「이 값이 재현되는가」를 모른다([[feedback_measure_design_needs_repeats]])
- **합성 분포다** — 세션 1,000개가 같은 템플릿이라 값 분포가 균일하다
- **캐시 상태를 안 통제했다** — 첫 20초(VU 1)가 가장 차가운 버퍼풀에서 돌았고, 그게 램프의 앞머리와 겹친다
- **p99 표본이 얇다** — 엔드포인트당 456회면 p99 는 상위 5개 정도로 결정된다. 「922 vs 877」의 차이를 값 하나로 인용하면 안 된다
