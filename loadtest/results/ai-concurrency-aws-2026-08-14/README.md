## 1. [C] 스레드 스케일 — 로컬의 「1.73배 천장」은 알고리즘이 아니었다

| 스레드 | 총 처리량 | 판별 최소~최대 | 스레드당 평균 | 1스레드 대비 |
|---|---|---|---|---|
| 1 | 55.7 fps | 55.7~55.9 | 14.8 ms | 1.00x |
| 2 | 104.8 | 102.6~107.6 | 15.6 | 1.88x |
| **4** | **184.4** | 184.2~184.6 | 17.5 | **3.31x** |
| **8** | **325.9** | 320.4~326.4 | 19.9 | **5.85x** ← 물리 코어 |
| 16 | 451.8 | 450.7~454.7 | 28.3 | 8.11x ← HT |
| 32 | 468.3 | 464.0~468.9 | 55.1 | 8.41x ← 포화 |

🔴 **같은 4스레드가 로컬에선 1.73x, 여기선 3.31x 다.** 로컬 i3-6100 은 **물리 2코어에 4스레드**를
밀어넣은 초과 구독 상태였다 — 그 1.73배는 **알고리즘의 천장이 아니라 그 박스의 코어 수**였다.
08-09 문서가 「물리 2코어 + HT 가 그대로 드러난다」로 읽은 것이 맞았고, 이제 대조군이 생겼다.

- **물리 코어 구간(1→8)**: 5.85x — 완전 선형(8x)은 아니고 **73% 효율**
- **HT 구간(8→16)**: +38.6%. 로컬과 달리 **HT 가 실제로 값을 한다**
- **초과 구독(16→32)**: +3.7%. 포화. 스레드당 지연만 28.3 → 55.1ms 로 나빠진다

→ **운영 스레드 수는 16(=논리 코어)가 적정**이다. 32 는 처리량을 거의 안 늘리면서 지연을 2배로 만든다.

## 2. 🔴 #164 는 하드웨어 탓이 아니었다 — 다른 CPU 에서 **같은 45%**

```
[B] 다른 사람 번갈아 → 검출률 11/20
    각 «사람» 은 단독 검출 100% 임을 매 실행 전제 확인에서 단언
```

**i3-6100 과 정확히 같은 11/20 이다.** 검출기가 스레드 로컬(`mediapipe_detector.py:107`)인데
FastAPI 가 스레드풀로 돌려(`pose.py:52`) 동시 세션이 한 스레드를 공유하면 서로의 트래킹을
깨뜨린다 — **설계에서 나오는 값이라 CPU 를 바꿔도 그대로**라는 것이 이번에 확인됐다.

추론 비용도 **1.30x** 로 오른다(15.0 → 19.4ms). 로컬은 1.59x 였으니 **비율은 CPU 를 탄다.**

⚠️ **그래서 §0 의 156세션은 상한이다.** [C] 는 *세션이 스레드에 1:1로 붙는 가장 유리한 배치*로
쟀고, 실제 FastAPI 스레드풀은 [B] 의 상황에 가깝다. **#164 를 고치지 않으면 실제 수용량은
156 보다 한참 아래**고, 그 격차가 얼마인지는 **안 쟀다.**

## 4. 미검증 · 한계

- 🔴 **156세션은 순수 추론의 상한이다.** HTTP·디코딩·GIL·같은 박스의 다른 컨테이너를 안 뺐고,
  무엇보다 **#164 의 손실이 안 들어가 있다**
- **GPU 는 안 봤다.** 이 측정은 전 구간 CPU(TFLite XNNPACK delegate)다. GPU 로 무엇이 달라지는지는
  **재지 않았으므로 말할 수 없다**
- **합성 인체 프레임**이다. 프레임당 비용은 고정 해상도 CNN 이라 내용과 무관하지만, 검출 성공
  여부는 내용을 타므로 매 실행 전제 확인으로 단언한다(rig 주석)
- **클라 3fps 가정**은 `exercise.tsx:150`(`intervalMs=330`)·`session_state.py:47`(0.300s 상한)에서 온다.
  이 값이 바뀌면 세션 수가 그대로 반비례로 움직인다
- **물리 16코어 이상은 안 봤다.** 8→16 이 또 선형일지는 이 데이터로 말할 수 없다
