### 판정선 ㄱ — 인접 팔의 차 vs 두 팔 산포 합

```
A→B (1→2)   +27.96%   산포합 4.70%   🟢 올랐다
B→C (2→3)    +5.07%   산포합 4.79%   🟢 올랐다 (아슬하게)
C→D (3→4)    +1.24%   산포합 6.36%   🔴 산포 안 — 여기가 천장
```

🟢 **N=3 이 답이다.** 4번째 프로세스는 **처리량을 안 준다** — 메모리(검출기 1개 98.7MB)와
운영 복잡도만 는다.

⚠️ **B→C 는 아슬하다**(5.07% vs 4.79%). 3번째 프로세스는 **+5%** 를 주는데 박스는
90%→98% 로 간다. **여유를 사는 값으로 보면 남는 장사가 아니다** — 2개로 두고 박스를
비워두는 선택도 근거가 있다.

## 3. 두 번째 천장 = **박스 포화** (판정선 ㄴ)

1차 proc-split 이 「14.5 vCPU 근처에 두 번째 천장」을 보고 정체를 안 밝혔다. 답은 단순했다:

```
A  box  9.80 / 16 =  61%
B  box 14.45 / 16 =  90%
C  box 15.69 / 16 =  98%
D  box 15.92 / 16 = 100%   ← 더 쓸 CPU 가 없다
```

🟢 **ㄴ 이다(박스), ㄷ(미지의 천장)이 아니다.** 처방이 명확해진다 — **더 큰 박스로 풀린다.**
부하기는 0.36 vCPU 라 한계가 아니다.

🔑 **지연은 N=4 에서도 계속 좋아진다**(470 → 264ms). 처리량은 평평한데 지연은 준다 —
같은 부하를 더 많은 프로세스가 나눠 물어 **큐가 짧아지기** 때문이다.
**처리량만 보면 N=4 가 무의미하지만, p50 을 사려면 값이 있다.**

## 4. 요청당 GIL 이 N 과 함께 **늘어난다**

| 팔 | N | 프로세스당 rps | `rho` | **GIL ms/요청** |
|---|--:|--:|--:|--:|
| A | 1 | 335.6 | 0.934 | **2.78** |
| B | 2 | 214.7 | 0.855 | 3.98 |
| C | 3 | 150.4 | 0.741 | 4.93 |
| D | 4 | 114.2 | 0.658 | **5.76** |

박스가 포화할수록 **같은 요청이 GIL 을 더 오래 쥔다**(2.78 → 5.76ms, **2.1배**).
GIL 을 쥔 스레드가 OS 에 밀려나도 프로브는 계속 기다리기 때문이다.

🔑 **이것이 §3 의 천장과 같은 이야기다** — 박스가 포화하면 처리량이 안 늘 뿐 아니라
**요청당 비용 자체가 는다.** N 을 늘려 얻는 것이 갈수록 작아지는 이유다.

---

## 5. 🔴 판정선 ㄹ 은 잘못 박았다 — 값이 있어도 못 쓴다

설계에 이렇게 적었다:

> 각 프로세스의 `rho` 가 **N 과 무관하게 0.9 근처**면 🟢 «GIL 은 프로세스당» 확증.
> **N 이 늘수록 rho 가 떨어지면** GIL 말고 공유 자원이 더 있다.

관측: `0.934 → 0.855 → 0.741 → 0.658`. 문자 그대로면 **「공유 자원이 더 있다」** 다.
**그렇게 읽으면 안 된다.**

🔴 **이 판은 합계 부하를 고정한다.** 그래서 N 이 늘면 **프로세스당 일이 줄고**(335→114 rps),
`rho` 는 **당연히 떨어진다.** 판정선이 「프로세스당 부하가 같다」를 암묵 가정했는데
설계가 바로 그 반대로 되어 있다 — **물음과 판이 안 맞는다.**

⚠️ 비례 예측과 비교하면 오히려 반대 방향이다:

```
비례 예측  0.934 → 0.598 → 0.419 → 0.318
실측       0.934 → 0.855 → 0.741 → 0.658    ← 훨씬 덜 떨어진다
```

떨어지는 폭이 작은 것은 §4 의 「요청당 GIL 증가」로 설명된다. **어느 쪽으로도 «공유 자원»
의 증거가 아니다.**

🟢 **제대로 물으려면**: 프로세스당 세션을 **고정**하고(예: N 개마다 160세션씩) N 을 늘려야
한다. 그러면 부하가 N 배가 되지만 각 프로세스의 조건은 같아서 `rho` 가 유지되는지 볼 수 있다.
🔴 **미실행.**

## 6. 이 판이 확정한 것과 안 한 것

- ✅ **N=3 이 답이다** — 3→4 는 산포 안(+1.24%)
- ✅ **두 번째 천장은 박스 포화** — N=3 에 98%, N=4 에 100%. **더 큰 박스로 풀린다**
- ✅ **요청당 GIL 이 포화와 함께 2.1배 는다**(2.78 → 5.76ms)
- 🟢 **지연은 N=4 까지 계속 좋아진다**(470 → 264ms) — 처리량과 다른 축이다
- 🔴 **판정선 ㄹ 은 물음과 판이 안 맞아 못 쓴다**(§5)
- 🔴 **스티키 라우팅을 안 다룬다** — 이 판은 rig 이 프로세스마다 따로 세션을 열어
  «이미 갈라진» 부하를 준다. 실제 배포는 같은 세션이 같은 프로세스로 가야 하고
  그 비용은 [`ai-sticky-routing.md`](../../../docs/decisions/ai-sticky-routing.md) 몫이다

## 7. 정직하게 비어 있는 것

- **RAM 을 안 쟀다.** 합계 풀이 고정이라 검출기 메모리는 같지만 **프로세스 오버헤드는
  N 에 비례**한다 — 그 크기를 안 봤다
- **N>4 는 안 봤다.** 박스가 이미 100% 라 의미가 없다고 판단했지만 **확인은 아니다**
- **더 큰 박스에서 안 쟀다.** 「박스로 풀린다」는 §3 의 **추론**이다 — 8xlarge 에서
  N=5·6 이 더 주는지는 미측정
- **`rho` 판정선을 다시 박아야 한다**(§5) — 프로세스당 부하 고정 판이 따로 필요하다
