## 0. 한 줄

**커버링 인덱스는 행 하나당 논리 페이지 수정을 «정확히 한 번» 더 시킨다 — +24.4%.**
그리고 이 판이 답을 낸 이유는 무대를 바꿔서가 아니라 **지표를 바꿔서**다. 같은 박스에서
1차·2차가 두 번 무너졌는데, 그때 보던 것은 «시간» 이었고 이번에 본 것은 «카운터» 다.

## 1. 결과

무대: 실 `pose_data`(데이터 **4,996MB**) vs 버퍼풀 **2,048MB** — **2.4배**로 풀을 넘는다
(R8 이 «메모리 안» 만 쟀던 그 경계를 이번엔 넘겼다). `innodb_change_buffering=all` ·
`flush_log_at_trx_commit=1` · `sync_binlog=1`. 판당 20,000행(800문 × 25행) · 문당 커밋 ·
순서 `A B B A B A A B`(첫 판 버림) · **8판 전부 유효, 결함 0**.

| 팔 | 판별 `bp_write_req` |
|---|---|
| **A** (인덱스 있음) | 106,254 · 106,335 · 106,339 &nbsp;*(버림 106,295)* |
| **B** (없음) | 85,274 · 85,371 · 85,468 · 85,556 |

**겹치지 않는다** — A 의 최솟값(106,254)이 B 의 최댓값(85,556)보다 크다. 팔 안쪽 산포는
**A 0.08% · B 0.33%**.

| 지표 | A | B | **A÷B** |
|---|---|---|---|
| 🔑 `Innodb_buffer_pool_write_requests` | 106,335 | 85,420 | **1.245** |
| 🔑 `Innodb_log_write_requests` | 103,720 | 83,513 | **1.242** |

### 행당으로 풀면 기제가 그대로 보인다

```
(106,335 − 85,420) ÷ 20,000행 = 행당 +1.046 페이지 수정
(103,720 − 83,513) ÷ 20,000행 = 행당 +1.010 redo
```

**행 하나 = 세컨더리 인덱스 엔트리 하나 = 리프 페이지 수정 1회.** 1.00 을 넘는 4%는
페이지 분할·상위 노드 몫이다. 이건 통계적 추정이 아니라 **산수가 맞아떨어진 것**이고,
**독립인 두 카운터가 0.3% 안에서 같은 답**을 냈다.

기준선도 같이 읽힌다 — B 팔은 행당 **4.27회**(클러스터드 + `uk_pose_event` +
`idx_session_timestamp` + undo·시스템). 거기에 1.046 이 얹혀 **+24.4%** 다.

### 인덱스 크기

| 인덱스 | MB |
|---|---|
| PRIMARY | 5,640.8 |
| `idx_session_timestamp` | 465.0 |
| **`idx_report_cover`** | **81.5** |
| `uk_pose_event` | 68.5 |

## 2. 🔴 지표를 바꾼 것이 이 판의 전부다

1차(08-20)는 판별 `DELETE` 가 만든 드리프트로 **무효**였고, 2차는 박스가 4배 느려져 접었다.
셋째 판이 성공한 이유는 무대가 좋아져서가 아니다 — **이 박스는 여전히 잡음투성이다.**

| 같은 팔 B 의 네 판 | 🔑 `bp_write_req` | ms |
|---|---|---|
| 판 1 | 85,468 | 159,428 |
| 판 2 | 85,371 | 169,742 |
| 판 4 | 85,274 | **71,791** |
| 판 7 | 85,556 | **272,298** |

**같은 조건인데 `ms` 는 3.8배 벌어지고(71.8초 ↔ 272.3초) 카운터는 0.33% 안에 붙는다.**
`ms` 로 판정했으면 이번에도 못 쟀다.

## 3. 🔴 미검증 · 말하면 안 되는 것

| 지표 | 왜 |
|---|---|
| **`ms` (A÷B 1.31)** | 위 표대로 **3.8배 잡음**이다. 처리량 대비는 **이 박스에서 못 낸다** — 조용한 박스가 필요하고, 그건 從 등급이라 별도 라운드에 얹어야 한다 |
| **`pages_written`** | A 1,201~1,400 ↔ B 75~1,576 으로 **겹친다.** 플러시 «타이밍» 이지 팔의 비용이 아니다. 1차 시도가 이 지표에 데였다 |
| **`bp_reads`** | 버림 판(806)은 MySQL 기동 직후라 **차가웠던 것**이고, 나머지는 0~112 다. 즉 **이 판의 대가는 디스크가 아니라 «메모리 안» 에서 났다** — 표는 풀을 2.4배 넘는데도 삽입 지점이 한 자리라 인덱스 페이지가 계속 상주했다. R8 과 같은 경계가 **다른 이유로** 다시 섰다 |
| **동시성 하 대가** | 단일 라이터 판이다. 여럿이 같이 넣을 때의 대가는 다른 판이다 |
| **인덱스가 풀을 넘는 규모** | `idx_report_cover` 는 81.5MB 로 2GB 풀에 통째로 들어간다. **인덱스 자체가 풀을 넘는 규모는 이 판이 못 본다** |

## 4. change buffer 는 안 탔다 — 그리고 계기가 고장나 있었다

08-20 rig 이 가설을 하나 박아뒀다: *「`idx_report_cover` 는 non-unique 라 change buffer 를
쓸 «수» 있고, 그러면 대가가 예상보다 쌀 수 있다」*. 그리고 그날 결정 로그는
**`Innodb_ibuf_merges` 전 판 0** 을 «이미 건진 사실» 로 적었다.

🔴 **그 근거는 무효다. MySQL 8.0 커뮤니티에 `Innodb_ibuf_merges` 라는 상태 변수는 없다.**
rig 이 빈 문자열을 받았고 bash 산술이 그것을 `0 - 0 = 0` 으로 계산해 **8판 내내 0 을 찍었다.**
아무것도 안 재고 있었다 — [#271](https://github.com/Shadowfit/init/issues/271) 계열의 **조용한 0** 이다.

진짜 출처(`information_schema.INNODB_METRICS`, `status=enabled`)로 다시 재고, 페이로드도
세 모양으로 갈라 봤다:

| 팔 | 삽입 지점 | `ibuf_merges` | `ibuf_ins` | `bp_reads` |
|---|---|---|---|---|
| **H** 집중 | 한 세션에 순차 (본 판과 같은 모양) | **0** | **0** | 0 |
| **S** 분산(새 id) | 새 `session_id` 8,000개에 흩뿌림 | **0** | **0** | 292 |
| **E** 분산(기존 id) | **이미 표에 있는** `session_id` 500개에 흩뿌림 | **0** | **0** | **221** |

교차 확인도 일치한다 — `Ibuf: ... 0 merges` · `merged operations: insert 0`.

**팔 E 가 결정적이다.** `bp_reads` 가 실제로 올라갔다(H는 0) — 즉 **삽입 지점이 메모리에
없어서 디스크를 쳤는데도** 경로가 안 켜졌다. 「페이로드가 조건을 안 만들어서」로는 더 설명이
안 된다.

⚠️ **왜 안 켜지는지는 확정 못 했다.** 유력한 후보는 **같은 키 앞부분을 유니크 인덱스가
이미 쥐고 있다**는 것이다 — `uk_pose_event`(unique)가 `session_id` 로 시작하므로 삽입마다
그 자리를 **반드시 읽어야** 하고(유니크 검사는 버퍼링이 원천적으로 불가), 그 과정에서 인접
구조가 메모리로 올라온다. **이건 가설이다** — 가르려면 `uk_pose_event` 를 뺀 대조 팔이
필요한데 이번 판엔 없다.

**카드 A 에 주는 결론은 분명하다: 위에서 잰 +24.4% 는 «나중에 청구될 비용이 미뤄진 값» 이
아니다.** change buffer 가 안 타므로 **그 자리에서 다 낸다.**

## 5. 🔴 이 판이 rig 에서 잡은 결함 다섯

측정보다 이쪽이 더 값질 수 있다. 전부 **표가 멀쩡해 보이는 종류**다.

1. **없는 카운터를 읽고 있었다** (`Innodb_ibuf_merges`) → `INNODB_METRICS` 로 교체 + 기동 시 단언
2. **새 지표가 표에 안 실렸다** — 08-21 수정이 `bp_write_req`·`log_write_req` 를 **걷기는 하는데**
   `raw.tsv` 에만 남고 `summary.md` 의 세 표는 전부 **`ms` 로 줄 세우고 있었다.**
   「시간은 못 쓴다」고 주석에 적어놓고 출력은 시간으로 판정하는 상태였다
3. **중앙값이 중앙값이 아니었다** — `ms` 로 정렬한 뒤 **그 행의** 다른 열 값을 «중앙값» 으로
   찍었다. 열마다 순위가 다르므로 틀린 값이다 → 열별로 따로 정렬
4. **누적량 주석이 기본값과 안 맞았다** — 「판당 7,500 · 총 6만 = 4%」인데 기본값으로는
   **판당 20,000 · 총 16만 = 13%** 다. 「판마다 안 지운다」의 정당화가 그 4% 에 걸려 있었다
5. **후속 판이 «넣다 죽은 판» 을 유효 판으로 셌다** — 팔 E 1차에서 `uk_pose_event` 충돌로
   삽입이 통째로 실패했는데(`err 1` · `bp_write_req` **12**), 집계는 그걸 그대로 «ibuf 0» 으로
   요약했다. **#271 의 재발**이라 그물을 셋 걸었다: 판마다 「삽입이 실제로 일어났는가」 단언 ·
   `err>0` 판 제외 · 표에 **유효 판/버린 판** 열
   ⚠️ 무효 판의 산출물은 **재실행이 같은 `OUT` 경로에 덮어썼다.** 남은 증거는 이 문서에 옮겨 적은
   그 표(`err 1` · `bp_write_req` 12·13)뿐이다 — 다음부터 재실행은 경로를 나눈다.
