# HTTP 쓰기 경로 p99 @ 가정 피크 배수 — EC2 2대 (2026-08-24)

`slo-baseline.md` §4-2 의 **「세션 쓰기 p99 ≤ 300ms」에 대응하는 실측이 0** 이던 자리를 채운다.
읽기 절반은 [2026-08-23 로컬 판](../http-read-p99-2026-08-23/README.md)이 채웠지만, 그 판은 스스로
*"판정선 대면은 EC2 從 라운드 몫"* 이라고 적었다 — 부하기까지 같은 2코어 박스에 있었기 때문이다.

이 판은 **부하기를 대상 밖에 두고** 돌렸다.

---

## 0. 무대

| | 값 |
|---|---|
| 대상 | EC2 **c7i.2xlarge** (8 vCPU · 15GB) — MySQL · Spring · AI 동거 |
| 부하기 | EC2 **c7i.xlarge** (4 vCPU) — k6 v2.1.0, 같은 VPC·서브넷 |
| 커밋 | 대상 `7267664`([#529](https://github.com/Shadowfit/init/pull/529) 포함) · rig `b8e9d08` |
| 팔 | 가정 피크 **×60 · ×180 · ×360** = 4.5 · 13.5 · 27 세션시작/초 |
| 판 | 120초 × 4블록(0 버림) · **라틴 방격** · 계정 48 |

🔴 **대상이 관례값(c7i.4xlarge)이 아니다.** 계정 vCPU 한도가 32 인데 다른 라운드의 c7i.4xlarge 가
이미 16 을 쓰고 있어서 8 vCPU 로 내렸다. **박스가 다르면 절대값도 다르다** — 이 표는 이 무대의 값이다.

### 부하를 어디서 유도했나 — 임의로 고른 값이 아니다

```
동접 67.5세션 = DAU 1,000 × 1.5세션/일 × p 0.18 × (15분/60)     ← load-test-strategy §4.2 (가정 P1)
세션 시작률   = 67.5 / 900초 = 0.075/초                          ← 이 rig 의 ×1
```

×1 은 120초에 표본 9개라 p99 가 안 나온다. 그래서 이 판이 답하는 질문은
**「가정 피크의 몇 배까지 300ms 를 지키나」** 다.

## 1. 결과

| 배수 | 도착률(세션시작/초) | 시작 p50 | **시작 p99** | 종료 p50 | **종료 p99** | 표본 | 게이트 |
|---|--:|--:|--:|--:|--:|--:|:--:|
| ×60 | 4.5 | 10.7ms | **14.2ms** | 7.3ms | **16.6ms** | 1,621 | ✅ |
| ×180 | 13.5 | 9.7ms | **16.9ms** | 7.3ms | **17.2ms** | 4,862 | ✅ |
| ~~×360~~ | ~~27~~ | ~~8.5~~ | ~~20.7~~ | ~~7.2~~ | ~~19.8~~ | 9,722 | 🔴 **409** |

유효 블록 3판의 중앙값. 원자료는 [`raw.txt`](./raw.txt), 실행 로그는 [`run.log`](./run.log).

### 1-1. 읽을 수 있는 것

**가정 피크의 180배(13.5 세션시작/초)까지 두 쓰기의 p99 가 17ms 다.** 목표 300ms 의 **5.7%** 다.
p99 가 목표에 닿으려면 여기서 **17배** 가 더 나빠져야 한다.

### 1-2. 🔴 ×360 은 인용하면 안 된다 — 「느리다」가 아니라 「부하를 못 걸었다」

409(`SESSION_ALREADY_IN_PROGRESS`)가 판당 ~1,180건 났다. 원인은 서버 지연이 아니라 **rig 의 천장**이다.

`PATCH /sessions/{id}/end` 는 «종료» 가 아니라 **«종료 요청»** 이다 — `Session.markEnded` 는
`end_time` 만 쓰고, `status` 가 `IN_PROGRESS` 를 벗어나는 것은 **AI 콜백이 온 뒤**다.
그런데 `createSession` 은 회원당 `IN_PROGRESS` 1개를 막는다. 즉 **계정은 «완결» 되어야 다시 쓰인다.**

```
도달 가능 도착률 ≈ 계정 수 ÷ 완결 왕복(아웃박스 폴 1초 + AI + 콜백)
```

실측된 유지 도착률은 **17.2/초**(성공 시작 6,184건 ÷ 3판 × 120초) — 48계정 기준 **완결 왕복 ≈ 2.8초**다.
그래서 ×180(13.5/초)은 통과하고 ×360(27/초)은 못 낸다.

### 1-3. 곁가지 — p50 이 부하가 커질수록 **내려간다**

시작 p50 이 10.7 → 9.7 → 8.5ms. 배수가 오를수록 빨라진다. 커넥션 재사용·JIT·캐시가 후보지만
**가르지 않았다.** 꼬리는 반대로 벌어진다(p99/p50 이 1.33 → 1.74 → 2.4).

## 2. 🔴 이 판이 답하지 않는 것

1. **세션 길이를 모사하지 않는다.** 시작하자마자 끝낸다 — 「15분 세션이 사는 동안」은 gRPC 적재 축 몫이다
2. **읽기축과 같은 표에 놓지 말 것.** 읽기 판은 로컬 2코어 동거였다. 박스가 다르다
3. **합성 계정·합성 세션**이다 — 값 분포가 균일하다([[project_synthetic_data_distribution_limit]])
4. **×360 이 못 간 것은 앱의 천장이 아니라 rig 의 천장**이다. 앱의 쓰기 천장은 아직 안 봤다
5. 대상 8 vCPU 는 **관례값이 아니다**(§0)

## 3. 이 라운드는 세 번 돌았다 — 앞의 둘이 버그를 하나 끄집어냈다

| 판 | 결과 | 원인 |
|---|---|---|
| 1차 | 🔴 스윕 전 정지 | 계정 64개를 만들다 **429** — 인증 레이트리밋(IP당 60초 60건)에 걸렸다. 버림 블록 게이트가 «표본을 못 만들었다» 며 멈췄다 |
| 2차 | 🔴 표는 나왔으나 전 팔 게이트 파손 | 409 가 iteration 수와 **같았다.** 계정 32개가 **전부** 갇혔다 |
| 3차 | ✅ 이 표 | 위 둘을 고치고 다시 |

2차의 원인이 [**#528**](https://github.com/Shadowfit/init/issues/528) 이다 —
`exercise_servicer.py:384` 의 `NameError: name 'judged' is not defined` 로 **StopAnalysis 가 통째로 죽어**
완결 콜백이 영영 안 왔다. 판정 프레임 0 이거나 **가시성 스킵이 한 번이라도 있는** 세션이면 걸리므로,
실사용에서도 *"운동을 끝냈는데 다음 운동을 못 시작한다"* 로 나타난다. 고침은 [#529](https://github.com/Shadowfit/init/pull/529).

**고침 뒤 같은 무대에서 `session_transitions{source="ai-callback",status="COMPLETED"} = 16,877`** —
콜백이 정상적으로 돈다는 확인까지 이 라운드에서 났다(outbox 적체 0 · 서킷 닫힘).

## 4. 판정은 사용자 몫

이 표는 **사실**이고, *"§4-2 의 목표를 현황으로 승격할 것인가"* 는 결정이다.
결정 전에 같이 볼 것: 무대가 8 vCPU 라는 점(§0), ×360 이 못 간 이유가 rig 의 천장이라는 점(§1-2),
그리고 이 판이 **세션 길이를 모사하지 않는다**는 점(§2-1).
