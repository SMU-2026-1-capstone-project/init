### 읽는 법

- **`success`가 거의 항상 `concurrency`와 같다** — 즉 그 동시성 레벨의 5판(+버림 1) 중
  **딱 한 판만 성공**하고 나머지는 전부 `rpcerror:UNAVAILABLE`로 즉시(p50 0.4~0.6ms) 실패한다.
  동시성 20(23/100)·30(60/150=30×2)·50(100/250=50×2)만 예외적으로 한두 판 더 성공했다.
- **p50은 작은데 평균·최대가 폭발한다** — 대부분은 즉시 실패(빠른 UNAVAILABLE)하고, 극소수가
  수십~수백 초, 심하면 **21분**을 끌다 실패한다. 이게 평균·p95·최대를 전부 밀어올린다.
- **서버 로그에 5분짜리 완전 정적 구간이 있다** — `reattach_ai.log` `12:54:23,465` →
  `12:59:17,819` 사이 **294초 동안 로그 한 줄도 없음**. 그런데 서버 시작 로그
  (`gRPC 서버 백그라운드 스레드 시작` · `ShadowFit AI gRPC Server 시작`)는 파일 맨 앞에 **한
  번뿐**이다 — 프로세스가 죽었다 재시작된 게 아니라, **떠 있는 채로 멈췄다.**

## 3. 이 판의 한계 (정직하게)

- **1대 1판, 반복 없음** — EC2 라운드 자체가 1회뿐이다. "매번 이렇게 재현되는가"는 안 쟀다.
- **클라이언트·서버가 같은 프로세스(같은 asyncio 부모)** — 스크립트 설계 자체가 그렇다
  (`boot()`가 서버를 서브프로세스로 띄우고 스윕 클라이언트는 부모에서 돈다). 서버가 CPU를
  포화시키면 클라이언트 자체도 OS 스케줄링에서 굶을 수 있어, 관측된 지연이 "서버가 못 답한
  시간"인지 "클라이언트가 시간을 못 잰 시간"인지 이 판만으로는 분리가 안 된다.
- **294초 정적 구간 동안 무엇이 멈춰 있었는지 직접 계측 안 됨** — 스레드 덤프·`py-spy` 없음.
- **박스 보정값**([`ai_venv_conditions.txt`](./ai_venv_conditions.txt) 하단)은 걷었지만 이
  판의 이상현상과 직접 대조하지 않았다(정상 판이었다면 참고용, 문제가 있다면 무관).
