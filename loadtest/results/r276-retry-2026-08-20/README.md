# #276 후속 — 재시도를 실측으로 (로컬, 2026-08-20)

이슈 [#276](https://github.com/Shadowfit/init/issues/276) 에 올라간 재시도 표는 전부 **계산**이었다 —
p 하나를 상수로 놓고 `p^(n+1)`. 실제로 재시도를 붙여 돌리고 유도와 대조한 판이다.

- 생성 표: [`summary.md`](./summary.md) · 원자료: [`raw.tsv`](./raw.tsv) · rig: [`../../measure_r276_retry.sh`](../../measure_r276_retry.sh)
- 팔 = **최대 재시도 0·1·2·3** × 4블록(첫 블록 버림) = **16판** · 라틴 방격 · **그 외 에러 0**
- 워커 8 · 워커당 논리요청 40 · 문당 행 25 · 재시도 **간격 0**(즉시)
- 🔴 mysql CLI 는 문당 재시도를 못 해서 `SQLSTATE '40001'` 핸들러를 가진 **저장 프로시저**로 돌렸다.
  각 INSERT 는 autocommit 이라 데드락이 나면 그 문만 롤백된다 — 재시도가 안전한 단위다.

## 0. 한 줄

🔴 **유도가 크게 틀렸다 — 그런데 «낙관» 이 아니라 «비관» 쪽으로다.**
1회 재시도의 실측 잔여 실패율은 **3.8%** 인데 유도값은 14.3% 였다(**약 4배 차이**).
**2회면 0.0%** 다. rig 머리말에 미리 박아둔 세 판정선 중 **「중복으로 접히는 경로가 이긴다」** 가 나왔다.

## 1. 실측 ↔ 유도

| 최대 재시도 | **실측 잔여 실패율** | 유도(`p^(n+1)`, p=0.378) | 요청당 실제 시도 |
|---|---|---|---|
| **0** | **37.8%** | 37.8% (기준선) | 1.00 |
| **1** | **3.8%** | 14.3% | 1.25 |
| **2** | **0.0%** | 5.4% | 1.20 |
| **3** | **0.0%** | 2.0% | 1.30 |

판별 3판의 산포: 0 → 33.1·37.8·40.9% · 1 → 1.6·3.8·7.5% · 2 → 0.0·0.0·0.3% · 3 → 전부 0.0%.

---

## 2. 왜 유도보다 좋은가 — 두 번째 시도는 대개 «중복» 이다

앞 라운드가 *"두 힘이 반대 방향이고 어느 쪽이 이기는지는 안 쟀다"* 라고 적어둔 자리다.
그 두 힘은 이랬다:

| 힘 | 방향 | 이 판의 결과 |
|---|---|---|
| 재시도가 동시성을 올린다 | 불리 | **작았다** — 요청당 시도가 1.25~1.30 에 그친다(30% 증가) |
| 두 번째 시도는 중복이 되어 접힌다 | 유리 | **이겼다** — 실측이 유도의 1/4 |

데드락으로 죽은 쪽이 다시 던질 때쯤이면 **상대 트랜잭션은 이미 커밋돼 있다.** 그러면 그 행은
`ON DUPLICATE KEY UPDATE` 로 접히고, [원 라운드 §2-ㄱ](../r276-deadlock-2026-08-20/README.md)
에서 본 대로 **접히는 경로는 데드락이 0%** 다.

숫자로도 보인다 — 첫 시도 실패율이 37.8% 인데, **첫 시도가 실패한 요청이 두 번째에도 실패할
조건부 확률은 3.8 / 37.8 = 약 10%** 다. 첫 시도의 1/4 이하로 떨어진다. 유도는 이 둘을
**같은 p** 로 놓았고, 거기서 어긋났다.

## 3. 구현에 주는 함의

- **재시도 1회로 37.8% → 3.8%**, **2회면 0.0%.** 3회는 이 조건에서 얻는 게 없다
- **비용이 싸다** — 요청당 시도가 1.2~1.3 이니 DB 일이 20~30% 늘 뿐이다
- 🔴 **다만 이건 「이 동시성에서」다.** [워커 스윕](../r276-worker-sweep-2026-08-20/README.md) 이
  p 가 동시성의 함수임을 보였다(w=16 이면 p=0.60). **더 높은 동시성에서 같은 2회로 0% 가 되는지는
  안 쟀다** — 이 판은 w=8 하나다
- 여전히 **동시성을 낮추는 쪽이 근본**이다(w=2 면 재시도 없이도 1.2%). 재시도는 그 위에 얹는 그물

## 4. 🔴 미검증 · 말하면 안 되는 것

1. **재시도 간격 0 이다.** 백오프를 넣으면 결과가 달라진다 — 지연이 붙으면 상대가 커밋할 시간이
   더 생겨 **더 좋아질 수도** 있고, 요청이 길게 살아남아 동시성이 올라 **나빠질 수도** 있다. 안 쟀다.
2. **DB 안에서 재시도했다.** 실제 구현은 앱(Spring) 쪽이라 재시도마다 **왕복이 하나 더** 붙는다.
   데드락 비율에는 영향이 없겠지만 **지연과 동시성 프로필은 다르다.**
3. **프로시저 오버헤드가 붙었다.** 팔 간에는 공통이라 상쇄되지만, 앞 스윕의 생 INSERT 값
   (p=0.4219)과 **직접 비교하면 안 된다.** 이 판의 기준선은 자기 팔 0(37.8%)이다.
4. **동시성 한 점(w=8)만 봤다** — §3 의 마지막 항목.
5. **「0.0%」는 «0 건» 이지 «불가능» 이 아니다.** 팔 2 는 유효 3판에서 1건이 났다(0.3%).
6. 앞 라운드들의 한계는 그대로 딸려 온다 — 로컬 2코어 동거 · payload 축소 · gRPC 경로 아님.
