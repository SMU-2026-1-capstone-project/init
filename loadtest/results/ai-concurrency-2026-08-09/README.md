## 0. 한 줄 요약

**추정의 두 전제가 다 틀렸는데, 서로 반대 방향이라 결론의 자릿수는 안 바뀌었다.**

| | 추정(구) | 실측 |
|---|---|---|
| 클라 전송 fps | 10fps | **~3fps** |
| MediaPipe 프레임당 | 20~50ms | **103.4ms** |
| 동시 세션 | 4코어 ≈ 6~8 | **물리 2코어에서 ≈ 6** (→ 4물리코어 ≈ ~12) |

DAU 1,000 의 피크 동시 ~67세션 대비 **여전히 5~10배 부족**하다. 원래 지적이 유효하고,
이제 근거가 추정이 아니라 실측이다.

**그리고 측정 도중 별건이 나왔다** — [#164](https://github.com/Shadowfit/init/issues/164).
동시 세션이 한 스레드를 공유하면 서로의 트래킹을 깨뜨려 **프레임이 버려진다.** 처리량이 아니라 품질 문제다.

## 1. 이 환경에서 무엇을 잴 수 있는가

이 장비는 i3-6100(**물리 2코어** + HT, 컨테이너에는 논리 4로 보임)이라 «동시 N세션» 절대값이 안 나온다.
그래서 셋으로 나눠 쟀다.

| | 무엇 | 왜 |
|---|---|---|
| **[A]** | 단일 스레드 · 같은 사람 연속 | 트래킹이 유지될 때의 프레임당 비용(바닥값) |
| **[B]** | 단일 스레드 · 다른 사람 번갈아 | 트래킹이 깨질 때 — 스레드 로컬 검출기 가설 |
| **[C]** | 동시 스레드 1·2·4·8 | 처리량 포화 지점 (**유도가 아니라 직접 측정**) |

⚠️ **시간(ms)은 이 CPU 에 묶인다.** 코어 «개수» 와는 무관하지만 «속도» 에는 비례하므로,
103.4ms 를 서버 사양에 그대로 옮기면 안 된다. 옮겨 쓸 수 있는 것은 **[C] 의 포화 곡선 모양**과
**[B]/[A] 비율**이다.

## 2. 결과

### 2-1. [A] 프레임당 추론 비용 — 추정의 2~5배

| 구성 | n | 평균 | p50 | p95 | 최대 |
|---|---|---|---|---|---|
| 같은 사람 연속 | 160 | **103.4ms** | 100.5 | 129.1 | 163.3 |

`model_complexity=1`. 검출률 20/20, 무릎 visibility 0.848.

### 2-2. [B] 트래킹이 깨지면 «느려지는» 게 아니라 «버려진다»

| | 검출률 |
|---|---|
| 사람0~3 을 **각각 단독** 실행(전용 검출기) | 20/20 · 20/20 · 20/20 · 20/20 |
| 같은 검출기에 **번갈아** 입력 | **11/20** |

| 구성 | 평균 | p50 | p95 | 최대 |
|---|---|---|---|---|
| 다른 사람 번갈아 | 123.6ms | 108.6 | 196.1 | 221.9 |

시간 비용은 **1.19x** 로 미미하다. 대가는 시간이 아니라 **버려지는 프레임 45%** 다. → [#164](https://github.com/Shadowfit/init/issues/164)

### 2-3. [C] 동시 스레드 포화 — 논리 4코어인데 1.73배가 천장

| 스레드 | 총 처리량 | 스레드당 평균 | 1스레드 대비 |
|---|---|---|---|
| 1 | 10.6 fps | 77.8ms | 1.00x |
| 2 | 13.3 fps | 117.9ms | 1.26x |
| **4** | **18.3 fps** | 165.1ms | **1.73x** |
| 8 | 17.4 fps | 323.1ms | 1.64x (역행) |

**물리 2코어 + 하이퍼스레딩이 그대로 드러난다.** 8스레드에서는 오히려 떨어진다.

### 2-4. 동시 세션 유도

실제 클라는 **~3fps** 다 — `frontend/app/(tabs)/exercise.tsx:150` 이 `intervalMs = 330`,
ai-server 도 `session_state.py:47` 에서 `MIN_FRAME_INTERVAL_SEC = 0.300` 으로 상한을 건다(#143).

**직접 측정된 값** (유도 아님):

> 이 장비(물리 2코어) 총 처리량 **18.3 fps ÷ 3fps ≈ 동시 6세션**

코어 선형 가정 시 4물리코어 ≈ **~12세션**. 문서의 «4코어 ≈ 6~8» 과 같은 자릿수이고 약간 낙관적이다.

## 3. 🔴 이 측정이 두 번 막혔다 — 둘 다 «다른 것을 잴 뻔한» 것이었다

### 3-1. 콜드 상태에서 어려운 자세는 검출이 실패한다

1차 실행이 «20프레임 중 1개 검출 실패» 로 중단됐다. 추적해보니 **같은 `squat=1.0` 이미지가
맨 처음엔 실패, 맨 마지막엔 성공**했다. 트래킹이 없는 콜드 상태에서는 사람 탐지기가 완전히 앉은
자세를 못 잡고, 쉬운 자세로 트래킹이 잡힌 뒤에는 같은 이미지도 잡는다.

실제 세션은 **서서 시작**하므로 프레임 순서를 그렇게 바꿨다. 다만 이건 픽스처 이슈가 아니라
**파이프라인 특성**이라 #164 곁가지로 남겼다 — 재부착(`ReattachAnalysis`)으로 세션 도중에 붙는
경우는 확인이 필요하다.

### 3-2. «다른 사람» 4개 중 3개가 단독으로도 검출 0/10 이었다

2차 실행이 «[B] 20프레임 중 16개 검출 실패» 로 중단됐다. **이걸 그대로 결과로 냈으면
«트래킹 깨짐으로 80% 손실» 이라고 발표했을 것이다.** 갈라보니:

| | 검출률 |
|---|---|
| 사람0 (x_shift −0.28, scale 0.75) | 20/20 |
| 사람1 (+0.28, 1.00) | **0/20** |
| 사람2 (−0.05, 0.85) | **0/20** |
| 사람3 (+0.10, 0.65) | **0/20** |
| 대조: 위치 고정, 배경·살색만 변화 | 20/20 |

**트래킹이 아니라 픽스처가 문제였다.** x_shift×scale 격자를 쓸어 검출 지도를 만들고
(`x_shift=-0.30` 은 전 구간 실패) 검출되는 칸에서만 다시 골랐다.

그래서 스크립트에 `verify_standalone()` 을 상시 전제로 박았다 — **각 «사람» 이 단독으로 100% 검출됨을
매 실행마다 확인하고, 아니면 중단한다.** 이 확인 없이는 [B] 의 실패를 «번갈아 넣은 탓» 으로
귀속할 수 없다.

> 📌 오늘 «조용히 다른 것을 재는» 도구를 세 번 봤다(#139·#140·#153). 이번엔 **내가 그걸 만들 뻔했고,
> 실행 전 가드가 막았다.** 가드가 없었으면 존재하지 않는 결함을 이슈로 등록했을 것이다.

## 4. ⚠️ 한계

- **합성 이미지로 쟀다.** 사람이 찍힌 픽스처가 repo 에 없어서 인체 비율로 그린 도형을 썼다.
  랜드마크 모델은 고정 해상도 CNN 이라 **연산량은 사진 내용과 무관**하므로 [A] 의 시간은 신뢰할 만하지만,
  **검출 난이도는 실제 카메라 프레임과 다를 수 있다.** [B] 의 45% 는 특히 그렇다.
- **[B] 는 최악의 경우다.** 매 프레임마다 사람을 바꿨다. 실제 피해량은 스레드풀 배정에 달려 있고
  **실제 동시 세션으로 재현하지 않았다.**
- **HTTP 를 안 탔다.** 컨테이너 안에서 `detect()` 를 직접 불렀다. base64 디코딩·FastAPI·네트워크가 빠져 있어
  실제 엔드투엔드는 이보다 느리다. (2코어 장비에서 부하 생성기를 같이 돌리면 무엇을 재는지 알 수 없어져
  일부러 뺐다.)
- **시간 절대값은 이 CPU 에 묶인다.** 위 §1 참조.
