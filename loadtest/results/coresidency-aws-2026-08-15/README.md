### 2-4. ⭐ 從 R5 — 메모리 유도식의 «공식 밖 몫» ([#229](https://github.com/Shadowfit/init/issues/229))

**이 라운드의 가장 값나가는 산출물이다.** 검출기 풀의 상한 공식이 «검출기만» 세고
*"프레임 버퍼·base64 임시·파이썬 힙·gRPC 는 미측정이라 안 뺐다"* 고 코드가 스스로 경고하는데,
**그 몫을 처음 쟀다.**

AI 컨테이너 RSS 최대(팔 A·B 평균, 판 3개씩):

| 세션 N | 실측 (MiB) | 공식 (MiB)¹ | 차이 | 세션당 실측 |
|---:|---:|---:|---:|---:|
| 20 | 2,780 | 1,978 | **+802** | 139.0 |
| 40 | 5,014 | 3,860 | **+1,154** | 125.4 |
| 80 | 9,301 | 7,624 | **+1,677** | 116.3 |
| 160 | 17,758 | 15,151 | **+2,607** | 111.0 |

¹ `memory_ceiling()` 의 `100.5MB + 98.7MB×N` 을 MiB 로 환산(95.8 + 94.1×N)

최소자승 적합 (잔차 ±62 MiB):

```
실측 RSS(MiB) ≈ 708 + 106.74 × N        (공식: 95.8 + 94.1 × N)
              고정 +612          세션당 +12.6
```

**그래서 공식은 용량을 과대평가한다.**

| | 20,000 MiB 한도에서 |
|---|---|
| 공식이 허용하는 세션 수 | **212** |
| 실측 적합이 한도에 닿는 세션 수 | **181** |
| N=201(공식 상한 부근)의 실측 예상 | **22,163 MiB = 한도의 111%** |

→ **공식대로 풀을 열면 181세션에서 이미 한도인데 풀은 212까지 받는다.** #229 가 *"풀이
거절하기 전에 컨테이너가 OOM 으로 죽는다"* 고 적은 시나리오가 **숫자로 확인됐다** — 약 31세션,
17% 의 초과 수용이다.

⚠️ **여유분의 «값» 은 아직 정하지 않는다.** 이 문서는 관측을 적는 데까지다
([[feedback_no_arbitrary_threshold_values]]). 다만 이제 근거가 있으므로
`docker-compose.prod.yml`·`.env.example`·`19-deployment.md` 의 «경고만» 상태를 닫을 수 있다.

⚠️ 실측 조건: **x86 c7i.4xlarge · 판 끝 최대값 · 판마다 AI 재기동**. 기본 RSS 100.5MB 는
M2 실측값이라 x86 미검증이었는데, 적합 절편 708 MiB 는 **그보다 크다** — 다만 절편에는
«세션 0 상태의 RSS» 와 «세션 수에 안 비례하는 오버헤드» 가 섞여 있어 갈리지 않았다
(N=0 판을 안 돌렸다).

## 4. 🔴 못 읽는 것 — 이 라운드가 #245 이전이라서

### 4-1. 라틴 방격이 없다 → 팔 C 의 하락을 «캡 효과» 라고 못 읽는다

스윕이 팔을 **블록으로** 돌았다(A 13판 → B 13판 → C 13판). 팔 C 가 **항상 마지막**이라
«캡 효과» 와 «시간이 흐르며 생긴 것»(EBS 버스트 크레딧·테이블 성장·열)이 같은 축에 겹친다.
4차 풀 사이징이 순서를 뒤집자 부호가 바뀐 전례가 있다([#245](https://github.com/Shadowfit/init/pull/245) ①).

> 📌 **단 §2-3 의 «캡에 정확히 붙었다»(798.8% ≈ 800%)는 순서로 설명되지 않는다.**
> 그건 기전이 보이는 관측이라 교락의 영향이 작다. 교락에 걸리는 것은 **«그래서 처리량이
> 16% 내려갔다» 쪽**이다.

### 4-2. `stats` 와 요청 표가 다른 시간축에 있다 → 포화 구간을 정확히 못 자른다

`stats_*.tsv` 는 epoch, `req_*.tsv` 는 t0 기준 상대초라 사후 정렬이 안 된다([#245](https://github.com/Shadowfit/init/pull/245) ③).
§2-3 의 CPU 값은 **판 전체 샘플의 중앙값**이라 세션 준비 구간이 섞여 있다
(그 구간엔 Spring 이 최대 95~121% 까지 튄다 — 계정·세션 생성). 중앙값이라 측정 구간이
지배하지만, **«포화 순간의 귀속» 은 이 데이터로 정확히는 못 만든다.**

### 4-3. 🔴 부하기가 천장이었을 가능성을 못 배제했다

160세션에서 목표 480 fps 중 291 만 나왔는데, **부하기는 c7i.large(2 vCPU)** 다.
그 박스의 CPU 는 **이 라운드가 기록하지 않았다**(`docker stats` 는 대상 박스만 본다).

- 80세션(240 fps)까지는 목표를 100% 냈다 → 240 fps 까지는 부하기가 버텼다
- 291 이 «대상의 천장» 인지 «부하기의 천장» 인지는 **이 데이터로 안 갈린다**

⚠️ **이게 갈리지 않으면 §0 의 «97세션» 이 통째로 흔들린다.** 정식 라운드에서 부하기 CPU 를
같이 걷어 닫아야 한다. (16 vCPU 중 AI 가 9.4 만 쓰고 남는다는 §0 의 관측과 같은 뿌리다)

### 4-4. 그밖에

- **격자가 4개** — 천장이 80~160 사이인데 그 안에 점이 없다
- **N=0 판이 없다** — §2-4 적합의 절편에서 «기본 RSS» 와 «고정 오버헤드» 가 안 갈린다
- **`detect_pct` 분모에 `nolease` 가 섞인다** — 이 라운드는 둘 다 0/100% 라 영향이 없었다
