## 3. 왜 어긋나 보였나 — 경로가 원래 비동기다

통보를 기록하는 것은 **스케줄러가 아니라 아웃박스 발행기**다([#98](https://github.com/Shadowfit/init/issues/98)):

```
타임아웃 스윕 → 세션 FAILED + 같은 트랜잭션에 OutboxEvent.stopAnalysis 적재
             → OutboxPublisher (batch-size 20 · poll 1s fixedDelay) 가 나중에 흘린다
             → 그때 ExerciseAnalysisService.stopAnalysis 가 지표를 올린다
```

### 3-1. 🟢 원 실측의 숫자가 그대로 맞아떨어진다

| | 건수 | 창(초) | 건/초 |
|---|--:|--:|--:|
| 원 실측 (1,000 판) | 280 | 69 | **4.06** |
| 이 판 (200) | 200 | ≈45 | **4.4** |

두 값이 사실상 같다. 즉 **「71% 유실」이 아니라 「그 창이 ~4건/초 × 69초 만큼만 담았다」** 였다. 원 문서가 마지막에 *"「71%가 유실된다」가 아니라 「71%가 그 창 안에 기록되지 않았다」가 정확한 서술"* 이라고 조심해 적어둔 것이 **맞았다.**

### 3-2. 「10개에서만 1:1」도 설명된다

`batch-size` 가 **20** 이라 10건은 **배치 하나**에 다 들어간다. 100·1,000 에서만 어긋난 것은 그 경계 때문이다.

## 4. 🟢 소화율이 설정값의 1/4.5 인 이유 — **fsync 다** (2026-08-23 추가 실측)

초판은 이 절을 «원인 미규명 · 후보 셋» 으로 남겼다. **갈랐다.**

### 4-1. 잰 것

| 측정 | 값 | 뜻 |
|---|--:|---|
| 아웃박스 이벤트 간 **중앙값 간격** | **181 ms** | 로그 201줄의 간격 분포(0.5초 미만 185건, 평균 188ms) |
| AI 쪽 `StopAnalysis` 처리 | **2.75 ms** (p90 9.0) | 컨테이너 안에서 30회 직접 호출. **범인이 아니다** |
| **이 박스의 단일 세션 커밋 지연** | **174.42 ms** | 한 세션에서 200회 UPDATE, `flush_log_at_trx_commit=1` · `sync_binlog=1` |

**이벤트당 비용 ≈ 커밋 한 번**이다. 나머지(gRPC 3ms, 앱 로직)는 노이즈다.

`session-missing` 분기가 `failSessionFast` 를 부르지만 **쓰기는 안 일어난다** — 세션이 이미 스윕에서 FAILED 라 `failIfInProgress` 가 저장 없이 반환한다(코드 확인). 그래서 이벤트당 쓰기 커밋은 **아웃박스 상태 갱신 1회**뿐이다.

### 4-2. 산수가 정확히 맞는다

```
속도 = batch / (batch × 커밋지연 + poll)
     = 20 / (20 × 0.1744 + 1)
     = 20 / 4.488  =  4.46 건/초        (실측 4.4)
```

**「1/4.5」의 4.5 는 곧 이 주기(4.488초)다** — 우연히 같은 숫자가 아니라 **같은 수**다. 설정값 「초당 20」은 **커밋이 공짜일 때**의 수였다.

### 4-3. 🔴 함의 — 그룹 커밋을 못 받는다

이 박스는 동시 부하에서 **231~649 RPS** 를 낸다(4차 라운드). 여기선 **4.4건/초**다. 40~150배 차이의 이유는 **직렬**이기 때문이다 — 동시 커밋은 group commit 으로 fsync 를 여럿이 나눠 지는데, 발행기는 한 스레드로 한 건씩 돌아 **분모가 1**이다.

즉 **«배치 크기를 늘리면 빨라진다» 가 아니다.** 직렬인 한 상한은 `1 ÷ 커밋지연 ≈ 5.7건/초`이고, `batch-size` 를 200으로 올려도 그 위로 못 간다. **레버는 동시 발행이거나 내구성 완화**이지 배치 크기가 아니다.

🔴 **어느 쪽도 채택 제안이 아니다** — 동시 발행은 lease·순서 보장과 얽히고, 내구성 완화는 [4차 라운드가 «안 아픈 것을 고치며 데이터 안전을 판다» 로 이미 기각](../../../docs/decisions/db-portfolio-roadmap.md)한 레버다.

## 5. 부수로 드러난 것 — 아웃박스는 `FAILED` 로 끝난다

행 200개가 `SENT` 가 아니라 **`FAILED`** 로 끝났다(3 → 3, 4 → 204).

**설계대로다** — AI 가 모르는 세션이라 `success=false` → `TERMINAL_FAILED` 분류이고 재시도 없이 한 번에 끝난다(`SessionService` 주석이 예고한 그대로). 🔴 다만 **「통보는 정상 기록됐는데 아웃박스는 FAILED」** 라는 조합이라, **아웃박스 FAILED 수를 「장애」로 읽으면 오독한다.**
