## 0. 한 줄

**`max_workers`를 5→10→20→40으로 8배 늘려도 처리량이 거의 안 바뀐다.** 전 구간(동시성
1~150) 에러 0건, 4개 값 모두 사실상 같은 곡선을 그린다 — 오히려 동시성이 아주 높을 때
(100·150)는 스레드를 더 준 쪽(20·40)이 살짝 **더 느리다.** 즉 **`max_workers=10`은
매직넘버가 아니지만, 위험한 값도 아니다** — 스레드풀 크기 자체가 이 시스템의 병목이
아니기 때문이다.

## 2. 읽는 법

- **처리량이 max_workers와 거의 무관하다** — 동시성 1~20 구간에서 4개 값 전부
  **초당 90~130건** 대에 몰려 있다. 스레드를 5개만 줘도 40개를 줘도 비슷하다.
- **동시성 30은 유일하게 값별 차이가 뚜렷한 지점이다** — mw5(78/s) < mw10(82/s) <
  mw20(91/s) < mw40(97/s), 스레드 수가 늘수록 나아진다. 이건 이론과 맞는다 — 동시성
  30이 mw5·mw10보다 크므로(5·10 < 30) 대기열이 생기고, mw20·mw40(20·40 ≥ 30)은
  대기 없이 바로 처리돼서다.
- **동시성이 스레드 수를 훨씬 넘어서면(100·150) 스레드를 더 준 쪽이 오히려 느리다** —
  mw40이 100에서 **가장 느림**(59/s, 4개 중 최저). 스레드가 남아도는데도 도움이
  안 되고, 오히려 동시에 뜬 스레드 수가 많을수록(컨텍스트 스위칭·자원 경합 추정)
  약간 손해로 보인다.
- **종합하면**: 스레드풀이 "충분히 크기만 하면"(제공된 동시성 이상이면) 대기열
  문제는 없어지지만, **그 이상으로 계속 키운다고 처리량이 느는 게 아니다.** 진짜
  천장은 스레드풀 밖의 무언가(CPU 바운드 작업 자체, GIL 직렬화 등 — 이전
  `per-process-ceiling-cause.md`가 AI 워커 프로세스 레벨에서 확인한 것과 같은
  메커니즘일 가능성)다.

## 3. #593 최종 판정

| 물음 | 답 |
|---|---|
| `max_workers=10`이 매직넘버(근거 없는 값)인가 | 🟡 **근거는 여전히 없었다** — 하지만 실측해보니 **해롭지도 않다**. 5·20·40과 비교해 눈에 띄게 나쁘지 않다 |
| 스레드를 늘리면 처리량이 느는가 | 🔴 **아니다.** 20·40이 5·10보다 나은 구간(동시성 30 근처)도 있지만, 아주 높은 동시성(100)에서는 오히려 더 나쁘다 |
| 그럼 몇으로 정해야 하나 | ⚪ **이 판은 "정한다"가 아니라 "스레드 수는 안 중요하다"까지만 답한다.** 10을 유지해도, 20으로 올려도 실질적 차이가 미미하므로 굳이 바꿀 근거가 약하다 — 바꾸려면 이 데이터가 아니라 다른 이유(예: 스레드 개수 자체의 메모리·컨텍스트 비용)가 있어야 한다 |
| 처리량 천장(~90~100/s)의 진짜 원인은 뭔가 | ⚪ **여전히 미확정.** 4개 값이 전부 비슷한 천장에 붙는다는 것 자체가 "스레드풀이 원인이 아니다"의 증거이지, 그럼 뭐가 원인인지는 이 판이 안 갈랐다 — 스레드별 CPU 분해가 다음 단계다 |

**결론: `max_workers=10`을 바꿀 실측 근거는 없다.** 이슈가 원래 걱정한 "매직넘버라서
위험할 수 있다"는 걱정은 **이 4종 비교로 충분히 해소됐다고 본다** — 닫을지는 판단 몫.

## 4. 남은 것

- 처리량 천장(~90~100/s)의 정체 — 스레드별 CPU 분해(`per-process-ceiling-cause.md`
  기법)를 이 gRPC 서버에 붙이면 GIL·MediaPipe 내부 스레드풀 중 무엇인지 가를 수 있다
- 동시성 12 근처의 이상값(이전 판)은 이번엔 **재현되지 않았다** — 그때 그 값은
  잡음이었다고 봐도 될 것 같다(4개 값 x 12동시성 = 48칸 중 이상값 없음)
