대상 코드: `ai-server/app/observability/frame_path.py` (커밋 `c35b7e0` / [#384](https://github.com/Shadowfit/init/pull/384))

> ([[project_loadtest_env_constraint]]). 이 판이 답하는 것은 **팔 사이의 상대 델타 하나**다.

## 0. 왜 이 판이 먼저인가

[#384](https://github.com/Shadowfit/init/pull/384) 가 붙인 계측은 **켜면 재려는 자원을 같이 쓴다** —
요청당 락 획득 4회 + 타임스탬프 6회이고, 그건 전부 **GIL 을 잡는 일**이다.

그래서 **「계측 ON/OFF」자체가 한 판의 팔**이다. 이 대가를 모르면 나중에 EC2 에서 받은
`wait`·`infer` 값이 **「경로가 그렇다」인지 「계측이 그렇게 만들었다」인지 못 가른다.**

## 1. 무대와 조건

| | 값 | 근거 |
|---|---|---|
| 팔 | **A = 계측 OFF** · **B = 계측 ON** | `FRAME_PATH_METRICS`. 다른 노브(`GIL_SWITCH_INTERVAL`)는 **0 으로 고정** — 이 판이 흔드는 것은 하나다 |
| 무대 | **AI 서버 단독** (MySQL·Spring 없음) | 2코어에 셋을 얹으면 **팔 간 차이보다 큰 잡음**이 든다 |
| 세션 열기 | **gRPC `StartAnalysis` 직접 호출** | Spring 이 하던 일과 같다. `pose.py:69` 의 `lease_detector` 가 요구하는 자리가 그렇게 생긴다 |
| 세션 수 | **8** (검출기 ~790MB) | 풀은 12 로 띄운다 |
| 프레임 | 합성 스쿼트 30장 (`../coresidency-2026-08-15/frames.json`) | 무릎 85~124° — **rep 이 안 생긴다.** Spring 콜백도 없다 |
| 유입 | **6 fps × 8세션 = 48 fps 요구** | 상한(300ms)이 절반을 `RATE_LIMITED` 로 가르지만 **그 프레임도 추론은 다 한다**(상한은 판정 **앞**에서 자른다) |
| 판 | **버림 1 + 본판 8** — `B · A B B A · B A A B` | 팔당 4판 · 앞뒤 위치 합이 같다 |
| 판 길이 | 40초 (+ 앞 5초는 표에서 버림) | 검출기 **지연 생성**이 앞 몇 초를 먹는다 |

### 1-1. 🔴 재시작이 조작 변수에 섞인다 — 없앨 수 없어서 «양쪽에 똑같이» 물렸다

`FRAME_PATH_METRICS` 는 **기동 시** 미들웨어를 붙일지 정한다. 팔을 바꾸려면 재시작이 강제되는데,
**재시작은 그 자체로 결과를 −24% 흔든다**(설계 §9-4). 그래서 **두 팔 다 매판 재시작**하고,
순서 효과가 팔에 얹히지 않도록 위치를 맞췄다([[feedback_measure_design_needs_repeats]]).

**이 판이 못 가르는 것**: 「계측 ON 의 대가」와 「그 판이 어쩌다 느린 재시작을 만난 것」.
위치 균형이 **평균에서는** 그걸 상쇄하지만, 판 간 산포가 델타보다 크면 **판정 불가**로 적는다.

## 4. 스모크에서 이미 나온 것 (4세션 · 미포화 · 참고값)

본 판 전에 연쇄를 확인하려고 돌린 10초 판이다. **조건이 다르므로 판정 근거가 아니다.**

| 구간 | p50 (ms) | p95 (ms) |
|---|---:|---:|
| `wait` | 1.197 | 4.201 |
| `decode` | 1.187 | 3.117 |
| **`lease`** | **0.017** | 0.031 |
| **`infer`** | **37.728** | 65.318 |
| `post` | 1.379 | 3.654 |
| `respond` | 0.522 | 1.476 |
| `total` | 42.499 | 71.573 |

- **`lease` 가 전체의 0.04%** — 후보 2순위(검출기 획득 경로, 설계 §10-2)가 **이 조건에서는** 안 보인다.
  ⚠️ §10-2 가 의심한 것은 「세션이 많을 때 리스 지점 직렬화」라 **4세션 판이 그걸 반증하지 않는다.**
- `handler_concurrency` = `{1:100, 2:64, 3:49, 4:12}` — **분포가 실제로 찍힌다.**
  「~9」를 산술 추론이 아니라 직접 값으로 대체할 준비가 됐다(단 그 값은 **EC2 에서** 나와야 한다).
- `partial: 0` — 조기 반환 없이 전 구간이 찍혔다. contextvar 가 threadpool 경계를 넘는다는 실물 확인.

## 5. 정직하게 비어 있는 것

- 🔴 **로컬 물리 2코어다.** 「346 RPS 에 9.5 vCPU」가 나온 조건(16 vCPU)과 **다른 무대**다.
  이 판은 «계측의 대가» 만 답하고 **병목 원인은 답하지 않는다**
- 🔴 **다른 Claude 세션이 같은 박스에 붙어 있다**([[project_concurrent_sessions]]). 그 세션의 작업이
  CPU 를 물면 특정 판만 느려지는데, 위치 균형은 **평균**을 지킬 뿐 그 판을 못 걸러낸다
- **구성 비율이 실사용과 다르다** — 6fps 라 절반이 `RATE_LIMITED` 로 갈린다. 그 갈래는
  분석·직렬화(`post`)를 건너뛰므로 **`post` 구간의 비중이 실사용보다 작다.**
  두 팔이 같은 비율을 보므로 **대조는 성립**하지만, **구간 절대값을 실사용으로 인용하면 안 된다**
- **rep·적재·리포트 경로는 안 탔다** — 합성 인체가 rep 문턱을 못 넘는다
- **`GIL_SWITCH_INTERVAL` 은 안 흔들었다** — 그건 별개 판이다(설계 §12 셋째 줄)
