## 1. 천장 — 동거 천장은 약 346 RPS, 캡을 걸면 312 RPS

| 세션 | A (유휴) | B (옆 일함) | C (B+캡) |
|---:|---:|---:|---:|
| 20 | 60.0 | 60.0 | 60.0 |
| 60 | 179.9 | 179.9 | 179.9 |
| 100 | 299.7 | 299.8 | 299.8 |
| **120** | **344.5** | **345.5** | **311.7** |
| **160** | **348.1** | **346.1** | **312.6** |

- 100세션까지는 세 팔 모두 **목표 RPS(3×세션)를 정확히** 낸다 — 천장이 아니다
- 120세션부터 갈린다. **A ≈ B ≈ 346** / **C ≈ 312**
- **옆이 일하는 것(A→B)은 천장을 거의 안 깎는다**: 348.1 → 346.1 (**−0.6%**)
- **캡은 깎는다**(B→C): 346.1 → 312.6 (**−9.7%**)

## 2. H3 — 캡이 «옆» 을 지키는가 → **아니다**

«옆» 은 ghz 가 때리는 Spring gRPC 경로다. #254 로 이번 라운드에 **처음으로** 이 지연을 걷었다
(08-16 두 라운드는 판정할 열 자체가 없어 H3 을 못 닫았다).

| 세션 | B p50 | C p50 | B p95 | C p95 | B p99 | C p99 | fail |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 20 | 8.8 | 9.0 | 10.2 | 10.5 | 11.1 | 11.3 | 0 |
| 60 | 8.7 | 8.5 | 10.0 | 10.3 | 11.2 | 11.7 | 0 |
| 100 | 8.2 | 8.5 | 9.8 | 10.2 | 10.9 | 11.7 | 0 |
| 120 | 8.3 | 8.5 | 9.5 | 9.9 | 10.7 | 12.5 | 0 |
| 160 | 8.3 | 8.6 | 9.6 | 10.2 | 10.7 | **12.7** | 0 |

**셋이 한꺼번에 읽힌다:**

1. **옆은 처음부터 안 아팠다.** AI 세션이 20→160 으로 **8배**가 되는 동안 옆의 p50 은
   8.2~8.8ms 로 **평평**하고 실패는 0이다. 지켜야 할 피해가 관측되지 않았다
2. **캡을 걸어도 옆이 좋아지지 않는다.** 오히려 전 구간에서 C 가 **미세하게 나쁘다**
   (160세션 p99 10.7 → 12.7)
3. **대가만 확실하다.** §1 의 처리량 −9.7% 에 더해, 100세션(둘 다 목표 RPS 달성 = 천장 아래)에서
   **AI 경로 p50 36.6 → 114.5ms (3.1배)** · p99 109.1 → 233.3ms

→ **H3 반증.** [#212](https://github.com/Shadowfit/init/issues/212)(컨테이너 CPU 한도 부재)의
전제 — 「캡이 없어서 서로 코어를 뺏는다」 — 가 **이 부하 수준에서는 성립하지 않는다.**

### 2-0. 캡은 실제로 물렸다 — 그리고 깎은 양이 아주 작다

`caps.tsv` 가 팔 C 의 적용값을 남겼다(#253 의 단언이 통과했다):

| 컨테이너 | NanoCpus | = |
|---|---:|---:|
| `shadowfit-ai` | 8,000,000,000 | **8 vCPU** |
| `shadowfit-backend` | 4,000,000,000 | 4 vCPU |
| `shadowfit-mysql` | 4,000,000,000 | 4 vCPU |

160세션에서 AI 컨테이너가 실제로 쓴 CPU(`stats_*`, 3판):

| 팔 | 평균 | **피크** |
|---|---:|---:|
| B (캡 없음) | 644.5 / 673.2 / 695.4 % | **944.6 / 927.5 / 947.0 %** (≈ **9.3~9.5 vCPU**) |
| C (캡 8) | 584.8 / 600.9 / 604.2 % | **829.0 / 830.4 / 829.6 %** (≈ **8.3 vCPU** — 캡에 딱 붙었다) |

🔴 **깎인 것은 약 1.2 vCPU 인데 처리량은 9.7% 빠졌다.** AI 는 캡 없이도 9.5 vCPU 에서 멈추지만,
그 위쪽 1.2 를 뺏으면 **거의 그대로 처리량이 준다** — 이 구간에서 AI 는 CPU-bound 다.

### 2-2. R6 과 붙이면 그림이 닫힌다

같은 날 같은 박스에서 [R6](../ai-scaling-aws-2026-08-17/README.md) 을 태웠다. **순수 추론만**
돌리면 이 박스는 **15.2 vCPU** 를 쓴다(16워커, CPU 피크 1517.6%). 그런데 **서비스 경로를 태우면
캡 없이도 9.5 에서 멈춘다**(위 표).

> **즉 AI 는 하드웨어가 모자라서 9.5 인 게 아니다.** R6 이 GIL·풀 크기·하드웨어를 전부 지웠으므로,
> 남은 것은 «추론 밖 · 동시성 하에서만 드러나는 직렬화» 다. **두 실험이 같은 자리를 가리킨다.**
> 무엇인지는 **아직 아무도 안 쟀다.**

### 2-3. §T — 「부하기가 천장」이 반증됐다. 346 은 **서버** 천장이다

08-16 라운드는 *"부하기가 천장"* 으로 끝났고, 08-17 리허설 회수 때도
*"「부하기가 병목이 아니다」는 아직 못 하는 말이다"* 로 남겨 뒀다(커밋 `cd5d9c6`).
**이제 할 수 있는 말이 됐다.**

부하기 코어를 **2개 ↔ 전체(4)** 로 흔든 12판(팔 B · 3쌍 · 레벨 120·160):

| 세션 | 부하기 2코어 | 부하기 전체 | 차이 |
|---:|---|---|---:|
| 120 | 345.4 / 345.6 / 346.1 | 346.2 / 346.8 / 347.0 | **0.3%** |
| 160 | 343.3 / 343.8 / 345.3 | 344.5 / 346.1 / 346.2 | **0.4%** |

지연도 같다(160세션 p50 456.8 ↔ 457.1). **부하기 코어를 절반 뺏어도 처리량이 안 변한다.**

확인 사살 — 부하기 자신의 CPU(`loader_*`, 160세션):

| 팔 | 평균 | 피크 | 상한 |
|---|---:|---:|---:|
| 2코어 | 47.0% | 102.5% | 200% |
| 전체 | 54.8% | 143.2% | 400% |

**2코어로 조여도 상한의 절반만 쓴다.** 포화 근처도 아니다.

→ **346 RPS 는 대상 박스(서버)의 천장이다.** 그리고 서버는 그 천장에서 **9.5 vCPU** 밖에 안 쓴다
(§2-0). 16코어 박스에서 **6코어가 논다.**

### 2-1. 🔴 이 판정의 범위를 좁혀서 읽을 것

- **옆의 부하가 약하다.** ghz 목표가 **19 RPS** 이고 달성도 19.0, 실패 0이다. 즉 «옆이 일한다» 는
  조건이 **옆을 아프게 할 만큼 세지 않았을 수 있다.** 「옆이 안 아팠다」는 **이 부하에서**의 사실이다
- **캡 값을 바꿔가며 재지 않았다.** 판정은 `AI=8 vCPU` **한 점**에서 나온 것이다(§2-0).
  캡을 9~10 으로 느슨하게 잡으면 −9.7% 가 줄어들 여지가 있고, 그건 안 재봤다.
  ⚠️ `AI_CPUS` 는 `MANIFEST.txt` 에 **없다** — 원본은 `coresidency/caps.tsv` 다
- **A 는 «AI 단독» 이 아니다**(#222). Spring·MySQL 이 같이 떠 있고 유휴일 뿐이라,
  A↔B 차이는 «서비스 경로 오버헤드» 가 아니라 «옆이 일하는 비용» 하나다
