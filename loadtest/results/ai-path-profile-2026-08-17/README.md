# AI 프레임 경로 프로파일 — 「서비스 경로가 비싸다」가 틀렸다 (2026-08-17, 로컬)

배경: [P6 2라운드 §4](../coresidency-aws-b-2026-08-16/README.md) ·
설계: [`../../../docs/decisions/ai-coresidency-capacity.md`](../../../docs/decisions/ai-coresidency-capacity.md) ·
탑승 목록: [`../../AWS-RIDE-ALONG.md`](../../AWS-RIDE-ALONG.md) 從-**R6·R7**

장비: **i3-6100(물리 2 / 논리 4)** · `model_complexity=1` · 합성 프레임 640×480(P6 rig `frames.json`)
⚠️ **절대 ms 인용 금지** — 2코어 박스이고 측정 중 IDEA·Chrome 이 CPU 를 100% 점유하고 있었다.
**옮길 수 있는 것은 비율뿐**이다.

---

## 0. 왜 쟀나

P6 2라운드가 **프레임당 27.6ms CPU** 를 관측했는데 순수 MediaPipe 추론은 **15.0ms**
([`ai-recalibrate-2026-08-11`](../ai-recalibrate-2026-08-11/README.md))다. **차이 12.6ms 를
아무도 안 쟀다.** 「base64 디코딩·JSON 직렬화가 비쌀 것」이 가설이었다.

**틀렸다.**

---

## 1. 단계별 — 추론이 95%, 나머지 전부가 5%

`app/api/endpoints/pose.py::detect_pose` 의 실제 단계를 그대로 쪼갰다(90회):

| 단계 | 벽시계 평균 ms | 비중 | CPU시간 평균 ms | 비중 |
|---|---:|---:|---:|---:|
| ① Pydantic 요청 파싱 | 0.01 | 0.0% | 0.00 | 0.0% |
| ② `base64_to_image` (b64decode + imdecode) | 0.95 | 2.7% | 0.69 | 1.8% |
| ③ `cv2.cvtColor` BGR→RGB | 0.20 | 0.6% | 0.52 | 1.3% |
| **④ MediaPipe `process()`** | **33.08** | **94.7%** | **37.67** | **95.6%** |
| ⑤ 랜드마크 33개 → Pydantic | 0.13 | 0.4% | 0.00 | 0.0% |
| ⑥ `analyzer.process_frame` | 0.29 | 0.8% | 0.17 | 0.4% |
| ⑦ `json.dumps` | 0.18 | 0.5% | 0.00 | 0.0% |
| ⑧ 응답 생성·직렬화 | 0.10 | 0.3% | 0.35 | 0.9% |
| **추론 밖 합계** | **1.86** | **5.3%** | **1.74** | **4.4%** |

**두 측정법이 일치한다.** 벽시계는 배경 부하에 오염될 수 있어 `time.process_time()` 으로
다시 쟀고, 결론이 안 바뀌었다 — 이 항목은 **AWS 로 옮겨도 안 바뀐다.**

📌 CPU시간 열의 중앙값이 전부 0 인 것은 Windows `process_time` 해상도가 ~15.6ms 라서다.
평균은 양자화됐지만 **편향은 없다**(작은 단계의 CPU 가 가끔 한 틱으로 잡힌다).

FastAPI 라우팅·미들웨어·응답까지 통과시킨 end-to-end(TestClient)는 중앙 **38.97ms** —
단계 합(34.94ms) 대비 **+4.0ms** 인데 여기엔 테스트 클라이언트 자신의 비용도 섞여 있다.
즉 **프레임워크 오버헤드의 상한이 4ms**다.

## 2. 그래서 12.6ms 는 경합이다

비율을 c7i 로 옮기면 (추론 15.0ms 기준):

| | ms/프레임 | 근거 |
|---|---:|---|
| 순수 추론 | 15.0 | `ai-recalibrate-2026-08-11` |
| 직렬 서비스 경로 | ~0.8 | 위 5.3% 비율 환산 |
| HTTP 프레임워크 | ≤1.7 | 위 end-to-end 상한 |
| **소계 (직렬)** | **~17.5** | |
| **P6 2라운드 실측 (동시 40스레드)** | **27.6** | [2라운드 §4](../coresidency-aws-b-2026-08-16/README.md) |
| **차 = 동시성 경합** | **~10 (37%)** | |

**프레임당 CPU 의 3분의 1이 «일» 이 아니라 «경합» 이다.**

### 2-1. 유력 가설 — GIL 이 정확히 1코어를 채운다 (미검증)

P6 2라운드에서 **40스레드가 in-flight 인데 AI CPU 는 8.69 vCPU**(16 중)였다. 즉 **31개
스레드가 CPU 를 안 쓰고 막혀 있었다** — 코어는 남는데.

GIL 은 한 번에 1코어어치만 통과시키므로, 프레임당 GIL 보유 시간을 `g` 라 하면
처리량 상한 = `1코어 ÷ g`. 관측 315 fps 를 넣으면:

```
g = 1.0 / 315          = 3.17 ms/프레임
GIL 구간 소모  = 315 × 3.17ms = 1.00 vCPU   (포화)
병렬 구간 소모 = 315 × 24.4ms = 7.69 vCPU
합계                            = 8.69 vCPU
관측 AI CPU                     = 8.69 vCPU  ✅
```

**세 관측치(처리량 315 · CPU 8.69 · 코어 16)를 하나의 모델이 동시에 설명한다.**
경쟁 가설은 안 맞는다:

| 가설 | 왜 밀리나 |
|---|---|
| 메모리·캐시 병목 | 메모리 대기는 **CPU 시간으로 계산된다.** 그러면 CPU 가 16 근처로 가야 하는데 8.69 에서 멈춘다 |
| HT 가 0 을 준다 | [`ai-recalibrate-2026-08-11` §C](../ai-recalibrate-2026-08-11/README.md) 가 같은 워크로드에서 **HT +44%** 를 쟀다 — 정면 충돌 |
| 스레드 과다구독 | 문맥교환은 CPU 를 **더** 쓰게 만들지 **덜** 쓰게 만들지 않는다 |

🔴 **이건 계산이 맞는다는 것이지 측정한 것이 아니다.** 반증 조건은 아래 §4-R6 이다.

### 2-2. 2순위 — 캐시 (비용 «증가» 쪽)

프레임당 CPU 가 세션 수에 따라 오른다(팔 A): 20세션 **22.5ms** → 160세션 **27.2ms**, **+21%**.
검출기 1개가 **98.7MB**([`detector-memory-2026-08-11`](../detector-memory-2026-08-11/))이고
세션마다 따로 가지므로 105세션이면 워킹셋이 **10GB** 다 — L3 로 덮이지 않는다.

**천장은 GIL 이 정하고 비용 증가는 캐시가 만든다** 가 지금의 그림이다. 둘 다일 수 있다.

## 3. 스레드 vs 프로세스 — 로컬로는 못 갈랐다 (예상대로)

워커당 100프레임 추론, 모델 로드·워밍업은 배리어 앞에 두고 제외:

| 워커 | 스레드 fps | 배수 | 프로세스 fps | 배수 | 프로세스/스레드 |
|---:|---:|---:|---:|---:|---:|
| 1 | 31.6 | 1.00× | 24.3 | 1.00× | 0.77× |
| 2 | 44.2 | 1.40× | 26.8 | 1.10× | 0.61× |
| 4 | 45.6 | 1.44× | 44.6 | 1.84× | **0.98×** |

**4워커에서 둘이 같은 천장(~45 fps)에 붙는다** — 이 박스에선 **코어가 GIL 보다 먼저 걸린다.**
GIL 컨보이는 코어 수가 늘수록 심해지므로 **물리 8코어 이상에서만 갈린다.** → R6.

⚠️ 첫 시도는 모델 로드(1~2초)를 계측에 포함해 «1워커 8.2fps · 2워커 28.1fps» 라는 불가능한
값을 냈다. 배리어로 고쳤다. 원인은 «측정 대상이 아닌 초기화» 였다.

---

## 4. 레버 — 하나는 되고 하나는 안 된다

배경 부하가 팔에 통째로 얹히는 것을 막으려고 **프레임마다 팔을 round-robin** 으로 바꿨다
(판마다 순서 회전). 지표는 중앙값이다.

### (가) `model_complexity` — 유효

| 팔 | 중앙 ms | p25 | p75 | full 대비 |
|---|---:|---:|---:|---:|
| 0 (lite) | 38.4 | 37.2 | 46.1 | **0.64×** |
| 1 (full, **현재**) | 60.4 | 56.6 | 76.3 | 1.00× |
| 2 (heavy) | 231.7 | 210.0 | 292.5 | 3.83× |

lite 로 내리면 **추론 36% 절감.** 대가는 정확도이고, 그것은
[#234](https://github.com/Shadowfit/init/issues/234)(정답지가 흔들리면 점수가 몇 점 움직이나)와
**같은 자**다. 정확도 영향을 재기 전에는 채택 대상이 아니다.

### (나) 입력 해상도 — ❌ 효과 없음

| 팔 | 중앙 ms | p25 | p75 | 640×480 대비 | 검출 |
|---|---:|---:|---:|---:|---:|
| 320×240 | 54.6 | 50.8 | 58.4 | 1.04× | 10/10 |
| 640×480 | 52.6 | 48.0 | 56.5 | 1.00× | 10/10 |
| 960×720 | 55.2 | 51.1 | 58.8 | 1.05× | 10/10 |

**±5%, 차이 없다.** MediaPipe 가 내부에서 고정 크기로 리사이즈하므로 **클라 해상도를 낮춰도
서버 비용은 안 준다.** 음성 결과지만 값이 있다 — 「해상도 낮추면 되지 않나」에 답이 생겼다.

## 6. 남은 것 (→ AWS 從 항목)

| # | 무엇 | 왜 로컬로 안 되나 |
|---|---|---|
| **R6** | 스레드 vs 프로세스 (1·2·4·8·16 워커) — **§2-1 GIL 가설의 반증 조건** | 물리 2코어에선 코어가 먼저 걸린다(§3) |
| **R7** | `model_complexity` 0/1/2 배수 재측정 | 0.64× 는 이 CPU 값. c7i 는 AVX-512·XNNPACK 이 달라 배수가 다를 수 있다(방향은 동일) |

**R6 판정선**: 프로세스 2개에서 처리량이 **1.7~2배**로 오르고 CPU 가 8.7 → 14~16 으로
오르면 GIL 이다. 안 오르면 §2-1 이 틀렸고 캐시·HT 쪽으로 간다.

⚠️ **R6 이 GIL 로 판정돼도 워커 증설은 바로 못 한다** — 검출기 풀(`mediapipe_detector.py:269`
`_pool` 전역)과 세션 레지스트리가 **프로세스 메모리**라, 워커를 늘리면 세션이 다른 워커로 가서
트래킹이 깨진다. [#164](https://github.com/Shadowfit/init/issues/164) 가 스레드 단위로 겪은
문제가 프로세스 단위로 재발한다. **세션 어피니티나 상태 외부화가 선행**이고, 그건 설계 결정이다.
