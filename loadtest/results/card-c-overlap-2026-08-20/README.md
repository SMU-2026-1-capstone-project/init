## 0. 한 줄

**N=8000 에서 422배**(22.2초 ↔ 52.6ms). 그리고 🔴 **O(N²) 의 근거는 「읽는 행 수」가 아니라
「비교 횟수」였다** — 계획이 `Inner hash join (no condition)`, 즉 **데카르트 곱 + 필터**다(§3).

## 1. 결과

| N | naive ms | sweep ms | **배수** | naive 핸들러 | sweep 핸들러 |
|---|---|---|---|---|---|
| 500 | 29.7 | 2.7 | 11배 | 4,937 | 3,006 |
| 1,000 | 273.4 | 2.7 | 101배 | 21,376 | 6,006 |
| 2,000 | 1,154.7 | 12.9 | 90배 | 53,057 | 12,006 |
| 4,000 | 5,113.3 | 19.3 | 265배 | 116,802 | 24,006 |
| 8,000 | **22,222.6** | **52.6** | **422배** | 244,170 | 48,006 |

**배가할 때마다의 시간 증가**

| 구간 | naive | sweep |
|---|---|---|
| 500→1,000 | 9.2배 | 1.0배 |
| 1,000→2,000 | 4.2배 | 4.8배 |
| 2,000→4,000 | 4.4배 | 1.5배 |
| 4,000→8,000 | **4.35배** | 2.7배 |

naive 는 **4.2~4.4배**로 안정적이다 — N 이 2배일 때 4배, **2차식**이다.
sweep 은 1.0~4.8 로 흔들리는데, 절대값이 2.7~52ms 라 **잡음이 지배**한다(§4-2).

## 2. 핸들러는 판마다 «완전히» 같다

| N | 500 | 1,000 | 2,000 | 4,000 | 8,000 |
|---|---|---|---|---|---|
| naive | 4,937 | 21,376 | 53,057 | 116,802 | 244,170 |
| sweep | 3,006 | 6,006 | 12,006 | 24,006 | 48,006 |

세 블록에서 **소수점 하나 안 틀리고 같은 값**이 나왔다. 시간이 같은 조건에서 130ms ↔ 416ms 로
흔들린 것(N=1,000 naive)과 대비된다 — **읽기 카운터는 캐시·경합과 무관하다.**

sweep 은 정확히 **6N**(= 이벤트 2N 을 세 번 훑는다)으로 **완벽한 선형**이다.

---

## 3. 🔴 그런데 naive 의 핸들러는 2차식이 아니다 — 그리고 그게 핵심이다

naive 핸들러의 배가별 증가는 **4.33 → 2.48 → 2.20 → 2.09** 로 **선형에 수렴한다.**
시간은 2차식인데 읽기는 선형이다. 계획이 이유를 준다:

```
-> Filter: ((s2.start_time <= s1.start_time) and (s2.end_time > s1.start_time))
    -> Inner hash join (no condition)        ← 🔴 조인 조건이 «없다»
        -> Index scan on s1 using idx_start  (rows=2000)
        -> Hash
            -> Table scan on s2              (rows=2000)
```

**조인 조건 없는 데카르트 곱을 만든 뒤, 겹침 판정을 `Filter` 로 매 쌍에 적용한다.**
겹침 조건이 등치(`=`)가 아니라 **부등호 두 개**라 해시 조인이 조건을 못 가져가고 필터로 밀린다.

| 무엇이 | 얼마나 | 무엇이 센다 |
|---|---|---|
| 테이블 **읽기** | O(N) — 빌드 한 번 + 스캔 한 번 | 핸들러 (선형) |
| **비교** | **N² 쌍** | 시간 (2차식) |

⚠️ **그래서 rig 머리말의 서술을 고쳤다.** 원래 *"O(N²) 주장의 본 근거는 핸들러"* 라고 적어뒀는데
**틀렸다** — 근거는 **시간**이고, 핸들러는 「읽기는 선형인데도 느리다」를 보여 **기제를 좁히는** 쪽이다.

> 🔶 이건 카드로서 오히려 낫다. 「인덱스를 걸면 되지 않나」에 대한 답이 여기 있다 —
> **인덱스는 읽기를 줄이는 도구인데, 여기서 비싼 것은 읽기가 아니다.**

## 4. 🔴 미검증 · 말하면 안 되는 것

1. **결과값(최대 동시 세션 37~38)은 의미 없다.** 합성 데이터고, 이슈가
   *"방법이 선다까지가 이번 범위"* 라고 못박은 그대로다. 여기서 잰 것은 **비용의 증가 곡선**이다.
2. **sweep 의 시간 곡선은 못 믿는다.** 2.7~52ms 라 이 박스의 잡음(수 ms)과 같은 자릿수다.
   sweep 이 선형이라는 근거는 **시간이 아니라 핸들러(정확히 6N)** 다.
3. **N=8000 까지만 봤다.** 모집단이 53,211행이라 더 갈 수 있었지만 naive 가 22초라 비용이 커진다.
4. **다른 계획을 강제해보지 않았다** — `BNL`/`NO_HASH_JOIN` 힌트로 옵티마이저를 다른 전략에 묶으면
   naive 의 곡선이 달라질 수 있다. 「self-join 은 원래 O(N²)」가 아니라 **「이 계획에서 O(N²)」**이다.
5. **답의 «정확성» 은 두 팔의 일치까지만 봤다.** 제3의 방법으로 검산하지 않았다 —
   둘이 같은 방식으로 틀렸을 가능성은 안 지웠다.
6. **동시성 없이 혼자 돌았다.** 실사용은 다른 부하와 같이 온다.

## 5. 카드로서 남는 문장

- **알고리즘 선택이 SQL 문장 모양으로 드러난다** — self-join ↔ 이벤트 펼치기 + 윈도우 함수
- **422배**(N=8000)이고, 증가율이 4.2~4.4배/배가로 **2차식임을 곡선으로 보였다**
- 🔴 **「인덱스로 고치면 되지 않나」에 답이 있다** — 비싼 것은 읽기가 아니라 비교다(§3)
- ⚠️ 결과값은 합성이라 못 쓴다. **방법과 비용 곡선까지가 이 카드다**
