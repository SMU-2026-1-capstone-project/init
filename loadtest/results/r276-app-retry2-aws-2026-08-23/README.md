## 1. 1차(수정 전) ↔ 2차(수정 후)

| 동시성 | 잔여 실패율 1차 | **2차** | retried(중앙값) | recovered | **exhausted** |
|---|---|---|---|---|---|
| 8 | 36.4% | **14.2%** | 320 | 120~141 | **71** |
| 16 | 45.2% | **19.2%** | 398 | 138~157 | **96** |
| 32 | 42.2% | **19.8%** | 403 | 151~154 | **99** |

**세 가지가 한 번에 확인된다:**

| | |
|---|---|
| ✅ 수정이 실제로 돈다 | `retried` 가 판당 **320~493** 회. 1차에는 **0** 이었다 |
| ✅ 두 지표가 이제 **정확히 일치**한다 | `exhausted` 와 ghz 의 `Internal` 이 **모든 판에서 같은 값**이다. 1차의 자기모순(36~45% 실패 · 지표 0)이 사라졌다 |
| 🔴 그래도 **상한이 모자란다** | 잔여가 절반 이하로는 내려갔지만 **14~20% 가 남는다** |

## 2. 🔴 «미검증» 하나가 로그로 닫혔다 — 예외는 `CannotAcquireLockException` 이다

1차 README §2-ㄷ 이 *"예외 객체의 클래스명을 로그로 직접 보지는 못했다"* 로 남겨둔 칸이다.
[#416](https://github.com/Shadowfit/init/issues/416) 이 추가한 로깅이 그 자리를 찍었다:

```
24  저장 실패: CannotAcquireLockException
```

`spring-jdbc 6.2.19` 클래스 목록에서 좁혀둔 추론(`SQLTransactionRollbackException` →
`CannotAcquireLockException` 계열)이 **관측으로 확인**됐다. 그리고 그 예외가 지금은
`PessimisticLockingFailureException` 으로 잡혀 재시도를 탄다 — 로그에 재시도 문구 **45건**,
소진 문구 **24건**.

## 3. 왜 저장 프로시저 판(2회 → 0.0%)과 다른가 — 🔶 가설, 안 쟀다

| 후보 | 왜 그럴듯한가 |
|---|---|
| **앱 왕복이 붙는다** | 시도마다 gRPC·트랜잭션 경계를 다시 지난다. 재시도가 «상대가 커밋한 뒤» 에 도착할 확률이 SP 판과 다르다 |
| **되먹임** | 재시도가 그 순간의 동시성을 올린다. 판당 320~493 회의 추가 시도가 그대로 부하다 |
| **한 요청이 만지는 행 수가 다르다** | 앱은 25프레임 → 다운샘플 R=5 → **5행**, SP 판은 문당 **25행** |

어느 쪽이 지배적인지는 **이 판이 못 가른다.**

## 4. 🔴 미검증 · 말하면 안 되는 것

1. **레벨 사이 비교는 여전히 조심.** 14.2 → 19.2 → 19.8% 인데, 부하기가 대상과 같은 4 vCPU
   박스에 산다. c 를 올리면 ghz 자신이 CPU 를 먹는다 — «동시성 효과» 와 «부하기 경합» 을 못 가른다
2. **상한을 3·4·5 로 올리면 어떻게 되는지 안 쟀다.** 상한은 코드 상수라 이 rig 은 못 바꾼다
3. **백오프 간격 0.** 간격을 주면 좋아질 수도(상대에게 커밋할 시간) 나빠질 수도(요청이 오래 살아
   동시성을 올린다) 있다 — 08-20 판도 같은 이유로 안 쟀다
4. **절대 실패율을 운영값으로 인용 금지** — 중복 100% 페이로드다. 실사용 재전송은 «실패했을 때만»
   이라 이 비율이 그대로 나오지 않는다
