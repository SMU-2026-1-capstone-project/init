# 타임아웃 스윕 적재량 — N 대비 선형임을 확인 (#207)

측정: 2026-08-17 · 로컬(i3-6100, 2물리코어) · MySQL 8.0.46 도커(3308 전용 컨테이너)

## 0. 한 줄

**`SessionTimeoutScheduler` 스윕 1회의 할당량이 진행 중 세션 수 N 에 선형이다 —
N 16배에 할당 15.9배, 세션당 약 3,785 B.** 걷어갈 대상이 **0** 인 판에서 잰 값이므로,
이 적재는 «할 일» 이 아니라 «목록 길이» 가 만든 것이다. #207 확정.

---

## 1. 결과

걷어갈 대상 0 · 버림판 3 + 본판 9(순환 라틴 방격) · 중앙값

| N (IN_PROGRESS) | 할당 중앙값 | **세션당 할당** | 소요 중앙값 |
|---:|---:|---:|---:|
| 1,000 | 3,809,512 B | **3,810 B** | 119.1 ms |
| 4,000 | 15,120,280 B | **3,780 B** | 223.6 ms |
| 16,000 | 60,553,040 B | **3,785 B** | 711.2 ms |

**N 16배 → 할당 15.9배.** 세션당 할당은 세 레벨에서 **1% 안쪽**으로 일정하다.

### 판별 원본

```
R1 P1  N=  1,000  alloc=   3,810,696 B   169.7 ms
R1 P2  N=  4,000  alloc=  15,120,280 B   377.4 ms
R1 P3  N= 16,000  alloc=  60,553,040 B   711.2 ms
R2 P1  N=  4,000  alloc=  15,120,280 B   223.6 ms
R2 P2  N= 16,000  alloc=  60,553,040 B   578.3 ms
R2 P3  N=  1,000  alloc=   3,809,512 B   119.1 ms
R3 P1  N= 16,000  alloc=  60,553,192 B   721.0 ms
R3 P2  N=  1,000  alloc=   3,807,272 B    58.6 ms
R3 P3  N=  4,000  alloc=  15,111,640 B   137.4 ms
```

## 2. 이 판정이 서는 이유 — 지표 선택이 결과를 갈랐다

**같은 N 이면 할당이 판마다 같은 값으로 나왔다.** N=4,000 은 R1 P2 와 R2 P1 이
`15,120,280 B` 로 **바이트까지 동일**하고, N=16,000 도 `60,553,040 B` 가 두 번이다.
위치(P1/P2/P3)를 바꿔도 안 움직였다.

**같은 판의 소요시간은 흔들렸다.** N=1,000 이 58.6 ~ 169.7 ms 로 약 3배다. 버림판을
넣었는데도 R1 P1 이 제일 느리고 R3 P2 가 제일 빠르다 — 시간 축에는 아직 추세가 남아 있다.

> 📌 **시간으로 쟀으면 이 결론을 못 냈다.** 판 간 변동이 재려던 효과와 같은 크기여서,
> #87 에서 락 비용을 기각했던 것과 같은 자리에 빠졌을 것이다. 할당량은 GC·스케줄링과
> 무관한 누적값이라 그 함정을 통과한다. 그리고 #207 이 묻는 «적재량» 에 직접 답한다.

**하드웨어 의존이 없다는 것도 여기서 나온다.** 할당 바이트는 같은 코드·같은 결과 집합이면
어느 기계에서든 같다. 그래서 이 표의 **할당 열은 조건 없이 인용할 수 있고, 시간 열은 못 쓴다.**

---

## 3. 무엇을 재지 않았나

- **걷어갈 대상이 0 인 판만 쟀다.** 이게 요점이다 — 일이 0인데도 적재가 N 에 비례한다는 것.
  실제로 타임아웃이 다수 발생하는 판은 안 쟀다(전이·아웃박스 INSERT 가 얹힌다)
- **힙 점유·GC 는 안 봤다.** 잰 것은 누적 할당이지 상주량이 아니다. 「스윕이 힙을 N 바이트
  붙들고 있다」는 이 표로 말할 수 없다 — 엔티티는 판이 끝나면 참조가 끊긴다
- **소요시간은 판정에서 뺐다.** 2코어에 개발 스택(backend·ai·mysql)이 같이 떠 있는 상태에서
  쟀다. 표에 남기는 것은 «할당과 같은 방향으로 는다» 는 정성적 확인까지다
- **N=100,000 은 못 쟀다** (§5)

## 4. 산술 — 이 수가 사는 자리

세션당 3,785 B 는 그 자체로는 작다. #207 이 지적한 것은 **방향**이다.

| 상황 | 진행 중 세션 | 스윕 1회 할당 | 분당(주기 1분) |
|---|---:|---:|---:|
| 평시 (실제 운동 중인 사람) | 수십 | ~0.1 MB | ~0.1 MB |
| 좀비 누적 | 10,000 | ~37 MB | ~37 MB |
| 좀비 누적 | 100,000 | ~370 MB | ~370 MB |

⚠️ **이 표의 세로축은 가정이다.** DAU 1,000 에서 `IN_PROGRESS` 상한이 얼마인지는 설계
문서 어디에도 없다(#207 §3). 위 10,000·100,000 은 근거 있는 값이 아니라 **자릿수 감각**이다.

핵심은 «세션이 안 끝나서 스윕이 필요해진 바로 그 순간에 스윕이 가장 비싸진다» 이고,
그 성질은 위 선형성으로 확인됐다.

## 5. 🔴 초판 리그가 못 돌았다 — 그 실패도 자료다

처음 레벨은 **1천 / 1만 / 10만**이었고 **완주 추정 22시간**이 나와 죽였다.

무너진 곳은 판 준비였다. `Innodb_rows_updated` 가 **분당 1,070행**까지 떨어졌는데,
같은 `UPDATE exercise_sessions SET status='COMPLETED'`(10만 행)를 **단독으로 재면 8.4초**다.
즉 UPDATE 가 느린 게 아니라 **N=100,000 스윕 한 판이 이 박스를 붙들어 옆을 굶겼다.**

⚠️ **이것을 #207 의 증거로 쓰지 않는다.** 개발 스택이 같이 떠 있었으므로 «스윕 탓» 과
«동거 탓» 이 안 갈린다. 여기 적는 것은 **리그 설계의 교훈**이다:

1. **판 준비가 측정보다 비싸면 리그가 안 돈다.** 초판은 판마다 전 행의 `status` 를 갈아엎었는데,
   `status` 는 보조 인덱스 **셋 모두**의 컬럼이라 행마다 인덱스 유지가 붙는다.
   지금은 «이미 맞는 행» 을 `WHERE` 에서 빼 델타만 쓴다
2. **판마다 `last_active_at` 을 갱신하던 것도 뺐다.** 대신 프로파일이 `idle-minutes` 를 크게
   잡아 시딩 때 박은 값 하나로 «전부 타임아웃 아님» 이 유지된다. 판정 코드 경로는 그대로 탄다
3. **16배면 충분하다.** 이 리그가 답하는 질문은 «기울기가 있는가» 이지 «10만에서 몇 초인가» 가
   아니다 — 후자는 어차피 이 환경에서 인용할 수 없다

### 그리고 첫 실행은 아예 안 돌았다

`-Dsweep.load=true` 를 줬는데 `BUILD SUCCESSFUL` 이 떴고, 리포트를 보니 `skipped=1` 이었다.
gradlew 에 준 `-D` 는 포크된 테스트 JVM 으로 전달되지 않는다. **`backend/build.gradle` 에
그 주석이 이미 있었는데 그대로 밟았다.** 스킵은 성공으로 보이므로 출력으로는 못 알아챈다 —
`build.gradle` 주석에 그 사실을 덧붙였다.

## 6. 반증 조건 대조 (#207 §6)

| 조건 | 결과 |
|---|---|
| 할당·시간이 N 에 **평탄**하면 #207 이 틀린 것 | ❌ 평탄하지 않다. 16배에 15.9배 |
| `IN_PROGRESS` 를 작게 유지하는 다른 장치가 이미 있다면 과대평가 | 🔶 **여전히 미확인.** 못 찾았으나 «못 찾은 것과 없는 것은 다르다» |

## 7. 재현

```bash
docker run -d --name shadowfit-sweep-mysql -e MYSQL_ROOT_PASSWORD=sweeptest \
  -e MYSQL_DATABASE=shadowfit -p 3308:3306 mysql:8.0 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci

./gradlew :backend:test --tests '*SessionTimeoutSweepLoadTest' -Dsweep.load=true
```

스키마는 Flyway 가 만든다. 프로퍼티가 없으면 통째로 건너뛰므로 CI 는 영향받지 않는다 —
**단 그 스킵은 `BUILD SUCCESSFUL` 로 나온다.** 돌았는지는 리포트의 `skipped` 로 확인할 것.
