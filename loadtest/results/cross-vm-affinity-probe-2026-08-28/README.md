## 0. 한 줄

**정확성·장애 격리 둘 다 통과.** `session_id % 2` 해시로 진짜 별개의 VM 2대에 세션을
나눴을 때 오배정이 0건이었고(ㄱ), VM A를 강제로 죽였을 때 VM B에 배정된 세션은 성공률이
조금도 안 변했다(ㄴ). 실패 모양은 타임아웃이 아니라 즉시 연결 거부였다(ㄷ, 0.008초).

---

## 1. 무대 — 설계에서 실제로 바뀐 것

설계 문서(§3-1)는 VM 3대(대상 2 + 부하기 1)를 전제했다. 실행 시점에 보안그룹 확인
결과 **SSH(22)만 운영자 IP에 열려 있고, HTTP/gRPC 포트는 같은 보안그룹 내 인스턴스끼리만
열려 있었다**(`sg-0382132d2f8b5f6ce`). 이 판은 처리량이 아니라 정확성·격리만 보므로,
부하기를 따로 안 두고 **VM B 안에서 직접 rig을 돌려 VM A로 요청**했다 — VM 2대로 줄임.
설계 문서와의 유일한 편차이고, 결론(§3의 판정 대상)에는 영향이 없다.

| | 값 |
|---|---|
| VM A, VM B | `c7i.large`(2 vCPU) 각 1대, AL2023, `ami-0ba2a8e103d0623b8` |
| 소프트웨어 | 커밋 [`e615088`](https://github.com/Shadowfit/init/commit/e61508824e6db61e13a3f4c25e5555a0edf1dfdc) 기준 `ai-server` Docker 이미지, 워커 1개(`AI_WORKER_COUNT=1`) |
| 세션 · fps | 20세션, 프레임 1장씩(스루풋이 아니라 정확성 확인이라 다수 판·다수 fps 불필요) |
| rig | 이 디렉토리의 [`affinity_probe.py`](./affinity_probe.py), VM B의 컨테이너 안에서 `docker exec`로 실행 |
| 소요 | 부트스트랩(docker build 포함) ~10분 + 실측 ~5분 ≈ **15분** |

## 2. 판정선별 결과

### ㄱ. 정확성 — 세션이 항상 배정된 VM으로만 가는가

킬 전(`frames pre`), 각 VM에 배정된 세션 10개씩 프레임을 보냈다:

```
backend A: 10/10 ok, 나머지=[]
backend B: 10/10 ok, 나머지=[]
```

**오배정(`nolease`) 0건.** `session_id % 2` 클라이언트 사이드 해싱이 진짜 네트워크 경계를
넘어서도(같은 박스의 다른 포트가 아니라 다른 VM의 다른 사설 IP) 정확하게 작동했다.

### ㄴ. 격리 — VM A가 죽어도 VM B 세션은 안전한가

VM A의 `shadowfit-ai` 컨테이너를 `docker kill`로 강제 종료한 직후, 같은 20세션에 다시
프레임을 보냈다(`frames post`):

```
backend A: 0/10 ok, 나머지=['http0'] × 10   (연결 자체가 안 됨)
backend B: 10/10 ok, 나머지=[]              (킬 전후 변화 없음)
```

**VM B 세션의 성공률이 절대 개수 기준으로 1도 안 변했다(10/10 → 10/10).** VM A 장애가
VM B로 전혀 안 번졌다 — `ai-horizontal-scaling.md`가 전제한 "VM을 분리하면 장애가
격리된다"는 이 조건에서 실측으로 확인됐다.

### ㄷ. VM A 세션의 실패 모양 (기록, 판정 아님)

```python
URLError(ConnectionRefusedError(111, 'Connection refused'))  elapsed = 0.008s
```

**타임아웃이 아니라 즉시 거부.** 컨테이너가 죽어 그 포트를 아무도 리슨하지 않아 TCP SYN에
바로 RST가 온다. 실무적으로 좋은 소식 — Spring이 이 상황을 초 단위 타임아웃까지 기다리지
않고 밀리초 단위로 알 수 있다는 뜻이다(단, 이건 "컨테이너가 완전히 죽은" 경우고, §5에 적은
대로 "느려지기만 하는" 경우나 네트워크 파티션은 다른 모양일 수 있다 — 이 판은 그건 안 쟀다).

## 3. 원본

- [`affinity_probe.py`](./affinity_probe.py) — 실행에 쓴 스크립트(파일 상단에 정확한 실행
  순서를 적어뒀다)
- 원시 JSON(`/tmp/affinity_manifest.json`, `/tmp/affinity_result_pre.json`,
  `/tmp/affinity_result_post.json`)은 **VM 종료 전에 회수하지 않았다** — 콘솔 출력(§2)만
  기록으로 남았다. 재현하면 다시 만들 수 있지만, 지금 이 문서의 숫자는 콘솔 로그를 옮겨
  적은 것이지 커밋된 원본 파일과 대조 가능한 상태가 아니다. **다음 판을 위한 교훈**: 종료
  전에 `docker cp`로 결과 JSON을 반드시 회수할 것.

## 5. 이 판이 답하지 못하는 것 (설계 문서 §6 그대로)

- **복구(재부착)** — VM A가 죽은 뒤 그 위 세션을 되살리는 것은 범위 밖. "VM B가 안전한가"만 봤다
- **처리량/사이징** — 이미 다른 축이 답함
- **실제 Spring `grpc-java` 리졸버 구현** — 이 rig은 파이썬 클라이언트가 라우팅을 흉내낸 것
- **동시 다중 VM 장애**
- **네트워크 파티션(VM은 살아있는데 연결만 끊기는 경우)** — 이 판은 컨테이너 종료만 봤다.
  진짜 네트워크 단절은 §2-ㄷ과 다른 실패 모양(타임아웃)을 낼 수 있다
- **"느려지기만 하는" 부분 장애** — 완전히 죽는 경우만 봤다. 응답은 하는데 느려지는 VM은
  이 판의 즉시-거부 모양과 다르게 감지가 더 어려울 수 있다
