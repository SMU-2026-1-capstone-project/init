# `post_loop` 안을 가른다 — 검증이 주범이다. 그런데 그게 중요하지 않다 (2026-08-23)

## 0. 한 줄

**`post_loop` 의 주범은 Pydantic 응답 검증이다** — 떼면 **20.32 → 9.75ms(−52%)**.

🔴 **그런데 처리량은 오히려 −5.28% 다.** 이유를 찾다가 더 큰 것이 나왔다 —
**요청 시간의 79~81% 가 우리 계측 밖에 있다.** `post_loop` 는 전체의 **4.6%** 였다.

---

## 1. 무대

| | |
|---|---|
| 부하 | **160세션 · 3.0fps** · 판당 90초 · 풀 201 · 계측 ON |
| 팔 | **R** `response_model=PoseResponse`(현행) · **N** dict 반환 · **J** `JSONResponse` 직접 |
| 배열 | 버림 1(R) + `R N J J N R R N J J N R` — **위치 합 셋 다 26** |
| 결과 | **12판 전부 유효 · 에러 0** · **R 팔 판 간 산포 0.88%** |

---

## 2. 답 — 검증이 `post_loop` 의 절반 이상이다

| 팔 | 모드 | rps | `post_app` | **`post_loop`** | `post` | `total` |
|---|---|--:|--:|--:|--:|--:|
| **R** | model | 354.5 | 1.04 | **20.32** | 21.84 | 87.85 |
| **N** | dict | 335.8 | 1.06 | **9.75** | 11.32 | 83.95 |
| **J** | json | 367.7 | 1.30 | **8.86** | 10.56 | 93.26 |

```
R → N   post_loop  −10.57 ms  (−52%)   ← Pydantic 응답 검증을 뗀 것
N → J   post_loop   −0.89 ms  ( −9%)   ← 인코딩을 스레드로 옮긴 것
```

🟢 **주범은 검증(B)이고 인코딩(C)은 작다.** FastAPI 의 `serialize_response` 가
`field.validate()` 로 **모델을 통째로 다시 만드는** 비용이다.

### 🔴 예상이 빗나간 자리 — 비용이 «옮겨간» 게 아니라 «사라졌다»

설계는 *「`model_dump()` 를 핸들러에서 부르니 `post_app` 으로 옮겨간다」* 로 봤고,
**`post_loop` 감소분 ≈ `post_app` 증가분**을 검산으로 삼았다. **안 맞았다:**

```
post_app   R 1.04 → N 1.06 (+0.02) → J 1.30 (+0.26)
post_loop  R 20.32 → N 9.75 (−10.57)
```

**`model_dump()` 는 0.02ms 도 안 되는데 `serialize_response` 는 10.57ms 다.**
같은 「모델 → dict」로 보이지만 **비용이 500배 차이난다** — 검증이 붙기 때문이다.

---

## 3. 🔴 그런데 처리량이 안 따라온다

```
R  post_loop 20.32ms · 354.5 rps
N  post_loop  9.75ms · 335.8 rps   ← 절반으로 줄였는데 5.28% 느리다
J  post_loop  8.86ms · 367.7 rps
```

**R 팔 산포가 0.88%** 이므로 ±5% 는 잡음이 아니다. 실재한다.

이유를 찾다가 §4 가 나왔다.

---

## 4. 🔑 진짜 발견 — 계측이 요청의 20% 만 보고 있다

리틀의 법칙을 ASGI 구간에 적용하면:

| 팔 | rps × `total` 평균 = **ASGI 안에 있는 수** | 세션 160 대비 | 클라 지연 중 ASGI 구간 |
|---|--:|--:|--:|
| R | 354.5 × 91.6ms = **32개** | 밖에 **128개** | 92 / 444ms = **21%** |
| N | 335.8 × 87.3ms = **29개** | 밖에 **131개** | 87 / 468ms = **19%** |
| J | 367.7 × 105.1ms = **39개** | 밖에 **121개** | 105 / 426ms = **25%** |

🔴 **요청 160개 중 ASGI 안에는 30개 안팎뿐이고, 130개는 계측이 못 보는 곳에 있다.**

`t_asgi_in` 은 **미들웨어가 도는 시점**이다. 그 앞의 **소켓 accept · HTTP 파싱 · 바디 수신**은
uvicorn 이 하고 **이벤트 루프에서 돈다** — 우리 계측 밖이다.

### 그래서 §2 의 답이 «작다»

```
post_loop 20.32ms  /  클라 지연 443.6ms  =  4.6%
```

**검증을 통째로 없애도 요청 시간의 2% 남짓이다.** N 이 그러고도 느려진 것이 그 증거다 —
얻은 것보다 다른 데서 잃은 것이 컸다.

## 5. 팔이 안 건드린 구간이 흔들린 것

| 팔 | `infer` | 스레드풀 `waiting`=0 비율 |
|---|--:|--:|
| R | 30.43 ms | 91.9% |
| N | 34.72 ms | 87.7% |
| J | **47.39 ms** | **72.2%** |

`infer` 는 MediaPipe 구간이라 **팔이 안 건드린다.** 그런데 J 에서 **+56%** 다.

읽으면: **J 는 인코딩을 스레드로 옮겼다** → 스레드풀이 더 붐빈다(대기 0 비율 92% → 72%) →
같은 풀에서 도는 `infer` 의 **벽시계 시간이 늘어난다.** 일이 준 게 아니라 **경합이 는 것**이다.

🟢 **그래도 J 가 처리량이 제일 높다** — 루프를 비운 이득이 스레드 경합보다 컸다.
🔴 **이 해석은 추론이다.** 스레드 경합을 따로 안 쟀다.

---

## 6. 이 판이 확정한 것과 안 한 것

- ✅ **`post_loop` 의 주범은 Pydantic 응답 검증**(−52%). 인코딩은 −9% 로 작다
- ✅ **설계의 검산 가설이 틀렸다** — 비용이 «옮겨간» 게 아니라 «사라졌다».
  `model_dump()`(0.02ms)와 `serialize_response`(10.57ms)는 **500배 다르다**
- 🔴 **그래서 고칠 값이 못 된다** — `post_loop` 는 요청 시간의 **4.6%** 다
- 🔑 **새 질문이 열렸다: 나머지 79~81% 는 어디인가.** ASGI 앞(uvicorn 수신 큐)으로 **추정**되지만
  **안 쟀다** — 계측이 거기까지 안 간다
- 🔴 **ㄱ(GIL)은 여전히 안 갈렸다**

---

## 7. 정직하게 비어 있는 것

- 🔴 **ASGI 앞 구간을 «추정» 했다.** 리틀의 법칙으로 「밖에 130개가 있다」까지는 나오지만
  **그것이 accept 큐인지 파싱인지 바디 수신인지 모른다.** 다음 판이 물을 것
- 🔴 **팔 N·J 의 응답이 프론트 계약과 같은지 확인 안 했다** — rig 이 파싱에 성공했으므로
  **필드 이름은 맞지만**, 값·타입까지 대조하지는 않았다. **측정용 팔이고 채택안이 아니다**
- **응답 바디 크기를 안 남겼다** — 설계 §11-3 이 「같이 남긴다」로 적었는데 rig 에 안 넣었다.
  인코딩 비용이 거기 비례하므로 N↔J 해석의 근거가 하나 빈다
- **`infer` 가 흔들린 것을 경합으로 읽었지만 안 쟀다**(§5)
- **판 간 절대값 비교는 여전히 못 한다** — [#255](https://github.com/Shadowfit/init/issues/255)
