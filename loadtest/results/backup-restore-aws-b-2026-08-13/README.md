## 2. 🔴 팔 B 의 「9초」— 원인이 페이지 캐시가 아니라 **reflink** 였다

#201 은 「`cp -a` 가 fsync 안 해서 10.4GB 가 페이지 캐시에 남아 있다」로 보고 `sync` 시간을
옆 칸에 세웠다([`backup_sweep.sh:232`](../backup-restore-2026-08-13/backup_sweep.sh)).
**그 칸이 15~22ms 로 나왔다** — 가설대로면 수십~수백 초가 나와야 한다.

인스턴스를 지우기 전에 직접 재봤다(2GB, 같은 이미지·같은 경로 구조):

| | 값 |
|---|---|
| 파일시스템 | `/dev/nvme0n1p1` **xfs, `reflink=1`** (`xfs_info`) |
| `cp -a` 2GB 소요 | 2,119 ms |
| **`df` 여유 변화** | **0 블록** (139,298,464 → 139,298,464) |
| 그 뒤 `sync` | **2 ms** |

**복사가 일어나지 않았다.** XFS reflink 로 extent 를 공유했을 뿐이다. 그래서 내려쓸 더러운
페이지도 없었고(→ `sync` 2ms), 「10.4GB 를 9초에」가 물리적으로 가능했던 것이다.

→ **`restore_durable_s` 는 틀린 자리를 정확하게 쟀다.** 값 자체는 정직하지만 「내구성까지
포함한 복구 시간」이라는 해석은 성립하지 않는다 — **내구성 이전에 복사가 없다.**
→ 팔 B 의 9~10초는 **여전히 하한선**이고, 본 측정 README §3 의 «페이지 캐시» 설명은
**갈아써야 한다**(그 절의 판정 방향 — 물리가 논리보다 빠르다 — 은 바뀌지 않는다).
→ 이슈: **(신규, §5)**

⚠️ 이 확인은 **탐침 1판**이다. 반복도 라틴 방격도 없다. 「reflink 가 걸린다」는 사실을
세우는 데는 충분하지만, **교정된 복구 시간은 아직 없다.**

## 3. #202 — real-JSON 은 팔 A 를 **덜** 불리하게 만든다 (예상 반증)

설계 §8 의 예상은 «21분은 real-JSON 에서 **더 나빠질** 값» 이었다. 규모가 달라 절대값은 못
비교하므로 **행당·바이트당으로 정규화**한다(팔 A 만 — 팔 B 는 §2 로 무효).

| | 더미 1억 행 | real 75만 행 | 배수 |
|---|---|---|---|
| 산출물 바이트/행 | 59.6 B | 2,394 B | **40.2배 뚱뚱** |
| 복구 시간/행 | 12.3 µs | 110.6 µs | **9.0배 느림** |
| **복구 처리량** | **4.63 MB/s** | **20.7 MB/s** | **4.5배 빠름** |

**행이 40배 뚱뚱해지는데 행당 비용은 9배만 는다.** 즉 논리 복구(`mysqldump` → `mysql` 재적재)의
비용은 **바이트가 아니라 행 수가 지배한다.** 같은 바이트라면 뚱뚱한 행 쪽이 오히려 유리하다.

→ 「real-JSON 에서 Q2 가 과소평가돼 있다」는 #202 의 걱정은 **이 축에서는 성립하지 않는다.**
단 **행 수를 고정하면** 여전히 real 쪽이 9배 비싸다 — 「1억 행이 real-JSON 이었다면 21분이
아니다」는 참이다. 두 문장이 모순이 아니라 **정규화 축이 다르다.**

⚠️ 한계: real 무대는 **판 1개**(+버림 1)다. 더미 3판과 통계적 무게가 다르다.
