# anyio 스레드풀 상한 프로브 — 0단계 (2026-08-23)

측정일: 2026-08-23 (UTC) · **로컬 i3-6100 (2 물리코어)** · 박스 비용 0
설계: [`ai-process-ceiling-cause.md` §4-2 0단계](../../../docs/decisions/ai-process-ceiling-cause.md)
산출물: [`probe.py`](probe.py) · [`run.txt`](run.txt)

> 🔴 **이 프로브가 답하는 것은 «상한이 걸리는 구조인가» 이지 «AI 서버에서 걸렸는가» 가 아니다.**
> 후자는 1단계(EC2)가 답한다. §3 이 그 구분을 적는다.

---

## 0. 한 줄

**anyio 기본 상한 40 은 실재하고, 동시 요청이 40 을 넘으면 실제로 걸린다.**
그리고 **`tasks_waiting` 이 관측된다** — 설계의 계측 ①이 성립한다.

🔴 **다만 0단계가 2단계를 없앨 수 있다던 기대는 틀렸다** — §3.

---

## 1. 무엇을 어떻게

mediapipe·MySQL·ai-server 를 **안 쓴다.** 재는 것은 앱이 아니라 **anyio 의 거동**이다.

| | |
|---|---|
| 앱 | FastAPI + **동기(`def`) 핸들러** 하나 — `ai-server` 의 `detect_pose` 와 같은 모양 |
| 핸들러가 무는 시간 | `time.sleep(0.10)` — R10-a 의 핸들러 `total` **106.9ms** 에 맞췄다 |
| 부하 | 닫힌 루프 **20 · 40 · 60 · 80** 동시 (레벨당 6초, 앞 1/4 은 램프라 버림) |
| 계측 | 이벤트 루프 안에서 `current_default_thread_limiter()` 를 20ms 마다 샘플 |

⚠️ **`sleep` 이라 CPU 를 안 쓴다.** 일부러 그렇게 했다 — 재려는 것이 **상한**이지 계산이 아니다.
그래서 2 물리코어가 결과를 안 흔든다.

---

## 2. 결과

```
동시  total  borrowed p50  borrowed max  waiting p50  waiting max
 20     40            19            20            0            0
 40     40            35            40            0            0
 60     40            40            40           11           20     ← 걸린다
 80     40            35            41            0           39
```

| | |
|---|---|
| 🟢 **`total_tokens = 40`** | 소스에서 읽은 기본값(`CapacityLimiter(40)`)이 **런타임에서 확인**됐다 |
| 🟢 **`tasks_waiting` 관측됨** | 계측 ①이 성립한다. 40 이하에서 0, 넘으면 양수 |
| 🟢 **40 을 넘으면 걸린다** | 60에서 최대 20 대기, 80에서 최대 39 |

⚠️ 80 의 `waiting p50` 이 0 인데 최대가 39 다 — 샘플이 대기 구간과 배출 구간을 오간다.
**중앙값이 아니라 최대·분포를 봐야 한다**는 뜻이고, 1단계 계측도 그렇게 짜야 한다.

---

## 3. 🔴 그런데 2단계를 못 없앤다 — 설계의 기대가 틀렸다

설계 §4-2 는 *「0단계가 2단계를 없앨 수 있다」* 로 적었다. **못 없앤다.** 이 프로브는
**구조**를 확인했지 **AI 서버에서 걸렸는지**는 안 봤고, 그건 로컬로 볼 수 없다.

그리고 R10-a 데이터를 이 눈으로 다시 보면 **안 맞는 게 있다**:

| | 값 | 뜻 |
|---|--:|---|
| `inflight_http` 최대 | **160** | ASGI 안에 세션 수만큼 들어와 있다 |
| `inflight_handler` 평균 | **18~24** | 핸들러 안은 20 남짓 — 게다가 이건 **과다 계수**다([설계 §2-2](../../../docs/decisions/ai-process-ceiling-cause.md)) |
| 차이 | **~140** | **ASGI 와 핸들러 사이에 있다** |

그 140 이 **스레드풀 큐면 ㄷ**, **이벤트 루프 디스패치 대기면 ㄴ** 이다. `wait` **24.92ms** 가
그 구간인데 **지금 계측은 둘을 안 가른다.**

### 산수가 닫히지 않는다

```
스레드 40개 × 핸들러 ~107ms  →  40 / 0.107 = 374 rps
실측                          →  271 rps (6fps) · 319 (3fps)
```

**유효 동시성이 40 에 못 미친다**는 뜻인데, 그러면 대기가 없어야 하고, 그러면 위의 140 은
어디 있나. 🔴 **이 모순을 푸는 것이 1단계다** — `tasks_waiting` 한 값이 갈라준다.

---

## 4. 이 프로브가 바꾸는 것

| 자리 | 무엇 |
|---|---|
| 설계 §4-2 | 「0단계가 2단계를 없앤다」 → 🔴 **못 없앤다.** 0단계는 **계측기 검증**이다 |
| 설계 §6 | 판정선이 날카로워졌다 — **`tasks_waiting` 0 이냐 아니냐**로 ㄴ/ㄷ 이 바로 갈린다 |
| 1단계 계측 | **중앙값이 아니라 최대·분포**를 남길 것(§2 ⚠️) |
| 계측 ① | 🟢 **코드가 검증됐다** — `probe.py` 의 샘플러를 그대로 옮기면 된다 |

---

## 5. 정직하게 비어 있는 것

- 🔴 **AI 서버로 안 돌렸다.** 핸들러가 `sleep` 이라 GIL 도 CPU 도 안 쓴다 — 실제 핸들러는
  MediaPipe·OpenCV·JSON 이 섞여 있고 **그 차이가 대기 양상을 바꿀 수 있다**
- **2 물리코어다.** `sleep` 이라 영향이 작다고 봤지만 **0 이라고 확인한 것은 아니다**
- **`borrowed` 가 41 로 찍힌 표본이 있다**(80 레벨) — 상한이 40 인데 41 이다.
  샘플링과 반납 사이의 경합으로 보이지만 **안 팠다**
- **레벨당 6초 · 반복 없음** — 이 프로브는 「있나 없나」를 보는 것이라 산포를 안 쟀다.
  🔴 **판정용 수치로 인용하면 안 된다**
