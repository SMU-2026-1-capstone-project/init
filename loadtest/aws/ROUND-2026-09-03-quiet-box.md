## 3. 실행 순서 — 러너를 두 번 부른다

🔴 **`PHASES`에 `q2`와 `card_a`를 같이 넣으면 러너가 멈춘다.** `run_all.sh:139`가 라운드가 둘 이상
섞이면 `exit 1`을 낸다(결과 디렉터리 이름을 하나 고르면 나머지가 틀린 이름으로 박히기 때문).
`OUTDIR`을 직접 주면 우회되지만 **우회하지 않는다** — 저장소 관례대로 결과가 두 디렉터리로
갈리는 편이 맞다.

**전체 순서는 從 R3 시딩 → ② → ①이다.** R3 을 먼저 하는 이유는 `EXPLAIN` 이라
무대를 안 흔들고(판 ② 는 자체 테이블 `pq_t` 를 쓴다), ①의 5GB 시딩 **전에** 걷어야
`reports` 조인 플랜이 «리포트 rig 규모» 에서 나온 값이 되기 때문이다.
R3 의 `EXPLAIN` 자체는 판 ② 호출의 `ridealong` 단계에서 같이 돈다.

②를 ①보다 먼저 돌리는 이유: ①의 시딩이 `pose_data`에 5GB를 부으면 버퍼풀
온도와 디스크 상태가 바뀌는데, ②는 `DROP PARTITION` 소요를 ms 단위로 재는 판이라 그 영향을
받는다. **깨끗한 박스에서 ②를 먼저 걷는다.**

### 판 ② — 파티션 유의성 재검정 (약 47분)

```bash

Q2_N_BLOCKS=40 \
AUTO_SHUTDOWN=0 \
PHASES="preflight q2 ridealong collect" \
  bash loadtest/aws/run_all.sh
```

- 결과 디렉터리: `loadtest/results/q2-partition-quiet-box-aws-<날짜>/`
- rig: `loadtest/results/row-shape-frag-2026-08-24/run_q2_blocks.sh` → `q2_partition_rig.sh`
- 노브는 러너가 안 건드린다 — 드라이버 기본값이 `WARM_DROP=1`·`SETTLE_SEC=10`(R12 round3과 동일)
- 팔은 블록마다 교대(홀수 블록 C→H, 짝수 블록 H→C) = 라틴 방격
- 🔴 `AUTO_SHUTDOWN=0` — 판 ①이 남아 있으므로 박스를 끄면 안 된다

### 판 ① — 커버링 인덱스 처리량 (시딩 20~40분 + 본 측정 약 25분)

- 결과 디렉터리: `loadtest/results/card-a-write-cost-aws-<날짜>/`

- `card_a_seed`가 `card_a`보다 **먼저**다 — 무대 전제(버퍼풀 초과)가 시딩에 걸려 있다
- 🔴 `preflight`를 **두 번째 호출에는 안 넣는다** — 첫 호출에서 이미 통과했고, 이 단계는

- 이번 호출은 `AUTO_SHUTDOWN` 기본값(1)을 그대로 둔다 → 업로드 성공 시 스스로 terminate

### 판 ③ — 從 R3 · 3-way 조인 조인 알고리즘 (약 15분 + 시딩)

**무슨 실험인가.** 포폴 카드 ⑤(Ch.9 옵티마이저·힌트)는 2026-07-16에 **절반만** 닫혔다.
닫힌 절반은 «단일 테이블 선택도» — `session_id BETWEEN 1 AND N`의 N을 넓히며 `range`→`ALL`
전환점을 찾고(15,000~18,000세션), 행당 비용 역산(range 122.6μs vs 풀스캔 21.2μs, 5.8배)으로
**옵티마이저의 선택이 실측 비용 모델과 맞는다**는 것까지 확인했다.

안 닫힌 절반이 **조인 알고리즘**이다. MySQL 8.0.18+가 넣은 **hash join**을
`reports ⋈ exercise_sessions ⋈ users` 3-way에서 관찰하는 것인데, 카드가
**«그 테이블들이 AWS엔 비어 있어 별도 시딩 필요, 이번엔 범위 밖»** 으로 닫아뒀다.
그래서 러너도 지금 이것을 **스텁으로** 남긴다 — `phase_ridealong`이
`R3_hash_join.SKIPPED.txt`에 «미실행 — 시딩이 선행 조건»을 적는다.

**읽는 것**: `EXPLAIN FORMAT=TREE`(«Inner hash join» ↔ «Nested loop» 이 문자로 나온다) ·
`EXPLAIN ANALYZE`(실제 행수·시간).

🔴 **읽지 않는 것 — 이 rig으로는 원리적으로 못 읽는다.** 시딩이 단일 템플릿 복제라
값 분포가 균일하다. 카드 ⑤ 자신이 같은 이유로 generated column 실험을 **«미수행 결정»**
으로 박았고 *«⑤ 옵티마이저도 동일 제약»* 이라고 적어뒀다. 따라서 **옵티마이저 카디널리티
추정 정확도·선택도 기반 플랜 전환은 결론을 내지 않는다.** 남는 것은 **플랜 모양**이다.

🔴 **그리고 무대에 구조적 제약이 하나 더 있다.** `seed_report_rig.sh`는 세션 1,000개를
**member_id 3개(1·5·12)** 에 나눠 붙인다. 즉 `users` 쪽 유효 소유자가 **3명**이다 —
hash join 이 뽑히는 조건(«쓸 인덱스가 없는 equi-join»)이 자연히 안 서고, 옵티마이저는
3행 테이블에 `eq_ref` 나 nested-loop 를 고를 것이 거의 확실하다. **팔을 하나 정해야 한다**:

| 팔 | 무엇을 묻나 | 대가 |
|---|---|---|
| **㉠ 자연 선택 관찰** (추천) | «이 스키마·이 규모에서 옵티마이저가 실제로 무엇을 고르는가» | hash join 이 **안 나올 가능성이 높다.** 그 자체가 답이다 — 「우리 조인은 인덱스가 있어서 hash join 조건이 안 선다」 |
| **㉡-1 `IGNORE INDEX FOR JOIN`** | «쓸 인덱스가 없으면 hash join 으로 가는가» | 🟢 **로컬 확인됨 — `Inner hash join` 이 나온다.** 인덱스를 떼는 것과 달리 **스키마를 안 건드린다**(조인 컬럼 둘 다 FK 라 DROP INDEX 는 못 쓴다) |
| **㉡-2 ㉡-1 + `block_nested_loop=off`** | «hash join 을 끄면 무엇으로 가나» | 같은 조건에서 nested-loop 로 돌아간다. ㉡-1↔㉡-2 cost 차가 **hash join 의 값** 이다 |

**추천은 ㉠을 기본으로 걷고 ㉡을 1판 더 얹는 것** — 둘이 합쳐져야
「인덱스가 있으니 nested-loop, 떼면 hash join」이라는 **대조**가 된다. 판당 수 초짜리
`EXPLAIN`이라 ㉡을 얹는 비용이 사실상 0이다.

```bash
# 시딩 (판 ① 시딩 전에 — pose_data 5GB 를 붓기 전 상태에서 걷는다)
SESSIONS=1000 ROWS=750 bash loadtest/seed/seed_report_rig.sh
```

- 🔴 **`members` 행이 먼저 있어야 한다** — 시더가 `member_id` 1·5·12 를 **참조만** 한다
  (INSERT 하지 않는다). 없으면 FK 로 죽는다. 계정이 필요하면 `seed/seed_k6_read_account.sh`
- 🔴 **러너 스텁을 실제 쿼리로 교체해야 한다**(§4-ㄹ) — 지금 상태로 `ridealong` 을 돌리면
  R3 는 또 «SKIPPED» 파일만 남는다. **이번에도 안 고치면 세 번째 라운드를 그냥 지나간다**

## 4. 🔴 착수 전 선행 4건

### ㄱ. `run_all.sh` 헤더 주석이 이 라운드를 막는 방향으로 적혀 있다

`run_all.sh:57-58`이 이렇게 적고 있다:

> 🔴 **card_a·card_a_seed 는 이 라운드에 안 넣는다** — #205 쓰기 대가는 2026-08-22 에
> 이미 닫혔다(A÷B=1.245). 다시 돌려도 같은 답을 반복할 뿐이다

**이 문장은 절반만 맞다.** 카드 A가 닫은 것은 **논리 카운터**(`bp_write_req`)이고, 같은 문서
§3이 **「`ms`는 3.8배 잡음이라 못 쓴다 — 처리량은 여전히 미측정, 조용한 박스가 필요」**를
명시적으로 남겼다. 즉 "같은 답을 반복"은 **카운터 축에서만** 참이고, 이번 라운드가 묻는
처리량 축에서는 거짓이다. 이 주석을 그대로 두면 다음 운영자가 같은 자리에서 또 막힌다.
→ **주석 수정이 선행**(문서 드리프트, 사용자 confirm 후 반영).

### ㄴ. ~~p50·p99를 낼 배선이 없다~~ → 🟢 **배선 완료 · 로컬 검증 완료 (2026-09-03)**

`measure_205_card_a_write_cost.sh`에 꼬리 계기를 넣었다(+77/−15).

| 무엇 | 어떻게 |
|---|---|
| 채널 | `performance_schema` digest 통계 — **서버가 이미 세는 값**이라 측정 오버헤드가 판에 안 얹힌다 |
| p95 · p99 | `events_statements_summary_by_digest`의 `QUANTILE_95`·`QUANTILE_99` |
| p50 | `QUANTILE_50` 열이 없어서 `events_statements_histogram_by_digest` 누적으로 중앙값 버킷을 낸다 |
| 리셋 | 판마다 두 테이블을 `TRUNCATE` — 이 판의 문만 남긴다 |
| 필터 | `DIGEST_TEXT LIKE 'INSERT INTO \`pose_data\`%'` — 사이에 낀 rig 자신의 조회는 digest가 달라 안 섞인다 |
| 🔴 게이트 | **본 digest 문 수 ≠ `STMTS`면 중단.** 그러면 그 quantile은 다른 문 집합을 설명하는 값인데 표에는 멀쩡하게 실린다 |
| 계기 단언 | `@@performance_schema=1` · `statements_digest` 소비자 `YES` · `QUANTILE_95/99` 열 존재 — 하나라도 없으면 기동 시 중단(ibuf_merges의 「조용한 0」 재발 방지) |
| 열 확장 | 출력 필드 10 → **13개**(p50·p95·p99), 필드 수 단언도 같이 올렸다 |

**로컬 검증 (2026-09-03, MySQL 8.0.46)**
- 독립 프로브: 200문 → `COUNT_STAR=200` 정확히 일치, p95 398ms · p99 1000ms · 히스토그램 p50 79.4ms
- rig 스모크(`STMTS=30 ROWS=5`): 판마다 p50·p95·p99가 채워지고 뒷정리 잔여 0
- rig 스모크 6판(`ORDER="A B A B A B"`): A÷B 표에 꼬리 2행이 실렸다 — p50 **2.036** · p99 **2.360**.
  `raw.tsv` 전 행이 **13열**이고, 6판 전부 `p50 ≤ p95 ≤ p99`를 만족(내부 정합성 확인)
- 게이트 음성 테스트: 본 것이 `0`·빈 값·`29`일 때 **셋 다 중단**(통과는 `30=30`에서만)
- 🟢 **버킷 천장은 문제가 아니다** — 히스토그램이 450버킷이고 최상단이 `18,446,744,073ms`(약 213일)라
  포화가 원리적으로 안 온다. `performance_schema_digests_size=10000`이라 digest 축출 위험도 없다.
  남는 한계는 **천장이 아니라 버킷 간격(해상도)** 하나다
- ⚠️ 위 로컬 수치는 **인용 금지** — 백엔드·AI·Grafana가 같이 도는 박스에서 잰 값이고
  `pose_data`가 165MB(버퍼풀 미만)라 ①의 무대 전제 자체가 안 선다. **배선 검증 전용이다**

🔴 **인용 조건 — quantile은 히스토그램 버킷의 상한이다(보간 아님).** 버킷 경계가 로그 간격이라
p99가 「1000ms」처럼 딱 떨어져 보일 수 있다. 그건 「정확히 1초」가 아니라 「그 버킷 안」이라는
뜻이다. **팔 간 비교에는 쓰고, 절대값 인용에는 이 단서를 붙인다.** 결과 문서의 표가 이 문장을
자동으로 같이 찍는다.

<details><summary>배선 전 상태 (기록용)</summary>

설계 §3의 판정 지표는 **「RPS·p50·p99(ms)」**인데, rig이 실제로 내는 것은:

| 설계가 약속한 것 | rig이 내는 것 |
|---|---|
| RPS | 🟢 **있다** — `ms`·`rows`·`rows/s` 열 (`measure_205_card_a_write_cost.sh`) |
| p50 · p99 | 🔴 **없다** — 판 전체 wall-clock `ms` 하나뿐이다 |

판당 800문을 한 커넥션으로 밀어 넣고 시작·끝만 찍으므로 **문 단위 분포가 없다.**
「대가가 평균이 아니라 꼬리에 있다」는 것이 R8이 남긴 교훈인데(처리량 −2.9%인데 p99 +98%),
그 교훈을 이 판에 적용하려면 꼬리를 봐야 한다.

**추천 처방**: `performance_schema.events_statements_summary_by_digest`를 판마다 TRUNCATE →
판 끝에 `QUANTILE_95`·`QUANTILE_99` 읽기. MySQL 8.0에 있는 열이고, 문마다 시간을 재는

## 5. 게이트와 판정선 (실행 전에 박는다)

### ② 파티션 유의성

| | |
|---|---|
| 게이트 | rig 내장 행 수·페이지 수 게이트 — 무대가 안 서면 측정 전에 죽는다(R12 round1 무효 재발 방지) |
| 유효 판 | 드라이버가 `유효 판 N/80`을 찍는다. **절반 미만이면 「측정했다」로 부르지 않는다** |
| 판정 | 쌍차(H−C) **부호검정** + Wilcoxon 부호순위 정확검정 |
| p<0.05 · R12와 같은 방향 | **확정** — 「DROP 1.8초·625배」를 구멍 유무와 무관하게 인용 가능 |
| p<0.05 · 반대 방향 | 🔴 **결함 신호** — R12의 10/13이 우연이었다는 뜻. 이슈 등록 |
| 여전히 p>0.05 | 「자릿수로는 독립」을 최종 결론으로 굳히고, +13%는 **잡음 안**으로 정리 |

### ① 커버링 인덱스 처리량

| | |
|---|---|
| 전제 단언 | 데이터 크기 > 버퍼풀(2,048MB)을 `[0] 조건 확인`이 찍는다 — **안 넘으면 R8과 같은 「메모리 안의 대가」라 이 판은 무효** |
| 계기 단언 | `INNODB_METRICS.ibuf_*`가 `enabled`인지 rig이 기동 시 검사하고 아니면 중단(#271 「조용한 0」 재발 방지) |
| 필드 수 단언 | `run_round` 출력이 **13필드**(꼬리 3열 추가 후)가 아니면 중단 — 안내 문구가 섞여 열이 밀리는 결함을 막는다 |
| 판정 | 첫 판 버림 후 A·B 각 3~4판의 **`ms` 중앙값 비**와 **rows/s** |
| 🔑 꼬리 판정 | **문당 p99 중앙값의 A÷B.** R8이 「처리량 −2.9%인데 p99 +98%」를 냈으므로 평균과 꼬리가 갈릴 수 있다 — 둘 다 표에 낸다 |
| 꼬리 게이트 | 판마다 **digest 문 수 = `STMTS`(800)** 를 단언한다. 안 맞으면 그 판에서 중단 |
| 🔴 산포 확인 | 팔 안 산포가 팔 간 차이보다 크면 **판 수를 13블록 이상으로 늘린다**(§1 결정) |
| 재확인 | `bp_write_req` A÷B가 **1.245 근처**로 재현되는지 — 아니면 무대가 카드 A와 다른 것이다 |
